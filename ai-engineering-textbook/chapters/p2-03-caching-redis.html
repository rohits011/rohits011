Caching Strategies & Redis Internals

A cache is the cheapest capacity you will ever buy and the most expensive bug you will ever debug. This chapter covers both halves: the strategy (which layer, which pattern, how to invalidate, how to survive stampedes, hot keys, penetration and avalanches) and the machine (how Redis actually stores, expires, evicts, persists, replicates and shards your data), so that your @Cacheable annotations are backed by an engineering argument rather than hope.

  • Prerequisites: Chapter 1 (latency numbers, percentiles), Chapter 2 (stateless services, Redis + Lua). You have used Spring's @Cacheable and Spring Data Redis.
  • You will be able to: pick the right caching layer and pattern for a workload; reason about consistency between cache and database including race conditions; prevent stampedes with locking, coalescing and probabilistic early expiration; handle hot keys, penetration and avalanches; choose eviction policies from workload shape; build a Caffeine + Redis two-level cache in Spring with cross-instance invalidation; and explain Redis's threading model, encodings, persistence, replication, Sentinel and Cluster at interview depth.

1. Introduction: Why Caching Is a Design Decision, Not an Annotation

Caching exploits a simple asymmetry: data is read far more often than it changes, and reading it from somewhere close and fast is orders of magnitude cheaper than recomputing or refetching it. From Chapter 1's latency table: a local memory read costs ~100 ns, a Redis round trip in the same zone ~0.3–1 ms, an indexed Postgres query 1–5 ms, a cross-region call ~70 ms, an LLM completion seconds. Every layer you can short-circuit saves the cost of every layer behind it, and also protects those layers from load. In many production systems the database survives only because 95–99% of reads never reach it.

That protection is precisely what makes caches dangerous. Once a system depends on a 98% hit ratio, the cache is no longer an optimisation; it is load-bearing. A cache restart, a mass expiry, a deploy that changes key formats, or a single viral key can expose the database to 50x its normal read load in seconds. And because a cache is a second copy of data, every write raises the question of how and when the copy is corrected, which is where most caching bugs live.

This chapter is in two halves. The first covers caching as architecture: layers, read and write patterns, invalidation, consistency, and the failure modes (stampede, hot keys, penetration, avalanche) together with their standard mitigations, ending in Spring's cache abstraction and a two-level Caffeine + Redis design. The second half opens Redis: its threading model, internal encodings, expiry and eviction algorithms, persistence, replication, Sentinel, Cluster, scripting, transactions, pub/sub versus streams, and the 2024 licensing change that produced the Valkey fork.

Why that is not enough
The abstraction hides the decisions that matter: what happens on a concurrent miss (100 threads all loading the same key), what happens when a write and a read race around an eviction, how stale is acceptable, whether the cache is per-instance or shared, what the eviction policy does on your access distribution, and how Redis behaves under memory pressure, failover, or resharding. These are the questions asked in design reviews and interviews, and the ones that cause incidents.
The modern approach
Cache deliberately per data type with explicit staleness budgets; use cache-aside with delete-on-write as the default; protect against stampedes (single-flight loading, early refresh, jittered TTLs); combine a small in-process Caffeine L1 for the hottest keys with a shared Redis/Valkey L2; invalidate from change data capture or events when correctness matters; size and monitor hit ratio, evictions and memory; and treat Redis as a distributed system with its own replication and failure semantics.
Where Python and Go fit
Go's golang.org/x/sync/singleflight is the canonical request-coalescing primitive and go-redis a widely used client; Python's redis-py (with asyncio support) and functools.lru_cache/cachetools cover the same ground. The patterns are language-independent; §7 shows all three.
In production
CDN for static and cacheable API responses; Caffeine in each Spring Boot pod; managed Redis or Valkey (ElastiCache, Memorystore, Azure Cache, or self-hosted with Sentinel/Cluster) as a shared tier; invalidation via Kafka/CDC; dashboards for hit ratio, latency, evictions, memory fragmentation and replication lag.
Use it when / avoid it when
Cache when reads dominate writes, the data tolerates bounded staleness, and recomputation or refetching is expensive. Avoid (or bypass) caching for data that must be strongly consistent per read (balances, inventory at checkout), data with no reuse (unique per request), and as a substitute for fixing an inefficient query you could index.

2. History: From CPU Caches to Valkey

Caching is as old as computing: CPU caches (the IBM System/360 Model 85 in 1968 is usually cited as the first commercial machine with a cache), operating-system page caches, and database buffer pools all predate the web. Laszlo Belady's 1966 paper described the optimal (clairvoyant) replacement policy that every practical eviction algorithm approximates.

2.1 Web caches and CDNs (1990s)

HTTP/1.1 (RFC 2068 in 1997, then RFC 2616 in 1999) introduced Cache-Control, ETag and conditional requests, which still govern browser and CDN caching (now specified in RFC 9111, 2022). Akamai, founded in 1998, commercialised content delivery networks: geographically distributed caches that move content close to users.

2.2 Memcached and the cache-aside era (2003–2013)

Brad Fitzpatrick wrote memcached in 2003 for LiveJournal: a simple, multi-threaded, in-memory key-value store with LRU eviction, sharded by clients using hashing. It defined the cache-aside pattern for a generation of web applications and was adopted at enormous scale; Facebook's 2013 NSDI paper Scaling Memcache at Facebook remains the best public account of operating cache-aside across regions, including leases to prevent stampedes and stale sets.

2.3 Redis (2009–2023)

Salvatore Sanfilippo released Redis in 2009: an in-memory data structure server with lists, sets, sorted sets and hashes, optional persistence and replication. Milestones relevant to this chapter: Redis Sentinel for high availability (stable in 2.8, 2013); Redis Cluster with 16,384 hash slots (3.0, 2015); modules and LFU eviction (4.0, 2017); Streams (5.0, 2018); ACLs, TLS and threaded I/O (6.0, 2020); Redis Functions, multi-part AOF and listpack replacing ziplist everywhere (7.0, 2022).

2.4 Licensing change, Valkey and Redis 8 (2024–present)

In March 2024 Redis Ltd. moved Redis from the BSD-3-Clause license to a dual source-available license (RSALv2 and SSPLv1) starting with 7.4; 7.2.4 was the last BSD-licensed release. Within weeks, a group of former contributors and cloud vendors forked 7.2.4 under the Linux Foundation as Valkey, keeping the BSD license. Valkey 8.0 (2024) substantially reworked I/O threading, and Valkey 9.0 (GA October 2025) added features such as atomic slot migration, hash field expiration and multiple databases in cluster mode. Major cloud providers now offer managed Valkey (for example, Amazon ElastiCache announced Valkey 9.0 support in May 2026). In May 2025, Redis 8 added the OSI-approved AGPLv3 as a third licensing option alongside RSALv2 and SSPLv1, and folded the previous Redis Stack modules (JSON, search, time series, probabilistic) and a new vector set type into the core distribution; Redis 8.4 (November 2025) and later releases continued that line. 2.5 JVM caches

Ehcache (2003) and Guava's cache (2011) dominated in-process JVM caching until Ben Manes's Caffeine (first released around 2015), whose Window TinyLFU admission policy delivers near-optimal hit ratios. Spring's cache abstraction (Spring 3.1, 2011) made swapping providers a configuration change; Spring Boot auto-configures Caffeine and Redis cache managers.

3. Fundamentals of Caching

3.1 Hit ratio, locality and what makes data cacheable

A cache is worthwhile when the hit ratio (fraction of lookups served from cache) is high enough that the saved cost exceeds the cache's own cost and the consistency risk it introduces. Hit ratio depends on temporal locality (recently used items are likely to be used again), popularity skew (a small fraction of items receives most requests; real workloads are often approximately Zipf-distributed), the cache size relative to the working set, the TTL relative to the re-access interval, and the eviction policy.

Data is cacheable when it is read much more often than written, when staleness is tolerable for some bounded time, when it is expensive to produce, and when the same value is requested by many requests (shared) or repeatedly by the same user (per-user, cached closer to them). Personalised responses, rapidly changing counters and one-off queries are poor candidates. A good design review question: "what is the staleness budget for this data, and who decided it?"

3.2 The caching layers

Requests pass through several potential caches. Each layer has different scope, latency, capacity and invalidation characteristics.

  • Client cache (browser HTTP cache, mobile app storage, SDK memoisation). Controlled by Cache-Control (max-age, no-cache, private, stale-while-revalidate) and validators (ETag/If-None-Match returning 304). Zero network cost on a hit, but you cannot reliably invalidate it: once a response is cached on a device with max-age=3600, it will be used for an hour. Use content-hashed URLs for static assets so new versions get new URLs.
  • CDN / edge cache. Shared across users in a region, close to them. Excellent for static assets, media and public API responses (product catalogue, public profiles). Supports purge APIs and surrogate keys (tag-based purge) for invalidation. Keys must include everything that varies the response (Vary headers, query parameters, locale); getting this wrong serves one user's content to another.
  • Gateway / reverse-proxy cache (NGINX proxy_cache, Varnish, Envoy cache filter). Inside your network, shared by all clients; useful for expensive, shared, read-heavy endpoints, and for micro-caching (caching for one or a few seconds) to absorb spikes.
  • Application in-process cache (Caffeine, Guava, a ConcurrentHashMap). Nanosecond-to-microsecond access, no serialisation, no network. Limited by heap size and duplicated in every instance; each instance has its own copy, so invalidation across instances needs a broadcast, and hit ratio per instance is lower than a shared cache when traffic is spread across many instances.
  • Distributed cache (Redis, Valkey, Memcached, Hazelcast). Shared by all instances, so one fill serves everyone; scales by sharding; survives application deploys. Costs a network round trip and serialisation, and is itself a system to operate.
  • Database caches: the buffer pool (PostgreSQL shared_buffers plus the OS page cache; InnoDB buffer pool) caches pages; plan caches and materialised views cache computation. They are automatic and always consistent, which is why adding RAM to a database is often the simplest "cache". MySQL's old query cache was removed in 8.0 precisely because invalidating it on every write to a table scaled poorly.

3.3 Read and write patterns

Cache-aside (lazy loading). The application checks the cache; on a miss it reads the database and populates the cache; on a write it updates the database and then deletes (invalidates) the cache entry. The cache is a passive store. This is the default for Redis and what Spring's @Cacheable/@CacheEvict implement. Strengths: only requested data is cached; a cache outage degrades to database reads rather than failure; simple. Weaknesses: every miss costs three steps; stale data is possible in races (§3.5); a cold cache sends all traffic to the database.

Read-through. The application asks the cache, and the cache itself loads from the data source on a miss using a configured loader. Caffeine's LoadingCache is read-through; so are some managed caching proxies. The application code is simpler and loading can be coalesced inside the cache. The cache must know how to reach the data source.

Write-through. Writes go to the cache, which synchronously writes to the data source before acknowledging. The cache is always populated with fresh data for written keys. Costs write latency (two writes per write) and caches data that may never be read. Useful when reads immediately follow writes.

Write-behind (write-back). Writes go to the cache and are acknowledged immediately; the cache flushes to the data source asynchronously, often batched and coalesced (ten updates to a counter become one database write). Very low write latency and reduced database load, at the cost of durability risk (writes in the cache are lost if it fails before flushing) and eventual consistency for anyone reading the database directly. Suitable for counters, analytics, view counts, rate-limit state; dangerous for orders and payments.

Refresh-ahead. The cache proactively reloads entries that are about to expire if they are still being accessed, so popular keys never experience a miss. Caffeine's refreshAfterWrite does this: after the refresh interval, the next read returns the current (slightly stale) value immediately and triggers an asynchronous reload. Reduces latency spikes and stampedes on hot keys; wastes work if the prediction is wrong.

3.4 Invalidation and TTLs

There are three ways to keep a cache acceptably fresh:

  • Time-based expiry (TTL). Every entry expires after a fixed time. Simple, self-healing (any inconsistency disappears within one TTL), but a trade-off: a short TTL means more misses; a long TTL means more staleness. Pick the TTL from the staleness budget, not from the hit ratio you would like.
  • Explicit invalidation on write. The writer deletes or updates the cache entry after changing the source of truth. Fresh data quickly, but every write path must remember to invalidate (including batch jobs, admin tools and manual SQL), and multi-key dependencies (a product change affects category pages, search results, recommendation lists) are hard to enumerate.
  • Event-driven / CDC invalidation. A change-data-capture stream (Debezium reading the database's WAL/binlog, or the database's own CDC) publishes every committed change; a consumer invalidates or updates affected cache keys. Catches all writers, including those that bypass the application, and orders invalidations by commit order. This is how Facebook (via its commit log), Uber's CacheFront and many others keep large caches consistent.

Combine them: explicit or CDC invalidation for freshness, plus a TTL as a safety net so that a missed invalidation heals eventually. Prefer delete over update on write: deleting is idempotent and avoids writing a value computed from a possibly stale read; the next reader repopulates from the source of truth.

3.5 Consistency: the races you must know

A cache plus a database is a tiny distributed system without transactions spanning both, so interleavings matter. Two classic races under cache-aside:

  • Stale set after delete. Reader R misses and reads value v1 from the database. Writer W updates the database to v2 and deletes the cache key. R, delayed (GC pause, slow network), now writes v1 into the cache. The cache holds stale v1 until TTL expiry, indefinitely if there is no TTL.
  • Update-cache-then-DB ordering. If a writer updates the cache before the database and the database write fails or a concurrent writer interleaves, the cache can hold a value that never committed.

Mitigations: always write the database first, then delete the cache; keep TTLs as a backstop; use leases or versioned sets (the cache issues a token on a miss, and a later set is accepted only if no delete happened in between; Facebook's memcache leases work this way); use delayed double delete (delete, and delete again after a short delay longer than a typical read-populate cycle) as a pragmatic approximation; or set values with a version and use a compare-and-set in Lua that only accepts newer versions. For data that must be linearizable, do not serve it from a cache at all.

3.6 Stampede (thundering herd / dog-piling)

When a popular key expires or is evicted, every concurrent request misses at the same moment and all of them go to the database to recompute the same value. For a key read 5,000 times per second whose recomputation takes 200 ms, about 1,000 identical queries hit the database before the first one repopulates the cache (Little's Law again). If the recomputation is expensive, the database slows, recomputation takes longer, and more requests pile up. Three defences:

  • Locking / single-flight. Only one caller recomputes; others wait for its result or serve stale. In-process: Caffeine's LoadingCache and @Cacheable(sync = true) ensure one load per key per JVM; Go's singleflight does the same. Across instances: a short Redis lock (SET lock:key token NX PX 5000); losers either wait briefly and re-read or serve a stale copy.
  • Request coalescing at the proxy. NGINX proxy_cache_lock and CDN "collapsed forwarding" send one request to the origin and make the others wait for its response.
  • Probabilistic early expiration (also called XFetch, from Vattani, Chierichetti and Lowenstein, VLDB 2015). Each reader, before the actual expiry, decides randomly whether to recompute early, with probability rising as expiry approaches and with how long recomputation takes (§6.4). One reader almost always refreshes a little before expiry, so the herd never forms, with no locks. Serving stale while revalidating (soft TTL plus hard TTL) has a similar effect.

3.7 Hot keys

In a sharded cache, a single key lives on one shard. If one key (a celebrity's profile, a flash-sale product, a global config) receives a large fraction of traffic, its shard saturates (CPU or network) while others idle, and adding shards does not help. Mitigations: an in-process L1 cache in front of Redis for the hottest keys (often the single most effective fix, since it removes network traffic entirely); key replication (store product:42#0 … product:42#7 on different shards and have readers pick one at random; writers update or delete all copies); reading from replicas for hot read-only keys; and detection (Redis --hotkeys scanning with LFU policy, client-side sampling, proxy metrics). Writes to a hot key (a global counter) are a different problem: shard the counter into N sub-counters and sum on read.

3.8 Penetration, breakdown and avalanche

Three failure modes are often grouped together, especially in Chinese-language engineering literature where the terms originated:

  • Cache penetration: requests for keys that do not exist in the database (random IDs from a scraper or attacker, or a bug) always miss the cache and always hit the database. Fixes: negative caching (cache "not found" with a short TTL, e.g. 30–60 s); a Bloom filter of all valid IDs checked before the cache (a "definitely not present" answer skips both cache and database; Redis 8 and Valkey both offer Bloom filters, or keep one in memory); input validation and rate limiting.
  • Cache breakdown: a single hot key expires and the stampede of §3.6 follows. Fixes: as in §3.6, plus never expiring the hottest keys and refreshing them proactively.
  • Cache avalanche: many keys expire at once (all loaded at startup with the same TTL, or a bulk import), or the whole cache becomes unavailable (node failure, flush, restart), so the database receives a large fraction of all reads simultaneously. Fixes: TTL jitter (TTL = base ± random 10–20%); highly available cache tiers (replicas, Cluster); circuit breakers and load shedding in front of the database; gradual warm-up (pre-populate the hottest keys before taking traffic); and capacity planning that knows what the database can serve with a cold cache.

3.9 Eviction policies

When the cache is full, the eviction policy decides what to remove. Belady's optimal policy evicts the item whose next use is furthest in the future; real policies estimate that from history.

  • FIFO: evict the oldest inserted. Simple, scan-resistant in a weak sense, ignores popularity. Surprisingly competitive in some recent research variants (e.g. S3-FIFO) that add small probationary queues.
  • LRU (least recently used): evict the item accessed longest ago. Captures recency; implemented with a hash map plus doubly linked list (Java's LinkedHashMap with access order). Vulnerable to scans: a one-off pass over many items (a report job) flushes the hot set.
  • LFU (least frequently used): evict the item with the lowest access count. Captures popularity, resists scans, but must age counts or yesterday's hits keep stale items forever, and new items start with low counts and are evicted before they can prove themselves.
  • TinyLFU and W-TinyLFU (Caffeine): a compact frequency sketch (count-min sketch with periodic halving) acts as an admission filter: a new item replaces the eviction candidate only if it is estimated to be more frequent. A small LRU "window" admits new items so recency bursts still work. Achieves near-optimal hit ratios across many workloads.
  • ARC / 2Q / SLRU: split the cache into recency and frequency segments and adapt their sizes; widely used in databases and file systems.
  • Random: evict a random item. No metadata; within a few percent of LRU on many workloads with large caches.
  • TTL-based (Redis volatile-ttl): evict the key with the nearest expiry first.

Redis implements approximations of LRU and LFU by sampling (§4.4), with policies noeviction, allkeys-lru, allkeys-lfu, allkeys-random, volatile-lru, volatile-lfu, volatile-random and volatile-ttl (the volatile-* ones only evict keys that have a TTL). Use the widget in §5 to compare policies on a Zipf workload.

3.10 Spring's cache abstraction and two-level caching

Spring's abstraction intercepts annotated methods via AOP: @Cacheable returns the cached value or invokes and caches; @CachePut always invokes and updates; @CacheEvict removes (optionally allEntries or beforeInvocation); @Caching combines them. Keys are SpEL expressions (key = "#id"), with condition and unless to control what is cached (e.g. unless = "#result == null", which disables negative caching, often not what you want against penetration). sync = true makes concurrent misses for the same key in one JVM wait for a single load. Because it is proxy-based, self-invocation (calling a @Cacheable method from the same bean) bypasses the cache, and @CacheEvict on a method in a transaction runs when the method returns, possibly before the transaction commits; use TransactionAwareCacheManagerProxy or evict in an @TransactionalEventListener(phase = AFTER_COMMIT) to avoid repopulating from uncommitted state.

A two-level cache puts a small, short-TTL Caffeine cache (L1) in each instance in front of a shared Redis cache (L2). Reads try L1 (nanoseconds), then L2 (sub-millisecond), then the database. L1 absorbs hot keys and removes most network traffic; L2 provides a shared, larger, deploy-surviving tier. The cost is a new consistency problem: when a value changes, every instance's L1 must be invalidated. The standard solution publishes invalidation messages (Redis pub/sub, Kafka, or Redis client-side caching's tracking invalidations) that each instance subscribes to, with a short L1 TTL (seconds) as a backstop for lost messages. §7 builds this in Spring.

4. Redis Internals

Redis (and Valkey) is worth understanding at the level of its implementation because most of its operational behaviour (latency spikes, memory surprises, failover data loss, Cluster errors) follows directly from a handful of design choices.

4.1 The event loop and I/O threads

Redis executes commands on a single main thread running an event loop (its own small library, ae, over epoll/kqueue). The loop waits for readable sockets, reads and parses commands, executes each one to completion against in-memory data structures, buffers replies, and writes them back. Because only one thread touches the data, there are no locks, every command is atomic, and the execution of a command is extremely fast (most are O(1) or O(log n) on in-memory structures, taking microseconds). The consequence is equally direct: one slow command blocks everybody. KEYS * on a large database, HGETALL on a million-field hash, SMEMBERS on a huge set, DEL on a huge key, a long Lua script, or a large SORT stalls every other client of that node for its duration. Use SCAN/HSCAN/SSCAN iteration, UNLINK (asynchronous freeing) instead of DEL for large keys, and watch the slow log.

For years network I/O (reading sockets, parsing, writing replies) was also on the main thread and became the bottleneck before CPU for command execution did. Redis 6.0 added optional I/O threads (io-threads) that parallelise socket reads/writes and protocol parsing while command execution stays single-threaded. Valkey 8.0 redesigned this into an asynchronous model where the main thread hands I/O jobs to I/O threads, with reported throughput improvements on many-core machines, and Redis 8 also reworked its threaded I/O Version-sensitive · checked Nov 2026. Background threads (bio) handle lazy freeing, AOF fsync and file closing. Persistence snapshots and AOF rewrites use a fork()ed child process (§4.5).

Practical implications: a single Redis process scales to on the order of 100k+ simple operations per second on one core, more with pipelining and I/O threads; to use many cores you run multiple shards (Cluster) rather than one big instance; and latency is excellent until something blocks the loop.

4.2 Data structures and their encodings

Every value is a redisObject with a type (string, list, hash, set, sorted set, stream, plus module types) and an encoding that Redis chooses and changes transparently to save memory. Small collections use compact, cache-friendly, sequential encodings; once they exceed thresholds they convert to pointer-based structures with better asymptotic complexity. Lookup in a listpack is O(n), which is fine for 128 small entries because a linear scan of contiguous memory is fast; beyond that the conversion to a hash table or skiplist kicks in.
  • intset: a sorted array of integers using the smallest width (16, 32 or 64 bits) that fits all members, upgraded when a larger value is inserted; membership by binary search.

  • skiplist: the sorted-set structure. A probabilistic multi-level linked list where each node is promoted to the next level with probability 1/4 (max 32 levels), giving O(log n) expected insert, delete and rank/range operations; each node also stores span counts so ZRANK is O(log n). A companion hash table maps member to score for O(1) ZSCORE. Redis chose a skiplist over a balanced tree for simpler code and natural range iteration.
  • hashtable (dict): chained hash table with incremental rehashing: when it grows, Redis keeps two tables and migrates a few buckets on each operation (and in the background cron), so resizing never blocks for long. Tip: the small-hash memory trick

Storing millions of tiny objects as individual keys costs per-key overhead (the key's SDS, the redisObject, the dictionary entry, and expiry entry if any; often 50–100 bytes before the value). Bucketing them into hashes that stay within the listpack thresholds (e.g. user:1234 → hash users:12, field 34) can reduce memory several-fold. The trade-off: per-field TTLs require hash field expiration (available in Redis 7.4+ and Valkey 9.0+), and the bucket hash becomes the unit of cluster placement.

4.3 Expiry: lazy plus active

Keys with a TTL are recorded in a separate expires dictionary (key → absolute expiry time in milliseconds). Expiry is enforced two ways. Lazy: every access checks whether the key has expired and deletes it if so, so an expired key is never returned. Active: a periodic cycle (driven by hz, default 10 times per second) samples random keys with TTLs from each database, deletes the expired ones, and repeats while more than a threshold fraction of the sample was expired, bounded by a time budget so it never hogs the loop. Consequence: expired keys that are never accessed are removed gradually and probabilistically, so memory used by expired-but-not-yet-collected keys can be noticeable after mass expiry. Replicas do not expire keys independently; they wait for the primary to send DEL (while hiding logically expired keys from reads), so all replicas converge.

4.4 Memory management and approximated LRU/LFU

Redis allocates with jemalloc by default. maxmemory caps the dataset; when a write would exceed it, the maxmemory-policy decides: noeviction returns errors for writes (right for a primary datastore or a rate-limit store), the others evict (§3.9). Memory fragmentation (mem_fragmentation_ratio in INFO memory = RSS / used memory) grows when many values of varying sizes are created and freed; activedefrag yes enables online defragmentation with jemalloc.

True LRU would need a linked list touched on every access, costing memory and CPU. Redis instead stores a 24-bit clock value in each object (the lru field) and, when it must evict, samples maxmemory-samples keys (default 5), adds them to a small eviction pool of the best candidates seen so far (16 entries) sorted by idle time, and evicts the best candidate. Larger samples approach true LRU at more CPU cost; with 10 samples the approximation is very close.

For LFU (Redis 4.0+), the same 24 bits are split into a 16-bit last-decrement time (minutes) and an 8-bit logarithmic counter. The counter is a Morris-style probabilistic counter: on access it increments with probability \(1 / ((\text{counter} - 5) \times \text{lfu-log-factor} + 1)\), so it can represent millions of hits in 8 bits (with the default factor of 10, reaching the maximum of 255 takes on the order of a million accesses). New keys start at 5 so they are not instantly evicted. The counter is decremented over time according to lfu-decay-time (minutes per decrement), so popularity ages. Eviction then samples and evicts the lowest counter. With an LFU policy, redis-cli --hotkeys can report the most frequently accessed keys.

4.5 Persistence: RDB, AOF and hybrid

RDB snapshots. On BGSAVE (or save rules such as "after 3600 s if at least 1 change"), Redis calls fork(). The child process inherits a copy-on-write view of memory and writes a compact binary snapshot to disk while the parent keeps serving. Pages the parent modifies during the snapshot are copied by the kernel, so peak memory can approach double the dataset under heavy writes (plan memory headroom and disable transparent huge pages, which inflate the copy granularity from 4 KB to 2 MB). fork() itself must copy page tables, which can stall the main thread for tens to hundreds of milliseconds on very large instances; this is a classic source of periodic latency spikes. RDB loses everything since the last snapshot on a crash.

AOF (append-only file). Every write command is appended to a log. appendfsync controls durability: always (fsync every write: safest, slowest), everysec (fsync once per second in a background thread: lose up to about a second, the usual choice), no (let the OS decide). The log grows unboundedly, so Redis periodically rewrites it (again via fork) into the minimal set of commands that recreate the current state. Since Redis 7.0 AOF is multi-part: a base file plus incremental files tracked by a manifest, which avoids the old double-buffering of writes during rewrite.

Hybrid. With aof-use-rdb-preamble yes (the default), the AOF base file is written in RDB format and followed by AOF increments, combining fast restarts with fine-grained durability. For a pure cache, persistence is often disabled entirely (and replicas provide availability); for a datastore, enable AOF everysec plus periodic RDB for backups.

Redis is not a durable database by default

Even with AOF everysec, a primary crash loses up to about one second of acknowledged writes, and asynchronous replication means a failover can lose more (§4.6). If losing acknowledged writes is unacceptable, use a database with synchronous replication, or use WAIT/WAITAOF to block until replicas or local AOF have the write, understanding that this is still not a consensus protocol.

4.6 Replication

Replication is asynchronous primary → replica. A replica connects and sends PSYNC replid offset. Each primary has a replication ID and a monotonically increasing byte offset into its replication stream, and keeps a circular replication backlog buffer (repl-backlog-size, default 1 MB; usually far too small for busy primaries). If the replica's offset is still within the backlog, it receives only the missing bytes (partial resync). Otherwise it requires a full resync: the primary forks, produces an RDB (to disk or streamed directly over the socket with repl-diskless-sync), sends it, then streams buffered commands. Full resyncs of large datasets are expensive (fork, bandwidth, replica load time), so size the backlog to cover realistic disconnections: backlog ≥ write throughput × outage duration.

Because acknowledgement to the client happens before replicas receive the write, a primary failure can lose writes that clients saw succeed. WAIT numreplicas timeout blocks the client until N replicas acknowledge the offset, narrowing but not closing the window. min-replicas-to-write / min-replicas-max-lag make a primary refuse writes when it cannot see enough up-to-date replicas, bounding how much a partitioned old primary can accept (a split-brain mitigation). Replicas are read-only by default and can serve stale reads.

4.7 Sentinel

Redis Sentinel provides high availability for non-clustered deployments. A set of Sentinel processes (at least three, on separate failure domains) monitor a primary and its replicas. When a Sentinel cannot reach the primary for down-after-milliseconds, it marks it subjectively down; when a quorum of Sentinels agree, it is objectively down. The Sentinels then elect a leader among themselves (a Raft-like election by epoch), and the leader promotes the best replica (by priority, replication offset, then run ID), reconfigures the other replicas to follow it, and publishes the new primary address. Clients ask Sentinels for the current primary (Lettuce and Jedis support this natively; Spring Boot via spring.data.redis.sentinel.*). Sentinel cannot prevent loss of asynchronously replicated writes during failover.

4.8 Redis Cluster

Redis Cluster shards data across multiple primaries, each with replicas, without a proxy. The keyspace is divided into 16,384 hash slots; a key's slot is CRC16(key) mod 16384. If the key contains a hash tag ({...}), only the substring inside the first braces is hashed, so cart:{user42} and orders:{user42} land in the same slot, enabling multi-key commands, transactions and scripts across them. Each primary owns a set of slots. Nodes exchange state over a cluster bus (a separate TCP port) using a gossip protocol: heartbeats carry each node's view of slot ownership and node health; nodes flag peers as PFAIL (possibly failed) and, when a majority of primaries agree, as FAIL, triggering replica promotion by an election among the failed primary's replicas, approved by a majority of primaries using a configuration epoch.

Clients are cluster-aware: they fetch the slot map (CLUSTER SHARDS, or CLUSTER SLOTS in older versions), compute the slot locally and send each command directly to the owning node. If the map is stale, the node replies with a redirect:

  • -MOVED 3999 10.0.0.12:6379: slot 3999 permanently lives elsewhere now. The client updates its slot map and retries there.
  • -ASK 3999 10.0.0.12:6379: slot 3999 is being migrated and this particular key has already moved. The client sends ASKING followed by the command to the target node, once, without updating its map (other keys of that slot may still be on the source).

Resharding moves slots between nodes: the slot is marked MIGRATING on the source and IMPORTING on the target, keys are moved in batches with MIGRATE (atomic per key, blocking for large keys), and finally slot ownership is reassigned. Recent versions introduced atomic slot migration (Valkey 9.0; Redis 8.4's CLUSTER MIGRATION) that moves a whole slot's data using replication-style streaming and switches ownership atomically, avoiding the per-key ASK dance Version-sensitive · checked Nov 2026. Limitations of Cluster: multi-key operations only within a slot; one database (DB 0) historically (Valkey 9.0 added multiple databases in cluster mode); asynchronous replication means acknowledged writes can be lost on failover; and a minority partition stops accepting writes after cluster-node-timeout.

4.9 Scripting with Lua and Functions

EVAL/EVALSHA run a Lua script atomically on the main thread (Chapter 2 used this for rate limiting). Scripts must declare the keys they touch in KEYS (required for Cluster routing). Since 7.0, Redis Functions (FUNCTION LOAD, FCALL) let you load named libraries that are persisted and replicated like data, rather than relying on each client to send script bodies or cached SHAs. Keep scripts short; busy-reply-threshold (formerly lua-time-limit, default 5 s) only makes the server start answering BUSY to others; it does not stop the script.

4.10 Pipelining and transactions

Pipelining sends many commands without waiting for each reply, then reads all replies. It removes per-command round-trip latency (100 commands become one RTT instead of 100) and reduces syscalls; it provides no atomicity, since other clients' commands may interleave. Lettuce pipelines automatically because it is asynchronous and multiplexes many in-flight commands on one connection.

Transactions: MULTI starts queuing commands; EXEC executes them all sequentially with no interleaving. There is no rollback: if a command fails at runtime (e.g. wrong type), the others still execute. WATCH key before MULTI gives optimistic concurrency: if a watched key is modified by anyone before EXEC, EXEC returns null and nothing runs, and the client retries. For read-modify-write logic, a Lua script is usually simpler and faster than WATCH loops.

4.11 Pub/Sub versus Streams

Pub/Sub is fire-and-forget fan-out: messages published to a channel are pushed to currently connected subscribers and then forgotten. A subscriber that is disconnected, slow (its output buffer exceeds client-output-buffer-limit pubsub, after which it is disconnected) or not yet started misses messages. In Cluster, classic pub/sub broadcasts every message to every node; sharded pub/sub (7.0+, SPUBLISH/SSUBSCRIBE) routes channels by slot instead. Good for cache invalidation broadcasts (where a missed message is backstopped by TTL) and ephemeral notifications.

Streams (5.0+) are an append-only log data type: entries with IDs (millisecondsTime-sequence) stored in a radix tree of listpacks. Consumers read by ID (XREAD), can block for new entries, and consumer groups (XREADGROUP) distribute entries among consumers with per-consumer pending entries lists, explicit acknowledgement (XACK), and reclaiming of stuck messages (XAUTOCLAIM). Streams are persistent (subject to Redis persistence) and replayable, with length caps (XADD ... MAXLEN ~ 1000000). They are a lightweight alternative to Kafka for modest volumes within one Redis node's memory; Chapter 7 compares them properly.

4.12 Client-side caching (tracking)

Redis 6 added server-assisted client-side caching: with CLIENT TRACKING ON, the server remembers which keys a client has read and sends it invalidation messages (over RESP3 push or a redirect connection) when those keys change. This lets a client maintain an L1 cache that is invalidated precisely by the server, which is exactly the two-level design of §3.10 with the invalidation plumbing built in. Lettuce supports it via its client-side caching API; adoption in Spring abstractions is limited, so many teams still use explicit pub/sub invalidation.

5. Architecture

Reading the diagram: each layer is closer to the user (faster, cheaper per hit) but harder to invalidate than the one behind it. The database buffer pool is always consistent; Redis can be invalidated precisely; per-pod Caffeine caches require a broadcast; CDN entries require a purge API; browser caches cannot be invalidated at all once served. The dotted path shows the robust invalidation design: the database's change stream, not application code, drives invalidation, so every writer (including batch jobs and manual fixes) triggers it. Choose for each data type the outermost layer whose invalidation characteristics match its staleness budget.

Reading the diagram: the writer did everything right (database first, then delete), yet the cache ends up stale because a slow reader's SET landed after the delete. The window is small but at high traffic it happens. A TTL bounds the damage; leases or version-checked sets eliminate it: on a miss, the reader obtains a token (or reads the row version); the delete invalidates outstanding tokens; the reader's later SET is rejected if its token is invalid or its version is older than the cached one.

What to try: start with a cache of about 10% of the key space and a strongly skewed (high exponent) Zipf distribution: all policies do well because a few keys dominate, and LFU edges ahead because it protects the most popular keys. Reduce the skew toward uniform: hit ratios fall toward cache size / key space for every policy, showing that no policy can create locality that is not there. Then shrink the cache: the gap between LFU and LRU/FIFO widens, because when space is scarce, keeping the genuinely popular items matters most. Mentally add a scan (a burst of one-off keys): LRU and FIFO would flush the hot set while LFU (and Caffeine's TinyLFU admission) would not, which is why frequency-aware admission is the modern default.

Reading the diagram: there is no proxy; each client caches the slot-to-node map and talks directly to the owning primary. Primaries gossip health and slot ownership over the cluster bus. When ownership changes (failover or resharding), the first request to the wrong node receives MOVED (update the map) or ASK (one-off redirect during migration). A replica is promoted when a majority of primaries agree its primary has failed, which is why production clusters need at least three primaries: with two, losing one leaves no majority.

What to try: client-sharded caches (classic memcached deployments, Redis without Cluster behind a client or a proxy such as twemproxy or Envoy's Redis proxy) use consistent hashing to map keys to nodes. Add a node with one virtual node each and observe that only a fraction of keys move, but the load is uneven. Increase virtual nodes to 100+ per server: the distribution evens out and removing a node spreads its keys across all survivors rather than dumping them on one neighbour. Compare with naive hash(key) mod N, where changing N remaps nearly every key and causes a cache-wide miss storm. Redis Cluster's fixed 16,384 slots solve the same problem differently: the key-to-slot mapping never changes, only slot-to-node assignments move.

Reading the diagram: this read path combines the mitigations of §3.6–3.8. L1 absorbs hot keys; single-flight collapses concurrent misses so the database sees one query per key; jittered TTLs prevent synchronised expiry (avalanche); negative caching stops penetration by non-existent IDs. The "serve stale" branch requires keeping a stale copy (soft TTL) beyond the logical expiry; it is the most user-friendly option when the database is struggling.

6. The Math of Caching

6.1 Effective latency and load

With hit ratio \(h\), cache latency \(t_c\) and miss latency \(t_m\) (cache check plus backend):

\[ \bar{t} = h\,t_c + (1-h)\,t_m \qquad \lambda_{\text{db}} = (1-h)\,\lambda \]

With \(t_c = 0.5\) ms, \(t_m = 10\) ms: at \(h = 0.90\), \(\bar t = 1.45\) ms; at \(h = 0.99\), \(\bar t = 0.6\) ms. Database load is what matters more: going from 90% to 99% hit ratio reduces database reads tenfold. Conversely, a drop from 99% to 90% (e.g. after a deploy changes key formats) multiplies database read load by ten. Always ask "what is the miss rate", not "what is the hit rate".

Two-level caching: with L1 hit ratio \(h_1\) and L2 hit ratio \(h_2\) (of L1 misses), database traffic is \((1-h_1)(1-h_2)\lambda\) and Redis traffic is \((1-h_1)\lambda\). An L1 with only 50% hit ratio halves Redis traffic and network bandwidth.

6.2 Zipf popularity and cache sizing

Under a Zipf distribution with exponent \(s\) over \(N\) items, the \(k\)-th most popular item has probability \(p_k = \frac{k^{-s}}{H_{N,s}}\), where \(H_{N,s} = \sum_{i=1}^{N} i^{-s}\). An ideal cache holding the top \(C\) items has hit ratio

\[ h(C) = \frac{H_{C,s}}{H_{N,s}} \]

For \(s = 1\), \(H_{n,1} \approx \ln n + 0.577\). With \(N = 10^7\) items and \(C = 10^5\) (1%): \(h \approx \frac{\ln 10^5 + 0.577}{\ln 10^7 + 0.577} \approx \frac{12.09}{16.69} \approx 0.72\). Ten times the cache (10%) gives \(\approx 0.86\). This logarithmic shape is the reason the last few percent of hit ratio are so expensive: each doubling of cache size buys a roughly constant increment of hit ratio.

6.3 Stampede size

When a key read at rate \(\lambda_k\) expires and recomputation takes \(T_r\), without protection the expected number of concurrent recomputations is about \(\lambda_k T_r\) (Little's Law). For \(\lambda_k = 2{,}000\)/s and \(T_r = 0.3\) s: 600 identical database queries. With single-flight per instance across \(n\) instances: at most \(n\). With a distributed lock: 1.

6.4 Probabilistic early expiration (XFetch)

Store with each value the time \(\delta\) its last recomputation took and its expiry \(t_{exp}\). On each read at time \(t\), recompute early if

\[ t - \delta\,\beta \ln(U) \ge t_{exp}, \qquad U \sim \text{Uniform}(0,1] \]

Since \(\ln U \le 0\), \(-\delta\beta\ln U\) is a non-negative random "head start", exponentially distributed with mean \(\delta\beta\). Far from expiry, the condition almost never holds; as \(t\) approaches \(t_{exp}\), it becomes likely; and expensive values (large \(\delta\)) start refreshing earlier. \(\beta = 1\) is the default; \(\beta > 1\) refreshes earlier. The result is that, with high probability, exactly one reader refreshes slightly before expiry and no herd forms, with no coordination.

6.5 TTL jitter

If \(K\) keys are loaded at once with identical TTL \(T\), they expire in the same instant, producing \(K\) misses at once. With TTL uniform in \([T(1-j), T(1+j)]\), expirations spread over a window of \(2jT\), so the peak miss rate is about \(\frac{K}{2jT}\). For \(K = 10^6\), \(T = 3{,}600\) s, \(j = 0.1\): about 1,400 misses per second instead of a million in one instant.

6.6 Redis memory sizing

Illustrative 50 million session-like string keys, key ~30 bytes, value ~200 bytes, all with TTL. Per-key overhead (dictionary entry, redisObject, key SDS, expires entry, allocator rounding) is commonly in the range of 50–100 bytes; assume 80. Total ≈ \(5\times10^7 \times (30 + 200 + 80) \approx 15.5\) GB. Add 20–30% for fragmentation and replication/client buffers, and, if persistence uses fork, headroom for copy-on-write under write load. Plan ~22–25 GB of memory per copy; across 3 Cluster shards that is ~8 GB per primary. Measure with MEMORY USAGE key on real data before committing; encoding choices can halve this.

6.7 Consistent hashing movement

With \(n\) nodes and well-spread virtual nodes, adding one node moves about \(\frac{1}{n+1}\) of keys (only those that the new node now owns); removing one moves about \(\frac{1}{n}\). Naive modulo hashing moves about \(1 - \frac{1}{n+1}\) of keys when going from \(n\) to \(n+1\) nodes (e.g. 90% for 9 → 10). With \(v\) virtual nodes per server, the standard deviation of load per server is roughly proportional to \(1/\sqrt{v}\), so going from 1 to 100 virtual nodes reduces imbalance about tenfold.

6.8 Replication backlog sizing

To allow partial resync after a replica disconnects for up to \(T_d\) seconds while the primary writes \(w\) bytes per second of replication stream: backlog \(\ge w\,T_d\). At 20 MB/s and a 60 s tolerance, at least 1.2 GB. The default 1 MB covers only 50 ms of such a stream, guaranteeing full resyncs on any blip.

7.1 Spring Boot: Redis cache with per-cache TTLs, jitter and JSON

Spring Boot 3.2+/4.x with Spring Data Redis 3.2+ supports a TTL function, which we use to add jitter Version-sensitive · checked Nov 2026. The example uses the Jackson 2 based GenericJackson2JsonRedisSerializer; Spring Data Redis 4.x (Spring Boot 4) also ships Jackson 3 based serializers and deprecates some Jackson 2 classes, so check the reference documentation for the variant matching your Jackson version.

package com.example.catalog.cache;

import com.github.benmanes.caffeine.cache.Caffeine;
import org.springframework.cache.CacheManager;
import org.springframework.cache.annotation.EnableCaching;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.data.redis.cache.RedisCacheConfiguration;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.cache.RedisCacheWriter;
import org.springframework.data.redis.connection.RedisConnectionFactory;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.listener.ChannelTopic;
import org.springframework.data.redis.listener.RedisMessageListenerContainer;
import org.springframework.data.redis.serializer.GenericJackson2JsonRedisSerializer;
import org.springframework.data.redis.serializer.RedisSerializationContext.SerializationPair;

import java.time.Duration;
import java.util.Map;
import java.util.concurrent.ThreadLocalRandom;

@Configuration
@EnableCaching
public class CacheConfig {

    static final String INVALIDATION_CHANNEL = "cache:invalidate";

    /** TTL = base +/- 10% so keys loaded together do not expire together (avalanche). */
    static RedisCacheConfiguration withJitteredTtl(Duration base) {
        return RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl((key, value) -> {
                    long ms = base.toMillis();
                    long jitter = (long) (ms * 0.1);
                    return Duration.ofMillis(ms + ThreadLocalRandom.current().nextLong(-jitter, jitter + 1));
                })
                .prefixCacheNameWith("catalog:v3:")         // bump version on incompatible changes
                .serializeValuesWith(SerializationPair.fromSerializer(new GenericJackson2JsonRedisSerializer()));
        // Null values are cached by default (as a marker): this is negative caching against penetration.
    }

    @Bean
    RedisCacheManager redisCacheManager(RedisConnectionFactory cf) {
        return RedisCacheManager.builder(RedisCacheWriter.nonLockingRedisCacheWriter(cf))
                .cacheDefaults(withJitteredTtl(Duration.ofMinutes(10)))
                .withInitialCacheConfigurations(Map.of(
                        "products", withJitteredTtl(Duration.ofMinutes(30)),
                        "prices",   withJitteredTtl(Duration.ofSeconds(60))))
                .transactionAware()                           // puts/evicts happen after commit
                .build();
    }

    @Bean
    CacheManager cacheManager(RedisCacheManager redis, StringRedisTemplate template) {
        // Two-level: small, short-lived Caffeine L1 in front of Redis L2
        return new TwoLevelCacheManager(redis, template,
                Caffeine.newBuilder().maximumSize(10_000).expireAfterWrite(Duration.ofSeconds(20)));
    }

    @Bean
    RedisMessageListenerContainer invalidationListener(RedisConnectionFactory cf, CacheManager cm) {
        var container = new RedisMessageListenerContainer();
        container.setConnectionFactory(cf);
        container.addMessageListener((message, pattern) ->
                ((TwoLevelCacheManager) cm).onRemoteInvalidation(new String(message.getBody())),
                new ChannelTopic(INVALIDATION_CHANNEL));
        return container;
    }
}

7.2 A two-level cache with cross-instance invalidation

package com.example.catalog.cache;

import com.github.benmanes.caffeine.cache.Caffeine;
import org.springframework.cache.Cache;
import org.springframework.cache.CacheManager;
import org.springframework.cache.support.NullValue;
import org.springframework.cache.support.SimpleValueWrapper;
import org.springframework.data.redis.cache.RedisCacheManager;
import org.springframework.data.redis.core.StringRedisTemplate;

import java.util.Collection;
import java.util.Map;
import java.util.concurrent.Callable;
import java.util.concurrent.ConcurrentHashMap;

public class TwoLevelCacheManager implements CacheManager {

    private final RedisCacheManager l2Manager;
    private final StringRedisTemplate redis;
    private final Caffeine<Object, Object> l1Spec;
    private final Map<String, TwoLevelCache> caches = new ConcurrentHashMap<>();

    public TwoLevelCacheManager(RedisCacheManager l2Manager, StringRedisTemplate redis,
                                Caffeine<Object, Object> l1Spec) {
        this.l2Manager = l2Manager;
        this.redis = redis;
        this.l1Spec = l1Spec;
    }

    @Override
    public Cache getCache(String name) {
        return caches.computeIfAbsent(name, n -> new TwoLevelCache(n, l1Spec.build(), l2Manager.getCache(n)));
    }

    @Override
    public Collection<String> getCacheNames() { return caches.keySet(); }

    /** Message format: cacheName|key  (or cacheName|* to clear). */
    void onRemoteInvalidation(String msg) {
        int i = msg.indexOf('|');
        TwoLevelCache c = caches.get(msg.substring(0, i));
        if (c == null) return;
        String key = msg.substring(i + 1);
        if ("*".equals(key)) c.l1.invalidateAll(); else c.l1.invalidate(key);
    }

    final class TwoLevelCache implements Cache {
        private final String name;
        final com.github.benmanes.caffeine.cache.Cache<Object, Object> l1;
        private final Cache l2;

        TwoLevelCache(String name, com.github.benmanes.caffeine.cache.Cache<Object, Object> l1, Cache l2) {
            this.name = name; this.l1 = l1; this.l2 = l2;
        }

        // Keys are normalised to String so that local and remote invalidation agree.
        private static String k(Object key) { return String.valueOf(key); }

        @Override public String getName() { return name; }
        @Override public Object getNativeCache() { return l1; }

        @Override
        public ValueWrapper get(Object key) {
            Object v = l1.getIfPresent(k(key));
            if (v != null) return new SimpleValueWrapper(fromStore(v));
            ValueWrapper w = l2.get(key);
            if (w != null) l1.put(k(key), toStore(w.get()));
            return w;
        }

        @Override
        @SuppressWarnings("unchecked")
        public <T> T get(Object key, Class<T> type) {
            ValueWrapper w = get(key);
            return w == null ? null : (T) w.get();
        }

        /** Used by @Cacheable(sync = true): Caffeine coalesces concurrent loads per key in this JVM. */
        @Override
        @SuppressWarnings("unchecked")
        public <T> T get(Object key, Callable<T> loader) {
            Object v = l1.get(k(key), kk -> toStore(l2.get(key, loader)));
            return (T) fromStore(v);
        }

        @Override
        public void put(Object key, Object value) {
            l2.put(key, value);
            l1.put(k(key), toStore(value));
            publish(k(key));
        }

        @Override
        public void evict(Object key) {
            l2.evict(key);              // L2 first: other pods refilling L1 will now miss through to DB
            l1.invalidate(k(key));
            publish(k(key));            // tell other pods to drop their L1 copy
        }

        @Override
        public void clear() {
            l2.clear();
            l1.invalidateAll();
            publish("*");
        }

        private void publish(String key) {
            redis.convertAndSend(CacheConfig.INVALIDATION_CHANNEL, name + "|" + key);
        }

        private static Object toStore(Object v) { return v == null ? NullValue.INSTANCE : v; }
        private static Object fromStore(Object v) { return v == NullValue.INSTANCE ? null : v; }
    }
}

import org.springframework.cache.annotation.CacheEvict;

@Service
public class ProductService {

    }

    @Transactional
    @CacheEvict(cacheNames = "products", key = "#cmd.id()")   // DB first; evict happens after the method

}

Spring angle: eviction timing and transactions

@CacheEvict runs after the method returns, but if the transaction commits later (an outer @Transactional), another request could re-populate the cache from the old row in between. The transactionAware() setting on the Redis cache manager defers puts and evicts until after commit for caches it manages directly; for the custom L1 above, or for evictions driven by domain events, use @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT). For complete coverage of all writers, drive eviction from CDC (Debezium → Kafka → an invalidation consumer).

7.3 Distributed single-flight with a Redis lock

When recomputation is expensive (a report, an LLM-generated summary, an aggregation over millions of rows), even one recomputation per instance is too many. Use a short lock so only one instance recomputes; others briefly wait and re-read, or serve stale.

package com.example.catalog.cache;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.RedisScript;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.List;
import java.util.UUID;
import java.util.function.Supplier;

@Component
public class SingleFlight {

    // Release only if we still own the lock (compare-and-delete must be atomic)
    private static final RedisScript<Long> RELEASE = RedisScript.of(
            "if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) else return 0 end",
            Long.class);

    private final StringRedisTemplate redis;

    public SingleFlight(StringRedisTemplate redis) { this.redis = redis; }

    public String getOrCompute(String key, Duration ttl, Duration lockTtl, Supplier<String> compute)
            throws InterruptedException {
        for (int attempt = 0; attempt < 50; attempt++) {
            String cached = redis.opsForValue().get(key);
            if (cached != null) return cached;

            String lockKey = "lock:" + key;
            String token = UUID.randomUUID().toString();
            Boolean won = redis.opsForValue().setIfAbsent(lockKey, token, lockTtl); // SET NX PX
            if (Boolean.TRUE.equals(won)) {
                try {
                    String value = compute.get();
                    redis.opsForValue().set(key, value, ttl);
                    return value;
                } finally {
                    redis.execute(RELEASE, List.of(lockKey), token);
                }
            }
            Thread.sleep(50 + (long) (Math.random() * 50)); // jittered wait for the winner
        }
        return compute.get(); // give up coalescing rather than fail the request
    }
}

This lock is an efficiency lock (preventing duplicate work), not a correctness lock: if the holder pauses past lockTtl, two computations may run, which is harmless here. Chapter 8 discusses why correctness locks need fencing tokens.

import json
import math
import random
import time
from typing import Callable

import redis

r = redis.Redis(decode_responses=True)


def xfetch(key: str, ttl_s: int, recompute: Callable[[], object], beta: float = 1.0) -> object:
    raw = r.get(key)
    now = time.time()
    if raw is not None:
        entry = json.loads(raw)
        delta, expiry = entry["delta"], entry["expiry"]
        # -delta*beta*ln(U) is a random head start; ln(U) <= 0
        if now - delta * beta * math.log(random.random() or 1e-12) < expiry:
            return entry["value"]
    start = time.time()
    value = recompute()
    delta = time.time() - start
    entry = {"value": value, "delta": delta, "expiry": time.time() + ttl_s}
    # keep the physical key a bit longer than the logical expiry so readers still see delta/expiry
    r.set(key, json.dumps(entry), ex=ttl_s + 60)
    return value

	"context"

	"time"

const notFound = "\x00nf" // negative-cache marker

type Store struct {
	rdb   *redis.Client
	group singleflight.Group
	load  func(ctx context.Context, id string) (string, bool, error) // value, found, err
}

func jitter(base time.Duration) time.Duration {
	j := int64(base) / 10
	return time.Duration(int64(base) + rand.Int63n(2*j+1) - j)
}

func (s *Store) Get(ctx context.Context, id string) (string, bool, error) {
	key := "product:" + id
	if v, err := s.rdb.Get(ctx, key).Result(); err == nil {
		if v == notFound {
			return "", false, nil
		}
		return v, true, nil
	} else if !errors.Is(err, redis.Nil) {
		// Redis down: fall through to the loader (degraded, but available)
	}
	// Collapse concurrent misses for the same key in this process into one load.
	res, err, _ := s.group.Do(key, func() (any, error) {
		v, found, err := s.load(ctx, id)
		if err != nil {
			return nil, err
		}
		if !found {
			s.rdb.Set(ctx, key, notFound, 30*time.Second) // short negative TTL
			return "", nil
		}
		s.rdb.Set(ctx, key, v, jitter(10*time.Minute))
		return v, nil
	})
	if err != nil {
		return "", false, err
	}
	v := res.(string)
	return v, v != "", nil
}

func main() {
	s := &Store{
		rdb: redis.NewClient(&redis.Options{Addr: "localhost:6379"}),
		load: func(ctx context.Context, id string) (string, bool, error) {
			time.Sleep(100 * time.Millisecond) // pretend DB
			if id == "missing" {
				return "", false, nil
			}
			return `{"id":"` + id + `","name":"Widget"}`, true, nil
		},
	}
	ctx := context.Background()
	fmt.Println(s.Get(ctx, "42"))
	fmt.Println(s.Get(ctx, "missing"))

8. Real-World Applications

  • Read-heavy catalogues and profiles: product pages, user profiles and configuration are cached with cache-aside in Redis, plus Caffeine for the hottest items; CDN caching for anonymous traffic.
  • Session and token stores: Spring Session, OAuth token introspection results and JWKS keys cached in Redis or locally.
  • Rate limiting, counters and leaderboards: Redis's atomic INCR, Lua scripts and sorted sets (ZADD/ZREVRANGE with WITHSCORES) make it the default for limiters (Chapter 2), real-time counters and rankings.
  • Feeds and timelines: precomputed (fan-out-on-write) timelines stored as capped Redis lists or sorted sets per user, with hybrid fan-out-on-read for accounts with huge follower counts (Chapter 5's celebrity problem).
  • Lightweight queues and streams: Redis Streams with consumer groups for modest-volume job queues and event fan-out within one service domain.
  • Distributed coordination: short-lived locks for deduplicating work, idempotency-key stores with TTL for API requests, and feature-flag caches.
  • AI systems: caching LLM responses for identical prompts (exact-match caches keyed by a hash of model + parameters + prompt), semantic caches keyed by embedding similarity (with care: a semantically similar question may need a different answer), embedding caches to avoid recomputing vectors, and vector search inside Redis 8/Valkey modules for small to medium corpora. Part 8 covers these in depth.
  • Database offload during migrations: caches absorb read traffic while a database is being resharded or upgraded, buying time and headroom.

9. Case Studies

9.1 Facebook: scaling memcache with leases and invalidation streams

Verified Scaling Memcache at Facebook (NSDI 2013) describes a demand-filled look-aside (cache-aside) design where web servers, after writing to the database, delete the corresponding memcache keys. Notable mechanisms map directly onto §3: leases issued on a miss, which (a) prevent stale sets because a delete invalidates the outstanding lease, and (b) mitigate thundering herds by letting only one client per key fetch from the database within a short interval while others wait or accept slightly stale data; a mcrouter-style routing layer and client-side request batching to cut round trips; a pool of spare "gutter" servers that temporarily take over for failed cache servers so their load does not cascade to databases; and invalidation daemons that tail the database commit log and broadcast deletes to cache clusters across regions, so cache consistency is driven by committed data rather than by application code. The paper is the canonical reference for cache-aside at scale.

9.2 Uber: CacheFront, an integrated cache with CDC invalidation

Verified Uber's February 2024 post How Uber Serves Over 40 Million Reads Per Second from Online Storage Using an Integrated Cache describes CacheFront, a Redis-based cache integrated into the stateless query engine of Docstore (Uber's MySQL-based distributed database). Reads use cache-aside inside the query engine; invalidation is driven by Docstore's change data capture, so committed updates update or invalidate cached rows; and services can enable caching per database, per table, or per request, bypassing it for flows that need strong consistency. The post reports large reductions in P75 and P99.9 latency. A later Uber post describes growing the system further with stronger consistency guarantees. The design lesson: put the cache in the data-access layer and drive invalidation from the commit stream, so application teams get caching without each implementing invalidation correctly.

9.3 Figma: a Redis proxy for connection scalability

Verified Figma's 2026 post Figma's next-generation data caching platform describes FigCache, an in-house proxy placed between application clients and Redis clusters on Amazon ElastiCache. Its primary purpose is connection multiplexing: decoupling the number of client connections (which grows with the application fleet) from the number of connections Redis must handle, together with centralised routing. Secondary coverage (e.g. InfoQ) summarises the reliability results Figma reported. The lesson: at large fleet sizes, Redis's per-connection costs and connection storms during deploys or failovers become a scaling limit in their own right, and a proxy tier (Envoy's Redis proxy, twemproxy, or a bespoke one) is a common answer.

9.4 The Redis license change and the Valkey fork

Verified In March 2024 Redis Ltd. relicensed Redis from BSD-3-Clause to RSALv2/SSPLv1; the Linux Foundation announced Valkey, a BSD-licensed fork of Redis 7.2.4, shortly after, backed by several cloud providers. Valkey 9.0 reached GA in October 2025 (Linux Foundation press release), and Redis 8 added AGPLv3 as an additional license option in May 2025 (Redis 8 GA announcement). Version-sensitive · checked Nov 2026 For engineering teams this is a supply-chain decision: managed services from several clouds now default to or strongly promote Valkey; organisations embedding Redis in distributed products must review AGPL/SSPL/RSAL obligations; and the projects are beginning to diverge in features (Valkey's atomic slot migration and multi-database clusters; Redis 8's integrated search, JSON, time series and vector sets). Spring Data Redis, Lettuce and Jedis work with both for the shared command set. 11. Engineering Trade-offs

11.1 Choosing a caching strategy

Reading the diagram: the first question eliminates caching for data that needs linearizable reads. Public content goes to the edge. Hot, small, staleness-tolerant data earns an in-process layer. Cache-aside with delete-on-write is the default for everything else, and the number and type of writers decides whether application-level invalidation is enough or CDC is needed. Note that this is a per-data-type decision; one service will typically use several branches.

11.2 Delete versus update on write

Deleting is idempotent, cheap, and avoids caching values that might be computed from stale state or that nobody will read. Updating keeps the cache warm for read-after-write and avoids a miss, but risks writing an older value over a newer one when writers race (two writers, out-of-order cache updates). Default to delete; update only with version-checked writes (a Lua script that compares a version field).

11.3 TTL length

Short TTLs bound staleness and self-heal inconsistencies but raise miss rates; long TTLs maximise hit ratio but rely on invalidation being correct. A common compromise: long TTL with reliable invalidation, plus a soft TTL for refresh-ahead, plus jitter. For data without any invalidation path, the TTL is the staleness budget.

11.4 Redis versus Memcached versus local

Memcached is a fine choice for a pure, large, simple key-value cache: multi-threaded, predictable, slab-allocated memory. Redis/Valkey win when you need data structures (sorted sets, hashes, streams), atomic scripts, replication with failover, or persistence. A local cache wins for the hottest keys whatever the shared tier. Many large systems run both a shared tier and local caches.

11.5 Redis versus Valkey

For new deployments, the choice is now mostly about licensing, managed-service availability, and divergent features. Both speak RESP and support the classic command set. If you depend on Redis 8's integrated query engine and vector sets, choose Redis; if you require a permissive license or your cloud's managed default is Valkey, choose Valkey. Opinion

12. Common Mistakes and Production Failures

  • Caching without a staleness budget. Nobody decided how stale prices may be; a 24-hour TTL ships; customers see yesterday's prices.
  • Evicting before commit. @CacheEvict inside a transaction that commits later lets a concurrent reader repopulate from old data (§7.2).
  • Updating cache before database. If the database write fails, the cache holds a value that never existed.
  • No TTL at all. A single missed invalidation leaves wrong data forever.
  • Same TTL for everything loaded at once. Avalanche one TTL after every deploy or warm-up.
  • Unbounded local caches. A ConcurrentHashMap used as a cache with no eviction is a memory leak with extra steps.
  • Blocking commands in production. KEYS *, FLUSHALL without ASYNC, DEL of a 10-million-member set, HGETALL on giant hashes, long Lua scripts. Each stalls the single execution thread.
  • Big keys and hot keys. A 500 MB hash or a single key receiving 30% of traffic defeats sharding and causes latency spikes during migration (MIGRATE blocks per key).
  • Treating Redis as durable by default. Async replication plus everysec AOF can lose acknowledged writes on failover; queues and ledgers in Redis need that risk accepted explicitly.
  • Using an evicting policy on a datastore. Rate-limit or session data silently evicted under memory pressure; use noeviction and alerts for such instances, and keep caches on separate instances.
  • Default 1 MB replication backlog. Every replica hiccup triggers a full resync, fork and multi-gigabyte transfer, often cascading into latency spikes and memory pressure on the primary.
  • Key schema changes on deploy. New code uses v2 keys; the hit ratio drops to zero; the database melts. Roll out key changes gradually, pre-warm, or read-through from the old key format during transition.
  • Caching personalised responses at the CDN without private or correct Vary: one user's data served to others. This is a security incident, not a performance bug.
  • Java serialisation of cached objects. Class changes break deserialisation across a rolling deploy; JDK serialisation of untrusted data is also a deserialisation-attack vector. Use JSON or another explicit format.

13. Production Engineering

13.1 Monitoring

  • Hit ratio per cache name (Micrometer exposes cache.gets{result=hit|miss}, cache.evictions, cache.puts for Caffeine with recordStats() and for Redis caches with statistics enabled).
  • Redis: keyspace_hits/keyspace_misses, evicted_keys, expired_keys, used_memory vs maxmemory, mem_fragmentation_ratio, connected_clients, instantaneous_ops_per_sec, latest_fork_usec, replication offset lag, rejected_connections, and the slow log.
  • Client-side command latency histograms (Lettuce publishes command latency metrics via Micrometer), because server-side metrics miss network and client queueing.
  • Database read QPS correlated with cache hit ratio: the alert that matters is "database load rising because hit ratio dropped".

13.2 Performance

  • Use Lettuce's single shared, multiplexed connection for most workloads; add a pool only for blocking commands (BLPOP, XREAD BLOCK) or transactions.
  • Batch with MGET/pipelining; avoid N+1 round trips to Redis just as you avoid them to the database.
  • Keep values small (compress large JSON; store only what the read path needs); large values increase network time and block the event loop during transfer.

13.3 Reliability

  • Design the cold-cache path: can the database survive a full cache loss at peak? If not, have load shedding and warm-up procedures, and run caches with replicas across zones.
  • Set client timeouts (command timeout in the tens of milliseconds for cache reads) and treat cache errors as misses where possible, with a circuit breaker so a dead cache does not add latency to every request.
  • Run at least three primaries in Cluster mode, spread across zones, with replicas in different zones from their primaries.
  • Test failover regularly; measure how long clients take to discover the new primary (topology refresh settings in Lettuce: periodic and adaptive refresh).

13.4 Security

  • Never expose Redis to the internet; enable TLS, ACL users with least privilege (separate users for application, replication, and administration), and disable or rename dangerous commands (FLUSHALL, CONFIG, DEBUG) for application users via ACLs.
  • Do not cache secrets or sensitive personal data unless required; if you must, encrypt values and set short TTLs; remember that RDB/AOF files and backups contain everything.
  • Patch promptly: Redis and Valkey have had remotely exploitable vulnerabilities, including issues in the Lua scripting engine; restrict EVAL via ACLs where not needed.

13.5 Maintainability

  • Document a key schema (prefix, version, hash tags, TTL, owner) per cache, and version prefixes so incompatible changes can roll out side by side.
  • Keep caches on separate Redis instances from datastore-like uses (rate limits, queues, sessions), so eviction policies and failure impact differ appropriately.

14. Exercises

Exercise 1 · Foundational

A service handles 20,000 reads/s. Cache hit ratio is 95%, cache latency 0.6 ms, miss latency 12 ms. (a) Mean latency? (b) Database read QPS? (c) If a deploy drops the hit ratio to 80%, what happens to database load?

Solution

(a) \(0.95 \times 0.6 + 0.05 \times 12 = 0.57 + 0.6 = 1.17\) ms. (b) \(0.05 \times 20{,}000 = 1{,}000\)/s. (c) \(0.2 \times 20{,}000 = 4{,}000\)/s: four times the database load, which may exceed capacity; mean latency rises to \(0.48 + 2.4 = 2.88\) ms even before the database slows.

Exercise 2 · Intermediate

Explain step by step how a stale value can end up in the cache when a service does "update DB, then delete cache" under cache-aside, and design a fix using Redis that does not require distributed transactions.

Solution

See Figure 3.2: reader misses, reads old row, stalls; writer commits and deletes; reader sets old value. Fix with versioned sets: store the row's version (an updated_at or monotonically increasing version column) with the cached value; populate via a Lua script that writes only if no cached entry exists with a higher version, and on write, instead of deleting, write a tombstone carrying the new version with a short TTL. A stale reader's set (lower version) is then rejected by the script. Alternatives: leases (store a lease token on miss; delete clears it; set only succeeds if the token matches), or delayed double delete as a cheaper approximation. Keep a TTL as a backstop either way.

Exercise 3 · Intermediate

An attacker requests /products/{random-uuid} at 3,000 requests/s. Each misses the cache and runs a database query. Propose a layered defence and quantify the database load after each layer.

Solution

(1) Validate input format (reject malformed IDs): no change for valid-looking UUIDs. (2) Rate limit per IP/API key at the edge: if the attacker uses 30 IPs limited to 10/s, load drops to 300/s. (3) Negative caching: random UUIDs never repeat, so this alone does not help against random keys (it helps against repeated invalid IDs). (4) Bloom filter of existing product IDs in memory (or a Redis Bloom filter): with a 1% false-positive rate, only ~3 of the 300/s reach the database. (5) Monitor the 404 rate per client to block persistent offenders. Combined: ~3 queries/s.

Exercise 4 · Advanced

Your Redis primary (40 GB dataset, AOF everysec, RDB every hour) shows p99 latency spikes of ~300 ms every hour and occasional OOM kills of the container during peak traffic. Diagnose and fix.

Solution

Hourly spikes align with BGSAVE: fork() of a 40 GB process copies page tables (check latest_fork_usec), stalling the main thread; transparent huge pages make it worse. OOM during peak: copy-on-write during the snapshot duplicates pages modified under heavy writes, pushing RSS toward 2x, exceeding the container limit. Fixes: disable THP; take RDB snapshots on a replica instead of the primary; leave memory headroom (container limit well above maxmemory); split the dataset into Cluster shards so each fork is smaller (e.g. 4 × 10 GB); with the hybrid AOF, AOF rewrites also fork, so schedule and monitor them; consider whether the workload needs persistence at all if it is a cache.

Exercise 5 · Advanced (design)

Design caching for an "AI answer" feature: users ask questions about a product's documentation; generation costs ~2 s and $0.01. 40% of questions are exact duplicates (same normalised text) within a day; documentation changes weekly. Cover keys, TTLs, invalidation, stampede protection and risks.

Solution

Key: hash of (normalised question, product ID, documentation version, model ID, prompt template version, relevant parameters such as temperature). Including the documentation version makes invalidation automatic: when docs change, the version increments and old keys are simply never read again (they expire via TTL). TTL: e.g. 7 days with jitter, as an upper bound. Stampede: a popular question asked by many users at once triggers one generation via a Redis single-flight lock (§7.3); waiters poll briefly or stream the in-progress answer from a shared stream key. Personalisation: only cache when the answer does not depend on user-specific data or permissions; otherwise include tenant/role in the key. Risks: caching a harmful or wrong answer amplifies it, so allow invalidation by key on user reports and record which cached answers were served; avoid semantic (similarity-based) caching unless you validate that similar questions truly have the same answer. Savings: at 40% duplicates, generation cost and latency drop by ~40% for that traffic.

15. Interview Questions and Answers

Conceptual Compare cache-aside, read-through, write-through and write-behind.

Cache-aside: application loads on miss and deletes on write; simple, resilient to cache failure, risk of stale-set races. Read-through: the cache loads on miss via a loader; simpler callers, coalescing inside the cache. Write-through: writes go synchronously through the cache to the store; fresh cache, higher write latency. Write-behind: writes acknowledged by the cache and flushed asynchronously; lowest latency and batching, but risk of data loss and inconsistency. Choose cache-aside by default, write-behind only for loss-tolerant data such as counters.

Conceptual Redis is single-threaded. How is it so fast, and what are the consequences?

Command execution is single-threaded over in-memory data structures with O(1)/O(log n) operations, so there are no locks or context switches; network I/O is multiplexed with epoll and, since 6.0, optionally parallelised by I/O threads. Each command takes microseconds, so one core handles 100k+ ops/s. Consequences: every command is atomic; one slow command (large KEYS, DEL of a huge key, a long script) blocks all clients; and scaling across cores requires multiple shards.

Conceptual Explain MOVED versus ASK in Redis Cluster.

MOVED means the slot is permanently owned by another node: the client updates its slot map and retries there. ASK occurs during migration of a slot: the specific key has already moved to the target, but the slot is not yet reassigned; the client sends ASKING plus the command to the target once, without updating its map, because other keys of the slot may still be on the source.

Conceptual How does Redis implement LRU and LFU eviction?

Approximately. Each object stores a 24-bit field. For LRU it is a coarse access clock; on eviction Redis samples maxmemory-samples keys, maintains a 16-entry pool of best candidates by idle time, and evicts the best. For LFU the field holds an 8-bit logarithmic (Morris) counter plus a 16-bit decay timestamp; increments are probabilistic so 8 bits can represent about a million accesses, counters decay over time, and new keys start at 5. Sampling avoids the memory and CPU cost of exact structures.

Architecture Design a cache for product pages serving 200k reads/s with prices that must not be more than 5 s stale.

Split the data: static product content (description, images) cached aggressively (CDN plus Redis, long TTL, CDC invalidation); prices cached separately with a ≤5 s budget: Caffeine L1 with 2–3 s TTL per pod plus Redis L2 updated by a price-change consumer, so the page composes cached content with fresh price. Hot products get L1 hits, so Redis traffic is far below 200k/s. Stampede protection with Caffeine loading and refresh-ahead; TTL jitter; negative caching for invalid IDs; Redis Cluster across zones; database sized for a cold-L2 scenario with load shedding. At checkout, read the authoritative price from the database, never from cache.

Scenario After a Redis failover, some users see data they had already changed. Why?

Replication is asynchronous: writes acknowledged by the old primary that had not reached the replica were lost at promotion, including invalidations (deletes) and updates; the cache now holds older values. Also, clients may have continued writing to the old primary during a partition. Mitigations: TTLs bound the staleness; for cache invalidations, replay recent invalidations from the CDC stream after failover (or flush affected key ranges); for datastore uses, WAIT/min-replicas-to-write narrow the window; for data that cannot tolerate this, use a strongly consistent store.

Scenario A single key receives 40% of all cache traffic and its Redis shard is at 100% CPU. What do you do?

Immediately: add an in-process L1 for that key (even a 1-second TTL removes almost all its Redis traffic); or replicate the key into N copies with suffixes on different slots and read a random copy. Longer term: detect hot keys (LFU + --hotkeys, client sampling), apply L1 generally for hot keys, and for hot write keys (counters) split into sub-counters. Adding shards does not help because one key lives on one shard.

Coding Implement an LRU cache with O(1) get and put.

Hash map from key to node in a doubly linked list ordered by recency; get moves the node to the head; put inserts at the head and, if over capacity, removes the tail node and its map entry. In Java the compact version is a LinkedHashMap with accessOrder = true overriding removeEldestEntry:

class Lru<K, V> extends java.util.LinkedHashMap<K, V> {
    private final int capacity;
    Lru(int capacity) { super(16, 0.75f, true); this.capacity = capacity; }
    @Override protected boolean removeEldestEntry(java.util.Map.Entry<K, V> e) { return size() > capacity; }
}

Mention that it is not thread-safe (wrap or use Caffeine in production) and that an interviewer may expect the explicit list-plus-map implementation.

Conceptual Pub/Sub or Streams for cache invalidation and for job processing?

Cache invalidation: Pub/Sub is acceptable because messages are ephemeral and a missed message is backstopped by a short TTL. Job processing: Streams, because they persist entries, support consumer groups, acknowledgements and reclaiming of unacknowledged messages, and allow replay; Pub/Sub would lose jobs whenever a worker is disconnected.

16. Knowledge Check

  • Think in miss rate: moving from 99% to 90% hit ratio is a tenfold increase in backend load.
  • Default to cache-aside with database-first writes, delete-on-write, TTL as a backstop, and CDC-driven invalidation when there are many writers.
  • Stampedes are prevented by single-flight loading, probabilistic early refresh and serving stale; avalanches by jitter and HA caches; penetration by negative caching and Bloom filters; hot keys by L1 caches and key replication.
  • Eviction policy matters most when the cache is small relative to the working set; frequency-aware admission (TinyLFU) resists scans.
  • Redis executes commands on one thread: atomic and fast, but one slow command blocks everyone. Compact encodings (listpack, intset) save memory for small collections.
  • RDB uses fork and copy-on-write; AOF everysec loses about a second; replication is asynchronous, so failover can lose acknowledged writes.
  • Redis Cluster uses 16,384 slots via CRC16, hash tags for co-location, and MOVED/ASK redirects; Valkey and Redis now diverge in licensing and features.

Under cache-aside, which write sequence is the recommended default?

  1. Update cache, then update database
  2. Delete cache, then update database, and never use TTLs
  3. Update database, then delete the cache key, with a TTL as backstop
  4. Update database, then set the cache to the new value without TTL
Writing the database first avoids caching uncommitted values; deleting is idempotent and avoids racing updates; the TTL heals the residual stale-set race.

How many hash slots does Redis Cluster use, and how is a key mapped?

  2. 16,384; CRC16(key) mod 16384, hashing only the hash-tag substring if present
  3. 65,536; consistent hashing ring with virtual nodes
  4. It depends on the number of primaries
The key-to-slot mapping is fixed; only slot ownership changes. Hash tags like {user42} co-locate related keys.

Which technique prevents a cache stampede without any locking?

  1. Probabilistic early expiration (XFetch)
  2. Increasing maxmemory
  3. Switching from LRU to FIFO
  4. Disabling AOF
Each reader independently decides to refresh early with probability rising toward expiry, so one reader almost always refreshes before the key expires.

Why can Redis lose acknowledged writes during a Sentinel failover?

  1. Sentinel deletes the AOF file
  2. Replicas expire keys independently
  3. RDB snapshots are taken only on replicas
  4. Replication is asynchronous, so the promoted replica may not have received the latest writes
The primary acknowledges before replicas receive the write. WAIT and min-replicas-to-write narrow but do not eliminate the window.

  2. allkeys-random
  3. noeviction
  4. volatile-ttl
Evicting limiter state silently resets limits. noeviction surfaces memory problems as errors you can alert on; keep caches on separate instances with an evicting policy.
