Security Foundations, Threat Modeling & the OWASP Top 10

Most breaches of backend systems are not exotic: they are a missing ownership check, a debug endpoint left open, a library nobody patched, or an incident nobody could reconstruct because the logs were useless. This chapter gives you the mental model senior engineers use to reason about security — principles, threat modeling, the OWASP Top 10:2025, logging and vulnerability management — and maps each idea onto the Spring Boot stack you already run.

  • Prerequisites: Comfortable with Spring Boot, Spring Security basics (you have configured a SecurityFilterChain), REST APIs, relational databases, CI pipelines.
  • You will be able to: apply CIA/AAA and least privilege to a design; run a STRIDE threat model on a data-flow diagram in a design review; explain and mitigate every OWASP Top 10:2025 category in a Spring service; design security logging that helps incident response without leaking secrets; triage vulnerabilities with CVSS, EPSS and CISA KEV and set realistic patch SLAs.

1. Introduction: Security Is a Property of the Whole System

Security engineering is the discipline of building systems that keep doing what their owners intend while someone is actively trying to make them do something else. That last clause is what separates security from ordinary reliability work. A disk fails at random; an attacker picks the weakest disk, at the worst moment, and keeps trying. Your load tests model users who want the system to work. Your threat models must model users who want it to fail in a specific, profitable way.

For a backend engineer this has a practical consequence: security is not a feature you add in a sprint, and it is not the security team's problem. Almost every serious vulnerability class in this chapter — broken access control, injection, misconfiguration, vulnerable dependencies — is introduced by ordinary application code and ordinary deployment choices. The people best placed to prevent them are the people writing the controllers, repositories, Helm charts and Gradle files. That is you.

This chapter is the foundation for Part 11. It establishes vocabulary (CIA, AAA, least privilege, attack surface), a repeatable method (threat modeling with STRIDE on data-flow diagrams), a shared catalogue of what goes wrong (the OWASP Top 10:2025), and two operational practices that most teams underinvest in (security logging and vulnerability management). Later chapters go deep on identity (11.2), application vulnerabilities (11.3), cryptography/cloud/supply chain (11.4) and AI-specific threats (11.5).

Bridging from Java & Spring Boot

What you already know
You have written a SecurityFilterChain bean, put @PreAuthorize("hasRole('ADMIN')") on a service method, relied on Spring Data JPA's parameter binding to avoid SQL injection, enjoyed Thymeleaf's auto-escaping, had CsrfFilter reject a POST you forgot to give a token, stored a database password with Jasypt or Vault, and (hopefully) restricted management.endpoints.web.exposure.include to health,info.
Why that is not enough
Each of those is a control. Controls only help if they are applied to the right place, configured correctly, and cover every path. Spring cannot know that /api/orders/{id} must check that the order belongs to the caller; it cannot know that a new Kafka consumer bypasses the HTTP filter chain entirely; it cannot patch your transitive Jackson dependency. You need a method for finding where controls are missing, not just a toolbox of controls.
The modern approach
Threat-model at design time (STRIDE over a data-flow diagram), make secure behaviour the default in shared libraries and platform templates, treat dependencies and configuration as first-class attack surface (OWASP 2025 moved supply chain and misconfiguration to #2 and #3), log for detection and forensics, and run vulnerability management as a prioritised, SLA-driven process informed by exploitation data (EPSS, CISA KEV) rather than CVSS alone.
Where Python and Go fit
The principles are language-neutral; the defaults are not. FastAPI has no built-in CSRF or session framework; Go's net/http gives you almost nothing by default — no auth, no rate limiting, permissive timeouts. In polyglot estates the Spring service is often the best-protected component, and the Python ML sidecar or Go proxy next to it is the weak link. Threat models must cover all of them.
In production
Mature teams have a lightweight threat-model template in the design-doc process, a security champion per team, SCA and SAST gates in CI, a written patch SLA by severity, centralised security logs with alerting, and an incident runbook that has actually been rehearsed.
Use it when / avoid it when
Use the full method for any new service, new trust boundary (a new external integration, a new tenant model, an LLM with tools), or new sensitive data. Avoid ceremony for trivial internal changes: a two-line config tweak does not need a workshop, but it does need a reviewer who asks "does this widen exposure?".

Scope and authorization

Everything in Part 11 is written from a defender's point of view. Attack techniques are described only to the depth needed to recognise and prevent them. Any hands-on testing in the exercises targets applications you run yourself on your own machine (for example OWASP Juice Shop or WebGoat in Docker). Testing systems you do not own or have explicit written permission to test is illegal in most jurisdictions, regardless of intent.

2. History: From Locked Rooms to Supply Chains

Understanding how the field evolved explains why today's guidance looks the way it does — and why some of it is still catching up.

2.1 The principles era (1970s)

In 1975 Jerome Saltzer and Michael Schroeder published "The Protection of Information in Computer Systems" in the Proceedings of the IEEE. Its eight design principles — economy of mechanism, fail-safe defaults, complete mediation, open design, separation of privilege, least privilege, least common mechanism and psychological acceptability — are still the most cited list in the field. When this chapter says "deny by default" or "check every access", it is restating Saltzer and Schroeder. Around the same time the US Department of Defense funded work on multilevel security that led to the "Orange Book" (TCSEC, 1983/1985), which introduced the idea of evaluating systems against formal assurance levels.

2.2 The network era (1988–2000)

The Morris worm (November 1988) exploited a buffer overflow in fingerd and weak sendmail/rsh configurations and infected a significant fraction of the then-small internet. It led directly to the creation of CERT/CC at Carnegie Mellon. In 1999 MITRE launched the CVE (Common Vulnerabilities and Exposures) list so that everyone could refer to the same vulnerability by the same identifier — the foundation of every vulnerability scanner you use today.

2.3 The web application era (2000–2015)

As business logic moved into web applications, the dominant bugs moved too: SQL injection (publicly described in 1998), cross-site scripting, session hijacking. OWASP — the Open Worldwide Application Security Project (renamed from "Open Web" in 2023) — was founded in 2001 and published the first OWASP Top 10 in 2003. Microsoft's Trustworthy Computing memo (January 2002) led to the Security Development Lifecycle and, internally, to the STRIDE threat classification created by Loren Kohnfelder and Praerit Garg in 1999. Adam Shostack's book Threat Modeling: Designing for Security (Wiley, 2014) brought that practice to the wider industry.

2.4 The cloud and API era (2015–2020)

APIs replaced server-rendered pages, and access-control bugs (one user reading another's data by changing an ID) became the most common serious finding. OWASP started a separate API Security Top 10 in 2019. Cloud misconfiguration — public storage buckets, over-privileged IAM roles — became a leading cause of data exposure; the 2019 Capital One breach (Chapter 11.3) combined an SSRF bug with an over-privileged instance role.

2.5 The supply-chain era (2020–today)

SolarWinds (disclosed December 2020) showed that compromising a vendor's build system compromises every customer. Log4Shell (CVE-2021-44228, December 2021) showed that a single transitive dependency could make a large fraction of Java services remotely exploitable overnight. The xz-utils backdoor (CVE-2024-3094, March 2024) showed a patient, multi-year social-engineering takeover of an open-source maintainer role. The response — SBOMs, SLSA, Sigstore, the CISA Known Exploited Vulnerabilities catalog (launched November 2021) — is covered in Chapter 11.4. OWASP's 2025 edition reflects this shift by creating a dedicated "Software Supply Chain Failures" category at #3.

2.6 The AI era (2023–)

Large language models introduced a new class of input-driven vulnerability (prompt injection) and a new class of over-privileged component (agents with tools). OWASP published a separate Top 10 for LLM Applications (first 2023, updated for 2025). AI coding assistants also changed the production of vulnerabilities: more code, written faster, reviewed by people who did not author it. Chapter 11.5 treats this in depth.

3. Fundamentals: The Vocabulary of Secure Design

3.1 The CIA triad — what you are protecting

Every security requirement ultimately protects one of three properties of information or service:

  • Confidentiality — only authorised parties can read the data. Violations: a tenant reading another tenant's invoices, a stack trace leaking a connection string, an S3 bucket readable by the world, a log line containing a bearer token.
  • Integrity — data and behaviour change only through authorised, correct operations. Violations: a user changing the price field in a checkout request, a mass-assignment bug that lets a user set role=ADMIN, a tampered build artifact, an unsigned webhook that lets anyone mark an order as paid.
  • Availability — the system serves legitimate users when they need it. Violations: an unbounded page_size that makes the database scan ten million rows, a regular expression with catastrophic backtracking (ReDoS), a ransomware infection, a credential-stuffing wave that locks out real users.

Two further properties are commonly added. Authenticity means you can trust the claimed origin of a message (a signed JWT, an HMAC-signed webhook). Non-repudiation means a party cannot credibly deny an action they took — usually achieved by digital signatures plus tamper-evident audit logs. For financial and healthcare backends, non-repudiation is often a regulatory requirement rather than a nice-to-have.

Insight

CIA properties conflict. Maximum confidentiality (encrypt everything, require MFA on every call) costs availability and usability. Maximum availability (fail open when the auth server is down) costs confidentiality and integrity. Security design is the explicit choice of where to sit on these trade-offs for each asset — not maximising all three.

3.2 AAA — authentication, authorization, accounting

Authentication answers "who are you?" and produces a principal: a user, a service account, a workload identity. In Spring this is the job of an AuthenticationManager and the resulting Authentication in the SecurityContextHolder. Authorization answers "may this principal perform this action on this resource?" — authorizeHttpRequests, @PreAuthorize, and (critically) the ownership checks inside your service layer that no framework writes for you. Accounting (often called auditing) records who did what, when, from where, and with what outcome, so you can detect abuse and reconstruct incidents.

The most important practical lesson: authentication bugs are rare in mature stacks because you use a framework; authorization bugs are common because authorization is business logic. Spring will happily authenticate Alice and then let her read Bob's order if your controller does orderRepository.findById(id) without checking ownership. That is why Broken Access Control has been #1 in the OWASP Top 10 since 2021.

3.3 Least privilege

Every principal — human, service, process, database user, CI job, LLM agent — should have exactly the permissions needed for its task and no more, for no longer than needed. In practice this means:

  • The application's database user can SELECT/INSERT/UPDATE/DELETE on its own schema but cannot DROP, cannot read other schemas, and is not the migration user. Run Flyway/Liquibase with a separate, more privileged credential in a one-shot job.
  • The pod's cloud IAM role can read one S3 prefix, not s3:* on *.
  • The container runs as a non-root UID with a read-only root filesystem and no Linux capabilities it does not need.
  • The CI token used by a pull-request build cannot publish releases or read production secrets.
  • Administrative privileges are granted just-in-time (time-boxed elevation with approval) rather than standing.

Least privilege does not prevent the initial compromise; it limits the blast radius afterwards. In the Capital One incident the SSRF bug was the entry point, but the reason it became a breach of over 100 million records was that the role reachable via the metadata service could list and read a large number of buckets.

3.4 Defense in depth

No single control is perfect, so you layer independent controls such that an attacker must defeat several of them. For a typical Spring API, the layers for "an outsider must not read another customer's data" might be: WAF/API gateway rate limiting and schema validation → TLS → OAuth2 resource server JWT validation → URL-level authorization in the filter chain → method-level @PreAuthorize → ownership check in the service → row-level security in PostgreSQL → encryption at rest → audit logging and anomaly alerts. The key word is independent: two layers that share a single point of failure (for example both trusting a header set by a proxy that can be bypassed) are really one layer.

3.5 Secure by default and fail-safe defaults

A system is secure by default when the out-of-the-box configuration is the safe one and insecure behaviour requires an explicit, visible opt-out. Spring Security is a good example: once it is on the classpath, every endpoint requires authentication, CSRF protection is enabled for browser flows, security headers (X-Content-Type-Options, X-Frame-Options, cache control) are added, and passwords must be encoded. Spring Boot Actuator only exposes health over HTTP by default. Your shared libraries and service templates should follow the same principle: the platform starter should default to deny-all authorization, strict CORS, and no debug endpoints.

Fail-safe defaults (Saltzer and Schroeder's term) means that when a decision cannot be made — the policy engine is unreachable, the token cannot be parsed, an exception is thrown in the middle of an authorization check — the outcome is deny. A surprising number of real vulnerabilities are "fail-open" logic: catch (Exception e) { return true; } in a permission evaluator, or a feature flag service that defaults to "admin features enabled" when it times out. OWASP 2025 created a whole new category (A10, Mishandling of Exceptional Conditions) partly for this.

3.6 Attack surface

The attack surface is the sum of all points where an untrusted party can supply input or observe output. For a backend service it includes: every HTTP route (including ones you forgot — actuator, Swagger UI, error pages, H2 console), every message consumer (Kafka topics are input), every file or object it parses, every outbound call whose response it trusts, every admin CLI, every environment variable and config source, and every dependency's code paths that those inputs reach. Attack surface reduction — removing endpoints, disabling unused features, shrinking images, closing ports — is often the highest-return security work because it eliminates whole classes of risk rather than mitigating them one by one.

3.7 Trust boundaries and complete mediation

A trust boundary is a line across which the level of trust changes: browser → API gateway, API → database, your service → a third-party payment API, your process → an LLM that reads untrusted web pages. Data crossing a boundary inward must be validated and authorised; data crossing outward must be encoded for its destination and checked for leakage. Complete mediation means every access to every protected resource is checked, every time — not just on the first request, not just on the UI path. The classic failure is checking authorization in the controller that the web UI uses while a second, internal endpoint (or a Kafka consumer, or a GraphQL resolver) reaches the same repository unchecked.

3.9 Threat modeling and the four questions

Threat modeling is structured thinking about what can go wrong before it is built. The most practical framing is the four questions popularised by Adam Shostack and adopted by the Threat Modeling Manifesto (2020):

  1. What are we working on? — draw a data-flow diagram (DFD) of the system.
  2. What can go wrong? — enumerate threats, e.g. with STRIDE per element.
  3. What are we going to do about it? — mitigate, eliminate, transfer or accept each threat.
  4. Did we do a good job? — validate: are mitigations implemented and tested? Did we miss components?

A data-flow diagram uses four element types: external entities (users, third-party systems you do not control), processes (your services, functions), data stores (databases, caches, buckets, queues) and data flows (arrows: HTTP calls, queries, messages). You then draw trust boundaries as dashed boxes. Threats cluster where flows cross boundaries. Section 5 shows a full DFD for an order service.

Other methodologies exist and are worth knowing by name: LINDDUN for privacy threats (linkability, identifiability, non-repudiation, detectability, disclosure, unawareness, non-compliance), PASTA (a seven-stage risk-centric process), and attack trees.

3.11 Attack trees

An attack tree, introduced by Bruce Schneier in 1999, puts an attacker goal at the root ("read another tenant's invoices") and decomposes it into sub-goals joined by OR (any child suffices) and AND (all children are needed) nodes. Leaves are concrete actions. Attack trees are useful for one high-value asset where you want to see all paths and find the cheapest one; STRIDE is better for broad coverage of a whole system. You can annotate leaves with cost or likelihood and propagate: an OR node is as easy as its easiest child; an AND node is as hard as the sum of its children.

3.12 Risk rating

Not every threat deserves the same effort. A rating method makes prioritisation explicit and repeatable. Common options:

  • Simple likelihood × impact matrix (each Low/Medium/High). Fast, good enough for most design reviews.
  • OWASP Risk Rating Methodology — scores likelihood factors (skill level, motive, opportunity, ease of discovery, ease of exploit, awareness, intrusion detection) and impact factors (technical and business) from 0–9 and combines them.
  • CVSS — designed for scoring published vulnerabilities, not design-time threats; see §3.14.
  • DREAD (Damage, Reproducibility, Exploitability, Affected users, Discoverability) — historically used at Microsoft but abandoned there because scores were too subjective. Know it for interviews; do not adopt it.

3.14 Vulnerability identifiers and scores: CVE, CWE, CVSS, EPSS, KEV

  • CVE — an identifier for a specific vulnerability in a specific product, e.g. CVE-2021-44228 (Log4Shell). Assigned by CVE Numbering Authorities (CNAs); enriched by NIST's National Vulnerability Database (NVD) and other databases (GitHub Advisory Database, OSV).
  • CWE — Common Weakness Enumeration: a class of weakness, e.g. CWE-89 (SQL injection), CWE-639 (authorization bypass through user-controlled key, i.e. IDOR). OWASP categories are groups of CWEs.
  • CVSS — Common Vulnerability Scoring System from FIRST. Version 4.0 was published in November 2023; much tooling still emits v3.1. The Base score (0.0–10.0) describes intrinsic severity; Threat (v4; "Temporal" in v3.1) and Environmental metrics adjust it for exploit maturity and your deployment. Most organisations wrongly use the Base score alone.
  • EPSS — Exploit Prediction Scoring System, also from FIRST: a daily-updated probability (0–1) that a CVE will be exploited in the wild in the next 30 days, derived from a model trained on observed exploitation. Version 4 was released in March 2025.
  • CISA KEV — the US Cybersecurity and Infrastructure Security Agency's Known Exploited Vulnerabilities catalog: CVEs with reliable evidence of active exploitation. US federal civilian agencies are required (Binding Operational Directive 22-01) to remediate them by a listed due date; everyone else should treat KEV membership as "patch now".

The combination matters: CVSS says how bad it could be, EPSS says how likely it is to be exploited soon, KEV says it is being exploited. Only a small minority of published CVEs are ever exploited in the wild, so prioritising purely by CVSS wastes effort on unexploited "criticals" while leaving exploited "highs" open.

4. Internal Working: How Each OWASP Risk Arises in a Spring Service — and How It Is Stopped

This section walks every OWASP Top 10:2025 category through the lens of a concrete Spring Boot order service. For each: the mechanism (why the bug happens internally), a vulnerable pattern, and the secure pattern. Full runnable configuration is in §7; deeper treatment of injection, XSS, CSRF and SSRF is in Chapter 11.3, identity in 11.2, cryptography and supply chain in 11.4.

4.1 Where controls live in a request's life

When an HTTP request arrives at a Spring MVC application, it passes through the servlet container, then the DelegatingFilterProxy → FilterChainProxy, which selects the first SecurityFilterChain whose securityMatcher matches. Inside that chain the relevant filters run in a fixed order: header writing, CORS, CSRF, logout, authentication (for example BearerTokenAuthenticationFilter for a resource server), request cache, anonymous authentication, exception translation, and finally AuthorizationFilter, which evaluates your authorizeHttpRequests rules. Only then does the DispatcherServlet pick a handler, bind and validate the request body (@Valid), and invoke the controller. Method security (@PreAuthorize, @PostAuthorize) is applied by an AOP proxy around your beans — which means it only works on calls that go through the proxy (not self-invocations within the same class).

Knowing this order explains several real bugs: a WebSecurityCustomizer.ignoring() path skips the entire chain including headers; a second SecurityFilterChain with a broad matcher and lax rules silently wins for paths you expected the strict chain to handle; an internal this.deleteOrder() call bypasses @PreAuthorize.

4.2 A01 Broken Access Control

Mechanism. The application authenticates the caller correctly but fails to check that the caller may perform the action on the specific object or function. Sub-types: insecure direct object reference (IDOR / BOLA — object level), missing function-level checks (a normal user calls /admin/**), privilege escalation via modifiable claims or parameters, CORS misconfiguration that lets an untrusted origin make credentialed requests, path traversal into files, and — new in 2025's grouping — SSRF, where the server is tricked into accessing resources the attacker cannot reach directly.

// VULNERABLE: authenticated, but any user can read any order by ID.
@GetMapping("/api/orders/{id}")
public OrderDto get(@PathVariable UUID id) {
    return mapper.toDto(orderRepository.findById(id).orElseThrow());
}
// SECURE: ownership enforced in the query itself, so there is no window
// where the object is loaded without a check. 404 (not 403) avoids
// confirming that the ID exists for someone else.
@GetMapping("/api/orders/{id}")
public OrderDto get(@PathVariable UUID id, @AuthenticationPrincipal Jwt jwt) {
    return orderRepository.findByIdAndCustomerId(id, jwt.getSubject())
            .map(mapper::toDto)
            .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND));
}

Function-level control belongs in the filter chain with deny by default (.anyRequest().denyAll() or .authenticated() as the last rule) plus method security for anything sensitive. Scoping queries by owner/tenant (or using PostgreSQL row-level security, or Hibernate's @TenantId / filters) moves the check from "remember to add it" to "impossible to forget".

4.3 A02 Security Misconfiguration

Mechanism. The code is fine; the deployment is not. Typical Spring examples: management.endpoints.web.exposure.include=* exposing /actuator/env, /actuator/heapdump (which contains secrets in memory) or /actuator/loggers; H2 console enabled in production; Swagger UI publicly reachable; server.error.include-stacktrace=always; CORS allowedOriginPatterns("*") with allowCredentials(true); default credentials on an admin tool; verbose X-Powered-By-style banners; missing security headers on a non-Spring component; a Kubernetes Service of type LoadBalancer on an internal admin port. OWASP's 2025 data showed this category being found in a large fraction of tested applications, which is why it rose to #2.

Prevention. Treat configuration as code with review; have a hardened baseline (application-prod.yml in a shared starter); expose actuator on a separate management port bound to the cluster network only; fail the build on dangerous properties; scan running environments (CSPM, Kubernetes admission policies). Repeatable hardening beats heroic audits.

4.4 A03 Software Supply Chain Failures

Mechanism. Your service executes far more third-party code than first-party code. Risks include known-vulnerable versions (Log4Shell), malicious packages (typosquatting, dependency confusion, compromised maintainer accounts), compromised build pipelines (SolarWinds), unverified artifacts pulled at deploy time, and unpinned base images. The 2025 category is broader than 2021's "Vulnerable and Outdated Components" because the industry learned that "is it vulnerable?" is only one of the questions; "is it what we think it is, built how we think it was?" is the other.

Prevention. Software composition analysis (SCA) in CI (OWASP Dependency-Check, Dependabot, Renovate, Snyk, Trivy, osv-scanner); dependency locking (Gradle lockfiles / Maven enforcer); a private artifact proxy; SBOM generation (CycloneDX Maven/Gradle plugins); signed images verified at admission; minimal base images; and a patch SLA (§13). Chapter 11.4 covers SLSA and Sigstore in detail.

4.5 A04 Cryptographic Failures

Mechanism. Sensitive data is exposed because cryptography is absent, weak or misused: HTTP instead of HTTPS between services, TLS without certificate verification (a custom TrustManager that accepts everything), passwords hashed with SHA-256 instead of a slow password hash, AES in ECB mode or GCM with a reused nonce, hard-coded keys, home-grown "encryption", or java.util.Random used for tokens.

// VULNERABLE: predictable token
String resetToken = Long.toHexString(new Random().nextLong());

// SECURE: 256 bits from a CSPRNG, URL-safe
byte[] buf = new byte[32];
SecureRandom.getInstanceStrong().nextBytes(buf); // or new SecureRandom()
String resetToken = Base64.getUrlEncoder().withoutPadding().encodeToString(buf);

Prevention. Classify data; encrypt in transit everywhere (TLS 1.2+ with 1.3 preferred); use DelegatingPasswordEncoder (bcrypt/Argon2) for passwords; use vetted high-level libraries (Google Tink, or JCA with AES-GCM and unique nonces); keep keys in a KMS or Vault, not in code. Chapter 11.4 covers this in depth. (Note: SecureRandom.getInstanceStrong() may block on some Linux configurations; plain new SecureRandom() is the usual server choice.)

4.6 A05 Injection

Mechanism. Untrusted data is concatenated into a string that another interpreter parses as code: SQL, JPQL/HQL, LDAP filters, OS commands, Spring Expression Language (SpEL), template engines, XPath, HTML/JavaScript (XSS is in this category). The interpreter cannot tell where your code ends and the attacker's data begins.

// VULNERABLE: string concatenation into JPQL — input such as  x' OR '1'='1  changes the query's logic
em.createQuery("select c from Customer c where c.email = '" + email + "'");

// SECURE: parameter binding — the value travels separately from the query text
em.createQuery("select c from Customer c where c.email = :email", Customer.class)
  .setParameter("email", email);

Prevention. Parameterised queries everywhere (Spring Data derived queries and @Query with named parameters are safe; JdbcTemplate with ? placeholders is safe; string-built ORDER BY clauses are not — allow-list column names); never pass user input to Runtime.exec or a shell; never evaluate user input as SpEL; context-aware output encoding (Thymeleaf th:text, not th:utext). Chapter 11.3 has the full treatment.

4.7 A06 Insecure Design

Mechanism. The implementation is faithful to a design that is itself unsafe. Examples: a password-reset flow that reveals whether an email is registered and has no rate limit; a "transfer funds" API with no idempotency key so retries double-charge; a coupon system that lets the client send the discount amount; a multi-tenant design with no tenant column; a booking system that allows unlimited holds so a bot can reserve all seats. No amount of input validation fixes a missing business rule.

Prevention. Threat modeling during design (§3.9), abuse cases alongside use cases ("as an attacker I want to…"), reference architectures and secure design patterns (server-side authority for prices, idempotency keys, per-account limits), and unit/integration tests that assert security invariants ("a user cannot see another tenant's data") rather than only happy paths.

4.8 A07 Authentication Failures

Mechanism. Attackers obtain or forge an identity: credential stuffing with leaked password lists, brute force on login or OTP endpoints without throttling, weak password policies, missing MFA for privileged accounts, session fixation, sessions or tokens that never expire, JWTs accepted without signature validation, and user-enumeration through different error messages or response timings.

Prevention. Delegate authentication to a hardened identity provider (Keycloak, Okta, Entra ID, Cognito, or Spring Authorization Server) using OIDC; enable MFA/passkeys; rate-limit and add progressive delays on login; check new passwords against breached-password lists (NIST SP 800-63B recommends this and discourages arbitrary composition rules); rotate session IDs on login (Spring Security does this by default via session fixation protection); validate JWT signature, issuer, audience and expiry. All of this is Chapter 11.2.

4.9 A08 Software or Data Integrity Failures

Mechanism. Code or data is trusted without verifying its integrity: Java native deserialization of untrusted bytes (gadget chains leading to remote code execution), Jackson polymorphic typing with enableDefaultTyping()/activateDefaultTyping on untrusted input, auto-update mechanisms that download unsigned code, CI pipelines that run untrusted pull-request code with production secrets, webhooks accepted without signature verification, and caches or cookies whose contents are trusted without a MAC.

// SECURE webhook verification (HMAC-SHA256, constant-time compare)
Mac mac = Mac.getInstance("HmacSHA256");
mac.init(new SecretKeySpec(webhookSecret, "HmacSHA256"));
byte[] expected = mac.doFinal(rawBody);                 // raw bytes, before JSON parsing
byte[] provided = HexFormat.of().parseHex(signatureHeader);
if (!MessageDigest.isEqual(expected, provided)) {
    throw new ResponseStatusException(HttpStatus.UNAUTHORIZED);
}

Prevention. Never deserialize untrusted data with Java serialization (if you must, use an ObjectInputFilter allow-list, JEP 290/415); keep Jackson default typing off; sign artifacts and verify at deploy; separate untrusted CI jobs from privileged ones; verify signatures on all inbound webhooks and include a timestamp to prevent replay.

4.10 A09 Security Logging & Alerting Failures

Mechanism. Attacks succeed or persist because nobody notices: login failures, access-control denials and high-value transactions are not logged; logs exist but are not centralised; logs are centralised but nobody alerts on them; or logs are so noisy and unstructured that an investigation cannot reconstruct a timeline. The 2025 rename from "Monitoring" to "Alerting" emphasises that a log nobody acts on provides little protection. The opposite failure — logging sensitive data — creates new confidentiality incidents. §4.13 and §7 detail what to log.

4.11 A10 Mishandling of Exceptional Conditions

Mechanism. New in 2025. Systems behave insecurely when something unexpected happens: an exception in an authorization check that defaults to allow, a partially completed transaction that leaves money moved but not recorded, error messages that leak internals, resource exhaustion because a failure path never releases a lock or connection, or unchecked return values. Many of these are logic flaws that scanners rarely find.

// VULNERABLE: fails open
boolean canApprove(Authentication auth, UUID invoiceId) {
    try {
        return policyClient.check(auth.getName(), "approve", invoiceId);
    } catch (Exception e) {
        log.warn("policy service unavailable, allowing", e);
        return true;                       // attacker just needs to slow the policy service down
    }
}

// SECURE: fails closed, surfaces the condition, keeps a bounded timeout
boolean canApprove(Authentication auth, UUID invoiceId) {
    try {
        return policyClient.check(auth.getName(), "approve", invoiceId); // client has 300 ms timeout
    } catch (PolicyUnavailableException e) {
        meterRegistry.counter("authz.policy.unavailable").increment();
        return false;                      // deny; caller sees 403/503, on-call is alerted
    }
}

Prevention. Fail closed; use transactions so failures roll back fully; centralise exception handling (@RestControllerAdvice returning RFC 9457 Problem Details without internals); set timeouts and limits everywhere; test failure paths (fault injection, chaos tests) not only happy paths.

4.12 Running a threat model, step by step

In a design review, the internal procedure that works for most teams is:

  1. Scope (5 min): what is changing? Which assets are touched? Who are plausible attackers (anonymous internet, authenticated customer, malicious tenant, compromised dependency, insider)?
  2. Diagram (15 min): draw the DFD at the level of deployable units and data stores. Mark every trust boundary. Annotate flows with protocol and authentication method ("HTTPS + JWT", "Kafka, mTLS, no per-message auth").
  3. Enumerate (20 min): go element by element applying STRIDE. Write threats as sentences: "A malicious tenant can read another tenant's documents by guessing IDs on GET /docs/{id}."
  4. Rate (10 min): likelihood × impact, High/Medium/Low.
  5. Decide (10 min): for each High and Medium, a mitigation with an owner and a ticket, or an explicit risk acceptance by the product owner.
  6. Validate (later): mitigations get tests (an integration test proving tenant isolation), and the threat model is updated when the design changes.

Keep the output small and living — a page in the design doc, the DFD source in the repository (Mermaid works well), and tickets. A 40-page threat model that nobody updates is worse than a one-page one that is maintained.

4.13 What happens when a vulnerability is disclosed

Internally, a vulnerability in a dependency moves through a pipeline: a researcher or maintainer discovers it → coordinated disclosure to the maintainer → a fix is prepared → a CVE is reserved by a CNA → an advisory is published (GitHub Security Advisory, project mailing list) → databases (NVD, GHSA, OSV) ingest and enrich it with CVSS and affected version ranges → your SCA tool matches it against your SBOM or lockfile → a ticket or automated PR (Dependabot/Renovate) is created → triage decides priority using CVSS, EPSS, KEV and reachability → fix is tested, merged and deployed → verification that the vulnerable version is gone from every running workload. The gap between public disclosure and exploitation can be very short for high-profile bugs; for Log4Shell, mass scanning was widely reported within hours of the December 2021 disclosure.

6. The Math of Risk: Likelihood, Impact, Layered Controls and Scores

6.1 Risk as expected loss

Intuition: a threat that is very likely but harmless and one that is catastrophic but nearly impossible may both deserve less attention than one that is moderately likely and seriously harmful. Formally, for each threat \( t \):

\[ \text{Risk}(t) = P(t) \times I(t) \]

where \( P \) is the probability of the threat being realised in a period and \( I \) the impact. The classic quantitative form from risk management is annualised loss expectancy:

\[ \text{ALE} = \text{SLE} \times \text{ARO} \]

with single loss expectancy SLE (cost of one incident) and annual rate of occurrence ARO. Illustrative If a credential-stuffing incident costs about 40,000 (support, resets, fraud) and you expect it 2.5 times per year without controls, ALE ≈ 100,000. A bot-protection and MFA rollout costing 30,000 per year that cuts ARO to 0.25 lowers ALE to 10,000 — net benefit ≈ 60,000. Real numbers are uncertain; the value is in forcing the conversation, not in false precision. Most teams use ordinal scales (Low/Medium/High) for exactly that reason.

6.2 Defense in depth, quantified (with a caveat)

If an attack must defeat \( n \) controls and control \( i \) is bypassed with probability \( p_i \), and the controls are independent, the probability that all are bypassed is

\[ P_{\text{breach}} = \prod_{i=1}^{n} p_i \]

Illustrative Three controls each bypassed 10% of the time give \( 0.1^3 = 0.001 \). The caveat is the independence assumption: if all three layers trust the same spoofable header, or share one misconfigured identity provider, they fail together and the real probability is closer to \( \max p_i \). This is why diversity of mechanism (network policy + application authorization + database RLS) beats three copies of the same check.

6.3 Attack-tree arithmetic

For cost-annotated trees: an OR node's cost is the minimum of its children's costs; an AND node's cost is the sum. For probability-annotated trees with independent leaves: \( P_{\text{OR}} = 1 - \prod (1-p_i) \) and \( P_{\text{AND}} = \prod p_i \). Fixing the cheapest leaf on every OR branch raises the attacker's minimum cost — the useful metric.

6.4 CVSS in brief

CVSS v3.1 base score combines exploitability (attack vector, attack complexity, privileges required, user interaction) and impact (confidentiality, integrity, availability), adjusted by scope. In simplified form, impact sub-score \( \text{ISS} = 1 - (1-C)(1-I)(1-A) \) where C, I, A take values 0, 0.22 or 0.56; exploitability \( = 8.22 \times AV \times AC \times PR \times UI \); and the base score is roughly \( \min(\text{Impact} + \text{Exploitability}, 10) \) rounded up to one decimal. CVSS v4.0 replaced the formula with a lookup over "macro-vectors" and added Attack Requirements and separate subsequent-system impacts. You rarely compute these by hand; you should understand that "network, no privileges, no user interaction, high C/I/A" produces 9.8 and that a 9.8 on an internal batch tool with no network exposure may matter less to you than a 7.5 on your login page.

6.5 EPSS as a probability, and why it changes priorities

EPSS gives \( P(\text{exploitation in next 30 days}) \). Treat it as a calibrated-ish probability across the CVE population, not a certainty for your system. A practical policy combines thresholds, e.g. Opinion "KEV or EPSS ≥ 0.1 → P1; CVSS ≥ 9 and internet-facing → P1; everything else by CVSS band". FIRST publishes percentile alongside probability; percentile is useful for ranking but should not be confused with probability.

6.6 Back-of-envelope numbers for security operations

  • Brute force: a 6-digit OTP has \(10^6\) values; with 5 attempts per code lifetime, an attacker's success chance per code is \(5 \times 10^{-6}\). Without throttling at 100 requests/s, they would enumerate the space in under 3 hours — which is why rate limiting is part of authentication.
  • Token entropy: 128 random bits gives \(2^{128} \approx 3.4\times10^{38}\) values; guessing is infeasible. A 32-bit value (e.g. Random.nextInt()) has 4.3 billion and is brute-forceable.
  • Log volume: Illustrative 2,000 req/s × 1 KB structured log line ≈ 2 MB/s ≈ 170 GB/day. Security logging is a capacity decision; sample access logs, but never sample authentication and authorization events.

package com.example.orders.security;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpMethod;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.oauth2.server.resource.authentication.JwtAuthenticationConverter;
import org.springframework.security.oauth2.server.resource.authentication.JwtGrantedAuthoritiesConverter;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.header.writers.ReferrerPolicyHeaderWriter.ReferrerPolicy;

@Configuration
@EnableMethodSecurity                      // enables @PreAuthorize / @PostAuthorize
public class SecurityConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .securityMatcher("/api/**")
            .authorizeHttpRequests(auth -> auth
                .requestMatchers(HttpMethod.GET, "/api/catalog/**").permitAll()
                .requestMatchers("/api/admin/**").hasAuthority("SCOPE_orders.admin")
                .requestMatchers(HttpMethod.POST, "/api/orders").hasAuthority("SCOPE_orders.write")
                .requestMatchers("/api/orders/**").hasAuthority("SCOPE_orders.read")
                .anyRequest().denyAll())                  // fail-safe default: unknown routes are closed
            .oauth2ResourceServer(rs -> rs.jwt(jwt -> jwt.jwtAuthenticationConverter(jwtAuthConverter())))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            // Bearer-token API with no cookies: CSRF is not exploitable here (see 11.3).
            .csrf(csrf -> csrf.disable())
            .headers(h -> h
                .contentSecurityPolicy(csp -> csp.policyDirectives("default-src 'none'; frame-ancestors 'none'"))
                .referrerPolicy(r -> r.policy(ReferrerPolicy.NO_REFERRER))
                .httpStrictTransportSecurity(hsts -> hsts.includeSubDomains(true).maxAgeInSeconds(31536000)));
        return http.build();
    }

    @Bean
    SecurityFilterChain everythingElse(HttpSecurity http) throws Exception {
        // Second chain for anything not under /api: closed by default.
        http.authorizeHttpRequests(auth -> auth.anyRequest().denyAll());
        return http.build();
    }

    private JwtAuthenticationConverter jwtAuthConverter() {
        JwtGrantedAuthoritiesConverter scopes = new JwtGrantedAuthoritiesConverter(); // "scope" claim -> SCOPE_x
        JwtAuthenticationConverter c = new JwtAuthenticationConverter();
        c.setJwtGrantedAuthoritiesConverter(scopes);
        return c;
    }
}

Note the two chains: the first is selected for /api/**; anything else falls to the second, which denies everything. Actuator runs on the management port, which Spring Boot serves through its own child context; secure that port at the network layer (Kubernetes NetworkPolicy so only Prometheus can reach it) and, if it must be reachable more widely, add a dedicated chain using EndpointRequest.toAnyEndpoint().

import org.springframework.web.bind.annotation.RestControllerAdvice;
import com.example.orders.OrderNotFoundException;

@RestControllerAdvice
public class ApiExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(ApiExceptionHandler.class);

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound() {
        return ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, "Order not found");
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail invalid(MethodArgumentNotValidException e) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, "Invalid request");
        pd.setProperty("fields", e.getBindingResult().getFieldErrors().stream()
                .map(fe -> fe.getField()).distinct().toList());   // names only, never rejected values
        return pd;
    }

    // Needed because the catch-all handler below would otherwise turn an AccessDeniedException
    // thrown by @PreAuthorize into a 500. Map it explicitly to 403.
    @ExceptionHandler(AccessDeniedException.class)
    ProblemDetail denied() {
        return ProblemDetail.forStatusAndDetail(HttpStatus.FORBIDDEN, "Forbidden");
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception e) {
        String incident = java.util.UUID.randomUUID().toString();
        log.error("unhandled exception incidentId={}", incident, e);   // full detail stays server-side
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Internal error");
        pd.setProperty("incidentId", incident);                          // correlatable, non-sensitive
        return pd;
    }
}

7.6 Security audit logging with masking

What to log (OWASP Logging Cheat Sheet, adapted): authentication successes and failures; authorization failures; session/token lifecycle (login, logout, refresh, revocation); input-validation failures that indicate probing; administrative and high-value business actions (refunds, role changes, exports); configuration and security-setting changes; startup/shutdown and changes to logging itself. Each event needs when (UTC, ISO-8601), who (principal ID, client ID, source IP, user agent), what (action, target resource ID), where (service, instance, trace ID) and outcome.

What never to log: passwords (including failed ones — users often type a password into the username field), session IDs, access/refresh tokens, API keys, private keys, full card numbers (PCI DSS), CVVs, bank account numbers, raw government IDs, health data, full request bodies of sensitive endpoints, and encryption keys or connection strings. Treat log data as sensitive anyway: restrict access and set retention.

package com.example.orders;

import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Set;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.slf4j.MDC;
import org.springframework.stereotype.Component;
import static net.logstash.logback.argument.StructuredArguments.entries;

@Component
public class AuditLogger {
    private static final Logger AUDIT = LoggerFactory.getLogger("AUDIT");   // routed to its own appender
    private static final Set<String> FORBIDDEN =
        Set.of("password", "token", "access_token", "refresh_token", "authorization", "secret", "cardNumber", "cvv");

    public void event(String action, String actor, String target, String outcome, Map<String, ?> details) {
        Map<String, Object> safe = new LinkedHashMap<>();
        safe.put("event.action", action);
        safe.put("user.id", actor);
        safe.put("target.id", target);
        safe.put("event.outcome", outcome);
        safe.put("trace.id", MDC.get("traceId"));
        details.forEach((k, v) -> safe.put("detail." + k, FORBIDDEN.contains(k) ? "[REDACTED]" : sanitize(v)));
        AUDIT.info("audit", entries(safe));
    }

    // Prevent log injection: strip CR/LF so attackers cannot forge extra log lines.
    private static Object sanitize(Object v) {
        return (v instanceof String s) ? s.replaceAll("[\\r\\n]", "_") : v;
    }
}

// TokenVerifier validates signature, iss, aud, exp (see Chapter 11.2 for a full JWKS implementation).
type TokenVerifier interface {
	Verify(ctx context.Context, raw string) (*Principal, error)
}

var audit = slog.New(slog.NewJSONHandler(os.Stdout, nil)).With("log.type", "audit")

func securityHeaders(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		h := w.Header()
		h.Set("X-Content-Type-Options", "nosniff")
		h.Set("Content-Security-Policy", "default-src 'none'; frame-ancestors 'none'")
		h.Set("Strict-Transport-Security", "max-age=31536000; includeSubDomains")
		h.Set("Cache-Control", "no-store")
		r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB request cap
		next.ServeHTTP(w, r)
	})
}

func authenticate(v TokenVerifier, next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		raw, ok := strings.CutPrefix(r.Header.Get("Authorization"), "Bearer ")
		if !ok {
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		p, err := v.Verify(r.Context(), raw)
		if err != nil { // any error -> deny (fail closed)
			audit.Info("authn.failure", "event.outcome", "FAILURE")
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		next.ServeHTTP(w, r.WithContext(context.WithValue(r.Context(), principalKey, p)))
	})
}

func requireScope(scope string, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		p, ok := r.Context().Value(principalKey).(*Principal)
		if !ok || !p.Scopes[scope] {
			audit.Info("authz.denied", "scope", scope, "event.outcome", "DENIED")
			http.Error(w, "forbidden", http.StatusForbidden)
			return
		}
		next(w, r)
	}
}

func getOrder(w http.ResponseWriter, r *http.Request) {
	p := r.Context().Value(principalKey).(*Principal)
	id := r.PathValue("id") // Go 1.22+ pattern routing
	// order, err := store.FindByIDAndCustomer(r.Context(), id, p.Subject) // owner-scoped, $1/$2 params
	_ = p
	w.Header().Set("Content-Type", "application/json")
	_ = json.NewEncoder(w).Encode(map[string]string{"id": id})
}

func main() {
	var verifier TokenVerifier // = newJWKSVerifier(...)
	mux := http.NewServeMux()

	}
}

8. Applications: How Engineering Teams Operationalise Security

8.1 Security in the design-doc template

The most cost-effective change most teams can make is adding a "Security & privacy" section to the design-doc template with four prompts: (1) DFD with trust boundaries, (2) assets and data classification, (3) top threats with mitigations (STRIDE table), (4) open risks needing acceptance. A security champion or AppSec engineer reviews it for designs that cross a new boundary. Lightweight is the point: the review happens because it is cheap.

8.2 Security champions

Central AppSec teams are typically far smaller than engineering, so many organisations run a champions programme: one engineer per team with extra training and a direct line to AppSec, who runs threat models, triages scanner findings and spreads secure patterns. The OWASP Security Champions Guide describes the model.

8.3 Paved roads

Platform teams encode the secure defaults of §7 in a company Spring Boot starter (security config, logging, error handling), a base Helm chart (non-root, read-only FS, NetworkPolicy, resource limits), and CI templates (SCA, SAST, SBOM, signing). Teams on the paved road get security "for free"; deviations are visible in review. This is the organisational form of "secure by default".

8.4 Security invariants as tests

Teams that rarely ship access-control bugs write tests for them. With spring-security-test: create two users, have user A create a resource, and assert user B receives 404. Assert that every controller method is covered by an explicit rule (some teams write an ArchUnit test that fails if a @RestController method lacks @PreAuthorize or an explicit allow-list entry).

8.5 Vulnerability management as a product

Mature organisations run vulnerability management with dashboards per team (open findings by priority and age), SLAs agreed with leadership, automated dependency PRs merged by a bot when tests pass (Renovate auto-merge for patch versions), and a monthly review of exceptions. The metric that matters is time to remediate exploited vulnerabilities, not the raw count of open CVEs.

8.6 Detection engineering

Security logs feed a SIEM (Splunk, Elastic Security, Microsoft Sentinel, Google SecOps, or OpenSearch with detection rules). Typical application-level detections: many authentication failures across many usernames from one IP (credential stuffing); one user receiving many 404/403s on sequential IDs (IDOR probing); an admin action outside business hours from a new country; a spike in validation errors on one endpoint; a service account calling an endpoint it never called before.

9. Case Studies

9.1 Equifax (2017): an unpatched framework and blind monitoring Verified

Attackers exploited CVE-2017-5638, a remote-code-execution flaw in Apache Struts' Jakarta multipart parser, in an Equifax online dispute portal. A fix had been available since March 2017; the vulnerable system was not patched, and a subsequent scan failed to find it. The attackers then moved through the network for weeks. According to the US Government Accountability Office report, data on roughly 145 million US consumers was exposed, and an expired certificate on a network traffic-inspection device meant encrypted exfiltration traffic was not being inspected for months. Lessons: asset inventory (you cannot patch what you do not know runs the vulnerable library), patch SLAs with verification, and monitoring that is itself monitored. Maps to OWASP A03 and A09. Source: GAO-18-559, Data Protection: Actions Taken by Equifax and Federal Agencies in Response to the 2017 Breach.

9.2 Log4Shell (2021): the transitive dependency Verified

CVE-2021-44228 in Log4j 2 allowed attacker-controlled strings that were logged to trigger JNDI lookups and load remote code. Because logging user input (a User-Agent header, a username) is ubiquitous, and Log4j 2 was a transitive dependency of a vast number of Java products, exposure was enormous; CISA added it to KEV and issued emergency guidance. Spring Boot's default logging backend is Logback, so plain Spring Boot apps were not affected unless they had opted into log4j-core — a nice example of how defaults shape blast radius. Teams with an SBOM or at least a queryable dependency inventory answered "are we affected?" in hours; others took weeks. Sources: NVD entry for CVE-2021-44228; Spring blog: Log4J2 Vulnerability and Spring Boot.

9.3 Spring4Shell (2022): data binding as attack surface Verified

CVE-2022-22965 affected Spring MVC/WebFlux applications running on JDK 9+; the published exploitation required deployment as a WAR on Apache Tomcat. Spring's data binder allowed a request parameter path to reach class.module.classLoader and manipulate Tomcat's logging configuration to write a web shell. Spring Framework 5.3.18 and 5.2.20 fixed it by restricting binding. Lessons: binding request data onto objects is an injection surface (the same family as mass assignment), and "only exploitable in configuration X" advisories still require you to know your configuration. Source: Spring security advisory CVE-2022-22965.

9.4 MOVEit Transfer (2023): one injection, thousands of victims Verified

CVE-2023-34362 was a SQL injection vulnerability in Progress Software's MOVEit Transfer managed file-transfer product. The Cl0p extortion group exploited it as a zero-day from late May 2023 to install a web shell and steal data from organisations running the product, affecting a very large number of downstream companies and their customers. Lessons: a classic A05 bug in an internet-facing product had supply-chain-scale consequences; internet-facing file-transfer and edge appliances deserve the strictest patch SLAs and exposure reduction. Source: CISA & FBI advisory AA23-158A.

9.5 Threat modeling at scale: Microsoft and OWASP tooling Verified

Microsoft's Security Development Lifecycle has made threat modeling part of product development for two decades and publishes a free DFD-based Threat Modeling Tool that generates STRIDE threats per element; OWASP publishes Threat Dragon, an open-source equivalent. Both show the same practice this chapter teaches: DFD, trust boundaries, STRIDE per element. Sources: Microsoft Threat Modeling Tool documentation; OWASP Threat Dragon.

11.1 Where to put authorization

Opinion Default: URL rules for coarse access + query scoping for ownership + RLS for regulated multi-tenant data. Add a policy engine when three or more services duplicate non-trivial policy.

11.2 Fail open vs fail closed

Fail closed is the security default, but it is an availability trade-off. A sensible pattern: fail closed for authorization and authentication; for non-security dependencies (recommendations, analytics) fail open with degraded responses. When the identity provider's JWKS endpoint is down, continue validating with cached keys (that is not failing open — signatures are still checked) but deny tokens signed with unknown key IDs.

11.3 Patch fast vs patch safely

Fast patching risks regressions; slow patching risks exploitation. Resolve the tension with test coverage and automated rollout (canary + automatic rollback), so that the cost of a patch release is low. Teams that can deploy safely in an hour can afford a "KEV within 72 hours" SLA; teams with a quarterly release train cannot, which is itself the risk to fix.

12. Common Mistakes, Misconceptions and Production Failures

  • "We use Spring Security, so we are secure." Spring Security authenticates and enforces the rules you write. It does not know your ownership model.
  • Returning 403 vs 404 inconsistently. A 403 for someone else's resource and a 404 for a missing one lets attackers enumerate valid IDs. Prefer 404 for objects the caller may not see.
  • Relying on unguessable IDs. UUIDs reduce enumeration but are not access control: IDs leak in URLs, logs, referrers and shared links.
  • Exposing actuator. /actuator/heapdump and /actuator/env have been the root cause of real credential leaks; never expose them on the public port.
  • Catch-all handlers that swallow AccessDeniedException and return 500 or, worse, 200 with an empty body.
  • Logging the Authorization header via a request-logging filter (e.g. CommonsRequestLoggingFilter with setIncludeHeaders(true)).
  • Treating internal traffic as trusted. "It's behind the VPN" fails the moment one internal service is compromised. Zero trust means authenticating service-to-service calls too.
  • Suppressing scanner findings forever. Suppressions need a reason, an owner and an expiry.
  • Prioritising by CVSS alone and drowning in "criticals" in test dependencies while an exploited high on the login path waits.
  • Threat models as one-off documents that are never revisited after the design changes.
  • Security as a final gate. A penetration test two weeks before launch finds design flaws when they are most expensive to fix.
  • Self-invocation bypassing method security: a public method without @PreAuthorize calls this.adminOnly(); the proxy is never involved.

13.2 Monitoring and alerting

Ship audit events to a separate index/stream with restricted access and longer retention than debug logs. Alert on: authentication-failure rate per source and per account; authorization-denied spikes; admin actions; new egress destinations; WAF block spikes; and the absence of logs (a silent service is a signal). Expose security counters as Micrometer metrics so they appear on dashboards next to latency and error rate.

13.3 Log integrity and privacy

Protect logs against tampering (write-once storage such as S3 Object Lock, or forwarding to a SIEM that the application cannot modify) and against over-collection (GDPR purpose limitation; pseudonymise user IDs where possible). Strip CR/LF from user-controlled values or use structured JSON logging so attackers cannot inject fake log lines.

13.4 Maintainability

Centralise security configuration in a shared starter with tests; version it; and upgrade Spring Boot regularly. Spring Boot open-source support windows are relatively short, so a service stuck on an end-of-life version stops receiving security fixes unless you buy extended support. 13.5 Performance

Security controls have costs you should measure: bcrypt at cost 12 takes on the order of hundreds of milliseconds per hash on typical server hardware — fine for login, catastrophic if accidentally applied per API request; JWT validation with cached JWKS is sub-millisecond; external policy calls add a network hop (cache decisions with care, short TTL). Rate limiting and request size limits are also performance controls against resource exhaustion.

15. Interview Questions

Conceptual What is the difference between authentication, authorization and accounting? Which is most often broken in practice, and why?

Authentication establishes identity, authorization decides whether that identity may perform an action on a resource, accounting records what happened. Authorization is most often broken because it is business logic specific to each resource; frameworks provide the mechanism (filter chain, @PreAuthorize) but not the ownership rules, so every new endpoint is a new opportunity to forget a check. Hence Broken Access Control is OWASP A01.

Conceptual Explain defense in depth and when it fails.

Layer independent controls so an attacker must defeat several. It fails when layers share a common failure mode (all trust the same header or the same compromised identity provider), giving an illusion of depth. Good layering uses diverse mechanisms: network policy, application authorization, database RLS, monitoring.

Conceptual What changed between the OWASP Top 10 2021 and 2025?

Security Misconfiguration rose to #2; Vulnerable and Outdated Components became the broader Software Supply Chain Failures at #3; SSRF was merged into Broken Access Control (still #1); Cryptographic Failures, Injection and Insecure Design moved to #4–#6; Authentication Failures stayed at #7 with a simplified name; Logging and Monitoring became Logging and Alerting Failures; and Mishandling of Exceptional Conditions was added at #10.

Architecture Walk me through threat modeling a new multi-tenant document-upload feature.

Draw a DFD: browser → gateway → upload service → object store, plus a virus-scan worker and a metadata DB; mark boundaries. STRIDE: spoofing (token theft — short-lived tokens), tampering (content-type spoofing — validate magic bytes, store with fixed content type), repudiation (audit uploads/downloads), information disclosure (cross-tenant reads — tenant prefix in keys, scoped IAM, owner-scoped metadata queries, pre-signed URLs with short TTL), DoS (size limits, quotas, zip-bomb protection), elevation (malicious files executing in a processor — sandbox the scanner, never serve uploads from the app origin). Rate, decide, write tests for tenant isolation.

Architecture Where should ownership checks live in a Spring application, and why not only in the API gateway?

In the service/query layer (and optionally RLS), because only there is the ownership data available and only there are all entry paths (HTTP, messaging, batch) covered. The gateway sees tokens and paths, not database rows, and internal callers may bypass it.

Coding Show how you would prevent an exception in a permission check from granting access.

Catch only the expected exception types, return false (deny), increment a metric and alert; never return true in a catch block. Set a timeout on remote policy calls so slowness is converted into a deny rather than a hang. Integration-test the failure path by stubbing the policy client to throw.

Coding What must never appear in logs, and how do you enforce that in code?

Passwords, tokens, session IDs, API keys, keys, full card data, sensitive personal data. Enforce with structured logging and a central audit helper that redacts by key name; avoid logging whole request bodies or headers; add a Logback/Log4j masking converter as a safety net; scan logs in CI tests for token patterns; restrict log access.

Scenario A new critical CVE drops in a library you use, on a Friday evening. What do you do?

Determine exposure via SBOM/dependency inventory (which services, which versions, which are internet-facing). Check KEV/EPSS and vendor advisories for exploitation status and mitigations (config flags, WAF rules). Apply temporary mitigations for exposed services immediately; patch and deploy via canary; verify running images no longer contain the vulnerable version; search logs for indicators of exploitation since disclosure; communicate status. Post-incident: measure time-to-remediate and fix inventory gaps.

Scenario Your scanner shows 1,400 open vulnerabilities. Leadership wants zero. How do you respond?

Reframe the goal as risk-based: zero exploited (KEV) and reachable criticals within SLA, and a downward trend in mean time to remediate. Triage with KEV/EPSS/reachability, remove noise (test scope, unshipped images, duplicates across images), automate upgrades for the long tail with Renovate, fix base images (one base-image update often clears hundreds of findings), and report by priority bucket rather than raw count.

Behavioral Tell me about a time you pushed back on a design for security reasons.

Structure with STAR: describe the design (e.g. a partner API that trusted a client-supplied tenant ID), the risk in concrete terms (one partner reading another's data), the alternative you proposed (tenant derived from the token's client ID; integration test), how you got agreement (showed a one-page threat model, offered to implement the change), and the outcome. Emphasise collaboration and cost-aware proposals, not vetoes.

16. Knowledge Check

  • CIA (+ authenticity, non-repudiation) defines what you protect; AAA defines how identities are established, checked and recorded.
  • Least privilege limits blast radius; defense in depth needs independent layers; fail-safe defaults mean deny on error.
  • Threat model with the four questions: DFD with trust boundaries, STRIDE per element, mitigate or accept, validate with tests.
  • OWASP Top 10:2025: Broken Access Control #1 (now including SSRF), Misconfiguration #2, Supply Chain #3, new #10 for exceptional conditions.
  • Log security events with who/what/when/where/outcome; never log secrets, tokens or passwords; alert, don't just store.
  • Prioritise vulnerabilities by KEV, then EPSS and reachability, then CVSS — and verify remediation in running workloads.

A customer can read another customer's invoice by changing the ID in the URL. Which OWASP Top 10:2025 category is this?

  1. A05 Injection
  2. A07 Authentication Failures
  3. A01 Broken Access Control
  4. A06 Insecure Design
The caller is correctly authenticated but acts outside their permissions on a specific object (IDOR/BOLA) — the canonical A01 case.

Which STRIDE categories apply to a data store element under "STRIDE per element"?

  1. Spoofing and Repudiation only
  2. Tampering, Information disclosure, Denial of service (and Repudiation for logs)
  3. All six
  4. Elevation of privilege only
Data stores can be modified, read and made unavailable; repudiation applies when the store is an audit log. Spoofing applies to entities and processes.

Which signal most strongly justifies emergency patching?

  1. CVSS base score 9.8
  2. The CVE is in a test dependency
  3. EPSS percentile above 50
  4. The CVE is in CISA KEV and the component is internet-facing
KEV means confirmed exploitation in the wild; combined with reachability it is the highest-priority signal. CVSS measures potential severity, not likelihood.

A permission evaluator returns true when the policy service times out. Which principle and 2025 category does this violate?

  1. Fail-safe defaults; A10 Mishandling of Exceptional Conditions
  2. Least privilege; A04 Cryptographic Failures
  3. Economy of mechanism; A09 Logging & Alerting Failures
  4. Open design; A03 Supply Chain Failures
Failing open on an error is the textbook violation of fail-safe defaults and is the type of flaw A10 was introduced to capture.

Three independent controls are each bypassed with probability 0.2. What is the probability all three are bypassed, and what assumption could make the real value much higher?

  1. 0.6; that controls are layered
  2. 0.008; that the controls are independent
  3. 0.2; that attackers are rational
  4. 0.04; that CVSS is accurate
0.2³ = 0.008 under independence. Shared failure modes (common trust anchor, same misconfiguration) correlate the controls and push the probability toward 0.2.

Which of these is safe to include in a security audit log event?

  1. The failed password, to detect typos
  2. The full Authorization header, for forensics
  3. The principal ID, action, target ID, outcome and trace ID
  4. The session cookie value, to correlate requests
Credentials and session identifiers must never be logged; use trace IDs for correlation.
