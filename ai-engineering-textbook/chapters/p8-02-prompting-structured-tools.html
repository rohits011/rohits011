Prompt Engineering, Structured Outputs, Tool Use & LLM APIs

The prompt is your interface definition, the JSON schema is your response contract, tools are your RPC surface, and the HTTP API is an unreliable, rate-limited, metered remote dependency. This chapter treats each of those as an engineering problem and ends with a production-grade Spring Boot LLM client that you could put in front of real traffic.

  • Prerequisites: Chapter 1 (tokens, sampling, context); Resilience4j and Spring Boot configuration; basic JSON Schema.
  • You will be able to: write and version prompts like code; get schema-valid JSON reliably; implement a correct tool-use loop including parallel calls and errors; stream, batch and cache requests; handle rate limits and timeouts; and choose between the raw SDKs, Spring AI and LangChain4j.

1. Introduction: From Chat Box to Contract

Typing a question into a chat window and integrating an LLM into a payment-dispute workflow are different activities. In the chat window, a vague question and an approximately right answer are fine; a human reads the response and adapts. In a service, the LLM's output feeds code: a switch on a category, a database write, a call to another microservice. That code needs contracts — and LLMs, by default, offer none. The work of this chapter is to impose contracts on a probabilistic component, layer by layer:

  • Prompts define the task precisely, the way a well-written interface Javadoc does, and are versioned and tested like code.
  • Structured outputs force responses into a JSON schema, so parsing never fails and fields are typed.
  • Tool use (function calling) lets the model request actions — query an order, check inventory — through a typed interface you control, instead of inventing facts.
  • The API layer handles the boring but vital concerns: streaming, rate limits, retries, timeouts, cost accounting and fallback.

Bridging from Java & Spring Boot

What you already know
Thymeleaf or FreeMarker templates rendered with a model map; OpenFeign or RestClient calls to remote services described by OpenAPI; Jackson binding JSON to records with Bean Validation (@NotNull, @Pattern); Resilience4j @Retry, @CircuitBreaker, @Bulkhead and @TimeLimiter around flaky dependencies; RPC frameworks such as gRPC where a client calls a typed method on a server.
Why that is not enough
A prompt template looks like a Thymeleaf template, but the "renderer" on the other side interprets it with judgement: wording changes behaviour, and there is no compiler. Tool calling looks like RPC, but the caller is the model, which decides when to call, with which arguments, and may call the wrong tool or invent arguments. Jackson can bind the JSON, but only if the model produced valid JSON. Resilience patterns apply, but retries are not idempotent in meaning (each retry may give a different answer) and a slow call is not necessarily a failed one.
The modern approach
Version prompts as artefacts with tests; use provider-side structured outputs (constrained decoding) plus local validation; design tools like public APIs with least privilege; wrap the client with timeouts, bounded jittered retries honouring retry-after, circuit breakers, bulkheads and model fallbacks; stream for latency; batch for throughput; cache prefixes for cost; log every request's usage.
Where Python and Go fit
Python is the fastest place to iterate on prompts and evaluation, and the Anthropic Python SDK's Pydantic integration is excellent for schema work. Go suits the gateway in front of all model traffic (Chapter 5). Spring AI and LangChain4j bring these concepts into idiomatic Spring beans for business services.
In production
Prompts live in a repository with owners and changelogs; every response is validated; tool executions are authorised per user; and dashboards show latency percentiles, stop reasons, retry rates, circuit-breaker state and cost per feature.
Use it when / avoid it when
Use structured outputs and tools whenever code consumes the result. Avoid free-text parsing with regexes, avoid giving the model tools with more authority than the calling user, and avoid adding an agent loop where a single call with a schema suffices.

3. Fundamentals

3.1 Anatomy of a request: system, user, assistant

A modern messages request has three kinds of content. The system prompt sets the operator's instructions: role, task, rules, output format, tool-use policy. It is the closest thing to configuration. User messages carry end-user input and attached context (documents, images, tool results). Assistant messages carry the model's previous turns, which you resend to continue a conversation — the API is stateless. A useful mental model is that the system prompt is your @Service code and the user message is the request payload: the former is trusted and versioned, the latter is untrusted data.

3.2 Writing instructions that work

Current frontier models follow instructions literally and well, so most prompt quality problems are specification problems. Principles that consistently help Opinion:

  • State the goal and the audience. "Classify the support ticket so the routing service can assign it to a queue" beats "Classify this." Context about why lets the model handle edge cases sensibly.
  • Define every label and boundary. If categories are BILLING, TECHNICAL, ACCOUNT, say what goes where and what to do with tickets that span two. Ambiguous specs produce inconsistent outputs no decoding setting can fix.
  • Separate instructions from data with delimiters. Wrap documents in XML-style tags (<ticket>…</ticket>) and refer to them by name. It improves accuracy and is a first, partial defence against injected instructions inside data.
  • Say what to do, not only what to avoid, and give the fallback: "If the ticket does not contain enough information, return UNKNOWN with a one-sentence reason."
  • Specify the output shape — ideally via a schema (§3.8) rather than prose.
  • Avoid shouting and over-constraining. Prompts written for older models often contain capitalised warnings and long lists of prohibitions; newer models over-apply them. Remove rules that no longer earn their place, and test.

3.3 Few-shot examples

Examples (input → output pairs) demonstrate format and decision boundaries more efficiently than prose. Three to five diverse examples covering edge cases usually suffice. Pitfalls: the model copies surface features of examples (length, vocabulary, even specific values), so vary them; examples consume input tokens on every request (cache them); and examples encode decisions — if an example is wrong, you have trained the wrong behaviour into every call. Keep examples in a versioned file alongside the prompt and include them in evaluation.

3.4 Chain-of-thought and extended thinking

Asking a model to reason step by step before answering improves performance on multi-step problems, because each generated reasoning token becomes context for the next (Chapter 1, §3.9). With reasoning models you no longer need to ask: the model thinks internally before responding, and you control how much via an effort or budget parameter. On Anthropic's current models, for example, thinking is adaptive and controlled with output_config.effort; the raw reasoning is not returned — you may opt into a summary. Version-sensitive · checked Nov 2026 Two engineering rules: thinking tokens are billed as output tokens, so set effort per route; and if code consumes the result, keep reasoning out of the parsed output — let the model think internally and return only the structured answer.

3.5 Decomposition and prompt chaining

A single prompt that extracts, validates, decides and writes a customer email is hard to debug and evaluate. Split it into a pipeline: extract fields (structured output) → validate in code → decide (small model or rules) → draft (LLM) → check (rules or a judge). Each step has a narrow contract and its own tests, can use a differently priced model, and can be retried independently. This is the same reasoning that makes you split a god-class service — and it is usually better than an autonomous agent for well-understood processes (Chapter 6).

3.6 Prompt templates and versioning

A prompt template is a text with placeholders, rendered per request — the Thymeleaf of LLM work. Spring AI's PromptTemplate uses StringTemplate syntax ({name}); LangChain4j uses {{name}} in @UserMessage; Python teams use f-strings or Jinja. Treat templates as code:

  • Store them as files in the repository (for example src/main/resources/prompts/ticket-classifier/v3.st), never as string literals scattered through services.
  • Give each a version identifier and log it with every request, so you can correlate quality changes with prompt changes.
  • Escape user-provided values, keep untrusted content inside delimiters, and never interpolate user input into the system prompt.
  • Gate changes with an evaluation run in CI (Chapter 5), exactly as you gate code changes with tests.
  • Keep the static parts (instructions, examples, tool definitions) first and the variable parts last — this maximises prompt-cache hits.

3.7 Prompt caching

Most requests in a feature share a long, identical prefix: system prompt, examples, tool definitions, perhaps a reference document. Prompt caching lets the provider store the KV cache for that prefix and reuse it on subsequent requests, reducing both cost and time to first token. Mechanics differ by provider: Anthropic uses explicit cache_control breakpoints (or a top-level automatic mode) with a default five-minute lifetime refreshed on each hit and an optional one-hour lifetime; writes cost more than normal input (1.25× for five minutes, 2× for one hour) and reads cost a small fraction of the input price (0.1× on most models, lower on some newer ones). Other providers cache matching prefixes automatically. Version-sensitive · checked Nov 2026

The cache is a byte-exact prefix match. Anything that varies — a timestamp in the system prompt, tool definitions serialised in a different order, a per-request ID near the top — invalidates everything after it. Design for caching: static content first, deterministic serialisation, variable content last, and verify with the usage fields (cache_read_input_tokens) that hits are actually happening.

3.8 Structured outputs

There are three generations of "get JSON back":

  1. Prompt-only: "Respond with JSON matching this example." Works most of the time; fails occasionally with prose preambles, trailing commas, truncated output or missing fields.
  2. JSON mode: the provider guarantees syntactically valid JSON, but not that it matches your schema.
  3. Schema-constrained output: you supply a JSON Schema, and the provider uses constrained decoding so that only tokens consistent with the schema can be generated. The result always parses and has the required fields and types. Anthropic exposes this as output_config.format with type: "json_schema" (and SDK helpers like messages.parse() with a Pydantic model); OpenAI exposes strict JSON Schema response formats; open-model servers such as vLLM support guided decoding with JSON Schema or grammars.

Constrained decoding guarantees syntax and shape, not truth. The model can still put the wrong category in a valid enum, hallucinate a plausible invoice number, or produce a string that fails your business rules. Supported schema features are also a subset of JSON Schema (for example, required additionalProperties: false, limits on recursion or certain formats), so check the provider's documentation. You therefore still need local validation: Pydantic validators in Python, Bean Validation annotations on Java records, plus business checks (does this order ID exist? does the total match the line items?). When validation fails, the standard pattern is a repair retry: send the validation error back to the model and ask for a corrected output, at most once or twice, then fail closed.

One more failure mode: if generation hits max_tokens, the JSON is truncated regardless of constraints. Check stop_reason before parsing and size max_tokens for the largest legitimate output.

3.9 Function calling and tool use

Tool use lets the model ask your code to do something. You describe tools — name, natural-language description, JSON Schema for input — in the request. The model may respond with a tool_use block naming a tool and arguments instead of (or as well as) text, with stop_reason set to tool_use. Your code executes the tool, then sends the result back in a tool_result block in the next user message, referencing the call's ID. The model then continues — perhaps calling more tools, perhaps answering. The model never executes anything itself; it only emits structured requests. Security follows from this: every tool call passes through your code, which can validate, authorise, rate-limit and audit it.

Key details of a correct loop:

  • Append the full assistant content (including tool_use blocks and any thinking blocks) to the history before adding tool results; the API validates that every result matches a call.
  • Parallel tool calls: a single assistant turn may contain several tool_use blocks (for example, look up three orders at once). Execute them concurrently, then return all results in a single user message.
  • Errors are results: if a tool fails, return a tool_result with is_error: true and a useful message ("order 123 not found; valid IDs look like ORD-######"). The model can recover; dropping the result breaks the conversation.
  • Bound the loop: cap iterations and total tokens, and detect repeated identical calls, to prevent runaway costs.
  • Strict schemas: setting strict: true on a tool (where supported) applies constrained decoding to the arguments, so they always validate against the schema. Still validate business rules.
  • Tool choice: auto lets the model decide; none forbids tools; some APIs allow forcing a specific tool, but several current models reject forced tool choice — use structured outputs when you only wanted JSON. Version-sensitive · checked Nov 2026

3.10 Designing tool schemas

Tool definitions are prompts: the model chooses tools from their names and descriptions, so write them for a reader who has never seen your codebase. Good practice Opinion:

  • Prefer a few well-scoped tools with clear purposes over dozens of thin CRUD wrappers. "get_order_status(order_id)" beats exposing your entire order service.
  • Describe when to use the tool, what it returns, and its limits ("returns at most 20 results; use cursor for more").
  • Use enums and formats for constrained parameters; avoid free-form strings where an ID pattern is known.
  • Return compact, relevant results — not raw 50 KB JSON payloads, which cost tokens and bury the signal.
  • Make write operations explicit and separately authorised; consider requiring human confirmation for destructive or financial actions (Chapter 6).
  • Keep the tool list deterministic in order and content so prompt caching works.

3.11 The messages API shape

Across providers, chat APIs share a shape: model ID, a list of messages with roles and typed content blocks (text, image, document, tool use, tool result), an optional system prompt, tool definitions, output constraints and limits, and a response with content blocks, a stop reason and usage. Anthropic's endpoint is POST /v1/messages with a required max_tokens; OpenAI's current primary interface is its Responses API, with Chat Completions still widely used; many open-model servers implement an OpenAI-compatible endpoint. Differences matter at the edges — where the system prompt goes, how tool results are represented, what usage fields mean — which is precisely what client abstractions like Spring AI and LangChain4j smooth over.

3.12 Streaming with server-sent events

With streaming enabled, the response is a text/event-stream. Anthropic's stream, for example, emits message_start, then for each content block a content_block_start, many content_block_delta events (text deltas, or partial JSON for tool inputs), and content_block_stop, followed by message_delta (stop reason and final usage) and message_stop; ping events may appear and an error event can arrive mid-stream. Practical consequences: an HTTP 200 does not mean success — errors can arrive inside the stream; your read timeout should be an idle timeout between events plus an overall deadline; and to relay to a browser you re-emit events from a Spring MVC SseEmitter or a WebFlux Flux<ServerSentEvent>.

3.13 Batch APIs

For work that does not need an immediate answer — nightly classification of the day's tickets, backfilling embeddings, evaluation runs — batch APIs accept thousands of requests in one submission and return results asynchronously within a deadline (Anthropic: most batches within an hour, at most 24 hours, results in any order keyed by custom_id) at a substantial discount (50% at both Anthropic and OpenAI). Version-sensitive · checked Nov 2026 This is the LLM equivalent of moving work from a synchronous endpoint to a Spring Batch job: cheaper, more throughput, no latency guarantee.

3.14 Rate limits

Providers limit requests per minute and tokens per minute (often separately for input and output), per organisation, model and tier; some also cap concurrent requests or have separate limits for special modes. Exceeding them yields HTTP 429 with a retry-after header; overloaded upstream capacity may yield a 5xx or provider-specific "overloaded" error. Treat token rate limits as a shared quota: a single batch job can starve your interactive traffic, so isolate workloads by API key or workspace and apply your own client-side rate limiting and bulkheads.

3.15 Retries, backoff and timeouts

Retry only what is retryable: 429, 408, 409 (where documented), 5xx, overloaded errors and connection failures. Never retry 400 (bad request), 401/403 (auth), 404, or 413 (too large) — they will fail again and waste quota. Use exponential backoff with full jitter, honour retry-after, cap attempts (2–3), and cap total time with a deadline. Remember that official SDKs retry by default (the Anthropic SDKs retry twice by default); if you add Resilience4j retries on top without disabling the SDK's, you get multiplicative retry storms. Pick one layer. For timeouts, distinguish connection timeout (short), idle/read timeout between streamed events (tens of seconds), and the overall request deadline (driven by your SLO and output size; long generations can legitimately take minutes).

3.16 Token accounting

Every response reports usage: input tokens, output tokens, and cache creation/read tokens. Log these with the model ID, prompt version, feature, tenant and request ID, and compute cost from a price table in configuration. Counting endpoints let you estimate before sending. Aggregated, this becomes your LLM FinOps dashboard and the basis for per-tenant quotas — and it is also your best early-warning system for runaway loops and abuse.

4. Internal Working

4.1 How constrained decoding enforces a schema

Recall from Chapter 1 that at each step the model produces logits for every token, and a processing pipeline transforms them before sampling. Constrained decoding inserts a mask into that pipeline. The schema is compiled ahead of time into a grammar — conceptually a state machine over characters — and then into a structure that answers, for the current state, "which tokens are allowed next?" Tokens that would make the output invalid get a logit of negative infinity and therefore zero probability.

Walk through a tiny schema {"type":"object","properties":{"priority":{"enum":["LOW","HIGH"]}},"required":["priority"],"additionalProperties":false}. At the start, only tokens beginning with { (and allowed whitespace) are permitted. After {, only the key "priority" can follow. After the colon, only tokens that are prefixes of "LOW" or "HIGH". Then only }. The model still chooses which enum value based on its learned probabilities; the mask only removes invalid options. Two subtleties make this hard to implement: tokens span multiple characters, so the engine must check whether each multi-character token keeps the automaton in a valid state; and doing that for a vocabulary of 100K+ tokens at every step must be fast, so engines precompute token-to-transition tables. Schema compilation is why the first request with a new schema can be slower, and why providers cache compiled grammars and limit schema complexity.

There is a quality caveat: forcing a model off its preferred path can push it into low-probability continuations. A schema that demands a field before the model has "seen" the reasoning it needs (for example, verdict before evidence) can lower accuracy. Order fields the way a careful human would fill them in: evidence first, conclusion last.

4.2 Tool calls are just tokens

Under the hood, tool definitions are rendered into the prompt in a format the model was post-trained on, and a tool call is a span of generated tokens in a special format that the provider parses into a tool_use block. Consequences: tool definitions consume input tokens on every request; models differ in how well they choose tools and fill arguments (it is a learned skill); "strict" tool mode applies constrained decoding to the argument span; and the provider stops generation when the call is complete so your code can execute it. The model has no access to your systems — it has only the text of the tool result you send back, which is why result content is also a prompt-injection surface.

4.3 Inside prompt caching

When a request marks a cache breakpoint, the provider hashes the prefix up to that point (tools, then system, then messages, in render order). On a miss, prefill runs normally and the KV cache for the prefix is stored (a "cache write"). On a later request whose prefix hashes identically, the stored KV entries are loaded and prefill runs only on the remaining tokens (a "cache read"). Because the KV cache at position i depends on every token before it, a single changed byte early in the prompt changes all subsequent entries — hence the byte-exact prefix rule. Entries are scoped to a model (and typically organisation), so switching models or effort mid-conversation can forfeit the cache. A write becomes readable only once the first response has begun, so many parallel requests with a cold cache all pay full price; warm the cache with one request first.

Tool input arrives as partial JSON fragments that are only valid once concatenated, so do not execute a tool until its block has stopped (the SDKs accumulate this for you). The final usage and stop reason arrive at the end, so a client that disconnects early loses them.

4.5 Where retries actually happen

In a typical Spring service there are up to four retry layers: the HTTP client (OkHttp can retry connection failures), the provider SDK (retries 408/409/429/5xx by default), your resilience layer (Resilience4j), and the caller (a message consumer redelivering on exception). Each layer multiplies attempts: 3 × 3 × 3 is 27 calls for one user action during an outage — the textbook retry storm. Choose a single owner for retries of LLM calls (this chapter's wrapper disables SDK retries and owns them in Resilience4j), and make outer layers fail fast while the circuit is open.

5. Architecture

5.1 The tool-use loop

Reading the diagram: the model requests two calls in one turn; the service executes both concurrently using the end user's permissions (never a superuser service account), then returns both results — including the error — in a single user message. The model turns the partial failure into a helpful answer. Note the service, not the model, holds all authority; the model only proposes calls.

5.2 Structured output with validation and repair

Reading the diagram: schema enforcement removes parse failures but not semantic ones, so validation remains. The repair loop sends the specific validation errors back, which works far better than blindly retrying. "Fail closed" means routing to a safe default or a human queue instead of persisting a dubious value — the LLM equivalent of a dead-letter topic.

5.3 A resilient client inside a Spring Boot service

Reading the diagram: retry is the outermost decorator, so every individual attempt passes through — and is recorded by — the circuit breaker (one per model), and once the breaker opens the retry sees a fast CallNotPermittedException that it must not retry; the bulkhead is innermost, so a permit is held only during an actual call, not while sleeping between retries, and a slow model cannot exhaust your request threads. The SDK's own retries are disabled to avoid multiplication. This is the same nesting Resilience4j's Spring Boot annotations use by default (Retry around CircuitBreaker around Bulkhead). Validation and metrics are part of the client contract, not afterthoughts.

5.4 Interactive: the circuit breaker

What to try: raise the failure rate past the threshold and watch the breaker open; while open, calls fail fast — for an LLM dependency this is where you route to a fallback model. Then let the wait duration elapse and watch half-open probes decide whether to close again. Consider how you would tune it for LLMs: calls are slow (seconds), so use a slow-call threshold as well as an error threshold, and size the sliding window by count rather than time when traffic is low.

6. The Math: Retries, Caching Break-even and Capacity

6.1 Exponential backoff with full jitter

Intuition: wait longer after each failure, but randomise the wait so thousands of clients that failed together do not retry together. For attempt \(n\) (starting at 1), base delay \(b\) and cap \(c\):

\[ \text{sleep}_n \sim \text{Uniform}\big(0,\ \min(c,\ b \cdot 2^{n-1})\big) \]

If the server sends retry-after = \(r\) seconds, use \(\max(r, \text{sleep}_n)\). With \(b = 1\) s and \(c = 20\) s, three attempts wait on average 0.5, 1 and 2 seconds.

6.2 Does retrying help?

If attempts fail independently with probability \(q\), success within \(k\) attempts is \(1 - q^k\). With \(q = 0.1\), two attempts give 99%, three give 99.9%. But failures during an outage or rate-limit event are highly correlated, so the real benefit is smaller and the cost is extra load on a struggling dependency. That is why retries need caps, jitter and a circuit breaker; the expected number of calls per request is \(\sum_{i=0}^{k-1} q^i\), which approaches \(k\) as \(q \to 1\) — exactly when you least want extra calls.

6.3 Prompt-cache break-even

Let a cacheable prefix have \(P\) tokens, input price \(p\), write multiplier \(w\) and read multiplier \(r\). Over \(n\) requests that share the prefix within the cache lifetime, cost with caching is \(P p (w + (n-1) r)\) versus \(P p\, n\) without. Caching wins when \(w + (n-1) r < n\). With Anthropic's five-minute cache (\(w = 1.25\), \(r = 0.1\)) this holds from \(n = 2\): \(1.25 + 0.1 = 1.35 < 2\). With the one-hour cache (\(w = 2\)): \(n = 3\) gives \(2 + 0.2 = 2.2 < 3\). Version-sensitive · checked Nov 2026 For a 4,000-token system prompt reused 1,000 times, caching cuts that prefix's cost to roughly \( (1.25 + 999 \times 0.1)/1000 \approx 10\% \) of uncached.

6.4 Capacity planning with Little's law

Little's law: average concurrency \(L = \lambda W\) (arrival rate × time in system). If a feature receives \(\lambda = 20\) requests/s and each LLM call takes \(W = 6\) s, you have on average 120 calls in flight. With blocking platform threads, that is 120 threads parked on I/O — use virtual threads (Java 21+, spring.threads.virtual.enabled=true) or reactive streaming, and size the bulkhead above the expected concurrency with headroom. Tokens-per-minute limits translate similarly: 20 req/s × 60 × 3,000 input tokens = 3.6M input tokens/min, which you must compare against your rate limit before launch.

6.5 Validation-retry expectation

If a structured response fails business validation with probability \(v\) and one repair attempt succeeds with probability \(s\), the expected calls per request are \(1 + v\), and the residual failure rate after one repair is \(v (1 - s)\). With \(v = 0.03\), \(s = 0.8\): 1.03 calls on average and 0.6% routed to humans. Measure \(v\) per prompt version; a jump in \(v\) after a model upgrade is a regression signal.

7.2 Structured output with Pydantic, business validation and one repair (Python)

"""Ticket triage with schema-constrained output plus semantic validation."""
import os
from enum import Enum

import anthropic
from pydantic import BaseModel, Field, ValidationError, field_validator

MODEL = os.getenv("LLM_MODEL", "claude-opus-5-5")
client = anthropic.Anthropic()


class Category(str, Enum):
    BILLING = "BILLING"
    TECHNICAL = "TECHNICAL"
    ACCOUNT = "ACCOUNT"
    UNKNOWN = "UNKNOWN"


class Triage(BaseModel):
    # Evidence before verdict: let the model ground its decision first.
    evidence: str = Field(description="Quote the sentence(s) that justify the category")
    category: Category
    priority: int = Field(description="1 (urgent) to 4 (low)")
    order_ids: list[str] = Field(description="Order IDs mentioned, format ORD-######")

    @field_validator("priority")
    @classmethod
    def priority_range(cls, v: int) -> int:
        if not 1 <= v <= 4:
            raise ValueError("priority must be between 1 and 4")
        return v

    @field_validator("order_ids")
    @classmethod
    def order_format(cls, ids: list[str]) -> list[str]:
        bad = [i for i in ids if not (i.startswith("ORD-") and len(i) == 10 and i[4:].isdigit())]
        if bad:
            raise ValueError(f"invalid order ids {bad}; expected ORD- followed by 6 digits")
        return ids


SYSTEM = """You triage customer support tickets for an e-commerce platform.
Categories: BILLING (payments, refunds, invoices), TECHNICAL (app errors, login failures caused
by bugs, performance), ACCOUNT (profile, password resets, account closure). If the ticket
spans categories, choose the one the customer needs resolved first. If there is not enough
information, use UNKNOWN. Priority 1 means money lost or account locked right now."""


def triage(ticket: str, max_repairs: int = 1) -> Triage:
    messages = [{"role": "user", "content": f"<ticket>\n{ticket}\n</ticket>"}]
    for attempt in range(max_repairs + 1):
        response = client.messages.parse(
            model=MODEL, max_tokens=1024, system=SYSTEM,
            messages=messages, output_format=Triage,
        )
        if response.stop_reason != "end_turn":
            raise RuntimeError(f"unexpected stop_reason {response.stop_reason}")
        try:
            # parsed_output is already schema-shaped; re-validate to run our custom rules
            return Triage.model_validate(response.parsed_output.model_dump())
        except ValidationError as e:
            if attempt == max_repairs:
                raise
            messages += [
                {"role": "assistant", "content": response.content},
                {"role": "user", "content": f"Your output failed validation:\n{e}\n"
                                            "Return a corrected result."},
            ]
    raise AssertionError("unreachable")


if __name__ == "__main__":
    print(triage("I was charged twice for ORD-004211 and ORD-4212!! Fix this now.").model_dump_json(indent=2))

The schema guarantees parseable output with an allowed category; Pydantic validators enforce what a schema cannot (the order-ID pattern here is deliberately checked in code to show the repair loop — with a well-designed prompt it rarely triggers). The repair message quotes the precise validation error, which models fix far more reliably than a generic "try again."

7.3 A correct tool-use loop with parallel calls and errors (Python)

"""Manual tool loop: parallel execution, is_error results, iteration and cost caps."""
import json
import os
from concurrent.futures import ThreadPoolExecutor

import anthropic

MODEL = os.getenv("LLM_MODEL", "claude-opus-5-5")
client = anthropic.Anthropic()

ORDERS = {"ORD-000001": "SHIPPED", "ORD-000002": "PROCESSING"}  # stand-in for a service call

TOOLS = [{
    "name": "get_order_status",
    "description": ("Look up the current fulfilment status of one order for the signed-in "
                    "customer. Use when the customer asks where an order is. Returns one of "
                    "PROCESSING, SHIPPED, DELIVERED, CANCELLED."),
    "strict": True,
    "input_schema": {
        "type": "object",
        "properties": {"order_id": {"type": "string", "description": "Format ORD-######"}},
        "required": ["order_id"],
        "additionalProperties": False,
    },
}]


class ToolError(Exception):
    pass


def get_order_status(order_id: str, *, customer_id: str) -> dict:
    # Authorisation happens HERE, with the end user's identity, never in the prompt.
    if order_id not in ORDERS:
        raise ToolError(f"Order {order_id} not found for this customer.")
    return {"order_id": order_id, "status": ORDERS[order_id]}


HANDLERS = {"get_order_status": get_order_status}


def run_tool(block, customer_id: str) -> dict:
    try:
        handler = HANDLERS[block.name]
        result = handler(**block.input, customer_id=customer_id)
        return {"type": "tool_result", "tool_use_id": block.id, "content": json.dumps(result)}
    except (ToolError, KeyError, TypeError) as e:
        return {"type": "tool_result", "tool_use_id": block.id, "content": str(e), "is_error": True}


def answer(question: str, customer_id: str, max_iterations: int = 6,
           max_output_tokens_total: int = 8000) -> str:
    messages = [{"role": "user", "content": question}]
    spent = 0
    with ThreadPoolExecutor(max_workers=4) as pool:
        for _ in range(max_iterations):
            response = client.messages.create(
                model=MODEL, max_tokens=2048, tools=TOOLS, messages=messages,
                system="You are a customer support assistant. Use tools for order facts; "
                       "never guess an order status.",
            )
            spent += response.usage.output_tokens
            if response.stop_reason != "tool_use":
                return "".join(b.text for b in response.content if b.type == "text")
            if spent > max_output_tokens_total:
                raise RuntimeError("tool loop exceeded token budget")
            # 1) append the FULL assistant turn (tool_use blocks, any thinking blocks)
            messages.append({"role": "assistant", "content": response.content})
            # 2) execute all calls concurrently, 3) return ALL results in ONE user message
            calls = [b for b in response.content if b.type == "tool_use"]
            results = list(pool.map(lambda b: run_tool(b, customer_id), calls))
            messages.append({"role": "user", "content": results})
    raise RuntimeError("tool loop did not finish within max_iterations")


if __name__ == "__main__":
    print(answer("Where are my orders ORD-000001 and ORD-999999?", customer_id="c-42"))

The loop ends when stop_reason is anything other than tool_use (in production, also handle max_tokens, refusal, and pause_turn for server-side tools explicitly). The unknown order comes back as an error result and the model explains it to the user. The SDK also offers a beta "tool runner" helper that drives this loop for you; writing it once by hand is the best way to understand what that helper — and Spring AI's ToolCallingAdvisor — is doing.

        this.validator = validator;
        this.retry = Retry.of("llm", RetryConfig.custom()
                .maxAttempts(props.maxAttempts())
                .retryOnException(ResilientLlmClient::isTransient)
                .intervalBiFunction((attempt, either) -> backoffMillis(attempt, either.getLeft()))
                .build());
    }

    // ---------- public API ----------

    /** Plain-text completion with resilience and model fallback. */
    public String complete(String route, String system, String user, long maxTokens) {
        Supplier<String> primary = () -> callText(route, props.primaryModel(), system, user, maxTokens);
        Supplier<String> fallback = () -> callText(route, props.fallbackModel(), system, user, maxTokens);
        return withResilience(props.primaryModel(), primary, fallback);
    }

    /** Structured completion: provider-enforced schema, Bean Validation, one repair attempt. */
    public <T> T completeStructured(String route, String system, String user,
                                    Class<T> type, long maxTokens) {
        T result = completeStructuredOnce(route, system, user, type, maxTokens);
        Set<ConstraintViolation<T>> violations = validator.validate(result);
        if (violations.isEmpty()) {
            return result;
        }
        meters.counter("llm.validation.repair", "route", route).increment();
        String feedback = violations.stream()
                .map(v -> v.getPropertyPath() + " " + v.getMessage())
                .collect(Collectors.joining("; "));
        T repaired = completeStructuredOnce(route, system,
                user + "\n\nA previous answer failed validation: " + feedback
                        + ". Return a corrected answer.", type, maxTokens);
        if (!validator.validate(repaired).isEmpty()) {
            meters.counter("llm.validation.failed", "route", route).increment();
            throw new LlmOutputInvalidException(route, feedback);
        }
        return repaired;
    }

    // ---------- internals ----------

    private <T> T completeStructuredOnce(String route, String system, String user,
                                         Class<T> type, long maxTokens) {
        Supplier<T> primary = () -> callStructured(route, props.primaryModel(), system, user, type, maxTokens);
        Supplier<T> fallback = () -> callStructured(route, props.fallbackModel(), system, user, type, maxTokens);
        return withResilience(props.primaryModel(), primary, fallback);
    }

    private <R> R withResilience(String model, Supplier<R> primary, Supplier<R> fallback) {
        CircuitBreaker breaker = breakers.circuitBreaker(model);
        return Decorators.ofSupplier(primary)
                .withBulkhead(bulkhead)            // innermost: permit held only during the call
                .withCircuitBreaker(breaker)       // records every attempt
                .withRetry(retry)                  // outermost: retries transient failures
                .withFallback(List.of(CallNotPermittedException.class, RateLimitException.class,
                                InternalServerException.class, AnthropicIoException.class),
                        t -> {
                            log.warn("LLM primary model {} unavailable ({}); using fallback",
                                    model, t.getClass().getSimpleName());
                            meters.counter("llm.fallback", "model", model).increment();
                            return breakers.circuitBreaker(props.fallbackModel())
                                    .executeSupplier(fallback);
                        })
                .decorate()
                .get();
    }

    private String callText(String route, String model, String system, String user, long maxTokens) {
        MessageCreateParams params = MessageCreateParams.builder()
                .model(model).maxTokens(maxTokens).system(system).addUserMessage(user).build();
        Message response = timed(route, model, () -> client.messages().create(params));
        record(route, model, response.usage());
        checkStop(route, response.stopReason().orElse(null));
        return response.content().stream()
                .flatMap(b -> b.text().stream())
                .map(TextBlock::text)
                .collect(Collectors.joining());
    }

    private <T> T callStructured(String route, String model, String system, String user,
                                 Class<T> type, long maxTokens) {
        StructuredMessageCreateParams<T> params = MessageCreateParams.builder()
                .model(model).maxTokens(maxTokens).outputConfig(type)
                .system(system).addUserMessage(user).build();
        StructuredMessage<T> response = timed(route, model, () -> client.messages().create(params));
        record(route, model, response.usage());
        checkStop(route, response.stopReason().orElse(null));
        return response.content().stream()
                .flatMap(b -> b.text().stream())
                .map(typed -> typed.text())
                .findFirst()
                .orElseThrow(() -> new LlmOutputInvalidException(route, "no structured content"));
    }

    private <R> R timed(String route, String model, Supplier<R> call) {
        return Timer.builder("llm.request").tag("route", route).tag("model", model)
                .publishPercentiles(0.5, 0.95, 0.99).register(meters).record(call);
    }

    private void record(String route, String model, Usage usage) {
        meters.counter("llm.tokens", "route", route, "model", model, "type", "input")
                .increment(usage.inputTokens());
        meters.counter("llm.tokens", "route", route, "model", model, "type", "output")
                .increment(usage.outputTokens());
        meters.counter("llm.tokens", "route", route, "model", model, "type", "cache_read")
                .increment(usage.cacheReadInputTokens().orElse(0L));
    }

    private void checkStop(String route, StopReason reason) {
        if (StopReason.MAX_TOKENS.equals(reason)) {
            throw new LlmOutputInvalidException(route, "truncated at max_tokens");
        }
        if (StopReason.REFUSAL.equals(reason)) {
            throw new LlmOutputInvalidException(route, "model refused");
        }
    }

    static boolean isTransient(Throwable t) {
        if (t instanceof RateLimitException || t instanceof InternalServerException
                || t instanceof AnthropicIoException) {
            return true;
        }
        return t instanceof AnthropicServiceException e
                && (e.statusCode() == 408 || e.statusCode() == 409 || e.statusCode() >= 500);
    }

    /** Full-jitter exponential backoff that never undercuts the server's retry-after. */
    long backoffMillis(int attempt, Throwable failure) {
        long cap = Math.min(props.maxBackoff().toMillis(),
                props.baseBackoff().toMillis() * (1L << Math.min(attempt - 1, 16)));
        long jittered = ThreadLocalRandom.current().nextLong(cap + 1);
        if (failure instanceof AnthropicServiceException e) {
            List<String> retryAfter = e.headers().values("retry-after");
            if (!retryAfter.isEmpty()) {
                try {
                    return Math.max(jittered, (long) (Double.parseDouble(retryAfter.get(0)) * 1000));
                } catch (NumberFormatException ignored) {
                    // HTTP-date form: fall through to jittered backoff
                }
            }
        }
        return jittered;
    }
}

8. Applications: Where These Techniques Earn Their Keep

  • Extraction pipelines. Invoices, contracts, KYC documents and emails become typed records via structured outputs plus validation, with low-confidence or invalid results routed to a human review queue — the LLM equivalent of a dead-letter topic.
  • Classification and routing. Support tickets, alerts, and incoming leads are labelled with enum-constrained outputs; small, fast models handle the bulk once evaluation proves they match the large model on the route.
  • Natural-language interfaces to internal APIs. Tool use turns "refund the duplicate charge on my last order" into authorised calls to existing services — with confirmation steps for money movement.
  • Text-to-SQL and analytics assistants. Tools expose schema discovery and query execution with read-only credentials and row limits; decomposition (pick domain → pick tables → write SQL → validate) beats one giant prompt.
  • Batch enrichment. Nightly batch jobs summarise, tag or translate large backlogs at a discount, written as Spring Batch steps or Airflow tasks that submit and poll batch APIs.
  • Streaming assistants. Chat and drafting UIs stream tokens over SSE from a Spring endpoint, with cancellation propagating to the upstream request to stop paying for unwanted tokens.
  • Prompt platforms. Larger organisations centralise prompt templates, versions, evaluation results and model configuration in an internal platform or gateway, so product teams consume "the ticket-triage capability v7" rather than raw model calls. Opinion

12. Common Mistakes and Production Failures

  • Parsing without checking stop_reason. Truncated JSON or a refusal message is fed to Jackson and surfaces as a confusing parse exception far from the cause.
  • Interpolating user input into the system prompt. Gives users operator-level influence. Keep user data in user messages, inside delimiters.
  • Dropping a failed tool result. Every tool_use needs a matching tool_result; omit one and the next request fails validation, or the model loses track.
  • Splitting parallel tool results across messages. Return all results of one turn in one user message; otherwise conversations break or the model learns to stop parallelising.
  • Tools with god-mode credentials. A "run SQL" tool connected as the application's admin user turns a prompt-injection into a data breach. Use the end user's identity and least privilege.
  • Unbounded tool loops. A confused model calls the same failing tool forever. Cap iterations, tokens and wall-clock time.
  • Timestamps or random IDs at the top of the prompt. Silently destroys prompt-cache hit rates. Check cache_read_input_tokens in dashboards.
  • Default HTTP timeouts. A 30-second read timeout kills legitimate long generations; no timeout at all leaks threads. Stream with idle timeouts and set overall deadlines.
  • Retrying 400s. Wastes quota and latency; a bad request stays bad.
  • Legacy tricks on new models. Assistant-turn prefill, forced tool_choice and temperature are rejected by some current Claude models and API versions; code that relied on them breaks on upgrade. Version-sensitive · checked Nov 2026
  • Prompt edits without evaluation. Fixing one complaint with a new rule regresses ten other cases nobody re-tested.
  • Logging full prompts and responses with PII to general-purpose logs. Use a dedicated, access-controlled store with retention limits, or redact.

13. Production Engineering

13.1 Reliability and performance

  • Resilience stack per model: timeout, retry (transient only, jittered, retry-after-aware), circuit breaker with slow-call threshold, bulkhead, fallback (§7.8).
  • Virtual threads or reactive streaming for high concurrency of long calls; size bulkheads with Little's law.
  • Stream user-facing responses; cancel upstream generation when the client disconnects.
  • Separate API keys or workspaces for batch versus interactive traffic so rate limits do not collide.

13.2 Observability

  • Per request: model, prompt version, route, tenant, input/output/cache tokens, latency (TTFT and total), stop reason, retries, fallback used, validation outcome, request ID from the provider.
  • Dashboards: p50/p95/p99 latency per route, error and refusal rates, cache-hit ratio, cost per route and tenant, circuit-breaker state (Resilience4j exports Micrometer metrics).
  • Traces: one span per model call and per tool execution, following the OpenTelemetry GenAI conventions (Chapter 5).

13.3 Security

  • Secrets in a vault or environment, never in prompts or code; rotate keys; restrict keys per environment.
  • Tools execute with the end user's authorisation; destructive actions require confirmation; inputs validated as strictly as any public API.
  • Treat tool results and retrieved documents as untrusted input to the model (indirect prompt injection, Chapter 6).

13.4 Maintainability

  • Domain interface (TicketTriager) in front of any SDK or framework, so you can swap providers or move to a framework without touching business code.
  • Prompts, schemas and examples versioned together; evaluation results attached to each version; model IDs and effort levels in configuration.
  • Contract tests with recorded responses for your parsing and tool-handling code; live evaluation suites for model behaviour.

Exercise 2 · Intermediate

Extend the Python tool loop in §7.3 with a second tool, cancel_order(order_id, reason), that must not execute without explicit human approval. Design how approval enters the loop.

Solution

Mark tools as requires_approval. When the model requests one, do not execute: persist the pending call (conversation ID, tool_use ID, arguments) and return to the client with a confirmation prompt. When the user approves, execute and send the real result; when they decline, send a tool_result with is_error: true and content "User declined cancellation." so the model can respond appropriately.

APPROVAL_REQUIRED = {"cancel_order"}

def step(messages, customer_id, approvals: dict[str, bool]):
    """approvals maps tool_use_id -> user decision for previously pending calls."""
    response = client.messages.create(model=MODEL, max_tokens=2048, tools=TOOLS, messages=messages)
    if response.stop_reason != "tool_use":
        return {"done": True, "text": "".join(b.text for b in response.content if b.type == "text")}
    calls = [b for b in response.content if b.type == "tool_use"]
    pending = [c for c in calls if c.name in APPROVAL_REQUIRED and c.id not in approvals]
    if pending:
        # Do not append anything yet; surface the request to the UI and resume later.
        return {"done": False, "needs_approval": [{"id": c.id, "tool": c.name, "args": c.input} for c in pending],
                "assistant_content": response.content}
    messages.append({"role": "assistant", "content": response.content})
    results = []
    for c in calls:
        if c.name in APPROVAL_REQUIRED and not approvals[c.id]:
            results.append({"type": "tool_result", "tool_use_id": c.id,
                            "content": "User declined this action.", "is_error": True})
        else:
            results.append(run_tool(c, customer_id))
    messages.append({"role": "user", "content": results})
    return {"done": False}

In a web application the pending state lives in a database row keyed by conversation, not in memory, so the approval can arrive minutes later on another instance — the same pattern Spring AI 2.1's tool-call confirmation feature describes as park-and-resume.

Exercise 3 · Intermediate

Your prompt-cache hit rate is 3% although every request uses the same 6,000-token system prompt. List the likely causes and how to confirm each.

Solution
  • A variable value (date, request ID, user name) inside or before the cached block — diff the rendered prefixes of two requests byte-for-byte.

  • Bursts of parallel cold requests — a cache entry becomes readable only after the first response starts; warm it with one request.

package com.example.llm;

import com.anthropic.client.AnthropicClient;
import com.anthropic.core.http.StreamResponse;
import com.anthropic.models.messages.MessageCreateParams;
import com.anthropic.models.messages.RawMessageStreamEvent;
import org.springframework.http.MediaType;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.servlet.mvc.method.annotation.SseEmitter;

import java.io.IOException;
import java.util.concurrent.Executors;
import java.util.concurrent.atomic.AtomicBoolean;

@RestController
class StreamingController {
    private final AnthropicClient client;
    StreamingController(AnthropicClient client) { this.client = client; }

    @PostMapping(value = "/chat/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    SseEmitter stream(@RequestBody String question) {
        SseEmitter emitter = new SseEmitter(180_000L);              // overall deadline
        AtomicBoolean cancelled = new AtomicBoolean(false);
        emitter.onCompletion(() -> cancelled.set(true));
        emitter.onTimeout(() -> cancelled.set(true));
        emitter.onError(e -> cancelled.set(true));

        MessageCreateParams params = MessageCreateParams.builder()
                .model("claude-opus-5-5").maxTokens(4096L).addUserMessage(question).build();

        Executors.newVirtualThreadPerTaskExecutor().submit(() -> {
            try (StreamResponse<RawMessageStreamEvent> stream = client.messages().createStreaming(params)) {
                var it = stream.stream().iterator();
                while (it.hasNext() && !cancelled.get()) {
                    RawMessageStreamEvent event = it.next();
                    event.contentBlockDelta()
                         .flatMap(d -> d.delta().text())
                         .ifPresent(t -> send(emitter, t.text()));
                    event.messageDelta().ifPresent(md ->
                         System.out.println("output tokens: " + md.usage().outputTokens()));
                }
                emitter.complete();
            } catch (Exception e) {
                emitter.completeWithError(e);
            }   // closing the StreamResponse aborts the upstream HTTP request
        });
        return emitter;
    }

    private static void send(SseEmitter emitter, String text) {
        try {
            emitter.send(SseEmitter.event().name("delta").data(text));
        } catch (IOException e) {
            throw new IllegalStateException("client disconnected", e);
        }
    }
}

Closing the StreamResponse (via try-with-resources) when the loop exits on cancellation aborts the HTTP request, so the provider stops generating and you stop paying for tokens nobody will read. In production, replace System.out with the Micrometer counters from §7.8 and reuse a shared virtual-thread executor bean.

15. Interview Questions

Conceptual What does constrained decoding guarantee, and what does it not?

It guarantees the output conforms to the grammar or JSON schema — parseable, required fields present, types and enums respected — by masking invalid tokens at each step. It does not guarantee correctness: values can be wrong, hallucinated or inconsistent with business rules; and output can still be truncated by max_tokens. You still validate semantics and check the stop reason.

Conceptual Walk through the tool-use protocol.

Send tool definitions with the request. If the model wants a tool, the response contains tool_use blocks (ID, name, input) and stop_reason=tool_use. Append the full assistant content to history, execute each call in your code with proper authorisation (in parallel if several), and send one user message containing a tool_result per call, referencing the IDs, using is_error for failures. Repeat until the model ends its turn; cap iterations.

Architecture Design the resilience configuration for an LLM dependency behind a synchronous REST endpoint with a 10-second SLO.

Use streaming or keep outputs short so normal calls finish well under 10 s; overall timeout around 8 s; at most one retry on 429/5xx with jitter and retry-after — only if remaining budget allows; circuit breaker per model counting slow calls (e.g., >6 s) and errors; bulkhead sized from Little's law; fallback to a faster model validated for the route or a degraded non-LLM response; disable SDK retries so only one layer retries. If p95 latency of the model exceeds the SLO, the endpoint should become asynchronous.

Coding How do you implement exponential backoff with full jitter that respects retry-after?

cap = min(maxBackoff, base * 2^(attempt-1)); sleep = random(0, cap); if retryAfter present: sleep = max(sleep, retryAfter). Bound attempts and total elapsed time; only retry transient errors. See backoffMillis in §7.8.

Scenario After a model upgrade, 4% of extraction responses fail validation, up from 0.5%. What do you do?

Roll back the model ID via configuration (it should be a flag, not a deploy). Then investigate offline: diff failures by field, check whether the new model formats dates or numbers differently, whether stop reasons changed (more truncation due to verbosity), or whether a prompt rule now over-applies. Fix prompt or schema descriptions, re-run the evaluation set on both models, and promote only when the new model matches or beats the old on validation rate and accuracy.

Conceptual How does prompt caching work and what breaks it?

The provider stores the KV cache of a prompt prefix and reuses it when a later request's prefix matches byte-for-byte within the cache lifetime, cutting cost and TTFT. Anything that changes earlier bytes — timestamps, request IDs, tool order, different model or settings — breaks it. Put static content first, variable content last, and monitor cache-read tokens.

Architecture Spring AI, LangChain4j or the raw Anthropic SDK — how do you choose?

For Spring Boot services doing standard chat, structured extraction, RAG and tools, Spring AI fits idiomatically (auto-configuration, advisors, Micrometer). LangChain4j suits teams that like declarative AI-service interfaces or run Quarkus/plain Java. Use the raw SDK for provider-specific features before frameworks support them, or for a central, heavily tuned client. In all cases, put a domain interface in front so the choice is reversible.

Scenario Your batch classification job keeps hitting 429s and also slows down the customer chat feature. Fix it.

Move the job to the provider's batch API (asynchronous, discounted, separate processing) or at least to a separate API key/workspace with its own limits; add client-side rate limiting and concurrency caps to the job; schedule it off-peak; and ensure chat traffic has reserved capacity. Monitor tokens-per-minute per workload.

Conceptual Why place an "evidence" field before a "verdict" field in a schema?

Generation is left-to-right; fields generated earlier become context for later ones. Asking for evidence first lets the model ground its verdict in quoted text, which usually improves accuracy and makes outputs auditable. Asking for the verdict first forces a decision before the supporting reasoning exists.

Behavioral A product manager wants to edit prompts directly in production through an admin UI. How do you respond?

Support the goal (fast iteration) while protecting reliability: allow editing in a staging prompt registry, run the evaluation suite automatically on each change, require review for promotion, version every change with rollback, and log the prompt version with each request. Prompts are behaviour-defining code and need the same change management.

16. Knowledge Check

  • Prompts are specifications: define goal, labels, edge cases, fallbacks and output shape; version and evaluate them like code.
  • Few-shot examples teach format and boundaries but cost tokens and are copied literally.
  • Use provider-enforced structured outputs, then validate semantics locally and repair once with specific feedback.
  • Tool use is a loop you own: append the full assistant turn, execute with the user's authority, return all results in one message, use is_error, cap iterations.
  • Streaming hides latency; batch APIs trade latency for cost; caching rewards stable prefixes.
  • Retry only transient errors, with jitter and retry-after, in exactly one layer; add per-model circuit breakers, bulkheads and validated fallbacks.
  • Spring AI 2.x runs tool calling in its advisor chain; LangChain4j offers declarative AI services; hide either behind a domain interface.

A model returns two tool_use blocks in one turn. How should you send the results?

  1. Two separate user messages, one per result, in completion order
  2. One user message containing both tool_result blocks, after appending the full assistant turn
  3. Only the successful result; omit the failed one
  4. A system message summarising both results
All results for one assistant turn go into a single user message, each referencing its tool_use ID; failures are included with is_error. Splitting or omitting results breaks the protocol or degrades parallel tool use.

Which error should your LLM client retry?

  1. 400 invalid_request_error
  2. 401 authentication_error
  3. 413 request too large
  4. 429 rate_limit_error, honouring retry-after
Rate limits and 5xx/overloaded errors are transient. 400, 401 and 413 will fail identically on retry and only waste quota.

Your system prompt starts with "Current time: 2026-11-26T10:15:03Z". What is the main consequence?

  1. The prompt-cache prefix changes on every request, so cache hits are lost
  2. The model will refuse to answer
  3. Output tokens increase
  4. Rate limits are applied per timestamp
Caching requires a byte-identical prefix. A changing value at the top invalidates everything after it. Put volatile values late in the request (for example, in the user message).

You enabled schema-constrained output but still occasionally get JSON parse errors. What is the most likely cause?

  1. The model ignores the schema at high load
  2. Jackson cannot parse enums
  3. Generation stopped at max_tokens, truncating the JSON
  4. Constrained decoding only works with streaming
Constraints guarantee validity only for a complete generation. If max_tokens is reached, output is cut mid-object. Check stop_reason before parsing and size max_tokens appropriately.

With Resilience4j decorators Retry, CircuitBreaker and Bulkhead around an LLM call, which nesting is recommended here?

  1. Bulkhead outermost, then Retry, then CircuitBreaker innermost
  2. Retry outermost, then CircuitBreaker, then Bulkhead innermost
  3. CircuitBreaker outermost so retries are invisible to it
  4. Order does not matter
Retry outside the breaker means each attempt is recorded and an open breaker fails fast; the bulkhead inside means a permit is held only during the actual call, not during backoff sleeps. This matches Resilience4j's default annotation ordering.

What is the main benefit of the batch API for a nightly job of 200,000 classifications?

  1. Lower latency per request
  2. Guaranteed result ordering
  3. Substantially lower price and isolation from interactive rate limits, at the cost of hours of latency
  4. Larger context windows
Batch processing is asynchronous and discounted; results can arrive in any order and are matched by custom_id.
