1. Introduction: Four Products, One Retrieval Core

Ask a dozen enterprises what they want from generative AI and most of the answers fit into four shapes. One is "let people ask questions of our documents". Another is "give employees an assistant that knows our stuff and remembers the conversation". A third is "deflect and speed up support tickets". The last is "make our search box understand what people mean". These are the four projects in this chapter, and they are numbered as in the book's project list:

All four depend on one capability: given a question and a user, fetch the few passages that the user may see and that best support an answer. So the chapter builds a shared retrieval core first. It is a PostgreSQL + pgvector store with full-text search, ACL columns, hybrid ranking and a reranker. Each project is then a thin, opinionated product on top of that core. This mirrors how mature teams work. Dropbox, for example, describes Dash as a shared retrieval and context layer with agents built over it (see §9). Teams that build four separate RAG stacks end up maintaining four separate sets of bugs.

The chapter does not re-teach how embeddings, chunking strategies or reranker models work. Those live in Chapter 8.4. Prompting and tool schemas are in Chapter 8.2, and guardrails and evaluation theory are in Chapter 8.5. This chapter is about systems: the requirements, data flows, schemas, code, tests, deployment and operational choices that turn those concepts into something you can run for real users.

Bridging from Java & Spring Boot

What you already know
You have built Spring Boot services backed by PostgreSQL and maybe Elasticsearch. You have secured them with Spring Security and OAuth2 resource servers, used @Transactional boundaries and Kafka listeners, and run them on Kubernetes with Actuator, Micrometer and Testcontainers. A document Q&A service is, structurally, a search service plus a templating step, and you have built search services.
Why that is not enough
Three things change. First, the "template" is a probabilistic model. Its output must be evaluated statistically, not only asserted in unit tests. Second, permissions have to go inside retrieval. A @PreAuthorize check on the controller cannot stop a forbidden paragraph from leaking into a prompt. Third, cost and latency become per-request variables measured in tokens, so you need budgets, caching and metering the way you once needed connection pools.
The modern approach
Treat the LLM as a remote dependency with a typed contract: structured output into Java records, tool calls into existing @Service beans, and timeouts and circuit breakers around it. Put retrieval, ACL filtering and ranking in deterministic code you can test. Keep a versioned evaluation set in the repository and gate merges on it, the same way you gate on integration tests.
Where Python and Go fit
Python owns document parsing (PDF layout, OCR, table extraction), offline evaluation and any model hosting you do yourself. Its ecosystem there is far ahead. Go is a good fit for the latency-critical search gateway in P6, which fans out to several backends in parallel with tight deadlines. Spring Boot owns the business-facing APIs, security, transactions and integration with existing systems such as the CRM.
In production
You will run an ingestion pipeline (Kafka + Python workers) and a query service (Spring Boot), use one or two model providers behind a gateway, and keep an eval and feedback store. Dashboards track the answer rate, citation validity, escalation rate, p95 latency and cost per conversation.
Use it when / avoid it when
Use these patterns when answers live in unstructured text that changes often and users need sources. Avoid them when the answer is a database lookup: "what is my order status" needs a tool call, not RAG. Also avoid them when regulations require deterministic, auditable answers that a model may not paraphrase. There you serve the retrieved passage verbatim.

2. History: From Enterprise Search Appliances to Grounded Assistants

2.1 Lexical enterprise search (1990s–2010s)

Organisations have wanted to search their documents for as long as they have had file servers. Early enterprise search products indexed intranets and file shares with inverted indexes and ranked results with term statistics. The probabilistic relevance framework produced Okapi BM25, presented at TREC in the mid-1990s, and it is still the lexical baseline every system in this chapter uses. Doug Cutting began Apache Lucene in 1999. Lucene became the engine under Solr and, from 2010, Elasticsearch, and with them "search" turned into a commodity that a backend team could run. Google sold a hardware Search Appliance for intranets and announced its phase-out in 2016. That was an early sign that the hard part of enterprise search was connectors, permissions and relevance tuning, not the box.

Those systems already met the two problems that still dominate. One was security trimming: showing a user only results they may open. The other was the vocabulary gap: a user searches for "PTO", the document says "annual leave", and BM25 cannot connect them. Teams patched the gap with synonym lists and query expansion maintained by hand.

2.2 Support automation before LLMs

Customer support automation went through decision-tree chatbots, intent classifiers trained on labelled utterances, and "deflection" widgets that suggested FAQ articles as the customer typed. Ticket triage meant routing rules plus, later, supervised text classifiers. These systems were predictable but brittle. Each new intent needed new training data and a new flow, and they could not write a fluent reply that fitted the case. DoorDash's 2024 write-up (§9) describes this transition explicitly: from flow-based resolutions covering a small set of issues to RAG over knowledge-base articles with guardrails.

2.3 Dense retrieval and the RAG pattern (2018–2022)

Transformer encoders made dense retrieval practical. Questions and passages are mapped into the same vector space, so "PTO" and "annual leave" land near each other. Sentence-BERT (2019) and Dense Passage Retrieval (2020) showed this could beat BM25 on many benchmarks, though not all: BEIR (2021) showed that BM25 stays strong out of domain. Lewis et al. named the retrieval-augmented generation pattern in 2020: retrieve passages, then condition a generator on them. Cross-encoder rerankers and late-interaction models such as ColBERT (2020) added a precision stage on top of cheap first-stage recall.

2.4 The LLM era (late 2022 onwards)

After ChatGPT's release in November 2022, general-purpose instruction-following models made the "generation" half good enough for business use almost overnight. The bottleneck moved back to retrieval quality, permissions, evaluation and cost. 2023–2024 brought the patterns this chapter uses as defaults:

  • Hybrid retrieval (BM25 + vectors fused with Reciprocal Rank Fusion), because neither signal alone is reliable.
  • Contextual chunking, where a chunk is prefixed with document-level context before embedding. Anthropic's "Contextual Retrieval" post (2024) measured large reductions in retrieval failures from it.
  • Native citations and structured outputs in model APIs. Grounding became something you can verify mechanically instead of something you hope for.
  • Tool calling, which turned support bots from answerers into actors that can look up an order and issue a refund. Human-in-the-loop guardrails followed.
  • Evaluation as engineering: LLM-as-judge with calibration against humans, versioned golden sets and online feedback loops. LinkedIn's and Shopify's write-ups (§9) both name evaluation as the hardest part.

By 2025–2026, vendors had shipped these patterns as products (Glean, Dropbox Dash, Slack AI, Intercom Fin and many others). Frameworks such as Spring AI reached a stable, Spring-native API: Spring AI 1.0 shipped in May 2025 and 2.0, built on Spring Boot 4, in June 2026. The engineering problem that remains is integration: your data, your permissions, your workflows and your quality bar. That is what these projects practise.

3. Fundamentals: Requirements, Scope and Success Metrics

A project chapter starts where a real project starts: with what the system must do, how well, and how you will know. Writing these down before any code is the most underrated skill in LLM engineering. Without a success metric, "the answers seem good" becomes the acceptance criterion, and that criterion never fails a demo or passes an audit.

3.1 Shared: the retrieval core contract

Every project calls one internal API:

retrieve(principal, query, filters, k) -> List<ScoredChunk{chunkId, docId, text, title, uri, page, score, aclVersion}>
  • Principal-scoped. The caller passes the end user's identity (subject plus group memberships), never a service account. The core returns only chunks whose ACL intersects the principal's groups at the time of the query.
  • Hybrid. Lexical (PostgreSQL full-text, BM25-like ts_rank_cd) and dense (pgvector HNSW) candidates are fused with RRF and then optionally reranked by a cross-encoder.
  • Deterministic and testable. Given the same index snapshot and query embedding, it returns the same ranking. All model calls are outside it except the embedding of the query and the reranker, and both are stubbable.
  • Budget: p95 under 250 ms for k=8 over 10 million chunks Illustrative. That target leaves most of a 3–5 s answer budget for generation.

Deflection is not resolution

A bot that makes customers give up looks great on "deflection" dashboards. Measure reopen rate, repeat contact within 7 days and CSAT for AI-handled conversations, and compare them with the same intents handled by humans. Klarna's widely quoted 2024 numbers (§9) were stated alongside customer-satisfaction and repeat-inquiry claims for exactly this reason.

4. Internals: Component Design and Key Flows

4.1 Shared: the ingestion pipeline

Ingestion is where most RAG quality is won or lost, and it is plain backend engineering: connectors, idempotency, retries, backpressure. The pipeline has five stages, each a Kafka consumer group, so each can scale and fail on its own:

  1. Discover: connectors (Confluence REST, S3 events, SharePoint/Graph delta queries) emit DocumentChanged{sourceId, externalId, version, aclSnapshot, uri} events. Confluence is polled with a CQL lastmodified cursor. Object stores push notifications.
  2. Fetch & parse (Python): download, detect type, extract text with layout (headings, page numbers, tables as Markdown), and OCR scanned pages. The output is a canonical ParsedDocument JSON in object storage. Parsing is the most failure-prone stage, so it has its own dead-letter topic.
  3. Chunk: structure-aware splitting (by heading, then by about 400–800 tokens with 10–15% overlap). Each chunk carries the heading path ("HR Policy › Leave › Contractors") and page range, plus a 1–2 sentence contextual prefix generated by a small, cheap model (see 8.4).
  4. Embed: batch chunks (e.g. 64 per call) through the embedding model. Results are cached by sha256(model_id + prefix + text), so unchanged chunks in a new document version are never re-embedded.
  5. Index: upsert the document row, replace the chunk set in one transaction keyed by (doc_id, version), and update the ACL rows. Old versions are deleted in the same transaction, so a query never sees half of two versions.

Reading the diagram: the connector only detects change and snapshots the ACL. It never parses, so a slow PDF cannot hold up change detection. Parsed output goes to object storage, not into Kafka messages, because a 300-page PDF's text would exceed sensible message sizes. Kafka carries only references. Step 10 is the key correctness property: deleting the old version and inserting the new one in a single transaction gives readers snapshot consistency per document. Each consumer commits its offset only after its side effect succeeds (at-least-once delivery). The idempotent upsert keyed by (doc_id, version) turns that into an effectively-once outcome.

4.2 Shared: ACL-aware hybrid retrieval

The core design decision is early-binding ACLs: permissions are copied into the index and filtered inside the SQL query. The alternative is late binding, where you retrieve the top-k and then ask the source system "may user U see doc D?" for each result. Late binding is always fresh but slow, and it ruins recall, because if 7 of the top 8 are forbidden you answer from one passage. Early binding is fast and keeps recall, but it is only as fresh as your last sync. The production answer is both:

  • Filter by the indexed ACL in SQL (fast path, keeps recall).
  • For the few chunks that will actually be cited, optionally re-check against the source system with a short-TTL cache. This catches revocations that happened after the last sync.
  • Run a permission-only sync more frequently than the content sync, because ACL changes are small and urgent.

ACLs are stored as an array of principal keys per document (group:eng, user:alice@corp, space:HR:viewers), with a GIN index. At query time the principal expands to its keys. The user's IdP groups are resolved once per session and cached. The filter is acl_keys && :principalKeys, the array-overlap operator. Both candidate generators (lexical and vector) apply the same filter.

Filtered HNSW can silently lose recall

With an approximate index, PostgreSQL may walk the HNSW graph, take ef_search candidates, and only then apply the ACL filter. A user who can see 0.1% of the corpus then gets few or no vector hits. pgvector 0.8 added iterative index scans (SET hnsw.iterative_scan = relaxed_order), which keep scanning until enough rows pass the filter Version-sensitive · checked Nov 2026. For very selective tenants or groups, also consider partial indexes or per-tenant partitions (see the Enterprise RAG capstone).

4.3 P1 — Answering with citations

The answer flow is a short, fixed pipeline. It is a workflow, not an agent, because the steps never change:

Reading the diagram: the first-stage retrieval over-fetches (k=40) so the reranker has room to improve precision, and only eight passages reach the model. The audit record holds chunk IDs rather than text, so the audit store does not become a second copy of every confidential document.

4.4 P2 — A conversational turn

A conversational turn adds three components in front of the P1 pipeline:

  1. Memory load: fetch the last N turns (window), the rolling summary, and long-term facts for the user from PostgreSQL.
  2. Query rewriter: a small, fast model (e.g. a Haiku-class model) turns (history, new message) into a structured RewrittenQuery{standalone, subQueries[], needsRetrieval, filters}. Small talk ("thanks!") sets needsRetrieval=false and skips retrieval entirely. That saves cost and avoids grounding "you're welcome" in an HR policy.
  3. Multi-query retrieval: retrieve for the standalone query and each sub-query in parallel, then fuse all lists with RRF.

Reading the diagram: summarisation runs asynchronously after the response, so the user never waits for it. Summary updates are versioned. If two turns race, the later one wins by optimistic locking on conversation.version. Long-term facts are never written silently. The model may propose a fact ("Remember that you are in the Berlin office?") and the UI asks for confirmation. That keeps memory explainable and avoids a store full of hallucinated "facts". Every persisted turn has a turnId, and feedback attaches to it along with the exact retrieved chunk IDs and prompt version, which is what makes feedback actionable later.

4.5 P3 — Ticket lifecycle and the autonomy boundary

The support platform is the only project here that changes state in other systems, so it needs an explicit state machine. The LLM proposes transitions and a deterministic policy engine authorises them.

Reading the diagram: there are two "human" exits from AI handling: escalation during resolution, and reopening after it. Both count against the AI in the metrics. The Reopened state always goes to a human, so a customer is never sent round the AI loop twice for the same issue. The state machine lives in the database (a ticket.state column with transition checks in a Spring @Service). It is not encoded in a prompt. The model can request "resolve"; the service decides.

Reading the diagram: the model never talks to the CRM directly. Every tool call goes through the service, which injects the authenticated customer ID. 5. Architecture: Diagrams and Technology Selection

5.1 Shared platform: component view

Reading the diagram: data flows left to right through Kafka into two stores. PostgreSQL + pgvector holds documents and chunks for P1–P3, and OpenSearch holds the product catalogue for P6, where faceting, aggregations and high-QPS BM25 justify a dedicated engine. The product services never call model providers directly. They all go through an LLM gateway (an internal service or a product such as LiteLLM or Envoy AI Gateway) that holds API keys, enforces per-team quotas, meters tokens, and fails over between models. That single choke point is what makes cost attribution and key rotation tractable. The capstone in Chapter 13.1 builds one. The reranker is a shared GPU deployment because cross-encoders are expensive and benefit from batching across products.

5.2 Data model (ER diagram)

Reading the diagram: DOCUMENT.acl_keys is denormalised onto chunks in the physical schema (§7), because the filter must run in the same index scan as the vector search. DOCUMENT_ACL is kept as the normalised source of truth for admin views and for rebuilding. TURN_CITATION links answers to the exact chunks used, and that link is what makes feedback debuggable ("the thumbs-down answer cited chunk X from an outdated policy"). TOOL_CALL records the policy decision (allow, deny or needs_approval) with the arguments, so the audit trail of P3 is in the same database as the ticket and can be read in one transaction.

5.3 Deployment view

Reading the diagram: the three namespaces scale on different signals. Product services scale on CPU and request rate with HPA. Ingestion workers scale on Kafka consumer lag with KEDA, so a 50,000-page backfill spins up workers and then scales to zero. The reranker runs on a GPU node pool with taints so ordinary pods do not land there. Only the LLM gateway has egress to model providers. A NetworkPolicy blocks egress from the product namespace, so a compromised dependency in qa-service cannot send data to the internet directly.

5.4 Try the retrieval core

Try a query that uses an exact identifier, such as an error code or product SKU. BM25 finds it while vector search often misses it. Then try a paraphrase with no shared words, where the reverse happens. Hybrid RRF is the reason every project in this chapter keeps both signals. Change the chunk size too, and watch how a large chunk can contain the answer and still rank poorly because its embedding averages several topics.

6. Math: Capacity, Cost and Ranking Formulas

The numbers below are Illustrative. They are worked examples to show the method, not benchmarks. Prices are list prices for the Claude 5.5 family at the time of writing Version-sensitive · checked Nov 2026: Sonnet 5.5 at $2 per million input tokens and $10 per million output tokens, and Haiku 5.5 at $0.10 / $0.50 for prompts up to 100K tokens. Always re-check them.

6.1 Storage for the vector index (shared)

Intuition: each chunk costs its text, its vector and its index overhead. For \(N\) chunks of dimension \(d\) stored as halfvec (2 bytes per component):

\[ S_{\text{vec}} = N \cdot d \cdot 2 \text{ bytes}, \qquad S_{\text{hnsw}} \approx N \cdot (d \cdot 2 + 2M \cdot 8) \text{ bytes} \]

where \(M\) is the HNSW neighbour count. The graph stores roughly \(2M\) links on layer 0 per node, and the HNSW index in pgvector also stores the vector. For \(N = 10^7\), \(d = 1024\), \(M = 16\): \(S_{\text{vec}} \approx 20.5\) GB, and the index is about \(10^7 \cdot (2048 + 256) \approx 23\) GB. Text at an average of 600 tokens, about 2.4 KB per chunk, adds about 24 GB plus the GIN index for tsvector (often 30–50% of the text size). Plan for about 80 GB of hot data, and size RAM so the HNSW index fits in shared buffers plus the page cache. A cold HNSW scan from disk is an order of magnitude slower.

6.2 Ingestion cost (P1/P2)

Embedding cost is \(C_{\text{emb}} = T_{\text{corpus}} \cdot p_{\text{emb}}\), where \(T_{\text{corpus}}\) is the token count. Contextual prefixes add one small-model call per chunk, and the whole document goes in as context, so prompt caching matters a lot:

\[ C_{\text{ctx}} \approx \sum_{\text{docs}} \Big( T_{\text{doc}} \cdot p_{\text{in}} + (n_{\text{chunks}}-1)\cdot T_{\text{doc}} \cdot p_{\text{cache-read}} + n_{\text{chunks}} \cdot (T_{\text{chunk}} \cdot p_{\text{in}} + 60 \cdot p_{\text{out}}) \Big) \]

Worked example: 200,000 documents averaging 8,000 tokens and 15 chunks each, using Haiku 5.5. The first call writes the document to the cache; ignore the cache-write premium for simplicity. Without caching, the document tokens alone are \(200{,}000 \cdot 15 \cdot 8{,}000 = 2.4 \times 10^{10}\) tokens, which is about $2,400 at $0.10/M. With cache reads at roughly a tenth of the input price, the same term drops to about $240 + $160 ≈ $400. The output term is \(3\text{M chunks} \cdot 60 \cdot \$0.5/\text{M} \approx \$90\). The lesson is that structure the prompt so the document is a cacheable prefix and the chunk varies at the end. Prompt caching turns a one-off cost from thousands into hundreds of dollars.

6.3 Query cost and QPS (P1/P2)

Per answer:

\[ C_{\text{answer}} = (T_{\text{sys}} + k \cdot T_{\text{chunk}} + T_{\text{hist}} + T_{q}) \cdot p_{\text{in}} + T_{\text{out}} \cdot p_{\text{out}} \]

With \(T_{\text{sys}}=800\), \(k=8\), \(T_{\text{chunk}}=600\), \(T_{\text{hist}}=1{,}500\) (P2), \(T_q=40\) and \(T_{\text{out}}=350\) on Sonnet 5.5: input is about 7,140 tokens, or $0.0143; output is $0.0035; the total is about $0.018 per answer. The P2 rewriter on Haiku 5.5 adds about 2,000 input and 80 output tokens, roughly $0.00024, which is negligible. At 20,000 employees × 5 questions per working day, that is 100,000 answers a day, or about $1,800 a day, before caching the stable system prompt. Peak QPS: if 30% of daily traffic falls in 2 hours, \(\text{QPS}_{\text{peak}} \approx 30{,}000 / 7{,}200 \approx 4.2\). The LLM step is I/O-bound, so the concern is concurrent streams (Little's law: \(L = \lambda W = 4.2 \cdot 8\,\text{s} \approx 34\) in flight) and provider rate limits (tokens per minute), not CPU.

6.4 Support economics (P3)

Let \(r\) be the autonomous resolution rate, \(b\) the bad-resolution rate (resolutions that are reopened), \(c_h\) the fully loaded cost of a human-handled ticket, \(c_{ai}\) the AI cost per attempt, and \(c_{bad}\) the extra cost of a bad resolution (a human ticket plus goodwill). The expected saving per eligible ticket is:

\[ \Delta = r(1-b)\,c_h \;-\; c_{ai} \;-\; r\,b\,c_{bad} \]

With \(c_h = \$6\), \(c_{ai} = \$0.08\) (a 6-call tool loop on Sonnet), \(r = 0.45\), \(b = 0.08\) and \(c_{bad} = \$15\): \(\Delta = 2.48 - 0.08 - 0.54 = \$1.86\). Sensitivity: if \(b\) rises to 0.25, \(\Delta = 2.03 - 0.08 - 1.69 = \$0.26\), and most of the value is gone. This is why the bad-resolution rate is a first-class SLO and the allow-list of intents grows only when the per-intent \(b\) stays low.

6.5 Reciprocal Rank Fusion (P6 and shared)

Intuition: rather than trying to make BM25 scores and cosine similarities comparable (they are not), use only ranks. A document that appears near the top of several lists wins. For a document \(d\) and ranked lists \(L\):

\[ \mathrm{RRF}(d) = \sum_{\ell \in L} \frac{w_\ell}{k + \mathrm{rank}_\ell(d)} \]

with \(k = 60\) by convention and \(w_\ell\) optional per-list weights. Since \(1/(60+1) \approx 0.0164\) and \(1/(60+10) \approx 0.0143\), rank differences near the top matter only modestly. RRF is robust and needs no score calibration, but it cannot express "this lexical hit is an exact SKU match, trust it completely". That is why P6 handles exact identifiers as a separate rule before fusion.

6.6 Ranking metrics (P6)

\[ \mathrm{DCG@k} = \sum_{i=1}^{k} \frac{2^{rel_i}-1}{\log_2(i+1)}, \qquad \mathrm{nDCG@k} = \frac{\mathrm{DCG@k}}{\mathrm{IDCG@k}} \]

Use graded relevance (0–3) judged by humans on a sample, and extend it with an LLM judge calibrated against those human labels. Recall@50 measures whether first-stage retrieval gives the reranker the right candidates. nDCG@10 measures the final order. If recall@50 is low, no reranker can fix it.

6.7 Latency budget (P6)

The results path is a sum on the critical path, with parallel branches contributing their maximum:

\[ t_{p95} \approx t_{QU} + \max(t_{BM25}, t_{ANN}) + t_{fuse} + t_{rerank} + t_{rules} + t_{net} \]

A budget of 20 + 80 + 5 + 60 + 10 + 40 = 215 ms leaves headroom under 300 ms. Tail latency of a fan-out is governed by the slowest branch: with two independent branches each at p99 = 80 ms, the probability that at least one exceeds its p99 is \(1 - 0.99^2 \approx 2\%\). Per-branch deadlines with graceful degradation are therefore mandatory, not optional.

  WITH (m = 16, ef_construction = 128);

-- ACL changes are applied without touching content: one UPDATE per document
CREATE OR REPLACE FUNCTION propagate_acl() RETURNS trigger AS $$
BEGIN
  IF NEW.acl_keys IS DISTINCT FROM OLD.acl_keys THEN
    UPDATE chunk SET acl_keys = NEW.acl_keys WHERE doc_id = NEW.id;
  END IF;
  RETURN NEW;
END $$ LANGUAGE plpgsql;

CREATE TRIGGER document_acl_propagate AFTER UPDATE OF acl_keys ON document
  FOR EACH ROW EXECUTE FUNCTION propagate_acl();

Design notes: halfvec halves storage relative to vector with negligible recall loss for most embedding models (validate on your eval set). The generated tsv column weights headings above body text. The ACL trigger means a permission-only sync is a cheap UPDATE on document, not a re-index.

7.3 Retrieval core: hybrid, ACL-filtered, RRF in one SQL round trip

package com.acme.retrieval;

import java.util.List;
import java.util.UUID;
import org.springframework.jdbc.core.simple.JdbcClient;
import org.springframework.stereotype.Component;
import org.springframework.transaction.annotation.Transactional;

// Separate files in the same package (shown here for reference):
//   public record Principal(String subject, List<String> aclKeys) {}
//   public record ScoredChunk(UUID chunkId, UUID docId, String title, String uri,
//                             String headingPath, Integer pageFrom, String content, double score) {}

@Component
public class HybridRetriever {

  private static final String SQL = """
      WITH lex AS (
        SELECT id, row_number() OVER (ORDER BY rank DESC) AS r FROM (
          SELECT c.id, ts_rank_cd(c.tsv, q) AS rank
          FROM chunk c, websearch_to_tsquery('english', :q) q
          WHERE c.tsv @@ q AND c.acl_keys && CAST(:keys AS text[])
          ORDER BY rank DESC LIMIT :n) l),
      vec AS (
        SELECT id, row_number() OVER (ORDER BY dist) AS r FROM (
          SELECT c.id, c.embedding <=> CAST(:emb AS halfvec) AS dist
          FROM chunk c
          WHERE c.acl_keys && CAST(:keys AS text[])
          ORDER BY dist LIMIT :n) v),
      fused AS (
        SELECT id, sum(1.0 / (60 + r)) AS score
        FROM (SELECT * FROM lex UNION ALL SELECT * FROM vec) u
        GROUP BY id ORDER BY score DESC LIMIT :k)
      SELECT c.id, c.doc_id, d.title, d.uri, c.heading_path, c.page_from,
             coalesce(c.context_prefix || E'\\n', '') || c.content AS content, f.score
      FROM fused f JOIN chunk c ON c.id = f.id JOIN document d ON d.id = c.doc_id
      ORDER BY f.score DESC
      """;

  private final JdbcClient jdbc;
  private final QueryEmbedder embedder;

  public HybridRetriever(JdbcClient jdbc, QueryEmbedder embedder) {
    this.jdbc = jdbc;
    this.embedder = embedder;
  }

  /** Returns at most k chunks the principal may read, fused from lexical and vector candidates. */
  @Transactional(readOnly = true)
  public List<ScoredChunk> retrieve(Principal p, String query, int k) {
    if (p.aclKeys().isEmpty()) return List.of();                 // fail closed
    float[] emb = embedder.embed(query);
    // keep scanning the HNSW graph until enough rows pass the ACL filter (pgvector >= 0.8)
    jdbc.sql("SET LOCAL hnsw.iterative_scan = relaxed_order").update();
    jdbc.sql("SET LOCAL hnsw.ef_search = 100").update();
    return jdbc.sql(SQL)
        .param("q", query)
        .param("keys", p.aclKeys().toArray(String[]::new))
        .param("emb", PgVectors.toLiteral(emb))                   // "[0.012,-0.3,...]"
        .param("n", Math.max(50, k * 5))
        .param("k", k)
        .query((rs, i) -> new ScoredChunk(
            rs.getObject("id", UUID.class), rs.getObject("doc_id", UUID.class),
            rs.getString("title"), rs.getString("uri"), rs.getString("heading_path"),
            (Integer) rs.getObject("page_from"), rs.getString("content"), rs.getDouble("score")))
        .list();
  }
}

Why hand-written SQL rather than Spring AI's VectorStore? The VectorStore abstraction (with PgVectorStore) is excellent for vector-only search with metadata filters, and you should use it for prototypes. This core needs three things it does not express in one call: lexical and vector fusion in a single round trip, array-overlap ACL filtering that uses a GIN index, and session-level HNSW settings. Wrapping custom SQL in your own small interface keeps the rest of the code just as testable. SET LOCAL scopes the HNSW settings to the read-only transaction, so pooled connections are not polluted.

Spring angle: fail closed

An empty aclKeys list returns nothing. A missing group claim must never mean "no filter". Encode this as a unit test. A refactor that turns && into an optional predicate is the most common way ACL leaks are introduced.

          List.of(), false, "NO_CONTEXT");

    String passages = IntStream.range(0, top.size())

        .user(u -> u.text("""
            <passages>
            {passages}
            </passages>
            Question: {question}""")

            .param("question", question))
        .call()

        .toList();

import java.util.regex.Matcher;
import java.util.regex.Pattern;
import org.springframework.stereotype.Component;

@Component
public class CitationValidator {
  private static final Pattern MARKER = Pattern.compile("\\[(\\d+)]");
  private static final Pattern SENTENCE = Pattern.compile("(?<=[.!?])\\s+");

  public record Result(double coverage, boolean allMarkersValid) {}

  public Result validate(String answer, int passageCount) {
    String[] sentences = SENTENCE.split(answer.strip());
    int supported = 0;
    boolean valid = true;
    for (String s : sentences) {
      Matcher m = MARKER.matcher(s);
      boolean any = false;
      while (m.find()) {
        any = true;
        int n = Integer.parseInt(m.group(1));
        if (n < 1 || n > passageCount) valid = false;     // hallucinated citation
      }
      if (any) supported++;
    }
    return new Result(sentences.length == 0 ? 0 : (double) supported / sentences.length, valid);
  }
}

import hashlib

log = logging.getLogger("embed_indexer")
llm = anthropic.Anthropic()                          # base_url points at the LLM gateway via env
s3 = boto3.client("s3")
CONTEXT_MODEL = "claude-haiku-5-5"                   # version-sensitive

CONTEXT_PROMPT = (
    "Here is a chunk from the document above. Write one or two sentences that situate this chunk "
    "within the overall document to improve search retrieval. Answer with the sentences only.\n"
    "<chunk>\n{chunk}\n</chunk>"
)


def contextual_prefix(doc_text: str, chunk: Chunk) -> str:
    # The document is a cacheable prefix; only the chunk varies -> cache reads after the first call.
    resp = llm.messages.create(
        model=CONTEXT_MODEL,
        max_tokens=120,
        system=[{"type": "text", "text": "<document>\n" + doc_text + "\n</document>",
                 "cache_control": {"type": "ephemeral"}}],
        messages=[{"role": "user", "content": CONTEXT_PROMPT.format(chunk=chunk.text)}],
    )
    return "".join(b.text for b in resp.content if b.type == "text").strip()


def index_document(conn: psycopg.Connection, embedder: Embedder, evt: dict) -> int:
    parsed = json.loads(s3.get_object(Bucket=evt["bucket"], Key=evt["key"])["Body"].read())
    chunks = structure_aware_chunks(parsed)
    prefixes = [contextual_prefix(parsed["text"], c) for c in chunks]
    texts = [f"{p}\n{c.text}" for p, c in zip(prefixes, chunks)]
    vectors = embedder.embed_cached(texts)              # cache key: sha256(model + text)

    with conn.transaction():                            # readers never see a half-swapped document
        doc_id = conn.execute(
            """INSERT INTO document (source_id, external_id, version, title, uri, acl_keys, content_hash)
               VALUES (%s,%s,%s,%s,%s,%s,%s)
               ON CONFLICT (source_id, external_id) DO UPDATE
                 SET version = EXCLUDED.version, title = EXCLUDED.title, uri = EXCLUDED.uri,
                     acl_keys = EXCLUDED.acl_keys, content_hash = EXCLUDED.content_hash, updated_at = now()
                 WHERE document.version <= EXCLUDED.version          -- ignore stale, out-of-order events
               RETURNING id""",
            (evt["sourceId"], evt["externalId"], evt["version"], parsed["title"], parsed["uri"],
             evt["aclKeys"], hashlib.sha256(parsed["text"].encode()).hexdigest()),
        ).fetchone()
        if doc_id is None:
            log.info("stale event ignored", extra={"externalId": evt["externalId"]})
            return 0
        conn.execute("DELETE FROM chunk WHERE doc_id = %s", (doc_id[0],))
        with conn.cursor() as cur:
            cur.executemany(

  public ConversationService(ChatClient.Builder builder, ChatMemory chatMemory, QueryRewriter rewriter,
                             HybridRetriever retriever, RerankClient reranker,
                             MemoryStore memory, TurnRepository turns) {
    this.chatMemory = chatMemory;
    this.chat = builder
        .defaultSystem(AssistantPrompts.SYSTEM)  // cite [n]; passages are untrusted; use facts if relevant
        .defaultAdvisors(MessageChatMemoryAdvisor.builder(chatMemory).build())
        .build();
    this.rewriter = rewriter;
    this.retriever = retriever;
    this.reranker = reranker;
    this.memory = memory;
    this.turns = turns;
  }

  public Flux<String> reply(Principal p, UUID conversationId, String message) {
    String history = turns.recentTranscript(conversationId, 6);
    var rq = rewriter.rewrite(history, message);
    List<ScoredChunk> context = rq.needsRetrieval() ? multiRetrieve(p, rq) : List.of();
    UUID turnId = turns.startTurn(conversationId, message, rq.standalone(), context);
    String facts = String.join("\n", memory.factsFor(p.subject()));

    return chat.prompt()
        .user(u -> u.text("""
            <user_facts>{facts}</user_facts>
            <passages>{passages}</passages>
            {message}""")
            .param("facts", facts)
            .param("passages", Passages.numbered(context))
            .param("message", message))
        .advisors(a -> a.param(ChatMemory.CONVERSATION_ID, conversationId.toString()))
        .stream()
        .content()
        .doOnComplete(() -> turns.completeTurnAsync(turnId))   // usage + citations; may trigger summary
        .doOnCancel(() -> turns.markCancelled(turnId));         // user pressed "stop"
  }

  private List<ScoredChunk> multiRetrieve(Principal p, QueryRewriter.RewrittenQuery rq) {
    List<String> queries = new ArrayList<>();
    queries.add(rq.standalone());
    queries.addAll(rq.subQueries());
    List<Future<List<ScoredChunk>>> futures = queries.stream()
        .map(q -> pool.submit(() -> retriever.retrieve(p, q, 20))).toList();
    Map<UUID, Double> rrf = new HashMap<>();
    Map<UUID, ScoredChunk> byId = new HashMap<>();
    for (var f : futures) {
      List<ScoredChunk> list = getQuietly(f);
      for (int r = 0; r < list.size(); r++) {
        var c = list.get(r);
        rrf.merge(c.chunkId(), 1.0 / (60 + r + 1), Double::sum);
        byId.putIfAbsent(c.chunkId(), c);
      }
    }
    var fused = rrf.entrySet().stream()
        .sorted(Map.Entry.<UUID, Double>comparingByValue().reversed())
        .limit(40).map(e -> byId.get(e.getKey())).toList();
    return reranker.rerank(rq.standalone(), fused, 8);
  }

  private static List<ScoredChunk> getQuietly(Future<List<ScoredChunk>> f) {
    try { return f.get(2, TimeUnit.SECONDS); }
    catch (Exception e) { return List.of(); }       // degrade: one failed sub-query is not fatal
  }
}

          .system(s -> s.param("intent", ticket.intent()))

          .call()

      if (post.escalate()) return handoff(ticket, post.reason());

    } catch (EscalationRequested er) {
      return handoff(ticket, er.summary());
    }
  }

    tickets.transition(t, TicketState.HUMAN_QUEUE);
    tickets.attachHandoffPacket(t, reason, audit.actionsFor(t.id()));   // summary + actions + draft reply
    return AgentTurn.reply("I'm connecting you with a colleague who can help with this. "
        + "They'll see everything we've discussed, so you won't need to repeat yourself.");
  }

7.8 P6 — Search gateway in Go: fan-out with deadlines and RRF

package fanout

import (
	"context"
	"log/slog"
	"sort"
	"time"
)

type Hit struct {
	ID    string
	Score float64
}

type Backend interface {
	Name() string
	Search(ctx context.Context, q ParsedQuery, k int) ([]Hit, error)
}

type Reranker interface {
	Rerank(ctx context.Context, query string, ids []string) ([]string, error)
}

type Gateway struct {
	Lexical, Semantic Backend
	Rerank            Reranker
	BranchTimeout     time.Duration // e.g. 80ms
	RerankTimeout     time.Duration // e.g. 60ms
}

type result struct {
	name string
	hits []Hit
	err  error
}

// Search runs lexical and semantic retrieval in parallel, fuses with RRF, and reranks if time allows.
// A slow or failed branch degrades quality; it never fails the request unless both branches fail.
func (g *Gateway) Search(ctx context.Context, q ParsedQuery, k int) ([]string, error) {
	ch := make(chan result, 2)
	for _, b := range []Backend{g.Lexical, g.Semantic} {
		go func(b Backend) {
			bctx, cancel := context.WithTimeout(ctx, g.BranchTimeout)
			defer cancel()
			hits, err := b.Search(bctx, q, 100)
			ch <- result{b.Name(), hits, err}
		}(b)
	}
	var lists [][]Hit
	for i := 0; i < 2; i++ {
		r := <-ch
		if r.err != nil {
			slog.WarnContext(ctx, "branch degraded", "backend", r.name, "err", r.err)
			continue
		}
		lists = append(lists, r.hits)
	}
	if len(lists) == 0 {
		return nil, ErrAllBackendsFailed
	}
	fused := RRF(lists, 60)
	if len(fused) > 50 {
		fused = fused[:50]
	}
	rctx, cancel := context.WithTimeout(ctx, g.RerankTimeout)
	defer cancel()
	if reranked, err := g.Rerank.Rerank(rctx, q.Normalized, fused); err == nil {
		fused = reranked
	} else {
		slog.InfoContext(ctx, "rerank skipped", "err", err) // serve fused order
	}
	if len(fused) > k {
		fused = fused[:k]
	}
	return fused, nil
}

// RRF fuses ranked lists by reciprocal rank; ties broken by ID for determinism.
func RRF(lists [][]Hit, k float64) []string {
	score := map[string]float64{}
	for _, l := range lists {
		for rank, h := range l {
			score[h.ID] += 1.0 / (k + float64(rank+1))
		}
	}
	ids := make([]string, 0, len(score))
	for id := range score {
		ids = append(ids, id)
	}
	sort.Slice(ids, func(i, j int) bool {
		if score[ids[i]] == score[ids[j]] {
			return ids[i] < ids[j]
		}
		return score[ids[i]] > score[ids[j]]
	})
	return ids
}

The buffered channel of size 2 means a goroutine whose branch finishes after the caller has given up never blocks, so there is no goroutine leak. Exact-identifier queries (SKU or order number patterns detected by query understanding) bypass this path and go straight to a keyword lookup. Answer generation lives in a separate Python or Java service that receives only the result IDs from the signed answerToken.

                recall.append(len(got_docs & set(row["expected_doc_ids"])) / len(row["expected_doc_ids"]))
            if set(row.get("must_not_cite", [])) & (got_docs | cited_docs):
                leaks += 1
            if not row["answerable"]:
                abstain_ok.append(0 if r["answerable"] else 1)
            elif r["answerable"]:
                faith.append(judge_faithfulness(r["answer"], [c["content"] for c in r["retrieved"]]))
    report = {"recall@8": statistics.mean(recall), "faithfulness": statistics.mean(faith),
              "abstention": statistics.mean(abstain_ok), "acl_leaks": leaks}
    print(json.dumps(report, indent=2))
    failed = (leaks > 0 or report["recall@8"] < th["recall"] or
              report["faithfulness"] < th["faithfulness"] or report["abstention"] < th["abstention"])
    return 1 if failed else 0


if __name__ == "__main__":
    sys.exit(main(*sys.argv[1:4]))

The /internal/eval/answer endpoint exists only in the eval profile. It accepts ACL keys directly so the dataset can impersonate principals, and it is never exposed through the ingress. For P3, the equivalent dataset holds labelled historical tickets (triage macro-F1) and simulated conversations: a second model plays the customer from a scenario card ("double charge, impatient, will ask for a human after two messages"). The resolver is scored on outcome, policy compliance and tool-call correctness. For P6, the judged query set yields nDCG@10 and recall@50 offline, before any A/B test.

9. Case Studies: Comparable Systems in Industry

Each summary paraphrases what the company has published. Numbers are the company's own claims, labelled as such. Follow the links for details.

9.1 DoorDash — RAG for Dasher support with guardrails and a judge Verified

DoorDash's September 2024 post "Path to high-quality LLM-based Dasher support automation" describes replacing flow-based automation with a RAG system over knowledge-base articles. There are three parts: the RAG component; an LLM Guardrail that checks responses for grounding, coherence and policy before they are sent, with a cheap first check followed by an LLM-based check; and an LLM Judge for quality monitoring. When the guardrail would add too much latency or flags a response, they default to a human agent. That is the same "escalate on doubt" pattern as P3's post-check. Lesson for P3: put a guardrail between generation and send, and make human fallback cheap.

9.2 Klarna — AI assistant in customer service Verified

Klarna's February 2024 press release claimed that in its first month the assistant handled 2.3 million conversations, two-thirds of its customer-service chats, with customer satisfaction on par with human agents. It also claimed fewer repeat inquiries and work equivalent to 700 full-time agents. Customers could still ask for a human. These are company claims, not independently audited figures. Lesson for P3: resolution claims are credible only next to satisfaction and repeat-contact metrics, which is why §3.4 defines bad-resolution rate and CSAT parity as success metrics.

9.3 LinkedIn — building a generative AI assistant Verified

LinkedIn's engineering post "Musings on building a Generative AI product" (2024) describes routing a query to specialised agents, retrieving from internal APIs and search, and generating a response. It reports that getting to a good-enough experience quickly was easy, while the last stretch of quality, consistent evaluation and latency were hard. It also describes a small horizontal team owning shared components such as prompt templates and evaluation tooling. Lesson for P2: budget most of the project for evaluation and quality iteration, not for the first demo.

9.4 Dropbox Dash — universal search with RAG and agents Verified

Dropbox's post "Building Dash: How RAG and AI agents help us meet the needs of businesses" (2025) describes a search product over many connected apps. It balances latency, quality and freshness in retrieval, uses agents for multi-step tasks that plain RAG cannot handle, and respects each user's permissions across sources. Follow-up posts on the Dropbox tech blog cover their context engine and knowledge-graph work. Lesson for P1/P6: connectors, permissions and freshness are first-class architecture, not afterthoughts.

9.5 Anthropic — Contextual Retrieval Verified

The Contextual Retrieval post (September 2024) prepends a short, model-generated context to each chunk before embedding and BM25 indexing. It reports that contextual embeddings plus contextual BM25 cut the top-20 retrieval failure rate substantially in their experiments, with reranking cutting it further, and it uses prompt caching to make the preprocessing affordable. The ingestion worker in §7.5 implements this pattern. Lesson: cheap preprocessing at index time often beats expensive cleverness at query time.

9.6 Shopify Sidekick — production agent lessons Verified

Shopify's "Building production-ready agentic systems: Lessons from Shopify Sidekick" (2025) discusses how a growing tool inventory created scaling problems, and why LLM judges were trusted only after they were shown to agree closely with human experts. It also covers reward hacking during training. Lesson for P3: calibrate the judge before you trust its numbers, and keep the per-intent tool set small.

9.7 Slack AI — privacy and permissions in RAG Verified

Slack's "How we built Slack AI to be secure and private" (2024) describes running models inside their own infrastructure boundary, not using customer data to train models, and making sure the AI only sees data the requesting user can already see, using the same permission model as search. Lesson for P1: "the assistant can see only what the user can see" is a design principle you state up front and test, not a feature added later.

12. Common Mistakes and Production Failures

  • Filtering ACLs after retrieval. The top-8 is computed globally, then forbidden chunks are removed, leaving one or zero passages and bad answers. Worse, someone "optimises" by caching the pre-filter list across users. Filter inside the query.
  • Trusting the model to respect permissions. Prompt text such as "do not reveal confidential information" is not access control. If a chunk reaches the prompt, assume it can reach the user.
  • Re-embedding the whole corpus on every sync. Without content hashing and an embedding cache, a nightly full sync costs as much as the initial load and saturates the embedding service.
  • Mixing embedding models in one index. A model upgrade written to the same column without a version field makes old and new vectors incomparable, and recall silently collapses. Store embed_model, build a new column or index, and switch over with a flag.
  • Letting tools take customerId from the model. This is the classic excessive-agency bug: an injected message makes the agent read another customer's order. Bind identity in code.
  • No idempotency on side-effecting tools. The provider times out, the framework retries the turn, and the refund is issued twice. Derive idempotency keys from ticket and step.
  • Evaluating only on happy-path questions. The golden set must include unanswerable, adversarial (ACL, injection), ambiguous and multi-hop items, or abstention and safety regress unnoticed.
  • Uncalibrated LLM judges. A judge that scores everything 4/5 makes every change look neutral. Measure judge–human agreement on a labelled sample before you rely on it, and re-measure when you change judge model or rubric.
  • Blocking search results on answer generation. Putting a 2-second LLM call on the synchronous path of P6 makes search feel broken. Decouple it.
  • Rewriter overreach in P2. The rewriter "helpfully" adds assumptions ("for full-time employees in the US"), which narrows retrieval wrongly. Log rewritten queries and eval them separately.
  • Silent memory. Storing inferred facts without consent creates privacy incidents and bizarre personalisation. Propose, confirm, display and allow deletion.
  • Measuring deflection instead of resolution. See §3.4.

13. Production: Deployment, Observability, Security, Scaling and Performance

13.1 Shared: deployment procedure

  1. Provision managed PostgreSQL 17 with pgvector enabled (check that your provider's pgvector version supports halfvec and iterative scans), managed Kafka, OpenSearch (P6) and an object-storage bucket with SSE-KMS.
  2. Apply Flyway migrations from a Kubernetes Job (helm upgrade --install db-migrate) before service rollout. Build the HNSW index CONCURRENTLY on large tables and raise maintenance_work_mem for the build.
  3. Deploy the LLM gateway and register per-service virtual keys and quotas. Services receive only gateway tokens, synced from Vault via External Secrets Operator.
  4. Deploy ingestion workers with KEDA ScaledObjects on consumer lag. Run the initial backfill with a dedicated consumer group and a rate limit on the embedding service.
  5. Deploy product services with Argo Rollouts canaries. The analysis template gates on error rate, p95 latency and an online eval metric (thumbs-down ratio or citation-validity ratio over the canary window).

13.2 Shared: observability

  • Traces: one OpenTelemetry trace per request with spans retrieve.lexical, retrieve.vector, rerank, llm.chat and tool.*. Spring AI emits Micrometer observations for chat-client and model calls, including token usage, which export as OTel spans and metrics. Record prompt version, model and retrieved chunk IDs as span attributes. Record prompt text only in a sampled, access-controlled store.
  • Metrics (SLIs): answer latency (TTFT and total), retrieval latency, gen_ai.client.token.usage by service and model, cost per request (computed in the gateway), abstention rate, citation-validity rate, thumbs-down rate, escalation rate (P3), bad-resolution rate (P3), zero-result rate (P6) and rerank-skipped rate (P6).
  • Logs: structured JSON with trace IDs. PII is redacted at the logger level, not by convention.
  • Quality dashboards: nightly eval trends per project, per-source "not found" rates (they reveal coverage gaps) and top negative-feedback queries.

13.3 P1 — Production specifics

Security. OIDC resource server; group resolution from the IdP (SCIM-synced table or Graph API) cached for 5 minutes; early-binding ACLs plus a re-check of cited documents against the source for high-sensitivity spaces; audit log of retrieved and cited chunk IDs. Passages are wrapped in tags and the system prompt treats them as data. Indirect prompt injection in documents remains possible, so the answer path has no tools: a Q&A bot with no tools can at worst say something wrong. Data residency is enforced by the gateway's routing configuration. Performance: cache the system prompt (provider prompt caching); keep k small after reranking; stream. Scaling: read replicas for retrieval; partition chunk by source if vacuum on one giant table becomes a problem. Degraded mode: on a provider outage, return the reranked passages as "top sources" without a generated answer. Users still get value.

13.4 P2 — Production specifics

Security and privacy: conversation ownership checks on every endpoint; memory export and delete endpoints; encryption at rest for turn.content with a per-tenant key if conversations hold sensitive data; retention jobs (30 days) implemented as partition drops, not deletes. Performance: the rewriter adds about 300–600 ms Illustrative. Start retrieval for the raw message speculatively in parallel with rewriting, and keep it if the rewrite is near-identical. Scaling: SSE connections are long-lived. Use WebFlux (or virtual threads with Spring MVC) and set ingress idle timeouts above your longest generation. Make the client reconnect with Last-Event-ID and serve the completed turn from the DB. Feedback operations: a weekly 30-minute triage meeting with a domain expert labels negative-feedback items into "retrieval miss", "bad source", "generation error" and "out of scope". Only the first three become eval items or tickets.

13.5 P3 — Production specifics

Security: tool calls bound to the authenticated customer; policy engine for limits; idempotency keys; rate limits per customer on side-effecting intents; injection red-team suite in CI (messages that attempt refunds over the limit, other customers' orders, or a system-prompt leak). Disclose to customers that they are talking to an AI, as required in many jurisdictions. Keep a full, immutable audit trail of tool calls and decisions in the ticket database and ship it to the SIEM. Reliability: the AI path is optional. A circuit breaker on the gateway, plus a queue-depth trigger, switches new tickets to "human queue with triage only". Triage itself has a rules-based fallback (keyword routing). Scaling: ticket ingestion goes through Kafka. Triage consumers scale with lag, and chat sessions are sticky only through the DB, never in memory. Performance: classify with a small model; reserve the large model for resolution; cap tool calls at 6 and wall-clock at 20 s per turn. Finance reconciliation: a daily job matches AI-issued refunds against the audit log and alerts on any mismatch.

13.6 P6 — Production specifics

Performance: the Go gateway has per-branch deadlines; the query-understanding cache (Redis, keyed by normalised query, TTL 1 day) absorbs head queries; vector search has a warm HNSW index in memory; the reranker batches across concurrent requests (dynamic batching in Triton or a custom asyncio batcher) with a 60 ms timeout. Scaling: the gateway is stateless and scales on RPS; OpenSearch scales with replica shards for QPS and primary shards for size; the reranker GPU pool scales on queue time, not GPU utilisation. Freshness: price and stock updates go through a separate fast lane (partial document updates in OpenSearch, no re-embedding), and only text changes trigger re-embedding. Security: the answer service only sees public catalogue data; the answerToken is signed and expires in 60 s, so result lists cannot be forged to make the summariser ground on arbitrary IDs. Experimentation: every ranking change ships behind an experiment flag with interleaving or A/B evaluation. Offline nDCG gains do not always survive contact with users.

14. Exercises and Extensions

Exercise 1 · Foundational

Extend HybridRetriever with a filters parameter (source kind, updated after a date). Make sure both CTEs apply it, and add a Testcontainers test proving that a filter on one branch only would change the results.

Solution

Add AND (CAST(:kinds AS text[]) IS NULL OR d.kind = ANY(:kinds)) style predicates. That requires joining document in both CTEs, or denormalising source_kind and updated_at onto chunk to keep single-table scans, which is preferable for the HNSW path. Test: index two documents with identical text, one old and one new. Query with updatedAfter between them and assert that only the new one is returned. Then deliberately remove the predicate from the vector CTE and watch the test fail, because RRF still surfaces the old document through the vector list. The lesson: every candidate generator must apply every filter, or fusion re-introduces filtered items.

Exercise 2 · Intermediate

Implement late-binding verification for P1. For the cited documents only, call a SourcePermissionClient.canRead(user, docIds) batch API with a 30 s Caffeine cache and a 150 ms timeout. Decide what to do on timeout, and justify it.

Solution

After generation and citation extraction, call canRead with the distinct cited doc IDs. If any is denied, regenerate without those passages, or remove the sentences that cite them and mark the answer partially supported. On timeout, the safe default for high-sensitivity sources is fail closed: hide citations from those sources and show a "could not verify access" notice. For low-sensitivity sources, fail open is acceptable, because early binding already filtered them and the residual risk is only sync lag. Make the policy configurable per source and record verification outcomes as a metric. A rising deny rate means your ACL sync is broken.

Exercise 3 · Intermediate

Build the P3 conversation simulator. A "customer" model receives a scenario card (goal, persona, hidden facts, when to demand a human) and talks to ResolutionAgent through its HTTP API for at most 8 turns. A judge scores outcome, policy compliance and tone. Report per-intent bad-resolution estimates.

Solution

Scenario cards are YAML: intent, persona, facts (order ID, amounts), success_condition, escalate_after. Seed a test CRM (WireMock or a Testcontainers Postgres) with matching orders. Loop: the simulator model generates the customer message from the card plus the transcript, and the agent replies. Stop on resolution, handoff or 8 turns. The judge rubric asks: did the outcome match success_condition? Were any tool calls out of policy (checked deterministically from the audit log, not by the judge)? Did the agent promise anything not in policy? Run each card 5 times to estimate variance. Report mean and spread per intent, and gate intent promotion (Figure 8.7.11) on these numbers plus shadow-mode data.

Exercise 4 · Advanced

Replace RRF in P6 with a learning-to-rank model trained on click logs. Design the features, the training data pipeline (handling position bias) and the safe rollout.

Solution

Features: BM25 score, vector similarity, reranker score, ranks in each list, freshness, popularity, price match to extracted attributes, and in-stock status. Labels: clicks and add-to-cart events, debiased for position with inverse propensity weighting, where propensities are estimated from a small randomisation experiment (swap adjacent results for 1% of traffic). Train LambdaMART (LightGBM lambdarank) offline. Evaluate nDCG@10 on human-judged queries and on held-out click data. Serve the model in the Go gateway via ONNX or a sidecar, with a 10 ms budget. Roll out with interleaving first (sensitive and fast), then an A/B test on conversion. Keep RRF as the fallback when features are missing.

Exercise 5 · Advanced

Migrate the embedding model from a 1024-d model to a new 768-d model without downtime and without a period of degraded recall.

Solution

Add a column embedding_v2 halfvec(768) and a new HNSW index on it. Run a backfill consumer group that re-embeds from the canonical chunk text, rate-limited and resumable by chunk ID. Dual-write new chunks to both columns. Once coverage is 100%, run the eval suite with a feature flag that switches the vector CTE to embedding_v2 and compare. Canary by user cohort. After full rollout and one rollback window, drop the old index and column. Query embeddings must use the matching model, so the flag selects both the column and the embedder bean. Never mix them.

15. Interview: Presenting These Projects

How to present one of these projects (5 minutes): (1) the problem and success metric in one sentence ("cut time-to-answer for internal policy questions; target faithfulness ≥ 0.95, zero ACL leaks"); (2) a single architecture diagram: ingestion, retrieval core, product service, gateway; (3) the hardest decision and its trade-off (early- vs late-binding ACLs, autonomy boundary); (4) how you know it works: the eval set, CI gating, online metrics; (5) one production incident or near miss and what you changed. Interviewers listen for whether you treat the model as an unreliable dependency that you surround with deterministic engineering.

Architecture How do you guarantee a RAG system never leaks documents a user cannot access?

Enforce permissions in retrieval, not in the prompt. ACL keys go on every chunk and are filtered in the same SQL or search query for all candidate generators, so they are present before fusion and reranking. Groups come from the IdP, never from the client. Empty groups fail closed. A permission-only sync runs frequently, and cited documents in sensitive sources are re-verified against the source system. I test it with an adversarial eval set and Testcontainers tests with identical text across permission levels, and the audit log records retrieved and cited chunk IDs so leaks can be detected after the fact.

Conceptual Why hybrid search instead of only vector search?

Dense retrieval handles paraphrase and vocabulary mismatch but is weak on exact tokens (error codes, SKUs, names) and on out-of-domain text. BM25 is the reverse. Fusing them with RRF uses only ranks, so it needs no score calibration and is robust. Benchmarks such as BEIR showed BM25 remains a strong baseline out of domain, which is why the combination is the default. Then a cross-encoder reranker fixes precision in the top-k.

Scenario Users say the assistant "forgets" what they were talking about after a few turns. What do you check?

First the rewriter: log and inspect rewritten queries for the failing conversations, since a lost referent there means retrieval runs on the wrong query. Then the memory window and summary: is the summary dropping key entities? Is the window too small in tokens because passages fill the context? Then the eval set: add these conversations as multi-turn items. Fixes include entity-preserving summary prompts, keeping the last user-mentioned entities as structured state, raising the window and lowering k, and evaluating the rewriter separately with its own metric.

Architecture Where do you put the limit "refunds up to $100 without approval"?

In code the model cannot influence: a policy engine invoked inside the refund tool, with the customer identity bound by the service, not passed by the model. The prompt may describe the policy so the model behaves sensibly, but enforcement is server-side, audited, and tested with injection attempts. Over-limit requests return NEEDS_APPROVAL and route to a human with a prepared packet.

Coding Write RRF and explain the constant.

For each list, for each document at 1-based rank r, add 1/(k + r) to its score, then sort descending (see the Go code in §7.8). k=60 dampens the advantage of top ranks, so one list's first place does not overwhelm consistent mid-ranks across lists. Smaller k makes fusion more top-heavy. Weights per list are an easy extension. Ties should be broken deterministically for testability.

Scenario The autonomous resolution rate looks great but CSAT for AI-handled tickets dropped. What happened and what do you do?

You are probably counting customers who gave up as resolved. Check reopen and repeat-contact within 7 days, and abandonment mid-conversation. Segment by intent, since usually one or two intents are responsible. Demote those intents to draft-only (Figure 8.7.11), review transcripts, and fix the cause: missing tool, wrong policy summary, or escalation triggers firing too late. Redefine the success metric as resolution without reopen, with CSAT parity as a guardrail metric in every rollout.

Conceptual How do you evaluate a RAG system before it has users?

Build a golden set with domain experts: answerable questions with expected source documents and reference answers, unanswerable questions, adversarial ACL and injection items, and multi-hop questions. Measure retrieval (recall@k, MRR) separately from generation (faithfulness, answer relevance, citation precision, abstention). Use an LLM judge calibrated on a human-labelled sample. Synthetic questions generated from documents are useful for coverage but biased towards lexical overlap, so do not use them alone. Gate CI on a smoke subset and releases on the full set.

Architecture Why is the answer panel in AI search asynchronous?

Results have a sub-300 ms budget, while generation takes seconds. Coupling them would make search slower for everyone, including the majority who just click a result. Decoupling lets the panel stream in when ready and be skipped under load. Passing the exact result IDs to the answer service (a signed token) grounds the summary in what the user sees and avoids a second retrieval.

Behavioral Tell me about a time an LLM feature failed in production.

Structure: context, failure, detection, fix, systemic change. A good answer shows detection by metrics (citation-validity drop, thumbs-down spike), root cause in deterministic code or data (an ACL sync bug, an embedding model mismatch, a stale KB article), not just "the model hallucinated", and a lasting fix: an eval item, a test, an alert. Interviewers want evidence that you build feedback loops.

16. Knowledge Check

  • Build one ACL-aware, hybrid, testable retrieval core and put thin products on top. Four separate RAG stacks mean four sets of bugs.
  • Permissions belong inside retrieval queries for every candidate generator. Prompts are not access control, and empty groups must fail closed.
  • Ingestion quality (parsing, structure-aware chunking, contextual prefixes, atomic version swaps, content hashing) decides most of the answer quality.
  • Citations should be validated by code. Abstention is a feature with its own metric.
  • Conversational RAG needs query rewriting, bounded memory with consent, and feedback tied to turn IDs.
  • Support autonomy is granted per intent based on evidence. Limits live in a policy engine, identity is bound in code, and side effects are idempotent and audited.
  • AI search keeps results fast and deterministic, and adds generated answers asynchronously. Deadlines and graceful degradation are part of the design.
  • Every project ships an eval set and CI gate. LLM judges are calibrated against humans before you trust them.

A user can see 0.2% of a 10M-chunk corpus. Vector search returns almost nothing for them although relevant chunks exist. The most likely cause?

  1. The embedding model is not multilingual
  2. RRF constant k is too large
  3. The HNSW scan collects ef_search candidates and the ACL filter removes nearly all of them
  4. The GIN index on tsvector is missing
Approximate indexes apply the filter after collecting candidates. Highly selective filters starve the result. Use iterative index scans (pgvector 0.8+), larger ef_search, or partial and partitioned indexes. The other options do not explain a permission-correlated recall loss.

In P3, where should the customer identity used by tools come from?

  1. A tool parameter the model fills from the conversation
  2. Bound by the service from the authenticated session when the tool instance is created
  3. The system prompt
  4. The triage classification output
Identity must never be under model control. An injected message could otherwise redirect actions to other customers' records.

Why does the ingestion worker delete old chunks and insert new ones in a single transaction?

  1. To reduce WAL volume
  2. Because HNSW indexes cannot be updated
  3. To trigger re-embedding
  4. So queries never see a mix of two document versions, or a document with no chunks
Atomic replacement gives per-document snapshot consistency to concurrent readers.

With RRF (k=60), a document ranked 1st in the lexical list only versus a document ranked 5th in both lists: which scores higher?

  1. The document ranked 5th in both (2/65 ≈ 0.0308 > 1/61 ≈ 0.0164)
  2. The document ranked 1st in one list
  3. They tie
  4. It depends on the BM25 score magnitude
RRF rewards agreement across lists, and only ranks matter, not raw scores.

Which metric best protects against a support bot that "resolves" tickets by frustrating customers?

  1. Deflection rate
  2. Average handle time
  3. Bad-resolution rate (reopen or repeat contact within 7 days) with CSAT parity
  4. Number of tool calls per conversation
Deflection counts abandonment as success. Reopen and repeat contact capture real outcomes.
