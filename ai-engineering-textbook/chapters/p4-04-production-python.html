Production Python: Testing, Packaging, Performance, Deployment & Java Interop

Writing Python that works is easy; shipping Python that a platform team will run for years is a discipline. This chapter covers the parts of the Python toolchain that correspond to Maven/Gradle, JUnit/Testcontainers, JFR/async-profiler, Spring Boot Actuator and Micrometer, and the integration contracts (REST, gRPC, Kafka) that let a Python AI service live inside a Spring Boot estate. We finish docflow with tests, a reproducible build, a hardened container image, telemetry, and Java clients.

  • Prerequisites: Chapters 4.1–4.3; Maven or Gradle, JUnit 5, Testcontainers, Docker, Kubernetes basics, Micrometer/OpenTelemetry in Spring.
  • You will be able to: structure a pytest suite with fixtures, parametrisation, property-based and container-backed tests; manage dependencies reproducibly with pyproject.toml and uv; profile CPU and memory with py-spy, Scalene and memray and pick the right optimisation (algorithmic, vectorised, compiled, cached); deploy with correctly sized Uvicorn/Gunicorn workers in a minimal container; instrument with OpenTelemetry; and integrate with Spring Boot through REST, gRPC and Kafka with shared schemas.

1. Introduction: From "It Runs on My Laptop" to a Platform Citizen

A Spring Boot team arrives with strong production expectations: mvn verify runs unit and integration tests; the build is reproducible from the lockstep of the POM and a repository manager; the artifact is a single JAR or an OCI image built by Jib or Buildpacks; Actuator exposes health and metrics; Micrometer and OpenTelemetry export to the observability stack; and other services consume an OpenAPI or protobuf contract. Python can meet every one of these expectations, but the tools are different, more numerous, and historically less standardised. In 2026 the ecosystem has largely converged: pyproject.toml for metadata and tool configuration, uv (or Poetry) for environments and lockfiles, pytest for tests, ruff for linting and formatting, pyright or mypy for types, OpenTelemetry for telemetry.

The second half of the chapter is about the boundary. A Python AI service in a Java company succeeds or fails on its contracts: are the request and event schemas shared and versioned? Are deadlines propagated? Can the Java team's tracing follow a request into Python and back? Do both sides agree on retries and idempotency? Those are architecture questions, and they are where your Spring experience is most valuable.

3. Fundamentals

3.1 pytest's model

pytest discovers test_*.py files and test_* functions, and rewrites assert statements at import time to produce rich failure messages (no AssertJ needed). Its central concept is the fixture: a function decorated with @pytest.fixture that provides a resource, requested by naming it as a test parameter. Fixtures have scopes (function, class, module, package, session), can depend on other fixtures, and use yield for teardown. This is dependency injection for tests, the equivalent of JUnit 5 extensions plus @BeforeEach/@BeforeAll, and Spring's test context caching corresponds roughly to session-scoped fixtures. conftest.py files share fixtures across a directory tree.

3.2 Parametrisation, markers and plugins

@pytest.mark.parametrize("a,b,expected", [...]) generates one test per case (@ParameterizedTest with @CsvSource); fixtures can be parametrised too (run every test against SQLite and PostgreSQL). Markers (@pytest.mark.integration) select subsets (-m "not integration"), like JUnit tags. Plugins extend everything: pytest-asyncio or AnyIO's plugin for async tests, pytest-xdist for parallel execution, pytest-cov for coverage, pytest-randomly for order randomisation.

3.3 Property-based testing with Hypothesis

Instead of hand-picked examples, you state properties ("chunking then joining preserves every word", "serialise then parse is identity") and Hypothesis generates inputs, including nasty edge cases, then shrinks failures to minimal examples and stores them in a database for replay. jqwik is the JVM equivalent. Property-based tests are especially valuable for parsers, chunkers, serialisers and anything handling LLM output.

3.4 Testcontainers and the test pyramid

Testcontainers for Python mirrors the Java library: start PostgreSQL, Redis or Kafka in Docker from a fixture, yield a connection URL, stop it at the end of the session. Use SQLite or fakes for fast unit tests of logic, but run repositories, migrations and locking behaviour against the real database engine.

3.5 Mocks, fakes and dependency overrides

unittest.mock (Mock, AsyncMock, patch) is Mockito with less ceremony and more danger: patch("module.name") replaces an attribute where it is looked up, not where it is defined, a classic source of tests that patch the wrong thing. Prefer fakes behind Protocols (docflow's HashEmbedder, LocalBlobStore) and FastAPI's dependency_overrides; use patch for genuinely global things (time, randomness) or third-party calls.

3.6 Environments: interpreter, venv, site-packages

A virtual environment is a directory with a pyvenv.cfg, a symlink or copy of an interpreter, and its own site-packages. Activating it just puts its bin/ first on PATH. There is no classpath per application: one environment has exactly one version of each distribution installed, so two dependencies requiring incompatible versions of a third cannot coexist (no shading as in Maven). The resolver must find one consistent set, which is why lockfiles matter so much.

3.7 pyproject.toml, build backends, wheels

  • [project] (PEP 621): name, version, requires-python, dependencies (with version specifiers), optional dependencies (extras), entry points/scripts.
  • [dependency-groups] (PEP 735): dev/test/lint groups that are not part of the published package, like Maven's test scope.
  • [build-system]: the PEP 517 backend (hatchling, setuptools, flit-core, maturin for Rust, scikit-build-core for C++).
  • [tool.*]: configuration for ruff, pyright, pytest, coverage, uv.
  • Wheels are zip archives with a tag like cp313-cp313-manylinux_2_28_x86_64 (interpreter, ABI, platform). Pure-Python wheels are py3-none-any. Installing a wheel is just unzipping into site-packages: fast and no compiler. An sdist must be built on install, which in a Docker build can mean pulling compilers: avoid.

3.8 Lockfiles

pyproject.toml declares ranges (fastapi>=0.121,<1); the lockfile records the exact resolved versions and hashes of the full transitive graph for all target platforms. uv.lock is cross-platform (one lock for Linux, macOS, Windows); uv sync --frozen installs exactly the lock and fails if pyproject.toml changed without relocking: the equivalent of Gradle's dependency locking in strict mode. Hashes protect against tampered artifacts. PEP 751's pylock.toml standardises the format across tools (uv can export it).

3.9 Profiling vocabulary

  • Deterministic profilers (cProfile): hook every call; exact counts, high overhead, distorts fast functions. Like an instrumenting Java profiler.
  • Sampling profilers (py-spy, Scalene, Austin, the 3.15 stdlib sampler): read the interpreter's stacks periodically from outside or via signals; low overhead, safe in production. Like async-profiler and JFR.
  • Memory profilers: tracemalloc (stdlib, snapshots and diffs), memray (Bloomberg; native and Python allocations, flame graphs), Scalene (CPU plus memory per line).
  • Native vs Python time: py-spy --native and Scalene separate time in C extensions from interpreter time, which tells you whether optimising Python code can help at all.

3.10 Performance levers, in order

  1. Do less: algorithms, data structures, avoid repeated work (caching).
  2. Do it in bulk in native code: vectorise with NumPy/Polars/Arrow; push work into the database.
  3. Do it concurrently where it waits: asyncio, threads for I/O.
  4. Do it in parallel where it computes: processes, or native code that releases the GIL.
  5. Compile the hot spot: Cython, mypyc, or Rust via PyO3/maturin.
  6. Change the runtime: PyPy, free-threaded CPython, or move the component to Go/Java.

3.11 Process models for serving

Uvicorn runs one event loop per process; uvicorn --workers N starts a supervisor with N worker processes. Gunicorn is a mature pre-fork process manager (worker restarts, graceful reloads, max_requests) and can host Uvicorn workers (via the uvicorn-worker package). In Kubernetes many teams run a single Uvicorn process per container and scale with replicas, letting the orchestrator be the process manager; others prefer several workers per pod to share memory and reduce per-pod overhead. Both are valid; be deliberate.

3.12 Integration styles with the JVM

  • Separate service over the network (REST/JSON, gRPC/protobuf): the default. Clear ownership, independent scaling and deployment, polyglot-friendly.
  • Asynchronous events (Kafka with Avro/Protobuf/JSON Schema in a schema registry): for decoupled workflows and fan-out.
  • Durable workflows (Temporal with Java workflows calling Python activities).
  • In-process embedding: Jython (Python 2.7 only, effectively obsolete for modern libraries), GraalPy (Python 3 on GraalVM, can run many pure-Python packages and some native ones, embeddable via the polyglot API), JEP (embeds CPython via JNI). Niche: plugin/scripting use-cases, not ML serving.

4. Internal Working

4.1 How pytest runs a test

  1. Collection: pytest imports test modules (with its assertion-rewriting import hook, which rewrites the AST of assert statements into code that records sub-expression values) and builds a tree of nodes (session, packages, modules, classes, functions). Parametrisation expands one function into several items.
  2. Fixture resolution: for each item, pytest computes the transitive closure of requested fixtures, ordered by scope (session first). A fixture instance is cached for its scope; teardown runs in reverse order when the scope ends.
  3. Execution: hooks (pytest_runtest_setup/call/teardown) run; plugins such as pytest-asyncio wrap coroutine tests by running them on an event loop with the configured loop scope.
  4. Reporting: failures display rewritten assertion details; xdist workers send reports to the controller process.

Because fixtures are cached by scope, an expensive session fixture (a PostgreSQL container) is started once, while a function-scoped fixture (a transaction rolled back after each test) isolates tests. This is the same idea as Spring's test-context cache combined with @Transactional test rollback.

4.2 How uv resolves and installs

  1. Reads pyproject.toml (and workspace members), the requires-python range and dependency groups.
  2. Resolves with a PubGrub-based solver (the same algorithm family as Dart's pub and Cargo-like resolvers), fetching only metadata where possible (PEP 658 metadata files on PyPI avoid downloading whole wheels), and produces a universal resolution with environment markers so that one lock covers all platforms and Python versions in range.
  3. Writes uv.lock with exact versions, sources and hashes.
  4. uv sync creates .venv (downloading a managed Python build if needed), computes the install plan for the current platform from the lock, fetches wheels into a global content-addressed cache and installs by hard-linking or copy-on-write cloning from the cache: why repeat installs take milliseconds to seconds.

Maven's model is different: the dependency tree is resolved at build time with "nearest wins" mediation and each application ships its own classpath; conflicts are resolved silently. Python's single-version-per-environment rule plus a real SAT-style resolver means conflicts are errors, not surprises at runtime.

4.3 How a sampling profiler reads a running Python process

py-spy is written in Rust and runs as a separate process. It locates the interpreter's global runtime state in the target's memory (using symbols or known offsets per Python version), then periodically reads each thread's frame chain via process_vm_readv (Linux) or equivalent, decoding code objects to function names and line numbers. The target is not paused by default and needs no instrumentation, which is why it is safe in production (it needs SYS_PTRACE capability in containers). Python 3.12+ adds sys.monitoring (PEP 669) for low-overhead in-process tooling, and 3.14 adds a safe external debugger interface (PEP 768), while 3.15 ships a sampling profiler in the stdlib.

4.4 What "vectorisation" really does

A Python loop over a million floats executes millions of bytecodes, each boxing and unboxing PyFloat objects. np.dot(a, b) executes one Python call that dispatches to a compiled BLAS kernel operating on contiguous double arrays with SIMD instructions, often multi-threaded, with the GIL released. The interpreter overhead becomes constant per call instead of per element. The JVM does not need this trick as much because C2 auto-vectorises simple loops (and the Vector API gives explicit SIMD).

4.5 PyO3 and the extension boundary

A Rust function exported with #[pyfunction] is compiled by maturin into a shared library with a C-ABI entry point. Arguments arrive as Python objects and are converted (&str borrows the UTF-8 buffer, Vec<f64> copies); results are converted back. Inside, you can release the GIL with py.detach (named allow_threads in older PyO3 versions) for pure-Rust work, enabling parallelism with Rayon. The conversion cost at the boundary is why you push whole batches across, never one element at a time: the same advice as for JNI or the FFM API.

4.6 What Uvicorn and Gunicorn do with signals

On SIGTERM, Uvicorn stops accepting new connections, waits for in-flight requests (up to --timeout-graceful-shutdown), sends the ASGI lifespan shutdown event (your lifespan's code after yield runs: dispose engines, flush telemetry), and exits. Gunicorn's master forwards SIGTERM to workers and waits up to graceful_timeout, then SIGKILLs. Kubernetes sends SIGTERM to PID 1 after removing the pod from endpoints (asynchronously, so a short preStop sleep avoids routing new requests to a terminating pod). If your entrypoint is a shell script that does not exec the server, SIGTERM never reaches it: the container is SIGKILLed after the grace period.

4.7 OpenTelemetry context propagation in Python

The OTel Python SDK stores the active span in a contextvars.ContextVar. Server instrumentation (ASGI/FastAPI) extracts the W3C traceparent header and starts a server span; client instrumentation (httpx, grpcio, confluent-kafka wrappers) injects the current context into outgoing headers. Because asyncio tasks copy the context when created, spans flow into child tasks automatically. Threads do not inherit context automatically, so run_in_executor callers must copy it (contextvars.copy_context().run; asyncio.to_thread does this for you). A Spring Boot service with Micrometer Tracing (OTel bridge) emits the same W3C headers, so traces connect across languages without extra work.

4.8 gRPC in Python

grpcio wraps the C-core gRPC implementation; grpc.aio exposes an asyncio API. grpcio-tools runs protoc with the Python plugin to generate message classes (*_pb2.py) and service stubs (*_pb2_grpc.py). Deadlines arrive as context.time_remaining(); cancellation from the client cancels the server-side coroutine. Java's gRPC stubs generated from the same .proto interoperate byte-for-byte, which makes protobuf the strongest cross-language contract available.

5. Architecture

Reading the diagram: three integration styles, each for a reason. Uploads are REST because they are coarse-grained, browser- and gateway-friendly. Search is gRPC because it is a low-latency, high-volume, strongly typed internal call from the Java assistant service, with deadlines. Completion notifications are Kafka events because several Java consumers react independently and may need replay. All components export OTLP to one collector, so a trace from the Java assistant through docflow's gRPC server into PostgreSQL is one trace.

Reading the diagram: the dependency layer only rebuilds when uv.lock changes, the same caching strategy as Jib's separate dependency and class layers. The runtime stage contains no compilers, no uv cache and no build tools, reducing size and attack surface.

Reading the diagram: the Java client sets a deadline; gRPC transmits it as the grpc-timeout header; the Python server reads the remaining time and derives the database statement timeout from it, so work stops when nobody is waiting anymore. This end-to-end deadline propagation is the cross-language equivalent of passing a Go context.Context down the call chain.

Reading the diagram: the separate-service path wins almost always. Embedding is reserved for scripting-style use where pure-Python code is small and isolation from native-library chaos is acceptable. Jython does not appear: it is Python 2.7, which cannot run any modern library.

6. The Math: Worker Sizing, Profiling Statistics and Benchmarks

6.1 Workers, memory and CPU

Per pod: \( W = \min\left(\left\lfloor \frac{C_{pod}}{c_{w}} \right\rfloor, \left\lfloor \frac{M_{pod} - M_{base}}{m_{w}} \right\rfloor\right) \), where \( C_{pod} \) is the CPU limit, \( c_w \) the CPU one busy worker uses (about 1 core), \( M_{pod} \) the memory limit, \( M_{base} \) shared overhead, and \( m_w \) private memory per worker. For an ML-heavy service where each worker loads a 1.2 GB model: a 4 CPU / 6 GB pod gives \( \min(4, \lfloor (6 - 0.3)/1.4 \rfloor) = \min(4, 4) = 4 \). If the model is loaded before fork and shared copy-on-write (and not touched), \( m_w \) shrinks and more workers fit; this is the economic reason for preload_app and gc.freeze().

6.2 Sampling profiler accuracy

With sampling interval \( \Delta \) over a duration \( T \), you collect \( n = T/\Delta \) samples. A function that truly accounts for fraction \( p \) of time appears in \( \hat{p} = k/n \) samples with standard error \( \sqrt{p(1-p)/n} \). At 100 Hz for 30 s, \( n = 3000 \); for \( p = 0.05 \) the standard error is about 0.4 percentage points: plenty for finding hotspots, useless for comparing two variants differing by 1%. For that, use benchmarks.

6.3 Benchmark statistics

Like JMH, Python's pyperf runs multiple processes, warm-ups and many loops, reporting mean and standard deviation. Treat a difference as real only if confidence intervals do not overlap and the effect is larger than run-to-run noise. The speed-up of an optimisation applied to a fraction \( f \) of runtime with local speed-up \( s \) is bounded by Amdahl: \( S = 1 / ((1 - f) + f/s) \). Rewriting a function that takes 20% of request time in Rust with a 50x local speed-up yields \( 1/(0.8 + 0.004) \approx 1.24 \)x overall. Profile first; the arithmetic often says "do not bother".

6.4 Cache effectiveness

Expected latency with a cache: \( E[L] = h \cdot L_{hit} + (1 - h) \cdot (L_{miss} + L_{hit}) \). For embedding lookups with \( L_{hit} = 1 \) ms (Redis), \( L_{miss} = 120 \) ms (API) and hit ratio \( h = 0.6 \): \( 0.6 + 0.4 \times 121 = 49 \) ms, and 60% fewer paid API calls. Cache keys must include the model name and version, or a model upgrade silently mixes vector spaces.

# python perf_demo.py ; then: py-spy record -o flame.svg -- python perf_demo.py
import cProfile
import pstats
import time
from functools import lru_cache

import numpy as np

def cosine_top_k_python(q: list[float], docs: list[list[float]], k: int) -> list[int]:
    def cos(a: list[float], b: list[float]) -> float:
        dot = sum(x * y for x, y in zip(a, b))
        na = sum(x * x for x in a) ** 0.5
        nb = sum(y * y for y in b) ** 0.5
        return dot / (na * nb)
    scores = [(cos(q, d), i) for i, d in enumerate(docs)]
    return [i for _, i in sorted(scores, reverse=True)[:k]]

def cosine_top_k_numpy(q: np.ndarray, docs: np.ndarray, k: int) -> np.ndarray:
    docs_n = docs / np.linalg.norm(docs, axis=1, keepdims=True)    # normalise once in real code
    scores = docs_n @ (q / np.linalg.norm(q))                       # one BLAS call, GIL released
    idx = np.argpartition(-scores, k)[:k]                           # O(n) selection, not a full sort
    return idx[np.argsort(-scores[idx])]

@lru_cache(maxsize=10_000)                                          # memoise pure, hashable inputs
def normalise_query(text: str) -> str:
    return " ".join(text.lower().split())

if __name__ == "__main__":
    rng = np.random.default_rng(0)
    docs = rng.standard_normal((20_000, 384)).astype(np.float32)
    q = rng.standard_normal(384).astype(np.float32)

    t0 = time.perf_counter(); cosine_top_k_numpy(q, docs, 8)
    print(f"numpy : {(time.perf_counter() - t0) * 1000:7.1f} ms")

    small = docs[:2000].tolist(); ql = q.tolist()
    with cProfile.Profile() as prof:
        t0 = time.perf_counter(); cosine_top_k_python(ql, small, 8)
        print(f"python: {(time.perf_counter() - t0) * 1000:7.1f} ms  (10x fewer docs!)")
    pstats.Stats(prof).sort_stats("cumulative").print_stats(5)

import asyncio
import logging
import signal
import uuid

import grpc

from docflow.models import Chunk, Document
from docflow.settings import get_settings
from docflow.telemetry import setup_telemetry
from docflow.v1 import docflow_pb2 as pb
from docflow.v1 import docflow_pb2_grpc as pb_grpc

log = logging.getLogger("docflow.grpc")

class DocflowService(pb_grpc.DocflowServiceServicer):
    def __init__(self, sessionmaker) -> None:
        self.sm = sessionmaker

    async def Search(self, request: pb.SearchRequest, context: grpc.aio.ServicerContext) -> pb.SearchResponse:
        if not request.tenant_id or len(request.query_embedding) != get_settings().embedding_dim:
            await context.abort(grpc.StatusCode.INVALID_ARGUMENT, "tenant_id and a 384-d embedding required")
        k = min(request.k or 8, 50)
        remaining = context.time_remaining()                     # seconds or None
        timeout_ms = int(max(0.05, (remaining or 2.0) - 0.05) * 1000)
        distance = Chunk.embedding.cosine_distance(list(request.query_embedding))
        stmt = (select(Chunk.document_id, Chunk.ordinal, Chunk.content, distance.label("d"))
                .join(Document, Document.id == Chunk.document_id)
                .where(Document.tenant_id == request.tenant_id, Chunk.embedding.is_not(None))
                .order_by(distance).limit(k))
        async with self.sm() as s, s.begin():
            await s.execute(text(f"SET LOCAL statement_timeout = {timeout_ms}"))   # deadline -> DB
            rows = (await s.execute(stmt)).all()
        return pb.SearchResponse(hits=[pb.SearchHit(document_id=str(r.document_id), ordinal=r.ordinal,
                                                    content=r.content, score=1.0 - float(r.d)) for r in rows])

    async def GetDocument(self, request: pb.GetDocumentRequest, context: grpc.aio.ServicerContext) -> pb.Document:
        try:
            doc_id = uuid.UUID(request.document_id)
        except ValueError:
            await context.abort(grpc.StatusCode.INVALID_ARGUMENT, "bad document_id")
        async with self.sm() as s:
            doc = await s.scalar(select(Document).where(Document.id == doc_id,
                                                        Document.tenant_id == request.tenant_id))
        if doc is None:
            await context.abort(grpc.StatusCode.NOT_FOUND, "document not found")
        return pb.Document(id=str(doc.id), filename=doc.filename, status=doc.status.value,
                           version=doc.version, chunk_count=doc.chunk_count)

    settings = get_settings()
    setup_telemetry("grpc")
    engine = make_async_engine(settings.database_url, settings.db_pool_size)
    server = grpc.aio.server(options=[("grpc.max_receive_message_length", 4 * 1024 * 1024)])

    await server.stop(grace=15)                 # finish in-flight RPCs, reject new ones
    await engine.dispose()

    asyncio.run(serve())

7.11 docflow Kafka publisher (used by the outbox relay)

import json
from collections.abc import Callable

from confluent_kafka import KafkaException, Producer

from docflow.models import OutboxMessage

def kafka_publisher(bootstrap: str) -> Callable[[OutboxMessage], None]:
    producer = Producer({
        "bootstrap.servers": bootstrap,
        "enable.idempotence": True,          # no duplicates from producer retries, ordered per partition
        "acks": "all",
        "compression.type": "zstd",
        "linger.ms": 5,
    })

    def publish(msg: OutboxMessage) -> None:
        errors: list[Exception] = []
        def on_delivery(err, _m) -> None:
            if err is not None:
                errors.append(KafkaException(err))
        producer.produce("document.ingested", key=msg.key.encode(),
                         value=json.dumps({"schema": "docflow.document.ingested.v1", **msg.payload}).encode(),
                         headers=[("content-type", b"application/json")], on_delivery=on_delivery)
        producer.flush(10)                   # synchronous per outbox row: simple and safe
        if errors:
            raise errors[0]                  # relay transaction rolls back; retried next poll
    return publish

Keyed by document ID, so all events for one document land in one partition in order. For higher throughput, flush once per relay batch instead of per row. Many organisations use a schema registry with Avro or Protobuf instead of JSON; confluent-kafka's serializers support both, and Spring Kafka consumes them with the matching Confluent deserializers.

Each client mirrors an idea from the Python side: the REST client tolerates the idempotent 200/202 contract; the gRPC client sets a deadline that Python honours down to PostgreSQL; the Kafka listener is idempotent because the outbox relay is at-least-once. Contracts and failure semantics, not languages, are what make polyglot systems reliable.

7.13 Why not embed Python in the JVM?

// org.graalvm.polyglot:polyglot + org.graalvm.polyglot:python (GraalPy). Works for pure-Python logic.
import org.graalvm.polyglot.*;

public class GraalPyDemo {
    public static void main(String[] args) {
        try (Context ctx = Context.newBuilder("python").allowAllAccess(false).build()) {
            Value fn = ctx.eval("python", "lambda text: ' '.join(text.lower().split())");
            System.out.println(fn.execute("  Hello   GraalPy ").asString());
        }
    }
}

This is fine for small, pure-Python rules or user scripts in a sandbox. It is the wrong tool for docflow-style services: native-extension compatibility (PyTorch, many wheels) is limited or slower, you inherit two runtimes' memory and debugging complexity in one process, and you lose independent scaling and deployment. Jython is not an option for modern code because it implements Python 2.7. Opinion Default to separate services; consider GraalPy only for embedded scripting.

8. Applications

8.1 Python as the AI tier of a JVM company

The most common shape in 2026: Java/Kotlin services own transactional domains; Python services own model inference, retrieval, document processing, evaluation and agent orchestration; contracts are gRPC/OpenAPI plus Kafka events; one observability stack spans both. docflow is a template for that tier.

8.2 Internal Python platform teams

Larger organisations create a "Python platform" team that maintains base images, a cookiecutter or copier template (pyproject, ruff, pyright, pytest, Dockerfile, OTel), an internal package index or proxy, and shared libraries (auth middleware, telemetry setup). Netflix has publicly discussed a central Python team providing shared tooling (Talk Python episode 421, 2023).

8.3 Batch and pipeline jobs

The same packaging and image practices apply to Airflow/Dagster tasks, Kubernetes Jobs for re-embedding, and evaluation runs in CI: one lockfile, one image, deterministic runs.

8.4 Performance-critical libraries in Rust

When a Python hotspot is unavoidable (tokenisation, parsing, validation), teams write a small Rust extension with PyO3 rather than rewriting the service. The ecosystem's best-known libraries (Pydantic-core, Polars, tokenizers, orjson) prove the pattern.

12. Common Mistakes

  1. Unpinned dependencies (pip install fastapi in a Dockerfile): every build is different. Use a lockfile and --frozen.
  2. Building sdists in the runtime image, pulling compilers into production. Build in a builder stage; install wheels only.
  3. Shell-form ENTRYPOINT without exec: SIGTERM never reaches Python; pods are SIGKILLed and in-flight requests drop.
  4. Running as root and writing to the image filesystem.
  5. patch() on the wrong import path, producing tests that pass while production fails.
  6. Session-scoped async fixtures with mismatched event loop scopes (pytest-asyncio): "attached to a different loop" errors. Configure loop scopes explicitly (see pyproject).
  7. Optimising without profiling, or profiling with cProfile in production (overhead). Use py-spy.
  8. Too many workers for the CPU limit, causing CPU throttling and latency spikes; or too few for I/O-heavy sync endpoints.
  9. Java and Python disagreeing on JSON naming (camelCase vs snake_case), nullability or date formats. Generate clients from the contract and configure Jackson accordingly.
  10. No deadline propagation: Java times out at 800 ms, Python keeps searching for 5 s, wasting DB capacity during incidents.
  11. Pickle across services (Celery with pickle, caching pickled objects shared with other services): remote code execution risk and version coupling.

13. Production Checklist

13.1 Build and supply chain

  • Lockfile with hashes; uv sync --frozen; private index proxy (Artifactory/Nexus support PyPI) like your Maven proxy.
  • Vulnerability scanning: pip-audit or the scanner of your image registry; SBOM generation (CycloneDX for Python exists).
  • Reproducible images: pinned base image digests, multi-stage builds, non-root user, read-only root filesystem where possible.

13.2 Runtime

  • Workers sized from §6.1; CPU limits that match; memory limits with headroom for fragmentation; periodic worker recycling for Gunicorn/Celery.
  • Probes: liveness cheap, readiness checks dependencies, startup probe for slow model loading.
  • Graceful shutdown: exec-form entrypoint, preStop sleep, grace periods longer than in-flight work.
  • Configuration via environment and mounted secrets into BaseSettings; fail fast on invalid config.

13.3 Observability

  • Traces: OTel server/client spans, Celery and Kafka propagation, consistent service.name.
  • Metrics: RED metrics per route, event-loop lag, queue depth and age, DB pool usage, GC collections.
  • Logs: structured JSON with trace and span IDs; no PII or document content at INFO.
  • Profiling: py-spy available in debug images or as an ephemeral container (kubectl debug with SYS_PTRACE); continuous profiling (Pyroscope/Grafana, Datadog) where available.

13.4 Security

  • mTLS between services (mesh) or TLS on gRPC; JWT verification on REST.
  • Input limits at the proxy and in models; tenant scoping in every query.
  • Dependency hygiene: avoid typosquatting by using an allow-listed internal index.

Write a pytest fixture that yields an httpx.AsyncClient against a FastAPI app with an overridden settings dependency and verify that it runs the lifespan.

import pytest

from docflow.api.app import create_app

@pytest.fixture

Exercise 2 · Intermediate

Your Docker build takes 6 minutes on every source change. Diagnose with the Dockerfile in §7.4 as the target.

Solution

Likely causes: copying the whole source before installing dependencies (cache busted on every change), no BuildKit cache mount for the uv/pip cache, building sdists (compilers) because wheels are unavailable for the base image's platform (e.g. musl/Alpine), or downloading Python. Fix: dependency layer from pyproject.toml + uv.lock only, cache mounts, glibc-based slim image so manylinux wheels apply, UV_PYTHON_DOWNLOADS=never with a Python base image.

Exercise 3 · Advanced

A FastAPI pod with 4 workers and a 2-CPU limit has good average latency but terrible p99 under load. CPU throttling metrics are high. Explain and fix.

Solution

Four busy single-threaded processes can consume 4 CPUs worth of time per CFS period; the 2-CPU quota is exhausted early in each 100 ms period and all processes are throttled for the rest, adding up to tens of ms to unlucky requests. Fix: match workers to the CPU limit (2), or raise the limit, or remove CPU limits and rely on requests (a common Kubernetes practice for latency-sensitive services); verify with container_cpu_cfs_throttled_periods_total.

Exercise 4 · Advanced

Add a server-side gRPC interceptor to docflow that rejects calls without an authorization metadata entry and records a latency histogram per method.

Solution
import time
import grpc
from prometheus_client import Histogram

RPC_LATENCY = Histogram("docflow_grpc_seconds", "gRPC latency", ["method", "code"])

class AuthAndMetrics(grpc.aio.ServerInterceptor):
    async def intercept_service(self, continuation, details: grpc.HandlerCallDetails):
        md = dict(details.invocation_metadata or ())
        handler = await continuation(details)
        if "authorization" not in md:
            async def deny(request, context):
                await context.abort(grpc.StatusCode.UNAUTHENTICATED, "missing credentials")
            return grpc.unary_unary_rpc_method_handler(deny)
        inner = handler.unary_unary
        async def timed(request, context):
            t0, code = time.perf_counter(), "OK"
            try:
                return await inner(request, context)
            except Exception:
                code = "ERROR"; raise
            finally:
                RPC_LATENCY.labels(details.method, code).observe(time.perf_counter() - t0)
        return grpc.unary_unary_rpc_method_handler(
            timed, request_deserializer=handler.request_deserializer,
            response_serializer=handler.response_serializer)

# server = grpc.aio.server(interceptors=[AuthAndMetrics()])

Real code verifies the token (JWT/JWKS) rather than checking presence, and handles streaming handlers too. The Java equivalent is a ServerInterceptor; Chapter 5.3 shows Go's.

Exercise 5 · Expert

Design the migration of docflow's event payload from JSON to Protobuf with a schema registry without breaking the Java consumers.

Solution

Define DocumentIngested in the contracts repo; register it with BACKWARD compatibility. Phase 1: relay dual-publishes to a new topic document.ingested.v2 (Protobuf, Confluent wire format) while keeping v1 JSON. Phase 2: Java consumers migrate to v2 with the Protobuf deserializer, verified by consumer-group lag on v1 dropping to idle. Phase 3: stop publishing v1 after all consumer groups have moved, then delete the topic after retention. Alternatively use a single topic with a header-based content type, but separate topics make the cut-over observable and reversible.

15. Interview Questions

Conceptual What is the difference between pyproject.toml dependencies and a lockfile?

The former declares compatible ranges (abstract requirements, like POM version ranges); the lockfile records the exact resolved transitive graph with hashes for reproducible installs. Libraries publish ranges; applications deploy locks.

Conceptual How do pytest fixtures compare with JUnit 5 extensions?

Both provide setup/teardown and injection. Fixtures are injected by parameter name, compose by depending on other fixtures, have explicit scopes up to session, and use yield for teardown; JUnit uses annotations, lifecycle callbacks and parameter resolvers. Session fixtures play the role of Spring's cached test context.

Conceptual When is a sampling profiler preferable to cProfile?

In production and for realistic workloads: low overhead, no code changes, attaches to running processes, and does not distort timings of small functions. cProfile is useful locally for exact call counts.

Architecture How would you integrate a Python ML service with a Spring Boot system?

Separate service; gRPC for low-latency internal calls with deadlines, REST/OpenAPI for coarse or external calls, Kafka events with a schema registry for async integration; shared identity and mTLS; W3C trace propagation; contract tests and breaking-change checks in CI; idempotent consumers. Avoid in-process embedding.

Architecture How many Uvicorn workers per pod?

Start with one per CPU of limit for CPU-heavy work (fewer if native libraries spawn their own threads), check memory per worker (models), and decide between "few workers per pod" and "one per pod, more replicas" based on memory sharing, per-pod overhead and autoscaling granularity. Measure throttling and latency.

Coding Write a minimal multi-stage Dockerfile for a uv project.

See §7.4: builder with uv copying pyproject.toml and uv.lock first, uv sync --frozen --no-install-project, then the source and a second sync; runtime stage copying .venv, non-root user, exec-form entrypoint.

Scenario p99 latency doubles after upgrading a transitive dependency; nobody changed code. How do you find it?

Diff the lockfiles between releases; bisect by pinning versions; profile both images under the same load with py-spy flame graphs; check changelogs of changed packages (e.g. a JSON library falling back to pure Python because a wheel was missing for the platform). Prevent with locked upgrades in small PRs and performance tests in CI.

Scenario Java calls to the Python gRPC service time out, but Python logs show successful responses a few seconds later. What is wrong?

The server ignores deadlines: it keeps working after the client gave up. Read context.time_remaining(), pass timeouts to downstream calls (DB statement timeout, HTTP timeouts), check for cancellation, and fix the slow path (likely event-loop blocking or pool exhaustion).

Behavioral How did you help a Java-centric team adopt Python safely?

Good answers mention a service template with the toolchain prebuilt, shared contracts, CI gates equivalent to the Java ones, pairing, clear guidance on when to use Python, and production readiness reviews.

What does uv sync --frozen guarantee?

  1. It upgrades all packages to the latest versions
  2. It installs exactly what the lockfile specifies and fails rather than re-resolving
  3. It builds a wheel
  4. It freezes the interpreter
Frozen mode installs from the lock without updating it, like strict dependency locking.

Why use a session-scoped Testcontainers fixture plus per-test cleanup?

  1. Containers cannot be restarted
  2. It is required by pytest
  3. Starting the DB once is fast; cleanup keeps tests isolated
  4. To share data between tests
Same trade-off as Spring's cached context with transactional rollback.

A function taking 10% of request time is made 100x faster in Rust. Overall speed-up?

  1. About 1.11x
  2. About 10x
  3. About 100x
  4. About 2x
Amdahl: 1 / (0.9 + 0.001) is approximately 1.11.

Why should a container use the exec form of ENTRYPOINT?

  1. Smaller image
  2. Faster startup
  3. Required for non-root users
  4. So the server is PID 1 and receives SIGTERM for graceful shutdown
Shell form wraps the process in /bin/sh -c, which does not forward signals.
