Part 2 · Chapter 8

Microservices, Discovery, Circuit Breakers & Distributed Locks

Splitting a system into services trades in-process method calls for network calls, and every network call can be slow, fail, or succeed without telling you. This chapter covers when the split is worth it (and when a Spring Modulith monolith is the better answer), how services find each other, and the resilience toolkit that stops one slow dependency from taking down everything: timeouts, retries with jitter and budgets, circuit breakers, bulkheads, load shedding and backpressure. It closes with the most misunderstood tool in the box, the distributed lock, and why correctness needs fencing tokens.

  • Prerequisites: Chapter 2 (load balancers, gateways), Chapter 6 (sagas, idempotency, consensus), Chapter 7 (event-driven integration).
  • You will be able to: decide between a modular monolith and microservices; draw service boundaries from bounded contexts; pick sync or async integration per interaction; version APIs; compare client-side, server-side and Kubernetes discovery and decide whether you need a mesh; configure Resilience4j correctly (and explain its sliding windows and states); compute timeouts and retry budgets; design load shedding and backpressure; and implement distributed locks that remain correct under GC pauses using fencing tokens.

1. Introduction: The Network Is Now Part of Your Call Stack

In a Spring Boot monolith, orderService.place() calling inventoryService.reserve() is a method call: nanoseconds, never "partially" executed, and inside the same @Transactional. Move InventoryService into its own deployable and the same line becomes an HTTP or gRPC call that can take 2 ms or 30 s, can fail with a connection reset after the inventory was reserved, and can be retried by three layers (your code, the HTTP client, the service mesh) at once. Peter Deutsch's "fallacies of distributed computing" (the network is reliable, latency is zero, bandwidth is infinite, and so on) are the checklist of assumptions that silently break.

Microservices are therefore an organisational scaling technique that you pay for with distributed-systems complexity. The payoff is independent deployment, team autonomy, independent scaling and technology heterogeneity. The price is everything in this chapter and in Chapters 6, 7 and 9. A good engineer can argue both sides and choose deliberately.

AI-era systems make the resilience half of this chapter more pressing, not less. An LLM provider call has p99 latencies of many seconds, rate limits measured in tokens per minute, and periodic regional outages. Agentic systems fan out to tools and other models. A gateway that does not apply timeouts, bounded retries with jitter, circuit breakers and load shedding to model calls will melt down at the first provider incident, and an agent that "locks" a resource with a naive Redis lock will eventually double-execute an action.

Bridging from Java & Spring Boot

What you already know
Spring Cloud (Eureka, Spring Cloud LoadBalancer, OpenFeign, Spring Cloud Gateway, Config Server), perhaps Hystrix in older systems, Resilience4j annotations (@CircuitBreaker, @Retry, @Bulkhead), RestTemplate/RestClient/WebClient, and @Scheduled jobs that must run on only one instance.
Why that is not enough
Annotations do not tell you what values to use. Wrong timeouts (or none), retries without jitter or budgets, a circuit breaker whose sliding window never fills, or a Redis lock without fencing cause the outages these tools were meant to prevent. Many teams also split services along technical layers or entities instead of bounded contexts, producing a distributed monolith with all the costs and none of the benefits.
The modern approach
Start modular (Spring Modulith) and extract services when there is a clear organisational or scaling reason; align services with bounded contexts and give each its own data; prefer async events for cross-context propagation; rely on platform discovery (Kubernetes Services, optionally a mesh for mTLS and traffic policy); apply a layered resilience policy (deadline propagation, timeouts, budgeted retries with jitter, circuit breakers, bulkheads, shedding); and use locks only for efficiency, with fencing or idempotency for correctness.
Where Python and Go fit
Go is popular for gateways, sidecars and high-concurrency edge services (Envoy is C++, but Linkerd's control plane, Consul and etcd are Go); context.Context deadlines are the idiomatic deadline propagation. Python ML services (FastAPI) need the same timeouts and limits, typically via httpx timeouts, tenacity retries and semaphores.
In production
Kubernetes Services and DNS for discovery, an ingress or API gateway at the edge, optionally Istio or Linkerd for mTLS, retries and traffic shifting; Resilience4j (or Spring Framework 7's built-in @Retryable/@ConcurrencyLimit) in services; dashboards for circuit-breaker state, rejection counts and saturation; ShedLock or Kubernetes leases for singleton jobs.
Use it when / avoid it when
Use microservices when several teams need independent release cadences, components have very different scaling or reliability needs, or regulatory isolation is required. Avoid them for a small team, an unclear domain, or a product still searching for fit: a modular monolith gives most of the structure at a fraction of the cost.

3. Fundamentals

3.1 Microservices versus the modular monolith

A microservice is independently deployable, owns its data, and is owned by one team. A modular monolith is a single deployable whose internal modules have enforced boundaries: each module has a public API and hidden internals, modules communicate through those APIs or in-process events, and dependency cycles are forbidden. The modular monolith gives you most of the design benefits (clear ownership, cohesive modules, the option to extract later) without network calls, distributed transactions or polyglot operations.

Spring Modulith makes this concrete for Spring Boot. Each direct sub-package of the application's main package is an application module; types in a module's base package are its API, sub-packages are internal. ApplicationModules.of(App.class).verify() in a test fails the build on illegal dependencies or cycles. @ApplicationModuleListener handles events asynchronously after the publishing transaction commits, and the Event Publication Registry persists those events so that they survive crashes (an in-process outbox); events can be externalised to Kafka, AMQP or SQS. It also generates C4/PlantUML documentation of the module structure and supports module-scoped integration tests (@ApplicationModuleTest).

3.2 Decomposition by bounded context

A bounded context is a boundary within which a domain model and its language are consistent. "Product" means a catalogue item with descriptions and images in the Catalog context, a SKU with quantities and locations in Inventory, and a price list entry in Pricing. Trying to build one shared Product entity for all three produces a giant, constantly contended model. Bounded contexts are the natural service (or module) boundaries because they minimise shared models and chatty cross-boundary calls.

Practical heuristics for finding them: event storming workshops (domain events on a timeline, grouped by the aggregates and actors that produce them); look for language changes (the same word means different things); align with business capabilities and team ownership (Conway's law: systems mirror communication structures, so design teams and boundaries together, the "inverse Conway manoeuvre"); and check transactional needs (data that must change atomically belongs together). Anti-patterns: splitting by technical layer (a "database service"), by entity (a "Customer service" that every flow calls synchronously), or so finely that a single user action requires ten synchronous hops.

Context mapping describes relationships between contexts: customer/supplier, conformist, anti-corruption layer (a translation layer protecting your model from an upstream's model, essential when integrating a legacy system or a third-party API such as an LLM provider), shared kernel, and published language (a well-documented event schema).

3.3 Data ownership

The rule is database per service: a service's tables are private, accessible only through its API or events. Shared databases create invisible coupling: a schema migration in one service breaks another, and locks in one service's queries slow another. Physical separation can be a separate schema on a shared cluster with distinct credentials (cheap) or a separate cluster (strong isolation). When another service needs your data, give it (1) a query API, (2) events so it can maintain a local projection (ECST, Chapter 7), or (3) a CDC feed. Reporting across services uses a separate analytical store fed by events or CDC, not cross-database joins.

The availability point deserves numbers: if a request synchronously traverses five services each at 99.9%, the chain is at most \( 0.999^5 \approx 99.5\% \). Long synchronous chains are an anti-pattern; aim for a user request to touch one or two services synchronously, with the rest fed by events. gRPC (HTTP/2, Protobuf, streaming, deadlines built in) is preferable to REST for internal high-volume calls; REST/JSON remains standard at public edges.

3.5 API versioning

Independent deployment requires that a service can change without breaking callers. Strategies:

  • Prefer additive, backward-compatible change: add optional fields, never remove or repurpose; follow the tolerant reader principle on the consumer side (ignore unknown fields, which Jackson does if FAIL_ON_UNKNOWN_PROPERTIES is disabled; Spring Boot disables it by default).
  • Version when you must break: URI path (/v2/orders, explicit and cache-friendly), header (API-Version: 2), media type (Accept: application/vnd.example.order.v2+json), or query parameter. Spring Framework 7 added first-class API versioning: configure a strategy once (path, header, query or media-type parameter) and declare version on request mappings; RestClient/WebClient can send versions too.   • Deprecate deliberately: Deprecation and Sunset response headers (RFC 9745 and RFC 8594), usage metrics per version, and a published removal date.
  • Consumer-driven contract tests (Spring Cloud Contract, Pact) verify in the provider's CI that changes do not break known consumers.
  • For gRPC/Protobuf, compatibility is by field numbers; never reuse or renumber.

3.6 Service discovery

Instances come and go (autoscaling, deploys, failures), so callers need a dynamic way to find healthy endpoints.

  • Client-side discovery (Eureka + Spring Cloud LoadBalancer): instances register with a registry and renew a lease by heartbeat; clients fetch and cache the registry and choose an instance themselves (round-robin, or zone-preference). Pros: no extra hop, smart client-side balancing. Cons: every language needs a client library; stale caches during churn. Eureka is AP by design: during network problems it enters self-preservation and stops expiring instances, preferring stale entries over an empty registry.
  • Server-side discovery: clients call a stable address (a load balancer or router), which knows the healthy backends: AWS ALB target groups, an API gateway, or a Kubernetes Service. Pros: language-agnostic, simple clients. Cons: extra hop (unless done in the kernel), the balancer must be highly available.
  • Kubernetes Services and DNS: a Service selects pods by labels; the EndpointSlice controller tracks ready pod IPs (readiness probes decide readiness); kube-proxy programs iptables, IPVS or nftables rules (or an eBPF dataplane such as Cilium does it) so the Service's virtual ClusterIP load-balances to pods at connection level. CoreDNS resolves orders.shop.svc.cluster.local to the ClusterIP. A headless Service (clusterIP: None) returns pod IPs directly, used by StatefulSets and client-side balancing (e.g., gRPC). Note that connection-level balancing does not spread requests over long-lived HTTP/2 connections, which is a main reason meshes and gRPC client-side balancing exist.
  • Consul: a Raft-backed service catalog with health checks, a DNS interface, key-value configuration and its own service mesh (Consul Connect). Common in multi-platform estates (VMs plus Kubernetes).

3.7 Service mesh basics

A service mesh moves network concerns (mTLS, retries, timeouts, load balancing, traffic shifting, telemetry) from application libraries into infrastructure. A data plane of proxies intercepts traffic; a control plane configures them.

  • Istio: Envoy-based. In sidecar mode, an Envoy proxy runs in every pod; in ambient mode (GA since Istio 1.24), a per-node ztunnel provides L4 mTLS and optional per-namespace waypoint Envoy proxies handle L7 policy, avoiding per-pod sidecar overhead. Configured with VirtualService, DestinationRule (outlier detection is Istio's circuit breaking), PeerAuthentication, AuthorizationPolicy, and increasingly the Kubernetes Gateway API.
  • Linkerd: a lightweight mesh with a purpose-built Rust micro-proxy; emphasises simplicity, automatic mTLS and latency-aware (EWMA) load balancing.

What a mesh gives you: uniform mTLS and identity (SPIFFE IDs) between services, golden metrics per edge without code changes, canary and traffic splitting, request-level load balancing for HTTP/2 and gRPC. What it costs: added latency per hop (typically sub-millisecond to a few milliseconds), resource overhead, a complex control plane to upgrade, and a new failure domain. And the danger: mesh-level retries multiply with application-level retries unless coordinated. Opinion Adopt a mesh when you need mTLS everywhere or fine-grained traffic management across many services; for a dozen services, Kubernetes Services plus in-app resilience is often enough.

3.8 Timeouts

A call without a timeout can hang forever, holding a thread, a connection and memory. There are several distinct timeouts: connect timeout (TCP/TLS establishment, short: 100s of ms within a data centre), read/response timeout (time to first byte or whole response), pool acquisition timeout (waiting for a free connection), and the overall deadline for the user request. Set per-call timeouts from the dependency's measured latency (e.g., slightly above its p99.9), not from guesswork, and make sure the sum along a call chain fits the caller's own deadline. Deadline propagation passes the remaining time budget downstream (gRPC does it natively; with HTTP you pass a header) so that downstream services do not keep working on requests whose callers have already given up.

3.9 Retries, exponential backoff and jitter

Retries convert transient failures into successes, but they also multiply load exactly when a dependency is struggling. Rules:

  • Retry only idempotent operations, or non-idempotent ones carrying an idempotency key (Chapter 6).
  • Retry only transient errors: connection failures, 503, 429 (honouring Retry-After), timeouts; never 400, 401, 404 or validation errors.
  • Use exponential backoff: wait \( b \cdot 2^{n} \) after attempt \( n \), capped. Without randomisation, all clients that failed together retry together, producing synchronised waves.
  • Add jitter. "Full jitter" (sleep a uniform random time between 0 and the exponential value) spreads retries most evenly and in AWS's simulations minimised total work; "equal jitter" keeps half the backoff fixed; "decorrelated jitter" bases each sleep on the previous one.
  • Retry at one layer. If the mesh, the HTTP client, the service code and the caller's caller each retry 3 times, a single failure at depth 4 can produce \( 4^4 = 256 \) attempts.

3.10 Retry budgets

A retry budget caps retries as a fraction of normal traffic, so that retries can never amplify an outage by more than a fixed factor. Google's SRE book describes a per-request cap (e.g., at most 3 attempts) combined with a per-client budget where retries must stay below about 10% of requests; Finagle and Linkerd implement budgets as token buckets that earn a fraction of a token per successful request and spend one per retry. When the budget is empty, fail fast. Budgets protect a recovering service from a retry storm, which per-request retry limits alone do not.

3.11 Circuit breakers

A circuit breaker wraps calls to a dependency and tracks outcomes. While the failure rate (or slow-call rate) is below a threshold, it is CLOSED and calls pass. When the threshold is exceeded over a sliding window, it trips OPEN: calls fail immediately (or go to a fallback) without touching the dependency, which frees the caller's threads and gives the dependency room to recover. After a wait duration it becomes HALF_OPEN and lets a limited number of trial calls through; if they succeed it closes, otherwise it reopens. The breaker turns slow failure into fast failure, the key to stopping cascades.

3.12 Bulkheads

Named after a ship's watertight compartments: isolate resources per dependency (or per tenant, or per request class) so that one saturated dependency cannot consume every thread or connection. Implementations: separate thread pools, semaphores (concurrency limits), separate connection pools, and at the infrastructure level separate deployments or cells. With Java 21 virtual threads, threads are no longer the scarce resource, so bulkheads become concurrency limits (semaphores) protecting the downstream rather than thread pools protecting the caller.

3.13 Fallbacks

When a call fails or a breaker is open, a fallback can return a cached value, a default (empty recommendations), a degraded response (static content), or queue the work for later. Fallbacks must be cheap, local and well tested; a fallback that calls another remote service just moves the failure. Some operations must not fall back (charging a card): fail clearly instead.

3.14 Load shedding

A server under overload should reject excess work early and cheaply (HTTP 503 or 429) rather than accept everything and serve everyone slowly, which leads to timeouts and wasted work (it completes requests whose clients already gave up). Techniques: concurrency limits (reject when in-flight requests exceed a limit), queue-length or queue-time limits (drop requests that waited longer than their deadline), priority-based shedding (protect checkout, shed recommendations), and adaptive limits based on latency (Netflix's concurrency-limits library adapts the limit using TCP-congestion-control-like algorithms such as Vegas and gradient). Shedding should happen as early in the stack as possible (gateway, then service ingress).

3.15 Backpressure

Backpressure is the mechanism by which a slow consumer tells a fast producer to slow down, rather than buffering unboundedly. Examples: TCP flow control, HTTP/2 stream windows, Reactive Streams request(n) in Project Reactor, bounded queues that block or reject producers, Kafka consumers that pull at their own pace (the log is the buffer), and 429 responses with Retry-After. Unbounded queues are latent outages: they convert overload into memory exhaustion and unbounded latency.

3.16 Distributed locks

A distributed lock gives one process at a time the right to do something across a cluster: run a scheduled job, refresh a cache, process a file. Kleppmann's key distinction: is the lock for efficiency (avoid doing work twice; occasional duplicates are tolerable) or for correctness (duplicates corrupt data)? For efficiency, a simple Redis lock is fine. For correctness, no lease-based lock is enough on its own, because a lock holder can pause (GC, VM migration, network delay) past its lease expiry while still believing it holds the lock. Correctness needs a fencing token: a monotonically increasing number issued with each lock grant, which the protected resource checks, rejecting writes with a token older than one it has already seen.

  • Redis SET key value NX PX ttl: acquire with a unique random value; release with a Lua script that deletes only if the value matches (never plain DEL, which could delete another holder's lock after your lease expired). Single-instance Redis loses the lock on failover if replication was asynchronous.
  • Redlock: acquire the same key on a majority of N (typically 5) independent Redis masters within a time bound, and consider the lock held for the TTL minus elapsed time and clock drift. Kleppmann's critique: it depends on timing assumptions (bounded pauses, clock drift, network delay) that real systems violate, and it does not produce fencing tokens, so it is unsafe for correctness; antirez's reply argued the assumptions are reasonable in practice. The engineering consensus: use Redlock (or a single Redis) only for efficiency locks.
  • ZooKeeper / etcd: consensus-backed. ZooKeeper's recipe uses ephemeral sequential znodes (the lowest sequence holds the lock; the node vanishes when the session expires); the znode's zxid or sequence number serves as a fencing token. etcd uses leases (TTL kept alive by the client) and the key's creation revision as a fencing token; its concurrency package provides mutexes and elections.
  • Database locks: PostgreSQL advisory locks (pg_try_advisory_lock(key) session-level, or pg_advisory_xact_lock released at transaction end), SELECT ... FOR UPDATE on a lock row, or a lock table with a unique key and expiry. If you already have a strongly consistent primary database, it is often the simplest correct choice, and a version column or sequence gives you a fencing token.
  • ShedLock: a library that makes Spring @Scheduled tasks run on at most one node at a time using a lock table (JDBC), Redis, Mongo, ZooKeeper and others, with lockAtMostFor and lockAtLeastFor. It is explicitly an efficiency lock, not a correctness guarantee.
  • Kubernetes Lease objects: leader election for controllers and singleton workloads, backed by etcd.

3.17 Idempotency in service calls

Every retry policy assumes the retried operation is safe to repeat. For synchronous service-to-service calls this means: idempotent HTTP methods used correctly (PUT/DELETE), idempotency keys on POSTs that create or charge, conditional requests (If-Match with ETags for optimistic concurrency), and deterministic request ids propagated through the call chain so that a downstream service can deduplicate. Chapter 6 covered the server-side mechanics in depth; here the rule is simply: do not add a retry policy to a call until you have proven the operation is idempotent.

4. Internal Working

4.1 How a cascading failure unfolds

Understanding the failure mechanism tells you which pattern stops which stage:

  1. A dependency (say, Inventory's database) slows from 20 ms to 2 s.
  2. Callers' threads (or connections, or virtual-thread-held DB connections) now stay busy 100× longer. By Little's law, in-flight requests rise 100× at constant throughput.
  3. The caller's pools saturate; requests queue; its own latency rises for all endpoints, including those that never touch Inventory.
  4. Upstream callers time out and retry, adding load to the already-struggling path.
  5. Health checks time out, the orchestrator restarts "unhealthy" pods, capacity drops further, and the remaining pods receive even more load.

Timeouts bound step 2; bulkheads contain step 3 to the Inventory path; circuit breakers cut step 2 off entirely once failure is evident; retry budgets and jitter prevent step 4 from amplifying; load shedding keeps step 3 from becoming collapse; and separating liveness from readiness probes (Chapter 9) avoids step 5.

4.2 Resilience4j circuit breaker internals

Resilience4j's CircuitBreakerStateMachine holds the current state in an atomic reference and records each call's outcome in a sliding window:

  • Count-based window (slidingWindowType=COUNT_BASED, size N): a circular array of N outcome measurements. Each new outcome overwrites the oldest, and the total aggregation (failed calls, slow calls, total calls, total duration) is updated incrementally by subtracting the evicted measurement and adding the new one. Recording and reading the failure rate are therefore O(1).
  • Time-based window (TIME_BASED, size N seconds): a circular array of N partial aggregations (buckets), one per epoch second. Calls in the same second update the same bucket; when time moves past a bucket's second it is reset before reuse. The total aggregation is maintained incrementally, again O(1) per call, and memory is O(N) regardless of call rate.

Failure and slow-call rates are evaluated only after minimumNumberOfCalls outcomes have been recorded in the window; before that, the breaker cannot trip, which protects low-traffic services from tripping on one failure but also means a breaker with minimumNumberOfCalls=100 on an endpoint receiving 10 calls per minute effectively never trips. When failureRate ≥ failureRateThreshold or slowCallRate ≥ slowCallRateThreshold (a call is slow if it exceeds slowCallDurationThreshold), the breaker transitions to OPEN.

In OPEN, calls are rejected with CallNotPermittedException, which is not recorded as a failure. After waitDurationInOpenState the breaker moves to HALF_OPEN, either lazily on the next call or proactively if automaticTransitionFromOpenToHalfOpenEnabled is set. In HALF_OPEN it permits exactly permittedNumberOfCallsInHalfOpenState calls, using a fresh measurement window; others are rejected. The rates of these trial calls decide: below thresholds, CLOSED; otherwise back to OPEN. maxWaitDurationInHalfOpenState bounds how long it can stay half-open. Special states DISABLED, FORCED_OPEN and METRICS_ONLY support operational overrides. Which exceptions count as failures is controlled by recordExceptions, ignoreExceptions and a recordFailurePredicate (e.g., do not count 4xx client errors as dependency failures).

4.3 Decorator ordering

With the Spring Boot starter's annotations, Resilience4j applies aspects in this default order (outermost first): Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead → your method. Consequences: each retry attempt passes through the circuit breaker and is recorded individually; when the breaker is open, CallNotPermittedException reaches the retry, which should be configured not to retry it (otherwise you spin against an open breaker); the time limiter bounds each individual attempt, not the total. If you compose decorators programmatically (Decorators.ofSupplier(...)), you choose the order yourself, and the same reasoning applies.

4.4 Bulkhead and rate limiter internals

SemaphoreBulkhead wraps a fair semaphore with maxConcurrentCalls permits (default 25); a call waits up to maxWaitDuration (default 0, i.e., fail immediately) and otherwise gets BulkheadFullException. FixedThreadPoolBulkhead runs calls on a dedicated pool with a bounded queue, useful for isolating blocking calls in platform-thread applications. The RateLimiter divides time into cycles of limitRefreshPeriod and grants limitForPeriod permissions per cycle (a fixed-window style limiter computed lazily, with an atomic state). For outbound calls to rate-limited APIs (LLM providers measured in requests and tokens per minute), a client-side rate limiter avoids burning your quota on 429s.

4.5 Spring Framework 7 core resilience

Spring Framework 7 (with Boot 4) adds @Retryable (with delay, multiplier, jitter, max delay, includes/excludes, and support for reactive return types) and @ConcurrencyLimit (a bulkhead-like throttle, especially useful with virtual threads), enabled with @EnableResilientMethods, plus a programmatic RetryTemplate. Note that maxAttempts in core Spring counts retries excluding the initial call, unlike Spring Retry and Resilience4j, where it includes the initial call. It does not include a circuit breaker, so Resilience4j remains the standard for breakers. Version-sensitive · checked Nov 2026

4.6 Eureka registration and client caching

  1. On startup an instance registers (POST /eureka/apps/ORDERS) with its host, port, status and metadata (zone, version).
  2. It renews its lease with a heartbeat (default every 30 s); the server expires an instance after about 90 s without renewal.
  3. Clients fetch the full registry, then deltas (default every 30 s) and cache it locally. Spring Cloud LoadBalancer chooses an instance from the cached list, optionally preferring the same zone, and may add its own health-check filtering and caching.
  4. On shutdown the instance de-registers. If it crashes, callers may route to it for up to a couple of minutes (heartbeat expiry plus cache refresh), which is why client-side retries to a different instance are part of the pattern.
  5. If renewals drop below a threshold (as in a network partition between instances and the registry), the server enters self-preservation and stops expiring instances: availability of stale data over an empty registry.

Kubernetes inverts this: the kubelet reports pod readiness, the control plane updates EndpointSlices, and kube-proxy or the CNI updates forwarding rules on every node within seconds. No registration code lives in your app; graceful shutdown requires a preStop delay so endpoints are removed before the pod stops accepting connections.

4.7 Redis locks step by step, and where they break

  1. Client A runs SET lock:report-42 <uuidA> NX PX 30000. Redis returns OK: A holds a 30 s lease.
  2. A starts work. A stop-the-world GC pause (or a VM stall, or a slow network) freezes A for 40 s.
  3. At 30 s the key expires. Client B acquires the lock with <uuidB> and starts the same work, writing results to storage.
  4. A resumes, unaware that its lease has expired, and writes its (now stale) results to storage, overwriting B's.
  5. A tries to release with the compare-and-delete script; the value is uuidB, so the delete correctly does nothing. Correct release did not prevent the corruption in step 4.

Checking "do I still hold the lock?" before writing does not help: the pause can occur between the check and the write. The only robust fix is for the storage to reject A's write. With a fencing token, the lock service returns token 33 to A and token 34 to B; storage remembers it has seen 34 and rejects any write carrying 33. Redis's SET NX does not produce such a token; consensus systems do (etcd revisions, ZooKeeper zxids), and so does a database sequence.

4.8 etcd and ZooKeeper locks

etcd: the client creates a lease with a TTL and keeps it alive; it creates a key under a lock prefix attached to the lease; the key with the lowest create revision under the prefix holds the lock, others watch the key just before theirs. The holder's create revision is globally monotonic, so it is a valid fencing token. If the client dies, the lease expires and its key disappears. ZooKeeper: create an ephemeral sequential znode under /locks/report-42; if yours has the lowest sequence number you hold the lock; otherwise watch the next-lower node (avoiding herd effects). The ephemeral node disappears when the session expires. Both still suffer from the "paused holder" problem; both give you a monotonic token to fence with.

4.9 PostgreSQL advisory locks

Advisory locks are application-defined locks keyed by a 64-bit integer (or two 32-bit ones), managed by PostgreSQL's lock manager. pg_try_advisory_lock(k) returns immediately; pg_advisory_lock(k) waits; session-level locks persist until released or the connection ends; pg_advisory_xact_lock(k) is released automatically at transaction end, which is safer with connection pools (a session-level lock on a pooled connection can leak to the next borrower if not released). Because the lock lives in the same database as the data, you can combine it with the write in one transaction, which sidesteps the fencing problem for writes to that database: if the session dies, its transaction aborts.

Reading the diagram: the only automatic way out of OPEN is through HALF_OPEN's limited trial, which is what prevents a recovering dependency from being flooded the instant the breaker closes. What to try: raise the dependency's failure rate gradually and watch the moment the breaker trips relative to the threshold and window size; then shrink the window and see it react faster but also trip on short blips. Reading the diagram: shedding at ingress protects the service itself; the decorators protect the dependency and the service's resources from each other. Each layer converts a slow or failing situation into a fast, explicit outcome. Fallback is reached from two places (breaker open, bulkhead full), so it must be cheap and must not call the same dependency.

Reading the diagram: the lock service cannot stop A from waking up and acting; only the resource can refuse. The token must be monotonic across grants and checked atomically with the write (for example, UPDATE ... SET data=?, fence=? WHERE id=? AND fence < ?). If your storage cannot check tokens, a lock cannot give you correctness, and you should redesign the operation to be idempotent or conditional instead.

6. Math: Availability, Amplification, Concurrency and Timeouts

6.1 Availability of call chains

Serial synchronous dependencies multiply: \( A_{chain} = \prod_{i=1}^{k} A_i \). Ten services at 99.95% give \( 0.9995^{10} \approx 99.5\% \), about 3.6 hours of downtime per month instead of 22 minutes for one service. Parallel redundant paths combine as \( 1 - \prod (1 - A_i) \): two independent replicas at 99% give 99.99%. This is the quantitative argument for async integration and fallbacks.

6.2 Retry amplification

If each of \( d \) layers makes up to \( r \) attempts, a failure at the bottom can cause up to \( r^{d} \) calls. With \( r=3 \) and \( d=4 \): 81 calls for one user request. With a retry budget of ratio \( \beta \) (say 0.1) at each layer, the worst-case load multiplier per layer is \( 1 + \beta \), so the total is \( (1+\beta)^{d} \approx 1.46 \) for \( d=4 \): bounded, regardless of failure rate.

6.3 Backoff with jitter

For attempt \( n \) (starting at 0), base \( b \) and cap \( c \):

\[ \text{exp}(n) = \min(c,\; b \cdot 2^{n}), \qquad \text{full jitter: } s_n \sim U(0, \text{exp}(n)), \qquad \text{equal jitter: } s_n = \tfrac{\text{exp}(n)}{2} + U\!\left(0, \tfrac{\text{exp}(n)}{2}\right). \]

Decorrelated jitter: \( s_n = \min(c, U(b, 3 s_{n-1})) \). Full jitter's expected wait is half the exponential value, and it spreads synchronized clients uniformly, which is why AWS's analysis found it does the least total work under contention.

6.4 Sizing bulkheads with Little's law

Little's law: average concurrency \( L = \lambda W \) (arrival rate times time in system). If a dependency is called 200 times/s with p99 latency 150 ms, steady-state concurrency is about \( 200 \times 0.15 = 30 \). A bulkhead of ~40 permits absorbs normal variance; if latency rises to 2 s, demand would be 400 concurrent calls, and the bulkhead caps it at 40, rejecting the excess quickly instead of letting it consume the whole service. The same arithmetic sizes connection pools: \( \text{pool} \approx \lambda \times W_{db} \times \text{headroom} \).

6.5 Timeout budgets

If the gateway's deadline is \( D \) and a request makes sequential calls with timeouts \( t_i \) and up to \( r_i \) attempts with backoff \( s \), the worst case is \( \sum_i r_i (t_i + s_i) \). This must be \( < D \), otherwise you do work after the client has gone. Example: \( D = 1\,\text{s} \), two sequential calls, each with timeout 250 ms and 2 attempts with 50 ms backoff: \( 2 \times 2 \times 300 = 1{,}200 \) ms, which exceeds the budget. Either reduce to one retry on one call, or propagate the remaining deadline so that late retries are skipped. Illustrative

6.6 Circuit-breaker detection time

With a time-based window of \( w \) seconds, threshold \( \theta \), and a dependency that fails at rate \( f > \theta \) starting at time 0 while traffic is \( \lambda \) calls/s, the breaker needs (approximately) enough failures to push the windowed rate over \( \theta \) and at least \( m \) = minimumNumberOfCalls calls. For a previously healthy window, the earliest trip time \( t \) satisfies \( \frac{f \lambda t}{\lambda w} \ge \theta \), i.e., \( t \ge \theta w / f \), and \( \lambda t \ge m \) if the window is not yet full. With \( w = 10 \) s, \( \theta = 0.5 \), \( f = 1 \) (total outage): \( t \approx 5 \) s. Smaller windows detect faster but trip on noise.

6.7 Lock lease safety

A lease-based lock is safe without fencing only if every holder finishes its critical section, including any pause \( p \) and clock drift \( \delta \), within the lease: \( t_{work} + p_{max} + \delta < \text{TTL} \). Because \( p_{max} \) is unbounded in practice (GC, swapping, VM migration, network delays), no TTL makes this provably true. Fencing replaces the timing assumption with a check at the resource.

    private final RestClient http;
    private final QuoteCache cache;    // last known good prices, e.g. Caffeine or Redis

    public PricingClient(RestClient.Builder builder, QuoteCache cache) {
        var jdk = HttpClient.newBuilder()
                .connectTimeout(Duration.ofMillis(200))      // connect timeout
                .build();
        var factory = new JdkClientHttpRequestFactory(jdk);
        factory.setReadTimeout(Duration.ofMillis(500));     // per-attempt response timeout
        this.http = builder.baseUrl("http://pricing.shop.svc.cluster.local:8080")
                .requestFactory(factory)
                .build();
        this.cache = cache;
    }

    // Aspect order (outermost first): Retry -> CircuitBreaker -> Bulkhead -> method
    @Retry(name = "pricing")
    @CircuitBreaker(name = "pricing", fallbackMethod = "cachedQuote")
    @Bulkhead(name = "pricing")
    public Quote quote(String sku) {
        Quote q = http.get().uri("/v1/quotes/{sku}", sku)
                .header("X-Request-Deadline-Ms", String.valueOf(RequestDeadline.remainingMillis()))
                .retrieve()
                .body(Quote.class);
        cache.put(sku, q);
        return q;
    }

    /** Fallback: same signature plus the exception. Cheap, local, no remote calls. */
    private Quote cachedQuote(String sku, Throwable cause) {
        Quote last = cache.get(sku);
        if (last == null) {
            throw new PricingUnavailableException(sku, cause);   // no safe default for prices
        }
        return new Quote(sku, last.price(), true);
    }
}

7.3 A retry budget

package com.example.resilience;

import java.util.concurrent.atomic.AtomicLong;

/**
 * Token-bucket retry budget in the style of Finagle/Linkerd: every request deposits
 * `ratio` tokens, every retry withdraws one. Retries are allowed only while the balance
 * covers them, so retries can never exceed ~ratio of traffic plus a small floor.
 * Amounts are stored in milli-tokens to keep the arithmetic lock-free.
 */
public final class RetryBudget {
    private final long depositMilli;
    private final long maxBalanceMilli;
    private final AtomicLong balanceMilli;

    public RetryBudget(double ratio, int minRetriesFloor) {
        this.depositMilli = Math.round(ratio * 1000);
        this.maxBalanceMilli = Math.max(minRetriesFloor, 100) * 1000L;
        this.balanceMilli = new AtomicLong(minRetriesFloor * 1000L);
    }

    public void onRequest() {
        balanceMilli.accumulateAndGet(depositMilli, (cur, d) -> Math.min(maxBalanceMilli, cur + d));
    }

    public boolean tryRetry() {
        while (true) {
            long cur = balanceMilli.get();
            if (cur < 1000) return false;                      // budget exhausted: fail fast
            if (balanceMilli.compareAndSet(cur, cur - 1000)) return true;
        }
    }
}

Wire it into a Resilience4j Retry via retryOnException(e -> isTransient(e) && budget.tryRetry()) and call budget.onRequest() per original request. With ratio = 0.1, a total outage produces at most about 10% extra load from retries instead of 2× or more.

7.4 Load shedding at the service edge

package com.example.resilience;

import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.core.Ordered;
import org.springframework.core.annotation.Order;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.concurrent.Semaphore;

/** Rejects work beyond a fixed in-flight limit, with priority for critical paths. */
@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
public class ConcurrencyLimitFilter extends OncePerRequestFilter {

    private final Semaphore general = new Semaphore(200);
    private final Semaphore critical = new Semaphore(50);     // reserved for checkout

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        boolean isCritical = req.getRequestURI().startsWith("/checkout");
        Semaphore s = isCritical ? critical : general;
        if (!s.tryAcquire()) {
            if (isCritical && general.tryAcquire()) {             // critical may borrow general capacity
                s = general;
            } else {
                res.setStatus(503);
                res.setHeader("Retry-After", "1");
                return;                                          // shed: cheap, before any work
            }
        }
        try {
            chain.doFilter(req, res);
        } finally {
            s.release();
        }
    }
}

A fixed limit is a start; an adaptive limiter (e.g., Netflix's concurrency-limits library with a gradient algorithm) adjusts the limit as latency changes. Pair shedding with readiness probes that do not fail under load, or Kubernetes will remove capacity exactly when you need it.

7.6 Distributed locks: Redis for efficiency, fenced writes for correctness

package com.example.locks;

import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.util.List;
import java.util.Optional;
import java.util.UUID;

/** Efficiency lock: avoids duplicate work most of the time. NOT a correctness guarantee. */
@Component
public class RedisLock {

    private static final DefaultRedisScript<Long> RELEASE = new DefaultRedisScript<>("""
        if redis.call('GET', KEYS[1]) == ARGV[1] then
            return redis.call('DEL', KEYS[1])
        else
            return 0
        end
        """, Long.class);

    private final StringRedisTemplate redis;

    public RedisLock(StringRedisTemplate redis) { this.redis = redis; }

    public Optional<String> tryAcquire(String name, Duration ttl) {
        String token = UUID.randomUUID().toString();
        Boolean ok = redis.opsForValue().setIfAbsent("lock:" + name, token, ttl);   // SET NX PX
        return Boolean.TRUE.equals(ok) ? Optional.of(token) : Optional.empty();
    }

    public boolean release(String name, String token) {     // compare-and-delete, atomic in Lua
        Long n = redis.execute(RELEASE, List.of("lock:" + name), token);
        return n != null && n == 1L;
    }
}

	},

// Quote calls pricing with the caller's deadline, one jittered retry, behind a breaker.
func Quote(ctx context.Context, sku string) ([]byte, error) {
	var lastErr error
	for attempt := 0; attempt < 2; attempt++ {
		if attempt > 0 {
			backoff := time.Duration(rand.Int64N(int64(100*time.Millisecond) << attempt)) // full jitter
			select {
			case <-time.After(backoff):
			case <-ctx.Done():
				return nil, ctx.Err() // caller's deadline passed: stop retrying
			}
		}
		body, err := pricingCB.Execute(func() ([]byte, error) {
			req, _ := http.NewRequestWithContext(ctx, http.MethodGet, "http://pricing:8080/v1/quotes/"+sku, nil)
			resp, err := httpClient.Do(req)
			if err != nil {
				return nil, fmt.Errorf("%w: %v", errTransient, err)
			}
			defer resp.Body.Close()
			if resp.StatusCode >= 500 {
				return nil, fmt.Errorf("%w: status %d", errTransient, resp.StatusCode)
			}
			return io.ReadAll(resp.Body)
		})
		if err == nil {
			return body, nil
		}
		if errors.Is(err, gobreaker.ErrOpenState) || !errors.Is(err, errTransient) {
			return nil, err // do not retry an open breaker or a non-transient error
		}
		lastErr = err
	}
	return nil, lastErr
}

// WithEtcdLock runs fn while holding a lock; fn receives a fencing token.
func WithEtcdLock(ctx context.Context, cli *clientv3.Client, name string, fn func(fence int64) error) error {
	sess, err := concurrency.NewSession(cli, concurrency.WithTTL(15)) // lease kept alive in background
	if err != nil {
		return err
	}
	defer sess.Close()
	m := concurrency.NewMutex(sess, "/locks/"+name)
	if err := m.Lock(ctx); err != nil {
		return err
	}
	defer m.Unlock(context.Background())
	return fn(m.Header().Revision) // monotonic across grants: pass it to the storage layer
}
