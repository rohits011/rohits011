Capstone: A Scalable, Multi-Tenant AI SaaS Platform

You will design and build the platform layer behind an AI product sold to many businesses. It covers tenant onboarding and isolation, an LLM gateway that routes, caches, limits and meters every model call, quotas and plans, a usage-metering pipeline you can bill from, and the operational controls that stop one tenant from hurting the others. Your margins depend on this platform layer as much as on the model.

  • Prerequisites: system design foundations, rate limiting, Kafka, OIDC/JWT, LLM cost & observability, Projects I.
  • You will be able to: choose a tenancy model per tier; enforce tenant isolation in PostgreSQL with row-level security; build an LLM gateway with per-tenant rate limits, budgets, fallbacks and metering; design an idempotent usage pipeline that feeds billing; price an AI product on usage; and operate the platform with per-tenant observability.

1. Introduction: The Business Behind the Model

The product in this capstone is Lumen Illustrative, a B2B AI workspace. Customers (tenants) upload documents, run AI workflows (summarise, extract, draft, ask questions with RAG), and call the same capabilities through a public API. Lumen sells three plans: Free, Team (per seat plus included AI credits) and Enterprise (committed spend, dedicated capacity options, SSO, data residency). The model providers bill Lumen per token. Lumen bills its customers per seat and per credit, so every request has a cost of goods sold (COGS) that must be measured, limited and recovered.

Earlier chapters showed how to build AI features. This capstone is about the platform those features run on. It has four concerns:

  1. Tenancy and isolation: one codebase serving thousands of tenants without data leaks or noisy-neighbour outages.
  2. The LLM gateway: a single control point for all model traffic: authentication, routing, fallbacks, caching, quotas and metering.
  3. Metering and billing: turning millions of usage events into accurate invoices, idempotently and auditable.
  4. Plans and quotas: enforcing what each tenant has paid for, in real time.

Bridging from Java & Spring Boot

What you already know
You have built Spring Boot services with Spring Security resource servers, Hibernate filters or @Where clauses for soft-deletes, Bucket4j or gateway rate limiting, Kafka consumers that aggregate events, and maybe a Stripe integration with webhooks.
Why that is not enough
Multi-tenancy turns every one of those into a security boundary. A forgotten WHERE tenant_id = ? is a data breach. A missing rate limit is an outage for other customers. A double-counted usage event is a billing dispute. LLM traffic adds two more problems: cost per request varies by two orders of magnitude depending on the tokens, and the upstream provider imposes its own rate limits that all your tenants share.
The modern approach
Enforce tenant isolation in the database (PostgreSQL row-level security driven by a session variable), not only in application code. Route all model calls through a gateway that knows the tenant, the plan and the budget. Emit an immutable usage event for every billable action with an idempotency key, and aggregate those events into meters that the billing system consumes. Choose the tenancy model per plan tier: pooled for Free and Team, bridged or siloed for Enterprise.
Where Python and Go fit
The LLM gateway is written in Go: a high-throughput proxy with streaming, low memory per connection and simple deployment. AI workflow workers are Python (document parsing, RAG). The control plane (tenants, plans, billing) is Spring Boot, where transactions, security and integrations dominate.
In production
You will run a control plane, a data plane per region, a gateway fleet, Redis for rate-limit state, Kafka for usage events, PostgreSQL (pooled plus a few dedicated clusters), a billing provider integration, and per-tenant dashboards that support and finance both rely on.
Use it when / avoid it when
Use a pooled multi-tenant platform when you have many small and mid-size customers and need unit economics. Avoid pooling for customers whose contracts demand physical isolation, dedicated keys or residency. Give them a silo, managed by the same control plane.

2. History: From ASP Hosting to Token-Metered SaaS

In the late 1990s, "application service providers" hosted a separate copy of enterprise software per customer, a model we would now call siloed. Salesforce, founded in 1999, popularised the multi-tenant architecture in which all customers share one application and one database schema, separated by an organisation identifier and metadata-driven customisation. Shared infrastructure brought the economics that made SaaS a mass market.

Cloud infrastructure (Amazon S3 and EC2 launched in 2006) made per-use pricing familiar to engineers: you pay for requests, gigabytes and instance-hours. Developer-facing APIs such as Twilio and Stripe made usage-based pricing standard for API businesses in the 2010s, and metering became core infrastructure. AWS later formalised SaaS architecture vocabulary (silo, pool, bridge; tenant isolation strategies) in its SaaS Lens and whitepapers. Its Builders' Library described shuffle sharding as a way to contain noisy neighbours.

LLM APIs, from OpenAI's API beta in 2020 onwards and then many providers, priced per token, separately for input and output, with discounts for cached and batched tokens. AI products therefore inherited a variable COGS per request at a scale classic SaaS never had. A single heavy user can cost more than their subscription. Since 2023, the industry has converged on a few patterns: an internal LLM gateway as the choke point, credits or token-based plans, hybrid pricing (seat plus usage), and billing platforms adding first-class AI metering. Stripe documents an LLM token billing feature, in preview at the time of writing, that meters tokens per customer by model and token type Version-sensitive · checked Nov 2026.

  • Noisy-neighbour impact: p95 latency of the least-busy tenants unchanged (± 10%) during the top tenant's bursts (measured in load tests).
  • Time-to-first-value for new tenants: sign-up to first AI result < 5 minutes.

4. Internals: Key Flows

4.1 Tenant context propagation

Every request carries a tenant identity from the edge to the database:

  1. The edge (API gateway) authenticates either a user JWT (issued by Lumen's IdP, which federates with the tenant's SSO) or an API key. Both resolve to tenant_id, principal_id and the plan. API keys are stored as hashes with a prefix for lookup (lmn_live_ab12…) and map to a tenant and scopes.
  2. The edge forwards a signed internal token (short-lived JWT with the tid, sub, plan and scopes claims). Services trust only this token, never a raw X-Tenant-Id header.
  3. Each Spring Boot service puts the tenant into a TenantContext (a request-scoped bean; a ScopedValue where available) and into the MDC for logs. OpenTelemetry baggage carries tenant.id to downstream spans.
  4. When a database connection is checked out for a transaction, the service runs SET LOCAL app.tenant_id = '…'. PostgreSQL row-level security policies compare every row's tenant_id with that setting. A query that forgot its WHERE clause returns only the current tenant's rows, and a query without the setting returns nothing.

4.2 An AI request through the gateway

Reading the diagram: the gateway reserves an estimated number of credits before calling the provider (based on input token count and max_tokens) and settles to the actual amount afterwards. Without the reservation, 50 concurrent requests from one tenant would all pass a "balance > 0" check and overspend. The usage event is emitted after the stream ends, keyed by a request ID, so a retried emission is deduplicated downstream. The fallback is a plan-level policy. Enterprise tenants with residency requirements never fall back to a provider or region outside their allowed set, so the routing table is part of the tenant's entitlements.

4.3 Quotas: two kinds of limit

  • Rate limits (requests per minute, tokens per minute) protect the platform and provide fairness. They use token buckets in Redis, keyed per tenant and per API key, with plan-dependent capacity and refill. Exceeding one returns HTTP 429 with Retry-After.
  • Budget limits (credits per billing period) protect revenue. They use a balance with reservations. Exceeding one returns an "insufficient credits" error, or allows overage if the plan permits it, in which case it is billed.

Global fairness is a third layer. The gateway holds the provider-side capacity (for example, tokens per minute for each model on the organisation's account) and divides it among plans with weighted fair queuing: Enterprise traffic gets reserved headroom and Free traffic is shed first under pressure.

4.4 The metering pipeline

Reading the diagram: raw events are append-only and never mutated. The dedupe stage uses a state store keyed by event ID, with exactly-once semantics in Kafka Streams, so producer retries do not double-bill. Aggregates are written as upserts keyed by (tenant, meter, hour), so re-processing produces the same numbers. Billing sync sends meter events to the billing provider with an identifier per tenant, meter and hour, which the provider uses for idempotency. The lake copy supports finance analytics and reconciliation against provider invoices. The reconciliation job compares our token totals per model per day with the provider's usage API.

4.5 Tenant provisioning

Provisioning is a saga run by the control plane: create the tenant record → create the IdP organisation (SSO connection for Enterprise) → create the billing customer and subscription → allocate the data plane (pooled: insert a row; bridge: create a schema and run migrations; silo: trigger a GitOps pipeline that renders a tenant overlay and waits for health) → seed defaults → mark the tenant ACTIVE. Each step is idempotent and has a compensation (delete the billing customer, and so on). Pooled provisioning finishes in seconds. Silo provisioning can take tens of minutes and is tracked as a long-running operation in the console.

4.6 Plan changes and entitlement propagation

Upgrades, downgrades, add-on purchases and support overrides all change what a tenant may do, and every gateway instance must notice quickly. The control plane writes entitlement changes to PostgreSQL and publishes an EntitlementsChanged{tenantId, version} event on a compacted Kafka topic. Gateways keep an in-memory map of entitlements, warmed from the compacted topic on start-up and updated as events arrive, with a 60-second TTL fallback that refetches from the control plane API if an event is missed. The version field makes updates monotonic, so a reordered older event cannot downgrade a tenant who just upgraded. Upgrades take effect immediately. Downgrades take effect at the end of the billing period, unless they come from non-payment, in which case they are immediate and also revoke active API keys' write scopes. Support overrides (a temporary higher rate limit for a launch) are entitlement rows with an expiry, so they cannot be forgotten.

Credit balances follow the same pattern but are owned by the ledger. When a tenant buys a credit pack, the billing webhook (invoice.paid) is verified by signature, deduplicated by event ID, written to the ledger, and then the Redis balance is incremented. If Redis loses data, a rebuild job recomputes balances from the ledger minus unsettled consumption for the current hour.

5. Architecture

5.1 Control plane and data planes

Reading the diagram: the control plane holds no customer content. It holds tenant metadata, plans and billing state, so it can be global while data planes are regional. A silo runs the same images and charts as the pooled plane with different values (dedicated DB endpoint, KMS key, routing table), which keeps the code path identical. Usage events from every plane converge on one metering pipeline. Events carry the data-plane ID and contain no customer content, only counts.

5.2 Data model

Reading the diagram: credits are a ledger (grants, purchases, consumption, adjustments), not a mutable balance column. The balance is a sum, and every change has a reference: an invoice, a usage hour or a support ticket. Redis holds the real-time balance for enforcement and is periodically reconciled against the ledger, which is the source of truth.

5.3 Try the rate limiter

Set a burst larger than the bucket capacity and compare the algorithms. The token bucket allows a short burst up to its capacity and then a steady rate. That suits AI requests, where a user often fires a few in a row and then pauses. Fixed windows let through up to twice the limit at window edges. The gateway uses token buckets for requests and tokens per minute, and a reservation ledger (not a bucket) for monthly credits.

6. Math: Pricing, Margins and Capacity

All values are Illustrative. Model prices are as listed for the Claude 5.5 family at the time of writing Version-sensitive · checked Nov 2026.

6.1 Defining a credit

Customers should not have to understand per-model token prices. Define one credit as a fixed amount of COGS plus margin, and convert each request's tokens into credits with per-model weights:

\[ \text{credits}(r) = \frac{T_{in}^{\text{uncached}} p_{in} + T_{in}^{\text{cached}} p_{cr} + T_{out} p_{out}}{u} \]

where \(u\) is the COGS value of one credit. If a credit sells for $0.01 and the target gross margin on usage is 70%, then \(u = \$0.003\). A typical RAG answer on Sonnet 5.5 (7,000 input tokens, 400 output) costs \(7{,}000 \cdot 2/10^6 + 400 \cdot 10/10^6 = \$0.018\), which is 6 credits. The same answer on Haiku 5.5 costs about \(7{,}000 \cdot 0.1/10^6 + 400 \cdot 0.5/10^6 = \$0.0009\), or 0.3 credits. Publish the per-model credit rates so customers can choose cheaper models, and round up per request to whole tenths of a credit.

6.2 Plan margin under a heavy-tailed workload

Usage per seat is heavy-tailed: a few power users dominate. Suppose a Team plan costs $30 per seat per month and includes 1,500 credits ($4.50 of COGS at \(u\)). If seat usage follows a distribution with mean 900 credits and a 99th percentile of 9,000, then the expected COGS per seat is \(900 \cdot u = \$2.70\), a 91% margin on the seat fee before infrastructure. Without a cap, a 99th-percentile seat costs \(9{,}000 \cdot u = \$27\), nearly the entire fee. Included credits plus metered overage (charged at the credit price) bound the downside: the overage revenue on that seat is \((9{,}000 - 1{,}500) \cdot \$0.01 = \$75\) against \$22.50 of extra COGS.

6.3 Rate-limit sizing

A token bucket has capacity \(b\) (burst) and refill rate \(r\). Over any interval \(t\), a tenant can send at most \(b + rt\) requests. Choose \(r\) from plan throughput and \(b\) from the burst you want to tolerate. For tokens-per-minute limits, charge the bucket with an estimate on admission (input tokens + max_tokens) and refund the difference on completion. Otherwise a tenant that sets max_tokens=64000 on many concurrent streams bypasses the limit.

Provider capacity allocation: if the organisation's limit on a model is \(C\) tokens per minute and plans have weights \(w_p\) with current demand \(d_p\), weighted max-min fairness allocates \(a_p = \min(d_p, \frac{w_p}{\sum_{q \in A} w_q} C_{\text{remaining}})\), iterating over unsatisfied plans \(A\). In practice, a reserved fraction for Enterprise (say 40%) plus weighted sharing of the remainder is simpler and almost as good.

6.4 Redis and metering capacity

At 2M AI requests per day with a peak factor of 4, peak rate is about \(2{,}000{,}000 / 86{,}400 \cdot 4 \approx 93\) requests/s. Each request makes about 3 Redis script calls (bucket check, reserve, settle), so around 280 ops/s, trivial for Redis. The tighter constraint is hot keys: one large tenant's keys live on one shard. Hash-tag keys by tenant so a tenant's scripts are atomic on one shard, and give very large tenants per-key-type sub-buckets if needed.

Usage events: about 2M per day plus storage and document events, around 3M events at about 400 bytes, or 1.2 GB/day raw. Over 13 months of retention in the lake (compressed roughly 5×), that is about 100 GB. Billing aggregates: 20,000 tenants × 5 meters × 24 hours ≈ 2.4M rows per day, which is easy for PostgreSQL with monthly partitions.

package com.lumen.platform;

import java.lang.reflect.Proxy;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.sql.Statement;
import javax.sql.DataSource;
import org.springframework.jdbc.datasource.DelegatingDataSource;

/**
 * Sets app.tenant_id on every connection checkout and resets it on return to the pool,
 * so PostgreSQL RLS policies see the current tenant. Missing tenant = no rows (fail closed).
 */
public class TenantAwareDataSource extends DelegatingDataSource {

  public TenantAwareDataSource(DataSource target) {
    super(target);
  }

  @Override
  public Connection getConnection() throws SQLException {
    Connection c = super.getConnection();
    String tenant = TenantContext.currentOrNull();     // null for system jobs: they use a separate DataSource
    try (PreparedStatement ps = c.prepareStatement("SELECT set_config('app.tenant_id', ?, false)")) {
      ps.setString(1, tenant == null ? "" : tenant);
      ps.execute();
    }
    return (Connection) Proxy.newProxyInstance(getClass().getClassLoader(), new Class<?>[]{Connection.class},
        (proxy, method, args) -> {
          if (method.getName().equals("close")) {
            try (Statement s = c.createStatement()) { s.execute("RESET app.tenant_id"); }
            catch (SQLException ignored) { /* connection is broken; pool will evict it */ }
          }
          return method.invoke(c, args);
        });
  }
}

An empty string cast to uuid raises an error, so any query without a tenant fails loudly rather than returning data. That is what we want: a background job that forgot to set a tenant is a bug to surface. Jobs that legitimately span tenants (billing aggregation, for example) use a separate DataSource with a role that has its own explicit, audited policies.

import org.springframework.web.filter.OncePerRequestFilter;

/** Runs after Spring Security: takes the tenant ONLY from the verified internal JWT. */
public class TenantFilter extends OncePerRequestFilter {
  @Override
  protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
      throws java.io.IOException, jakarta.servlet.ServletException {
    var auth = SecurityContextHolder.getContext().getAuthentication();
    if (!(auth instanceof JwtAuthenticationToken jwt) || jwt.getToken().getClaimAsString("tid") == null) {
      res.sendError(401);
      return;
    }
    String tid = jwt.getToken().getClaimAsString("tid");
    try (var ignored = TenantContext.open(tid);
         Scope s = Baggage.current().toBuilder().put("tenant.id", tid).build().makeCurrent()) {
      MDC.put("tenant_id", tid);
      chain.doFilter(req, res);
    } finally {
      MDC.remove("tenant_id");
    }
  }
}

7.3 LLM gateway: limits, reservation, proxy and metering (Go)

-- KEYS[1] = {tid}:bucket:rpm   KEYS[2] = {tid}:credits   KEYS[3] = {tid}:resv:{requestId}
-- ARGV: now_ms, capacity, refill_per_ms, est_millicredits, allow_overage(0/1), resv_ttl_s
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(b[1]) or tonumber(ARGV[2])
local ts = tonumber(b[2]) or tonumber(ARGV[1])
tokens = math.min(tonumber(ARGV[2]), tokens + (tonumber(ARGV[1]) - ts) * tonumber(ARGV[3]))
if tokens < 1 then
  return {0, 'rate_limited', math.ceil((1 - tokens) / tonumber(ARGV[3]))}
end
local balance = tonumber(redis.call('GET', KEYS[2]) or '0')
local est = tonumber(ARGV[4])
if balance < est and ARGV[5] == '0' then
  return {0, 'insufficient_credits', 0}
end
redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'ts', ARGV[1])
redis.call('PEXPIRE', KEYS[1], 120000)
redis.call('DECRBY', KEYS[2], est)                       -- reserve; integer milli-credits (may go negative with overage)
redis.call('SET', KEYS[3], est, 'EX', tonumber(ARGV[6]))  -- remember reservation for settlement
return {1, 'ok', 0}

Credits are stored as integer milli-credits to avoid floating-point drift. The keys share the hash tag {tid}, so the script runs atomically on one Redis Cluster shard. The settle script (omitted) reads the reservation key, applies INCRBY with the difference between estimate and actual, and deletes the key. An expired reservation (gateway crash) is reconciled later from the usage events. The Redis balance itself is periodically re-derived from the credit ledger.

import (
	"bufio"
	"bytes"

	"io"
	"log/slog"

	"lumen/gateway/internal/auth"
	"lumen/gateway/internal/limits"
	"lumen/gateway/internal/meter"
	"lumen/gateway/internal/route"

type Handler struct {
	Limits *limits.Limiter
	Routes *route.Table
	Meter  *meter.Producer
	Client *http.Client
}

func (h *Handler) ServeHTTP(w http.ResponseWriter, r *http.Request) {
	claims, err := auth.InternalClaims(r) // verified internal JWT: tid, plan, feature, sub
	if err != nil {
		http.Error(w, "unauthorized", http.StatusUnauthorized)
		return
	}
	body, _ := io.ReadAll(io.LimitReader(r.Body, 10<<20))
	var req struct {
		Model     string `json:"model"`
		MaxTokens int    `json:"max_tokens"`
	}
	if err := json.Unmarshal(body, &req); err != nil {
		http.Error(w, "bad request", http.StatusBadRequest)
		return
	}
	ent := h.Routes.Entitlements(claims.TenantID)
	if !ent.ModelAllowed(req.Model) {
		http.Error(w, `{"error":"model_not_in_plan"}`, http.StatusForbidden)
		return
	}
	requestID := r.Header.Get("X-Request-Id")
	est := ent.EstimateCredits(req.Model, len(body)/4, req.MaxTokens) // rough input estimate; refined on settle
	dec, err := h.Limits.Admit(r.Context(), claims.TenantID, requestID, ent, est)
	if err != nil || !dec.Allowed {
		writeLimitError(w, dec)
		return
	}

	start := time.Now()
	var usage meter.Usage
	var upstream route.Target
	for _, target := range h.Routes.Candidates(claims.TenantID, req.Model) { // primary, then plan-approved fallbacks
		upstream = target
		resp, err := h.forward(r, target, body)
		if err != nil || resp.StatusCode == 429 || resp.StatusCode >= 500 {
			if resp != nil {
				resp.Body.Close()
			}
			slog.WarnContext(r.Context(), "upstream failed, trying fallback", "target", target.Name)
			continue
		}
		usage = streamAndCount(w, resp) // copies SSE to client, parses usage from message_start / message_delta
		resp.Body.Close()
		break
	}
	credits := ent.Credits(upstream.Model, usage)
	h.Limits.Settle(r.Context(), claims.TenantID, requestID, est, credits) // refund or charge the difference
	h.Meter.Emit(meter.Event{
		ID: requestID, TenantID: claims.TenantID, Principal: claims.Subject, Feature: claims.Feature,
		Model: upstream.Model, Provider: upstream.Provider, InputTokens: usage.Input,
		CacheReadTokens: usage.CacheRead, CacheWriteTokens: usage.CacheWrite, OutputTokens: usage.Output,
		Credits: credits, LatencyMs: time.Since(start).Milliseconds(), At: time.Now().UTC(),
	})
}

// streamAndCount relays SSE lines unchanged and extracts token usage from the provider's events.
func streamAndCount(w http.ResponseWriter, resp *http.Response) meter.Usage {
	w.Header().Set("Content-Type", resp.Header.Get("Content-Type"))
	w.WriteHeader(resp.StatusCode)
	flusher, _ := w.(http.Flusher)
	var u meter.Usage
	sc := bufio.NewScanner(resp.Body)
	sc.Buffer(make([]byte, 0, 64*1024), 1<<20)
	for sc.Scan() {
		line := sc.Bytes()
		w.Write(line)
		w.Write([]byte("\n"))
		if bytes.HasPrefix(line, []byte("data: ")) {
			u.Observe(line[6:]) // reads usage fields if present
		}
		if len(line) == 0 && flusher != nil {
			flusher.Flush()
		}
	}
	return u
}

Omitted for brevity: forward (sets the provider API key from a secret, removes tenant headers, applies timeouts), non-streaming responses, and writeLimitError (429 with Retry-After, or 402-style JSON). One subtlety: if the client disconnects mid-stream, the provider may still bill the generated tokens. The gateway should cancel the upstream request when the client context is cancelled, and meter what the provider reports. Version-sensitive · checked Nov 2026: usage fields in streaming events differ between providers, so implement Usage.Observe per provider adapter.

7.4 Deduplication with Kafka Streams (exactly-once)

package com.lumen.metering;

import java.time.Duration;
import org.apache.kafka.common.serialization.Serdes;
import org.apache.kafka.streams.StreamsBuilder;
import org.apache.kafka.streams.Topology;
import org.apache.kafka.streams.kstream.*;
import org.apache.kafka.streams.processor.api.*;
import org.apache.kafka.streams.state.*;

public final class DedupeTopology {
  static final String STORE = "seen-event-ids";

  public static Topology build() {
    StreamsBuilder b = new StreamsBuilder();
    b.addStateStore(Stores.windowStoreBuilder(
        Stores.persistentWindowStore(STORE, Duration.ofDays(7), Duration.ofDays(7), false),
        Serdes.String(), Serdes.Long()));

    b.stream("usage.raw", Consumed.with(Serdes.String(), UsageSerde.INSTANCE))   // key = tenantId
        .process(() -> new Processor<String, UsageEvent, String, UsageEvent>() {
          private WindowStore<String, Long> seen;
          private ProcessorContext<String, UsageEvent> ctx;

          @Override public void init(ProcessorContext<String, UsageEvent> c) {
            ctx = c;
            seen = c.getStateStore(STORE);
          }

          @Override public void process(Record<String, UsageEvent> rec) {
            String id = rec.value().id();
            long now = rec.timestamp();
            try (var it = seen.fetch(id, now - Duration.ofDays(7).toMillis(), now)) {
              if (it.hasNext()) return;                    // duplicate within 7 days: drop
            }
            seen.put(id, now, now);
            ctx.forward(rec.withValue(Enrich.withPriceVersion(rec.value())));
          }
        }, STORE)
        .to("usage.clean", Produced.with(Serdes.String(), UsageSerde.INSTANCE));
    return b.build();
  }
}
// application config: processing.guarantee=exactly_once_v2 so store updates and output commit atomically

Because the stream is keyed by tenant, duplicates of one event land in the same partition and therefore the same state store instance. This is why the producer keys by tenant and not by request ID. exactly_once_v2 makes "mark as seen" and "emit downstream" atomic, so a crash between them cannot lose or duplicate an event.

7.5 Billing sync to the billing provider

package com.lumen.billing;

import com.stripe.StripeClient;
import com.stripe.param.billing.MeterEventCreateParams;
import java.time.Instant;
import org.springframework.scheduling.annotation.Scheduled;
import org.springframework.stereotype.Component;

@Component
class MeterPublisher {
  private final StripeClient stripe;           // API key from Vault; version-sensitive SDK
  private final UsageHourlyRepository usage;
  private final TenantBillingRepository tenants;

  MeterPublisher(StripeClient stripe, UsageHourlyRepository usage, TenantBillingRepository tenants) {
    this.stripe = stripe; this.usage = usage; this.tenants = tenants;
  }

  /** Publishes closed hours (now - 2h, to allow late events) that have not been published yet. */
  @Scheduled(cron = "0 7 * * * *")
  void publishClosedHours() throws Exception {
    for (var row : usage.unpublishedClosedHours(Instant.now().minusSeconds(7200))) {
      var customer = tenants.stripeCustomerId(row.tenantId());
      var params = MeterEventCreateParams.builder()
          .setEventName("ai_credits")
          .putPayload("stripe_customer_id", customer)
          .putPayload("value", row.quantity().toPlainString())
          .setTimestamp(row.hour().getEpochSecond())
          .setIdentifier(row.tenantId() + ":ai_credits:" + row.hour())   // provider-side idempotency
          .build();
      stripe.billing().meterEvents().create(params);
      usage.markPublished(row);                    // same identifier on retry -> provider dedupes
    }
  }
}

Late events (arriving after an hour was published) are handled by publishing a separate adjustment event with its own identifier rather than mutating a published hour. The audit trail then reads as an append-only history, which accountants appreciate.

9. Case Studies and Reference Architectures

9.1 AWS SaaS architecture guidance Verified

AWS's SaaS Tenant Isolation Strategies whitepaper and the SaaS Lens of the Well-Architected Framework define the silo, pool and bridge vocabulary used in §3.3. They argue that isolation must be enforced by mechanisms (IAM policies, database policies) rather than by developer discipline, and that the control plane should be shared across deployment models. Lesson: RLS and scoped credentials are the "mechanism" in this capstone.

9.2 Shuffle sharding for noisy-neighbour containment Verified

The Amazon Builders' Library article "Workload isolation using shuffle-sharding" explains how assigning each customer to a random small subset of workers sharply reduces the chance that one bad customer's traffic takes down another customer's entire capacity. Lesson: for the AI workers in Lumen (document processing and RAG), assign each tenant to 2 of N worker pools by hash. A poison workload then affects only tenants sharing both pools.

9.3 Stripe on pricing and metering AI products Verified

Stripe's "A framework for pricing AI products" discusses charge metrics including consumption-based pricing per token or per call, and Stripe's LLM token billing documentation describes metering tokens per customer segmented by model and token type, with markup configured over provider prices (a private preview at the time of writing Version-sensitive · checked Nov 2026). Lesson: billing platforms are converging on the "events → meters → prices" model that §4.4 implements, which keeps your pipeline portable.

9.4 PostgreSQL row-level security in multi-tenant SaaS Verified

The PostgreSQL documentation on row security policies describes USING and WITH CHECK expressions, FORCE ROW LEVEL SECURITY for table owners, and the BYPASSRLS attribute. Several SaaS vendors and Postgres-based platforms publicly recommend RLS keyed on a session setting as a defence-in-depth layer for pooled tenancy. Lesson: it is a well-trodden path, but performance depends on tenant_id leading your indexes, and on policies being simple, non-volatile expressions.

12. Common Mistakes

  • Trusting a tenant header from the client. Any X-Tenant-Id header is attacker-controlled. Derive the tenant from verified tokens or keys only.
  • RLS with a superuser or BYPASSRLS application role. The policies silently do nothing. Use FORCE ROW LEVEL SECURITY and a NOBYPASSRLS app role, and test it.
  • Tenant setting leaking across pooled connections. A connection returned without reset carries the previous tenant into the next request. Reset on return, or use SET LOCAL inside transactions.
  • Check-then-act budget enforcement. Concurrent requests all see a positive balance. Reserve atomically.
  • Metering from application logs. Logs are sampled, dropped and reformatted. Bill from a dedicated, schema-governed event stream with idempotency keys.
  • Counting tokens yourself instead of using provider usage fields. Tokenisers differ and cached tokens are priced differently. Meter what the provider reports, and estimate only for admission.
  • One provider API key for everything. One leaked key, or one tenant's abuse, takes everyone down. Use separate keys per data plane or tier, keep them only in the gateway, and rotate them.
  • Ignoring cancelled streams. A client disconnects and the provider keeps generating, so you are billed but you do not bill. Propagate cancellation upstream and meter what is reported.
  • Unbounded Free tier. Free plans attract abuse (scripted sign-ups, prompt farming). Require verification, set strict limits, and shed Free traffic first under provider pressure.
  • Global limits only. Per-tenant limits without per-API-key limits let one leaked key exhaust a tenant's whole quota. Layer them.

13. Production: Deployment, Observability, Security and Scaling

13.1 Deployment

  1. Bootstrap the control plane (global) and one pooled data plane per region with Terraform: VPCs, managed Kubernetes, managed PostgreSQL (with a separate migration owner role and the app role NOBYPASSRLS), Redis Cluster, managed Kafka with Schema Registry, and an object store.
  2. Deploy charts with Argo CD. Each data plane is an ApplicationSet generator entry, and silo tenants are additional entries rendered from deploy/tenants/silo/<tenant>.
  3. Provider API keys live in Vault (per data plane), injected only into the gateway via External Secrets. App services receive gateway-scoped tokens.
  4. Run the isolation suite and synthetic tenants as post-deploy checks (Argo Rollouts analysis). A failure rolls back automatically.

13.2 Observability

  • Per-tenant RED metrics without cardinality explosion: label metrics with plan and a bounded tenant_tier_bucket. Put per-tenant breakdowns in the usage store and traces (tenant as a span attribute and in baggage), not in Prometheus labels for 20,000 tenants.
  • Gateway: admits and denies by reason, upstream latency by provider and model, fallback rate, reservation drift (estimate vs actual), stream cancellation rate.
  • Metering: events in vs out of dedupe, duplicate rate, lag, late-event rate, published-hours backlog, reconciliation error per model per day.
  • Business: margin per plan, top 50 tenants by COGS, credit burn rate, tenants approaching limits. These feed customer-success alerts, not only engineering.

13.3 Security

  • Isolation in two layers (application + RLS) for pooled tiers; schema, database and key isolation for bridge and silo; KMS keys per tenant for silo and bridge, with crypto-shredding on offboarding (delete the key to make backups unreadable).
  • API keys: hashed with a server-side pepper, prefixed for identification, scoped, rotatable, with last-used tracking and secret-scanning partner registration so leaked keys get reported.
  • Tenant admins get audit logs (logins, key changes, data exports). Lumen staff access to tenant data is just-in-time, approved and logged.
  • The prompt and completion content of tenants is not stored by default. If you store it for debugging, make it opt-in per tenant with retention limits. Choose provider settings (data retention, regional processing) to match the DPA you signed.
  • Abuse controls on Free: email or domain verification, CAPTCHA on sign-up, anomaly detection on credit burn, and the provider's usage-policy requirements reflected in your terms.

13.4 Scaling and performance

  • Gateway: stateless, horizontal, HPA on concurrent streams per pod (exported metric). Tune HTTP/2 to providers, keep-alive pools and per-provider circuit breakers.
  • Database: all pooled tables lead with tenant_id in indexes and partition keys. Move very large tenants to bridge (rebalancing) rather than scaling the pool vertically forever. Read replicas serve dashboards.
  • Workers: shuffle-sharded queues per tenant group, with per-tenant concurrency caps inside each worker.
  • Cost levers: prompt caching for shared system prompts (per feature, not per tenant, to maximise hits); batch API for non-interactive workflows (cheaper credits, passed on to customers as a "batch" option); semantic caching only for public, non-tenant-specific content. Never cache across tenants.

13.5 Disaster recovery and runbooks

  • Gateway unavailable: app services fail fast (circuit breaker) and show a degraded state. The gateway has no persistent state of its own, so recovery means redeploying. Redis is the dependency to protect: if it is down, the gateway runs in a fail-open-with-caps mode for paid plans (a conservative in-memory per-pod limit) and fail-closed for Free, and emits usage events as normal so billing stays correct.
  • Kafka unavailable: the gateway spills usage events to a local write-ahead file on a persistent volume and replays them when Kafka returns. The dedupe stage makes replays safe. Alert when the spill exceeds a size threshold.
  • Billing provider outage: meter publishing pauses, and unpublished hours accumulate in PostgreSQL. Nothing customer-facing breaks, because enforcement uses our own ledger.
  • Provider outage: plan-approved fallbacks are exercised monthly in a game day so they are known to work. Residency-locked tenants degrade instead of failing over across regions, and their status page entry says so.
  • Regional loss: pooled data planes are regional by design (residency), so DR is cross-zone within a region plus point-in-time recovery from backups in a paired region of the same jurisdiction. The global control plane runs active-passive across two regions.

14. Exercises

Exercise 1 · Foundational

Write a CI check that fails if any table with a tenant_id column lacks an enabled and forced RLS policy.

Solution

After migrations run in a Testcontainers database, query pg_class joined with pg_attribute for tables having a tenant_id column, and check relrowsecurity and relforcerowsecurity are true and that pg_policies has at least one policy for the table whose qual references app.tenant_id. Fail with the list of offending tables. Run it in the same Maven verify phase as other ITs.

Exercise 2 · Intermediate

Design credit packs (prepaid) that expire after 12 months, consumed after the monthly included credits and before overage. Show the ledger entries for a month in which a tenant uses 3,000 credits with 1,500 included and a 1,000-credit pack.

Solution

Ledger entries: GRANT included +1500 (period 2026-11); PURCHASE pack +1000 (expires 2027-11-03, ref invoice in_123); consumption is posted hourly as CONSUME -n with an allocation order: included first (FIFO by expiry), then packs (earliest expiry first), then OVERAGE. For 3,000 used: −1,500 from included, −1,000 from the pack, −500 recorded as overage and published to the billing meter. At period end, unused included credits get an EXPIRE entry. Balances per bucket are derived by summing entries by bucket_id. Redis holds a combined real-time balance (included remaining + packs remaining, plus overage allowance if enabled).

Exercise 3 · Intermediate

Add weighted fair sharing of provider capacity in the gateway: Enterprise 50%, Team 35%, Free 15%, with unused share redistributed.

Solution

Maintain per-plan token buckets whose refill rates are recomputed every second from the provider limit \(C\) and current demand. Measure each plan's admitted and denied demand over the last 10 s, compute weighted max-min allocations (§6.3), and set refill rates accordingly. Admission requires tokens from both the tenant bucket and the plan bucket. When the provider returns 429s, multiplicatively reduce \(C\) (AIMD) and recover additively. Test with a simulator that replays recorded traffic.

Exercise 4 · Advanced

Migrate a large tenant from the pooled database to a bridge schema with less than 1 minute of write unavailability.

Solution

Create the target schema and run migrations. Use logical replication (a publication with a row filter on tenant_id, available in PostgreSQL 15+) or CDC (Debezium) to stream the tenant's rows into the target and let it catch up. Put the tenant in a short "write freeze" (the gateway and API return 503 with Retry-After for writes; reads continue), wait for replication lag to reach zero, verify row counts and checksums per table, flip the tenant's data_plane and tenancy_model in the registry (services resolve the DataSource per tenant from the registry), and lift the freeze. Delete pooled rows after a retention window, then rotate the tenant's KMS key association.

15. Interview: Presenting the Capstone

Pitch (90 seconds): "Lumen is a multi-tenant AI SaaS. One control plane manages pooled, bridged and siloed data planes. Isolation is enforced in the app and in PostgreSQL RLS. Every model call goes through a Go gateway that checks entitlements, rate-limits with token buckets, reserves credits atomically, fails over between providers per plan policy, and emits idempotent usage events. Those are deduplicated with Kafka Streams exactly-once, aggregated hourly, and pushed to billing with idempotency identifiers. We reconcile against provider usage daily, with error under 0.5%."

Architecture How do you prevent cross-tenant data leaks in a pooled database?

Tenant from verified tokens only; tenant set on the connection for every transaction; RLS with FORCE and a NOBYPASSRLS app role, failing closed when unset; app-layer filters as well; a generated CI check that every tenant table has policies; and cross-tenant integration tests plus pen tests.

Conceptual Silo vs pool vs bridge: when would you pick each?

Pool for many small tenants (cost, agility); bridge when tenants need stronger data separation or custom keys but compute can be shared; silo for contractual or regulatory isolation, residency or dedicated capacity. Keep one control plane and the same code for all three.

Coding Implement a token bucket in Redis that is safe under concurrency.

A Lua script that reads tokens and timestamp, refills by elapsed time × rate capped at capacity, denies if tokens < cost, otherwise decrements and writes back with a TTL. Scripts execute atomically. Hash-tag keys per tenant for cluster mode. Return a retry-after value derived from the deficit and the rate.

Scenario Finance says your AI costs from the provider are 4% higher than what you billed customers. How do you investigate?

Reconcile by model and day: compare provider usage with our metered tokens. Common causes: cancelled streams not metered, gateway crashes after the upstream call but before emitting (check the WAL spill), internal traffic (evals, staging) on the production key, cache-write tokens not priced, fallbacks to a pricier model billed at the primary's credit rate, or retries billed upstream but metered once. Fix the cause, then backfill adjustments where contractually allowed.

Architecture Why reserve credits before the call instead of charging after?

Because concurrency makes check-then-charge unsafe: many in-flight requests would each see sufficient balance. Reservation makes admission atomic. Settlement corrects the estimate. Expired reservations are reconciled from usage events.

Scenario One tenant's batch job is causing 429s from the provider for everyone. What do you do now, and what do you change?

Now: tighten that tenant's tokens-per-minute bucket via an entitlement override and shed its lowest-priority traffic. Change: per-plan capacity allocation at the gateway, a batch API route for bulk jobs (separate provider limits and cheaper), and shuffle-sharded worker pools. Add an alert on any single tenant exceeding X% of provider capacity.

Conceptual How do you price an AI feature whose cost varies by 100× between requests?

Abstract to credits with published per-model rates; include a credit allowance in seat plans for predictability; meter overage; offer cheaper models and batch modes as explicit choices; protect margins with caps on max_tokens and context size per plan; and watch heavy-tail tenants in a margin dashboard.

Behavioral Describe a time you balanced customer needs against platform safety.

Example structure: an Enterprise customer wanted unlimited throughput for a launch. Instead of removing limits, you provisioned a temporary dedicated capacity route (silo-like routing at the gateway) with its own provider quota, monitored margins, and documented the arrangement in their entitlements. Both the customer and the platform were protected.

16. Knowledge Check

  • One control plane, many data-plane shapes: pool, bridge, silo.
  • Enforce isolation with mechanisms (RLS, scoped credentials, per-tenant keys), not only conventions.
  • The LLM gateway is the choke point for keys, routing, fallbacks, limits and metering.
  • Reserve-then-settle makes budgets safe under concurrency. Token buckets handle rate.
  • Meter from idempotent events, deduplicate with exactly-once processing, keep your own ledger, and reconcile with providers.
  • Price with credits plus hybrid plans, and watch heavy-tail tenants for margin.

Your RLS policy is in place but a query from the app returns other tenants' rows. Most likely cause?

  1. Missing index on tenant_id
  2. Using JdbcClient instead of JPA
  3. The app connects as the table owner or a role with BYPASSRLS, without FORCE ROW LEVEL SECURITY
  4. The policy uses WITH CHECK
Owners and BYPASSRLS roles skip policies unless FORCE is set. Use a dedicated NOBYPASSRLS app role.

Why is the usage topic keyed by tenant ID?

  1. Duplicates of an event and all events of a tenant land in the same partition, enabling local dedupe state and per-tenant ordering
  2. To encrypt events per tenant
  3. Kafka requires string keys
  4. To make billing faster
Partition affinity lets the dedupe store be partition-local and keeps per-tenant aggregates ordered.

A Free tenant fires 50 concurrent requests with a balance for 10. With check-then-charge, what happens?

  1. Exactly 10 succeed
  2. All fail
  3. Redis rejects concurrent reads
  4. Many more than 10 may succeed because each check sees the same positive balance
That is the race that atomic reservation (a Lua script) prevents.

Which identifier should be sent with each meter event to the billing provider?

  1. A random UUID per attempt
  2. A deterministic ID such as tenant:meter:hour, so retries are deduplicated
  3. The provider's request ID
  4. None; providers deduplicate automatically by value
Deterministic identifiers make publication idempotent across retries and restarts.

Where should per-tenant breakdowns for 20,000 tenants live?

  1. As Prometheus labels on every metric
  2. In application logs only
  3. In the usage store and traces (span attributes), with bounded labels in metrics
  4. Nowhere; aggregate only by plan
High-cardinality labels overload time-series databases. Use stores built for per-entity queries.
