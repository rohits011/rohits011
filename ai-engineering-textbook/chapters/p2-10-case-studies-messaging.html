Case Studies I: URL Shortener, Messaging & Notifications

The first nine chapters of Part 2 gave you the parts: load balancers, caches, storage engines, replication, consistency models, Kafka, resilience patterns and multi-region operations. This chapter assembles them into three complete systems, each chosen because it stresses a different axis: a URL shortener (read-dominated, key-generation and cache design), a WhatsApp-class messenger (millions of long-lived connections, ordering, offline delivery and end-to-end encryption), and a notification platform (fan-out to unreliable third parties under priorities, preferences and rate limits).

  • Prerequisites: estimation and SLOs, caching & Redis, sharding, idempotency and outbox, Kafka, circuit breakers.
  • You will be able to: run a full design end to end, from requirements to numbers to APIs to schemas to failure tables; pick and defend an ID-generation scheme; design a stateful WebSocket tier with routing and offline queues; explain what the Signal protocol actually guarantees; and build a notification pipeline that degrades gracefully when a provider goes down.

1. Introduction: Why These Three Systems

Design case studies are often treated as interview theatre: draw five boxes, say "Kafka", add a cache. That is not what this chapter is for. Each of these three systems exists, in some form, inside almost every company you will work for. Marketing teams want tracked short links. Every product with users eventually needs in-app chat or support messaging. And every product, without exception, sends notifications — password resets, order updates, fraud alerts, and the marketing pushes that users love to disable. When these systems are built naively they fail in ways that are both predictable and expensive: the shortener's database melts under a viral link, the chat server loses messages during a deploy, the notification service sends the same OTP five times or sends none during an SMS-provider outage.

The three designs were also chosen because together they cover the main shapes of backend load:

  • URL shortener — a key-value lookup at enormous read amplification (roughly 100 reads per write in our assumptions). The interesting parts are generating short, unique, non-guessable keys without a coordination bottleneck, and absorbing hot keys with layered caches. It is the cleanest possible example of read-path optimisation.
  • Messaging — a stateful system. Unlike the stateless request/response services you build in Spring MVC, a chat gateway holds a live connection per user for hours. That forces you to solve connection routing ("which of 600 servers holds Alice's socket?"), ordering, at-least-once delivery with deduplication, offline storage, presence, and — because users now expect it — end-to-end encryption, which changes what the server is even allowed to see.
  • Notification platform — a fan-out-to-third-parties system. Your reliability is bounded by APNs, FCM, SMS aggregators and email providers you do not control. The design problem is about priorities, idempotency, rate limits, user preferences, retries and provider failover: the classic asynchronous pipeline built on Kafka.

Each design is presented the same way, so you can internalise a repeatable method: requirements, capacity estimation, API, data model, high-level architecture, key flows, component responsibilities, database choices, bottlenecks, failure scenarios, security, trade-offs and an illustrative infrastructure bill. Sections 4 and 5 hold the designs; section 6 collects the estimation maths; section 7 implements the hardest components in Java, Go and Python.

Bridging from Java & Spring Boot

What you already know
You have built Spring Boot services with @RestController, JPA repositories over PostgreSQL or MySQL, Redis via Spring Data or Lettuce, and probably @KafkaListener consumers. You may have used spring-boot-starter-websocket with STOMP for a dashboard, @Scheduled jobs for retries, and Resilience4j for circuit breaking. You know that a @Transactional method gives you atomicity within one database.
Why that is not enough
The default Spring idioms assume stateless instances behind a round-robin load balancer and a single relational database. A chat gateway is not stateless; an in-memory STOMP broker (enableSimpleBroker) works on one node and silently drops messages for users connected to another. A JPA IDENTITY primary key is a single-writer bottleneck when you shard. @Transactional cannot span "write to DB and publish to Kafka". And @Retryable without an idempotency key turns a timeout into a duplicate SMS.
The modern approach
Decentralised ID generation (Snowflake-style or pre-allocated ranges), connection-routing registries, partitioned wide-column stores for append-heavy timelines, transactional outbox into Kafka, priority-separated topics with per-channel worker pools, idempotency keys at every boundary, and provider abstraction with health-based failover. End-to-end encryption moves trust out of the server entirely.
Where Python and Go fit
Go is the natural choice for the connection gateway: goroutines are cheap per-connection, memory per socket is small, and the standard library's networking is excellent. Java with Netty (or Spring WebFlux on Reactor Netty) is equally capable but needs more tuning. Python fits the template rendering, analytics and ML-driven send-time optimisation around the notification platform, and admin tooling — not the hot connection path.
In production
Expect to run a mix: Spring Boot for the business APIs (link management, notification API, preferences), Go or Netty for gateways, Kafka for the spine, Cassandra/ScyllaDB or DynamoDB for message timelines, Redis for presence, rate limits and dedup, and managed providers (APNs, FCM, SES, an SMS aggregator) at the edges.
Use it when / avoid it when
Use these reference designs when you face the same load shape. Avoid copying them at small scale: a shortener for 10,000 links a day is a single PostgreSQL table with a unique index, and a chat feature for an internal tool can be a managed service. The estimation step exists precisely to tell you which regime you are in.

2. History: How These Systems Evolved in Industry

2.1 URL shorteners: from convenience to infrastructure

TinyURL launched in 2002 to solve a mundane problem: long URLs broke when wrapped in plain-text email. The idea exploded with Twitter's 140-character limit after 2006, which made every character in a link costly. bit.ly (2008) turned shortening into an analytics business: each redirect is a measurable click with a timestamp, referrer, user-agent and coarse location. Twitter later built its own wrapper, t.co, so that every outbound link could be checked against malware lists and counted. That arc — utility, then analytics, then security gateway — is why a modern shortener design must include abuse detection and click analytics, not just a key-value map. Shorteners have also shown how fragile link permanence is: Google shut down its goo.gl service for new links in 2019, a reminder that the hardest non-functional requirement is often "this must still redirect in ten years".

2.2 Messaging: from XMPP to Erlang to end-to-end encryption

Instant messaging in the late 1990s (ICQ, AIM, MSN) used proprietary protocols over long-lived TCP connections. XMPP (originally Jabber, standardised by the IETF as RFC 3920 in 2004 and revised as RFC 6120 in 2011) offered an open, federated XML protocol, and many early mobile messengers started from an XMPP server. WhatsApp, founded in 2009, began with a heavily modified ejabberd (an Erlang XMPP server) and then rewrote large parts of it; its engineers' talks at Erlang Factory between 2012 and 2014 became the canonical reference for how a handful of engineers could serve hundreds of millions of users on Erlang/FreeBSD with very high connection counts per server (see §9).

Three shifts defined the 2010s. First, mobile networks made connections intermittent: phones sleep, switch from Wi-Fi to cellular and lose the socket, so store-and-forward and push-notification wake-ups became core. Second, the browser gained WebSocket (RFC 6455, 2011), giving web clients a full-duplex channel instead of long-polling hacks. Third, end-to-end encryption went mainstream: Open Whisper Systems published the protocol now called the Signal protocol (X3DH key agreement plus the Double Ratchet), and WhatsApp announced it had completed rolling it out to all its users in April 2016. After that, a messaging server is increasingly a blind router of ciphertext.

In parallel, team chat (Slack, 2013; Discord, 2015) pushed a different shape: very large channels with long, searchable histories. That drove adoption of wide-column stores for message timelines — Discord's public write-ups moving from MongoDB to Cassandra (2017) and then to ScyllaDB (2023) are the best-known example.

2.3 Notifications: from cron-and-SMTP to platforms

For most of the 2000s "notifications" meant a cron job that ran a SQL query and called an SMTP relay. Apple introduced the Apple Push Notification service with iOS 3 in 2009; Google followed with C2DM (2010), then Google Cloud Messaging (2012), then Firebase Cloud Messaging, which replaced GCM (GCM's server APIs were shut down in 2019). Apple moved APNs to an HTTP/2-based provider API in 2015. Each transition forced companies to rewrite integrations, which is a strong argument for a provider-adapter layer.

As products added channels (push, SMS, email, in-app inbox, later WhatsApp/RCS business messaging) teams discovered that the hard problems were not "send" but "should we send, on which channel, how often, and what happens when it fails". Large companies built centralised platforms — Netflix's Rapid Event Notification System is a published example — and a SaaS market grew around the same need. Regulation tightened the requirements: anti-spam laws such as CAN-SPAM (US, 2003) and the EU's GDPR (in force 2018) made consent, unsubscribe and data-minimisation first-class design constraints.

3. Fundamentals: The Recurring Building Blocks

The three designs share a small set of mechanisms. Learn them once here; §4 and §5 apply them.

3.1 The design method

Every design in this chapter follows the same loop, which you should treat as a checklist:

  1. Functional requirements — the verbs (shorten, redirect, send, receive, mark read).
  2. Non-functional requirements — latency targets (p99, not average), availability (99.9% allows about 43 minutes of downtime per 30-day month; 99.99% about 4.3 minutes), durability, consistency expectations, compliance.
  3. Estimation — QPS (average and peak), storage growth, bandwidth, memory for caches and connections. The point is to discover which resource dominates; see Chapter 2.1.
  4. API and data model — the contract and the access patterns. In wide-column and key-value stores the access pattern is the schema.
  5. High-level architecture, then deep dives on the components that the estimation says are hard.
  6. Failure analysis — for each component: what happens when it is slow, down, or duplicated?

3.2 Unique ID generation

All three systems need identifiers that are unique across many writers: short codes, message IDs, notification IDs. You already know the single-node options — a database sequence or AUTO_INCREMENT — and their weakness: one writer, one point of failure, and IDs that leak business volume. Discord's message IDs are Snowflakes too, which lets it bucket messages by time just by shifting the ID. We implement both Snowflake and base62 in §7.

3.3 Base62 encoding and key-space arithmetic

Base62 uses [0-9a-zA-Z]: URL-safe without escaping. A string of length \(k\) has \(62^k\) values: \(62^6 \approx 5.7 \times 10^{10}\), \(62^7 \approx 3.5 \times 10^{12}\). If you encode a dense counter, a 7-character code lasts a very long time. If you encode a random value, the birthday bound governs collisions: with \(n\) random keys in a space of size \(N\), the probability of at least one collision is approximately \(1 - e^{-n^2/2N}\). We work this through in §6.

3.4 Read-path caching and hot keys

Read-heavy systems are dominated by a few hot keys (Zipf-like popularity). Layering helps: CDN or edge cache for 301/302 responses, an in-process cache (Caffeine) on each app node, a shared Redis tier, and finally the database. The in-process layer is what saves you from a single viral key overloading one Redis shard; see Chapter 2.3 for eviction policies and stampede protection (request coalescing, probabilistic early refresh).

3.5 Long-lived connections: WebSocket, MQTT and friends

HTTP request/response cannot push. The options for server-to-client delivery are:

  • Short polling — wasteful; latency equals poll interval.
  • Long polling — the server holds the request until data arrives; workable but each delivery costs a new request.
  • Server-Sent Events (SSE) — one-way server-to-client stream over HTTP; perfect for token streaming and feeds (used in Chapter 2.12's chatbot).
  • WebSocket (RFC 6455) — full-duplex frames after an HTTP Upgrade; the default for browser chat.
  • MQTT or custom binary over TCP/TLS — common on mobile for compact framing and keep-alive control. Facebook Messenger's mobile client historically used MQTT; WhatsApp uses its own binary protocol.

Stateful connections break the assumption that "any instance can serve any request". You need a session registry mapping userId → (gatewayId, connectionId), and a way to route a message to the right gateway. You also need to handle connection draining during deploys, because killing a gateway disconnects every user on it at once and they will all reconnect in a thundering herd.

3.6 Delivery semantics, acks and idempotency

Across unreliable networks you can only choose between at-most-once and at-least-once delivery; "exactly-once" is at-least-once plus deduplication at the receiver. Every design here therefore uses client-generated idempotency keys (a message's client ID, a notification's dedup key, a create-link request's Idempotency-Key header) and stores "already processed" markers with a TTL. The theory is in Chapter 2.6; here we focus on where to place the keys.

3.7 Fan-out: on write versus on read

When one event must reach many recipients you either fan out on write (copy or enqueue for each recipient at send time — fast reads, expensive writes, bad for huge audiences) or fan out on read (store once, recipients pull — cheap writes, more expensive reads). Messaging uses fan-out on write for small groups and per-recipient delivery queues; very large channels (Discord/Slack style) store once per channel and fan out only to online subscribers. Notifications are fan-out on write by nature, but broadcast campaigns to millions should be expanded lazily in batches rather than materialised at once.

3.8 Asynchronous pipelines with priorities

Kafka topics do not have priorities: a consumer reads a partition in order. Priority is therefore implemented structurally: separate topics (or separate clusters) for critical, normal and bulk traffic, each with its own consumer pool sized for its SLO, so a 50-million-recipient marketing blast cannot delay a password-reset code. Retries go to delay topics (e.g. retry-1m, retry-10m) and finally a dead-letter topic, rather than blocking the partition. See Chapter 2.7 for partitioning and consumer-group mechanics.

3.9 Rate limiting and backpressure

Rate limits appear three times in this chapter: abuse protection on link creation, per-user send limits in chat (spam), and frequency caps plus provider quotas in notifications. The algorithms (token bucket, sliding window) are covered in Chapter 2.2. The design question here is the key: per API key, per user, per (user, channel, category), per provider account.

3.10 End-to-end encryption in one paragraph

Transport encryption (TLS) protects data between client and server; the server still sees plaintext. End-to-end encryption (E2EE) means only the endpoints hold the keys, so a compromised or subpoenaed server reveals ciphertext and metadata only. The Signal protocol achieves this with an asynchronous key agreement (X3DH, so you can start a session with someone who is offline, using keys they pre-published to the server) and the Double Ratchet (a fresh key per message, giving forward secrecy and post-compromise security). The server's role shrinks to: storing public prekeys, routing ciphertext, and holding undelivered ciphertext. §4.2 goes deeper.

4.1 Case study A — URL shortener

Functional requirements

  • Create a short link for a long URL, optionally with a custom alias and an expiry time.
  • Redirect GET /{code} to the long URL.
  • Owners can list, disable and delete their links; see click analytics (counts by day, country, referrer, device).
  • Abuse controls: block malware/phishing destinations, rate-limit creation, allow takedowns.

Non-functional requirements

  • Redirect latency p99 under 50 ms server-side from the nearest region (excluding client RTT).
  • Redirect availability 99.99%: a broken short link in a printed QR code cannot be fixed by the sender.
  • Durability: once acknowledged, a mapping must never be lost or changed to point elsewhere (a hijacked link is a security incident).
  • Codes should not be trivially enumerable (to stop scraping of private links).
  • Analytics may lag by up to a minute; redirect must not wait on analytics.

Data model

Reading the diagram: LINK is the only entity on the redirect hot path, and it is accessed exclusively by primary key code. CLICK_EVENT is an append-only stream that never lives in the same store as links: it goes to Kafka and then to an OLAP store (ClickHouse, Pinot or Druid — see Chapter 2.12). CLICK_ROLLUP is the pre-aggregated table that powers the stats endpoint. A secondary access pattern, "list my links", needs an index on (account_id, created_at).

Database choice. The redirect path is a single-key read at high QPS with no joins and no transactions spanning keys — the textbook fit for a partitioned key-value or wide-column store: DynamoDB, Cassandra/ScyllaDB, or sharded MySQL/PostgreSQL behind Vitess or Citus. Our choice Opinion: DynamoDB or Cassandra for links (partition key code, uniform hash distribution, linear scaling, multi-region replication available), with a global secondary index (DynamoDB) or a separate table links_by_account(account_id, created_at, code) (Cassandra) for owner listings. If your company already runs PostgreSQL well, a hash-sharded PostgreSQL cluster with 64 logical shards is entirely viable at 3,500 writes/s; the redirect reads mostly hit cache anyway.

Key generation — the core algorithm

There are four realistic designs; we compare them and pick one.

  1. Hash and truncate. base62(sha256(longUrl + salt))[0..7]. On collision (code exists with a different URL), append a counter and retry. Pros: stateless. Cons: the insert must be a conditional write (PutItem with attribute_not_exists(code), or Cassandra INSERT ... IF NOT EXISTS, which costs a Paxos round), and collisions rise as the table fills.
  2. Random code with conditional insert. Generate 7 random base62 characters from a CSPRNG; insert-if-absent; retry on conflict. Codes are unguessable. With 1.8 × 10¹¹ keys in 3.5 × 10¹² space, the chance a fresh random code collides is about 5% near end of life — fine with a retry, but every insert still needs a conditional write.
  3. Counter plus base62. A global counter (or range allocation) yields a unique integer; encode it. No collisions, no conditional write needed. But sequential codes are enumerable: aaaaab follows aaaaaa.
  4. Counter plus bijective scrambling. Take the unique counter value and apply a keyed permutation over the 7-character space (for example a small Feistel network or format-preserving encryption) before base62 encoding. Uniqueness is preserved because the permutation is a bijection; output looks random; no conditional write is needed.

We choose option 4 with range allocation: each shortener instance leases a block of, say, 100,000 counter values from a small strongly consistent store (an etcd key, a DynamoDB atomic counter, or a single-row PostgreSQL sequence with INCREMENT BY 100000). It then issues codes locally until the block is exhausted. A crash wastes at most one block — irrelevant in a 3.5 × 10¹² space. The lease store sees ~1 request per 100,000 links, i.e. about one request every 30 seconds across the whole fleet at peak.

Custom aliases bypass the generator and use a conditional insert. To prevent an alias from ever colliding with a generated code, either reserve a disjoint namespace (generated codes are exactly 7 characters; aliases must be 4–6 or 8+ characters, or contain a -) or always use conditional inserts. Deduplication of long URLs

Should two requests to shorten the same URL return the same code? For an anonymous public shortener, yes (saves space); for an analytics product, no — two campaigns want separate click counts. We scope deduplication to (account_id, long_url_hash) with an optional flag, stored in a separate table. Do not make dedup global: it lets one tenant learn that another tenant shortened a given (possibly private) URL.

4.2 Case study B — WhatsApp-class messaging system

Functional requirements

  • 1:1 chat and group chat (up to 1,024 members in our design) with text, emoji reactions and media (images, video, voice notes, documents).
  • Delivery state per message: sent (server accepted), delivered (recipient device received), read.
  • Offline delivery: messages to offline users are held and delivered when they reconnect; push notification wakes the device.
  • Presence ("online", "last seen") and typing indicators, subject to privacy settings.
  • Multi-device: a user may have a phone plus up to four companion devices.
  • End-to-end encryption of message content and media for 1:1 and groups.

Non-functional requirements

  • End-to-end delivery latency p99 under 500 ms when both parties are online in the same region.
  • No message loss once the sender sees "sent"; no duplicates shown to the user.
  • Per-conversation ordering as seen by all participants (we do not require a global order).
  • High availability of the send path (99.99%); presence may degrade first.
  • The server must not be able to read message content (E2EE); metadata minimisation where feasible.
  • Server-side retention: undelivered messages kept up to 30 days, then dropped; delivered messages are not stored on the server in the WhatsApp-style model (history lives on devices and in optional encrypted backups). A Slack/Discord-style product would instead keep full server-side history — we discuss both.

Protocol and API design

Clients keep one persistent connection (WebSocket for web; a compact binary framing over TLS on mobile). Everything on it is a typed frame. REST is used only for bulk or cacheable operations: media upload URLs, prekey bundles, profile and group management.

}

  string client_msg_id = 1;    // UUIDv7 generated on device: idempotency key

The crucial fields are client_msg_id (generated by the sender, so a resend after a dropped connection is recognised as a duplicate) and conv_seq (a per-conversation sequence assigned by the server, which defines the order every participant displays and lets receipts be expressed compactly as "read up to seq 1,042").

Data model

Reading the diagram: there are two message structures and you should understand why. INBOX_ENTRY is a per-device store-and-forward queue: the sender's ciphertext for that device waits there until the device acknowledges it, then it is deleted. This is all a WhatsApp-style E2EE system needs, because history lives on devices. MESSAGE is a per-conversation log keyed by (conv_id, bucket) and clustered by conv_seq; it is what a Slack/Discord-style product needs for server-side history, search (only possible without E2EE, or with client-side indexes) and multi-device sync. The bucket (for example, a 10-day time window derived from the Snowflake ID) caps partition size so that a decade-old busy group does not become a 100 GB partition — the same technique Discord described for Cassandra.

Database choice. Inbox and message tables are append-heavy, partition-local reads ("give me everything after seq N for this conversation/device"), with TTL-based expiry — a strong fit for Cassandra/ScyllaDB (LSM-tree writes, native TTL, tunable consistency) or DynamoDB. User, device and group metadata are small, relational and read-heavy: a sharded MySQL/PostgreSQL or the same wide-column store. Prekeys need an atomic "pop one one-time prekey" operation, which can be a conditional delete in the wide-column store or a small Redis set with SPOP backed by durable storage. The session registry and presence are ephemeral and live in Redis (or in-memory in a dedicated presence service).

Tombstone warning: deleting inbox entries after delivery creates a tombstone per message in Cassandra. If a device's inbox partition receives and deletes millions of entries, reads must scan tombstones until compaction removes them (after gc_grace_seconds). Mitigations: time-bucket inbox partitions ((user_id, device_id, day)) so old buckets are dropped wholesale, use TTLs rather than explicit deletes where possible, and read with a lower bound on the clustering key so the scan starts after the acknowledged position.

Ordering: what the server guarantees

A single sender over a single connection sends in order, but two senders in a group race. We assign conv_seq at a single point per conversation: the conversation's owning chat service shard (conversations are hash-partitioned across chat-service instances, and each instance is the single writer for its conversations, similar to Slack's channel servers). The owner increments the in-memory counter, persists the message with that sequence, then fans out. On owner failover, the new owner reads last_seq from storage (persisted with every write or via a conditional update) before accepting new messages. Clients display by conv_seq and buffer out-of-order arrivals briefly; a gap triggers a "sync from seq N" request.

End-to-end encryption: what the Signal protocol does, at the level a backend engineer needs

The backend never implements the cryptography (clients use libsignal), but it implements the key distribution service and must respect the protocol's assumptions. In brief:

  • Each device holds a long-term identity key pair, a medium-term signed prekey (signed by the identity key, rotated periodically) and a batch of single-use one-time prekeys, and uploads the public halves.
  • To message Bob for the first time, Alice's device fetches Bob's prekey bundle (identity key, signed prekey and signature, and one one-time prekey — which the server must hand out exactly once). X3DH combines several Diffie-Hellman outputs into a shared secret, so Alice can send immediately even though Bob is offline. The Signal project published PQXDH in 2023, adding a post-quantum KEM to this handshake.
  • Thereafter the Double Ratchet derives a new message key for every message, mixing in new DH outputs whenever the direction of conversation changes. Compromise of today's keys does not reveal past messages (forward secrecy) and the session heals after a compromise once new DH ratchet steps occur (post-compromise security).
  • Groups: pairwise-encrypting each message for 1,000 devices is expensive, so WhatsApp's published design uses Sender Keys: each sender distributes a symmetric chain key to each member once (over the pairwise channels), then encrypts each group message once and the server fans out the single ciphertext. The cost moves to membership changes, when sender keys must be rotated.
  • Multi-device: each device is a separate Signal endpoint. The sender encrypts per device, which is why Send.payloads is a list.
  • Media: the sender encrypts the file with a random symmetric key, uploads the ciphertext to blob storage, and sends the key and a hash inside the E2EE message. The blob store and CDN only ever see ciphertext.

Server obligations under E2EE

The server must hand out each one-time prekey at most once (atomically), rate-limit prekey bundle fetches (they are an enumeration and exhaustion vector), alert clients to replenish prekeys when they run low, and notify contacts when a user's identity key changes so clients can show a "security code changed" warning. Server-side features that need plaintext — search, spam classification on content, link previews — must move to the client or be redesigned around metadata.

Presence

Presence is the most write-amplified feature in chat and the first one to degrade. A naive design publishes every online/offline change to every contact: with 200 contacts and frequent mobile reconnects, that is an enormous fan-out for data that nobody is looking at. Practical designs:

  • Store presence as a Redis key presence:{userId} = {status, lastSeen} with a TTL slightly longer than the heartbeat interval (for example a 30 s heartbeat and a 75 s TTL). Absence of the key means offline.
  • Push presence changes only to users who subscribed — i.e. currently have a chat with that user open — and pull "last seen" on demand when a chat opens.
  • Debounce flaps: do not announce "offline" until the TTL expires, which hides network blips.
  • Enforce privacy settings at read time ("last seen: nobody / my contacts").

4.3 Case study C — Multi-channel notification platform

Functional requirements

  • Internal services submit notification requests: a template, a recipient (user ID or segment), variables, a category (e.g. security.otp, order.shipped, marketing.weekly), and an optional idempotency key, schedule time and expiry.
  • Channels: mobile push (APNs, FCM), SMS, email, in-app inbox, and web push. The platform chooses channels based on category policy and user preferences, optionally with fallback ("push, then SMS if not opened in 10 minutes").
  • User preferences per category and channel, quiet hours by user time zone, global unsubscribe; legally required messages (security, transactional) bypass marketing opt-outs but not channel feasibility.
  • Templating with localisation and versioning; preview and test sends.
  • Tracking: accepted, sent to provider, delivered (where providers report it), opened/clicked, bounced, failed; queryable per request.
  • Bulk campaigns to segments of millions, with throttled ramp-up.

Non-functional requirements

  • Priority isolation: P0 (OTP, security alerts) reaches the provider within 2 s p99 regardless of marketing load; P1 (transactional) within 30 s; P2 (marketing) best effort within hours.
  • At-least-once processing internally, with effectively-once sends to users: no duplicate OTPs or duplicate shipping emails.
  • Provider failover: an SMS or email provider outage must not stop P0 traffic.
  • Respect provider rate limits and per-user frequency caps.
  • Compliance: consent records, unsubscribe in one click for email marketing, PII minimisation, audit trail.

Data model

Reading the diagram: CATEGORY is the policy object: it binds a business event type to a priority, a set of permitted channels, whether it can bypass marketing opt-outs, and a frequency cap. The processing pipeline, stage by stage

  1. Accept. The API validates the request, checks the idempotency key (INSERT ... ON CONFLICT DO NOTHING on (caller, idem_key)), writes the notification row and an outbox row in one transaction, and returns 202. A relay (Debezium CDC or a polling publisher) moves outbox rows to the Kafka topic for the category's priority: notif.p0, notif.p1, notif.p2. Scheduled sends go to a scheduler store instead and are released at send_at.
  2. Plan. A planner consumer per priority loads the category policy and the user's preferences, applies opt-outs, quiet hours (P2 is deferred; P0 ignores quiet hours), frequency caps and expiry, resolves device tokens and addresses, and decides the channel plan. It emits one channel task per (notification, channel) to channel topics such as push.p0, sms.p1.
  3. Render. Rendering can happen in the planner or in channel workers. We render in channel workers (closer to the channel-specific format and limits — SMS segment length, push payload limit, email MIME) using cached immutable template versions.
  4. Send. Channel workers check the dedup key (notification_id, channel) with Redis SET NX, acquire a token from the provider's rate limiter, call the provider through an adapter wrapped in timeouts and a circuit breaker, and record the attempt.
  5. Retry or fail over. Retryable errors (timeouts, 429, 5xx) go to delay topics with exponential backoff and jitter; non-retryable errors (invalid token, hard bounce) mark the attempt failed and trigger hygiene (deactivate the token, suppress the address). If the provider's breaker is open, the adapter routes to the secondary provider.
  6. Track. Provider webhooks and app-open events update attempt status, feed analytics, and can trigger escalation rules ("if push not opened in 10 min and category allows, send SMS").

Why dedup needs two layers

The idempotency key at the API stops a caller from creating two notifications. It does nothing about the platform itself sending twice: a channel worker can call APNs, succeed, and crash before committing its Kafka offset; after rebalancing, another worker reprocesses the task. The send-side marker SET dedup:{notificationId}:{channel} 1 NX EX 86400 taken before calling the provider closes most of that window. There is an inherent trade-off: if you set the marker and then crash before calling the provider, the message is never sent (at-most-once for that task). For P0 OTPs a lost message is worse than a duplicate, so we store a state rather than a flag — SENDING with a short TTL (e.g. 60 s), then SENT with a 24 h TTL — and allow reprocessing only after SENDING expires. Some providers also accept an idempotency or client reference that suppresses duplicates on their side; use it where available.

Scaling bottlenecks and how to remove them

  • Hot key (viral link). One code at 50,000 req/s would pin a single Redis shard. L1 in-process caching spreads it across all redirect pods; a short CDN cache (even 5–30 s) removes it almost entirely. For extreme cases, replicate hot keys under suffixed keys (code#0..7) in Redis.

5.2 Messaging — high-level architecture

Reading the diagram: the gateway tier is the only stateful edge. Gateways terminate TLS and the persistent connection, authenticate the device once at connect time, register (userId, deviceId) → gatewayId in the session registry, and forward frames over gRPC. They contain no business logic, which lets you deploy business changes without disconnecting 150 M users. The chat service is partitioned by conversation (consistent hashing over conv_id, membership via a coordination service), and each conversation has exactly one owner at a time that assigns conv_seq. Media never touches the chat path: clients upload encrypted blobs directly to object storage using pre-signed URLs and send only references through chat. Push notifications are a separate asynchronous path, used only to wake offline devices.

Key flow: sending a 1:1 message

Reading the diagram: the ordering of steps 4–6 is the core durability rule — persist before acknowledging the sender. If the chat service crashed after step 6 but before delivery, Bob's device will still find the message in its inbox when it next syncs. Deduplication in step 3 uses client_msg_id (with a short-lived cache of recently seen IDs per conversation); if Alice's connection drops before she sees the ack, her client resends with the same ID and receives the same server_msg_id. Delivery to Bob is at-least-once; Bob's client dedups by server_msg_id. The inbox entry is removed only after the device acknowledges, not after the gateway writes to the socket — a socket write succeeding says nothing about whether the phone processed it. The push for an offline device carries no message content (with E2EE the server has none); it merely wakes the app to connect and sync.

Key flow: reconnect and sync

When a device reconnects (to any gateway), it sends its last acknowledged position. The gateway registers the new session, then asks the inbox service for entries after that position in pages of, say, 100, delivering them before switching to live delivery. A race exists: a live message could arrive while the backlog is being paged. The standard fix is to register the session first (so live messages begin to flow), buffer live messages in the gateway, drain the backlog, then flush the buffer, with the client deduplicating by server_msg_id. Ordering is restored by conv_seq on the client.

Key flow: group message with Sender Keys

Reading the diagram: Sender Keys let the server fan out a single ciphertext. Two optimisations matter at scale. First, batch by gateway: 312 devices might live on 150 gateways, so the chat service sends 150 RPCs each carrying a device list, not 312. Second, write once, reference many: for large groups store the message once in the conversation log and give each device a cursor (read_up_to_seq) rather than copying the payload into 312 inboxes. That is the fan-out-on-read model from §3.7, and it is how channel-oriented products such as Slack and Discord scale to very large channels.

Scaling bottlenecks and how to remove them

  • Reconnect storms. A gateway deploy or crash drops 250 K connections, all of which reconnect within seconds, each performing TLS handshakes, auth and sync. Mitigations: drain gateways gradually (stop accepting, then close connections over minutes with jittered "reconnect" hints), client-side exponential backoff with jitter, TLS session resumption, and rate-limited sync.
  • Hot conversations. A 1,024-member group in heavy use is one owner and one partition. Keep group payloads written once (cursor model), and bucket the log by time.
  • Session registry lookups. 1.5 M deliveries/s means 1.5 M lookups/s; cache device→gateway mappings in the chat service, invalidated by connection-epoch changes.
  • Gateway memory. Per-connection buffers dominate. Use small read buffers, release write buffers when idle, and in Go avoid one goroutine per direction per connection if memory is tight (or accept ~8–16 KB of goroutine stacks per connection).
  • Presence fan-out. Subscription-based and debounced as described in §4.2; shed presence first under load.

Security considerations

  • E2EE key distribution integrity: a malicious or compromised server could hand out its own keys (a man-in-the-middle).   • Metadata: even with E2EE the server sees who talks to whom and when. Minimise logs, shorten retention, and consider sealed-sender-style designs (Signal hides the sender from the server for delivery).
  • Authentication: device-bound credentials (keys generated on device, registration via SMS/phone verification with abuse limits), token rotation, and per-device revocation.
  • Abuse and spam: without content access, rely on metadata signals (send rate, new-account fan-out, report rates) and user reporting (which can include the reported messages, decrypted by the reporting client).
  • Media: pre-signed URLs with short expiry, content-length limits, and scanning only where not E2EE.

WebSocket is universal for web; custom binary protocols save bandwidth and battery on mobile.

5.3 Notification platform — high-level architecture

Reading the diagram: priority is structural — three topics, three consumer groups, and per-channel topics split by priority, each with its own worker pool and autoscaling policy. P0 pools are over-provisioned and never shared with P2. The planner is the only component that knows about users (preferences, caps, quiet hours, device tokens); channel workers know only about channels and providers. That separation keeps provider integrations simple and makes the planner the single place where compliance rules live. Feedback (APNs responses, provider webhooks) flows back through a tracking service that updates attempt status and performs hygiene (invalidating tokens, suppressing bounced addresses).

Key flow: an OTP with provider failover

Reading the diagram: the OTP is accepted durably before any provider call, so the auth service's latency does not depend on the SMS provider. The worker's dedup marker starts as SENDING with a short TTL so that a crash between steps 7 and 12 permits a retry after a minute (preferring a possible duplicate to a lost OTP) while a completed send is protected for a day. Failover is decided per call by the circuit breaker on provider A; when A recovers, the breaker's half-open probes restore it. An expired OTP (past expiresAt) is dropped at any stage — sending a stale code is worse than not sending.

Rate limiting: three different limiters

The platform runs three distinct limiters, and confusing them is a common design error:

  1. Caller quota at the API (per calling service), protecting the platform from a buggy producer looping.
  2. User frequency caps in the planner (e.g. at most 3 marketing pushes per user per day; P0 exempt), a business rule implemented with per-user counters keyed by day.
  3. Provider throughput limits in channel workers (e.g. an SMS account limited to N messages/s per sender ID or per country; APNs and FCM have their own throttles). These are distributed token buckets shared by all workers, typically a Redis Lua script.

What to try: configure a burst similar to a campaign start — a large spike after a quiet period. Observe that the fixed-window limiter admits up to twice the limit across a window boundary, which is exactly how you exceed an SMS provider's per-second limit and start receiving 429s. The token bucket smooths the burst to the refill rate after the initial bucket drains, which is the behaviour you want for provider limits; the sliding-window log is precise but memory-hungry, which is acceptable for per-user caps with small limits but not for 10,000 msg/s provider quotas.

Scaling bottlenecks

  • Campaign expansion. Materialising 50 M notification rows at once floods the database and Kafka. Expand segments in pages (e.g. 10 K users) with a ramp schedule, and do not store a full NOTIFICATION row per marketing recipient — store a campaign row plus per-user attempts.

  • Head-of-line blocking. A slow provider stalls a partition. Use bounded in-flight concurrency per worker with async I/O, and move slow retries to delay topics instead of sleeping in the consumer.

6. Mathematical Foundations: The Estimation Toolkit

System-design arithmetic is not about precision; it is about getting the order of magnitude right so you choose the right architecture. Every number below is an input you will revisit with real telemetry. All worked values are Illustrative.

6.1 Throughput from user behaviour

Intuition: total daily actions spread over 86,400 seconds, then multiplied by a peak factor because traffic is never flat.

\[ \text{QPS}_{\text{avg}} = \frac{\text{DAU} \times a}{86\,400}, \qquad \text{QPS}_{\text{peak}} = k \cdot \text{QPS}_{\text{avg}},\; k \in [2, 5] \]

For messaging: \(500\text{M} \times 40 / 86\,400 \approx 231\text{K/s}\), peak \(\approx 700\text{K/s}\) with \(k = 3\). A useful mental shortcut: 1 million per day ≈ 11.6 per second.

6.2 Fan-out amplification

If a fraction \(g\) of messages goes to groups of average size \(m\), deliveries per send are

\[ D = (1-g)\cdot 1 + g\,(m-1) \]

With \(g = 0.3, m = 20\): \(D = 0.7 + 5.7 = 6.4\). Delivery work, not send work, sizes the chat and inbox tiers. Multiply again by devices per user (multi-device) — at 1.3 devices per user, \(D \approx 8.3\).

6.3 Storage growth

\[ S = N_{\text{per day}} \times s \times 365 \times Y \times RF \]

Shortener: \(10^8 \times 500\,\text{B} \times 365 \times 5 \times 3 \approx 2.7 \times 10^{14}\,\text{B} = 274\,\text{TB}\). Include compaction headroom for LSM stores (often 30–50% free space is recommended during compaction, depending on strategy).

6.4 Key space and collisions (birthday bound)

Intuition: collisions appear far sooner than "when the space is full" because every new key can collide with every existing key — the number of pairs grows quadratically. For \(n\) uniformly random keys in a space of size \(N\):

\[ P(\text{at least one collision}) \approx 1 - e^{-n^2 / (2N)} \]

With \(N = 62^7 \approx 3.52 \times 10^{12}\), a collision becomes 50% likely at only \(n \approx 1.177\sqrt{N} \approx 2.2 \times 10^6\) keys. That is why random codes require a conditional insert: collisions are not rare events you can ignore, they are certain within the first day. What matters operationally is the per-insert collision probability when the table holds \(n\) keys: \(p \approx n/N\). At \(n = 1.8 \times 10^{11}\), \(p \approx 5.1\%\), so the expected number of attempts per insert is \(1/(1-p) \approx 1.05\). A counter-plus-permutation design has \(p = 0\) by construction.

6.5 Little's law for concurrency

Intuition: the number of things "in flight" equals arrival rate times how long each stays.

\[ L = \lambda W \]

Notification workers: \(\lambda = 12\text{K/s}\), provider latency \(W = 300\,\text{ms}\) gives \(L = 3{,}600\) concurrent provider calls. With blocking HTTP clients at 200 threads per pod you need 18 pods just for concurrency; with an async client (or Java 21 virtual threads) a handful of pods suffice and you are bounded by the providers' rate limits instead. Messaging gateways: concurrent connections \(=\) connect rate \(\times\) mean session length — 150 M online users are the \(L\), not an input.

6.6 Retry amplification and backoff

If each attempt fails independently with probability \(p\) and you allow up to \(r\) retries, the expected number of attempts is

\[ E[\text{attempts}] = \sum_{i=0}^{r} p^{i} = \frac{1 - p^{r+1}}{1 - p} \]

At \(p = 0.5\) (a degraded provider) and \(r = 5\), each request costs about 1.97 attempts — nearly doubling load on a provider that is already struggling, which is why retries must be paired with circuit breakers and jittered exponential backoff: \(t_i = \min(t_{\max}, t_0 \cdot 2^{i}) \cdot U(0.5, 1.5)\).

6.7 Availability with failover

Components in series multiply availabilities; redundant alternatives multiply unavailabilities (assuming independent failures, which is optimistic):

\[ A_{\text{series}} = \prod_i A_i, \qquad A_{\text{failover}} = 1 - \prod_j (1 - A_j) \]

Two SMS providers each at 99.5% give \(1 - 0.005^2 = 99.9975\%\) in theory. In practice failures correlate (shared carriers, shared country routes), and failover detection takes time, so measured availability is lower — but still far better than a single provider.

6.8 Connection memory

\[ M_{\text{host}} = C \times (b_{\text{kernel}} + b_{\text{tls}} + b_{\text{app}}) \]

With \(C = 250\text{K}\) and roughly 30 KB per connection, \(M \approx 7.5\,\text{GB}\). Shrinking per-connection application buffers from 16 KB to 4 KB saves 3 GB per host — which across 800 hosts is the difference between needing 64 GB and 32 GB instances.

7.1 Short-code generation: range lease + Feistel permutation + base62

The generator turns a dense, unique counter into a 7-character code that looks random. A balanced Feistel network over 42 bits is a bijection for any round function; cycle-walking (re-applying the permutation until the result falls below \(62^7\)) restricts it to our domain while preserving bijectivity. This is obfuscation against casual enumeration, not cryptography — use a real format-preserving encryption mode (NIST FF1) if codes must resist a determined adversary.

package dev.book.shortener;

import java.util.Objects;

/** Maps a unique counter in [0, 62^7) to a unique, random-looking 7-char base62 code. */
public final class CodeGenerator {
    private static final char[] ALPHABET =
        "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ".toCharArray();
    public static final int LENGTH = 7;
    public static final long DOMAIN = 3_521_614_606_208L;   // 62^7
    private static final int HALF_BITS = 21;                  // 2^42 = 4.4e12 > 62^7
    private static final long HALF_MASK = (1L << HALF_BITS) - 1;

    private final long[] roundKeys;

    public CodeGenerator(long[] roundKeys) {
        Objects.requireNonNull(roundKeys);
        if (roundKeys.length < 4) throw new IllegalArgumentException("use at least 4 rounds");
        this.roundKeys = roundKeys.clone();
    }

    public String encode(long counter) {
        if (counter < 0 || counter >= DOMAIN) throw new IllegalArgumentException("counter out of range");
        long x = counter;
        do { x = permute(x); } while (x >= DOMAIN);   // cycle-walking keeps the map bijective
        return toBase62(x);
    }

    long permute(long x) {
        long left = (x >>> HALF_BITS) & HALF_MASK;
        long right = x & HALF_MASK;
        for (long k : roundKeys) {
            long next = left ^ (mix(right ^ k) & HALF_MASK);
            left = right;
            right = next;
        }
        return (left << HALF_BITS) | right;
    }

    private static long mix(long z) {                 // SplitMix64 finaliser as round function
        z = (z ^ (z >>> 30)) * 0xbf58476d1ce4e5b9L;
        z = (z ^ (z >>> 27)) * 0x94d049bb133111ebL;
        return z ^ (z >>> 31);
    }

    static String toBase62(long v) {
        char[] out = new char[LENGTH];
        for (int i = LENGTH - 1; i >= 0; i--) {
            out[i] = ALPHABET[(int) (v % 62)];
            v /= 62;
        }
        return new String(out);
    }

    public static long fromBase62(String s) {
        long v = 0;
        for (char c : s.toCharArray()) {
            int d = (c >= '0' && c <= '9') ? c - '0'
                  : (c >= 'a' && c <= 'z') ? c - 'a' + 10
                  : (c >= 'A' && c <= 'Z') ? c - 'A' + 36 : -1;
            if (d < 0) throw new IllegalArgumentException("not base62: " + s);
            v = v * 62 + d;
        }
        return v;
    }
}

const (
	alphabet = "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ"
	codeLen  = 7
	Domain   = uint64(3_521_614_606_208) // 62^7
	halfBits = 21
	halfMask = uint64(1)<<halfBits - 1
)

type CodeGenerator struct{ keys []uint64 }

func NewCodeGenerator(keys []uint64) (*CodeGenerator, error) {
	if len(keys) < 4 {
		return nil, errors.New("use at least 4 rounds")
	}
	return &CodeGenerator{keys: append([]uint64(nil), keys...)}, nil
}

func mix(z uint64) uint64 {
	z = (z ^ (z >> 30)) * 0xbf58476d1ce4e5b9
	z = (z ^ (z >> 27)) * 0x94d049bb133111eb
	return z ^ (z >> 31)
}

func (g *CodeGenerator) permute(x uint64) uint64 {
	left, right := (x>>halfBits)&halfMask, x&halfMask
	for _, k := range g.keys {
		left, right = right, left^(mix(right^k)&halfMask)
	}
	return left<<halfBits | right
}

func (g *CodeGenerator) Encode(counter uint64) (string, error) {
	if counter >= Domain {
		return "", errors.New("counter out of range")
	}
	x := g.permute(counter)
	for x >= Domain { // cycle-walk back into [0, 62^7)
		x = g.permute(x)
	}
	var out [codeLen]byte
	for i := codeLen - 1; i >= 0; i-- {
		out[i] = alphabet[x%62]
		x /= 62
	}
	return string(out[:]), nil
}

The counter comes from a leased range. In a Spring Boot service the lease can be a single-row table updated atomically; the returned block is consumed locally with an AtomicLong, and the next lease is fetched in the background when 80% is used.

package dev.book.shortener;

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Component;
import java.util.concurrent.CompletableFuture;
import java.util.concurrent.atomic.AtomicReference;

/** Leases disjoint counter blocks from PostgreSQL. Table: id_range(name text primary key, next_start bigint). */
@Component
public class RangeLease {
    private static final long BLOCK = 100_000;
    private record Block(long start, long end, java.util.concurrent.atomic.AtomicLong next) {}

    private final JdbcTemplate jdbc;
    private final AtomicReference<Block> current = new AtomicReference<>();
    private volatile CompletableFuture<Block> prefetch;

    public RangeLease(JdbcTemplate jdbc) { this.jdbc = jdbc; current.set(lease()); }

    private Block lease() {
        // Single atomic statement: no lost updates even with many pods.
        Long end = jdbc.queryForObject(
            "UPDATE id_range SET next_start = next_start + ? WHERE name = 'links' RETURNING next_start",
            Long.class, BLOCK);
        long start = end - BLOCK;
        return new Block(start, end, new java.util.concurrent.atomic.AtomicLong(start));
    }

    public long next() {
        while (true) {
            Block b = current.get();
            long v = b.next().getAndIncrement();
            if (v < b.end()) {
                if (v - b.start() == (long) (BLOCK * 0.8) && prefetch == null) {
                    prefetch = CompletableFuture.supplyAsync(this::lease);
                }
                return v;
            }
            synchronized (this) {                       // block exhausted: swap in the next one
                if (current.get() == b) {
                    Block nb = (prefetch != null) ? prefetch.join() : lease();
                    prefetch = null;
                    current.set(nb);
                }
            }
        }
    }
}

7.2 Snowflake IDs in Java, Go and Python

Used for message IDs, notification IDs and anywhere you want 64-bit, roughly time-ordered IDs without coordination. Layout: 41 bits of milliseconds since a custom epoch (2025-01-01T00:00:00Z here), 10 bits of worker ID, 12 bits of sequence. The two subtle parts are the per-millisecond sequence overflow (wait for the next millisecond) and clocks moving backwards (NTP step corrections): small regressions are waited out, large ones fail loudly rather than risk duplicates. Worker IDs must be unique — assign them from the Kubernetes StatefulSet ordinal, or lease them from etcd/ZooKeeper with a TTL.

package dev.book.ids;

public final class Snowflake {
    private static final long EPOCH_MS = 1_735_689_600_000L; // 2025-01-01T00:00:00Z
    private static final int WORKER_BITS = 10, SEQ_BITS = 12;
    private static final long MAX_WORKER = (1L << WORKER_BITS) - 1;
    private static final long SEQ_MASK = (1L << SEQ_BITS) - 1;
    private static final long MAX_BACKWARD_MS = 10;

    private final long workerId;
    private long lastMs = -1L;
    private long seq = 0L;

    public Snowflake(long workerId) {
        if (workerId < 0 || workerId > MAX_WORKER) throw new IllegalArgumentException("workerId 0..1023");
        this.workerId = workerId;
    }

    public synchronized long nextId() {
        long now = System.currentTimeMillis();
        if (now < lastMs) {
            if (lastMs - now > MAX_BACKWARD_MS)
                throw new IllegalStateException("clock moved backwards by " + (lastMs - now) + " ms");
            now = waitUntil(lastMs);
        }
        if (now == lastMs) {
            seq = (seq + 1) & SEQ_MASK;
            if (seq == 0) now = waitUntil(lastMs + 1);  // 4096 IDs used this ms
        } else {
            seq = 0;
        }
        lastMs = now;
        return ((now - EPOCH_MS) << (WORKER_BITS + SEQ_BITS)) | (workerId << SEQ_BITS) | seq;
    }

    public static long timestampMs(long id) { return (id >>> (WORKER_BITS + SEQ_BITS)) + EPOCH_MS; }

    private static long waitUntil(long target) {
        long t;
        while ((t = System.currentTimeMillis()) < target) Thread.onSpinWait();
        return t;
    }
}

		time.Sleep(100 * time.Microsecond)

	s.mu.Lock()
	defer s.mu.Unlock()
	now := nowMs()

		if s.lastMs-now > maxBackwardMs {
			return 0, fmt.Errorf("clock moved backwards by %d ms", s.lastMs-now)
		}
		now = waitUntil(s.lastMs)
	}
	if now == s.lastMs {
		s.seq = (s.seq + 1) & seqMask
		if s.seq == 0 {
			now = waitUntil(s.lastMs + 1)
		}
	} else {
		s.seq = 0
	}
	s.lastMs = now
	return (now-epochMs)<<(workerBits+seqBits) | s.workerID<<seqBits | s.seq, nil
}

7.3 The redirect hot path in Spring Boot

A fragment of the redirect service showing the L1 (Caffeine async cache with request coalescing) → L2 (Redis) → store chain, negative caching, and non-blocking click emission. package dev.book.shortener;

import java.util.concurrent.CompletableFuture;
import java.util.concurrent.Executors;

@RestController
public class RedirectController {
    private static final String MISSING = "\u0000";             // negative-cache sentinel
    private final AsyncLoadingCache<String, String> l1;
    private final KafkaTemplate<String, String> kafka;

    public RedirectController(StringRedisTemplate redis, LinkRepository repo,
                              KafkaTemplate<String, String> kafka) {
        this.kafka = kafka;
        this.l1 = Caffeine.newBuilder()
            .maximumSize(500_000)
            .expireAfterWrite(Duration.ofMinutes(5))
            .executor(Executors.newVirtualThreadPerTaskExecutor())
            .buildAsync(code -> {                                  // one load per key per pod
                String cached = redis.opsForValue().get("l:" + code);
                if (cached != null) return cached;
                String target = repo.findActiveTarget(code).orElse(MISSING);
                Duration ttl = target.equals(MISSING) ? Duration.ofSeconds(30)
                                                      : Duration.ofHours(24).plusMinutes((long) (Math.random() * 60));
                redis.opsForValue().set("l:" + code, target, ttl);
                return target;
            });
    }

    @GetMapping("/{code:[0-9A-Za-z_-]{4,30}}")
    public CompletableFuture<ResponseEntity<Void>> redirect(@PathVariable String code,
                                                            @RequestHeader(value = "Referer", required = false) String ref) {
        return l1.get(code).thenApply(target -> {
            if (MISSING.equals(target)) return ResponseEntity.status(HttpStatus.NOT_FOUND).build();
            // fire-and-forget; producer configured with small max.block.ms so a broker outage never blocks here
            kafka.send("clicks", code, code + "|" + System.currentTimeMillis() + "|" + Optional.ofNullable(ref).orElse(""));
            return ResponseEntity.status(HttpStatus.FOUND)
                .location(URI.create(target))
                .header(HttpHeaders.CACHE_CONTROL, "private, max-age=300")
                .build();
        });
    }
}

interface LinkRepository {
    /** Returns the target only if status = ACTIVE and not expired. */
    Optional<String> findActiveTarget(String code);
}

const (
	sessionTTL   = 75 * time.Second
	pingInterval = 30 * time.Second
	writeTimeout = 5 * time.Second
	sendBuffer   = 256 // frames queued per connection before we drop the client
)

type Deliver struct {
	UserID   string          `json:"userId"`
	DeviceID string          `json:"deviceId"`
	Frame    json.RawMessage `json:"frame"`
}

type client struct {
	key  string // userId:deviceId
	conn *websocket.Conn
	send chan []byte
}

type Gateway struct {
	id      string
	rdb     *redis.Client
	mu      sync.RWMutex
	clients map[string]*client
	up      websocket.Upgrader
}

func (g *Gateway) register(ctx context.Context, c *client) {
	g.mu.Lock()
	if old, ok := g.clients[c.key]; ok { // same device reconnected: close the stale socket
		close(old.send)
	}
	g.clients[c.key] = c
	g.mu.Unlock()
	g.rdb.Set(ctx, "session:"+c.key, g.id, sessionTTL)
}

func (g *Gateway) unregister(ctx context.Context, c *client) {
	g.mu.Lock()
	if cur, ok := g.clients[c.key]; ok && cur == c {
		delete(g.clients, c.key)
		close(c.send)
		// only delete the registry entry if it still points at us
		g.rdb.Eval(ctx, `if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end return 0`,
			[]string{"session:" + c.key}, g.id)
	}
	g.mu.Unlock()
}

func (g *Gateway) handleWS(w http.ResponseWriter, r *http.Request) {
	userID, deviceID, ok := authenticate(r) // validate a device-bound token; omitted
	if !ok {
		http.Error(w, "unauthorized", http.StatusUnauthorized)
		return
	}
	conn, err := g.up.Upgrade(w, r, nil)
	if err != nil {
		return
	}
	c := &client{key: userID + ":" + deviceID, conn: conn, send: make(chan []byte, sendBuffer)}
	ctx := context.Background()
	g.register(ctx, c)
	go g.writeLoop(ctx, c)
	g.readLoop(ctx, c) // blocks until the socket closes
	g.unregister(ctx, c)
}

func (g *Gateway) readLoop(ctx context.Context, c *client) {
	defer c.conn.Close()
	c.conn.SetReadLimit(64 << 10)
	c.conn.SetReadDeadline(time.Now().Add(sessionTTL))
	c.conn.SetPongHandler(func(string) error {
		c.conn.SetReadDeadline(time.Now().Add(sessionTTL))
		g.rdb.Expire(ctx, "session:"+c.key, sessionTTL) // heartbeat refreshes the registry
		return nil
	})
	for {
		_, msg, err := c.conn.ReadMessage()
		if err != nil {
			return
		}
		forwardToChatService(c.key, msg) // gRPC to the conversation owner; omitted
	}
}

func (g *Gateway) writeLoop(ctx context.Context, c *client) {
	ticker := time.NewTicker(pingInterval)
	defer ticker.Stop()
	for {
		select {
		case frame, ok := <-c.send:
			if !ok {
				c.conn.Close()
				return
			}
			c.conn.SetWriteDeadline(time.Now().Add(writeTimeout))
			if err := c.conn.WriteMessage(websocket.BinaryMessage, frame); err != nil {
				c.conn.Close()
				return
			}
		case <-ticker.C:
			c.conn.SetWriteDeadline(time.Now().Add(writeTimeout))
			if err := c.conn.WriteMessage(websocket.PingMessage, nil); err != nil {
				c.conn.Close()
				return
			}
		}
	}
}

// consumeRoutes receives deliveries addressed to this gateway and hands them to local sockets.
func (g *Gateway) consumeRoutes(ctx context.Context) {
	sub := g.rdb.Subscribe(ctx, "gw:"+g.id)
	for m := range sub.Channel() {
		var d Deliver
		if err := json.Unmarshal([]byte(m.Payload), &d); err != nil {
			continue
		}
		g.mu.RLock()
		c, ok := g.clients[d.UserID+":"+d.DeviceID]
		if ok {
			select {
			case c.send <- d.Frame:
			default: // slow consumer: drop the connection; the message is still in the inbox
				go c.conn.Close()
			}
		}
		g.mu.RUnlock()
	}
}

	}

}

7.5 Notification channel worker: dedup state, distributed token bucket, provider failover

A Spring Boot Kafka listener for the sms.p0 topic. It applies the SENDING/SENT dedup protocol from §4.3, acquires a provider-rate token from a Redis Lua token bucket, and fails over between providers using Resilience4j circuit breakers. Dependencies: spring-kafka, spring-boot-starter-data-redis, io.github.resilience4j:resilience4j-circuitbreaker 2.x.

package dev.book.notify;

import io.github.resilience4j.circuitbreaker.CallNotPermittedException;
import io.github.resilience4j.circuitbreaker.CircuitBreaker;
import io.github.resilience4j.circuitbreaker.CircuitBreakerConfig;
import org.springframework.data.redis.core.StringRedisTemplate;
import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Component;

import java.time.Duration;
import java.time.Instant;
import java.util.List;

record SmsTask(String notificationId, String phone, String body, Instant expiresAt, int attempt) {}

interface SmsProvider {
    String name();
    String send(SmsTask task) throws ProviderException;   // returns provider message id
}

class ProviderException extends Exception {
    final boolean retryable;
    ProviderException(String msg, boolean retryable) { super(msg); this.retryable = retryable; }
}

@Component
public class SmsWorker {
    private static final DefaultRedisScript<Long> TOKEN_BUCKET = new DefaultRedisScript<>("""
        local cap  = tonumber(ARGV[1])
        local rate = tonumber(ARGV[2])          -- tokens per second
        local t    = redis.call('TIME')
        local now  = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)
        local b    = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
        local tokens = tonumber(b[1]) or cap
        local ts     = tonumber(b[2]) or now
        tokens = math.min(cap, tokens + (now - ts) * rate / 1000)
        local ok = 0
        if tokens >= 1 then tokens = tokens - 1; ok = 1 end
        redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
        redis.call('PEXPIRE', KEYS[1], math.ceil(cap * 1000 / rate) + 1000)
        return ok
        """, Long.class);

    private final StringRedisTemplate redis;
    private final KafkaTemplate<String, SmsTask> kafka;
    private final List<SmsProvider> providers;              // ordered by preference
    private final List<CircuitBreaker> breakers;

    public SmsWorker(StringRedisTemplate redis, KafkaTemplate<String, SmsTask> kafka, List<SmsProvider> providers) {
        this.redis = redis;
        this.kafka = kafka;
        this.providers = providers;
        var cfg = CircuitBreakerConfig.custom()
            .failureRateThreshold(30)
            .slidingWindowSize(50)
            .waitDurationInOpenState(Duration.ofSeconds(20))
            .permittedNumberOfCallsInHalfOpenState(5)
            .build();
        this.breakers = providers.stream().map(p -> CircuitBreaker.of("sms-" + p.name(), cfg)).toList();
    }

    @KafkaListener(topics = "sms.p0", groupId = "sms-workers-p0", concurrency = "8")
    public void onTask(SmsTask task) {
        if (Instant.now().isAfter(task.expiresAt())) return;            // stale OTP: drop
        String key = "dedup:" + task.notificationId() + ":sms";
        Boolean claimed = redis.opsForValue().setIfAbsent(key, "SENDING", Duration.ofSeconds(60));
        if (!Boolean.TRUE.equals(claimed)) return;                      // SENT, or another worker is SENDING

        for (int i = 0; i < providers.size(); i++) {
            SmsProvider p = providers.get(i);
            CircuitBreaker cb = breakers.get(i);
            if (!acquire("rl:sms:" + p.name(), 200, 100)) continue;     // provider quota exhausted: try next
            try {
                String providerId = cb.executeCheckedSupplier(() -> p.send(task));
                redis.opsForValue().set(key, "SENT:" + p.name() + ":" + providerId, Duration.ofHours(24));
                return;
            } catch (CallNotPermittedException open) {
                // breaker open: fall through to next provider
            } catch (ProviderException e) {
                if (!e.retryable) { redis.opsForValue().set(key, "FAILED", Duration.ofHours(24)); return; }
            } catch (Throwable t) {
                // timeouts and unexpected errors count as failures in the breaker; try next provider
            }
        }
        // every provider failed or was throttled: release the claim and schedule a retry
        redis.delete(key);
        int next = task.attempt() + 1;
        String retryTopic = next <= 1 ? "sms.p0.retry-5s" : next <= 3 ? "sms.p0.retry-30s" : "sms.p0.dlq";
        kafka.send(retryTopic, task.notificationId(),
            new SmsTask(task.notificationId(), task.phone(), task.body(), task.expiresAt(), next));
    }

    private boolean acquire(String bucketKey, int capacity, int perSecond) {
        Long ok = redis.execute(TOKEN_BUCKET, List.of(bucketKey), String.valueOf(capacity), String.valueOf(perSecond));
        return ok != null && ok == 1L;
    }
}

What to notice: the retry is published to a delay topic rather than performed with Thread.sleep inside the listener, so one bad message never blocks a partition; the delay-topic consumers simply wait until record.timestamp + delay before re-publishing (Spring Kafka's @RetryableTopic automates this pattern). The worker deletes the SENDING claim before re-queueing so the retry can proceed. Expiry is checked first, because for an OTP lateness is a failure mode, not a success.

8. Real-World Applications

  • Marketing and attribution: branded short domains carry UTM parameters and power campaign dashboards; the click stream joins with conversion data in the warehouse. The same pattern underlies QR codes on packaging and deep links that route to an app if installed.
  • Security gateways: email security products and social platforms rewrite links so that every click passes through a scanner at click time, catching destinations that turned malicious after delivery.
  • In-product messaging: marketplaces (buyer–seller chat), ride-hailing (driver–rider masked chat), healthcare (patient–clinician messaging with retention rules) and customer support (agent chat, now increasingly AI-first, see Chapter 2.12). Most of these need server-side history for dispute resolution and compliance, so they choose the Slack-style model, not E2EE.
  • Real-time collaboration: the gateway-plus-registry pattern is reused for live cursors, multiplayer editing, live sports scores and trading dashboards.
  • Notification platforms sit behind every login (OTP), every order (transactional), every fraud alert and every re-engagement campaign. Increasingly they include ML for send-time optimisation and channel selection, and they are a primary lever on SMS cost.
  • AI-era twist: LLM agents now generate notification content (summaries, digests) and consume chat (support bots). This adds new requirements — content safety checks before send, attribution of AI-generated text, and cost controls — but the delivery machinery in this chapter is unchanged.

9.1 WhatsApp: Erlang, FreeBSD and very dense servers Verified

WhatsApp engineers described their architecture in a series of Erlang Factory talks; Rick Reed's 2014 talk "That's 'Billion' with a 'B': Scaling to the Next Level at WhatsApp" covers how the team scaled an Erlang/FreeBSD backend, the per-server tuning they did, and their use of the Mnesia database for parts of their state. Contemporaneous summaries reported very high concurrent-connection counts per server (over two million TCP connections on a single box was reported in 2012). 9.2 WhatsApp and Signal: end-to-end encryption at scale Verified

WhatsApp's security whitepaper documents its use of the Signal protocol, including prekey bundles, Sender Keys for groups and encrypted media with keys carried inside messages. The Signal project publishes the X3DH, Double Ratchet and PQXDH specifications. These are the primary sources for §4.2. Sources: WhatsApp Encryption Overview (whitepaper), X3DH spec, Double Ratchet spec.

9.3 Discord: storing messages in wide-column stores Verified

Discord's 2017 post explains how it moved message storage from MongoDB to Cassandra with a partition key of (channel_id, bucket), where the bucket is a time window derived from the Snowflake message ID, so partitions stay bounded. Its 2023 follow-up describes migrating to ScyllaDB and placing Rust "data services" in front of the database that coalesce identical concurrent requests — a direct answer to hot partitions in very large channels. Sources: How Discord Stores Billions of Messages, How Discord Stores Trillions of Messages.

9.4 Slack: channel servers on a consistent-hash ring Verified

Slack's engineering blog describes its real-time messaging stack: stateful, in-memory channel servers that own channels via consistent hashing, gateway servers that hold WebSocket connections and subscriptions (deployed in multiple regions near users), and presence servers. Twitter open-sourced Snowflake in 2010 to generate roughly time-ordered 64-bit IDs without a central sequence after moving off MySQL auto-increment. Netflix's Rapid Event Notification System (2022 write-up) delivers server-initiated events to devices. 12. Common Mistakes and Production Failures

  • Using a database auto-increment as the short code. Enumerable, leaks volume, and becomes a single-writer bottleneck when you shard.
  • Hash-and-truncate without collision handling. Two different URLs eventually map to the same code and the second silently overwrites the first — a link now points to someone else's page.
  • Allowing destination edits. A compromised account redirects millions of printed QR codes to phishing.
  • Putting analytics on the redirect path. A synchronous insert per click couples redirect latency to the analytics database.
  • Acknowledging a chat message before persisting it. A crash loses messages the sender believes were sent.
  • Deleting from the inbox on socket write instead of device ack. The phone was backgrounded mid-frame; the message is gone.
  • Ordering messages by device timestamps. Phones have wrong clocks; conversations appear scrambled.
  • Broadcast routing between gateway nodes. O(nodes × messages) work; collapses at scale.
  • Restarting all gateways at once. The reconnect storm overwhelms auth and sync services; the outage is caused by the deploy, not the bug it fixed.
  • Presence fan-out to all contacts. The most expensive feature nobody looks at.
  • Retrying notification sends without idempotency. Five copies of the same OTP; users enter the wrong one.
  • One Kafka topic for all priorities. A marketing campaign delays password resets by an hour.
  • Ignoring provider feedback. Continuing to send to invalid push tokens or hard-bounced email addresses damages sender reputation and can get you throttled.
  • No kill switch. A template bug or producer loop sends millions of wrong messages before anyone can stop it.
  • Unbounded OTP issuance. SMS pumping fraud turns your signup page into someone else's revenue stream.

14. Exercises

Exercise 1 · Foundational

Your shortener must support 2 billion new links per year for 10 years using codes of fixed length drawn from base62. What is the minimum code length if you use a dense counter? What length would you choose for random codes if you want the per-insert collision probability at end of life to stay below 0.1%?

Solution

Total links \(n = 2 \times 10^{10}\). Dense counter: need \(62^k \ge 2 \times 10^{10}\); \(62^5 \approx 9.2 \times 10^8\) is too small, \(62^6 \approx 5.7 \times 10^{10}\) suffices, so 6 characters. Random codes: per-insert collision probability \(\approx n / 62^k \lt 10^{-3}\) requires \(62^k \gt 2 \times 10^{13}\); \(62^7 \approx 3.5 \times 10^{12}\) is not enough, \(62^8 \approx 2.2 \times 10^{14}\) is, so 8 characters. The difference of two characters is the price of not having a coordinator.

Exercise 2 · Intermediate

A single short link goes viral at 80,000 requests/s. Your Redis cluster has 6 shards each comfortable at 100,000 ops/s, and you run 60 redirect pods. Explain what happens with and without the L1 cache, and propose two further mitigations.

Solution

Without L1, all 80 K req/s for one key hit one Redis shard, consuming most of its capacity and starving every other key on that shard (latency rises for unrelated links). With L1 (Caffeine, 5-minute TTL), each pod loads the key once per TTL: 60 loads per 5 minutes — effectively zero. Further mitigations: (1) short CDN caching (Cache-Control: public, max-age=30 for links flagged hot) so most requests never reach origin; (2) hot-key detection (sampling top-N keys in the redirect service) that pins hot keys in L1 with longer TTL; (3) Redis key replication with suffixes for systems without L1.

Exercise 3 · Intermediate

Design the receipt protocol so that a group with 500 members does not generate 500 × 500 read-receipt deliveries when everyone reads a message. What does each client send, what does the server store, and what does each sender see?

Solution

Make receipts cumulative watermarks, not per-message events: each device sends Receipt{conv, read_up_to_seq} at most every few seconds (coalesced). The server stores MEMBERSHIP.read_up_to_seq per member. Senders do not receive every member's receipt in real time; instead the client fetches "read by N of 499" lazily when the sender opens message info, computed as count of members with read_up_to_seq ≥ msg.conv_seq. For 1:1 chats, push the watermark to the peer immediately. This turns O(members²) events into O(members) small updates plus on-demand queries; many products also disable per-member read receipts above a group size threshold.

Exercise 4 · Advanced

Your notification platform must guarantee that a user never receives more than 3 marketing pushes per day across all campaigns, even though 40 planner pods process campaigns concurrently. Design the cap so that it is correct under concurrency, cheap, and does not undercount when a send later fails.

Solution

Use a per-user, per-day counter in Redis keyed by the user's local day: cap:mkt:{userId}:{yyyymmdd}. Reserve atomically with a Lua script: if the counter is below 3, increment and return OK; otherwise reject. Set an expiry of about 48 h. Reserve in the planner (before enqueuing), and on permanent send failure release the reservation with DECR (guarded so it never goes below 0). Because the reservation is atomic in Redis, concurrency across 40 pods is safe. If Redis is unavailable, fail closed for marketing (skip or defer). For analytics truth, also record actual sends; the counter is an admission-control device, not the system of record.

Exercise 5 · Advanced

Gateway hosts are being upgraded. Each holds 250 K connections; your auth service handles 20 K logins/s and your sync service 30 K syncs/s. Design a rollout that keeps both below 50% utilisation, and compute how long upgrading 800 gateways takes.

Solution

Budget: 10 K reconnects/s (50% of the auth capacity, which is the tighter constraint). Draining one gateway by closing connections evenly over 120 s produces ~2 K reconnects/s, so up to 5 gateways can drain concurrently. 800 / 5 = 160 waves × ~3 minutes (2 min drain + restart + health check) ≈ 8 hours. To go faster: support token-based session resumption that skips full auth (cheaper reconnect), let sync resume from the last ack without re-fetching metadata, or add gateway capacity so drained clients spread out. Always add jitter to client reconnect so the arrival rate matches the drain rate.

Exercise 6 · Expert

Your company wants server-side search over chat history and end-to-end encryption. Outline two designs, their security trade-offs, and which one you would ship.

Solution

(1) Client-side index: each device indexes its own decrypted history locally (SQLite FTS); search is local; new devices rebuild the index from an encrypted backup. Strong privacy; costs device storage and complicates multi-device. (2) Searchable encryption / encrypted server index: clients upload encrypted index tokens (e.g. keyed hashes of terms); the server matches tokens without seeing terms. Leaks access patterns and term frequencies, which is a known weakness of such schemes. (3) Escrow or enterprise key management (compliance products) — not E2EE in the consumer sense. For a consumer product, ship (1) Opinion; for regulated enterprise chat, be honest that compliance access means the provider or the customer's admin holds keys.

15. Interview Questions and Answers

Conceptual Why do most analytics-focused URL shorteners return 302 rather than 301?

Browsers may cache a 301 indefinitely, so subsequent clicks never reach the shortener: no click analytics, no ability to disable a link for abuse, no expiry. A 302/307 keeps every click observable at the cost of more traffic. Pure character-saving shorteners can use 301 with an explicit Cache-Control limit.

Architecture How do you generate unique short codes across 100 stateless pods without a per-request database round trip?

Range allocation: each pod leases a block of counter values from a linearizable store and issues codes locally, prefetching the next block before exhaustion. To make codes non-sequential, apply a keyed bijective permutation (Feistel with cycle-walking, or FF1) before base62 encoding. Alternative: random codes with a conditional insert, which needs no coordinator but costs a conditional write per create.

Architecture How does a message reach a user whose WebSocket is on a different server from the sender's?

The receiver's gateway registers (user, device) → gateway in a session registry on connect, refreshed by heartbeats. The chat service owning the conversation looks up the recipient devices, groups them by gateway and sends targeted RPCs. Offline devices are served from their persisted inbox on reconnect, plus a wake-up push. Broadcasting to all gateways does not scale.

Conceptual What does the server know in a Signal-protocol messenger, and what does it not know?

It knows metadata — who is registered, public keys, which device sends to which, timing, sizes, IP addresses (unless mitigated) — and holds undelivered ciphertext. It does not know message content, media content (blobs are encrypted with keys inside the messages), or past message keys. Its integrity matters for key distribution: a malicious server could substitute keys, which safety-number verification and key transparency are designed to detect.

Scenario Users report that some messages appear only after they reopen the app. Where do you look?

Suspects in order: (1) session registry pointing at a stale gateway (race on reconnect; check compare-and-delete and epochs); (2) gateway dropping frames for slow consumers without closing the connection; (3) inbox entries deleted on socket write rather than device ack; (4) live/backlog race during sync; (5) push wake-ups failing (invalid tokens) so the app only syncs on open. Instrument per-message traces: accepted → persisted → routed → written → acked.

Architecture How do you prevent a marketing campaign from delaying OTP delivery in a Kafka-based notification system?

Kafka has no priority within a partition, so isolate structurally: separate topics per priority (and per channel), separate consumer groups and worker pools, separate provider rate-limit budgets (reserve a share of SMS throughput for P0), and ideally separate provider accounts or sender IDs. Monitor lag per priority with P0 alerts at seconds.

Coding Write the core of a Snowflake generator and explain its two edge cases.

See §7.2. Edge cases: (1) sequence overflow within a millisecond — spin until the next millisecond; (2) clock moving backwards — wait if the regression is small, otherwise refuse to generate (or switch to a reserved worker ID) rather than risk duplicate IDs. Also mention worker-ID uniqueness (StatefulSet ordinal or leased from etcd).

Scenario Your primary SMS provider's success rate in one country drops from 98% to 40%. What should happen automatically, and what manually?

Automatically: the per-provider (ideally per provider-and-country) circuit breaker opens and traffic fails over to the secondary; retries use backoff; alerting fires on success-rate SLI. Manually: confirm with the provider, adjust routing tables per country, watch the secondary's rate limits and cost, and decide whether to fall back to voice OTP or email for affected users. Post-incident: was the breaker keyed finely enough? A global breaker would have either not tripped (other countries fine) or failed over everything.

Conceptual Why is "exactly-once delivery" of notifications impossible, and what do you build instead?

Because the provider call and your bookkeeping cannot be atomic: a crash between "provider accepted" and "recorded as sent" leaves you unable to know whether to resend. You build at-least-once processing with deduplication: idempotency keys at the API, send-side dedup state with TTLs, provider-side idempotency references where offered, and per-category choice of whether to err towards duplicates or omissions.

Behavioral Tell me about a time a deploy caused an outage. How would you design to prevent it?

A strong answer describes a concrete incident (for example, restarting all instances of a stateful service at once causing a reconnect storm), the blast radius, the detection signal, the mitigation, and the systemic fix: progressive rollout with automated canary analysis, drain logic with jitter, capacity headroom for reconnects, and a runbook. Emphasise blameless analysis and the guardrail added, not individual fault.

16. Knowledge Check

  • Estimate first: it tells you whether the hard problem is QPS, storage, connections, bandwidth, or third-party limits.
  • Short codes: dense counter plus a bijective permutation avoids both collisions and enumeration; random codes need conditional inserts because of the birthday bound.
  • Read-heavy systems live or die by layered caches; in-process L1 is the defence against hot keys.
  • Stateful gateways need a session registry, targeted routing, device-level acks, and careful drain/reconnect engineering.
  • Persist before acknowledging; delete from inboxes only after device acknowledgement; order by server-assigned sequence numbers.
  • Under E2EE the server becomes a key directory and ciphertext router; Sender Keys make group fan-out efficient.
  • Notification priority must be structural (separate topics and pools); dedup needs two layers (API idempotency and send-side state).
  • Provider failover plus fine-grained circuit breakers turn vendor outages into degraded latency rather than lost OTPs.

With 7-character random base62 codes (≈3.5 × 10¹² possibilities), roughly when does the probability of at least one collision reach 50%?

  1. After about 1.75 × 10¹² codes (half the space)
  2. After about 3.5 × 10¹¹ codes (10% of the space)
  3. After about 2.2 million codes
  4. Never, if a CSPRNG is used
The birthday bound puts the 50% point at about 1.18 × √N ≈ 2.2 × 10⁶. A CSPRNG makes codes unpredictable, not collision-free; random-code designs therefore need conditional inserts.

When should a chat server remove a message from a recipient device's inbox?

  1. As soon as the gateway writes the frame to the socket
  2. When the recipient device sends an acknowledgement for that message
  3. When the sender receives the delivered receipt
  4. After a fixed 24-hour TTL regardless of delivery
A successful socket write does not mean the app processed the message (it may be backgrounded or killed). Only the device's ack proves receipt. TTLs are a backstop for devices that never return.

Why do large-group E2EE messengers commonly use Sender Keys?

  1. They provide stronger post-compromise security than pairwise ratchets
  2. They let the server read group messages for moderation
  3. They remove the need for prekeys
  4. The sender encrypts each message once and the server fans out one ciphertext, instead of encrypting per recipient device
Sender Keys trade some post-compromise security (until rotation) for O(1) encryption per message. Distribution of the sender key itself still uses pairwise Signal sessions.

A notification system uses one Kafka topic for all priorities with a "priority" field in each message. What is the main problem?

  1. Consumers read partitions in order, so a backlog of bulk messages delays urgent ones behind them
  2. Kafka rejects messages with custom fields
  3. Messages with higher priority are compacted away
  4. Consumer groups cannot be scaled beyond one consumer
Kafka has no intra-partition priority. Isolation requires separate topics and consumer pools (and separate provider budgets).

Two SMS providers each have 99.5% availability. Why is the real availability of a failover pair usually lower than the theoretical 99.9975%?

  1. Because availabilities in parallel are added, not multiplied
  2. Because the circuit breaker always reduces availability
  3. Because failures correlate (shared carriers/routes) and detection plus failover takes time
  4. Because the formula only applies to databases
The parallel formula assumes independent failures and instantaneous failover. Shared downstream dependencies and breaker detection windows erode both assumptions.

In the gateway code, why does unregister delete the session registry entry only if it still contains this gateway's ID?

  1. To save a Redis round trip
  2. Because the device may already have reconnected to another gateway, and an unconditional delete would erase the new registration
  3. Because Redis does not support DEL inside Lua
  4. To keep presence status "online" longer
Reconnect races are common on mobile networks. Compare-and-delete (or epoch-based fencing) ensures stale gateways cannot clobber newer sessions.
