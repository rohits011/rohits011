Bridging from Java & Spring Boot

What you already know
You have built workflow-style systems before: Spring Batch jobs with restartable steps, Spring State Machine or Camunda/Temporal processes with persisted state, sagas with compensations, Resilience4j around flaky HTTP clients, and @Async or Kafka for long-running work. You have integrated services across languages over REST and gRPC, and secured them with OAuth2 client credentials or mTLS.
Why that is not enough
In a classic workflow engine, you write the control flow. In an agent, the model chooses the next step at runtime, so the set of possible executions is open-ended. You cannot enumerate paths in tests. You must instead bound them with budgets, allow-lists, approval gates and idempotent tools, and you must evaluate behaviour statistically. Code assistants add a second twist: the artefact is code that must be executed to be trusted, so you need an isolated sandbox.
The modern approach
Treat an agent as a durable workflow whose step-selection function is a model. Persist state after every step, and make every tool idempotent and typed. Put policy and approval outside the model. Expose tools through a registry, either in-process (@Tool) or out of process via MCP. For integrations, keep the LLM behind a typed Java interface, with structured output to records, timeouts, fallbacks and Micrometer observations, so the rest of the codebase does not know or care that a model is involved.
Where Python and Go fit
Python hosts the ML-heavy parts: tree-sitter indexing at scale, embedding and reranking models, vLLM-served open models and the evaluation harnesses. Go suits sandbox supervisors and lightweight MCP servers that wrap internal CLIs. Spring Boot owns the business APIs, transactions, security context and integration with existing domain services.
In production
You will operate an agent runtime with a database of runs and steps, a queue of pending approvals, a sandbox pool (gVisor or Firecracker-backed containers), per-tenant budgets and a trace for every run. The Spring Boot integrations look like any other dependency on dashboards: latency, error rate, token usage and cost per endpoint.
Use it when / avoid it when
Use agents when the task truly needs open-ended exploration (unknown codebase, unknown number of lookups). Prefer a fixed workflow with one or two LLM calls when the steps are known. That is cheaper, faster and testable, and most "agent" requests in enterprises are really workflows. Avoid autonomous execution for irreversible actions without approval.

2. History: From Autocomplete to Agents, and from Model Servers to AI Microservices

2.1 Code assistance

IDE code completion based on static analysis (symbol tables, type inference) has existed since the 1990s. Microsoft shipped IntelliSense in Visual Studio in the late 1990s, and JetBrains IDEs made deep, type-aware completion the Java norm in the 2000s. Statistical completion arrived in the late 2010s with language models trained on code. OpenAI's Codex paper (2021) and the GitHub Copilot technical preview (June 2021) made multi-line generation mainstream. Copilot's 2023 engineering posts (see §9) show the shift of attention to context assembly: which snippets from neighbouring files to include in a limited prompt.

From 2023, evaluation moved from "does the completion compile" to "does the change fix a real issue". SWE-bench (Jimenez et al., 2023) gave models real GitHub issues from Python repositories and graded them by running the repository's tests. That framing (issue in, patch out, tests decide) is exactly the P4 architecture. Agentic coding tools that read files, run commands and iterate on test failures became widespread products in 2024–2026.

2.2 Agents

The ReAct paper (Yao et al., 2022) popularised interleaving reasoning and tool actions. Early open-source "autonomous agents" in 2023 showed both the promise and the failure modes: loops, runaway cost, compounding errors. Model providers then added native tool calling and parallel tool calls, and frameworks such as LangGraph (2024) modelled agents as explicit graphs with persisted state. Anthropic's "Building effective agents" (December 2024) argued for simple, composable workflow patterns before autonomous agents. Anthropic introduced the Model Context Protocol (MCP) in November 2024 as an open standard for connecting models to tools and data. MCP has since moved through several specification revisions, including 2025-11-25, which Spring AI 2.0's MCP Java SDK implements, and has become the de facto way to expose tools across vendors.

2.3 LLMs in Java and model serving in Python

Java teams first called model APIs with raw HTTP clients. LangChain4j (2023) and Spring AI (1.0 GA in May 2025; 2.0 on Spring Boot 4 in June 2026) brought idiomatic abstractions: chat clients, advisors, structured output, tool calling and vector stores. Meanwhile, model serving matured on the Python side: TensorFlow Serving (2016), TorchServe and NVIDIA Triton, then LLM-specific engines such as vLLM (2023, PagedAttention) with OpenAI-compatible endpoints. gRPC (open-sourced by Google in 2015) and Kafka became the standard glue between a Java core and Python ML services. P8 follows that well-trodden path.

4. Internals: Component Design and Key Flows

4.1 P4 — Indexing a repository

Code is not prose, and chunking it by token count cuts methods in half. The indexer parses each file with tree-sitter, an incremental parser with grammars for most languages that produces a concrete syntax tree even for files with syntax errors. From the tree it extracts:

  • Symbols: fully qualified name, kind, signature, docstring or Javadoc, byte span, and enclosing symbol. One code chunk per method or function. Small classes are kept whole, and large classes get a "skeleton" chunk (fields plus method signatures, without bodies).
  • References: identifiers used inside each symbol body, resolved heuristically by name and imports. This gives an approximate call graph without a full compiler. For Java you can upgrade to precise resolution with an LSP server (Eclipse JDT LS) or SCIP indexers where available.
  • File metadata: path, language, test or production, last commit, and churn (how often the file changes). Frequently changed files are more likely to be relevant to new issues.

Each chunk is stored three ways: as text for lexical search (identifiers split by camelCase and snake_case, so getOrderTotal matches "order total"), as a code-embedding vector, and as a node in the symbol graph. Incremental indexing uses the git diff: only changed files are re-parsed, and symbols whose content hash is unchanged keep their embeddings.

4.2 P4 — Context assembly

Given a task, the assembler must choose maybe 30–60K tokens from a repository of millions. The algorithm is a scored knapsack:

  1. Seed retrieval: hybrid search over chunks with the issue text, plus exact matches for identifiers, file paths and stack-trace frames found in the issue. Stack traces are gold. A frame OrderService.java:142 pins the exact method.
  2. Graph expansion: add callers and callees of seed symbols (1 hop), the tests that reference them, and the interfaces they implement.
  3. Scoring: \(s = w_1\,\text{retrieval} + w_2\,\text{graph proximity} + w_3\,\text{test relevance} + w_4\,\text{churn}\).
  4. Packing: fill the budget greedily by score per token. Large symbols degrade to skeletons, and a repo map (a tree of paths with one-line summaries of key files) is always included so the model can ask for more.
  5. On-demand tools: the model also gets read_file, search_code and list_dir tools, so it can fetch what the assembler missed. The assembler does not need to be perfect, only to give a good start.

4.3 P4 — The edit–test loop

Reading the diagram: the sandbox is created before the loop from a pre-built image that has the dependency cache warmed, because downloading Maven dependencies inside a no-network sandbox is impossible and slow even with network. Test output fed back to the model is trimmed: failing test names, assertion messages and the top stack frames, not 5,000 lines of Gradle output, which would waste context and confuse the model. Targeted tests (those that reference changed symbols, from the index) run inside the loop, and the full affected suite runs once at the end. The PR is always a draft. The merge decision belongs to a human reviewer.

Edits as search/replace, not whole files

Asking the model to rewrite whole files wastes output tokens and invites accidental deletions far from the change. Search/replace blocks (an exact old snippet and its replacement) or unified diffs are cheaper and easier to review. When an old snippet does not match exactly, return a precise error ("snippet not found; closest match at line 120") rather than fuzzy-applying it.

4.4 P5 — Agent runtime: planner, executor, state

The agent runtime is a durable state machine. A run has a goal, a plan, a budget, a status and an append-only list of steps. The executor loop is:

  1. Load the run and its steps. If status is WAITING_APPROVAL or DONE, stop.
  2. Check the budget (steps, tokens, cost, deadline). If exhausted, set BUDGET_EXHAUSTED and produce a partial report.
  3. Call the model with goal, plan, step history (compacted) and the available tool schemas. It returns either tool calls, a plan revision or a final answer.
  4. For each tool call: validate the arguments against the schema, check policy (risk level, tenant permissions, rate), and if approval is required, persist an approval_request, set WAITING_APPROVAL and stop. Otherwise execute with an idempotency key runId:stepNo:toolCallId and retry with backoff on retryable errors.
  5. Persist the step (model output, tool inputs and outputs, tokens, latency) in the same transaction as the budget counters. Loop.

Reading the diagram: waiting for approval is a first-class state, not a blocked thread. The worker releases the run and a later event (the approval decision) re-enqueues it. Because of that, a run can wait days without holding resources, and a deploy in between is harmless. Rejection leads to re-planning, not failure: the model is told "the user rejected sending this email because X" and can propose an alternative. Terminal states are explicit, so dashboards can count each outcome.

Plan-and-execute versus pure ReAct. A pure ReAct loop decides each step only from the history so far. Plan-and-execute first writes an explicit plan, which (a) can be shown to the user and approved as a whole, (b) gives the executor a checklist, which reduces wandering, and (c) lets a cheaper model execute simple steps while a stronger model plans. The cost is rigidity, which re-planning on failure mitigates. The runtime supports both: the plan is advisory, and the model may revise it with a revise_plan pseudo-tool.

4.5 P5 — Tool registry and MCP

Tools come from two places. In-process tools are Java or Python functions with schemas. MCP servers are remote processes exposing tools over Streamable HTTP, which became the default MCP transport in Spring AI 2.0, replacing the deprecated SSE transport Version-sensitive · checked Nov 2026. The registry stores, per tool: the name, schema, description, risk level, owner team, rate limit, the tenants allowed to use it and, for MCP, the server URL and the auth method (OAuth 2.1 as specified by MCP for HTTP transports). At run start, the runtime builds the tool list from the registry filtered by tenant and user permissions. The model never sees tools the user could not use.

MCP servers are third-party code paths

An MCP server's tool descriptions are injected into your model's context, and its tool results are untrusted input. Pin server versions, review descriptions on registration (diff them on every update to catch "tool poisoning"), run third-party servers in isolated network segments, and never forward the user's broad tokens to a server that does not need them. See 8.6 and 11.5.

4.6 P7 — Inside a Spring AI call

Reading the diagram: in Spring AI 2.0, the tool-call loop moved out of each model implementation into the advisor chain as an auto-registered ToolCallingAdvisor Version-sensitive · checked Nov 2026. Advisors are Spring's interceptor idea applied to model calls: they can modify requests (add memory, retrieved context), re-enter the chain (structured output retries) and observe responses (metrics, logging). The tool method is a plain method on a Spring bean, so it runs with your transaction management, method security and caching. That is the main advantage over hand-rolled HTTP integrations. Note the security implication: the tool runs as the calling user only if you propagate the security context into the thread that executes it. With reactive streaming, make that explicit (§7.7).

4.7 P8 — Java ↔ Python request paths

Reading the diagram: two identities are in play. The workload identity (SPIFFE ID in the mTLS certificate) answers "which service is calling". The user identity (a short-lived JWT, audience-restricted to ai-service) answers "on whose behalf", which the RAG endpoint needs for ACL filtering. gRPC deadlines propagate, so the Python service can abandon work the caller no longer wants. The async path uses the tenant as the message key, which preserves ordering per tenant and spreads load. Results are keyed by jobId so redelivery overwrites rather than duplicates.

5. Architecture: Diagrams and Technology Selection

5.1 P4 — Coding assistant architecture

Reading the diagram: the orchestrator is the only component that talks to the sandbox pool, and the sandboxes have no route back to the control plane or the internet. Pushes trigger both re-indexing and an image refresh (dependency cache warm-up), so sandboxes start in seconds. The git host token used to open PRs lives only in the orchestrator, never in a sandbox, so code generated by the model cannot exfiltrate it even if it tries.

5.2 P5 — Agent runtime architecture

Reading the diagram: executors are stateless. Any worker can pick up any ready run from Kafka (keyed by run ID for ordering), load its state from PostgreSQL and take one or more steps. Approval decisions come back through the API and re-publish run.ready. The policy engine is consulted before every tool call, so changing a risk threshold is a policy deploy, not a code deploy. If you prefer not to build the runtime yourself, Temporal, LangGraph with a Postgres checkpointer, and hosted agent platforms provide the durable-execution part. The design concerns (budgets, approval, idempotency) stay the same.

5.3 P7 and P8 — Integration architecture

Reading the diagram: the Java service talks to two kinds of AI dependency: a hosted frontier model via the LLM gateway (for generation and tools), and the in-house Python service (for embeddings, reranking and a fine-tuned classifier). Both go through Resilience4j. The AI features call existing domain beans and never the reverse, so the domain does not depend on AI. The Python service exposes the same models through gRPC (for Java) and REST (for humans and notebooks) behind one batcher, so both paths share GPU batching.

6. Math: Cost, Reliability and Capacity

All figures are Illustrative. Prices assume Claude Opus 5.5 at $4 / $20, Sonnet 5.5 at $2 / $10 and Haiku 5.5 at $0.10 / $0.50 per million input and output tokens, with cache reads at a small fraction of the input price Version-sensitive · checked Nov 2026.

6.1 Agent loops have quadratic token cost (P4, P5)

Intuition: each step re-sends the whole conversation so far. If the first request has \(C_0\) tokens and each step appends \(\Delta\) tokens (tool call plus result), then step \(i\) sends \(C_0 + i\Delta\), and \(n\) steps send

\[ T_{\text{in}}(n) = \sum_{i=0}^{n-1} (C_0 + i\Delta) = nC_0 + \Delta\frac{n(n-1)}{2}. \]

For P4 with \(C_0 = 40{,}000\) (assembled context), \(\Delta = 3{,}000\) (edits plus trimmed test output) and \(n = 12\) steps: \(T_{\text{in}} = 480{,}000 + 3{,}000 \cdot 66 = 678{,}000\) tokens. On Sonnet 5.5 with no caching that is about $1.36 of input, plus about 12 × 1,500 output tokens = $0.18, so about $1.54 per task. With prompt caching, everything except the newest \(\Delta\) is a cache read. The input cost then approaches \(n\Delta\) at full price plus the rest at the cache-read price, roughly a 5× reduction here. Two practical rules follow: keep the prefix stable (do not edit earlier messages; append) so caching works, and trim tool results, because \(\Delta\) enters the quadratic term.

6.2 Compounding step reliability (P5)

If each step independently succeeds with probability \(p\), a run needing \(n\) correct steps succeeds with \(p^n\). With \(p = 0.97\): \(n=5 \Rightarrow 0.86\), \(n=15 \Rightarrow 0.63\), \(n=30 \Rightarrow 0.40\). Steps are not really independent, and agents can notice and fix their own mistakes, which raises effective \(p\). Even so, the shape explains three design choices: shorter plans, verification steps after risky actions (a check raises \(p\) for the steps that follow), and narrowly scoped tools that are hard to misuse.

With retries on transient tool errors (probability \(q\) per attempt, up to \(r\) retries), a tool's effective success rate is \(1 - q^{r+1}\). With \(q = 0.05\) and \(r = 2\), that is 0.999875. Retries make infrastructure failures negligible but do nothing for reasoning failures, which need re-planning or a human.

6.3 Budget enforcement (P5)

Enforce the budget before each call using a worst-case estimate: \(\hat{c}_{\text{next}} = T_{\text{ctx}} \cdot p_{\text{in}} + T_{\max} \cdot p_{\text{out}}\). Stop if \(c_{\text{spent}} + \hat{c}_{\text{next}} > B\). This guarantees the hard cap \(B\) is never exceeded, at the price of sometimes stopping a little early. Models that support a server-side task budget (a token ceiling the model sees and paces itself against) complement this. The model then wraps up instead of being cut off mid-thought, while your check remains the hard limit.

6.4 Concurrency for streaming endpoints (P7)

Little's law, \(L = \lambda W\): at 50 assistant requests per second and an 8 s mean stream duration, there are 400 concurrent streams. On a classic Spring MVC thread-per-request model with a 200-thread pool, that saturates the pool, and every other endpoint queues behind LLM streams. Options: (a) WebFlux for the streaming endpoints, where 400 idle streams cost little; (b) Spring MVC with virtual threads (spring.threads.virtual.enabled=true), where 400 blocked virtual threads are cheap; (c) a Resilience4j Bulkhead capping AI concurrency at, say, 300, so overflow fails fast with a 503 rather than starving the service. Use (b) or (a) together with (c).

6.5 GPU and Kafka capacity (P8)

Reranker throughput: if one batch of 32 (query, document) pairs takes 25 ms on a GPU, one replica handles about \(32 / 0.025 = 1{,}280\) pairs/s. At a peak of 400 rerank requests/s × 50 candidates = 20,000 pairs/s, you need \(\lceil 20{,}000 / 1{,}280 \rceil = 16\) replica-GPUs at 100% utilisation. At a 70% target, \(16 / 0.7 \approx 23\). That cost is why P8 reranks 50 candidates, not 200, and why the Java side caches rerank results for repeated queries.

Kafka partitions for the job topic: if one worker processes 4 documents/s (GPU-bound) and the target is 2,000 documents/s during backfills, you need 500 consumer instances. That is impractical, so batch inside the worker (64 documents per GPU call → about 100 documents/s per worker) and plan 24–32 partitions with 20 workers. The partition count caps consumer parallelism, so size it for peak plus headroom, since increasing it later reshuffles keys.

7.2 P4 — Indexing with tree-sitter

"""Extract symbol-level chunks from source files with tree-sitter.

Uses py-tree-sitter >= 0.23 with per-language wheels (tree-sitter-java, tree-sitter-python, ...).
The Query API changed across versions, so this walks the tree directly. Version-sensitive.
"""
from __future__ import annotations

import hashlib
import re
from dataclasses import dataclass, field

import tree_sitter_go as tsgo
import tree_sitter_java as tsjava
import tree_sitter_python as tspython
from tree_sitter import Language, Node, Parser

LANGS = {
    ".java": (Language(tsjava.language()), {"class_declaration", "interface_declaration",
                                            "method_declaration", "constructor_declaration"}),
    ".py": (Language(tspython.language()), {"class_definition", "function_definition"}),
    ".go": (Language(tsgo.language()), {"function_declaration", "method_declaration", "type_declaration"}),
}
IDENT = re.compile(r"[A-Za-z_][A-Za-z0-9_]{2,}")


@dataclass
class Symbol:
    path: str
    kind: str
    name: str
    qualified: str
    start_line: int
    end_line: int
    text: str
    refs: set[str] = field(default_factory=set)
    is_test: bool = False

    @property
    def content_hash(self) -> str:
        return hashlib.sha256(self.text.encode()).hexdigest()

    def search_text(self) -> str:
        """Identifier-split text so 'getOrderTotal' matches 'order total'."""
        split = re.sub(r"([a-z])([A-Z])", r"\1 \2", self.text).replace("_", " ")
        return f"{self.qualified}\n{split}"


def _name(node: Node, src: bytes) -> str:
    n = node.child_by_field_name("name")
    return src[n.start_byte:n.end_byte].decode() if n else "<anon>"


def extract(path: str, src: bytes, max_symbol_lines: int = 200) -> list[Symbol]:
    ext = path[path.rfind("."):]
    if ext not in LANGS:
        return []
    lang, kinds = LANGS[ext]
    tree = Parser(lang).parse(src)
    out: list[Symbol] = []
    is_test = "/test" in path or path.endswith(("_test.go", "Test.java")) or "/tests/" in path

    def walk(node: Node, scope: list[str]) -> None:
        if node.type in kinds:
            name = _name(node, src)
            text = src[node.start_byte:node.end_byte].decode(errors="replace")
            lines = text.count("\n") + 1
            if node.type in {"class_declaration", "class_definition"} and lines > max_symbol_lines:
                text = skeleton(node, src)             # signatures only; bodies indexed as methods
            sym = Symbol(path, node.type, name, ".".join(scope + [name]),
                         node.start_point[0] + 1, node.end_point[0] + 1, text,
                         set(IDENT.findall(text)) - {name}, is_test)
            out.append(sym)
            scope = scope + [name]
        for child in node.children:
            walk(child, scope)

    walk(tree.root_node, [])
    return out


def skeleton(node: Node, src: bytes) -> str:
    """Class header + field declarations + method signatures (no bodies)."""
    parts = []
    class_body = node.child_by_field_name("body")
    members = class_body.children if class_body else []
    header = src[node.start_byte:class_body.start_byte if class_body else node.end_byte]
    parts.append(header.decode(errors="replace").strip())
    for child in members:                        # fields kept whole; methods cut before their body
        body = child.child_by_field_name("body")
        end = body.start_byte if body else child.end_byte
        parts.append(src[child.start_byte:end].decode(errors="replace").strip())
    return "\n".join(p for p in parts if p)

References are approximate: the identifiers used in a body, minus the symbol's own name. Resolving them against the symbol table by name (preferring same package and imported packages) gives a call graph that is good enough for context expansion. Precision matters less than recall here, because the packer and the model filter noise.

7.3 P4 — Context assembly and the sandbox

from __future__ import annotations

import re
from dataclasses import dataclass

STACK_FRAME = re.compile(r"at ([\w.$]+)\.(\w+)\(([\w]+\.java):(\d+)\)|File \"([^\"]+)\", line (\d+)")


@dataclass
class Candidate:
    symbol_id: str
    text: str
    tokens: int
    score: float
    skeleton: str | None = None


def assemble(task: str, index, budget_tokens: int = 40_000) -> str:
    pinned = index.symbols_for_frames(STACK_FRAME.findall(task))          # exact hits from stack traces
    seeds = index.hybrid_search(task, k=30)                               # lexical + vector, RRF
    graph = index.neighbours({s.symbol_id for s in seeds + pinned}, hops=1, include_tests=True)
    cands: dict[str, Candidate] = {}
    for weight, group in ((3.0, pinned), (1.0, seeds), (0.5, graph)):
        for c in group:
            prev = cands.get(c.symbol_id)
            score = weight * c.score + (prev.score if prev else 0)       # accumulate evidence
            cands[c.symbol_id] = Candidate(c.symbol_id, c.text, c.tokens, score, c.skeleton)

    parts, used = [index.repo_map(max_tokens=3_000)], 3_000
    for c in sorted(cands.values(), key=lambda c: c.score / max(c.tokens, 1), reverse=True):
        if used + c.tokens <= budget_tokens:
            parts.append(f"### {c.symbol_id}\n{c.text}")
            used += c.tokens
        elif c.skeleton and used + len(c.skeleton) // 4 <= budget_tokens:
            parts.append(f"### {c.symbol_id} (skeleton)\n{c.skeleton}")
            used += len(c.skeleton) // 4
    return "\n\n".join(parts)

Propose edits ONLY via the `edit` tool as exact search/replace blocks.

                                     "new": {"type": "string"}}}},
]


def solve(task, index, sb_name: str, test_cmd: str, max_iterations: int = 4, max_steps: int = 40) -> dict:
    messages = [{"role": "user", "content": f"<context>\n{assemble(task.text, index)}\n</context>\n"
                                              f"<issue>\n{task.text}\n</issue>"}]
    iterations, steps = 0, 0
    while steps < max_steps:
        steps += 1
        resp = client.messages.create(model=MODEL, max_tokens=16_000, system=SYSTEM, tools=TOOLS,
                                      output_config={"effort": "high"}, messages=messages)
        if resp.stop_reason == "refusal":
            return {"status": "refused"}
        messages.append({"role": "assistant", "content": resp.content})   # append-only: keeps cache prefix
        tool_uses = [b for b in resp.content if b.type == "tool_use"]
        if not tool_uses:                                  # model believes it is done -> verify with tests
            iterations += 1
            res = sandbox.run(sb_name, test_cmd)
            if res.exit_code == 0:
                return {"status": "passed", "diff": sandbox.run(sb_name, "git diff").output}
            if iterations >= max_iterations:
                return {"status": "tests_failing", "log": sandbox.trim_test_output(res.output)}
            messages.append({"role": "user", "content": "Tests fail:\n" + sandbox.trim_test_output(res.output)})
            continue
        results = []
        for tu in tool_uses:                               # return ALL results in one user message
            try:
                out = dispatch(tu.name, tu.input, index, sb_name)
                results.append({"type": "tool_result", "tool_use_id": tu.id, "content": out})
            except EditError as e:
                results.append({"type": "tool_result", "tool_use_id": tu.id, "content": str(e), "is_error": True})
        messages.append({"role": "user", "content": results})
    return {"status": "step_budget_exhausted"}


def dispatch(name: str, args: dict, index, sb_name: str) -> str:
    if name == "read_file":
        return index.read(args["path"], args.get("start"), args.get("end"))
    if name == "search_code":
        return index.render(index.hybrid_search(args["query"], k=8))
    if name == "edit":
        apply_search_replace(sb_name, args["path"], args["old"], args["new"])   # raises EditError on no/multi match
        return "ok"
    raise EditError(f"unknown tool {name}")

The loop treats "the model stopped calling tools" as a claim that the work is done and verifies it by running tests. Tool results go back in one user message, which preserves parallel tool use, and history is append-only so the prompt-cache prefix stays valid (§6.1). The self-review step (omitted) sends the final diff, the test report and the issue to a fresh model call with a reviewer rubric: correctness risks, missing tests, unrelated changes. Its findings go into the PR description.

"""One executor 'tick': load a run, take steps until it finishes, pauses, or exhausts its budget."""
from __future__ import annotations

import json
import time
import uuid
from decimal import Decimal

import anthropic
from tenacity import retry, retry_if_exception_type, stop_after_attempt, wait_exponential_jitter

from .budget import estimate_next_cost, usage_cost
from .policy import Decision, PolicyEngine
from .store import RunStore, StaleRunError
from .tools import ToolRegistry, TransientToolError

client = anthropic.Anthropic()
PLANNER_MODEL = "claude-opus-5-5"     # version-sensitive
EXECUTOR_MODEL = "claude-sonnet-5-5"


class Executor:
    def __init__(self, store: RunStore, registry: ToolRegistry, policy: PolicyEngine):
        self.store, self.registry, self.policy = store, registry, policy

    def tick(self, run_id: uuid.UUID) -> None:
        run = self.store.load(run_id)
        if run.status not in ("RUNNING", "PLANNING", "REPLANNING"):
            return
        tools = self.registry.for_principal(run.tenant_id, run.requested_by)   # filtered by permission
        while True:
            if run.steps_used >= run.max_steps or time.time() > run.deadline.timestamp():
                return self.store.finish(run, "BUDGET_EXHAUSTED", self._partial_report(run))
            model = PLANNER_MODEL if run.status in ("PLANNING", "REPLANNING") else EXECUTOR_MODEL
            if run.cost_usd + estimate_next_cost(model, run.messages, max_out=4_000) > run.max_cost_usd:
                return self.store.finish(run, "BUDGET_EXHAUSTED", self._partial_report(run))

            resp = client.messages.create(
                model=model, max_tokens=4_000, system=self._system(run), tools=tools.schemas(),
                messages=run.messages, output_config={"effort": "medium"},
            )
            cost = usage_cost(model, resp.usage)
            run.messages.append({"role": "assistant", "content": [b.model_dump() for b in resp.content]})
            tool_uses = [b for b in resp.content if b.type == "tool_use"]

            if resp.stop_reason == "refusal" or not tool_uses:
                final = "".join(b.text for b in resp.content if b.type == "text")
                return self.store.finish(run, "DONE", {"answer": final}, add_cost=cost)

            results = []
            for tu in tool_uses:
                spec = tools.get(tu.name)
                decision = self.policy.evaluate(run, spec, tu.input)
                if decision == Decision.DENY:
                    results.append(self._error(tu, "Denied by policy: " + self.policy.reason(run, spec, tu.input)))
                elif decision == Decision.NEEDS_APPROVAL:
                    # Persist everything so far, park the run, and stop. A later approval re-enqueues it.
                    try:
                        self.store.park_for_approval(run, tu, rationale=self._rationale(resp), add_cost=cost)
                    except StaleRunError:
                        pass                                       # another executor advanced the run
                    return
                else:
                    key = f"{run.id}:{run.steps_used}:{tu.id}"
                    results.append(self._execute(spec, tu, key, run))
            run.messages.append({"role": "user", "content": results})
            run.status = "RUNNING"
            try:
                self.store.commit_step(run, add_cost=cost, step_increment=1)   # optimistic lock on version
            except StaleRunError:
                return                                             # someone else owns this run now

    @retry(retry=retry_if_exception_type(TransientToolError), stop=stop_after_attempt(3),
           wait=wait_exponential_jitter(initial=0.5, max=8))
    def _call_tool(self, spec, args: dict, key: str, run):
        return spec.invoke(args, idempotency_key=key, on_behalf_of=run.requested_by)

    def _execute(self, spec, tu, key: str, run) -> dict:
        cached = self.store.step_output_for_key(key)               # replay after crash: no double side effect
        if cached is not None:
            return {"type": "tool_result", "tool_use_id": tu.id, "content": json.dumps(cached)}
        try:
            out = self._call_tool(spec, tu.input, key, run)
            self.store.record_tool_step(run, tu, out, key)
            return {"type": "tool_result", "tool_use_id": tu.id, "content": json.dumps(out)[:20_000]}
        except Exception as e:                                     # permanent error: let the model re-plan
            return self._error(tu, f"{type(e).__name__}: {e}")

    @staticmethod
    def _error(tu, msg: str) -> dict:
        return {"type": "tool_result", "tool_use_id": tu.id, "content": msg, "is_error": True}

    def _system(self, run) -> str:
        return (f"You are an operations agent acting for {run.requested_by}. Goal and plan follow. "
                "Prefer read-only tools to verify state before writes. If a write is rejected, propose an "
                "alternative or stop and explain. Never invent tool results. "
                f"Budget: {run.max_steps - run.steps_used} steps left.\nPLAN: {json.dumps(run.plan)}")

    def _rationale(self, resp) -> str:
        return "".join(b.text for b in resp.content if b.type == "text")[:2_000]

    def _partial_report(self, run) -> dict:
        return {"completed_steps": self.store.summarize_steps(run.id), "reason": "budget"}

from __future__ import annotations

import asyncio

from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client   # MCP Python SDK; version-sensitive


class McpToolSpec:
    def __init__(self, server_url: str, token_provider, tool, risk: str):
        self.server_url, self.token_provider = server_url, token_provider
        self.name, self.risk = tool.name, risk
        self.schema = {"name": tool.name, "description": tool.description, "input_schema": tool.inputSchema}

    def invoke(self, args: dict, idempotency_key: str, on_behalf_of: str) -> dict:
        return asyncio.run(self._invoke(args, idempotency_key, on_behalf_of))

    async def _invoke(self, args, key, user):
        # Token exchange: a short-lived, audience-restricted token for this server, carrying the user.
        headers = {"Authorization": f"Bearer {self.token_provider.for_audience(self.server_url, user)}",
                   "Idempotency-Key": key}
        async with streamablehttp_client(self.server_url, headers=headers) as (read, write, _):
            async with ClientSession(read, write) as session:
                await session.initialize()
                result = await session.call_tool(self.name, args)
                if result.isError:
                    raise RuntimeError(str(result.content))
                return {"content": [c.model_dump() for c in result.content]}


async def discover(server_url: str, token_provider, risk_overrides: dict[str, str]) -> list[McpToolSpec]:
    headers = {"Authorization": f"Bearer {token_provider.for_audience(server_url, 'registry')}"}
    async with streamablehttp_client(server_url, headers=headers) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()
            listed = await session.list_tools()
            # Unknown tools default to the most restrictive risk; descriptions are reviewed on registration.
            return [McpToolSpec(server_url, token_provider, t, risk_overrides.get(t.name, "irreversible"))
                    for t in listed.tools]

Key properties of this runtime: (1) every model call and tool result is persisted before the next step, so a crashed worker loses at most one in-flight call; (2) the idempotency key runId:stepNo:toolUseId plus step_output_for_key makes replay after a crash safe; (3) the policy check happens per call, outside the model; (4) approval parks the run with no thread held; (5) MCP tools default to the most restrictive risk class until someone classifies them. The same structure could be built on LangGraph (nodes for plan, act and approve, with a Postgres checkpointer) or on Temporal (activities for tools, signals for approvals). Choose based on what your team already operates.

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.security.access.prepost.PreAuthorize;

import org.springframework.security.oauth2.jwt.Jwt;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.*;

@RestController
@RequestMapping("/v1/approvals")
class ApprovalController {
  record Decision(boolean approve, JsonNode editedInput, String comment) {}

  private final ApprovalRepository approvals;
  private final RunRepository runs;
  private final KafkaTemplate<String, String> kafka;

  ApprovalController(ApprovalRepository a, RunRepository r, KafkaTemplate<String, String> k) {
    this.approvals = a; this.runs = r; this.kafka = k;
  }

  @PostMapping("/{id}")
  @PreAuthorize("hasAuthority('SCOPE_agent.approve')")
  @Transactional
  ResponseEntity<Void> decide(@PathVariable UUID id, @RequestBody Decision d, @AuthenticationPrincipal Jwt jwt) {
    var req = approvals.findPendingForUpdate(id).orElseThrow(NotFoundOrExpired::new);
    var run = runs.findById(req.runId()).orElseThrow();
    if (run.requestedBy().equals(jwt.getSubject()) && req.riskLevel().equals("irreversible")) {
      throw new FourEyesViolation();                         // requester may not self-approve irreversible actions
    }
    req.decide(d.approve(), jwt.getSubject(), d.editedInput(), d.comment());
    run.resumeAfterApproval(req);                            // appends tool_result or rejection note, status RUNNING
    // Transactional outbox in production; shown directly for brevity.
    kafka.send("run.ready", run.id().toString(), run.id().toString());
    return ResponseEntity.accepted().build();
  }
}

package com.acme.orders.ai;

import io.github.resilience4j.circuitbreaker.annotation.CircuitBreaker;
import io.github.resilience4j.timelimiter.annotation.TimeLimiter;
import io.micrometer.observation.annotation.Observed;
import jakarta.validation.Validator;
import java.util.concurrent.CompletableFuture;
import org.springframework.ai.chat.client.ChatClient;
import org.springframework.stereotype.Service;

@Service
public class OrderExtractor {

  private final ChatClient chat;
  private final Validator validator;
  private final CatalogService catalog;      // existing bean: SKU lookup and fuzzy match
  private final ManualReviewQueue manualQueue;

  public OrderExtractor(ChatClient.Builder builder, Validator validator, CatalogService catalog,
                        ManualReviewQueue manualQueue) {
    this.chat = builder.defaultSystem("""
        Extract a purchase order from the email. Use only information in the email.
        If a value is missing or unclear, leave it null and add a note to ambiguities.
        Lower confidence for any line you had to guess.""").build();
    this.validator = validator;
    this.catalog = catalog;
    this.manualQueue = manualQueue;
  }

  @Observed(name = "ai.order.extract")
  @CircuitBreaker(name = "llm", fallbackMethod = "toManualReview")
  @TimeLimiter(name = "llm")
  public CompletableFuture<ExtractionResult> extract(InboundEmail email) {
    return CompletableFuture.supplyAsync(() -> {
      OrderDraft draft = chat.prompt()
          .user(u -> u.text("<email from=\"{from}\" subject=\"{subject}\">\n{body}\n</email>")
              .param("from", email.from()).param("subject", email.subject()).param("body", email.body()))
          .call()
          .entity(OrderDraft.class);
      var violations = validator.validate(draft);
      if (!violations.isEmpty() || draft.confidence() < 0.7) {
        return ExtractionResult.needsReview(draft, violations);
      }
      return ExtractionResult.ok(catalog.resolveSkus(draft));   // deterministic SKU resolution
    });
  }

  CompletableFuture<ExtractionResult> toManualReview(InboundEmail email, Throwable t) {
    manualQueue.enqueue(email, "llm_unavailable: " + t.getClass().getSimpleName());
    return CompletableFuture.completedFuture(ExtractionResult.queuedForHuman());
  }
}

import io.github.resilience4j.bulkhead.annotation.Bulkhead;
import org.springframework.ai.chat.client.ChatClient;

import org.springframework.http.codec.ServerSentEvent;

import org.springframework.web.bind.annotation.*;
import reactor.core.publisher.Flux;
import reactor.core.scheduler.Schedulers;

@RestController
@RequestMapping("/v1/ops-assistant")
class OpsAssistantController {
  record Question(String text) {}

  private final ChatClient chat;
  private final OrderTools tools;

  OpsAssistantController(ChatClient.Builder builder, OrderTools tools) {
    this.tools = tools;
    this.chat = builder.defaultSystem("""
        You help support staff investigate orders. Use tools to look up facts; never guess order data.
        Answer in at most 5 sentences, then list the facts you used.""").build();
  }

  @PostMapping(produces = MediaType.TEXT_EVENT_STREAM_VALUE)
  @Bulkhead(name = "llm-streams", type = Bulkhead.Type.SEMAPHORE)   // cap concurrent AI streams
  Flux<ServerSentEvent<String>> ask(@RequestBody Question q) {
    // Tools are invoked off the request thread; bridge the reactive security context so @PreAuthorize works.
    return ReactiveSecurityContextHolder.getContext().flatMapMany(ctx ->
        chat.prompt().user(q.text()).tools(tools).stream().content()
            .contextWrite(c -> c.put(SecurityContextKeys.CTX, ctx))
            .subscribeOn(Schedulers.boundedElastic()))
        .map(token -> ServerSentEvent.builder(token).event("token").build())
        .onErrorResume(e -> Flux.just(ServerSentEvent.builder(
            "The assistant is unavailable right now. Order data is still available in the console.")
            .event("error").build()));
  }
}

The testing layers for P7: (1) unit tests of everything around the model (validation, SKU resolution, fallbacks) with a stubbed ChatClient; (2) integration tests with WireMock replaying recorded provider responses (capture real responses once, store them as fixtures, and refresh them when you change prompts), plus Testcontainers for PostgreSQL so tools hit real queries; (3) eval tests, a nightly JUnit suite tagged @Tag("eval") that runs the 300 labelled emails against the real model and asserts field-level accuracy thresholds, publishing a report. Do not run (3) on every PR. It is slow, costs money and is noisy.
