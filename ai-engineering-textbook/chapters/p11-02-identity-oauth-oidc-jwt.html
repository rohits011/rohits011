Authentication, Authorization, OAuth 2.0, OIDC, JWT & Sessions

Identity is where most backend engineers meet security every day — and where copy-pasted configuration hides the deepest misunderstandings. This chapter rebuilds the whole stack from first principles: how passwords and passkeys actually work, what a session cookie must look like, what each OAuth 2.0 grant is for and which ones are now forbidden, what OpenID Connect adds, how to validate a JWT correctly, and how to model authorization beyond roles.   • You will be able to: choose and configure password hashing; design MFA/passkey rollout; harden cookie sessions; pick the correct OAuth 2.0 grant for any client; explain RFC 9700's recommendations; validate JWTs safely in Java, Python and Go; choose between JWT and opaque tokens; design RBAC, ABAC and ReBAC authorization; run a Spring Authorization Server.

1. Introduction: Two Questions, Many Protocols

Every protected request answers two questions. Authentication: who is making this request, and how sure are we? Authorization: is this principal allowed to do this specific thing to this specific resource right now? The protocols in this chapter — OAuth 2.0, OpenID Connect, JWT, WebAuthn — exist because answering those questions gets hard once there are many applications, many APIs, many devices and third parties involved.

OAuth 2.0 is the most misunderstood of them. It is a delegated authorization framework: it lets a user grant a client application limited access to an API on their behalf, without giving the client their password. It is not, by itself, an authentication protocol — an access token tells an API what the bearer may do, not who logged in to the client. OpenID Connect (OIDC) adds authentication on top by defining the ID token. JWT is merely a token format that both may use. Keeping these layers separate in your head prevents most identity design errors.

Bridging from Java & Spring Boot

What you already know
You have configured spring.security.oauth2.resourceserver.jwt.issuer-uri, used @AuthenticationPrincipal Jwt, mapped scopes to SCOPE_ authorities, written @PreAuthorize("hasRole('ADMIN')"), used BCryptPasswordEncoder or PasswordEncoderFactories.createDelegatingPasswordEncoder(), and perhaps set up oauth2Login() against Keycloak or Okta. Spring Session with Redis may be how your sessions survive pod restarts.
Why that is not enough
Defaults hide decisions. Does your resource server check the aud claim? (Spring Boot only does if you set audiences.) Does your SPA use the implicit grant from a 2017 tutorial? Are refresh tokens rotated? What happens when a user is disabled but holds a valid one-hour JWT? Does a role check stop one tenant's admin from administering another tenant? These are design questions the starter cannot answer.
The modern approach
Authorization code + PKCE for every user-facing client (RFC 9700, OAuth 2.1 draft); no implicit or password grant; short-lived, audience-restricted access tokens; sender-constrained tokens (DPoP or mTLS) where theft matters; backend-for-frontend (BFF) for browser apps so tokens never reach JavaScript; passkeys for phishing-resistant login; and fine-grained authorization (ABAC/ReBAC) in the service or a policy engine, not just roles in the token.
Where Python and Go fit
Python (PyJWT, Authlib) and Go (golang-jwt/jwt/v5, coreos/go-oidc) services often validate tokens issued for the Spring estate. The validation checklist is identical; the defaults are weaker, so you must pin algorithms, require exp, and check iss/aud explicitly.
In production
One identity provider (Keycloak, Okta/Auth0, Entra ID, Cognito, Ping, or Spring Authorization Server for bespoke needs), standard OIDC everywhere, JWKS caching and key rotation, central session/token revocation hooks, and authorization decisions logged.
Use it when / avoid it when
Use OAuth/OIDC whenever more than one application or API shares users, or third parties need delegated access. Avoid building your own authorization server unless you have a strong reason (unusual token formats, embedded product); a managed or established IdP is cheaper and safer. Avoid JWTs as browser session storage.

2. History: From /etc/passwd to Passkeys

2.1 Passwords and their storage

Early Unix stored password hashes in a world-readable /etc/passwd. Robert Morris and Ken Thompson's 1979 paper "Password Security: A Case History" introduced salting and deliberately slow hashing (crypt based on DES iterated 25 times) — the two ideas behind every modern password hash. bcrypt followed in 1999 (Provos and Mazières, USENIX), scrypt in 2009 (Colin Percival), and Argon2 won the Password Hashing Competition in 2015 and was standardised as RFC 9106 in 2021. PBKDF2 (RFC 2898, 2000; updated in RFC 8018) remains the FIPS-approved option.

2.2 Federated identity

Kerberos (MIT, 1980s; v5 as RFC 1510 in 1993, later RFC 4120) introduced tickets issued by a trusted third party. In the enterprise web, SAML 2.0 (OASIS, 2005) became the standard for browser single sign-on using signed XML assertions — and still dominates B2B SSO. OAuth 1.0 emerged in 2007 from Twitter and others to stop users giving their passwords to third-party apps; it was published as RFC 5849 in 2010. OAuth 2.0 (RFC 6749, with bearer tokens in RFC 6750) followed in October 2012, simplifying OAuth 1.0 by relying on TLS instead of per-request signatures.

2.3 Tokens and OpenID Connect

The JOSE specifications — JWS (RFC 7515), JWE (RFC 7516), JWK (RFC 7517), JWA (RFC 7518) — and JWT (RFC 7519) were published in May 2015. OpenID Connect Core 1.0 was finalised by the OpenID Foundation in February 2014, built on OAuth 2.0 with JWT-format ID tokens. PKCE (RFC 7636, September 2015) was designed for mobile apps to protect the authorization code from interception. In 2015, a widely-read analysis by Tim McLean showed several JWT libraries accepting alg: none or confusing RSA and HMAC keys — leading to the JWT Best Current Practices (RFC 8725, February 2020).

2.4 Hardening OAuth

The Device Authorization Grant (RFC 8628, 2019) handled TVs and CLIs. Token introspection (RFC 7662, 2015) and revocation (RFC 7009, 2013) standardised token lifecycle. Mutual-TLS client authentication and certificate-bound tokens came in RFC 8705 (2020); DPoP (Demonstrating Proof of Possession, RFC 9449) in September 2023. The OAuth 2.0 Security Best Current Practice was published as RFC 9700 in January 2025, formally deprecating the implicit grant and the resource owner password credentials grant and requiring PKCE broadly. OAuth 2.1 consolidates these into a single document; Version-sensitive · checked Nov 2026 it is still an IETF Internet-Draft (draft-ietf-oauth-v2-1, revisions continuing through 2026), not yet an RFC.

2.5 Phishing-resistant authentication

The FIDO Alliance (founded 2012) produced U2F security keys; FIDO2, combining W3C Web Authentication (WebAuthn Level 1, a W3C Recommendation in March 2019) and CTAP, generalised it. In 2022 Apple, Google and Microsoft announced support for synced, multi-device FIDO credentials — "passkeys". NIST SP 800-63B Revision 4, finalised in July 2025, incorporates syncable authenticators and continues to favour phishing-resistant options.

2.6 Authorization at scale

Role-based access control was formalised by Ferraiolo and Kuhn at NIST (1992) and standardised as ANSI INCITS 359 (2004). XACML (OASIS, 2003) attempted standard attribute-based policies. Google's Zanzibar paper (USENIX ATC 2019) described a global relationship-based authorization system for Drive, YouTube and others, inspiring open-source ReBAC systems such as SpiceDB and OpenFGA. Open Policy Agent (2016, CNCF graduated 2021) and AWS's Cedar language (2023) popularised policy-as-code.

2.7 In the Spring world

Spring Security OAuth (the old spring-security-oauth2 project with @EnableAuthorizationServer) was deprecated around 2019–2020 in favour of first-class OAuth2 client and resource-server support in Spring Security 5. Spring Authorization Server started in 2020 as a community-driven project, reached 1.0 in November 2022, and — as announced in September 2025 — has moved into Spring Security itself as of Spring Security 7.0 (same artifact ID, versioned with Spring Security). 3. Fundamentals

3.1 Authentication vs authorization, precisely

Authentication verifies a claim of identity using one or more factors: something you know (password, PIN), something you have (phone, security key, private key on a device), something you are (biometric, normally used only to unlock a local key). The output is a principal plus metadata about how it was authenticated (method, time, assurance level — in OIDC, the amr, acr and auth_time claims). Authorization consumes that principal and decides on an action. A clean architecture keeps them separate: the identity provider authenticates; your services authorize. Mixing them — e.g. encoding every permission for every resource in the token — makes tokens huge and stale.

3.2 Password storage

If you store passwords at all (prefer delegating to an IdP), the requirements are: never store plaintext or reversibly encrypted passwords; hash with a salted, slow, memory-hard (ideally) password hashing function; make the work factor configurable and upgradeable.

  • Why not SHA-256? General-purpose hashes are designed to be fast. GPUs compute billions of SHA-256 hashes per second, so a leaked table of unsalted or even salted SHA-256 hashes yields most human-chosen passwords quickly.
  • Salt: a unique random value per password stored alongside the hash. It defeats precomputed (rainbow) tables and ensures identical passwords have different hashes. Salt is not secret.
  • Pepper: an optional secret key (stored outside the database, e.g. in a KMS/HSM) mixed in via HMAC before hashing. It helps if only the database leaks. Rotation is awkward; treat as defense in depth.
  • Work factor: tune so a single hash takes roughly a few hundred milliseconds or less on your login hardware, and revisit as hardware improves.

3.4 Passkeys and WebAuthn

WebAuthn is public-key authentication in the browser. At registration, the authenticator generates a new key pair scoped to the relying party ID (your domain), keeps the private key (in secure hardware or a synced credential manager), and returns the public key and a credential ID, which the server stores. At authentication, the server sends a random challenge; the authenticator, after local user verification (biometric or PIN), signs a structure containing the challenge, the origin and the RP ID hash; the server verifies the signature with the stored public key. Nothing reusable is ever sent to the server — there is no shared secret to phish or leak in a database breach.

Passkeys is the industry name for discoverable FIDO credentials, typically synced across a user's devices by their platform (iCloud Keychain, Google Password Manager, Windows/Microsoft, or third-party managers). Synced passkeys trade some assurance (the key is no longer bound to one device) for recoverability. Device-bound passkeys (on hardware security keys) offer higher assurance for administrators. 3.5 Sessions and cookies

A server-side session maps a random identifier (the cookie) to state stored on the server (memory, Redis via Spring Session, JDBC). Security requirements:

  • Identifier entropy: at least 64 bits from a CSPRNG (servlet containers use far more).
  • Cookie flags: Secure (HTTPS only), HttpOnly (not readable by JavaScript, limiting XSS theft), SameSite=Lax or Strict (limits cross-site sending, a CSRF defence), narrow Path, and no Domain attribute unless you need subdomains (host-only cookies are safer). The __Host- name prefix enforces Secure, no Domain and Path=/.
  • Session fixation: an attacker plants a known session ID in the victim's browser before login; if the ID survives authentication, the attacker shares the authenticated session. Defence: issue a new session ID on login (and on privilege change). Spring Security does this by default (changeSessionId strategy via sessionFixation()).
  • Timeouts: idle timeout (e.g. 15–30 minutes for sensitive apps) and absolute timeout (e.g. 8–12 hours), plus re-authentication for sensitive operations.
  • Logout must invalidate server-side state, not merely delete the cookie.
  • Concurrent session control: optionally cap sessions per user (maximumSessions(1)) — requires a SessionRegistry; with Spring Session use SpringSessionBackedSessionRegistry.

Spring Session externalises the HttpSession to Redis/JDBC/Hazelcast so sessions survive restarts and scale horizontally; it also offers FindByIndexNameSessionRepository to find and invalidate all sessions for a user (e.g. after a password change).

3.6 OAuth 2.0 roles

  • Resource owner — usually the end user, who owns the data.
  • Client — the application requesting access (SPA, mobile app, server-side web app, CLI, another service). Confidential clients can keep a secret (server-side); public clients cannot (SPAs, mobile, desktop, CLI).
  • Authorization server (AS) — authenticates the resource owner, obtains consent, issues tokens (Keycloak, Okta, Entra ID, Spring Authorization Server).
  • Resource server (RS) — the API that accepts access tokens (your Spring Boot service with oauth2ResourceServer()).

3.8 Token types

  • Access token — presented to resource servers. Either self-contained (JWT, validated locally by signature) or opaque/reference (random string, validated by calling the AS introspection endpoint). Short-lived: minutes, not days.
  • Refresh token — presented only to the AS to get new access tokens. Long-lived, high value; must be stored securely and, for public clients, rotated on each use (reuse detection revokes the family) or sender-constrained.
  • ID token (OIDC) — a JWT for the client, asserting who authenticated. Never send it to APIs as an access token.
  • Bearer vs sender-constrained: a bearer token works for anyone who holds it (like cash). A sender-constrained token is bound to a key the client must prove possession of — via mTLS (RFC 8705, cnf.x5t#S256 claim) or DPoP (RFC 9449, cnf.jkt). A stolen sender-constrained token is useless without the private key.

3.9 Scopes, audiences and claims

Scopes are coarse permissions the client asks for and the user consents to (orders.read, openid, profile). They limit what the client can do on the user's behalf — they are not a replacement for per-user authorization in the API. Audience (aud) states which resource server a token is for; an API must reject tokens whose aud is not itself, otherwise a token issued for a low-trust API can be replayed against a high-trust one. RFC 8707 (Resource Indicators) lets clients request audience-specific tokens. Claims are statements about the subject (sub, email, roles, tenant); keep access-token claims minimal and stable.

3.10 RFC 9700 — the OAuth 2.0 Security Best Current Practice

The key recommendations, summarised (read the RFC for exact normative language):

  • Use authorization code with PKCE; PKCE required for public clients, recommended for confidential ones; use S256, not plain.
  • Do not use the implicit grant or other response types that return access tokens in the authorization response.
  • Do not use the resource owner password credentials grant.
  • Exact string matching of redirect URIs (no wildcards, no open redirectors on the client or AS).
  • Protect against CSRF on the redirect (PKCE, or state, or OIDC nonce).
  • Sender-constrain refresh tokens for public clients, or use refresh-token rotation; sender-constrain access tokens where feasible (mTLS or DPoP).
  • Restrict access-token privileges: audience restriction and minimal scope.
  • Defend against mix-up attacks when clients use multiple authorization servers (the iss authorization response parameter, RFC 9207).
  • Authenticate confidential clients with asymmetric methods (private_key_jwt, mTLS) where possible.

3.11 OpenID Connect

OIDC adds: the openid scope; the ID token (a signed JWT with iss, sub, aud = the client ID, exp, iat, auth_time, nonce, optional acr/amr); the UserInfo endpoint returning claims for an access token; Discovery at /.well-known/openid-configuration (issuer, endpoints, jwks_uri, supported algorithms); dynamic client registration; and session management/logout specs (RP-initiated, front-channel, back-channel logout). The stable user identifier is the pair (iss, sub) — never the email, which can change or be reassigned.

3.12 JWT structure

A JWS-signed JWT is three base64url-encoded parts joined by dots: header.payload.signature. The header names the algorithm (alg), the key ID (kid) and type (typ, e.g. at+jwt for access tokens per RFC 9068). The payload holds claims. The signature covers base64url(header) + "." + base64url(payload). A JWT is signed, not encrypted: anyone can read the payload. Do not put secrets or sensitive PII in it. (JWE provides encryption but is rarely needed for access tokens.)

3.14 Authorization models

  • ACL — per-object lists of who may do what. Simple, but hard to manage at scale.
  • RBAC — permissions attach to roles, users get roles. Great for coarse function-level access (ADMIN, SUPPORT). Fails at object level ("support agents may only see tickets of their region") and suffers role explosion when you encode context into role names (EU_SUPPORT_READONLY).
  • ABAC — decisions from attributes of subject, resource, action and environment ("allow if user.department == doc.department and time within business hours and device managed"). Expressive; harder to audit; policies need testing. Implemented with policy engines (OPA/Rego, Cedar, XACML) or in code.
  • ReBAC — decisions from relationships in a graph ("user is editor of folder; folder is parent of doc; editors of a parent are viewers of children"). The Zanzibar model: tuples object#relation@subject, plus a namespace config defining how relations compose. Ideal for sharing/collaboration products and hierarchical multi-tenant data. Implementations: SpiceDB, OpenFGA, Permify, Ory Keto.
  • Policy-as-code engines — OPA (Rego) evaluates JSON input against policies, often as a sidecar or library; Cedar (AWS, open source, also behind Amazon Verified Permissions) is a typed policy language designed for analysability.

Most real systems combine them: RBAC for admin functions, ownership/ReBAC for data, ABAC conditions for context (tenant, region, risk).

4. Internal Working

4.1 Authorization code flow with PKCE, step by step

  1. The client generates a code_verifier: 43–128 characters of high-entropy randomness. It computes code_challenge = BASE64URL(SHA256(code_verifier)). It also generates state (and, for OIDC, nonce) and stores all three in the user's session (for a BFF) or secure storage (native apps).
  2. The client redirects the browser to the AS's authorization endpoint with response_type=code, client_id, redirect_uri, scope, state, nonce, code_challenge, code_challenge_method=S256.
  3. The AS authenticates the user (password + MFA, passkey, upstream federation), checks the client and the redirect URI by exact match, and obtains consent if needed.
  4. The AS redirects back to redirect_uri?code=...&state=...&iss=.... The code is short-lived (often around a minute or less) and single-use; the AS remembers the challenge associated with it.
  5. The client checks state (and iss) match what it stored, then POSTs to the token endpoint: grant_type=authorization_code, code, redirect_uri, code_verifier, plus client authentication if confidential.
  6. The AS recomputes SHA256(code_verifier) and compares with the stored challenge. An attacker who intercepted the code (malicious app on the same device, log leakage, referrer) does not have the verifier and cannot redeem it.
  7. The AS returns access_token, token_type, expires_in, optional refresh_token, and with openid an id_token. The client validates the ID token (signature, iss, aud = its client ID, exp, nonce).

Why PKCE even for confidential clients? It also defends against authorization code injection, where an attacker injects a stolen code into their own session with the legitimate client; the client's stored verifier will not match the code's challenge.

4.2 How Spring's resource server validates a JWT

For a request with Authorization: Bearer ...:

  1. BearerTokenAuthenticationFilter extracts the token via BearerTokenResolver (header only by default; query-parameter and form-body tokens are disabled by default — keep it that way, since URLs are logged).
  2. It delegates to the AuthenticationManager, which routes to JwtAuthenticationProvider.
  3. NimbusJwtDecoder parses the JWT, finds the key by kid in the JWKS (fetched from jwks_uri discovered via issuer-uri, cached, refreshed when an unknown kid appears), and verifies the signature using only the algorithms it is configured for (RS256 by default, or those advertised by the issuer).
  4. An OAuth2TokenValidator<Jwt> chain runs: by default timestamps (exp/nbf with 60 seconds clock skew) and issuer (when configured via issuer URI). Audience is validated only if you configure audiences or add a validator. Version-sensitive · checked Nov 2026 Spring Security 7 adds a typ header validator to the defaults.
  5. JwtAuthenticationConverter turns claims into a JwtAuthenticationToken with authorities (by default SCOPE_-prefixed entries from scope/scp).
  6. The token is placed in the SecurityContext; AuthorizationFilter and method security then evaluate rules. On failure, BearerTokenAuthenticationEntryPoint returns 401 with a WWW-Authenticate: Bearer error="invalid_token" header.

4.3 The JWT validation checklist

Whatever the language, a resource server must:

  1. Pin the algorithm(s) server-side. Never trust the token's alg to choose the verification method. Reject none.
  2. Select keys only from a trusted source: the configured issuer's JWKS. Ignore jku, x5u and embedded jwk header parameters (they let the token point to an attacker's key). Treat kid as an opaque lookup key, never as a file path or SQL fragment.
  3. Verify the signature before trusting any claim.
  4. Check iss equals the expected issuer exactly.
  5. Check aud contains this API's identifier.
  6. Check exp (required) and nbf/iat with small clock skew.
  7. Check typ (at+jwt for access tokens per RFC 9068) to prevent an ID token or other JWT being used as an access token ("token confusion").
  8. Check sender constraint if present (cnf against DPoP proof or mTLS certificate).
  9. Then authorize using scopes/claims plus your own data.

4.4 Algorithm confusion and other classic JWT bugs

RS256→HS256 confusion. A naive library function like verify(token, key) picks the algorithm from the token header. If the server passes its RSA public key (which is public!) and the attacker sets alg: HS256, the library computes an HMAC using the public key bytes as the secret — which the attacker can also do. The attacker can therefore forge arbitrary tokens. Fix: algorithm pinned per key; keys typed (an RSA key object cannot be used as an HMAC secret).

alg: none. Some early libraries accepted unsigned tokens. Fix: reject none; modern libraries do by default when given a key.

Weak HMAC secrets. HS256 with a short or dictionary secret can be brute-forced offline from any captured token. Fix: 256-bit random secrets, or asymmetric algorithms.

Missing audience check. A token for the low-privilege newsletter-api works on payments-api because both trust the same issuer. Fix: validate aud.

Cross-issuer acceptance. Multi-tenant resource servers that accept tokens from several issuers must map each issuer to its own JWKS; never accept "any signature from any key we know" (the Storm-0558 case study in §9 shows a variant of this at hyperscale).

4.6 JWT vs opaque tokens

JWTs: no per-request call to the AS, good for high-throughput microservices and cross-domain; but content is readable by any holder (privacy), revocation is delayed, and tokens grow with claims. Opaque tokens: immediately revocable, carry no data to leak, small; but every RS must introspect (latency, AS load, availability). A common hybrid is the phantom token pattern: clients receive opaque tokens; the API gateway introspects once and forwards a short-lived JWT to internal services. Spring supports both: .jwt() and .opaqueToken() on oauth2ResourceServer, and an AuthenticationManagerResolver to support both at once.

4.7 Refresh token rotation and reuse detection

With rotation, each refresh returns a new refresh token and invalidates the old one. If an old refresh token is presented again, the AS knows that either the client or an attacker holds a stolen copy, and revokes the whole token family, forcing re-authentication. Spring Authorization Server exposes TokenSettings.reuseRefreshTokens(false) to issue a new refresh token on every use.

4.8 DPoP in brief

The client generates a key pair. On each token request and each API call, it sends a DPoP header containing a short JWT signed with its private key, including its public key (jwk header), the HTTP method (htm), URI (htu), a unique jti, iat, and for API calls a hash of the access token (ath). The AS binds the access token to the key thumbprint (cnf.jkt). The resource server verifies the proof signature, that the key thumbprint matches cnf.jkt, that method and URI match, freshness, and jti uniqueness. A stolen access token without the private key is useless. Version-sensitive · checked Nov 2026 Spring Security added DPoP support for resource servers in the 6.5 line; check your IdP's DPoP support before planning a rollout.

4.9 Where browser apps should keep tokens: the BFF pattern

Any token accessible to JavaScript (localStorage, sessionStorage, in-memory in the SPA) can be exfiltrated by an XSS bug or a malicious dependency. The IETF draft "OAuth 2.0 for Browser-Based Applications" recommends, in order of preference, a backend-for-frontend: a server-side component (Spring Boot with oauth2Login(), or Spring Cloud Gateway with TokenRelay) that is the confidential OAuth client, holds tokens server-side, and gives the browser only an HttpOnly, Secure, SameSite session cookie. API calls go through the BFF, which attaches the access token. The trade-off is that the cookie reintroduces CSRF concerns (handled by SameSite plus CSRF tokens) and a stateful component.

4.10 Session fixation protection, internally

On successful authentication, Spring Security's SessionManagementFilter/AbstractAuthenticationProcessingFilter invoke the configured SessionAuthenticationStrategy. The default ChangeSessionIdAuthenticationStrategy calls HttpServletRequest.changeSessionId() (Servlet 3.1+), keeping attributes but issuing a new ID. The pre-login ID the attacker planted becomes worthless. Alternatives: newSession() (fresh session, attributes dropped) and migrateSession().

5. Architecture: The Flows as Sequence Diagrams

5.1 Authorization code + PKCE through a BFF

Reading the diagram: steps 2–3 create the PKCE pair and anti-CSRF values server-side. Steps 5–7 happen entirely between browser and AS; the BFF never sees the password. Step 11 is the back-channel code redemption: the verifier proves the redeemer is the same party that started the flow. Step 13 is where many implementations are sloppy — the ID token must be validated, including nonce. From step 14 the browser holds only an opaque session cookie; XSS can still make requests while the user is on the page, but it cannot steal a long-lived token to use elsewhere. Steps 17–18 are the resource server's independent validation; it trusts nothing about the BFF except the token.

5.2 Client credentials for service-to-service

Reading the diagram: there is no user, so the token's subject is the client itself. Using private_key_jwt instead of a shared client secret means the AS stores only a public key, and the private key can live in a KMS or be replaced by workload identity (Chapter 11.4). The resource server should authorize on both scope and client identity: a scope alone does not say which service is calling.

5.3 Device authorization grant

Reading the diagram: the device never handles the user's credentials. The user authenticates on a full browser where passkeys and MFA work. The main risk is social engineering ("enter this code to claim your prize"), so the AS should display the requesting client clearly on the approval screen, and user codes should expire quickly. Respect slow_down responses when polling.

5.4 Token exchange for multi-hop calls

Reading the diagram: forwarding T1 to Payments would require Payments to accept tokens whose audience is Orders — breaking audience restriction — and would give Orders the ability to do anything Alice's token allows anywhere. With exchange, T2 is narrow (one audience, one scope, short lifetime) and records the actor (act claim), so Payments' audit log shows "Orders acting for Alice". This is the same "no token passthrough" principle that the MCP specification enforces for AI tool servers (Chapter 11.5).

5.5 A ReBAC authorization check

Reading the diagram: no tuple directly says Alice may view the document. The engine walks relations defined in the schema: doc.viewer includes parent.editor; folder.editor includes team.member. Because relationships are data, sharing a folder with a team is one tuple write, and the check stays fast via graph caching. Zanzibar's paper also addresses consistency ("new enemy" problem) using snapshot tokens called zookies.

6. The Math: Hash Cost, Entropy, Token Exposure

6.1 Password cracking economics

Intuition: an attacker with a stolen hash table tries candidate passwords; your only lever is the cost of each guess. If one guess costs \( c \) seconds of attacker hardware and the attacker needs on average half the candidate space \( N \), time to crack one password is

\[ T \approx \frac{N}{2} \cdot \frac{c}{k} \]

with \( k \) parallel units. Illustrative For a password drawn uniformly from \( N = 10^{10} \) candidates: with a fast hash (\( c = 10^{-10} \) s per guess on a GPU), \( T \approx 0.5 \) s. With bcrypt at a cost where a guess takes \( 10^{-4} \) s on the same GPU (bcrypt resists GPU acceleration), \( T \approx 5\times10^{5} \) s ≈ 6 days — per password, per GPU. Salt multiplies this by the number of users, since each must be attacked separately. Memory-hard functions further raise \( c \) on GPUs/ASICs by requiring large RAM per guess.

6.2 bcrypt cost is exponential

bcrypt cost \( w \) performs \( 2^{w} \) key-expansion rounds, so each +1 doubles time: cost 10 → 12 is 4× slower. Benchmark on production hardware; a login endpoint that takes 250 ms of CPU per attempt also needs rate limiting, or attackers can use it for CPU exhaustion.

6.3 Entropy of secrets

Entropy in bits for a uniformly random string of length \( L \) from alphabet size \( A \): \( H = L \log_2 A \). A 43-character base64url PKCE verifier: \( 43 \times 6 = 258 \) bits. A 6-digit OTP: \( \log_2 10^6 \approx 19.9 \) bits — safe only because of short lifetime and attempt limits. Human passwords do not have uniform entropy; that is why breached-password checks matter more than composition rules.

6.4 Token lifetime vs exposure

If tokens are stolen at rate \( \lambda \) per day and each remains usable for lifetime \( L \) after theft (no revocation), expected attacker-usable token-time per day is \( \lambda L \). Halving lifetime halves exposure but doubles refresh traffic: refresh requests per second ≈ active sessions ÷ \( L \). Illustrative 200,000 concurrent sessions with 5-minute tokens ⇒ ≈ 667 refreshes/s at the AS; with 15-minute tokens ≈ 222/s. Pick \( L \) as a capacity and risk decision.

6.5 JWKS caching and validation latency

RSA-2048 signature verification costs on the order of tens of microseconds on modern CPUs; ES256 verification is somewhat slower than RSA verification but signing is much faster. JWKS fetches happen once per key rotation (cache with refresh on unknown kid, rate-limited to avoid being turned into a DoS amplifier by tokens with random kids). Introspection adds a network round trip (typically 1–10 ms in-region) per request unless cached.

import org.springframework.security.web.SecurityFilterChain;

@Configuration
@EnableMethodSecurity
public class ResourceServerConfig {

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {

                .jwsAlgorithm(SignatureAlgorithm.RS256)          // pinned; add PS256/ES256 only if your IdP uses them
                .build();
        OAuth2TokenValidator<Jwt> audience = new JwtClaimValidator<List<String>>(
                JwtClaimNames.AUD, aud -> aud != null && aud.contains("orders-api"));
        OAuth2TokenValidator<Jwt> type = jwt -> "at+jwt".equalsIgnoreCase(String.valueOf(jwt.getHeaders().get("typ")))
                ? OAuth2TokenValidatorResult.success()
                : OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", "wrong typ", null));
        decoder.setJwtValidator(new DelegatingOAuth2TokenValidator<>(
                JwtValidators.createDefaultWithIssuer(issuer), audience, type));
        return decoder;
    }
}

7.6 Validating access tokens in Python and Go

# token_validation.py — pip install "pyjwt[crypto]==2.9.*" "fastapi==0.115.*"
import time
import jwt
from jwt import PyJWKClient, InvalidTokenError
from fastapi import Depends, FastAPI, HTTPException
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer

ISSUER = "https://idp.example.com"
AUDIENCE = "orders-api"
ALLOWED_ALGS = ["RS256"]                      # pinned; never read from the token
# Discover jwks_uri from /.well-known/openid-configuration once at startup in real code.
jwk_client = PyJWKClient(f"{ISSUER}/oauth2/jwks", cache_keys=True, lifespan=300)

def validate(raw: str) -> dict:
    header = jwt.get_unverified_header(raw)
    if header.get("alg") not in ALLOWED_ALGS:
        raise InvalidTokenError("algorithm not allowed")
    if any(h in header for h in ("jku", "x5u", "jwk")):
        raise InvalidTokenError("untrusted key reference")
    signing_key = jwk_client.get_signing_key_from_jwt(raw)   # looks up by kid in the trusted JWKS only
    claims = jwt.decode(
        raw, signing_key.key, algorithms=ALLOWED_ALGS,
        issuer=ISSUER, audience=AUDIENCE, leeway=30,
        options={"require": ["exp", "iat", "iss", "aud", "sub"]},
    )
    return claims

app = FastAPI()
bearer = HTTPBearer()

def principal(creds: HTTPAuthorizationCredentials = Depends(bearer)) -> dict:
    try:
        return validate(creds.credentials)
    except InvalidTokenError:
        raise HTTPException(401, headers={"WWW-Authenticate": 'Bearer error="invalid_token"'})

@app.get("/api/orders")
def orders(p: dict = Depends(principal)):
    if "orders.read" not in p.get("scope", "").split():
        raise HTTPException(403)
    return {"customer": p["sub"], "orders": []}
// validate.go — go get github.com/golang-jwt/jwt/v5 github.com/MicahParks/keyfunc/v3
package main

import (
	"context"
	"errors"
	"log"
	"net/http"
	"slices"
	"strings"
	"time"

	"github.com/MicahParks/keyfunc/v3"
	"github.com/golang-jwt/jwt/v5"
)

const (
	issuer   = "https://idp.example.com"
	audience = "orders-api"
)

type Claims struct {
	Scope string `json:"scope"`
	jwt.RegisteredClaims
}

type Validator struct {
	kf     keyfunc.Keyfunc
	parser *jwt.Parser
}

func NewValidator(ctx context.Context) (*Validator, error) {
	// Background refresh of the JWKS; unknown kid triggers a rate-limited refresh.
	kf, err := keyfunc.NewDefaultCtx(ctx, []string{issuer + "/oauth2/jwks"})
	if err != nil {
		return nil, err
	}
	p := jwt.NewParser(
		jwt.WithValidMethods([]string{"RS256"}), // pinned algorithm
		jwt.WithIssuer(issuer),
		jwt.WithAudience(audience),
		jwt.WithExpirationRequired(),
		jwt.WithIssuedAt(),
		jwt.WithLeeway(30*time.Second),
	)
	return &Validator{kf: kf, parser: p}, nil
}

func (v *Validator) Validate(raw string) (*Claims, error) {
	c := &Claims{}
	tok, err := v.parser.ParseWithClaims(raw, c, v.kf.Keyfunc)
	if err != nil || !tok.Valid {
		return nil, errors.Join(errors.New("invalid token"), err)
	}
	return c, nil
}

func (v *Validator) Require(scope string, next http.HandlerFunc) http.HandlerFunc {
	return func(w http.ResponseWriter, r *http.Request) {
		raw, ok := strings.CutPrefix(r.Header.Get("Authorization"), "Bearer ")
		if !ok {
			w.Header().Set("WWW-Authenticate", "Bearer")
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		c, err := v.Validate(raw)
		if err != nil {
			w.Header().Set("WWW-Authenticate", `Bearer error="invalid_token"`)
			http.Error(w, "unauthorized", http.StatusUnauthorized)
			return
		}
		if !slices.Contains(strings.Fields(c.Scope), scope) {
			http.Error(w, "forbidden", http.StatusForbidden)
			return
		}
		next(w, r)
	}
}

func main() {
	v, err := NewValidator(context.Background())
	if err != nil {
		log.Fatal(err)
	}
	mux := http.NewServeMux()
	mux.HandleFunc("GET /api/orders", v.Require("orders.read", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte(`{"orders":[]}`))
	}))
	srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: 5 * time.Second}
	log.Fatal(srv.ListenAndServe()) // terminate TLS at the mesh/ingress or use ListenAndServeTLS
}

Both implementations pin algorithms, use only the trusted JWKS, require exp, and check issuer and audience. PyJWT's jwt.decode rejects tokens whose algorithm is not in algorithms; golang-jwt's WithValidMethods does the same. Ignoring jku/x5u is automatic in both because neither fetches keys from token headers — the explicit check in Python is belt-and-braces. Both libraries' key functions return typed keys, so an RSA public key cannot be misused as an HMAC secret.

8. Applications: Identity Architectures Teams Actually Run

8.1 B2C web + mobile

One OIDC provider; web via BFF (Spring Boot or a gateway); mobile apps as public clients using authorization code + PKCE through the system browser (AppAuth libraries — never embedded web views, which let the app capture credentials); short access tokens with rotating refresh tokens; passkeys offered at sign-up and promoted at login; risk-based step-up (re-authentication or stronger factor) for payments and profile changes.

8.2 B2B SaaS with enterprise SSO

Customers bring their own IdP (Entra ID, Okta, Google Workspace) via OIDC or SAML; your IdP brokers federation (Keycloak identity brokering, Auth0 enterprise connections). Tokens carry a tenant/organisation claim derived from the federation connection — never from user input. SCIM (RFC 7644) provisions and deprovisions users so leavers lose access promptly. Authorization is per-tenant RBAC plus ownership/ReBAC inside the tenant.

8.3 Microservices

Edge validates user tokens; internal calls use either token exchange (user context preserved, narrow audience) or service identity (mTLS via a service mesh with SPIFFE IDs, or client credentials). Every service re-validates and authorizes; none trusts identity headers unless they are cryptographically bound (e.g. a signed internal JWT). The anti-pattern is a gateway that strips the token and forwards X-User-Id, so any internal caller can impersonate anyone.

8.4 Machine identities and CLIs

CI pipelines use OIDC workload identity federation (GitHub Actions OIDC tokens exchanged for cloud credentials) instead of long-lived keys. Developer CLIs use the device grant or a loopback-redirect authorization code flow with PKCE (RFC 8252 for native apps).

8.5 Admin access

Administrators authenticate with device-bound phishing-resistant credentials (hardware security keys), hold no standing admin rights (just-in-time elevation through an approval workflow), and their actions are audited separately. Break-glass accounts exist, are vaulted, and alert when used.

9. Case Studies

9.1 Storm-0558 (2023): a stolen signing key and a validation gap Verified

In July 2023 Microsoft disclosed that a threat actor it tracked as Storm-0558 had used an acquired Microsoft account (MSA) consumer signing key to forge authentication tokens and access Outlook Web Access in Exchange Online and Outlook.com for about 25 organisations, including US government agencies. Microsoft reported that a token-validation issue allowed tokens signed with the consumer key to be accepted for enterprise (Azure AD) accounts. Its follow-up investigation concluded that the key most likely leaked into a crash dump in 2021 that later reached a debugging environment on the corporate network. The US Cyber Safety Review Board's 2024 report was sharply critical of Microsoft's security culture. Lessons for your systems: keys belong in HSM/KMS where they cannot be dumped; key scoping must be enforced by validators (which issuer, which key, which audience); and key rotation plus monitoring of token anomalies limits damage. Sources: MSRC, July 2023; MSRC, results of key-acquisition investigation.

9.2 JWT library vulnerabilities (2015) Verified

Tim McLean's 2015 write-up showed that several popular JWT libraries would accept tokens with alg: none and could be tricked into verifying an HS256 token using an RSA public key as the HMAC secret. Libraries were fixed, and the episode drove the "pin the algorithm, type the key" guidance later codified in RFC 8725. The lesson generalises: a security protocol whose message tells the verifier how to verify it is inviting attack. Source: Auth0 blog, "Critical vulnerabilities in JSON Web Token libraries".

9.3 Google Zanzibar (2019) Verified

Google's Zanzibar paper describes a single authorization system serving many products (Calendar, Drive, Maps, Photos, YouTube) with relation tuples, a namespace configuration language, and snapshot-consistent checks. The paper reports trillions of stored tuples and millions of authorization checks per second at low latency. It shows why ReBAC is attractive for sharing-heavy products and why consistency (avoiding the "new enemy" problem when permissions are revoked and content changes) needs explicit design. Source: Pang et al., "Zanzibar: Google's Consistent, Global Authorization System", USENIX ATC 2019.

9.4 Airbnb Himeji (2021) Verified

Airbnb described moving permission checks from duplicated logic in presentation services into a centralised, Zanzibar-inspired authorization service called from the data layer. Their write-up explains the motivations (consistency, duplicated checks, maintainability) and the operational effort required. Source: Airbnb Engineering, "Himeji: A Scalable Centralized System for Authorization at Airbnb".

9.5 Spring Security removes the password grant Verified

Following RFC 9700's prohibition, Spring Security 7.0 removed client support for the resource owner password credentials grant. Teams that used it for "simple" mobile logins must migrate to authorization code + PKCE with the system browser. Source: Spring Security "What's New".

11. Engineering Trade-offs: Choosing Flows, Tokens and Models

11.1 Which grant?

Reading the diagram: every user-facing path ends in authorization code + PKCE; the variations are where tokens live (BFF server, native secure storage, server session). Machine paths prefer asymmetric client authentication or, better, platform workload identity so there is no secret at all.

11.2 Sessions vs tokens for your own web app

Opinion For a first-party web application served from your domain, server-side sessions (or a BFF holding tokens) are simpler and safer than storing JWTs in the browser. Use bearer JWTs for API-to-API and for third-party/native clients. "Stateless JWT sessions" in localStorage optimise a non-problem (session lookups in Redis are cheap) while creating real ones (XSS token theft, no revocation).

Buy (or run Keycloak) when you need standard OIDC, social/enterprise federation, MFA/passkeys, admin UI and compliance certifications. Build on Spring Authorization Server when you need custom grant types, embedded deployment in a product, unusual token contents, or full control — and accept owning key management, user storage, MFA, account recovery, abuse protection and audits.

12. Common Mistakes

  • Using the ID token as an API access token. Its audience is the client; APIs should reject it.
  • Not validating aud in resource servers — Spring Boot only checks it if configured.
  • Letting the token choose the algorithm, or verifying with a key fetched from jku.
  • Storing tokens in localStorage in SPAs.
  • Using email as the user key. Use (iss, sub); emails change and can be recycled, and unverified emails enable account takeover through federation.
  • Wildcard redirect URIs (https://*.example.com/*) or open redirects on the client, enabling code theft.
  • Long-lived bearer access tokens (24 h+) "to avoid refresh complexity".
  • Encoding all permissions in the JWT, making tokens huge and permissions stale until expiry.
  • Treating scopes as user permissions. orders.write means the client may write orders on behalf of the user — not that the user may write this order.
  • Different error messages for "unknown user" vs "wrong password", enabling enumeration; also timing differences when unknown users skip hashing (Spring's DaoAuthenticationProvider mitigates this by hashing a dummy password).
  • Forgetting to invalidate sessions on password change, MFA reset or account disable.
  • Account recovery weaker than login: passkeys everywhere, but recovery by SMS code — attackers take the easiest path.
  • HS256 shared across services, so any service can mint tokens for all.
  • Trusting X-Forwarded-User or similar headers that external clients can set.

13. Production Concerns

13.1 Key management and rotation

Sign tokens with keys held in an HSM or KMS (or at minimum a protected keystore). Rotate on a schedule: publish the new public key in JWKS first, wait for caches to pick it up (longer than the maximum JWKS cache time), switch signing to the new key, keep the old public key published until all tokens signed with it have expired, then remove it. Have an emergency rotation runbook for key compromise, which also requires revoking refresh tokens.

13.2 Availability

The authorization server is a tier-0 dependency: when it is down, nobody logs in or refreshes. Run it highly available, monitor token endpoint latency and error rates, and size it for refresh traffic (§6.4). Resource servers with cached JWKS keep working through brief AS outages; introspection-based ones do not, unless you cache — and caching trades revocation speed for availability.

13.3 Abuse protection

Rate-limit login, MFA verification, password reset and token endpoints by account and by source; detect credential stuffing (many usernames per IP, high failure rates, known-breached credentials); use bot mitigation on public login; lock or step-up rather than hard-lock accounts (hard locks become a DoS tool).

13.4 Monitoring

Metrics: login success/failure rates, MFA challenge rates, refresh-token reuse detections (each one is a likely theft), token validation failures by reason (expired vs bad signature vs wrong audience — a spike in bad signatures is an attack or a botched rotation), session counts. Logs: authentication events with method (amr), client ID, IP, user agent; never tokens.

13.5 Performance

JWT validation with cached keys is cheap; the expensive parts are password hashing on login (CPU-bound — run login on dedicated capacity or rate-limit it), introspection round trips, and fine-grained authorization calls. For ReBAC, batch checks and cache negative and positive decisions briefly; for policy engines, run them as a sidecar or embedded library to avoid network hops.

13.6 Compliance

Map controls to the frameworks you are audited against: NIST SP 800-63 assurance levels, PCI DSS v4 MFA requirements for access to cardholder data environments, SOC 2 access-review evidence, and GDPR data minimisation (keep PII out of tokens).

Exercise 2 · Intermediate

Write a Spring OAuth2TokenValidator<Jwt> that rejects tokens issued before the user's "revoked-before" timestamp, stored in Redis under revoked:{sub}. Consider performance and failure behaviour.

Solution
public class RevokedBeforeValidator implements OAuth2TokenValidator<Jwt> {
    private final StringRedisTemplate redis;
    private final Cache<String, Optional<Instant>> local =
        Caffeine.newBuilder().expireAfterWrite(Duration.ofSeconds(10)).maximumSize(100_000).build();

    public RevokedBeforeValidator(StringRedisTemplate redis) { this.redis = redis; }

    @Override
    public OAuth2TokenValidatorResult validate(Jwt jwt) {
        Instant iat = jwt.getIssuedAt();
        if (iat == null) return fail("missing iat");
        Optional<Instant> revokedBefore;
        try {
            revokedBefore = local.get(jwt.getSubject(), sub ->
                Optional.ofNullable(redis.opsForValue().get("revoked:" + sub)).map(Instant::parse));
        } catch (RuntimeException e) {
            return fail("revocation store unavailable");      // fail closed (or open, as an explicit, documented risk decision)
        }
        return revokedBefore.filter(iat::isBefore).isPresent() ? fail("token revoked") : OAuth2TokenValidatorResult.success();
    }

    private static OAuth2TokenValidatorResult fail(String msg) {
        return OAuth2TokenValidatorResult.failure(new OAuth2Error("invalid_token", msg, null));
    }
}

Add it to the DelegatingOAuth2TokenValidator. The 10-second local cache bounds Redis load and adds at most 10 s to revocation latency. Set a Redis TTL on each key equal to the maximum access-token lifetime, since older tokens expire anyway. Failing closed means a Redis outage blocks all API traffic — many teams choose fail-open here with an alert because tokens are short-lived; whichever you choose, make it explicit.

15. Interview Questions

Conceptual Is OAuth 2.0 an authentication protocol?

No. It is a delegated authorization framework: access tokens tell resource servers what the bearer may do. Using an access token to infer "the user logged in to my app" is unsafe (a token obtained by another client could be substituted). OpenID Connect adds authentication with the ID token, whose audience is the client and which carries nonce, auth_time and authentication context.

Conceptual What problem does PKCE solve, and why is it now recommended for confidential clients too?

It binds the authorization code to the client instance that started the flow: only the holder of the code_verifier can redeem the code. Originally for public clients (code interception on mobile); for confidential clients it also prevents authorization code injection, where an attacker injects a stolen code into a legitimate client session. RFC 9700 recommends it for all clients.

Conceptual Why are the implicit and password grants deprecated?

Implicit returns tokens in the URL fragment where they leak (history, referrer, extensions) and cannot be sender-constrained; PKCE + code works in browsers now via CORS. Password exposes user credentials to the client, blocks MFA/passkeys/federation, and trains phishing-prone behaviour. RFC 9700 deprecates implicit and forbids password; OAuth 2.1 omits both.

Coding List what your resource server checks on every JWT.

Algorithm in a server-pinned allow-list; key from the trusted issuer's JWKS by kid; signature; iss exact match; aud contains this API; exp/nbf with small skew; typ where used; sender constraint if cnf present; then scopes and business authorization. In Spring: NimbusJwtDecoder with jwsAlgorithm, JwtValidators.createDefaultWithIssuer, plus an audience validator.

Conceptual Explain the RS256/HS256 algorithm confusion attack and its fix.

If a verifier picks the algorithm from the token header and passes the RSA public key as "the key", an attacker sets alg=HS256 and signs with HMAC using the public key bytes as the secret; the verifier computes the same HMAC and accepts. Fix: pin allowed algorithms server-side and use typed key objects so an RSA key cannot be used for HMAC.

Architecture How do you revoke access for a fired employee within one minute in a JWT-based microservice estate?

Disable the account in the IdP and revoke refresh tokens/sessions; emit a revocation event; services hold a small revoked-before map keyed by sub (Redis or pushed in-memory) and reject tokens issued earlier; keep access-token lifetime short (≤ 5 min) so the deny-list stays small and the worst case is bounded. Also kill active server-side sessions via Spring Session's index by principal name. For the highest-risk APIs, use introspection.

Architecture RBAC, ABAC or ReBAC for a Google-Docs-like product?

ReBAC for sharing and inheritance (folders, groups), RBAC for administrative functions, ABAC conditions for context (time-limited links, IP restrictions, data residency). Pure RBAC cannot express "people this doc was shared with" without per-document roles; pure ABAC needs relationship attributes anyway. A Zanzibar-style engine with conditional tuples covers most of it.

Scenario Your SPA stores JWTs in localStorage and the pen test found an XSS. What do you change?

Fix the XSS (encoding, CSP — Chapter 11.3), then move to a BFF: confidential client, tokens server-side, HttpOnly/Secure/SameSite cookie to the browser, CSRF tokens for writes. Revoke existing refresh tokens; shorten access-token lifetime; consider DPoP for any remaining public clients. Explain that HttpOnly does not stop XSS from making requests during the session, but it prevents token exfiltration and long-term reuse.

Scenario Login latency spikes to 3 s under a credential-stuffing attack. What happened and what do you do?

Each attempt runs a deliberately slow password hash, so the attack is also CPU exhaustion. Rate-limit by IP, account and ASN; add bot detection/challenge on suspicious traffic; check against breached-credential lists; isolate login onto separate capacity; push users to passkeys (no hashing per attempt). Do not lower the hash cost.

Conceptual What is session fixation and how does Spring Security prevent it?

An attacker sets a known session ID in the victim's browser; after the victim logs in, the attacker uses the same ID. Spring Security changes the session ID on authentication by default (ChangeSessionIdAuthenticationStrategy), so the pre-login ID is useless.

16. Knowledge Check

  • Authentication establishes a principal; authorization decides per action and resource. OAuth is delegated authorization; OIDC adds authentication.
  • Hash passwords with Argon2id/scrypt/bcrypt via DelegatingPasswordEncoder; follow NIST 800-63B: length, breached-password checks, no forced rotation.
  • Passkeys/WebAuthn are phishing-resistant because the authenticator binds responses to the origin; recovery is the new weak point.
  • Use authorization code + PKCE for every user-facing client, client credentials for machines, device grant for constrained devices; never implicit or password (RFC 9700).
  • Validate JWTs with pinned algorithms, trusted JWKS, issuer, audience, expiry and type; never let the token choose how it is verified.
  • Short access tokens + rotating refresh tokens + targeted deny-lists handle revocation; sender-constraining (DPoP/mTLS) makes theft less useful.
  • Combine RBAC (functions), ReBAC/ownership (data) and ABAC (context); fail closed when a policy engine is unavailable.
