Data Preprocessing & Feature Engineering

Models learn from features, not from data. The step that turns raw rows (nulls, typos, timestamps, free text, wildly different scales, a 1-in-500 positive class) into a clean numeric matrix decides more of a model's quality than the choice of algorithm. This chapter treats preprocessing as what it is for a backend engineer: an input-validation and transformation layer with a strict contract, which must behave identically in training and in production.

  • Prerequisites: Chapter 6.1 (means, variances, norms, conditional probability). Working pandas and NumPy.
  • You will be able to: choose and justify imputation, outlier, scaling and encoding strategies; engineer datetime, text, ratio and aggregate features; select features; handle class imbalance with weights, resampling and thresholds; split data without leakage (random, stratified, grouped, temporal); and package everything in a scikit-learn Pipeline/ColumnTransformer that serialises as one artifact.

1. Introduction: The Input-Validation Layer of ML

In a Spring Boot service you never let raw JSON reach the domain layer. A DTO is deserialised by Jackson, validated with Bean Validation (@NotNull, @Min, @Pattern), normalised (trimmed strings, canonical enums, UTC timestamps), and only then mapped to a domain object. ML has exactly the same layer, with one twist that makes it harder: many of the transformations are learned from data. The mean used to fill missing ages, the standard deviation used for scaling, the list of known categories for one-hot encoding, the per-category target averages for target encoding: all of these are parameters, estimated on the training set and then frozen. Apply them inconsistently between training and serving, or estimate them using data the model should not have seen, and the model silently degrades.

That twist produces the two failure modes this chapter is built around. Training/serving skew: production computes a feature differently from the training pipeline (different null handling, a different time zone, an unseen category that crashes the encoder). Data leakage: information unavailable at prediction time sneaks into training features, so offline metrics are spectacular and production performance is not. Both are bugs of the preprocessing layer, and both are prevented by the same engineering discipline: a single, versioned, testable transformation object that is fit once on training data and used everywhere.

Why do models need preprocessing at all? Because each algorithm family makes assumptions. Linear models and neural networks need numeric inputs on comparable scales (the condition-number argument from Chapter 6.1, §6.6). Distance-based methods (k-NN, k-means, SVM with RBF kernel) treat a feature measured in dollars as thousands of times more important than one measured in years unless you rescale. Most scikit-learn estimators reject NaN. Tree ensembles are more forgiving (scale-invariant, and XGBoost/LightGBM/HistGradientBoosting handle missing values natively), but they still need categorical handling and are just as vulnerable to leakage.

Bridging from Java & Spring Boot

What you already know
Bean Validation on DTOs, @ControllerAdvice for rejecting bad input, MapStruct for DTO-to-entity mapping, Jackson custom deserialisers, Flyway migrations as versioned schema changes, and contract tests that pin an API's shape. You know that validation must be identical on every entry path.
Why that is not enough
Bean Validation rejects bad records; ML preprocessing must usually repair them (impute, clip, bucket) because dropping every imperfect row discards most real data. And the repair rules are statistics estimated from a dataset, which introduces leakage and skew risks that ordinary validation never has.
The modern approach
Express every transformation as a fit/transform object (scikit-learn transformers), compose them in a Pipeline with the model, fit only on the training fold, and serialise the whole thing as one artifact. Add schema/data validation (pandera, Great Expectations, TensorFlow Data Validation) as the ML equivalent of Bean Validation, and use a feature store when the same features feed several models and must be computed identically online and offline.
Where Python and Go fit
Training-time preprocessing lives in Python (pandas/Polars, scikit-learn). For serving, either (a) export the fitted pipeline to ONNX with skl2onnx so a Java service runs preprocessing and model in one ONNX Runtime session, (b) call a Python model server, or (c) re-implement transformations in Java/Go from exported parameters (scaler means, category vocabularies) with golden-file tests proving parity. Option (c) is the classic source of skew; prefer (a) or (b).
In production
Feature pipelines run as batch jobs (Spark, dbt) and streaming jobs (Flink, Kafka Streams) that populate an offline store for training and an online store (Redis, DynamoDB) for low-latency lookups. Your Spring service fetches features by entity key, assembles the vector in a fixed order, validates it, and calls the model.
Use it when / avoid it when
Always put learned preprocessing inside the pipeline. Avoid ad-hoc notebook transformations on the full dataset before splitting, hand-maintained duplicate feature code in two languages, and resampling (SMOTE) anywhere except inside the training fold.

3. Fundamentals

3.1 Data types and measurement levels

Before choosing a transformation, classify each column by what arithmetic is meaningful on it:

  • Continuous numeric (latency in ms, price): differences and ratios meaningful. Scale, transform, bin.
  • Count (orders last 30 days): non-negative integers, usually right-skewed. Log-transform or use count-aware losses.
  • Nominal categorical (country, device type, merchant ID): labels with no order. Arithmetic on their integer codes is meaningless; one-hot, target or hash encode.
  • Ordinal categorical (size S/M/L, education level, severity): ordered, but distances not defined. Ordinal-encode with an explicit order.
  • Datetime: decompose into components, cyclic encodings, and elapsed durations.
  • Text: tokenise and vectorise (TF-IDF, embeddings).
  • Identifiers (user ID, order UUID): usually not features. Using them invites memorisation and leakage; use them as join keys and grouping variables.

3.2 Missing values: mechanisms first

Why a value is missing determines what you may do about it. Rubin's three mechanisms:

  • MCAR (missing completely at random): missingness unrelated to anything, e.g. a sensor dropping 1% of readings at random. Dropping rows loses data but does not bias.
  • MAR (missing at random): missingness depends on observed columns, e.g. income missing more often for younger users, and age is recorded. Imputation conditioned on age can remove the bias.
  • MNAR (missing not at random): missingness depends on the missing value itself, e.g. high earners decline to state income. No imputation from observed data fully fixes this; the fact of missingness is itself informative.

Practical consequence: in real systems missingness is often informative ("no previous orders" for new customers), so the best default is impute plus a missing-indicator column. The model can then learn both a reasonable value and the signal "this was missing".

3.3 Outliers

An outlier is a value far from the bulk of the data. It is either an error (age 999, a timestamp in 1970 from a zero epoch, a price in cents mixed with prices in dollars) or a genuine extreme (a whale customer, a viral post). Errors should be fixed or nulled at the validation layer; genuine extremes should usually be kept but prevented from dominating.

Detection rules. The z-score rule flags |x − mean| / sd > 3, but the mean and sd are themselves dragged by outliers. The IQR rule is robust: compute the first and third quartiles Q1 and Q3, the interquartile range IQR = Q3 − Q1, and flag values outside [Q1 − 1.5·IQR, Q3 + 1.5·IQR]. Example: order values with Q1 = $20, Q3 = $80, IQR = $60; fences are −$70 and $170, so a $5,000 order is flagged. For multivariate outliers, use isolation forests (Chapter 6.4).

Treatments: clip/winsorise to percentiles (e.g. the 1st and 99th, learned on training data); transform with log or Yeo-Johnson so the tail compresses; use robust scaling (median and IQR instead of mean and sd); or use models that are insensitive (trees split on order, not magnitude) and losses that are robust (Huber).

3.4 Scaling and normalisation

Scaling puts features on comparable ranges. Four common transformers, each with intuition and an example on incomes [30k, 45k, 60k, 1,000k]:

Standardisation (StandardScaler): subtract the mean, divide by the standard deviation, so the result has mean 0 and variance 1. Intuition: express each value as "how many standard deviations from typical". With mean 283.75k and sd ≈ 414k, the values become about [−0.61, −0.57, −0.54, 1.73]. The single outlier compresses everyone else into a tiny range.

\[ z = \frac{x - \mu_{\text{train}}}{\sigma_{\text{train}}} \]

Min-max scaling (MinMaxScaler): map the training minimum to 0 and maximum to 1. Same example: [0, 0.015, 0.031, 1]. Even worse with outliers, and production values outside the training range land outside [0, 1].

\[ x' = \frac{x - x_{\min}}{x_{\max} - x_{\min}} \]

Robust scaling (RobustScaler): subtract the median, divide by the IQR. Median 52.5k; with linear interpolation Q1 = 41.25k and Q3 = 295k, so IQR ≈ 253.75k: values ≈ [−0.09, −0.03, 0.03, 3.73]. The bulk keeps its spread; the outlier stays visibly extreme.

Power/log transforms (np.log1p, PowerTransformer with Box-Cox or Yeo-Johnson): reshape skewed distributions to look more Gaussian. log10 of the incomes gives [4.48, 4.65, 4.78, 6.0]: the 33× ratio becomes a difference of about 1.5. Income, prices, counts and latencies are almost always better on a log scale.

Separately, row normalisation (Normalizer) scales each row to unit norm; it is for vectors where direction matters (TF-IDF documents, embeddings), not for tabular features.

Which models need scaling?

Need it: linear/logistic regression with regularisation (the penalty treats all coefficients alike, so unscaled features get unequal penalties), SVMs, k-NN, k-means, PCA, neural networks. Do not need it: decision trees, random forests, gradient-boosted trees, which only compare a feature with thresholds.

3.5 Encoding categorical variables

One-hot encoding creates one binary column per category. Device ∈ {ios, android, web} becomes three columns; "android" is [0, 1, 0]. It assumes nothing about order or similarity. Its problems are high cardinality (a merchant ID with 200,000 values yields 200,000 sparse columns) and unseen categories at serving time. scikit-learn's OneHotEncoder(handle_unknown="infrequent_if_exist", min_frequency=...) groups rare categories into an "infrequent" bucket and maps unseen ones there instead of raising. For linear models with an intercept, one column per feature is redundant (the columns always sum to 1, the rank deficiency from Chapter 6.1), which drop="first" removes; with regularisation this rarely matters.

Ordinal encoding maps ordered categories to integers: S → 0, M → 1, L → 2. Fine for truly ordinal data and for tree models (which can split anywhere). Wrong for nominal data in linear models: encoding {red: 0, green: 1, blue: 2} asserts that green is between red and blue.

Target (mean) encoding replaces each category with the average target value for that category. City "Lyon" with 40 orders of which 6 were fraudulent becomes 0.15. One numeric column regardless of cardinality, and directly predictive. Two dangers. First, small categories are noisy: a city with 1 order and 1 fraud gets 1.0. The fix is smoothing toward the global mean (the MAP shrinkage from Chapter 6.1):

\[ \text{enc}(c) = \frac{n_c\,\bar y_c + m\,\bar y}{n_c + m}, \]

where nc is the category count, ȳc its target mean, ȳ the global mean and m the smoothing strength. With global fraud rate 0.02 and m = 20: Lyon → (40 × 0.15 + 20 × 0.02) / 60 ≈ 0.107; the 1-order city → (1 × 1 + 20 × 0.02) / 21 ≈ 0.067. Second, and worse, target leakage: if a row's own label contributed to its encoding, the feature partially contains the answer. On rare categories the effect is enormous: a category seen once encodes its own label exactly. The fix is out-of-fold encoding: split the training data into k folds and encode each fold using statistics from the other folds only. scikit-learn's TargetEncoder does this cross-fitting inside fit_transform Version-sensitive · checked Nov 2026, and CatBoost uses ordered target statistics for the same purpose.

Hashing (FeatureHasher): map each category string through a hash function into one of, say, 218 columns. No vocabulary to store, handles unseen values gracefully, constant memory; collisions merge unrelated categories. Identical in spirit to sharding keys with a hash ring.

Learned embeddings: in neural networks, a categorical is mapped to a trainable dense vector (an embedding table). The network learns that similar merchants have nearby vectors. This is the standard for very high cardinality in deep recommenders.

3.6 Datetime features

A raw timestamp is a single number that grows forever; models extrapolate poorly on it. Decompose it into what plausibly drives behaviour: hour of day, day of week, month, is_weekend, is_holiday (from a calendar table), and elapsed durations relative to the prediction time (days since signup, minutes since last login, days until contract end). Durations are usually the most predictive and the most leak-prone: they must be computed relative to the moment of prediction, not "now" at training time.

Cyclic encoding: hour 23 and hour 0 are adjacent, but as integers they are 23 apart. Map the hour onto a circle with two features:

\[ h_{\sin} = \sin\!\left(\frac{2\pi h}{24}\right),\qquad h_{\cos} = \cos\!\left(\frac{2\pi h}{24}\right). \]

Hour 0 is (0, 1), hour 6 is (1, 0), hour 23 is (−0.259, 0.966), whose Euclidean distance to hour 0 is about 0.26, the same as one hour apart anywhere on the clock. Trees can use the raw hour directly; linear models and neural networks benefit from the circle. Always normalise time zones: store UTC, derive local hour with the user's zone, exactly as you would in a java.time service.

3.7 Text features

The classical pipeline: lowercase and tokenise; build a vocabulary; represent each document as counts of terms (bag of words), optionally n-grams; reweight with TF-IDF so terms frequent in this document but rare across documents get high weight. For term t in document d over N documents, with df(t) documents containing t:

\[ \text{tfidf}(t,d) = \text{tf}(t,d)\cdot\log\frac{N}{\text{df}(t)}\quad(\text{scikit-learn uses a smoothed variant}). \]

Example: in 1,000 support tickets, "refund" appears in 50 and "the" in 990. In a ticket mentioning each twice, "refund" scores 2 × ln(20) ≈ 6.0 and "the" 2 × ln(1.01) ≈ 0.02. TF-IDF plus logistic regression remains a strong, cheap, explainable baseline for ticket routing and spam filtering. Modern alternatives use pretrained sentence embeddings (Chapter 7.3) as dense features. Simple engineered text features also help: length, number of URLs, ratio of capitals, presence of an order number pattern.

3.8 Feature engineering

Feature engineering encodes domain knowledge as columns, so the model does not have to discover it from scratch. The most productive patterns:

  • Ratios and differences: price per square metre, debt-to-income, (current balance − average balance). A tree needs many splits to approximate a ratio; giving it the ratio directly is far more data-efficient.
  • Aggregations over entities and windows: for a transaction, the customer's count of transactions in the last 1 h / 24 h / 7 d, mean amount over 30 d, number of distinct devices in 24 h. These "velocity features" are the backbone of fraud models and are computed by streaming jobs. Each must be point-in-time correct: aggregated only over events strictly before the prediction timestamp.
  • Interactions: products of features (PolynomialFeatures) let linear models capture "high income AND young". Trees and neural nets learn interactions themselves.
  • Binning: KBinsDiscretizer turns a continuous feature into quantile buckets, letting a linear model learn a non-linear step function; it also stabilises noisy features.
  • Domain transforms: geohash of coordinates, distance to nearest store, haversine distance between billing and shipping addresses, whether an email domain is free-mail.

California housing illustrates it: the raw data has total rooms and households per district, but "rooms per household" is what predicts value. Adding three such ratios to a linear model typically gives a noticeable improvement in RMSE Illustrative; the exact gain depends on the split.

3.9 Feature selection

More features are not free: each one is a pipeline dependency that can break, a source of potential leakage, a latency cost to fetch online, and a degree of freedom to overfit. Selection methods:

  • Filter methods score each feature independently of the model: variance threshold (drop constants), correlation with the target, mutual information, chi-squared for counts. Fast but blind to interactions and redundancy.
  • Wrapper methods search over subsets using model performance: recursive feature elimination (RFECV), forward/backward sequential selection. Accurate but expensive and prone to overfitting the validation set.
  • Embedded methods select as part of training: L1 (lasso) drives coefficients to zero; tree importances; SelectFromModel wraps these.
  • Permutation importance on a validation set (Chapter 6.5) measures how much the score drops when a feature is shuffled: model-agnostic and honest, but misleading for correlated features (shuffle one and its twin covers for it).

Mutual information deserves a sentence of intuition: it is how much knowing X reduces uncertainty (entropy, Chapter 6.1) about Y, I(X; Y) = H(Y) − H(Y | X). Unlike correlation, it detects any dependence, including non-monotone ones. Feature selection must be done inside cross-validation; selecting the top features using all data, then cross-validating, is a classic leakage bug that makes pure noise look predictive.

3.10 Imbalanced data

In fraud (often well under 1% positives), churn, defect detection and medical screening, the class of interest is rare. Problems: accuracy is meaningless (predict "not fraud" always and score 99.5%); the model sees few positives; the default 0.5 threshold is badly placed. Remedies, roughly in the order you should try them:

  1. Use the right metric: precision, recall, PR-AUC, cost-weighted metrics (Chapter 6.5). This changes nothing about the model but everything about your decisions.
  2. Tune the decision threshold on validation data to meet a business constraint (e.g. recall ≥ 0.9, or minimum expected cost). Often the single largest improvement.
  3. Class weights: multiply each example's loss by a weight, e.g. class_weight="balanced" sets wc = n / (K · nc). With 990 negatives and 10 positives, positives get weight 50 and negatives about 0.505. Equivalent in expectation to oversampling without duplicating data. XGBoost's scale_pos_weight = negatives/positives (99 here) does the same.
  4. Resampling: random undersampling of the majority (fast, discards data), random oversampling of the minority (duplicates, can overfit), or SMOTE, which creates synthetic minority points by interpolating between a minority example and one of its k nearest minority neighbours: xnew = xi + u · (xnn − xi), u ∈ [0, 1]. Example: minority points (1, 2) and (3, 6), u = 0.25: synthetic point (1.5, 3).

Resampling distorts probabilities

Weighting or resampling changes the class prior the model sees, so predicted probabilities are no longer calibrated to the real base rate. If downstream logic needs probabilities (expected-loss calculations, bidding), recalibrate on untouched validation data or correct analytically. For a model trained with positives weighted by w, the odds are inflated by w: ptrue ≈ p/(p + w(1 − p)). And never resample the validation or test set: it must reflect production. Recent work also questions whether SMOTE helps strong learners such as gradient-boosted trees compared with weighting and threshold tuning; treat it as one option to validate, not a default Opinion.

3.11 Train, validation and test splits

The purpose of splitting is to simulate the future: the test set stands in for data the model will see after deployment. So the right split mirrors how production differs from training:

  • Random split (e.g. 70/15/15): fine when rows are i.i.d. and the future looks like the past.
  • Stratified split: preserves class proportions in each part. Essential for imbalanced classification; with 1% positives and a 1,000-row test set, a random split could plausibly give 4 or 16 positives.
  • Group split (GroupShuffleSplit, GroupKFold): all rows of one user/patient/device go to the same side. Otherwise the model memorises the user and the test score measures recognition, not generalisation.
  • Temporal split: train on the past, validate on later, test on the latest period, with a gap if labels mature slowly. Mandatory for forecasting, fraud, churn, recommendation: anything where the world drifts.

Roles: the training set fits parameters, including preprocessing statistics; the validation set (or cross-validation folds) chooses hyperparameters, features and thresholds; the test set is touched once, at the end, to estimate production performance. Every time you look at test results and change something, the test set becomes a validation set and its estimate becomes optimistic.

3.12 Data leakage

Leakage is any path by which information unavailable at prediction time reaches the training features or the evaluation. Its signature is offline metrics that are too good to be true. Common forms:

  • Target leakage: a feature derived from the label or from events after it. "Refund issued" as a feature for predicting fraud; "number of support calls in the account's lifetime" for predicting churn when calls happen after the churn decision; a "status" column that gets updated when the outcome is known.
  • Train-test contamination: fitting a scaler, imputer, encoder, feature selector or SMOTE on the full dataset before splitting. The test rows influenced the transformation.
  • Temporal leakage: random splits on time-dependent data, or aggregates computed over windows that extend past the prediction time (a "30-day average" computed with a centred window).
  • Group leakage: the same entity in train and test (duplicate rows, multiple images of the same patient).
  • Proxy leakage: an ID or timestamp that correlates with the label because of how the data was collected (positive examples were collected in a later batch, so higher IDs mean positive).

The defence is architectural: features computed point-in-time from an event log, transformations fit only inside the training fold (Pipelines), splits that mirror production, and a sceptical review of any feature with suspiciously high importance.

3.13 Pipelines and ColumnTransformer

A scikit-learn Pipeline chains transformers and a final estimator into one estimator. Calling fit fits each step on the output of the previous one, using only the data passed in; predict applies the fitted transformations and the model. A ColumnTransformer routes different columns through different sub-pipelines (numeric: impute → scale; categorical: impute → one-hot) and concatenates the results. Together they give you:

  • Leak-proof cross-validation: cross_val_score(pipe, X, y) refits the preprocessing on each training fold.
  • One artifact: serialise the fitted pipeline with joblib/skops (or export to ONNX), and serving applies exactly the training transformations.
  • Joint tuning: hyperparameters of preprocessing steps (preprocess__num__imputer__strategy) are searched alongside model hyperparameters.

It is the ML analogue of a Spring HandlerInterceptor chain plus a validated DTO mapper, packaged as one deployable unit.

4. Internal Working: What fit and transform Really Do

4.1 The transformer contract

Every scikit-learn transformer implements two phases. fit(X, y=None) learns state from data and stores it in attributes ending in an underscore: StandardScaler.mean_ and scale_, SimpleImputer.statistics_, OneHotEncoder.categories_, TargetEncoder.encodings_. transform(X) applies that frozen state to any data, training or new. fit_transform does both, sometimes with a different, leakage-aware behaviour (TargetEncoder's cross-fitting happens only in fit_transform, so the training-set encoding differs from what transform would produce on the same rows; this is intentional).

Think of the fitted transformer as a compiled configuration: like a Spring @ConfigurationProperties bean whose values were computed from the training set rather than read from YAML, and which must never be recomputed at request time.

4.2 How a Pipeline executes

  1. Pipeline.fit(X_train, y_train): for each intermediate step i, call fit_transform on the current data and pass the output to step i + 1; finally call fit on the estimator.
  2. Pipeline.predict(X_new): for each intermediate step call transform only (no refitting), then predict on the estimator.
  3. Inside cross_val_score or GridSearchCV, the whole pipeline is cloned (unfitted) and fit on each training fold separately, so each fold's validation rows never influence the preprocessing state used to score them.

4.3 How ColumnTransformer assembles the matrix

A ColumnTransformer holds a list of (name, transformer, columns) triples. On fit, it selects each column subset (by name, index or a make_column_selector(dtype_include=...) rule), fits each sub-transformer independently, and horizontally stacks their outputs in the declared order, followed by any remainder columns (dropped by default). If any output is sparse and the overall density is below sparse_threshold, the result is a SciPy sparse matrix. get_feature_names_out() reports the final column names (e.g. cat__workclass_Private), which you need for interpretability and for verifying serving parity. With set_output(transform="pandas"), outputs are DataFrames with those names.

4.4 How native missing-value handling works in boosted trees

When a histogram-based gradient-boosting implementation (XGBoost, LightGBM, scikit-learn's HistGradientBoosting*) evaluates a split on feature j at threshold t, it computes the loss reduction twice: once sending all rows with missing xj to the left child and once to the right, and keeps the better "default direction". At prediction time, a missing value follows that learned direction. Missingness thus becomes a learned signal, without imputation, as long as training data contained missing values for that feature.

4.5 How SMOTE generates points

  1. For each minority example xi, find its k nearest minority-class neighbours (default k = 5) in feature space (so features must be scaled).
  2. To create a synthetic point, pick one neighbour xnn at random and a random u ∈ [0, 1]; output xi + u (xnn − xi), a point on the segment between them.
  3. Repeat until the requested ratio is reached. Variants: Borderline-SMOTE focuses on minority points near the class boundary; SMOTE-NC handles mixed categorical/numeric features by taking the majority category among neighbours.

In imbalanced-learn, samplers implement fit_resample, and its Pipeline applies resampling only during fit, never during predict. That is why you must use imblearn.pipeline.Pipeline, not scikit-learn's, when a sampler is a step.

4.6 Point-in-time feature joins

For a training example "transaction T at time t0", a correct velocity feature is computed from events with timestamp strictly before t0 (and, if features in production are refreshed with a delay, before t0 − delay). Feature stores implement this as an as-of join: for each label row, take the latest feature value whose event time ≤ t0. In pandas this is pd.merge_asof; in SQL a window function or a lateral join; in Spark a range join. Getting this wrong (a plain join on the latest feature snapshot) is the most common source of temporal leakage in production ML.

5. Architecture: Preprocessing in the ML System

Reading the diagram: the split happens before any statistics are learned, and only the training partition flows into fit. Validation and test rows are passed through transform by the same artifact. On the serving side, the Spring layer is responsible for structural validation and fetching features, but all learned transformations come from the artifact produced in training, distributed through the model registry. If the serving path reimplemented scaling or encoding by hand, a second arrow of "logic" would appear, and with it skew.

Reading the diagram: each branch is an independent fit/transform chain over its own columns, so the numeric branch never sees category strings and vice versa. The concatenation order is fixed by the declaration, which is what makes the output column order stable between training and serving. Note the ordinal branch uses an explicit category order supplied by a human, because alphabetical order ("Bachelors" < "Doctorate" < "HS-grad") is meaningless.

Reading the diagram: every fold gets a fresh clone, so no fitted state carries over from a previous fold. Each validation fold plays the role of "future data" for the preprocessing as well as the model. If instead you had scaled or selected features on the full dataset first, each validation fold would have contributed to the statistics used to transform it: a small leak for scaling, a large one for target encoding, feature selection and SMOTE.

Reading the diagram: the same feature definition (say, "transactions per card in the last hour") is materialised twice: into a low-latency online store for serving, and into a time-stamped offline store for training. Training sets are built with point-in-time joins so each label sees feature values as they were at that moment. Because both stores come from one definition, the online and offline values agree, eliminating the most insidious skew. This is what Michelangelo's feature store, Feast and Chronon provide.

6. The Math Behind the Transformations

6.1 Why standardisation helps gradient descent

In words: unscaled features stretch the loss bowl into a narrow ravine, and the learning rate must be small enough for the steepest wall, so progress along the floor crawls. Standardising makes the bowl rounder.

For linear regression with MSE the Hessian is \( \frac{2}{m}X^\top X \). If feature 1 is age (sd ≈ 13) and feature 2 is income (sd ≈ 40,000) and both are centred and roughly uncorrelated, the diagonal entries scale with their variances, about 169 versus 1.6 × 109: a condition number near 107. Using the rate bound from Chapter 6.1, convergence along the age direction needs on the order of 107 iterations. After standardisation both diagonals are 1 and, absent correlation, κ ≈ 1: gradient descent converges in a handful of steps.

6.2 Variance shrinkage under mean imputation

In words: filling gaps with the mean adds points at the centre, so the variance shrinks and the feature looks less informative than it is.

If a fraction r of n values are missing and replaced by the observed mean \( \bar x \), the sample variance becomes

\[ s^2_{\text{imputed}} = \frac{1}{n}\sum_{\text{observed}}(x_i - \bar x)^2 + \frac{1}{n}\sum_{\text{imputed}}0 = (1-r)\,s^2_{\text{observed}}. \]

With 30% missing, variance drops by 30%; correlations with other variables are attenuated similarly. This is why multiple imputation and indicator columns exist.

6.3 Smoothed target encoding as a Bayesian estimate

Treat each category's positive rate θc as unknown, with a Beta prior centred on the global rate p̄ with strength m: Beta(m p̄, m(1 − p̄)). After observing kc positives in nc rows, the posterior mean is

\[ \mathbb{E}[\theta_c\mid\text{data}] = \frac{k_c + m\bar p}{n_c + m} = \frac{n_c}{n_c+m}\,\bar y_c + \frac{m}{n_c+m}\,\bar p. \]

That is exactly the smoothing formula in §3.5: a weighted average of the category mean and the global mean, with weight shifting to the category as its count grows. scikit-learn's TargetEncoder(smooth="auto") chooses the weight with an empirical-Bayes estimate of the between-category variance.

6.4 How much does target leakage inflate a feature?

Consider a category with nc rows and a non-cross-fitted mean encoding. Each row's encoding includes its own label with weight 1/nc, so the correlation between the encoding and the row's label is inflated by roughly that amount. For nc = 1 the encoding equals the label. With a high-cardinality ID where most categories have 1–3 rows, an unregularised, non-cross-fitted target encoding is close to a copy of the target, and a model will reach near-perfect training and in-sample validation scores. Out-of-fold encoding removes the self-contribution entirely.

6.5 Class weights and the expected loss

With weights w1 for positives and w0 for negatives, the weighted log-loss is

\[ \mathcal{L}_w = -\frac{1}{m}\sum_i\Big[w_1\,y_i\log\hat p_i + w_0\,(1-y_i)\log(1-\hat p_i)\Big]. \]

For a group of identical inputs with true positive rate π, minimising this over p̂ gives \( \hat p = \frac{w_1\pi}{w_1\pi + w_0(1-\pi)} \): the model predicts the probability under a re-weighted prior. With π = 0.01 and w1/w0 = 99, p̂ = 0.99/(0.99 + 0.99) = 0.5. Invert this relation to recover calibrated probabilities. The minimiser derivation: set the derivative \( -w_1\pi/\hat p + w_0(1-\pi)/(1-\hat p) \) to zero.

6.6 Mutual information

For discrete X and Y, \( I(X;Y) = \sum_{x,y}p(x,y)\log\frac{p(x,y)}{p(x)p(y)} \), the KL divergence between the joint distribution and the product of marginals: zero exactly when independent. Example: a binary feature X and label Y with p(X=1,Y=1) = 0.1, p(X=1,Y=0) = 0.1, p(X=0,Y=1) = 0.0, p(X=0,Y=0) = 0.8. Marginals: p(X=1) = 0.2, p(Y=1) = 0.1. I = 0.1 ln(0.1/0.02) + 0.1 ln(0.1/0.18) + 0.8 ln(0.8/0.72) ≈ 0.161 − 0.059 + 0.084 = 0.186 nats, out of H(Y) ≈ 0.325 nats: the feature removes more than half the uncertainty about Y.

import numpy as np
import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.datasets import fetch_openml
from sklearn.impute import SimpleImputer

from sklearn.preprocessing import FunctionTransformer, OneHotEncoder, OrdinalEncoder, StandardScaler

SEED = 42
df = fetch_openml("adult", version=2, as_frame=True).frame

    X, y, test_size=0.2, stratify=y, random_state=SEED)

ordered_edu = [["Preschool", "1st-4th", "5th-6th", "7th-8th", "9th", "10th", "11th", "12th",
                "HS-grad", "Some-college", "Assoc-voc", "Assoc-acdm", "Bachelors",
                "Masters", "Prof-school", "Doctorate"]]
nominal = ["workclass", "marital-status", "occupation", "relationship", "race", "sex", "native-country"]

preprocess = ColumnTransformer(
    transformers=[
        ("skewed", make_pipeline(
            SimpleImputer(strategy="median"),
            FunctionTransformer(np.log1p, feature_names_out="one-to-one"),
            StandardScaler()), skewed),

            SimpleImputer(strategy="median", add_indicator=True),

            SimpleImputer(strategy="constant", fill_value="MISSING"),
            OneHotEncoder(handle_unknown="infrequent_if_exist", min_frequency=50,
                          sparse_output=False)), nominal),
    ],
    remainder="drop",
    verbose_feature_names_out=True,
).set_output(transform="pandas")

    ("preprocess", preprocess),

])

import numpy as np
import pandas as pd
from sklearn.base import BaseEstimator, TransformerMixin

class DatetimeFeatures(BaseEstimator, TransformerMixin):
    """Stateless transformer: decomposes a UTC timestamp column into model-ready features."""
    def __init__(self, column="event_ts", tz="Europe/Paris"):
        self.column, self.tz = column, tz

    def fit(self, X, y=None):
        return self

    def transform(self, X):
        ts = pd.to_datetime(X[self.column], utc=True).dt.tz_convert(self.tz)
        out = pd.DataFrame(index=X.index)
        hour = ts.dt.hour
        out["hour_sin"] = np.sin(2 * np.pi * hour / 24)
        out["hour_cos"] = np.cos(2 * np.pi * hour / 24)
        out["dow"] = ts.dt.dayofweek
        out["is_weekend"] = (ts.dt.dayofweek >= 5).astype(int)
        signup = pd.to_datetime(X["signup_ts"], utc=True)
        # Duration relative to the EVENT time, never to "now"
        out["days_since_signup"] = (pd.to_datetime(X[self.column], utc=True) - signup).dt.days
        return out

    def get_feature_names_out(self, input_features=None):
        return np.array(["hour_sin", "hour_cos", "dow", "is_weekend", "days_since_signup"])

9.4 A composite leakage incident

Illustrative A team builds a churn model on a customer table snapshot. Validation ROC-AUC is 0.97. In production, it is 0.66. Root cause: the snapshot's plan_status and last_support_contact columns were overwritten when customers cancelled, so for churned customers they reflected the cancellation process itself. The fix was architectural: rebuild training data from the event log with point-in-time joins at a fixed "prediction date" for each customer, and add a test asserting that every feature timestamp is strictly before the label's reference time. This pattern (a mutable table masquerading as history) is the most common leakage story the author has encountered Opinion.

12. Common Mistakes

  • Fitting transformers before splitting. StandardScaler().fit_transform(X) then train_test_split. Minor leak for scalers, major for selectors, target encoders and SMOTE.
  • Oversampling before cross-validation. Synthetic points derived from a validation example end up in training, so the model is evaluated on near-copies of what it trained on.
  • Resampling or reweighting the test set. Test data must reflect production prevalence or metrics like precision are meaningless.
  • Ordinal-encoding nominal categories for linear models. Imposes a fake order and fake distances.
  • Using IDs as features. The model memorises entities and fails on new ones; also a privacy hazard.
  • "Now"-relative durations. Computing days_since_signup as of the training run date rather than as of each event time.
  • Silent category drift. Upstream renames "iOS" to "ios"; the encoder maps everything to unknown; predictions shift. Monitor the unknown-category rate.
  • Time-zone mismatch. Training used UTC hour, serving used server local time. A cyclic hour feature makes this a quiet 1–2 hour shift that degrades accuracy without errors.
  • Dropping rows with nulls in training while production rows still have nulls. The model never learned how to handle them, and the serving code improvises.
  • Trusting suspiciously important features. If one feature carries most of the importance and the AUC is near 1, assume leakage until proven otherwise.

13. Production Concerns

13.1 Training/serving parity tests

Keep a golden dataset of a few thousand raw rows, including nulls, unseen categories and extreme values. In CI, run them through the training pipeline and through the serving path (ONNX in Java, or the model server) and assert outputs match within tolerance. This is a contract test, and it catches the majority of skew bugs before deployment.

13.2 Monitoring

Per feature: null rate, unknown-category rate, min/max/quantiles, PSI against training. Per model: score distribution, fraction above the decision threshold. Emit these as Micrometer metrics from the scoring service or compute them in a streaming job over request logs. Alert on the unknown-category rate in particular; it is the earliest signal of an upstream schema change.

13.3 Performance

Preprocessing can dominate inference latency for small models. One-hot encoding into dense arrays wastes memory (use sparse or index-based inputs), Python-level apply calls are slow, and per-request feature lookups across several stores add network round-trips. Batch lookups (Redis MGET/pipelining), precompute static features, and keep the transformation graph in a compiled runtime (ONNX Runtime) for hot paths.

13.4 Security and privacy

Preprocessing touches raw PII. Minimise: hash or tokenise identifiers before they reach the feature pipeline; never use protected attributes as features without a fairness and legal review (Chapter 6.5), and check for proxies (postcode can proxy ethnicity). Pickled artifacts execute arbitrary code on load: only load joblib/pickle files from your own registry with integrity checks, or use safer formats (skops, ONNX).

13.5 Maintainability

Version the pipeline with the model; record the scikit-learn version (pickles are not guaranteed compatible across versions); log feature names and order with every model; write custom transformers as small, unit-tested classes with get_feature_names_out. Treat feature definitions like database migrations: additive changes are easy, renames and semantic changes require coordinated retraining.

Exercise 1 · Foundational

Training values of a feature: [2, 4, 4, 4, 5, 5, 7, 9]. (a) Compute the standardised value of a serving input x = 11 using training statistics (population sd). (b) Compute min-max scaled x = 11. (c) What do the results tell you about each scaler with out-of-range inputs?

Solution

(a) Mean = 40/8 = 5. Squared deviations: 9, 1, 1, 1, 0, 0, 4, 16 = 32; variance 4; sd 2. z = (11 − 5)/2 = 3.0. (b) (11 − 2)/(9 − 2) = 9/7 ≈ 1.286. (c) Standardisation degrades gracefully: 3 sd is unusual but representable. Min-max produces values outside [0, 1], which can break models (such as networks with bounded-input assumptions) and signals the input is beyond the training range: worth monitoring.

Exercise 2 · Intermediate

Global conversion rate is 5%. Category A has 2,000 rows at 8%; category B has 4 rows with 2 conversions. Compute smoothed target encodings with m = 100. Then explain what happens to B's encoding without smoothing and without cross-fitting.

Solution

A: (2000 × 0.08 + 100 × 0.05)/2100 = (160 + 5)/2100 ≈ 0.0786. B: (2 + 5)/104 ≈ 0.0673. Unsmoothed, B = 0.5, ten times the global rate on four rows of evidence. Without cross-fitting, each of B's four rows contributes its own label: the two converters see an encoding computed with themselves included, so the feature partially reveals the label. Out-of-fold, a converter in B would see the rate among the other B rows in different folds, removing self-contribution.

Exercise 3 · Intermediate

You train with class_weight giving positives weight 20 and negatives weight 1. True base rate is 2%. For an input whose true probability is 10%, what probability does the (ideal) weighted model output? Derive the correction formula and apply it.

Solution

From §6.5, p̂ = w₁π / (w₁π + w₀(1 − π)) = 20 × 0.1 / (2 + 0.9) = 2/2.9 ≈ 0.690. Inverting: odds(p̂) = (w₁/w₀) odds(π), so π = p̂ / (p̂ + (w₁/w₀)(1 − p̂)) = 0.690 / (0.690 + 20 × 0.310) = 0.690/6.89 ≈ 0.100. The base rate does not enter, only the weight ratio. In practice, also verify with a calibration curve on validation data.

Exercise 4 · Advanced

Design the training-data generation for a "will this order be cancelled within 24 h" model. You have an orders table (mutable status), an order_events Kafka topic and a customers table. Specify the prediction time, the label definition, three features with their point-in-time rules, and the split.

Solution

Prediction time t₀ = order creation timestamp (the model scores at checkout). Label = 1 if a CANCELLED event occurs in (t₀, t₀ + 24 h]; rows less than 24 h old at training time are excluded because their labels are immature. Features, all from the event log as-of t₀: (1) customer's cancellation rate over orders placed in [t₀ − 180 d, t₀ − 24 h) (the 24 h offset ensures those older orders' labels were known at t₀); (2) number of orders by the customer in the last 1 h before t₀; (3) payment method and basket value from the order-created event itself. Never use the orders.status column, which is mutated. Split temporally: train on months 1–9, validate on month 10, test on month 11, with a 1-day gap between periods. Group-by-customer considerations are secondary given the temporal split but check for heavy repeat customers.

Exercise 5 · Advanced

Write a custom scikit-learn transformer QuantileClipper that learns per-column 1st and 99th percentiles in fit and clips in transform, supports get_feature_names_out, and works inside a ColumnTransformer.

Solution
import numpy as np
from sklearn.base import BaseEstimator, TransformerMixin, OneToOneFeatureMixin
from sklearn.utils.validation import check_is_fitted, validate_data  # sklearn >= 1.6

class QuantileClipper(OneToOneFeatureMixin, TransformerMixin, BaseEstimator):
    def __init__(self, lower=0.01, upper=0.99):
        self.lower, self.upper = lower, upper

    def fit(self, X, y=None):
        X = validate_data(self, X, ensure_all_finite="allow-nan")
        self.low_ = np.nanquantile(X, self.lower, axis=0)
        self.high_ = np.nanquantile(X, self.upper, axis=0)
        return self

    def transform(self, X):
        check_is_fitted(self)
        X = validate_data(self, X, reset=False, ensure_all_finite="allow-nan")
        return np.clip(X, self.low_, self.high_)

The quantiles are learned state (trailing underscore), estimated only on training data; OneToOneFeatureMixin provides get_feature_names_out. On scikit-learn versions before 1.6, use self._validate_data instead of validate_data and force_all_finite instead of ensure_all_finite.

15. Interview Questions

Conceptual What is data leakage? Give three distinct examples.

Leakage is information available during training or evaluation that would not be available at prediction time, inflating offline metrics. Examples: (1) target leakage, a feature derived from the outcome (refund flag predicting fraud); (2) preprocessing leakage, fitting a scaler, target encoder, feature selector or SMOTE on data including the test set; (3) temporal leakage, random splits or look-ahead windows on time-dependent data; (4) group leakage, the same patient or user in train and test.

Conceptual When does a model need feature scaling and when does it not?

Needed for models whose optimisation or geometry depends on magnitudes: gradient-based linear models and neural networks (conditioning), regularised models (penalty fairness), distance/kernel methods (k-NN, k-means, SVM-RBF), PCA (variance-driven). Not needed for tree-based models, which split on thresholds and are invariant to monotone transformations.

Conceptual Explain target encoding, its risks, and how to mitigate them.

Replace a category by the mean target for that category. Risks: noise for rare categories, and leakage because a row's own label contributes to its encoding. Mitigate with Bayesian smoothing toward the global mean and out-of-fold (cross-fitted) or ordered encoding, as in scikit-learn's TargetEncoder and CatBoost; handle unseen categories with the global mean.

Scenario Offline ROC-AUC is 0.98, production is 0.70. How do you investigate?

Suspect leakage and skew. Check feature importance for dominant features and inspect their provenance and timestamps; rebuild a validation set with a temporal split and point-in-time features; compare feature distributions between training and production logs (null rates, unknown categories, ranges); replay production requests through the training pipeline and compare scores (parity test); verify label definitions match. Also consider genuine drift if the training data is old.

Scenario Fraud rate is 0.2%. A colleague proposes SMOTE to 50/50 before splitting. Respond.

Splitting after SMOTE leaks synthetic points derived from test examples into training and makes the test set unrepresentative. Correct order: split (temporally for fraud), then optionally resample only inside the training fold via an imblearn Pipeline. Before SMOTE, try class weights or scale_pos_weight, evaluate with PR-AUC and cost-based metrics, and tune the threshold on untouched validation data. Recalibrate probabilities if they feed cost calculations.

Architecture How do you guarantee the same feature values at training and serving time across a Python training stack and a Java serving stack?

Options in order of preference: export the whole pipeline (preprocessing + model) to ONNX and run it in ONNX Runtime Java; or serve via a Python model server so the same code runs; or use a feature store with one definition materialised online and offline. If logic must be reimplemented, export learned parameters as data, generate code from one spec, and enforce parity with golden-file contract tests in CI. Monitor unknown-category and null rates in production.

Coding Build a ColumnTransformer that median-imputes and scales numeric columns and one-hot encodes categoricals with unknown handling.
from sklearn.compose import ColumnTransformer, make_column_selector as sel
from sklearn.impute import SimpleImputer
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

pre = ColumnTransformer([
    ("num", make_pipeline(SimpleImputer(strategy="median", add_indicator=True), StandardScaler()),
     sel(dtype_include="number")),
    ("cat", make_pipeline(SimpleImputer(strategy="most_frequent"),
                          OneHotEncoder(handle_unknown="ignore")),
     sel(dtype_include=["object", "category"])),
])

Then wrap with the estimator in a Pipeline and cross-validate the whole thing.

Conceptual Why encode hour-of-day with sine and cosine rather than a single sine?

A single sine maps two different hours to the same value (hour 3 and hour 9 both give sin = 0.707 with a 24-hour period), destroying information. Sine and cosine together give a unique point on the unit circle for each hour, while preserving adjacency between 23:00 and 00:00.

Conceptual What are MCAR, MAR and MNAR and why does the distinction matter?

MCAR: missingness independent of everything; MAR: depends only on observed variables; MNAR: depends on the unobserved value itself. Under MCAR dropping or simple imputation is unbiased (but wasteful); under MAR conditioning on observed variables can correct bias; under MNAR no method using only observed data is fully unbiased, and the missingness indicator itself carries signal. In practice, add indicators and validate.

16. Knowledge Check

  • Preprocessing is an input-validation and transformation layer whose parameters are learned; fit on training data only and reuse the fitted object everywhere.
  • Impute with median plus missing indicators by default; GBDTs can learn missing-value directions natively.
  • Log-transform skewed positives; standardise for linear/NN/distance models; trees need no scaling.
  • One-hot for low cardinality; cross-fitted, smoothed target encoding or hashing for high; embeddings in neural networks.
  • Engineer ratios, windowed aggregates and cyclic time features; compute every aggregate point-in-time.
  • For imbalance: right metric, threshold tuning and class weights first; resample only inside training folds; recalibrate.
  • Choose the split that simulates production: stratified, grouped, temporal.
  • Pipelines plus ColumnTransformer make cross-validation honest and produce one deployable artifact; parity tests guard the Java serving path.

Which preprocessing step causes the largest leakage if fit on the full dataset before cross-validation?

  1. StandardScaler on numeric columns
  2. Selecting the top 20 of 10,000 features by correlation with the label
  3. Lowercasing text
  4. Converting timestamps to UTC
Supervised selection uses labels from validation folds to pick features, producing large optimistic bias (even on pure noise). Scaling leaks only mean/variance information; lowercasing and UTC conversion are stateless.

A feature has 150,000 distinct merchant IDs and you are training logistic regression. Best default encoding?

  1. OrdinalEncoder
  2. Dense one-hot
  3. Cross-fitted smoothed target encoding or feature hashing
  4. Drop the feature unconditionally
Ordinal codes impose fake order in a linear model; dense one-hot is enormous and sparse in information per column; target encoding (leak-safe) or hashing keep dimensionality manageable.

Where must SMOTE be applied?

  1. Only to the training portion, inside each CV fold, via an imblearn Pipeline
  2. To the whole dataset before splitting
  3. To the test set so metrics are balanced
  4. At serving time to balance incoming requests
Synthetic points must never be derived from or placed into evaluation data, and serving data must not be altered.

You predict next-week demand. Which split is appropriate?

  1. Random 80/20
  2. Stratified by store
  3. GroupKFold by SKU
  4. Train on earlier weeks, validate and test on later weeks
Forecasting must simulate predicting the future from the past; random splits leak future information through lags and seasonality.
