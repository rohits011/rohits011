1. Introduction: Untrusted Data Meets an Interpreter or a Decision

Almost every vulnerability in this chapter reduces to one of two shapes. Either untrusted data reaches an interpreter (SQL engine, browser, shell, deserializer, file system, URL fetcher) in a position where it is treated as code or as a target, or a security decision is made on the wrong basis (the object's owner is not checked, the client supplies a field that should be server-controlled, a request's origin is assumed). Once you see vulnerabilities this way, the defences become systematic: keep data and code in separate channels (parameter binding, contextual encoding, typed APIs), make decisions on server-held facts, and constrain what any single request can consume.

APIs make the second shape dominant. A server-rendered page used to hide object IDs and fields behind forms; a JSON API exposes them directly, and clients — mobile apps, SPAs, partners, scripts, and now AI agents — can call any endpoint with any payload. That is why OWASP maintains a separate API Security Top 10, and why its top entries are about authorization rather than injection.

Bridging from Java & Spring Boot

What you already know
Spring Data JPA derived queries and @Query with named parameters bind values safely; Thymeleaf's th:text HTML-escapes; CsrfFilter rejects state-changing browser requests without a token; Bean Validation (@Valid, @Size, @Pattern) rejects malformed input; Jackson maps JSON to your DTOs.
Why that is not enough
Each safe default has an escape hatch you will eventually use: native queries with string concatenation for a dynamic ORDER BY; th:utext for "rich text"; CSRF disabled globally because "we are an API" while a cookie session still exists; binding JSON straight onto JPA entities (mass assignment); RestTemplate fetching a user-supplied URL (SSRF); ObjectInputStream in an old integration. Bean Validation checks shape, not authorization.
The modern approach
Treat every API as public; authorize every object and every property; bind requests to dedicated DTOs; limit every resource (rate, size, page, time); encode output by context and add CSP with nonces; use SameSite cookies plus CSRF tokens for cookie-authenticated endpoints; route outbound fetches of user-influenced URLs through an allow-list and egress controls; never deserialize untrusted native formats; and automate detection with SAST, SCA, DAST and security unit tests.
Where Python and Go fit
Python's DB-API placeholders and SQLAlchemy bind parameters are safe; f-strings into execute() are not. Jinja2 autoescapes only if enabled (Flask enables it for HTML templates). Pydantic models give strict request schemas (use extra="forbid"). Go's database/sql placeholders and html/template (contextual auto-escaping) are safe; text/template for HTML is not. Both ecosystems have pickle/gob-style serializers you must not expose.
In production
An API gateway enforces authentication, quotas and schema; services enforce object- and property-level authorization; a WAF provides virtual patching but is never the primary control; SAST runs on every PR; DAST runs nightly against staging; the API inventory is generated from code (OpenAPI) so nothing is forgotten.
Use it when / avoid it when
Use the full checklist on every endpoint that accepts input or returns data — that is all of them. Avoid relying on client-side validation, obscurity (unguessable URLs), or a WAF as substitutes for server-side controls.

2. History

  • 1998 — SQL injection is described publicly in Phrack magazine (issue 54) by Jeff Forristal ("rain.forest.puppy").
  • 2000 — Microsoft security engineers coin the term "cross-site scripting".
  • 2001 — Cross-site request forgery is described (initially as "session riding" in some literature); it remained under-appreciated for years.
  • 2005 — The Samy worm spreads through MySpace via stored XSS, adding over a million "friends" in about a day — the first famous XSS worm.
  • 2012 — GitHub is affected by a Rails mass-assignment bug that let a user attach an SSH key to another account (CVE-2012-2055); Rails moves to "strong parameters".
  • 2012–2016 — W3C Content Security Policy Level 1 (2012) and Level 2 (2016) give sites a declarative way to restrict script sources; Level 3 introduces strict-dynamic.
  • 2015 — Frohoff and Lawrence's "Marshalling Pickles" talk shows practical Java deserialization gadget chains (Apache Commons Collections); a wave of CVEs follows across Java middleware. Java adds serialization filtering (JEP 290, Java 9, backported to 8u121).
  • 2016–2020 — The SameSite cookie attribute ships in browsers (2016); Chrome makes Lax the default for cookies without the attribute (rolled out in 2020).
  • 2019 — OWASP publishes the first API Security Top 10. Capital One's breach via SSRF and an over-privileged role leads AWS to launch IMDSv2 (November 2019).
  • 2020 — Trusted Types ships in Chromium (version 83), enforcing safe sinks for DOM XSS.
  • 2021 — OWASP Top 10 2021 adds SSRF as its own category; Java 17 adds context-specific deserialization filters (JEP 415).
  • 2023 — OWASP API Security Top 10 2023 adds Unrestricted Access to Sensitive Business Flows, SSRF and Unsafe Consumption of APIs; MOVEit's SQL injection is exploited at scale.
  • 2025 — OWASP Top 10:2025 folds SSRF into Broken Access Control; AI-generated code becomes a significant source of new code to review.

3.2 BOLA, BOPLA and BFLA — three levels of authorization

Think of authorization at three granularities. Function level: may this caller invoke DELETE /users/{id} at all? Object level: may this caller act on user 42? Property level: may this caller read user.ssn or write user.role? Frameworks help with the first; the second and third are business logic in your service and DTO design. BOLA is the API list's #1 because every endpoint that takes an ID is a candidate, and automated scanners rarely detect it — they do not know who should own what.

3.3 Mass assignment

Mass assignment happens when a framework binds all request fields onto an object that has fields the client must not control. In Spring, the classic form is accepting a JPA entity as @RequestBody: a client adds "role":"ADMIN" or "accountBalance":1000000 and Jackson happily sets it, then save() persists it. The fix is structural: request DTOs (Java records) containing only client-settable fields, explicit mapping to the entity, and FAIL_ON_UNKNOWN_PROPERTIES so unexpected fields are rejected rather than silently ignored. For form binding with @ModelAttribute, use WebDataBinder.setAllowedFields (Spring Framework 6.1 also added setDeclarativeBinding to bind only via constructor).

3.4 Rate limiting algorithms

  • Fixed window — count requests per key per calendar window (e.g. per minute). Simple; allows bursts of up to 2× the limit at window boundaries.
  • Sliding window log — store timestamps of recent requests; exact but memory-heavy.
  • Sliding window counter — weighted combination of the current and previous fixed windows; good approximation with O(1) memory.
  • Token bucket — a bucket of capacity B refills at rate r; each request takes a token. Allows bursts up to B while enforcing long-run rate r. Used by Bucket4j, Envoy, AWS API Gateway, Spring Cloud Gateway's Redis rate limiter.
  • Leaky bucket — queue drained at a constant rate; smooths output.
  • Concurrency limits — cap in-flight requests (bulkheads), which protect against slow, expensive calls better than rate limits do.

Choose the key carefully: per IP (weak behind NAT and trivially rotated by attackers), per API key/client ID, per authenticated user, per tenant, and per sensitive resource (e.g. per phone number for OTP sends). Layers: gateway global limits, service per-user limits, and business-flow limits (API6).

3.5 Input validation principles

Validation answers "is this input well-formed and within expected bounds?" It reduces attack surface but does not replace output encoding or parameter binding, because valid input can still be dangerous in another context (an Irish surname with an apostrophe is valid and still breaks concatenated SQL). Rules: validate on the server; prefer allow-lists (enumerations, regex for formats, ranges) over deny-lists; canonicalise before validating (Unicode normalisation, URL decoding once); validate types, lengths, ranges and cross-field rules; reject rather than "sanitise and continue" where possible; and enforce limits on collections and nesting depth to prevent resource exhaustion.

3.6 Injection — the general model

Injection occurs when a program builds a string in some language (SQL, JPQL, HQL, LDAP filter, OS shell, XPath, SpEL, OGNL, template syntax, MongoDB query JSON, log format) by concatenating untrusted data, and the interpreter parses the whole string. The universal fix is to use an API that keeps code and data in separate channels: prepared statements, typed query builders, argument arrays for processes, escaping functions specific to the target grammar only as a last resort.

  • SQL injection — e.g. "... WHERE email = '" + email + "'". With input ' OR '1'='1 the WHERE clause becomes always true.
  • JPQL/HQL injection — the same bug one layer up; JPA is not magic if you concatenate into createQuery.
  • NoSQL injection — in MongoDB, passing a parsed JSON object where a string is expected: {"username": {"$ne": null}} matches any user. Spring Data MongoDB's derived queries and Criteria API are safe; string-built @Query JSON or BasicQuery with concatenation is not.
  • OS command injection — passing user data to sh -c. Use ProcessBuilder with an argument list and no shell, plus allow-listed values.
  • Expression language injection — evaluating user input as SpEL (parser.parseExpression(userInput)) is remote code execution. Use SimpleEvaluationContext if you must evaluate anything, and never on untrusted input.
  • Log injection — CR/LF in logged values forges log lines (Chapter 11.1).

3.7 Cross-site scripting (XSS)

XSS is injection into a web page: attacker-controlled data is rendered so that the browser executes it as script in your origin, with access to the DOM, cookies not marked HttpOnly, and the ability to make authenticated requests as the user.

  • Stored XSS — payload saved (comment, profile, invoice note) and served to other users.
  • Reflected XSS — payload in the request (query parameter) echoed into the response.
  • DOM-based XSS — client-side JavaScript reads attacker-influenced data (location.hash, postMessage, API responses) and writes it to a dangerous sink (innerHTML, document.write, eval, setTimeout(string), location = "javascript:..."). The server may never see the payload.

Contextual output encoding is the core defence: the correct encoding depends on where data lands. HTML element content needs &lt;, &gt;, &amp;, quotes encoded; an HTML attribute value needs quoting plus attribute encoding; a JavaScript string needs JS escaping (\x3c style); a URL parameter needs percent-encoding and a scheme allow-list (no javascript:); CSS values need CSS escaping. Template engines do HTML-context escaping automatically (Thymeleaf th:text, React JSX text, Go html/template with full contextual escaping, Jinja2 with autoescape); XSS usually enters through escape hatches: th:utext, dangerouslySetInnerHTML, v-html, |safe, template.HTML(userInput).

When you genuinely need user-supplied HTML (rich-text editor), sanitise with a maintained allow-list sanitizer (OWASP Java HTML Sanitizer server-side, DOMPurify client-side) — never with your own regex.

3.8 Content Security Policy (CSP)

CSP is a response header that tells the browser which sources of script, style, frames and connections are permitted. A strict policy turns many XSS bugs from "full compromise" into "blocked and reported". The modern recommendation (from Google's research on CSP effectiveness) is a nonce-based strict CSP:

Content-Security-Policy: script-src 'nonce-R4nd0m...' 'strict-dynamic'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; report-to csp-endpoint

Every legitimate <script> carries the per-response random nonce; injected scripts do not know it. 'strict-dynamic' lets trusted scripts load further scripts. Avoid 'unsafe-inline' and 'unsafe-eval'; host allow-lists (script-src https://cdn.example.com) are often bypassable via JSONP endpoints or script gadgets on allowed hosts. Roll out with Content-Security-Policy-Report-Only first.

3.9 Trusted Types

Trusted Types attacks DOM XSS at the sink. With the header Content-Security-Policy: require-trusted-types-for 'script', the browser refuses to accept plain strings at dangerous sinks such as innerHTML; code must pass a TrustedHTML object created by a named policy (e.g. one that runs DOMPurify). The set of places that can create trusted values becomes small and reviewable. Support: Chromium-based browsers since 2020; Version-sensitive · checked Nov 2026 other engines have been adding support — check current compatibility tables, and treat Trusted Types as defense in depth.

3.10 Cross-site request forgery (CSRF)

CSRF abuses ambient credentials: the browser automatically attaches cookies (and HTTP Basic or client-certificate credentials) to requests for your site, even when the request is initiated by another site. A malicious page can auto-submit a form to https://bank.example/transfer; if the bank authenticates by cookie alone, the transfer happens as the victim. Defences:

  • Synchronizer / double-submit tokens — the server requires a secret token in a header or form field that a cross-site page cannot read. Spring Security's CsrfFilter implements this (with BREACH-resistant masking since 6.0).
  • SameSite cookies — Lax stops cookies on cross-site subresource requests and cross-site POSTs (but sends them on top-level GET navigations); Strict stops them on all cross-site requests. Note "site" means registrable domain: evil.example.com is same-site with app.example.com, so a compromised sibling subdomain bypasses SameSite.
  • Fetch metadata — browsers send Sec-Fetch-Site; a server can reject cross-site state-changing requests.
  • Never change state on GET.

When do stateless APIs need CSRF protection? If and only if the browser attaches credentials automatically. An API authenticated solely by an Authorization: Bearer header that JavaScript sets explicitly is not CSRF-able, because a cross-site page cannot make the browser add that header. The moment you move tokens into cookies (a BFF, or "JWT in a cookie"), CSRF protection is required again. CORS is not a CSRF defence by itself: simple requests (form-encoded POSTs) are sent cross-origin without preflight; CORS only controls whether the attacker can read the response.

3.11 Server-side request forgery (SSRF)

SSRF occurs when the server makes a network request to a destination influenced by the attacker — webhooks, URL previews, PDF/image renderers fetching remote assets, "import from URL", XML external entities, redirects followed by HTTP clients. The server usually sits inside the trust boundary, so it can reach things the attacker cannot: internal admin services, databases with HTTP interfaces, Kubernetes APIs, and especially cloud instance metadata services (169.254.169.254 on AWS, Azure, GCP), which hand out temporary credentials for the instance's role. Variants include blind SSRF (attacker sees no response but can scan or trigger side effects) and bypasses via redirects, alternative IP encodings, IPv6, and DNS rebinding (a hostname that resolves to a public IP at validation time and a private IP at fetch time).

IMDSv2 on AWS requires a session token obtained via an HTTP PUT with a TTL header before metadata can be read, and the token response has an IP hop limit (default 1 for EC2; set to 2 where containers need it, or block container access entirely). Most SSRF primitives can only issue GETs with no custom headers, so IMDSv2 blocks them. Azure and GCP require a Metadata: true / Metadata-Flavor: Google header for the same reason.

3.12 Insecure deserialization

Native object serialization formats (Java ObjectInputStream, Python pickle, .NET BinaryFormatter, PHP unserialize, Ruby Marshal, YAML loaders that construct arbitrary types) let the byte stream choose which classes to instantiate. Combined with "gadget" classes on the classpath whose deserialization hooks (readObject, hashCode, toString) have side effects, an attacker can chain calls to execute code. Jackson is safe by default but becomes vulnerable when polymorphic typing is enabled for broad base types (activateDefaultTyping, @JsonTypeInfo(use = Id.CLASS) on Object fields). SnakeYAML before 2.0 constructed arbitrary types by default (CVE-2022-1471). Defences: use data-only formats (JSON into concrete DTOs, Protobuf); never deserialize untrusted native formats; if unavoidable, use ObjectInputFilter allow-lists (JEP 290/415); for Jackson polymorphism use logical type names with Id.NAME and a closed set of subtypes, or a PolymorphicTypeValidator.

3.13 Path traversal

Path traversal occurs when user input is used to build a file path, and sequences like ../ (or encoded variants, absolute paths, or symlinks) escape the intended directory. A download endpoint /files?name=../../etc/passwd or a ZIP extraction that writes entries named ../../app/config.yml ("Zip Slip") are classic forms. Defence: do not use user input as paths at all — map IDs to stored paths server-side; if you must, resolve and normalise the path, then verify it starts with the canonical base directory (Path.normalize() + startsWith, or toRealPath() to resolve symlinks), and allow-list file names.

4. Internal Working: Why the Defences Work

4.1 How parameter binding separates code from data

With PostgreSQL's extended query protocol (used by pgJDBC for PreparedStatement), the driver sends a Parse message containing the SQL text with placeholders ($1), then a Bind message with parameter values in a separate field, then Execute. The server parses the SQL before it ever sees the values, so a value can never change the query's structure; it is only ever a literal of the declared type. Some drivers (MySQL Connector/J by default) emulate prepared statements client-side by escaping values into the SQL text; that is also safe because the driver escapes according to the server's exact lexical rules and connection character set — unlike application code doing ad-hoc escaping.

Hibernate and Spring Data do the same: :email in JPQL becomes a JDBC ? in generated SQL, bound via PreparedStatement.setString. Criteria API and Querydsl build an abstract syntax tree, not strings. Placeholders cannot stand for identifiers (table/column names), keywords (ASC/DESC) or SQL fragments — which is why dynamic ORDER BY is the most common place injection survives in otherwise clean Spring code. Spring Data's Sort and Pageable pass property names through Hibernate's path resolution, which rejects unknown properties for derived queries; with native queries or JpaSort.unsafe you must allow-list yourself.

4.2 Browser parsing contexts

A browser runs several parsers over one response: the HTML tokenizer, then attribute value parsing, then URL parsing for href/src, the JavaScript parser for <script> blocks and event-handler attributes, and the CSS parser for style. Each has its own metacharacters. HTML-encoding < stops a new tag in element content, but inside a JavaScript string literal the dangerous characters are quotes, backslashes and the sequence </script; inside an unquoted attribute, a space ends the value; inside an href, the danger is the javascript: scheme, which no HTML encoding neutralises. Context-aware template engines (Go's html/template, Thymeleaf's attribute processors like th:href with URL handling) track which parser will see each insertion point and pick the right encoder. Generic "escape HTML everywhere" helpers fail in the non-HTML contexts.

4.3 How a nonce-based CSP blocks injected script

The server generates a fresh random nonce (≥128 bits) per response, puts it in the CSP header and in the nonce attribute of each legitimate script tag. When the browser encounters a <script>, it checks whether the element's nonce matches the policy. An injected <script>alert(1)</script> has no nonce (the attacker cannot predict it), so it does not execute; inline event handlers like onerror= are blocked because 'unsafe-inline' is absent (and 'unsafe-hashes' is not set). With 'strict-dynamic', a nonced script that calls document.createElement('script') passes trust to the created script, so modern bundlers and tag managers keep working. Browsers also hide the nonce attribute from the DOM-reading API to make exfiltration harder. A nonce reused across responses (cached HTML with a static nonce) defeats the scheme.

4.4 Inside Spring Security's CSRF protection

CsrfFilter runs early in the chain. For every request it loads (lazily, since 6.0, through a DeferredCsrfToken) the expected token from a CsrfTokenRepository — HttpSessionCsrfTokenRepository by default or CookieCsrfTokenRepository for SPAs. Requests with "safe" methods (GET, HEAD, TRACE, OPTIONS) pass. For others, it reads the actual token from the X-CSRF-TOKEN header (or X-XSRF-TOKEN with the cookie repository) or the _csrf parameter, and compares it in constant time with the expected value. The XorCsrfTokenRequestAttributeHandler (default since 6.0) XORs the token with fresh randomness each time it is rendered, protecting against BREACH-style compression side channels; SPAs that read the raw cookie value need the documented SpaCsrfTokenRequestHandler so both raw and masked forms validate. On mismatch, an AccessDeniedHandler returns 403. Logout is POST-only by default when CSRF is enabled, preventing forced-logout attacks.

4.5 How the browser decides whether to send a SameSite cookie

For each request, the browser computes whether the request's initiator is same-site with the target (comparing scheme and registrable domain, using the Public Suffix List). If same-site, all cookies are sent. If cross-site: SameSite=Strict cookies are withheld; Lax cookies are sent only for top-level navigations with safe methods (clicking a link, GET form); None cookies (which must be Secure) are always sent. Cookies with no attribute are treated as Lax in Chromium-based browsers (with a short grace period for top-level POSTs on very new cookies) — but do not rely on defaults; set the attribute explicitly.

4.6 How an SSRF reaches cloud credentials — and where it is cut

Defender's walkthrough of the chain, so you can see each place to break it:

  1. A feature accepts a URL ("import avatar from URL"). The handler calls restClient.get().uri(userUrl).
  2. Instead of a public image URL, the request names an internal address such as the link-local metadata endpoint. Break here: resolve the hostname yourself, reject private, loopback, link-local, multicast and unique-local ranges (IPv4 and IPv6), connect to the vetted IP, and disable redirects (or re-validate each hop).
  3. With IMDSv1, a simple GET returns the instance role name and then temporary credentials. Break here: enforce IMDSv2 (HttpTokens=required), set the hop limit to 1 so containers cannot reach it, or block 169.254.169.254 from application pods with a NetworkPolicy; on EKS use IRSA/Pod Identity rather than node roles.
  4. The response body (credentials) is returned to the caller, or the attacker infers it via errors. Break here: never return raw fetched content to the client for features that only need, say, an image — validate content type and size and re-encode.
  5. The credentials are used from outside the cloud account. Break here: least-privilege role (Chapter 11.4), and alerting on instance-role credentials used from unexpected sources (AWS GuardDuty has a finding type for this).

4.7 Why Java deserialization executes code

ObjectInputStream.readObject() reads a class descriptor from the stream, loads that class from the classpath, allocates an instance without calling its constructor, populates fields from the stream, and invokes the class's private readObject method if present. Collections such as HashMap call hashCode() on keys during deserialization to rebuild buckets. A gadget chain is a sequence of ordinary library classes where one class's deserialization hook calls a method on a field whose type is chosen by the attacker, and so on, until a method with a powerful side effect (reflection, Runtime.exec, JNDI lookup) is reached. The application never calls the gadget code; the stream does. That is why the fix is to never deserialize untrusted streams, or to install an ObjectInputFilter that rejects every class not on a short allow-list before it is loaded.

4.8 Path normalisation and where checks go wrong

Path.of(base, userName).normalize() collapses .. segments lexically. The check must be performed on the normalised, absolute path (startsWith(baseDir) on Path objects, which compares path elements — not on strings, where /data/app-evil "starts with" /data/app). Symlinks inside the base directory can still point outside; toRealPath() resolves them but requires the file to exist. URL-decoding twice (once by the container, once by your code) re-opens encoded traversal sequences, which is why Spring Security's StrictHttpFirewall rejects encoded slashes, backslashes, %2e and semicolons in request paths by default.

4.9 Token bucket internals and distributed enforcement

A token bucket stores two numbers per key: tokens remaining and last refill timestamp. On each request: compute elapsed time, add elapsed × rate tokens up to capacity, then if at least one token remains, decrement and allow; otherwise reject with 429 Too Many Requests and a Retry-After header. In a cluster the state must be shared and updated atomically, typically in Redis via a Lua script (Spring Cloud Gateway's RedisRateLimiter) or compare-and-swap (Bucket4j's JCache/Redis/JDBC proxies). Local per-instance buckets are cheaper but the effective limit becomes limit × instances and varies with load-balancer skew.

5. Architecture: Diagrams and an Interactive Rate Limiter

5.1 Layered API protection

Reading the diagram: the WAF and gateway handle volume, shape and identity (API2, API4, API8, API9 partly); the services handle object-, property- and function-level authorization (API1, API3, API5) and business-flow limits (API6), because only they know ownership and business rules. Outbound calls go through an egress proxy so SSRF (API7) and unsafe consumption (API10) are constrained at the network layer as well as in code.

5.2 Interactive: rate-limiting algorithms under bursts

What to try: set a limit of 10 requests per window and send a burst at the end of one window followed by a burst at the start of the next. Watch the fixed window admit nearly double the limit across the boundary, while the sliding-window log holds the line. Then compare the token bucket with a capacity equal to the limit: it admits the initial burst (which is often what you want for interactive clients) and then settles to the refill rate. For login and OTP endpoints, a small bucket capacity with a slow refill is the right shape; for read APIs, a larger capacity smooths user experience.

5.3 A CSRF attack and the two defences

Reading the diagram: the attacker never sees the cookie; they rely on the browser attaching it. SameSite removes the cookie from cross-site requests; the token requires a secret the attacker's page cannot read (same-origin policy). Use both: SameSite does not help against same-site attackers (a compromised subdomain) or older browsers, and tokens protect even when the cookie is sent.

5.4 SSRF defence in depth

Reading the diagram: the application checks (allow-list, IP classification, pinned connection, no redirects) stop most attempts, including DNS rebinding because the connection uses the IP that was checked. The network controls (egress proxy, NetworkPolicy, IMDSv2) still hold if a developer later adds a new fetch path that skips the helper — they are the independent layer.

5.5 Where untrusted data flows in a typical Spring service

Reading the diagram: SAST tools like CodeQL and Semgrep model exactly this: sources, sinks, and sanitisers in between. When reviewing code, trace each source in the diff to every sink it can reach. Note that Kafka messages and third-party responses are sources too — data that "came from our own system" may have originated with a user several hops earlier.

6. The Math: Rate Limits, Token Entropy and Search Spaces

6.1 Token bucket

Intuition: a bucket holds up to \( B \) tokens and refills at \( r \) tokens per second; you can burst up to \( B \) and then sustain \( r \). Over any interval of length \( t \), the maximum number of admitted requests is

\[ N_{\max}(t) = B + r\,t \]

For a fixed window of size \( W \) with limit \( L \), two adjacent windows can admit \( 2L \) requests within an interval just over \( \epsilon \) around the boundary, so the worst-case short-term rate is \( 2L/\epsilon \) — unbounded in principle. A sliding window guarantees at most \( L \) in any interval of length \( W \).

6.2 Brute-force budgets

If an attacker can make \( q \) guesses per second against a secret space of size \( S \), the expected time to success is \( S/(2q) \). Illustrative A 6-digit reset code (\( S=10^6 \)) behind a limit of 5 attempts per code and 3 codes per hour per account gives at most 15 guesses per hour: success probability per hour \( \approx 15/10^6 = 1.5\times10^{-5} \), roughly 1 in 67,000. Without limits at 1,000 req/s, expected time is 500 s.

6.3 BOLA and identifier spaces

Sequential IDs make enumeration trivial: \( S \approx \) number of records. Random UUIDv4 (122 random bits) makes blind enumeration infeasible: \( 2^{122} \approx 5.3\times10^{36} \). But this only defeats guessing; leaked IDs (URLs, logs, shared links, other API responses) are still exploitable without an authorization check. Treat ID randomness as defence in depth, never as access control.

6.4 Capacity math for limits

Set limits from capacity, not intuition. If a search endpoint costs about 40 ms of database time and the database pool supports roughly 200 concurrent queries, throughput is about \( 200 / 0.04 = 5{,}000 \) queries/s. Reserving half for other endpoints and supporting 1,000 concurrent active users suggests a per-user limit around \( 2{,}500/1{,}000 = 2.5 \) req/s sustained, with a small burst. Illustrative

6.5 Cost amplification

API4 includes downstream cost: an endpoint that sends an SMS costing \( c \) per message with no per-number limit lets an attacker spend \( c \times q \times t \) of your money ("SMS pumping"); an LLM-backed endpoint with no token budget does the same with model costs. Limit by the resource that costs money (per destination number, per tenant token budget), not just by request count.

/** Per-principal token bucket. Register AFTER authentication (e.g. http.addFilterAfter(..., AuthorizationFilter.class)).
 *  Single-instance demo: use bucket4j-redis / bucket4j-jcache for a shared limit across replicas. */
public class RateLimitFilter extends OncePerRequestFilter {
    private final Cache<String, Bucket> buckets = Caffeine.newBuilder()
            .expireAfterAccess(Duration.ofMinutes(10)).maximumSize(200_000).build();

    private Bucket newBucket() {
        return Bucket.builder()
                .addLimit(Bandwidth.builder().capacity(20).refillGreedy(20, Duration.ofMinutes(1)).build())  // 20/min, burst 20
                .addLimit(Bandwidth.builder().capacity(5).refillIntervally(5, Duration.ofSeconds(1)).build()) // and max 5/s
                .build();
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        Authentication auth = SecurityContextHolder.getContext().getAuthentication();
        String key = (auth != null && auth.isAuthenticated()) ? "u:" + auth.getName() : "ip:" + req.getRemoteAddr();
        ConsumptionProbe probe = buckets.get(key, k -> newBucket()).tryConsumeAndReturnRemaining(1);
        if (probe.isConsumed()) {
            res.setHeader("RateLimit-Remaining", String.valueOf(probe.getRemainingTokens()));
            chain.doFilter(req, res);
        } else {
            long waitSeconds = Math.max(1, probe.getNanosToWaitForRefill() / 1_000_000_000L);
            res.setHeader("Retry-After", String.valueOf(waitSeconds));
            res.sendError(429, "Too Many Requests");
        }
    }
}

req.getRemoteAddr() is the proxy's address behind a load balancer unless you configure server.forward-headers-strategy and trust only your proxies' X-Forwarded-For; never trust that header from the internet directly, or attackers will rotate it to evade limits.

7.6 SSRF-safe outbound fetching

package com.example.fetch;

import java.net.InetAddress;
import java.net.URI;
import java.net.UnknownHostException;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.Set;

public final class SafeUrlFetcher {
    private static final Set<String> ALLOWED_HOSTS = Set.of("images.partner.example", "cdn.example.net");
    private static final long MAX_BYTES = 2 * 1024 * 1024;

    private final HttpClient client = HttpClient.newBuilder()
            .followRedirects(HttpClient.Redirect.NEVER)          // a redirect could point anywhere
            .connectTimeout(Duration.ofSeconds(3))
            .build();

    public byte[] fetch(String raw) throws Exception {
        URI uri = URI.create(raw).normalize();
        if (!"https".equalsIgnoreCase(uri.getScheme())) throw new IllegalArgumentException("https only");
        if (uri.getUserInfo() != null) throw new IllegalArgumentException("no credentials in URL");
        String host = uri.getHost();
        if (host == null || !ALLOWED_HOSTS.contains(host.toLowerCase())) throw new IllegalArgumentException("host not allowed");
        if (uri.getPort() != -1 && uri.getPort() != 443) throw new IllegalArgumentException("port not allowed");

        for (InetAddress a : resolve(host)) {
            if (a.isAnyLocalAddress() || a.isLoopbackAddress() || a.isLinkLocalAddress()
                    || a.isSiteLocalAddress() || a.isMulticastAddress() || isUniqueLocalV6(a)) {
                throw new IllegalArgumentException("resolves to a non-public address");
            }
        }
        // Residual risk: DNS may change between this check and connect (rebinding). With a strict host
        // allow-list the risk is small; for open-ended fetching, route through an egress proxy that
        // re-checks the connected IP, or use a resolver-pinned client.
        HttpRequest req = HttpRequest.newBuilder(uri).timeout(Duration.ofSeconds(5)).GET().build();
        HttpResponse<byte[]> res = client.send(req, HttpResponse.BodyHandlers.ofByteArray());
        if (res.statusCode() != 200) throw new IllegalStateException("upstream status " + res.statusCode());
        if (res.body().length > MAX_BYTES) throw new IllegalStateException("too large");  // also cap Content-Length up front
        return res.body();
    }

    private static InetAddress[] resolve(String host) throws UnknownHostException {
        return InetAddress.getAllByName(host);
    }

    private static boolean isUniqueLocalV6(InetAddress a) {
        byte[] b = a.getAddress();
        return b.length == 16 && (b[0] & 0xFE) == 0xFC;      // fc00::/7
    }
}

Java's isSiteLocalAddress covers 10/8, 172.16/12 and 192.168/16; isLinkLocalAddress covers 169.254/16 (including the metadata address) and fe80::/10. Also consider carrier-grade NAT (100.64/10) and IPv4-mapped IPv6 addresses for completeness. Pair this with the network controls in Figure 4.

8. Applications: How Teams Keep These Bugs Out

8.1 Secure-by-construction libraries

Teams with low vulnerability rates make the unsafe thing hard: a shared SafeUrlFetcher is the only HTTP client allowed to take user URLs (enforced by an ArchUnit or Semgrep rule); a TenantScopedRepository base adds tenant predicates automatically; DTO-only controllers are enforced by a lint rule; the HTML templating setup forbids th:utext outside one sanitised component. Google has written publicly about this approach ("safe coding"): eliminating vulnerability classes through safe APIs rather than relying on developer vigilance.

8.2 Security unit tests for API invariants

Every endpoint gets at least three negative tests: unauthenticated → 401; authenticated without the scope/role → 403; authenticated with scope but another user's object → 404. Payload tests assert that unknown fields are rejected (mass assignment) and that responses do not contain forbidden properties (BOPLA) — e.g. asserting that the JSON has no passwordHash or internalNotes key.

8.3 DAST in the pipeline

An OWASP ZAP baseline scan against an ephemeral staging environment on every merge catches missing headers, cookie flags, reflected XSS and information leaks; an authenticated, OpenAPI-driven ZAP scan nightly covers more depth. Findings flow into the same triage process as SCA results.

8.4 Bug bounty and pen testing

External testers find what internal tooling misses — mostly authorization and business-logic flaws. Mature programmes route each valid report back to a root cause ("why did our tests and review not catch this class?") and add a rule, test or library change.

8.5 Reviewing AI-generated code

Assistants reproduce common patterns from training data, including insecure ones (string-built SQL, disabled TLS verification in examples, entities as request bodies, permissive CORS). Treat AI-authored diffs like any external contribution: run the same SAST/SCA gates, require tests for authorization, and apply the checklist in §13. 9.1 Capital One (2019): SSRF plus an over-privileged role Verified

In July 2019 Capital One announced that an outside individual had obtained data on about 100 million people in the US and about 6 million in Canada, mostly from credit card applications. Public court filings and subsequent analysis described a misconfigured web application firewall that could be induced to make requests to the EC2 instance metadata service, yielding temporary credentials for a role that could list and read many S3 buckets. The response from the industry included AWS's IMDSv2 (November 2019), which requires a PUT-obtained session token and limits hop count precisely to blunt this class of SSRF. Lessons: SSRF is an access-control problem (as OWASP 2025 now classifies it); least privilege on instance roles turns a bug into a contained incident; network-layer controls on metadata access are cheap and effective. Sources: Capital One, "Information on the Capital One cyber incident"; AWS Security Blog on IMDSv2.

9.2 GitHub mass assignment (2012) Verified

A researcher demonstrated that GitHub's public-key update form accepted a user_id parameter that was mass-assigned onto the key record, letting him attach a key to another account (the Rails organisation's). GitHub's incident write-up attributed the root cause to failing to properly check incoming form parameters and audited the codebase; Rails subsequently made "strong parameters" the default. The Spring equivalent is binding a request body to an entity — the pattern §7.1 eliminates. Source: GitHub blog, "Public Key Security Vulnerability and Mitigation" (March 2012).

9.3 The Samy worm (2005) Verified

A MySpace user found a way past MySpace's input filters to store JavaScript in his profile; anyone viewing it executed the script, which added him as a friend and copied itself to the viewer's profile. It spread to over a million profiles in about 20 hours. Lessons: deny-list filtering of HTML is fragile; stored XSS in social features is wormable; output encoding and CSP (which did not exist then) are the robust answers. Source: Samy Kamkar's technical explanation.

9.4 MOVEit Transfer (2023): SQL injection at supply-chain scale Verified

As summarised in Chapter 11.1, CVE-2023-34362 — a SQL injection in an internet-facing file-transfer product — was exploited by the Cl0p group to steal data from many organisations. It is a reminder that injection, decades old, remains a live risk in commercial software, and that parameterised queries are not optional anywhere. Source: CISA advisory AA23-158A.

9.5 Google's CSP research Verified

Google researchers analysed CSP deployments across the web and found that the large majority of host-allow-list policies offered no effective XSS protection because of unsafe allowed hosts or unsafe-inline. This work produced the nonce-plus-strict-dynamic recommendation used in §7.4. Source: Weichselbaum et al., "CSP Is Dead, Long Live CSP!", ACM CCS 2016.

11. Engineering Trade-offs

11.1 Validate, encode or sanitise?

Reading the diagram: validation always applies at the boundary, but it is the destination that determines the primary defence. Sanitisation is a last resort for genuinely rich content because sanitizers must anticipate every browser quirk; encoding is simpler and safer when markup is not needed.

11.2 Where to rate-limit

Gateway limits are cheap and protect everything, but key only on what the gateway knows (API key, IP, token subject). Service-level limits can key on business entities (per phone number, per card, per tenant) and protect business flows (API6). Opinion Do both: coarse at the edge for availability, precise in the service for abuse.

11.3 Strict CSP: effort vs benefit

Retrofitting a nonce CSP onto a legacy server-rendered app with inline handlers can take weeks; a modern SPA built by a bundler often needs only a nonce on the bootstrap script. Prioritise by exposure: authenticated apps handling sensitive data and apps with user-generated content first. Start in report-only mode and fix violations iteratively.

11.4 Generic 404 vs precise errors

Returning 404 for unauthorised objects hides existence but can confuse legitimate clients and support teams. A reasonable compromise: 404 externally, with the precise reason (not found vs not permitted) in the server log and audit trail, correlated by request ID.

12. Common Mistakes

  • Disabling CSRF globally in a service that also has a cookie-based login form or admin UI.
  • Assuming JSON content type prevents CSRF. Some frameworks accept form-encoded or text/plain bodies on JSON endpoints; enforce Content-Type: application/json and still use tokens with cookies.
  • CORS with reflected origins and credentials — echoing any Origin into Access-Control-Allow-Origin with Allow-Credentials: true lets any site read authenticated responses.
  • Validating a URL, then fetching a different one (following redirects, re-resolving DNS, or using a different parser than the HTTP client).
  • Blocking 169.254.169.254 by string match — alternative encodings and IPv6 forms bypass it; classify resolved IPs instead.
  • Sanitising input once at write time and then rendering it in a different context (JS, attribute) at read time.
  • Using th:utext / dangerouslySetInnerHTML for convenience.
  • String-building ORDER BY from a request parameter.
  • Returning entities from controllers, leaking fields added later (BOPLA via schema evolution).
  • Unbounded pagination, file sizes, JSON nesting, regexes (ReDoS) and batch sizes.
  • Trusting third-party responses (API10): rendering partner-provided HTML, following partner-provided redirect URLs, or deserializing partner payloads polymorphically.
  • Old API versions left running (API9) without the fixes applied to the current version.
  • Relying on the WAF instead of fixing the code.

13.1 Monitoring

Track 401/403/404 rates per endpoint and per principal (BOLA probing shows as many 404s from one principal across sequential IDs), 429 rates (limits too tight or abuse), CSP violation reports (new XSS or a broken deployment), WAF block rates, and outbound connection attempts denied by the egress proxy (SSRF attempts or misconfiguration).

13.2 Performance

Most of these controls are cheap. Exceptions: HTML sanitisation of large documents (cache sanitised output), distributed rate-limit state (Redis round-trip per request — use local pre-filters or batching), and egress proxies (connection reuse matters). Measure before and after.

13.3 Reliability

Rate limiters and security filters are in the request path; if the Redis behind a distributed limiter fails, decide explicitly whether to fail open (availability) or closed (abuse protection), per endpoint. Login and OTP endpoints should fail closed; catalogue browsing can fail open with local limits.

Exercise 2 · Intermediate

This code builds a report query. Identify every vulnerability and rewrite it safely.

@GetMapping("/api/reports")

Solution

private static final Map<String, String> SORT = Map.of("date", "created_at", "total", "total_cents");

    String tenant = jwt.getClaimAsString("tenant_id");              // from the token, not the request
    String sql = "SELECT id, created_at, total_cents FROM orders WHERE tenant_id = :t AND created_at >= :f ORDER BY "
               + SORT.getOrDefault(sort, "created_at") + " LIMIT 500";

}

Exercise 3 · Intermediate

A team says: "Our API uses JWTs in an HttpOnly cookie, so XSS can't steal tokens and we disabled CSRF because it's a REST API." Evaluate.

Solution

HttpOnly prevents token theft by script, but cookies are ambient credentials, so the API is CSRF-able: re-enable CSRF protection (tokens) and set SameSite=Lax or Strict. Also ensure CORS is not reflecting arbitrary origins with credentials, require Content-Type: application/json, and remember XSS can still act as the user during the session — CSP remains necessary.

Exercise 4 · Advanced

Design a "webhook URL" feature where tenants register an HTTPS endpoint that your platform POSTs events to. Address SSRF, abuse and integrity.

Solution
  • Validate at registration and at every delivery: HTTPS only, port 443 (or allow-listed), no credentials in URL, resolved IPs must be public; re-check at connect time (Go Dialer.Control-style or egress proxy) to defeat DNS rebinding.
  • Send deliveries from a dedicated worker pool in an isolated network segment whose egress permits only the public internet — no route to internal services or metadata.
  • Disable redirects; short timeouts; cap response size read (you only need the status code).
  • Sign each delivery with an HMAC over timestamp + body using a per-tenant secret, so receivers can verify integrity and reject replays.
  • Verify ownership of the endpoint (challenge on registration), rate-limit per tenant and per destination host, and back off on failures so you cannot be weaponised to flood a third party.

Exercise 5 · Advanced (local lab)

Run WebGoat locally (docker run --rm -p 127.0.0.1:8080:8080 -p 127.0.0.1:9090:9090 webgoat/webgoat). Complete its SQL injection and XSS lessons, then for each lesson write the Spring fix you would apply to the equivalent code in your own service, plus a regression test.

Solution

For SQL injection lessons, the fix is parameter binding (NamedParameterJdbcTemplate or JPA named parameters) plus allow-listed identifiers; a regression test submits a quote-containing value and asserts that the result set matches a literal search (no extra rows). For XSS lessons, the fix is template auto-escaping and removing utext-style escape hatches; a test renders a value containing <script> and asserts the response body contains &lt;script&gt;. Always keep WebGoat bound to 127.0.0.1 — it is deliberately vulnerable.

15. Interview Questions

Conceptual Why is BOLA the #1 API risk, and why don't scanners find it?

Every endpoint taking an object ID needs a business-specific ownership check, so the opportunity for omission is everywhere. Scanners lack the knowledge of who should own what; detecting BOLA requires two identities and a model of ownership — that is, tests written by people who understand the domain.

Conceptual Explain why prepared statements prevent SQL injection but not ORDER BY injection.

Placeholders carry literal values in a separate protocol field after the query is parsed, so they cannot change structure. Identifiers and keywords are part of the structure and cannot be placeholders, so they are often concatenated; the fix is mapping user choices to a fixed allow-list of SQL fragments.

Conceptual Does a stateless REST API need CSRF protection?

Only if the browser sends credentials automatically — cookies, HTTP Basic, client certificates. Bearer tokens set explicitly in the Authorization header are not sent by cross-site forms, so CSRF does not apply; tokens stored in cookies bring it back.

Architecture How would you design defence against SSRF for a URL-preview feature?

Isolated fetcher service in a network segment with internet-only egress; scheme/host/port validation; resolve and classify IPs and dial the vetted IP (or check at connect time); no redirects or re-validate each; timeouts and size limits; strip and re-encode content; IMDSv2 and metadata blocking; least-privilege identity for the fetcher; logging of denied destinations.

Coding How do you prevent mass assignment in Spring?

Never bind request bodies to entities; use request records with only settable fields; map explicitly; enable FAIL_ON_UNKNOWN_PROPERTIES; for form binding use setAllowedFields or constructor/declarative binding; test that unknown/privileged fields are rejected.

Conceptual What does a strict CSP protect against, and what does it not?

It prevents execution of injected scripts lacking the nonce (and inline handlers), turning most XSS into non-executing HTML injection. It does not prevent HTML injection used for phishing, data exfiltration via allowed connections, logic flaws, or attacks via compromised trusted scripts. It is defense in depth on top of encoding.

Scenario A pen test shows that changing an invoice ID in the mobile app's API call returns another customer's invoice. What do you do in the next 24 hours and the next month?

24 hours: hot-fix with owner-scoped query; search logs for cross-customer access patterns (many invoice IDs per principal, 200s for non-owned IDs) to determine exposure; engage incident response and privacy/legal if data was accessed. Month: audit all endpoints taking IDs; add a negative-test template and an ArchUnit/Semgrep rule; introduce tenant-scoped repositories or RLS; add BOLA monitoring alerts.

Coding Write a safe file-download path check in Java.

Resolve the base with toRealPath(); resolve the candidate against it, normalize(), check startsWith(base) using Path, then toRealPath() again to defeat symlinks and re-check; better still, look up the stored name by an authorised ID rather than accepting a path (see §7.7).

Conceptual Why is Java native deserialization of untrusted data dangerous even if your code never calls dangerous methods?

The stream selects classes from the classpath and triggers their deserialization hooks; gadget chains of ordinary library classes can reach reflection or command execution. Your code does not need to call anything — readObject does it. Use data-only formats or strict ObjectInputFilter allow-lists.

Behavioral How do you get a team to adopt a secure code review checklist without slowing delivery?

Keep it short (one table), automate the mechanical items (SAST rules, ArchUnit, test templates), attach it to the PR template only for relevant file types, show a concrete bug it would have caught, and measure review time before and after. Make the safe path the easiest path via libraries.

16. Knowledge Check

  • API risks are dominated by authorization at three levels: object (BOLA), property (BOPLA/mass assignment) and function (BFLA).
  • Bind request bodies to DTOs, reject unknown fields, return view DTOs.
  • Parameterise every query; allow-list identifiers; the same applies to JPQL and MongoDB.
  • Encode output for its context; sanitise only true rich text; add a nonce-based strict CSP and Trusted Types.
  • CSRF matters whenever credentials are ambient (cookies); SameSite plus tokens; bearer-header APIs are not CSRF-able.
  • SSRF: allow-list, classify resolved IPs, check at connect time, no redirects, egress controls, IMDSv2, least-privilege roles.
  • Never deserialize untrusted native formats; confine file paths; limit every resource.
