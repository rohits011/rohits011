Model Selection, Open Models, Fine-Tuning, LoRA/QLoRA & Quantization

Which model should you use, and should you ever change its weights? This chapter replaces vibes and leaderboard-watching with an evaluation-led selection process, explains what licences actually allow, and shows — with the low-rank mathematics and a runnable training script — how parameter-efficient fine-tuning and quantization let a single GPU adapt and serve models that once needed a cluster.

1. Introduction: The Model Is a Dependency You Choose

In Chapter 2 the model was a configuration value: llm.primary-model=…. That value is one of the most consequential dependency decisions your system makes. It sets quality, latency, cost per request, where data goes, which jurisdictions you can serve, what licence obligations you carry, and how hard it will be to switch later. Unlike most dependencies, it also changes behaviour silently when a vendor updates it, and its "performance" cannot be read off a datasheet — it must be measured on your task.

This chapter covers three decisions, in the order you should make them. First, which model: hosted frontier API, hosted open-weight model, or self-hosted open weights, chosen by evaluation against your own data. Second, whether to change the model at all: most problems are solved by better prompts or retrieval; fine-tuning is the right tool for a narrower set of problems than its popularity suggests. Third, how to run it efficiently: quantization and specialised serving engines decide whether an open model is economical.

Bridging from Java & Spring Boot

What you already know
Choosing PostgreSQL vs. a managed cloud database vs. Oracle involves capability, operational burden, licence (GPL vs. Apache vs. commercial), cost and lock-in. You have weighed OpenJDK distributions and their licences, tuned JVM heap and GC for throughput vs. latency, and accepted that a managed service trades control for convenience. You configure an application rather than modifying the framework's source — and you fork a library only as a last resort.
Why that is not enough
Model capability is task-specific and non-transitive: a model that wins public benchmarks can lose on your support tickets. Licences for "open" models are often custom documents with usage restrictions, not OSI licences. And "modifying the source" — fine-tuning — is cheap enough to tempt teams into it when prompting or retrieval would be better, more maintainable choices.
The modern approach
Build a small, representative evaluation set first; shortlist models on capability, latency, cost and data constraints; measure; pick the cheapest model that passes. Fine-tune only to change behaviour (format, style, a narrow skill, latency via a smaller model), not to inject frequently changing knowledge. Use parameter-efficient methods (LoRA/QLoRA) and quantization to make open models affordable, and serve them through an OpenAI-compatible endpoint so your Spring code does not care where the model runs.
Where Python and Go fit
Training, evaluation and quantization tooling is Python (Hugging Face transformers, peft, trl, bitsandbytes). Serving engines are Python/C++/CUDA (vLLM) or C/C++ (llama.cpp); Ollama is written in Go. Your Spring Boot services consume models over HTTP and never need the training stack.
In production
Teams run a model registry (model ID, licence, evaluation scores, approved routes), re-evaluate on every candidate model, version adapters like artefacts, and operate GPU serving with autoscaling, KV-cache monitoring and canary rollouts.
Use it when / avoid it when
Self-host or fine-tune when data residency, cost at scale, latency, offline operation or a narrow repeatable task justify the operational burden. Avoid it when volume is low, requirements change weekly, or the task needs frontier-level reasoning — a hosted API will be cheaper in engineer time.

3. Fundamentals

3.1 Closed, open-weight and open-source

Three categories are often confused:

  • Closed (proprietary) models are available only through an API or a cloud partner (Anthropic's Claude, OpenAI's flagship GPT models, Google's Gemini). You never see weights; you get the provider's serving, safety systems, and update cadence.
  • Open-weight models publish trained weights you can download, run and usually fine-tune (Llama, Qwen, Mistral's open models, DeepSeek, Gemma, gpt-oss). Training data and full training code are usually not published.
  • Open-source models, in the stricter sense used by the Open Source Initiative's Open Source AI Definition (2024), also make available enough information about training data and the code to reproduce training. Few frontier-scale models meet this bar; projects such as AI2's OLMo aim to.

For an engineer the practical distinction is control: with weights you choose hardware, location, quantization, fine-tuning and version pinning; you also own uptime, scaling, security patching and safety filtering.

3.5 Evaluation-led selection

Public leaderboards measure general skills on public data that may have leaked into training sets. Your decision should rest on a private evaluation set drawn from your domain:

  1. Collect 100–500 representative inputs with expected outputs or grading rubrics, including hard and adversarial cases. Production logs (anonymised) are the best source.
  2. Define metrics per task: exact-match accuracy for classification, field-level F1 for extraction, rubric-based LLM-as-judge scores for generation (with human spot checks), schema-validity rate, latency percentiles, cost per 1,000 requests.
  3. Run every shortlisted model with the same prompt (adjusted only for templates), several samples per input to measure variance.
  4. Choose the cheapest model that meets the quality bar, with a margin, then re-run the set on every model or prompt change.

This is test-driven development applied to model choice. Chapter 5 covers evaluation design in depth; §7.4 gives a runnable harness that compares any OpenAI-compatible endpoints, hosted or self-hosted.

3.7 Full fine-tuning

Full fine-tuning updates every weight with gradient descent on your data. It is the most expressive option and the most expensive. With the Adam optimiser in mixed precision, each parameter typically needs about 16 bytes of GPU memory during training (2 for BF16 weights, 2 for gradients, 4 for an FP32 master copy, 8 for Adam's two moment estimates), plus activations. An 8B-parameter model therefore needs on the order of 128 GB before activations — multiple GPUs with sharding (DeepSpeed ZeRO or PyTorch FSDP). The output is a full copy of the model per task, and aggressive training risks catastrophic forgetting of general abilities. For application teams, full fine-tuning is rarely justified.

3.8 Parameter-efficient fine-tuning (PEFT)

PEFT methods freeze the pretrained weights and train a small number of new parameters. Variants include adapters (small bottleneck layers inserted between blocks), prefix/prompt tuning (trainable virtual tokens), IA³ (learned scaling vectors), and — dominant in practice — LoRA. Benefits: far less memory (no gradients or optimiser state for frozen weights), small artefacts (megabytes instead of gigabytes), many task adapters sharing one base model, and lower risk of forgetting. Hugging Face's peft library implements these behind one API.

3.9 LoRA: low-rank adaptation

LoRA's insight (Hu et al., 2021) is that the change needed to adapt a pretrained weight matrix has low intrinsic rank. Instead of learning a full update \(\Delta W\) of shape \(d \times k\), learn two thin matrices \(B\) (\(d \times r\)) and \(A\) (\(r \times k\)) with rank \(r \ll \min(d,k)\), so \(\Delta W = BA\). The forward pass becomes \(h = W_0 x + \frac{\alpha}{r} B A x\). \(B\) is initialised to zero so training starts from exactly the base model. After training, \(BA\) can be merged into \(W_0\), so inference has zero extra latency — or kept separate so many adapters can be hot-swapped on one base model.

Key hyperparameters: rank \(r\) (commonly 8–64; higher for harder or broader tasks), alpha \(\alpha\) (scales the update; often set to \(r\) or \(2r\)), target modules (originally attention query/value projections; applying LoRA to all linear layers usually works better), dropout, and a learning rate around \(10^{-4}\) — roughly ten times higher than full fine-tuning, because only the new parameters are learned.

3.10 QLoRA: LoRA on a 4-bit base model

QLoRA (Dettmers et al., 2023) keeps LoRA's trainable adapters in 16-bit precision but stores the frozen base model in 4 bits, cutting memory roughly fourfold. The paper reported fine-tuning a 65B-parameter model on a single 48 GB GPU while matching 16-bit fine-tuning performance on its benchmarks. Three innovations make it work:

  • 4-bit NormalFloat (NF4): pretrained weights are approximately normally distributed, so NF4 places its 16 quantization levels at quantiles of a normal distribution rather than evenly spaced, giving each level equal expected usage — information-theoretically well suited to such weights.
  • Double quantization: weights are quantized in blocks (64 values) with an FP32 scale per block; QLoRA quantizes those scales too (8-bit, in blocks of 256), saving about 0.37 bits per parameter — around 3 GB on a 65B model.
  • Paged optimisers: optimiser states use NVIDIA unified memory so that memory spikes (for example, long sequences with gradient checkpointing) page to CPU RAM instead of crashing with out-of-memory errors.

During the forward and backward passes, each 4-bit block is dequantized to BF16 on the fly for the matrix multiply; gradients flow through the frozen quantized weights into the LoRA matrices only. The cost is some training speed (dequantization overhead); the benefit is fine-tuning 7–14B models on a single 24 GB consumer or cloud GPU.

3.11 Preference tuning with DPO

Supervised fine-tuning teaches "produce this answer." Preference tuning teaches "prefer this answer over that one," which suits qualities that are easier to compare than to write: tone, helpfulness, conciseness, refusing correctly. DPO (Chapter 1, §3.8) trains on triples (prompt, chosen, rejected) against a frozen reference model, with a hyperparameter \(\beta\) controlling how far the policy may move from the reference. Typical pipeline: SFT on demonstrations → DPO on preference pairs collected from users (thumbs up/down, edits), from human raters, or from an LLM judge with a rubric. TRL's DPOTrainer supports LoRA, so it fits on the same hardware as QLoRA SFT.

3.12 Distillation

Knowledge distillation (Hinton et al., 2015) trains a small student to imitate a large teacher. In the LLM world the common, practical form is sequence-level distillation: generate high-quality outputs from a strong model on your task's inputs, filter them (validation, judges, humans), and fine-tune a small model on them. Classic distillation also matches the teacher's full probability distribution (soft labels), which requires access to logits — usually only possible with open models. Before distilling from a hosted model, check the provider's terms: many prohibit using outputs to develop competing models.

3.13 Quantization

Quantization stores weights (and sometimes activations and the KV cache) in fewer bits. Memory falls proportionally; decode speed usually improves because decoding is memory-bandwidth-bound (Chapter 1, §4.4); quality degrades slightly, more so at lower bit-widths and for smaller models.

4. Internal Working

4.1 One QLoRA training step, end to end

  1. Load. The base model's linear-layer weights are quantized to NF4 at load time in blocks of 64 values, each block with its own scale (itself 8-bit quantized under double quantization). Embeddings, norms and the LM head usually stay in 16-bit.
  2. Attach adapters. For each targeted linear layer, PEFT wraps the module: the original quantized weight is frozen, and two new BF16 matrices \(A\) (random init) and \(B\) (zeros) are added. Only these require gradients.
  3. Batch. Conversations are rendered through the chat template, tokenized, optionally packed into fixed-length sequences, and a loss mask marks which tokens contribute to the loss (for assistant-only training, user and system tokens are masked out).
  4. Forward. In each wrapped layer, the NF4 weight block is dequantized to BF16 in GPU registers, multiplied with the input, and the LoRA path \( \frac{\alpha}{r} B(Ax) \) is added. Gradient checkpointing discards most intermediate activations, recomputing them during the backward pass to save memory.
  5. Loss. Cross-entropy on the next token, only over unmasked (assistant) positions.
  6. Backward. Gradients propagate through the frozen dequantized weights (no gradient is stored for them) into \(A\) and \(B\).
  7. Optimise. A paged 8-bit AdamW updates only adapter parameters; optimiser state pages to CPU memory if GPU memory spikes.
  8. Save. Checkpoints contain only adapter weights (tens to hundreds of MB) plus configuration naming the base model.

4.2 Block-wise quantization

A weight matrix is split into blocks (for example 64 or 128 consecutive values). For each block, compute a scale (for symmetric schemes, the absolute maximum divided by the largest representable level) and store each weight as a small integer index into the format's levels. Dequantization multiplies indices' level values by the block scale. Smaller blocks track local magnitude better (higher quality) but store more scales (more memory). GGUF k-quants add a second level: super-blocks of blocks with quantized sub-scales. GPTQ goes further by quantizing columns one at a time and adjusting not-yet-quantized columns to compensate for the error just introduced, using an approximation of the layer's Hessian computed from calibration data. AWQ observes that a small fraction of weight channels see large activations; scaling those channels up before quantization (and inversely scaling the activations) protects them from rounding error.

4.3 What a serving engine does with your model

vLLM loads weights (possibly sharded across GPUs with tensor parallelism), reserves a configurable fraction of remaining GPU memory for the KV cache, and divides that pool into fixed-size blocks (pages) of a few tokens each. Each sequence holds a block table mapping its logical positions to physical blocks — exactly like an OS page table — so memory is allocated on demand, fragmentation is minimal, and sequences that share a prefix (the same system prompt) can share physical blocks (prefix caching). The scheduler runs continuous batching: each iteration it admits waiting requests if blocks are free, runs one decode step for all running sequences, and preempts (swaps or recomputes) sequences if memory runs out. With multi-LoRA serving, requests specify an adapter name; the engine batches requests for different adapters together and applies each adapter's low-rank update with specialised kernels.

6. The Math

6.1 LoRA parameter count

A full update to a \(d \times k\) matrix has \(dk\) parameters; LoRA has \(r(d + k)\). For a \(4096 \times 4096\) projection: full = 16,777,216; LoRA with \(r = 16\) = \(16 \times 8192 = 131{,}072\) — 0.78% of the full matrix. Applied to all seven linear projections in each of 32 layers of a typical 8B model (q, k, v, o in attention with GQA-reduced k/v widths; gate, up, down in the MLP), LoRA at \(r=16\) trains on the order of 40 million parameters — about 0.5% of the model. 6.2 The LoRA forward pass and why the scale exists

\[ h = W_0 x + \frac{\alpha}{r} B A x, \qquad B \in \mathbb{R}^{d \times r},\ A \in \mathbb{R}^{r \times k} \]

Intuition for \(\alpha / r\): if you double the rank, the update's magnitude would roughly change too, forcing you to retune the learning rate. Dividing by \(r\) keeps the effective update scale stable across ranks, so \(\alpha\) works like a rank-independent learning-rate multiplier. (Variants such as rsLoRA scale by \(\alpha/\sqrt{r}\) for better behaviour at high ranks.)

6.4 NF4 levels

For a standard normal distribution, choose 16 values \(q_i\) so that each level covers equal probability mass: roughly, \(q_i = \Phi^{-1}\!\left(\frac{i + 0.5}{16}\right)\) normalised to \([-1, 1]\), with an exact zero included (QLoRA's construction uses asymmetric halves to represent zero exactly). A block of weights is normalised by its absolute maximum \(m\), each value is mapped to the nearest level, and dequantization is \(\hat{w} = m \cdot q_{\text{index}}\). Dense levels near zero, where most weights live, minimise expected rounding error compared with evenly spaced INT4.

6.5 Inference memory and speed under quantization

Weights memory ≈ \(N \times \text{bits}/8\): an 8B model needs ~16 GB at BF16, ~8 GB at 8-bit, ~4.5–5 GB at 4-bit including scales. Since decode reads all weights per step, an upper bound on single-sequence decode speed is memory bandwidth ÷ bytes read per token. With ~1 TB/s of bandwidth (a common order for a data-centre GPU; check your hardware), an 8B BF16 model is bounded near \(10^{12} / (16 \times 10^9) \approx 60\) tokens/s for one sequence; at 4-bit, the bound rises toward ~200 tokens/s. Batching raises total throughput because the weight read is shared across sequences. Illustrative

6.6 The DPO objective

\[ \mathcal{L}_{\text{DPO}} = -\,\mathbb{E}_{(x, y^+, y^-)} \left[ \log \sigma\!\left( \beta \left[ \log\frac{\pi_\theta(y^+ \mid x)}{\pi_{\text{ref}}(y^+ \mid x)} - \log\frac{\pi_\theta(y^- \mid x)}{\pi_{\text{ref}}(y^- \mid x)} \right] \right) \right] \]

Intuition: increase the log-probability of the chosen answer relative to the reference model, decrease it for the rejected answer, and stop pushing once the margin is large (the sigmoid saturates). \(\beta\) (often 0.1) sets how strongly preferences can pull the model away from the reference; too high a pull and quality on everything else degrades.

6.7 Self-hosting break-even

Let a GPU instance cost \(G\) per hour and sustain \(T\) output tokens per second at your quality and latency targets, at utilisation \(u\). Cost per million output tokens is \( \frac{G}{3600\, T\, u} \times 10^6 \). Example Illustrative: \(G = \$4\)/h, \(T = 2{,}000\) tokens/s aggregate under batching, \(u = 0.4\): \(4 / (3600 \times 2000 \times 0.4) \times 10^6 \approx \$1.39\) per million output tokens — before engineering time, redundancy (you need at least two instances), and the input tokens your workload also processes. Low utilisation is the usual reason self-hosting loses to APIs; high, steady volume on a small specialised model is the usual reason it wins.

7.2 QLoRA supervised fine-tuning with TRL + PEFT (Python)

"""QLoRA SFT of an open-weight chat model on conversational JSONL.
pip install "transformers>=5" "trl>=1" "peft>=0.20" "bitsandbytes>=0.45" datasets accelerate
Run: python train_qlora.py --model Qwen/Qwen3-0.6B --train data/triage_train.jsonl --eval data/triage_eval.jsonl
"""
import argparse

import torch
from datasets import load_dataset
from peft import LoraConfig
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from trl import SFTConfig, SFTTrainer


def main() -> None:
    p = argparse.ArgumentParser()
    p.add_argument("--model", default="Qwen/Qwen3-0.6B")
    p.add_argument("--train", required=True)
    p.add_argument("--eval", required=True)
    p.add_argument("--out", default="adapters/triage-v1")
    p.add_argument("--rank", type=int, default=16)
    p.add_argument("--epochs", type=float, default=2.0)
    args = p.parse_args()

    data = load_dataset("json", data_files={"train": args.train, "eval": args.eval})

    bnb = BitsAndBytesConfig(
        load_in_4bit=True,
        bnb_4bit_quant_type="nf4",            # NormalFloat4
        bnb_4bit_use_double_quant=True,       # quantize the block scales too
        bnb_4bit_compute_dtype=torch.bfloat16 # dequantize to BF16 for matmuls
    )
    tokenizer = AutoTokenizer.from_pretrained(args.model)
    model = AutoModelForCausalLM.from_pretrained(
        args.model, quantization_config=bnb, dtype=torch.bfloat16, device_map="auto")

    lora = LoraConfig(
        r=args.rank,
        lora_alpha=2 * args.rank,
        lora_dropout=0.05,
        target_modules="all-linear",          # attention + MLP projections
        task_type="CAUSAL_LM",
    )

    config = SFTConfig(
        output_dir=args.out,
        num_train_epochs=args.epochs,
        per_device_train_batch_size=4,
        gradient_accumulation_steps=4,        # effective batch 16
        learning_rate=2e-4,                   # adapters tolerate higher LRs than full FT
        lr_scheduler_type="cosine",
        warmup_steps=20,
        max_length=1024,                      # truncate long examples; check none are cut
        assistant_only_loss=True,             # learn only the assistant turns
        gradient_checkpointing=True,
        optim="paged_adamw_8bit",             # QLoRA's paged optimiser
        bf16=True,
        logging_steps=10,
        eval_strategy="steps",
        eval_steps=50,
        save_strategy="steps",
        save_steps=50,
        save_total_limit=2,
        load_best_model_at_end=True,
        metric_for_best_model="eval_loss",
        report_to="none",
        seed=42,
    )

    trainer = SFTTrainer(
        model=model,
        args=config,
        train_dataset=data["train"],
        eval_dataset=data["eval"],
        processing_class=tokenizer,
        peft_config=lora,
    )
    trainer.model.print_trainable_parameters()   # expect well under 1% trainable
    trainer.train()
    trainer.save_model(args.out)                 # saves the adapter only
    tokenizer.save_pretrained(args.out)


if __name__ == "__main__":
    main()

What to watch while it trains: training loss should fall smoothly; evaluation loss should fall then flatten — if it rises while training loss keeps dropping, you are overfitting (reduce epochs or rank, add data). print_trainable_parameters() confirms you are training adapters only. Then evaluate with task metrics (§7.4), not just loss: a lower loss does not guarantee better JSON or better labels.

7.4 An evaluation harness across hosted and self-hosted models (Python)

The harness below runs one labelled dataset against several backends — Claude through the Anthropic SDK, and any open model behind an OpenAI-compatible server (vLLM, llama.cpp, Ollama) through the openai client — and reports accuracy, JSON validity, latency and token usage. This is the core of evaluation-led selection.

"""pip install anthropic openai
Usage: python compare_models.py data/triage_test.jsonl"""
import json
import statistics
import sys
import time
from dataclasses import dataclass, field

import anthropic
from openai import OpenAI

SYSTEM = ('Classify the ticket. Reply with JSON {"category": BILLING|TECHNICAL|ACCOUNT, '
          '"priority": 1-4} and nothing else.')


@dataclass
class Result:
    name: str
    correct: int = 0
    valid_json: int = 0
    latencies: list[float] = field(default_factory=list)
    in_tokens: int = 0
    out_tokens: int = 0


class AnthropicBackend:
    def __init__(self, model: str):
        self.name, self.model, self.client = f"anthropic:{model}", model, anthropic.Anthropic()

    def __call__(self, text: str) -> tuple[str, int, int]:
        r = self.client.messages.create(model=self.model, max_tokens=200, system=SYSTEM,
                                        output_config={"effort": "low"},
                                        messages=[{"role": "user", "content": text}])
        return ("".join(b.text for b in r.content if b.type == "text"),
                r.usage.input_tokens, r.usage.output_tokens)


class OpenAICompatibleBackend:
    """vLLM (`vllm serve ...`), llama.cpp (`llama-server`) or Ollama all expose /v1."""
    def __init__(self, base_url: str, model: str):
        self.name, self.model = f"local:{model}", model
        self.client = OpenAI(base_url=base_url, api_key="not-needed-locally")

    def __call__(self, text: str) -> tuple[str, int, int]:
        r = self.client.chat.completions.create(
            model=self.model, max_tokens=200, temperature=0,
            messages=[{"role": "system", "content": SYSTEM}, {"role": "user", "content": text}])
        return r.choices[0].message.content, r.usage.prompt_tokens, r.usage.completion_tokens


def evaluate(backend, rows) -> Result:
    res = Result(backend.name)
    for row in rows:
        start = time.perf_counter()
        reply, tin, tout = backend(row["text"])
        res.latencies.append(time.perf_counter() - start)
        res.in_tokens += tin
        res.out_tokens += tout
        try:
            parsed = json.loads(reply.strip())
            res.valid_json += 1
            res.correct += parsed.get("category") == row["category"]
        except (json.JSONDecodeError, AttributeError):
            pass
    return res


def main(path: str) -> None:
    rows = [json.loads(line) for line in open(path, encoding="utf-8")]   # {"text":..., "category":...}
    backends = [
        AnthropicBackend("claude-haiku-5-5"),                         # Version-sensitive model IDs
        AnthropicBackend("claude-sonnet-5-5"),
        OpenAICompatibleBackend("http://localhost:8000/v1", "triage"),  # vLLM base + LoRA adapter
        OpenAICompatibleBackend("http://localhost:8000/v1", "Qwen/Qwen3-8B"),  # base model, no adapter
    ]
    print(f"{'backend':38} {'acc':>6} {'json':>6} {'p50 s':>6} {'p95 s':>6} {'in tok':>8} {'out tok':>8}")
    for b in backends:
        r = evaluate(b, rows)
        n = len(rows)
        lat = sorted(r.latencies)
        p95 = lat[int(0.95 * (n - 1))]
        print(f"{r.name:38} {r.correct / n:6.1%} {r.valid_json / n:6.1%} "
              f"{statistics.median(lat):6.2f} {p95:6.2f} {r.in_tokens:8d} {r.out_tokens:8d}")


if __name__ == "__main__":
    main(sys.argv[1])

Multiply token counts by each provider's current prices (or your GPU cost model from §6.7) to add a cost column. 7.7 A tiny Go client for an OpenAI-compatible local server

Gateways, sidecars and CLIs written in Go can call a local model with nothing but the standard library.

package main

import (
	"bytes"
	"context"
	"encoding/json"
	"fmt"
	"net/http"
	"os"
	"time"
)

type message struct {
	Role    string `json:"role"`
	Content string `json:"content"`
}

type chatRequest struct {
	Model     string    `json:"model"`
	Messages  []message `json:"messages"`
	MaxTokens int       `json:"max_tokens"`
}

type chatResponse struct {
	Choices []struct {
		Message message `json:"message"`
	} `json:"choices"`
	Usage struct {
		PromptTokens     int `json:"prompt_tokens"`
		CompletionTokens int `json:"completion_tokens"`
	} `json:"usage"`
}

func main() {
	base := os.Getenv("LLM_BASE_URL") // e.g. http://localhost:11434/v1 (Ollama) or :8000/v1 (vLLM)
	if base == "" {
		base = "http://localhost:8000/v1"
	}
	body, _ := json.Marshal(chatRequest{
		Model:     "triage",
		Messages:  []message{{Role: "user", Content: "Refund not received after 10 days"}},
		MaxTokens: 100,
	})
	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
	defer cancel()
	req, _ := http.NewRequestWithContext(ctx, http.MethodPost, base+"/chat/completions", bytes.NewReader(body))
	req.Header.Set("Content-Type", "application/json")

	resp, err := http.DefaultClient.Do(req)
	if err != nil {
		fmt.Fprintln(os.Stderr, "request failed:", err)
		os.Exit(1)
	}
	defer resp.Body.Close()
	if resp.StatusCode != http.StatusOK {
		fmt.Fprintln(os.Stderr, "unexpected status:", resp.Status)
		os.Exit(1)
	}
	var out chatResponse
	if err := json.NewDecoder(resp.Body).Decode(&out); err != nil || len(out.Choices) == 0 {
		fmt.Fprintln(os.Stderr, "bad response:", err)
		os.Exit(1)
	}
	fmt.Printf("%s\n(tokens in=%d out=%d)\n", out.Choices[0].Message.Content,
		out.Usage.PromptTokens, out.Usage.CompletionTokens)
}

8. Applications: How Teams Use Model Choice, Fine-Tuning and Quantization

  • Model portfolios. Mature teams run several models: a frontier model for complex reasoning and agentic flows, a small hosted model for high-volume simple tasks, and sometimes a self-hosted open model for sensitive data. A routing layer chooses per route, backed by evaluation scores (Chapter 5 covers cascades).
  • Specialised small models for narrow tasks. Classification, entity extraction, PII detection, query rewriting and routing are classic fine-tuning targets: stable task definitions, abundant labelled data from production, and high volume where latency and cost dominate.
  • Brand voice and format. Marketing copy, clinical note formatting, or legal clause drafting in house style — behaviours that are easier to demonstrate with thousands of examples than to describe in a prompt.
  • Data-residency deployments. Regulated industries (healthcare, banking, government) self-host open models in their own VPC or data centre, combined with RAG over internal documents, to keep data within jurisdiction.
  • Multi-tenant adapters. SaaS vendors serve one base model with per-customer or per-task LoRA adapters via multi-LoRA serving, keeping GPU fleets small while offering customisation.
  • Edge and offline. Quantized 1–8B models run on laptops, phones, factory gateways or ships with intermittent connectivity, via llama.cpp or vendor on-device runtimes.
  • Evaluation infrastructure. Local quantized models served by Ollama or llama.cpp run inside CI to test prompt and parsing logic cheaply, while final quality gates use the production model.

9. Case Studies

9.1 LoRA: adapting GPT-3 175B with a fraction of the parameters

Verified The original LoRA paper (Hu et al., Microsoft, 2021) reported that, compared with full fine-tuning of GPT-3 175B with Adam, LoRA reduced the number of trainable parameters by 10,000 times and GPU memory by about three times, while matching or exceeding fine-tuning quality on the evaluated tasks and adding no inference latency once merged. Lesson: the adaptation an application needs is low-dimensional; you rarely need to touch all the weights. (arXiv:2106.09685)

9.2 QLoRA and Guanaco: a 65B fine-tune on one GPU

Verified Dettmers et al. (2023) introduced NF4, double quantization and paged optimisers, and reported fine-tuning a 65B-parameter model on a single 48 GB GPU while preserving 16-bit fine-tuning performance. Their Guanaco models, trained this way in about a day on a single GPU, were reported to reach 99.3% of ChatGPT's performance on the Vicuna benchmark at the time. The authors also cautioned about the limits of such chatbot benchmarks. Lesson: memory engineering, not new learning algorithms, democratised fine-tuning; and benchmark claims need your own evaluation behind them. (arXiv:2305.14314)

9.3 LoRA Land: many small specialists versus one generalist

Verified Predibase's "LoRA Land" study (Zhao et al., 2024) trained 310 LoRA adapters (4-bit base models) across 10 base models and 31 tasks and reported that fine-tuned models outperformed their base models by 34 points and GPT-4 by 10 points on average across those tasks; it also described serving many adapters on a single GPU with their LoRAX server. Lesson: for narrow, well-defined tasks, a fine-tuned small open model can beat a general frontier model of its era — but results are task-dependent, and frontier models have improved since, so measure on your own data. (arXiv:2405.00732)

9.4 Apple's on-device models: adapters plus aggressive quantization

Verified In June 2024, Apple's machine-learning research blog described its on-device foundation model for Apple Intelligence: a roughly 3B-parameter model compressed with a mixed 2-bit/4-bit scheme averaging about 3.5 bits per weight, with task-specific LoRA adapters (rank 16) loaded dynamically on top of a shared base model for features such as summarisation and proofreading. Lesson: the base-plus-adapters architecture and low-bit quantization are not just research ideas; they are how a consumer product ships many specialised behaviours within strict memory budgets. (Apple Machine Learning Research)

9.5 vLLM: serving efficiency through memory management

Verified Kwon et al. (SOSP 2023) introduced PagedAttention, which stores the KV cache in non-contiguous fixed-size blocks managed like virtual-memory pages, and reported that vLLM improved throughput of popular LLMs by 2–4× at the same latency compared with the state-of-the-art serving systems they evaluated (FasterTransformer and Orca), with larger gains for longer sequences and more complex decoding. Lesson: for self-hosting, the serving engine can matter as much as the model; operating-system ideas transfer directly. (arXiv:2309.06180)

12. Common Mistakes and Production Failures

  • Fine-tuning to add knowledge. The model memorises some facts, hallucinates neighbouring ones confidently, and goes stale the moment documents change. Use RAG for knowledge.
  • Choosing by leaderboard. Public benchmarks may be contaminated and rarely resemble your task. Build the private evaluation set first.
  • Ignoring the licence. Shipping a product on a non-commercial or custom-licensed model without review creates legal risk; fine-tuned derivatives usually inherit terms.
  • Wrong chat template. Training with one template and serving with another (or none) silently ruins quality. Use the tokenizer's template in both places and test the rendered prompt.
  • Training on prompts, not just answers. Without assistant-only or completion-only loss, the model also learns to generate user and system text, wasting capacity.
  • Train/test leakage. Near-duplicate tickets in both splits inflate scores; deduplicate by normalised text or embeddings.
  • Evaluating only loss. Lower loss can coexist with worse JSON validity or label accuracy. Use task metrics.
  • Merging into a 4-bit base. Merging LoRA weights into quantized weights loses precision; merge into the BF16 base, then quantize.
  • Over-quantizing small models. 3-bit or 2-bit quantization of small models often collapses quality; test before shipping.
  • Unpinned base models. A model repository can be updated; pin revisions (commit hashes) so a re-run reproduces training.
  • Forgetting safety. Fine-tuning can weaken a model's safety behaviour; re-run safety and refusal evaluations, and add guardrails (Chapter 5) for self-hosted models.
  • Under-provisioned KV cache. Serving fails or thrashes under long prompts because the KV pool was sized for short ones; size with Chapter 1's formula and set --max-model-len deliberately.

13. Production Engineering

13.1 Model registry and governance

  • Record per model/adapter: base model and revision, dataset version, training config, evaluation scores per route, licence, approved data classifications, owner, deprecation date.
  • Promote through environments with automated evaluation gates and canary traffic; keep rollback to the previous adapter one config change away.

13.2 Serving operations

  • Monitor GPU utilisation, KV-cache usage, queue length, preemptions, TTFT and tokens/s (vLLM exposes Prometheus metrics); autoscale on queue depth or KV usage, not CPU.
  • Run at least two replicas across failure domains; warm new replicas before taking traffic (model load takes minutes).
  • Set request limits (max context, max output, concurrent requests per tenant) at a gateway in front of the engine.

13.3 Security

  • Download models only from trusted sources, verify hashes, and prefer the safetensors format over pickle-based checkpoints, which can execute code on load.
  • Never expose inference servers directly to the internet; put authentication, rate limiting and logging in front.
  • Treat training data as sensitive: fine-tuned models can regurgitate training examples, so scrub PII and secrets before training.
  • Supply-chain risk (poisoned models or datasets) is an OWASP LLM Top 10 category; Chapter 6 and Part 11 Chapter 5 go deeper.

13.4 Cost management

  • Track cost per 1,000 requests per route for both hosted and self-hosted options, including idle GPU time.
  • Consolidate low-volume tasks onto one base model with multiple adapters; scale to zero for development environments.
  • Re-run the API-vs-self-host comparison quarterly: API prices and open-model capabilities both move fast.

14. Exercises

Exercise 1 · Foundational

Compute the number of LoRA parameters for rank 8 applied to the q, k, v and o projections of a model with hidden size 2048, 16 layers, and KV projection width 512. What fraction of a 1.5B-parameter model is that?

Solution

q: 8 × (2048 + 2048) = 32,768; k: 8 × (2048 + 512) = 20,480; v: 20,480; o: 32,768. Per layer 106,496; × 16 layers = 1,703,936 ≈ 1.7M parameters, about 0.11% of 1.5B.

Exercise 2 · Intermediate

A product team wants to fine-tune a model "so it knows our 4,000-page product documentation." Write the reply you would send, including what you would build instead and how you would measure success.

Solution

Explain that fine-tuning is poor at reliably injecting large, changing knowledge: the model would learn some facts imperfectly, hallucinate others with confidence, could not cite sources, and would need retraining every documentation release. Propose RAG: parse and chunk the docs, embed them into a vector index with metadata (product, version), retrieve and rerank per question, and instruct the model to answer only from retrieved passages with citations. Success metrics: a golden set of 200 real questions with expected answers and source pages; retrieval recall@10 and answer faithfulness/correctness via LLM-as-judge with human spot checks; latency and cost per answer. Fine-tuning may come later for tone or answer format if evaluation shows a gap.

Exercise 3 · Intermediate

Run train_qlora.py on a small public instruction dataset (or your own 500 examples) with ranks 4, 16 and 64. Plot eval loss and a task metric against rank. What do you expect, and why might the task metric disagree with loss?

Solution

Expect diminishing returns: rank 4 may underfit a broad task; 16 often captures most of the gain; 64 may overfit a small dataset (eval loss rising late). The task metric can disagree because loss averages over all assistant tokens (including phrasing) while the metric checks only what matters (label correctness, JSON validity). A model can reduce loss by matching wording style better without improving decisions. Choose the rank by task metric with a held-out set, and prefer the smallest rank within noise of the best.

Exercise 4 · Advanced

Your company processes 30 million short classification requests per month (≈400 input, 10 output tokens each). Build a cost model comparing (a) a small hosted model, (b) a self-hosted fine-tuned 1.5B model on two GPU instances. List every cost component and the break-even volume. Use placeholder prices and state assumptions explicitly.

Solution

Illustrative (a) Hosted: tokens/month = 30M × 400 = 12B input, 300M output. With placeholder prices \$0.10 per M input and \$0.50 per M output: \$1,200 + \$150 = \$1,350/month, plus engineering for resilience. (b) Self-hosted: two instances at \$2/h × 730 h = \$2,920/month, plus storage/egress/monitoring (~\$200), plus engineering time (e.g. 0.2 FTE for operations — often the largest component), plus fine-tuning and evaluation runs. Capacity check: 30M requests/month ≈ 11.6 req/s average; a 1.5B model on vLLM handles this comfortably. Break-even on infrastructure alone requires hosted cost > ~\$3,100/month, i.e. roughly 2.3× today's volume at these prices — and higher once staff time is included. Conclusion: at this volume and these prices, the hosted small model wins unless residency or latency requirements force self-hosting. The model's value is in making assumptions explicit and re-running it when prices or volumes change.

Exercise 5 · Advanced

Design a CI pipeline that retrains a triage adapter weekly from newly labelled production tickets and promotes it only if it is better. Include data, training, evaluation and rollout stages, and the guardrails against silent regressions.

Solution
  1. Data: export the week's human-corrected labels; PII scrubbing; deduplicate against the frozen test set; version the dataset (e.g. DVC or object-store snapshot with hash).
  2. Train: QLoRA job on a GPU runner with pinned base revision and config; store adapter and metrics.
  3. Evaluate: frozen golden test set plus a rolling "recent" set; metrics: accuracy per class, JSON validity, latency; safety/refusal suite; compare with the production adapter using a paired test (e.g. McNemar on per-example correctness).
  4. Gate: promote only if overall accuracy is not worse within confidence bounds and no class regresses beyond a threshold.
  5. Rollout: register adapter; vLLM multi-LoRA loads it under a new name; route 5% traffic (canary) and compare online metrics (human override rate); then 100%.
  6. Rollback: routing config points back to the previous adapter name; keep the last three adapters loaded.

15. Interview Questions

Conceptual Explain LoRA and why it adds no inference latency.

LoRA freezes a pretrained weight \(W_0\) and learns a low-rank update \(\Delta W = BA\) with rank \(r\), scaled by \(\alpha/r\). Only \(A\) and \(B\) train, a tiny fraction of parameters. After training, \(W = W_0 + \frac{\alpha}{r}BA\) can be computed once and stored, so the deployed model has exactly the original architecture and cost. Keeping adapters unmerged adds a small overhead but enables multi-adapter serving.

Conceptual What three ideas make QLoRA work?

NF4 4-bit storage of the frozen base model with levels matched to normally distributed weights; double quantization of the per-block scales to save memory; paged optimisers using unified memory to survive memory spikes. Computation happens in BF16 by dequantizing blocks on the fly, and gradients flow only into 16-bit LoRA adapters.

Architecture How would you choose a model for a new summarisation feature?

Define requirements (quality bar, latency, volume, data constraints, budget). Build an evaluation set of 100–300 real documents with reference summaries or a rubric; define metrics (faithfulness and coverage via LLM-as-judge with human calibration, length, latency, cost). Shortlist 3–5 models across tiers (hosted large/small, open-weight if residency matters). Run, compare, choose the cheapest that passes with margin. Re-evaluate on model updates.

Scenario Leadership asks to "fine-tune our own model to stop hallucinations." How do you respond?

Fine-tuning does not remove hallucination and can increase confident errors when used to inject knowledge. Hallucination is mitigated by grounding (RAG with citations), constrained outputs, abstention instructions, verification steps and evaluation (Chapter 5). Propose measuring hallucination rate on a golden set first, then applying those fixes; fine-tune only for behaviours like abstaining correctly or format, if evaluation shows a residual gap.

Conceptual Compare GPTQ, AWQ and GGUF.

GPTQ is post-training weight quantization that uses approximate second-order information to compensate rounding error layer by layer with calibration data; good GPU kernels exist. AWQ protects salient weight channels identified from activation statistics by rescaling before quantization; robust 4-bit quality and fast GPU inference. GGUF is a file format (llama.cpp) containing weights in various block-quantized types (k-quants), tokenizer and metadata, optimised for CPU/Apple Silicon/consumer GPUs. GPTQ/AWQ are methods; GGUF is a container with its own quantization types.

Architecture Design multi-tenant customisation for a SaaS product where each enterprise customer wants its own tone.

One base open model on vLLM with multi-LoRA serving; per-tenant adapters trained with QLoRA on tenant-approved examples; adapter registry mapping tenant to adapter version; gateway injects the adapter name per request; per-tenant evaluation and rollback; isolation of training data per tenant; cap the number of adapters per GPU and load on demand. For tenants with few examples, use per-tenant prompt templates instead.

Coding What does assistant_only_loss=True do in TRL, and what goes wrong without it?

It masks the loss so only assistant-turn tokens contribute to gradients. Without it, the model also learns to predict system and user text, which wastes capacity and can make the model imitate user phrasing or regurgitate system prompts. It requires a chat template that marks generation spans; TRL patches known templates.

Scenario After quantizing to 4-bit, JSON validity drops from 99% to 93%. What do you try?

Enable constrained/guided decoding in the serving engine (vLLM supports JSON-schema-guided generation) so validity no longer depends on the model; try a better 4-bit method (AWQ vs. naive), larger group size settings or keep sensitive layers (embeddings, LM head) in higher precision; try 8-bit/FP8 if memory allows; add calibration data from your domain; re-evaluate accuracy, not just validity.

Conceptual What is the difference between open-weight and open-source models, and why does it matter commercially?

Open-weight releases publish weights under some licence but usually not training data or full training code; open-source (per OSI's Open Source AI Definition) also provides enough data information and code to reproduce. Commercially, what matters is the licence: permissive (Apache/MIT) vs. custom terms with use restrictions or user-count thresholds, and whether derivatives inherit obligations.

16. Knowledge Check

  • Choose models with a private evaluation set: the cheapest model that meets the quality bar wins.
  • Read licences; "open" ranges from Apache/MIT to custom terms with real restrictions.
  • RAG for knowledge, fine-tuning for behaviour, prompting first.
  • LoRA learns \(BA\) low-rank updates; QLoRA adds NF4, double quantization and paged optimisers to fit large models on one GPU.
  • DPO tunes preferences without RL; distillation transfers a task from a large teacher to a small student (check terms).
  • 8-bit is near-lossless; 4-bit needs a good method and evaluation; formats differ by hardware target.
  • vLLM/SGLang for GPU production; llama.cpp/Ollama for local and edge; expose OpenAI-compatible endpoints to your services.

Why is \(B\) initialised to zero in LoRA?

  1. To make the adapter sparse
  2. To reduce memory usage
  3. So the adapted model starts exactly equal to the base model
  4. So that the rank can be changed during training
With B = 0, BA = 0, so the initial forward pass equals the pretrained model and training starts from a known-good point.

Which problem is RAG better suited for than fine-tuning?

  1. Answering questions from frequently updated internal policies with citations
  2. Producing output in a strict house writing style
  3. Reducing latency by moving a narrow task to a smaller model
  4. Teaching an internal DSL's syntax
Changing knowledge with provenance is retrieval's strength. Style, latency via smaller models, and skills are fine-tuning targets.

Roughly how much GPU memory do the frozen weights of an 8B-parameter model take in NF4?

  1. About 32 GB
  2. About 16 GB
  3. About 1 GB
  4. About 4.5–5 GB including quantization scales
4 bits = 0.5 bytes per parameter → 4 GB, plus block scales and unquantized layers, giving roughly 4.5–5 GB.

You trained a LoRA adapter on a 4-bit base. What is the recommended way to produce a deployable quantized model?

  1. Merge the adapter directly into the 4-bit weights
  2. Merge into the BF16 base model, then quantize the merged model
  3. Discard the adapter and quantize the base
  4. Convert the adapter to GGUF only
Merging into quantized weights loses precision; merge into full-precision weights first, then apply the chosen quantization method and re-evaluate.

What is the main reason vLLM achieves high throughput?

  1. It uses a smaller vocabulary
  2. It disables the KV cache
  3. Paged KV-cache management with continuous batching fits more sequences in GPU memory
  4. It always quantizes to 2 bits
PagedAttention eliminates most KV-cache fragmentation and enables prefix sharing; continuous batching keeps the GPU busy, so many more concurrent sequences fit.

A model's licence requires a separate agreement above a monthly active user threshold. Which licence family typically has such a clause?

  1. Meta's Llama community licences
  2. Apache-2.0
  3. MIT
  4. BSD-3-Clause
Llama 2 and 3 licences required a separate licence for products exceeding 700 million monthly active users. OSI licences such as Apache, MIT and BSD have no such clause.
