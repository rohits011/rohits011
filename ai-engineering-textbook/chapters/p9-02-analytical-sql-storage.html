Part 9 · Chapter 2

Analytical SQL, Warehouses, Lakes & the Lakehouse

You know how to make Postgres fast for a thousand small transactions per second. This chapter is about the opposite workload: a handful of queries that each scan billions of rows. It explains why analytical engines store data by column, how Parquet files and lakehouse table formats such as Iceberg give you ACID tables on object storage, how cloud warehouses separate storage from compute, and how to model data so that analysts can query it correctly.

  • Prerequisites: Solid SQL (joins, GROUP BY, indexes) and Postgres or MySQL operational experience; Chapter 9.1 is helpful but not required.
  • You will be able to: write window-function, grouping-set and approximate queries; read a columnar query plan; explain Parquet's layout, encodings and predicate pushdown; compare Snowflake, BigQuery and Redshift architectures; design a star schema with SCD Type 2 dimensions; explain how Iceberg, Delta Lake and Hudi implement snapshots, time travel and ACID commits on S3; and use DuckDB as a local analytical engine.

1. Introduction: Two Workloads, Two Kinds of Database

Your order service writes one row per order and reads orders by primary key. Postgres excels at this: a B-tree index finds a row in a few page reads, row-oriented heap pages keep all of an order's columns together, and MVCC lets thousands of short transactions run concurrently. This is OLTP, online transaction processing.

Now finance asks: revenue by merchant category by week for the last three years, compared with the same week the previous year, excluding refunds. That query touches hundreds of millions of rows but only five of the orders table's forty columns. On a row store it reads every byte of every row, including the 35 irrelevant columns, and it competes for buffer cache and I/O with checkout traffic. This is OLAP, online analytical processing, and it needs a different storage layout (columnar), a different execution model (vectorized, parallel scans), different modelling (denormalized star schemas instead of 3NF), and usually a different system: a cloud warehouse such as Snowflake, BigQuery or Redshift, or a lakehouse built from open files (Parquet) and open table formats (Apache Iceberg, Delta Lake, Apache Hudi) on object storage, queried by engines such as Spark, Trino or DuckDB.

This chapter goes from the SQL you write, down through the query plan, into the bytes on disk, and back up to the table formats and modelling patterns that make analytical data trustworthy.

Bridging from Java & Spring Boot

What you already know
JPA entities mapped to normalized Postgres tables, Flyway migrations that evolve the schema, B-tree indexes chosen from EXPLAIN ANALYZE, read replicas for reporting queries, and the pain of a long-running report query holding back vacuum or saturating I/O on the primary.
Why that is not enough
Row storage and B-trees optimize for point lookups and small ranges. Analytical queries scan, aggregate and join huge fractions of the data; indexes do not help, normalization multiplies joins, and a single-node database cannot scale scans horizontally. Running analytics on OLTP replicas works until it does not, usually around the time data reaches hundreds of GB.
The modern approach
Replicate operational data (CDC, Chapter 9.3) into columnar storage: a managed warehouse, or Parquet files under an Iceberg/Delta table on S3/GCS/ADLS. Model it into fact and dimension tables. Query it with engines that prune files by statistics, read only needed columns, and process data in vectorized batches across many machines.
Where Python and Go fit
Python is the lingua franca for working with these formats (PyArrow, PyIceberg, DuckDB, Polars). Go appears in ingestion tooling and has Parquet and Arrow libraries. Java/Scala is the home of Spark, Trino, Flink and the reference Iceberg implementation, so JVM skills transfer directly to the engines.
In production
Warehouses are governed with role-based access, cost controls (warehouse auto-suspend, slot reservations), and table maintenance (clustering, compaction, snapshot expiry). Lakehouse tables need the same care your Postgres gets from vacuum and index maintenance, just under different names.
Use it when / avoid it when
Use columnar OLAP for scans and aggregations over large history. Avoid it as the backing store for request-path point lookups or high-rate single-row updates; that is still Postgres, a key-value store, or an online feature store.

The core asymmetry

OLTP optimizes for latency of many small operations; OLAP optimizes for throughput of few large scans. Almost every design decision in this chapter (columns, compression, immutable files, batch commits, denormalized models) follows from that.

2. History: From Codd to Open Table Formats

2.1 Relational and the first warehouses (1970–1996)

Edgar Codd's 1970 paper defined the relational model. By the late 1980s companies were copying operational data into separate "decision support" databases so that reports would not slow down transactions. Bill Inmon's Building the Data Warehouse (1992) argued for an enterprise-wide, normalized warehouse feeding departmental marts. Ralph Kimball's The Data Warehouse Toolkit (1996) argued for dimensional modelling: business-process-oriented star schemas that analysts can query directly. Both schools still shape how teams organize warehouses. The SQL:1999 standard added GROUPING SETS, ROLLUP and CUBE; SQL:2003 standardized window functions.

2.2 Columnar engines and MPP (2000s)

Research systems such as MonetDB and the C-Store paper (Stonebraker et al., VLDB 2005) showed that storing columns separately, compressing them aggressively, and executing queries over compressed columns was dramatically faster for analytics. C-Store was commercialized as Vertica. MPP (massively parallel processing) appliances such as Teradata, Netezza and Greenplum spread scans across many nodes with shared-nothing architecture.

2.3 Hadoop, Hive and the data lake (2006–2013)

Hadoop (2006) made it cheap to store everything in HDFS and process it with MapReduce. Hive (developed at Facebook, open-sourced 2008) put SQL on top, along with the Hive Metastore, which mapped table names to directories and is the ancestor of today's catalogs. The term "data lake" was coined by James Dixon around 2010. Google's Dremel paper (VLDB 2010) described nested columnar storage and tree-structured query execution; it inspired Apache Parquet, created by Twitter and Cloudera in 2013. Hortonworks and Facebook introduced ORC in Hive the same year. Lakes delivered cheap storage but became "swamps": directories of files with no transactions, no schema enforcement and no reliable way to update or delete a row.

2.4 Cloud warehouses separate storage and compute (2010–2016)

Google announced BigQuery in 2010, exposing Dremel as a service. Amazon Redshift was announced in late 2012 (based on technology licensed from ParAccel) and became generally available in early 2013. Snowflake, founded in 2012 and generally available in 2015, was built from scratch for the cloud with storage on S3 and independent virtual warehouses for compute; its design was published at SIGMOD 2016. Separation of storage and compute is the defining architectural shift of this era: you pay for storage continuously and for compute only while queries run.

2.5 Table formats and the lakehouse (2017–2026)

Three projects independently attacked the lake's lack of transactions. Apache Hudi was built at Uber (introduced publicly in 2017) for incremental upserts on HDFS. Apache Iceberg was created at Netflix to fix Hive table correctness and performance problems, entered the Apache incubator in 2018, and graduated in 2020. Delta Lake was open-sourced by Databricks in 2019. The 2021 CIDR paper "Lakehouse" by Armbrust and colleagues named the architecture: warehouse-grade management (ACID, schema, time travel, governance) over open files in object storage. Since then the formats have converged on features: Iceberg's v3 specification (2025) adds deletion vectors, row lineage and a variant type for semi-structured data, and Delta Lake's 4.x line adds a variant type and catalog-coordinated commits Version-sensitive · checked Nov 2026. Warehouses responded by reading and writing Iceberg natively, and DuckDB (2019) brought a fast embedded columnar engine to laptops; its 1.4 LTS release (September 2025) added Iceberg writes and MERGE.

3.2 Window functions

A window function computes a value for each row using a set of related rows (its window) without collapsing them as GROUP BY does. The anatomy is func(...) OVER (PARTITION BY ... ORDER BY ... frame):

  • PARTITION BY splits rows into independent groups (per zone, per customer).
  • ORDER BY orders rows within a partition, which ranking and offset functions need.
  • Frame selects which ordered rows feed an aggregate: ROWS BETWEEN 6 PRECEDING AND CURRENT ROW (a physical 7-row window) or RANGE BETWEEN INTERVAL 7 DAYS PRECEDING AND CURRENT ROW (a logical window by value). The default frame when ORDER BY is present is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW, which produces running totals and surprises people when ties exist.

Families: ranking (ROW_NUMBER, RANK, DENSE_RANK, NTILE, PERCENT_RANK), offset (LAG, LEAD, FIRST_VALUE, LAST_VALUE, NTH_VALUE), and aggregate (SUM, AVG, COUNT over a frame). The QUALIFY clause (Snowflake, BigQuery, DuckDB, Databricks) filters on window results the way HAVING filters on aggregates, which removes a layer of subquery for "top N per group" and deduplication.

Canonical uses: deduplicate CDC rows by keeping the latest version per key (ROW_NUMBER() OVER (PARTITION BY id ORDER BY updated_at DESC) = 1); sessionization (start a new session when LAG(ts) is more than 30 minutes earlier, then running-sum the session starts); period-over-period comparisons with LAG; moving averages; cumulative distributions.

3.3 Common table expressions and recursion

CTEs (WITH name AS (...)) name intermediate results, making long analytical queries readable as a pipeline of steps, which is how dbt models are usually written. Most modern engines inline CTEs and optimize across them (Postgres stopped treating CTEs as optimization fences by default in version 12). WITH RECURSIVE walks hierarchies (org charts, category trees, bill of materials) and graph-like structures; it is rarer in analytics but invaluable when needed.

3.4 GROUPING SETS, ROLLUP and CUBE

Reports often need totals at several levels: by borough and payment type, by borough alone, and a grand total. Writing three queries and a UNION ALL scans the data three times. GROUPING SETS ((borough, payment_type), (borough), ()) computes all three in one pass. ROLLUP(a, b, c) is shorthand for the hierarchical sets (a,b,c), (a,b), (a), (); CUBE(a, b) produces all 2n combinations. In the output, columns aggregated away are NULL; the GROUPING(col) function returns 1 when col is a rolled-up placeholder rather than a real null, which you need to label subtotal rows correctly.

3.5 Approximate aggregates

Exact COUNT(DISTINCT user_id) over billions of rows requires remembering every distinct value (memory proportional to cardinality) and a shuffle across nodes. HyperLogLog (HLL) estimates distinct counts in a few kilobytes with roughly 1–2% error, and HLL sketches are mergeable: you can store a daily sketch per merchant and combine them into weekly or monthly uniques without rescanning raw data. Similarly t-digest and KLL sketches estimate quantiles (p50, p99 latency or order value) with bounded error, and Count-Min Sketch estimates frequencies for heavy hitters. SQL surfaces these as APPROX_COUNT_DISTINCT, APPROX_QUANTILES / APPROX_PERCENTILE, approx_top_k and sketch-typed columns (BigQuery's HLL_COUNT.*, Snowflake's HLL_*, Apache DataSketches in Druid/Spark). Use them for dashboards and exploration; use exact counts for billing and finance.

3.6 Columnar storage, compression and encodings

A columnar layout stores each column's values contiguously. Three benefits follow. I/O reduction: a query touching 5 of 40 columns reads roughly an eighth of the bytes. Compression: values of one column share a type and often a small set of distinct values, so lightweight encodings work well: dictionary encoding (replace strings with small integer codes), run-length encoding (store (value, run length) for sorted or repetitive data), bit-packing (store small integers in the minimum bits), delta encoding (store differences between successive timestamps or ids), and byte-stream split for floats. A general-purpose codec (Snappy, ZSTD, LZ4, GZIP) is applied on top. Vectorized execution: operators process a batch of a few thousand values of one column at a time in tight loops (as in Chapter 9.1), and some operators work directly on encoded data (comparing dictionary codes instead of strings).

3.7 Parquet and ORC

Parquet files are divided into row groups (horizontal slices, commonly 128 MB–1 GB of uncompressed data), each containing one column chunk per column, each chunk split into pages (around 1 MB) that are the unit of encoding and compression. The file ends with a footer holding the schema and, for every column chunk, statistics (min, max, null count), offsets, encodings and codec. Optional page indexes add per-page min/max, and optional bloom filters help with equality predicates on high-cardinality columns. Parquet supports nested data (structs, lists, maps) via Dremel-style repetition and definition levels. ORC has an equivalent structure (stripes, streams, a footer with statistics, lightweight indexes every 10,000 rows) and remains common in Hive-heavy environments; Parquet has become the default almost everywhere else.

3.8 Predicate pushdown, projection pushdown and partition pruning

These three optimizations are why lakehouse queries can be fast despite object storage latency:

  • Projection pushdown: read only the column chunks the query references.
  • Predicate pushdown: evaluate filters against row-group and page statistics before reading data. If a row group's pickup_date max is before the filter's lower bound, skip the whole row group. Effectiveness depends on data being clustered on the filter column; random order makes every row group's min/max span the whole range, and nothing is skipped.
  • Partition pruning: when data is laid out by a partition key (Hive-style directories dt=2024-01-15/, or Iceberg hidden partitions), whole files are skipped based on the partition values recorded in metadata.

3.9 Cloud data warehouses

Snowflake has three layers: a cloud-services layer (metadata, optimizer, transactions, access control), virtual warehouses (independent compute clusters of a chosen size that can be started, suspended and scaled), and storage (tables stored as immutable, compressed columnar micro-partitions of roughly 50–500 MB uncompressed in object storage, with min/max metadata for pruning). Because compute is decoupled, a BI team and an ETL job can use separate warehouses on the same data with no contention. Time travel and zero-copy cloning fall out of immutable micro-partitions plus metadata versioning.

BigQuery is serverless: storage in Google's Colossus file system in the Capacitor columnar format, compute in a shared pool of execution units called slots scheduled by Dremel, and an in-memory distributed shuffle tier between stages, all connected by Google's Jupiter network. You pay per byte scanned (on-demand) or for reserved slot capacity. Partitioning (by date or integer range) and clustering (sorting within partitions by up to four columns) are the main levers for both performance and cost.

Amazon Redshift started as a shared-nothing MPP cluster (a leader node plus compute nodes, data distributed by a distribution key, sorted by sort keys). Its RA3 node types and Redshift Serverless separate compute from Redshift Managed Storage backed by S3 with local SSD caching, and Spectrum queries external tables in S3. Distribution style (KEY, EVEN, ALL, AUTO) matters because joins on a shared distribution key avoid network redistribution.

Other important engines: Databricks SQL (Delta Lake with the Photon vectorized engine), Trino/Starburst and Amazon Athena (federated SQL over lake tables), ClickHouse (very fast columnar database, popular for event analytics and observability), Apache Druid and Apache Pinot (real-time OLAP for user-facing dashboards with sub-second latency).

3.10 Dimensional modelling: facts, dimensions and grain

Kimball's method designs analytical tables around business processes (taking an order, completing a trip). Each process gets a fact table whose rows are measurement events at a declared grain ("one row per completed trip", "one row per order line"). Facts hold foreign keys to dimensions plus numeric measures (fare, tip, distance). Measures are additive (sum across all dimensions: revenue), semi-additive (sum across some dimensions but not time: account balance), or non-additive (ratios: tip percentage, which must be recomputed from additive parts). Dimension tables describe the who/what/where/when: dim_zone, dim_date, dim_vendor, dim_payment_type. They are wide, denormalized, and full of descriptive attributes that analysts filter and group by.

A star schema is one fact table joined to its dimensions by surrogate keys. A snowflake schema normalizes dimensions into sub-dimensions (zone → borough), saving a little storage at the cost of more joins; in columnar engines, storage savings are negligible, so stars are preferred. Conformed dimensions (one dim_customer shared by orders, returns and support facts) let analysts compare across processes, the "bus architecture". Fact table types: transaction (one row per event), periodic snapshot (one row per entity per period: daily account balances), and accumulating snapshot (one row per workflow instance updated as it passes milestones: order placed, shipped, delivered). A factless fact records events with no measures (student attended class). Degenerate dimensions such as an order number live directly in the fact table. Junk dimensions group low-cardinality flags.

Surrogate keys (warehouse-generated integers or hashes) rather than natural keys decouple the warehouse from source-system key changes and are required for history tracking.

3.12 Data vault, briefly

Data Vault 2.0 (Dan Linstedt) models the integration layer as hubs (unique business keys), links (relationships between hubs) and satellites (descriptive attributes with load timestamps and record sources, append-only). It is insert-only, highly auditable and resilient to source changes, which suits large enterprises integrating dozens of systems under regulation. It is not meant for direct analyst querying: star-schema marts are built on top. Many teams in practice use a lighter layering (staging → intermediate → marts) instead.

3.13 Data lakes

A data lake stores raw and processed data as files in object storage (S3, GCS, ADLS) in open formats, organized by zones: raw/bronze (as ingested, immutable), cleaned/silver (deduplicated, typed, conformed), curated/gold (business-level aggregates and marts), the "medallion" naming popularized by Databricks. Lakes are cheap, open to every engine, and hold any data type including images and logs for ML. Their classic failures: no atomic multi-file commits (readers see half-written data), no safe concurrent writes, expensive directory listing on object stores, no row-level updates or deletes (a GDPR erasure means rewriting partitions by hand), and schemas that drift silently.

3.14 The lakehouse and open table formats

A table format is a metadata layer that defines which files constitute a table at a point in time. Iceberg, Delta Lake and Hudi all provide:

  • Snapshots: each commit produces a new immutable table version listing its data files.
  • ACID commits on object storage: writers write new files, then atomically publish a new snapshot via a single atomic operation (a catalog compare-and-swap, or a put-if-absent of the next log file). Readers always see a complete snapshot.
  • Optimistic concurrency control: concurrent writers detect conflicts at commit time and retry.
  • Time travel: query AS OF a snapshot id or timestamp; roll back a bad write.
  • Schema evolution: add, drop, rename and reorder columns safely (Iceberg tracks columns by id, so a rename never misreads old files).
  • Partition evolution and hidden partitioning (Iceberg): partitions are derived by transforms such as day(ts) or bucket(16, id); queries filter on ts and pruning happens automatically; the partition spec can change without rewriting old data.
  • Row-level changes: MERGE, UPDATE, DELETE via copy-on-write (rewrite affected files) or merge-on-read (write delete files or deletion vectors and reconcile at read time).
  • File-level statistics in metadata: so engines prune files without listing directories or opening footers.

A catalog (Hive Metastore, AWS Glue, Iceberg REST catalogs such as Apache Polaris, Unity Catalog, Nessie) maps table names to the current metadata pointer and is where the atomic commit happens for Iceberg.

3.15 DuckDB

DuckDB is an in-process columnar SQL engine (like SQLite for analytics): no server, a single library linked into Python, Java (JDBC), Go, Node or the CLI. It uses vectorized execution with morsel-driven parallelism, reads Parquet, CSV, JSON, Iceberg and Delta directly from local disk or object storage, spills to disk for larger-than-memory operations, and integrates zero-copy with pandas, Polars and Arrow. It is ideal for local development against production-shaped data, CI tests of SQL models, embedded analytics inside services, and medium-scale ETL on a single machine.

4. Internal Working: Bytes on Disk, Plans in Memory, Commits on S3

4.1 Anatomy of a Parquet file

yellow_tripdata_2024-01.parquet
+-----------------------------------------------------------+
| "PAR1" magic (4 bytes)                                    |
| Row group 0  (~1M rows)                                   |
|   Column chunk: tpep_pickup_datetime                      |
|     [dictionary page?] [data page 1] [data page 2] ...    |
|   Column chunk: PULocationID   (dict + RLE/bit-packed)    |
|   Column chunk: fare_amount    (plain or byte-stream-split)|
|   ...                                                     |
| Row group 1 ...                                           |
| Row group N ...                                           |
| [column indexes / offset indexes]  (optional page stats)  |
| [bloom filters]                    (optional)             |
| Footer (Thrift FileMetaData):                             |
|   schema, num_rows, key/value metadata (e.g. Arrow schema)|
|   per row group, per column chunk:                        |
|     offsets, sizes, codec, encodings,                     |
|     statistics {min, max, null_count, distinct_count?}    |
| footer length (4 bytes) | "PAR1" magic                    |
+-----------------------------------------------------------+

A reader seeks to the end, reads the footer length and footer, and from then on knows exactly which byte ranges to fetch. On object storage that translates into a handful of HTTP range GETs: one for the footer, then one per needed column chunk in each surviving row group. This is why Parquet works well over S3 even though each request has tens of milliseconds of latency: engines issue many range requests in parallel and skip most of the file.

4.2 Encoding a column, step by step

Take PULocationID (about 260 distinct zone ids) for one million trips. The writer (1) builds a dictionary of distinct values, written once as a dictionary page; (2) replaces each value with its dictionary index, which fits in 9 bits; (3) encodes the index stream with the RLE/bit-packing hybrid: runs of repeated indexes become (value, count) pairs, other stretches are bit-packed 9 bits per value; (4) compresses each page with the chosen codec (ZSTD or Snappy). An int32 column that would take 4 MB raw might occupy a few hundred KB Illustrative. If the data is sorted by zone, RLE collapses it to a few hundred runs. If the dictionary grows too large (high-cardinality strings), the writer falls back to plain encoding for later pages.

4.3 How a columnar engine executes a query

Consider: SELECT pu_borough, SUM(total_amount) FROM trips JOIN dim_zone USING (zone_key) WHERE pickup_date BETWEEN '2024-01-01' AND '2024-01-07' GROUP BY 1. A distributed columnar engine (Snowflake, BigQuery, Spark SQL, Trino) proceeds roughly like this:

  1. Parse and bind names against the catalog; resolve types.
  2. Logical optimization: push the date predicate down to the scan, prune unused columns (only zone_key, pickup_date, total_amount from trips), and decide join order using statistics.
  3. Metadata pruning: consult file/micro-partition min/max statistics for pickup_date; skip files outside the range. For a well-clustered table, 1 week out of 3 years leaves under 1% of files.
  4. Physical planning: the dimension is small, so choose a broadcast hash join (ship dim_zone to every worker) rather than a shuffle (partitioned) hash join.
  5. Distributed execution: each worker scans its assigned files, decodes only the needed column chunks into vectors of a few thousand values, applies the filter as a selection vector, probes the broadcast hash table, and computes a partial aggregate per borough.
  6. Exchange: partial aggregates are shuffled by borough (tiny: a handful of rows per worker) to final aggregators.
  7. Final aggregation and return.

Reading a plan in a columnar engine means looking for: bytes scanned versus table size (pruning efficiency), the join strategy (broadcast vs shuffle), exchange/shuffle volume, and skew (one worker processing far more than others). Section 7.3 shows DuckDB's EXPLAIN ANALYZE.

4.4 Iceberg's metadata tree

An Iceberg table is a tree of immutable files:

  • Catalog entry: table name → location of the current metadata file. This pointer is the only mutable thing.
  • Metadata file (vN.metadata.json): schemas (with column ids), partition specs, sort orders, properties, the list of snapshots, and the current snapshot id.
  • Snapshot: points to one manifest list and records the operation (append, overwrite, delete) and summary statistics.
  • Manifest list (Avro): one entry per manifest file, with partition-value ranges for each manifest so whole manifests can be skipped.
  • Manifest files (Avro): one entry per data or delete file with its path, partition values, record count, and per-column lower/upper bounds, null counts and sizes.
  • Data files (Parquet, ORC or Avro) and delete files (position deletes, equality deletes, or in v3, deletion vectors stored as Roaring bitmaps in Puffin files).

Read path: catalog → metadata file → current snapshot → manifest list (prune manifests by partition range) → manifests (prune data files by column bounds) → read surviving data files, applying delete files. No directory listing is ever needed.

Write path (commit): the writer writes new data files, writes new manifests describing them, writes a new manifest list that references new plus unchanged manifests, writes a new metadata file with the new snapshot, then asks the catalog to atomically swap the pointer from the metadata file it started from to the new one. If another writer committed first, the swap fails; the writer re-reads the latest metadata, checks whether its change conflicts (for an append, usually not; for an overwrite of the same files, yes), and retries by rewriting only the metadata, not the data.

4.5 Delta Lake's transaction log

A Delta table directory contains Parquet data files and a _delta_log/ folder of ordered JSON commit files (00000000000000000000.json, ...001.json). Each commit lists actions: add (a file with its statistics), remove (a file logically deleted), metaData (schema, partitioning), protocol (reader/writer feature versions), and commitInfo. The table state at version N is the replay of commits 0..N. Every 10 commits by default a checkpoint Parquet file summarizes the state so readers do not replay thousands of JSON files. Atomicity comes from creating the next numbered log file with put-if-absent semantics; on stores that historically lacked it (S3 before conditional writes), Delta used a coordination service such as DynamoDB. Newer Delta versions add catalog-managed/coordinated commits so that a catalog, not the file system, arbitrates commits Version-sensitive · checked Nov 2026. Deletion vectors mark deleted rows in existing files without rewriting them.

4.6 Hudi's timeline, copy-on-write and merge-on-read

Hudi organizes a table around a timeline of instants (commits, delta commits, compactions, cleans) in a .hoodie directory, and around file groups identified by a record-key index, so an upsert can find which file group holds a key. Copy-on-Write (CoW) tables rewrite the affected Parquet base file on each update: reads are fast, writes are expensive. Merge-on-Read (MoR) tables append updates to row-based (Avro) log files next to the base file, and readers merge them on the fly until an asynchronous compaction folds logs into a new base file: writes are cheap, reads pay a merge cost. Hudi's strength is high-frequency upserts and incremental queries ("give me all records changed since instant T"), which is why it originated from Uber's need to apply database changelogs to the lake within minutes.

4.7 Snowflake and BigQuery internals in brief

Snowflake automatically partitions table data into micro-partitions in load order and stores per-column min/max, distinct counts and null counts in the metadata service. Pruning uses that metadata; if a large table's natural load order does not match common filters, a clustering key causes a background service to re-sort micro-partitions. Updates and deletes write new micro-partitions and retire old ones in metadata (copy-on-write), which is why time travel and cloning are cheap. BigQuery's Dremel engine compiles a query into stages of a tree; leaf stages read Capacitor columnar files from Colossus, intermediate results go through the distributed in-memory shuffle, and the scheduler assigns slots dynamically, so a query can use thousands of slots for seconds.

5.2 Iceberg metadata tree and pruning

Reading the diagram: two snapshots share manifest A because nothing in the first half of January changed; snapshot 9001 added manifest B. 5.3 Optimistic commit protocol

Reading the diagram: both writers do the expensive work (writing data files) in parallel without locks. Only the final pointer swap is serialized. Writer A loses the race, re-reads the new state, and checks whether Writer B's changes conflict with its own (two appends never conflict; two overwrites of the same partition do, and then A's operation fails). On retry, A rewrites only small metadata files. This is the same optimistic concurrency you use with JPA @Version columns, applied to an entire table.

5.4 A star schema for taxi trips

Reading the diagram: the fact table is narrow and long (one row per trip, foreign keys plus additive measures). Dimensions are short and wide. DIM_ZONE is a role-playing dimension: it joins twice, as pickup and dropoff zone. Its valid_from/valid_to/is_current columns make it SCD Type 2, so if the TLC ever redraws a zone, historical trips keep their original zone attributes. Tip percentage is deliberately absent: it is non-additive, so it is computed at query time as SUM(tip)/SUM(fare).

6. Mathematical Foundations: Scan Cost, Compression and Sketches

6.1 Bytes scanned is the cost function

For analytical engines, a good first-order cost model is bytes read. For a table with \( N \) rows, column widths \( w_c \) after compression, a query touching column set \( Q \), and a fraction \( f \) of files surviving pruning:

\[ \text{bytes}_{\text{columnar}} \approx f \cdot N \sum_{c \in Q} w_c \qquad \text{versus} \qquad \text{bytes}_{\text{row}} \approx N \sum_{c} w_c^{\text{raw}} \]

Illustrative 3 billion trips, 20 columns averaging 6 bytes raw: a row store reads about 360 GB. A columnar query touching 3 columns that compress to 2 bytes each, with 1 week of 3 years surviving pruning (\( f \approx 0.0064 \)): \( 0.0064 \times 3\times10^9 \times 6 \approx 115\ \text{MB} \). That is a 3,000x difference, which is why the same query takes hours on a row store and seconds in a warehouse, and why BigQuery's on-demand pricing (per byte scanned) rewards pruning directly.

6.2 Dictionary encoding size

With cardinality \( d \), each value costs \( \lceil \log_2 d \rceil \) bits plus the dictionary itself:

\[ \text{size} \approx N \lceil \log_2 d \rceil / 8 \;+\; d \cdot \bar{\ell} \]

where \( \bar{\ell} \) is the mean byte length of distinct values. For \( d = 263 \) zones and \( N = 10^6 \): \( 10^6 \times 9/8 \approx 1.1\ \text{MB} \) versus several MB for raw strings. For a column of UUIDs (\( d \approx N \)), the dictionary is as large as the data and gives no benefit, which is why writers fall back to plain encoding.

6.3 Pruning effectiveness and clustering

If a filter selects a fraction \( s \) of the value range and data is perfectly sorted on that column across \( F \) files, about \( sF + 1 \) files survive. If data is randomly ordered, each file's min/max spans nearly the full range and almost all \( F \) files survive. Clustering (sorting or Z-ordering on common filter columns) moves you from the second regime to the first. Z-ordering or Hilbert curves interleave several columns so that pruning works reasonably on each, at the cost of being optimal on none.

6.4 HyperLogLog error

Intuition: hash every value; in a uniformly random hash, seeing a hash with \( k \) leading zeros suggests you have seen about \( 2^k \) distinct values. One estimate is noisy, so HLL splits values into \( m \) buckets by the first bits of the hash, tracks the maximum leading-zero count per bucket, and combines buckets with a harmonic mean. The relative standard error is:

\[ \sigma \approx \frac{1.04}{\sqrt{m}} \]

With \( m = 2^{14} = 16{,}384 \) registers of 6 bits each (about 12 KB), the error is about 0.8%, regardless of whether the true count is a thousand or a billion. Merging two sketches is an elementwise max of registers, which is why sketches can be pre-aggregated per day and rolled up.

6.5 Window function complexity

A window with PARTITION BY p ORDER BY o requires sorting (or hashing then sorting) rows by \( (p, o) \): \( O(n \log n) \), plus a shuffle by \( p \) in a distributed engine. Ranking and running aggregates are then \( O(n) \) in one pass. Sliding-frame aggregates are \( O(n) \) with incremental (add/remove) algorithms for invertible aggregates such as SUM; for MIN/MAX or medians, engines use segment trees giving \( O(n \log w) \). A window without PARTITION BY forces all rows onto one worker: a classic scalability bug.

6.6 Small files: the metadata tax

Each data file costs per-file overhead: a footer read, an HTTP request, a manifest entry, and task scheduling. With per-request latency \( L \) and parallelism \( P \), opening \( F \) files costs about \( F \cdot L / P \) before any useful bytes. Illustrative A streaming job committing every minute into 50 partitions produces 72,000 files per day; at \( L = 30 \) ms and \( P = 64 \), just opening them takes about 34 seconds per full-day query. Compaction to ~512 MB files reduces that by orders of magnitude, which is why table maintenance is not optional.

7.2 Window functions: ranking, period-over-period, moving averages, dedup, sessions

-- (a) Top 3 pickup zones by revenue within each borough, with share of borough revenue.
WITH zone_rev AS (
    SELECT z.borough, z.zone_name, SUM(f.total_amount) AS revenue
    FROM fact_trip f JOIN dim_zone z ON z.zone_key = f.pickup_zone_key
    GROUP BY ALL
)
SELECT borough, zone_name, revenue,
       DENSE_RANK() OVER (PARTITION BY borough ORDER BY revenue DESC) AS rnk,
       revenue / SUM(revenue) OVER (PARTITION BY borough)             AS share_of_borough
FROM zone_rev
QUALIFY rnk <= 3
ORDER BY borough, rnk;

-- (b) Daily trips with day-over-day change, same-weekday-last-week change,
--     and a 7-day trailing moving average (ROWS frame: exactly 7 rows).
WITH daily AS (
    SELECT pickup_date, COUNT(*) AS trips FROM fact_trip GROUP BY 1
)
SELECT pickup_date, trips,
       trips - LAG(trips) OVER w                                 AS dod_change,
       trips::DOUBLE / LAG(trips, 7) OVER w - 1                  AS wow_pct,
       AVG(trips) OVER (w ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS trips_ma7
FROM daily
WINDOW w AS (ORDER BY pickup_date)
ORDER BY pickup_date;

-- (c) Running total vs. the default RANGE frame trap: with ties on pickup_date,
--     RANGE includes all peers, ROWS does not.
SELECT pickup_date, total_amount,
       SUM(total_amount) OVER (ORDER BY pickup_date)                                   AS range_running,
       SUM(total_amount) OVER (ORDER BY pickup_date, trip_id ROWS UNBOUNDED PRECEDING) AS rows_running
FROM fact_trip
LIMIT 20;

-- (d) Deduplicate a CDC-style table: keep the latest version of each key.
CREATE OR REPLACE TABLE orders_cdc AS
SELECT * FROM (VALUES
    (1, 'CREATED', TIMESTAMP '2024-01-01 10:00:00', 'c'),
    (1, 'PAID',    TIMESTAMP '2024-01-01 10:05:00', 'u'),
    (2, 'CREATED', TIMESTAMP '2024-01-01 11:00:00', 'c'),
    (1, 'PAID',    TIMESTAMP '2024-01-01 10:05:00', 'u')      -- duplicate delivery
) t(order_id, status, updated_at, op);

SELECT * FROM orders_cdc
QUALIFY ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY updated_at DESC) = 1;

-- (e) Sessionization: a new "shift" for a vendor when the gap between
--     consecutive pickups in a zone exceeds 30 minutes.
WITH ordered AS (
    SELECT pickup_zone_key, pickup_ts,
           CASE WHEN pickup_ts - LAG(pickup_ts) OVER (PARTITION BY pickup_zone_key ORDER BY pickup_ts)
                     > INTERVAL 30 MINUTE
                  OR LAG(pickup_ts) OVER (PARTITION BY pickup_zone_key ORDER BY pickup_ts) IS NULL
                THEN 1 ELSE 0 END AS is_new_session
    FROM fact_trip
)
SELECT pickup_zone_key,
       SUM(is_new_session) OVER (PARTITION BY pickup_zone_key ORDER BY pickup_ts) AS session_id,
       pickup_ts
FROM ordered
LIMIT 50;

-- Revenue by (borough, payment_type), by borough, and grand total, in one scan.

7.4 Write and inspect Parquet with PyArrow

"""Write the same data sorted and unsorted, then compare size and row-group statistics."""
import duckdb
import pyarrow.compute as pc
import pyarrow.parquet as pq

con = duckdb.connect("tlc.duckdb", read_only=True)
table = con.sql("SELECT * FROM fact_trip").arrow()       # Arrow table, zero-copy

def write(tbl, path: str) -> None:
    pq.write_table(
        tbl, path,
        row_group_size=500_000,            # rows per row group
        compression="zstd", compression_level=3,
        use_dictionary=["payment_type", "pickup_zone_key", "dropoff_zone_key"],
        write_statistics=True,
        write_page_index=True,             # per-page min/max for finer pruning
    )

write(table, "trips_unsorted.parquet")
write(table.sort_by([("pickup_ts", "ascending")]), "trips_sorted.parquet")

for path in ("trips_unsorted.parquet", "trips_sorted.parquet"):
    md = pq.ParquetFile(path).metadata
    col = md.schema.to_arrow_schema().get_field_index("pickup_ts")
    print(f"\n{path}: {md.num_rows:,} rows, {md.num_row_groups} row groups")
    for rg in range(md.num_row_groups):
        stats = md.row_group(rg).column(col).statistics
        print(f"  rg{rg}: pickup_ts min={stats.min} max={stats.max}")

# Predicate pushdown: count row groups that survive a one-day filter.
import datetime as dt
lo, hi = dt.datetime(2024, 1, 15), dt.datetime(2024, 1, 16)
for path in ("trips_unsorted.parquet", "trips_sorted.parquet"):
    md = pq.ParquetFile(path).metadata
    col = md.schema.to_arrow_schema().get_field_index("pickup_ts")
    survivors = sum(
        1 for rg in range(md.num_row_groups)
        if not (md.row_group(rg).column(col).statistics.max < lo
                or md.row_group(rg).column(col).statistics.min >= hi)
    )
    print(f"{path}: {survivors}/{md.num_row_groups} row groups must be read")

t = pq.read_table("trips_sorted.parquet", columns=["pickup_ts", "total_amount"],
                  filters=[("pickup_ts", ">=", lo), ("pickup_ts", "<", hi)])
print(t.num_rows, pc.sum(t["total_amount"]))

Run it and the lesson of Section 6.3 becomes concrete: the unsorted file's row groups all span the whole month, so a one-day filter must read every one; the sorted file's row groups are disjoint, so one or two survive. Sort order is a physical design decision, just as index choice is in Postgres.

7.7 SCD Type 2 with MERGE

-- dim_merchant: merchant_sk, merchant_id, name, category, city,
--               valid_from, valid_to, is_current, row_hash
-- stg_merchant: latest snapshot of the source system (one row per merchant_id)

MERGE INTO dim_merchant AS d
USING (
    -- Rows whose attributes changed appear twice: once to close the old version
    -- (join_key = merchant_id) and once to insert the new one (join_key = NULL).
    SELECT s.merchant_id AS join_key, s.* FROM stg_merchant s
    UNION ALL
    SELECT NULL AS join_key, s.*
    FROM stg_merchant s
    JOIN dim_merchant d ON d.merchant_id = s.merchant_id AND d.is_current
    WHERE d.row_hash <> s.row_hash
) AS src
ON d.merchant_id = src.join_key AND d.is_current
WHEN MATCHED AND d.row_hash <> src.row_hash THEN
    UPDATE SET d.valid_to = current_timestamp(), d.is_current = false
WHEN NOT MATCHED THEN
    INSERT (merchant_sk, merchant_id, name, category, city,
            valid_from, valid_to, is_current, row_hash)
    VALUES (xxhash64(src.merchant_id, current_timestamp()), src.merchant_id, src.name,
            src.category, src.city, current_timestamp(), TIMESTAMP '9999-12-31 00:00:00',
            true, src.row_hash);

-- Point-in-time join: attach the merchant category valid at order time.
SELECT o.order_id, o.order_ts, d.category
FROM fact_order o
JOIN dim_merchant d
  ON d.merchant_id = o.merchant_id
 AND o.order_ts >= d.valid_from AND o.order_ts < d.valid_to;

The UNION ALL trick ("merge with a null join key") lets a single atomic MERGE both close the old row and insert the new one, so readers never see a merchant with zero or two current rows. row_hash (for example sha2(concat_ws('|', name, category, city), 256) computed in staging) makes change detection a single comparison.

8. Real-World Applications

8.1 Enterprise BI on a cloud warehouse

The most common setup: Fivetran/Airbyte or CDC loads source data into Snowflake or BigQuery, dbt builds staging and dimensional marts, and BI tools (Looker, Tableau, Power BI, Superset) query the marts. Separate compute for loading, transformation and BI prevents a dashboard storm from slowing the nightly build.

8.2 Open lakehouse for multi-engine access

Companies with large data volumes, ML workloads, or a desire to avoid vendor lock-in store tables as Iceberg or Delta on object storage. Spark or Flink write; Trino, Snowflake, BigQuery, Databricks SQL and DuckDB read. ML training jobs read the same tables as BI, with time travel providing reproducible training snapshots (Chapter 10.1).

8.3 Real-time user-facing analytics

"Your store's sales today" pages and observability backends need sub-second queries under high concurrency. That is the domain of ClickHouse, Druid and Pinot, which ingest from Kafka and pre-aggregate or index aggressively. Warehouses are rarely the right backend for a page that thousands of merchants load at once.

8.4 Regulatory and audit reporting

SCD Type 2 dimensions, time travel, and immutable snapshots answer "what did we report on March 31, and why?" Auditors care that a historical report can be reproduced exactly; table formats make that a query rather than an archaeology project.

8.5 Local development and CI with DuckDB

Teams run their dbt models or SQL transformations against DuckDB with sampled Parquet fixtures in CI, catching SQL errors and test failures in seconds without warehouse cost. Analysts query production-sized Parquet extracts on laptops.

9.1 Netflix and the origin of Iceberg

Verified Iceberg was created at Netflix to address correctness and performance problems with Hive tables at very large scale: Hive tracked partitions in a metastore but files by directory listing, which made atomic changes impossible and listings slow on S3. Iceberg replaced directory listing with tracked file metadata and atomic snapshot commits. The project's own documentation and the Apache incubation record describe this origin. Source: Apache Iceberg table specification.

9.2 Uber and Apache Hudi

Verified Uber introduced Hudi in 2017 as an incremental processing framework that applies mutations to data in HDFS within minutes and chains incremental processing, splitting storage into a columnar base format and row-based logs. A 2023 follow-up describes Uber's transactional data lake running incremental ETL on Hudi, using incremental reads and upserts instead of recomputing whole partitions, with snapshot reads for backfills. Sources: Hudi: Uber Engineering's Incremental Processing Framework on Apache Hadoop and Setting Uber's Transactional Data Lake in Motion with Incremental ETL Using Apache Hudi.

9.3 Snowflake's architecture paper

Verified Dageville et al. described Snowflake's multi-cluster, shared-data architecture at SIGMOD 2016: storage in S3, independent elastic virtual warehouses, and a cloud services layer for metadata and transactions, with micro-partition pruning instead of indexes. It is the clearest primary source on why separating storage from compute changed warehouse economics. Source: The Snowflake Elastic Data Warehouse (SIGMOD 2016).

9.4 Google Dremel

Verified The Dremel paper (VLDB 2010) introduced the nested columnar representation with repetition and definition levels that Parquet adopted, and multi-level serving trees for interactive queries over trillions of rows; a 2020 retrospective ("Dremel: A Decade of Interactive SQL Analysis at Web Scale") describes how BigQuery evolved toward disaggregated storage, compute and in-memory shuffle. Sources: Dremel: Interactive Analysis of Web-Scale Datasets and Dremel: A Decade of Interactive SQL Analysis at Web Scale.

9.5 Shopify's dbt-on-BigQuery modelling workflow

Verified Shopify's data team described building a production-grade SQL modelling workflow with dbt on BigQuery, with conventions for model layering, testing and CI, an example of dimensional and modular modelling discipline applied at scale. Source: Build Production Grade Workflow with SQL Modelling.

11. Engineering Trade-offs and Decisions

Reading the diagram: the first branch is scale, because the cheapest system is the one you already run. The second is openness: if ML pipelines, multiple engines or long-term cost control matter, a table format over object storage is the default, with the upsert profile choosing between formats. If you value operational simplicity above all, a managed warehouse wins. Real-time user-facing analytics is a separate serving concern regardless of which analytical store you choose. Opinion Many organizations end up with a hybrid: Iceberg as the system of record and a warehouse that reads and writes those Iceberg tables.

11.1 Star schema versus one big table (OBT)

Columnar engines make wide denormalized tables cheap to scan, so some teams skip stars and publish one big table per use case. OBT is simpler for BI tools and fast to query, but duplicates dimension attributes (updating a merchant category means rewriting history), and different OBTs drift apart. A common compromise: model stars as the source of truth and generate OBTs from them as presentation views or tables.

11.2 Copy-on-write versus merge-on-read

CoW makes writes expensive and reads cheap: choose it for tables read far more often than updated (most marts). MoR makes writes cheap and reads more expensive until compaction: choose it for CDC targets updated every few minutes. The compaction schedule is the knob that trades freshness cost for read cost.

11.3 Partitioning granularity

Partition by the most common filter (usually event date), at a granularity that yields files of hundreds of MB. Over-partitioning (by hour and customer) creates millions of tiny files. Under-partitioning forces large scans. With Iceberg, rely on hidden partitioning plus sort order within files rather than encoding every filter into directory structure.

12. Common Mistakes and Production Failures

  • Running analytics on the OLTP primary. A month-end report scans the orders table, evicts the buffer cache and causes checkout latency spikes. Use replicas at minimum, CDC to analytics properly.
  • Window without PARTITION BY on huge data. ROW_NUMBER() OVER (ORDER BY ts) over billions of rows pushes everything to one worker.
  • The default RANGE frame. Running totals that jump in steps because ties on the ordering column are included together.
  • Averaging non-additive measures. Storing tip percentage in the fact table and summing or averaging it across groups.
  • Unpartitioned SELECT * in BigQuery. A single exploratory query scanning tens of TB on on-demand pricing. Require partition filters (require_partition_filter) and set per-user quotas.
  • Small files. Streaming writes every few seconds into many partitions without compaction; query planning time dominates.
  • Never expiring snapshots. Storage grows without bound because every overwritten file is retained for time travel; GDPR deletes are not physically complete until old snapshots expire.
  • SCD Type 1 where Type 2 was needed. Last year's revenue by category changes every time a merchant is recategorized; finance loses trust.
  • Joining facts to current dimension rows. Using is_current instead of the event-time validity range, rewriting history in every report.
  • Treating approximate counts as exact. Billing customers from APPROX_COUNT_DISTINCT.
  • Leaving warehouses running. A Snowflake warehouse with auto-suspend disabled over a weekend.
  • Multiple catalogs for one table. Two engines committing to the same Iceberg table through different catalogs corrupts its history; use exactly one catalog of record.

13. Production Concerns

13.1 Performance

Cluster or sort large tables on dominant filter columns; target file sizes of 256 MB–1 GB; keep statistics fresh; prefer broadcast joins for small dimensions; materialize expensive aggregates (incremental models or materialized views); use result caches for repeated BI queries. Monitor bytes scanned per query and the pruning ratio.

13.2 Cost control

Warehouses: auto-suspend in minutes, size warehouses per workload, resource monitors or budgets, query tagging for chargeback. BigQuery: partition filters required, reservations for predictable workloads, per-project quotas. Lakehouse: lifecycle policies on object storage, snapshot expiry, compaction to reduce request costs.

13.3 Security and governance

Centralize permissions in the catalog (Unity Catalog, Polaris, Lake Formation) or warehouse RBAC; use column masking and row-access policies for PII; encrypt at rest with managed keys; never grant direct bucket access that bypasses catalog policies. Deletion for privacy requests must include expiring snapshots that still reference deleted rows. Chapter 9.4 covers governance in depth.

13.4 Reliability and maintenance

Schedule table maintenance like you schedule vacuum: compaction, manifest rewriting, snapshot expiry, orphan file removal. Back up catalog state. Test restores via time travel. Alert on commit conflicts and failed maintenance jobs.

13.5 Monitoring

Track per-table freshness (last commit time), row-count deltas, file counts and average file size, query latency percentiles by workload, queueing time in warehouses, and spend per team. These are the Micrometer-dashboard equivalents for the analytical tier.

14. Exercises

Exercise 1 · Foundational

Using fact_trip in DuckDB, compute for each day the number of trips, the 7-day moving average, and the percentage change versus the same weekday one week earlier. Which days of January 2024 show the largest week-over-week drop, and what plausible non-data explanation exists?

Solution

Use query 7.2(b) and order by wow_pct ascending. Expect drops around holidays (New Year's Day; Martin Luther King Jr. Day on January 15, 2024) and around severe weather. Before concluding, check that the pipeline loaded all hours for those days (a data issue would show as missing hours).

Exercise 2 · Intermediate

Write one query that returns revenue by (borough, day-of-week), subtotals per borough, subtotals per day-of-week across boroughs, and a grand total, with readable labels for subtotal rows. Then explain why CUBE would be equivalent here.

Solution
SELECT CASE WHEN GROUPING(z.borough)=1 THEN 'ALL' ELSE z.borough END AS borough,
       CASE WHEN GROUPING(dayname(f.pickup_date))=1 THEN 'ALL' ELSE dayname(f.pickup_date) END AS dow,
       SUM(f.total_amount) AS revenue
FROM fact_trip f JOIN dim_zone z ON z.zone_key = f.pickup_zone_key
GROUP BY CUBE (z.borough, dayname(f.pickup_date))
ORDER BY 1, 2;

CUBE(a, b) expands to GROUPING SETS ((a,b), (a), (b), ()), exactly the four levels requested. ROLLUP(a, b) would omit the (b) level. GROUPING() distinguishes subtotal placeholders from genuine null boroughs (the TLC lookup has "Unknown" and null-like zones).

Exercise 3 · Intermediate

Write the trips Parquet file twice, once sorted by pickup_ts and once by pickup_zone_key. For the queries "one day of trips" and "all trips from zone 132 (JFK)", count surviving row groups for each layout. What layout would you choose if both queries are equally common?

Solution

Each layout prunes well for its own sort column and poorly for the other. Options: partition by day and sort within each file by zone (day pruning via partitions, zone pruning via in-file sort; good for both); Z-order on both columns; or keep two copies if both are latency-critical. With Iceberg: PARTITIONED BY (day(pickup_ts)) plus WRITE ORDERED BY pu_location_id.

Exercise 4 · Advanced

Design the SCD Type 2 dim_merchant pipeline for a source Postgres table updated in place. Specify the change-detection method, the MERGE, how fact rows get the right surrogate key, and how a late-arriving fact (an order from 3 days ago arriving today) is handled.

Solution

Change detection: CDC from Postgres gives every update with its commit timestamp; alternatively, daily snapshot comparison with a row hash. Use the source commit time, not load time, as valid_from, so history reflects reality. MERGE: Section 7.7. Fact keys: look up the dimension version where valid_from <= order_ts < valid_to during fact loading, which handles late-arriving facts naturally because the range join uses the order's own timestamp. If a fact arrives before its dimension row exists (an early-arriving fact), insert an "inferred member" placeholder row and update it in place (Type 1 for that row) when the real attributes arrive.

Exercise 5 · Advanced

A streaming job appends to an Iceberg table every 30 seconds into hourly partitions. After a month, queries over one day take 40 seconds, mostly in planning. Diagnose using metadata tables and propose a maintenance plan.

Solution

Query table.files for file count and average size per partition (expect thousands of tiny files per day), table.manifests for manifest count, and table.snapshots (tens of thousands of snapshots). Plan: run rewrite_data_files hourly on the previous hour's partition (binpack to ~512 MB, optionally sort), rewrite_manifests daily, expire_snapshots keeping 2–7 days for time travel, remove_orphan_files weekly. Increase the streaming commit interval if freshness allows (2–5 minutes). Verify by measuring planning time and files scanned before and after.

15. Interview Questions

Conceptual Why is columnar storage faster for analytics, and when is it slower?

It reads only referenced columns, compresses far better because each column is homogeneous, enables vectorized SIMD execution, and supports statistics-based pruning. It is slower for point lookups and single-row updates: reconstructing a row touches every column file, and updating a value means rewriting compressed, immutable files.

Conceptual What is the difference between RANK, DENSE_RANK and ROW_NUMBER?

For values 100, 90, 90, 80: ROW_NUMBER gives 1,2,3,4 (arbitrary among ties unless ordered further); RANK gives 1,2,2,4 (gaps after ties); DENSE_RANK gives 1,2,2,3 (no gaps). Use ROW_NUMBER for deduplication, DENSE_RANK for "top N distinct values".

Architecture How do Iceberg tables achieve ACID transactions on S3, which has no multi-object transactions?

Data and metadata files are immutable and written first. The only mutable state is the catalog pointer to the current metadata file, updated by an atomic compare-and-swap. Readers resolve a snapshot and see a consistent set of files; writers commit optimistically and retry metadata on conflict. Isolation is snapshot isolation by default, with serializable available for some operations.

Architecture Explain separation of storage and compute and why it matters.

Storage lives in durable object storage; compute clusters are stateless (with caches) and can be created, resized and shut down independently. Benefits: pay for compute only when used, isolate workloads with separate clusters on the same data, scale storage without moving data, and restart compute without data loss. Costs: remote reads (mitigated by caching and pruning) and a metadata service that becomes critical.

Coding Deduplicate a CDC table keeping the latest row per key, but drop keys whose latest operation is a delete.
SELECT * EXCLUDE (rn)
FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY order_id ORDER BY lsn DESC) AS rn
  FROM orders_cdc
)
WHERE rn = 1 AND op <> 'd';

Order by the log sequence number (or commit LSN plus event position), not a wall-clock timestamp, since multiple changes can share a timestamp.

Scenario Finance says last quarter's revenue by region changed since they last ran the report. What could cause it?

Late-arriving facts loaded after the first run; SCD Type 1 overwrites moving merchants between regions; a backfill or bug fix reprocessing old partitions; currency rates restated; deduplication logic changed. Fixes: SCD2 for region; snapshot or time-travel the reported dataset and record the snapshot id with the report; document restatement policy.

Conceptual Kimball versus Inmon versus Data Vault?

Kimball: bottom-up, business-process star schemas with conformed dimensions, optimized for querying. Inmon: top-down normalized enterprise warehouse feeding marts, optimized for integration. Data Vault: hubs/links/satellites, insert-only, optimized for auditability and absorbing source change, with marts on top. Modern practice often uses a light layered approach with Kimball-style marts.

Scenario A BigQuery bill doubled this month. How do you investigate and prevent recurrence?

Query INFORMATION_SCHEMA.JOBS for bytes billed by user, project and query hash; find the top offenders (often a dashboard refreshing a SELECT * on an unpartitioned table, or a scheduled query without partition filters). Fix with partitioning and clustering, require_partition_filter, materialized aggregates for dashboards, per-user quotas, and possibly moving predictable workloads to reserved slots.

Conceptual When would you use merge-on-read rather than copy-on-write?

When updates are frequent and small relative to file size (CDC applied every few minutes): MoR writes compact delete markers or log files instead of rewriting large files, then compaction amortizes the rewrite. Reads pay a merge cost until compaction, so it suits write-heavy tables with tolerant readers.

16. Knowledge Check

  • OLAP workloads scan and aggregate; columnar storage, compression, vectorization and pruning make them fast.
  • Window functions, CTEs, GROUPING SETS and approximate aggregates are the core analytical SQL toolkit; know frames and QUALIFY.
  • Parquet = row groups of column chunks of pages, with footer statistics enabling pushdown; sort order determines pruning effectiveness.
  • Snowflake, BigQuery and Redshift all separate storage from compute in different ways; cost follows compute time or bytes scanned.
  • Dimensional models: declare the grain, keep measures additive, use conformed dimensions and SCD Type 2 where history matters.
  • Iceberg, Delta and Hudi add snapshots, atomic commits, time travel and schema evolution to files on object storage; they need maintenance.
  • DuckDB brings the same columnar engine ideas to a single process: ideal for dev, CI and medium data.

A Parquet file's row groups each span the full date range of the data. What does that imply for a one-day filter?

  1. Bloom filters will compensate
  2. Min/max statistics cannot prune any row group, so all must be read
  3. Dictionary encoding makes the filter free
  4. Projection pushdown will skip the irrelevant rows
Statistics pruning only skips a row group if the filter range lies outside its min/max. Unsorted data gives every row group a wide range. Bloom filters help equality predicates, not ranges; projection pushdown skips columns, not rows.

In Iceberg, what is the single mutable piece of state changed by a commit?

  1. The newest manifest file
  2. The data files of the affected partition
  3. The catalog's pointer to the current metadata file
  4. A lock file in the table directory
Everything else is written as new immutable files; the commit is an atomic swap of the catalog pointer from the old metadata file to the new one.

Sales must be reported by the customer's region at the time of sale, even after customers move. Which SCD type?

  1. Type 2
  2. Type 1
  3. Type 0
  4. Type 3
Type 2 keeps a new row per version with validity ranges, so facts join to the version valid at event time. Type 1 overwrites history; Type 3 keeps only one previous value.

Which query pattern forces all rows onto a single worker in a distributed engine?

  1. SUM(x) OVER (PARTITION BY customer_id)
  2. GROUP BY GROUPING SETS ((a), (b))
  3. APPROX_COUNT_DISTINCT(user_id)
  4. ROW_NUMBER() OVER (ORDER BY event_ts) with no PARTITION BY
A global ordering without partitions requires a single sorted sequence. Partitioned windows, grouping sets and mergeable sketches all parallelize.

Approximately how large an HLL sketch gives about 0.8% relative error?

  1. Proportional to the number of distinct values
  2. About 16K registers, roughly 12 KB, independent of cardinality
  3. 1 bit per input row
  4. It cannot be bounded
Relative error ≈ 1.04/√m; m = 214 gives ≈ 0.81%, with 6-bit registers totalling about 12 KB, regardless of how many distinct values exist.

Which property best distinguishes merge-on-read from copy-on-write tables?

  1. MoR tables cannot be time-travelled
  2. CoW tables only support appends
  3. MoR records changes separately and reconciles at read time until compaction; CoW rewrites affected files at write time
  4. MoR stores data row-wise only
The trade is where the merge cost is paid: on write (CoW) or on read plus compaction (MoR).
