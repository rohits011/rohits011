AWS Fundamentals, Cloud Networking & Serverless

The Lumen platform now has images, manifests, pipelines and Terraform; it needs a home. This chapter covers the AWS building blocks a backend engineer must reason about — identity, compute, storage, databases, messaging — then designs the network that connects them (VPCs, subnets, routing, NAT, security groups, endpoints, load balancers, DNS and CDN), and finally shows when to drop servers entirely and run event-driven code on Lambda, including how to make Java start fast enough to be serverless.

1. Introduction: The Cloud as an API for Infrastructure

On-premises, getting a server meant a purchase order; on AWS it is an API call that returns in seconds. That shift is why Infrastructure as Code (Chapter 3) works at all. But the cloud is not "someone else's computer" in a simple sense: it is a set of managed services with explicit failure domains (Regions and Availability Zones), a global identity system (IAM) that gates every API call, a software-defined network (VPC) with its own routing and firewall semantics, and a pricing model in which architecture decisions — especially data transfer and NAT — show up directly on the bill.

This chapter is about AWS because it is the most common target for Spring Boot teams and the platform Lumen runs on, but the concepts — regions and zones, identity-based access, private networks with NAT and private endpoints, L4/L7 load balancers, functions-as-a-service — exist in Google Cloud and Azure under different names.

Bridging from Java & Spring Boot

What you already know
Spring Cloud AWS or the AWS SDK for Java v2 to call S3 and SQS; @SqsListener; datasource URLs pointing at RDS; maybe credentials in application.yaml or environment variables; a load balancer someone else configured in front of your service.
Why that is not enough
Static access keys leak; "the network team" cannot debug your security-group-induced timeouts for you; an un-designed VPC runs out of IP addresses as soon as EKS assigns one per pod; a Spring Boot fat JAR on Lambda can take seconds to cold start; and a single NAT gateway can quietly become your largest line item.
The modern approach
Workload identity (EKS Pod Identity, IAM roles for Lambda/ECS tasks) with least-privilege policies; a VPC designed for growth with private subnets per AZ, gateway and interface endpoints for AWS APIs; managed data services (RDS/Aurora, DynamoDB, SQS) instead of self-hosting; L7 ALB or L4 NLB chosen deliberately; and serverless for spiky, event-driven work with SnapStart or native images to fix JVM cold starts.
Where Python and Go fit
Python and Go cold-start fast on Lambda and dominate glue functions; boto3 and the Go SDK v2 are the usual clients. The Go gateway in Lumen benefits from NLB's static IPs and connection-level balancing; Python AI services call model APIs over interface endpoints (e.g., Amazon Bedrock) or through NAT.
In production
Most AWS incidents a backend team causes are networking (security group or route missing, NAT exhaustion, DNS), identity (AccessDenied after a policy change), quotas (throttling, ENI/IP limits) or cost surprises (cross-AZ and NAT data). Regional service events are rarer but real — design for AZ failure always, region failure when the business needs it.
Use it when / avoid it when
Use managed services by default; they remove undifferentiated operational work. Avoid serverless for steady, high-throughput, latency-critical workloads where containers are cheaper and more predictable, and avoid multi-region active-active unless the business case justifies its complexity.

2. History

Amazon Web Services launched its first broadly available infrastructure service, Amazon S3, in March 2006, followed by SQS (2006) and EC2 (beta August 2006). Early EC2 instances lived on a flat shared network ("EC2-Classic"); Amazon VPC arrived in 2009 and became the default for new accounts from 2013, bringing private address spaces, subnets and routing under customer control. RDS launched in 2009, IAM in 2010–2011, DynamoDB in 2012 (based on lessons from the 2007 Dynamo paper), and Aurora in 2014–2015.

AWS Lambda was announced at re:Invent in November 2014 and started the "serverless" era; API Gateway (2015), Step Functions (2016), EventBridge (2019, evolved from CloudWatch Events) and Fargate (2017) completed the picture. Containers on AWS came via ECS (2014–2015) and EKS (GA June 2018). Networking evolved with PrivateLink (2017), Transit Gateway (2018) and VPC Lattice (GA 2023). In December 2020 S3 became strongly consistent for all operations and Lambda moved to 1 ms billing granularity and container image packaging. Lambda SnapStart for Java was launched at re:Invent 2022 and extended to Python and .NET in November 2024 and to container image functions in 2026; EKS Auto Mode, which runs Karpenter-based node management, storage and load balancing as a managed capability, was announced in December 2024 Version-sensitive · checked Nov 2026. In 2025 AWS raised the maximum SQS message size and Lambda asynchronous payload size from 256 KB to 1 MiB/1 MB.

The history of outages matters as much as the history of launches: major us-east-1 events in 2011 (EBS), 2017 (S3 in us-east-1, triggered by a mistyped command), December 2021 (internal network congestion) and October 2025 (a DNS race condition in DynamoDB's automation) shaped how both AWS and its customers think about blast radius — see §9.
