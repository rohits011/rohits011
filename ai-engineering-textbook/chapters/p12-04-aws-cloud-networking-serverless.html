AWS Fundamentals, Cloud Networking & Serverless

The Lumen platform now has images, manifests, pipelines and Terraform; it needs a home. This chapter covers the AWS building blocks a backend engineer must reason about — identity, compute, storage, databases, messaging — then designs the network that connects them (VPCs, subnets, routing, NAT, security groups, endpoints, load balancers, DNS and CDN), and finally shows when to drop servers entirely and run event-driven code on Lambda, including how to make Java start fast enough to be serverless.

  • You will be able to: design a three-AZ VPC for EKS and RDS; trace a packet from the internet to a pod and from a pod to S3; write least-privilege IAM; choose between EC2, ECS, EKS and Lambda, and between RDS, Aurora and DynamoDB; build an SQS-triggered Lambda in Java with SnapStart; and estimate the cost of NAT, data transfer and serverless.

1. Introduction: The Cloud as an API for Infrastructure

On-premises, getting a server meant a purchase order; on AWS it is an API call that returns in seconds. That shift is why Infrastructure as Code (Chapter 3) works at all. But the cloud is not "someone else's computer" in a simple sense: it is a set of managed services with explicit failure domains (Regions and Availability Zones), a global identity system (IAM) that gates every API call, a software-defined network (VPC) with its own routing and firewall semantics, and a pricing model in which architecture decisions — especially data transfer and NAT — show up directly on the bill.

This chapter is about AWS because it is the most common target for Spring Boot teams and the platform Lumen runs on, but the concepts — regions and zones, identity-based access, private networks with NAT and private endpoints, L4/L7 load balancers, functions-as-a-service — exist in Google Cloud and Azure under different names.

Bridging from Java & Spring Boot

What you already know
Spring Cloud AWS or the AWS SDK for Java v2 to call S3 and SQS; @SqsListener; datasource URLs pointing at RDS; maybe credentials in application.yaml or environment variables; a load balancer someone else configured in front of your service.
Why that is not enough
Static access keys leak; "the network team" cannot debug your security-group-induced timeouts for you; an un-designed VPC runs out of IP addresses as soon as EKS assigns one per pod; a Spring Boot fat JAR on Lambda can take seconds to cold start; and a single NAT gateway can quietly become your largest line item.
The modern approach
Workload identity (EKS Pod Identity, IAM roles for Lambda/ECS tasks) with least-privilege policies; a VPC designed for growth with private subnets per AZ, gateway and interface endpoints for AWS APIs; managed data services (RDS/Aurora, DynamoDB, SQS) instead of self-hosting; L7 ALB or L4 NLB chosen deliberately; and serverless for spiky, event-driven work with SnapStart or native images to fix JVM cold starts.
Where Python and Go fit
Python and Go cold-start fast on Lambda and dominate glue functions; boto3 and the Go SDK v2 are the usual clients. The Go gateway in Lumen benefits from NLB's static IPs and connection-level balancing; Python AI services call model APIs over interface endpoints (e.g., Amazon Bedrock) or through NAT.
In production
Most AWS incidents a backend team causes are networking (security group or route missing, NAT exhaustion, DNS), identity (AccessDenied after a policy change), quotas (throttling, ENI/IP limits) or cost surprises (cross-AZ and NAT data). Regional service events are rarer but real — design for AZ failure always, region failure when the business needs it.
Use it when / avoid it when
Use managed services by default; they remove undifferentiated operational work. Avoid serverless for steady, high-throughput, latency-critical workloads where containers are cheaper and more predictable, and avoid multi-region active-active unless the business case justifies its complexity.

2. History

Amazon Web Services launched its first broadly available infrastructure service, Amazon S3, in March 2006, followed by SQS (2006) and EC2 (beta August 2006). Early EC2 instances lived on a flat shared network ("EC2-Classic"); Amazon VPC arrived in 2009 and became the default for new accounts from 2013, bringing private address spaces, subnets and routing under customer control. RDS launched in 2009, IAM in 2010–2011, DynamoDB in 2012 (based on lessons from the 2007 Dynamo paper), and Aurora in 2014–2015.

AWS Lambda was announced at re:Invent in November 2014 and started the "serverless" era; API Gateway (2015), Step Functions (2016), EventBridge (2019, evolved from CloudWatch Events) and Fargate (2017) completed the picture. Containers on AWS came via ECS (2014–2015) and EKS (GA June 2018). Networking evolved with PrivateLink (2017), Transit Gateway (2018) and VPC Lattice (GA 2023). In December 2020 S3 became strongly consistent for all operations and Lambda moved to 1 ms billing granularity and container image packaging. Lambda SnapStart for Java was launched at re:Invent 2022 and extended to Python and .NET in November 2024 and to container image functions in 2026; EKS Auto Mode, which runs Karpenter-based node management, storage and load balancing as a managed capability, was announced in December 2024 Version-sensitive · checked Nov 2026. In 2025 AWS raised the maximum SQS message size and Lambda asynchronous payload size from 256 KB to 1 MiB/1 MB.

The history of outages matters as much as the history of launches: major us-east-1 events in 2011 (EBS), 2017 (S3 in us-east-1, triggered by a mistyped command), December 2021 (internal network congestion) and October 2025 (a DNS race condition in DynamoDB's automation) shaped how both AWS and its customers think about blast radius — see §9.

3. Fundamentals

3.1 Regions, Availability Zones and edge locations

A Region (e.g., eu-west-1, Ireland) is a separate geographic area with its own control planes for most services; Regions are isolated from each other by design, and data does not leave a Region unless you move it. Each Region has multiple Availability Zones (typically three or more): one or more discrete data centres with independent power, cooling and networking, connected by low-latency links (single-digit milliseconds or less). AZ names like eu-west-1a are mapped per account; the stable identifier is the AZ ID (euw1-az1). Edge locations host CloudFront and Route 53 close to users. The design rule: every production workload survives the loss of one AZ; surviving the loss of a Region is a business decision with real cost.

3.2 IAM: every API call is authorised

Identity and Access Management decides whether a principal (an IAM user, a role session, an AWS service) may perform an action (s3:GetObject) on a resource (arn:aws:s3:::lumen-docs/*) under conditions (source VPC endpoint, tags, MFA). Key concepts:

  • Roles are identities without long-term credentials; they are assumed via STS to obtain temporary credentials. EC2 instance profiles, ECS task roles, Lambda execution roles, EKS Pod Identity and GitHub OIDC (Chapter 3) are all role assumption.
  • Policies: identity-based (attached to a role), resource-based (bucket policies, SQS queue policies, KMS key policies), permission boundaries, session policies, and organisation-level Service Control Policies and resource control policies that cap what any principal in an account can do.
  • Evaluation: an explicit Deny anywhere wins; otherwise access requires an Allow (and for cross-account access, allows on both sides); everything else is implicitly denied.
  • Least privilege: scope actions and resources tightly; use IAM Access Analyzer to generate policies from CloudTrail activity and to find unintended external access.

Java angle: the default credentials provider chain

The AWS SDK for Java v2 resolves credentials through a chain: system properties, environment variables, web identity token file (used by IRSA), the shared credentials file, the container credentials endpoint (used by ECS task roles and EKS Pod Identity), and the EC2 instance metadata service. In production you should configure nothing in code: the platform injects a role, and the chain finds it. If you see AWS_ACCESS_KEY_ID in a Deployment manifest, that is a finding.

3.3 Compute: EC2, containers and functions

EC2 instances are virtual machines on the Nitro hypervisor, chosen by family (general purpose m, compute c, memory r, GPU g/p, ARM-based Graviton variants suffixed g), size and purchase option (On-Demand, Savings Plans/Reserved, Spot at steep discounts with two-minute interruption notices). Auto Scaling groups keep a fleet at the desired size across AZs. ECS is AWS's own container orchestrator (tasks and services, simpler than Kubernetes, deeply integrated with IAM and ALB); EKS is managed Kubernetes; both run containers on EC2 or on Fargate (serverless per-task VMs). Lambda runs functions in response to events with per-millisecond billing.

3.4 Storage: S3, EBS and EFS

S3 is object storage: buckets of objects addressed by key, eleven nines of designed durability, strong read-after-write consistency, storage classes from Standard to Glacier Deep Archive, lifecycle rules, versioning, object lock, event notifications and presigned URLs. It is the backbone for data lakes, backups, Terraform state and — for Lumen — the source documents that assist-service indexes. EBS volumes are block devices attached to one instance in one AZ (the reason a StatefulSet Pod with an EBS volume cannot move to another AZ). EFS is a regional NFS file system mountable by many instances across AZs.

3.5 Databases: RDS, Aurora and DynamoDB

RDS runs PostgreSQL, MySQL, MariaDB, Oracle, SQL Server and Db2 with automated backups, patching and Multi-AZ deployments (a synchronous standby in another AZ, automatic failover by DNS flip typically within one to two minutes). Aurora (PostgreSQL- and MySQL-compatible) separates compute from a distributed storage layer that keeps six copies across three AZs; replicas share storage, so failover is faster and read replicas lag less; Aurora Serverless v2 scales capacity in fine increments. DynamoDB is a serverless key-value and document store with single-digit-millisecond latency at any scale, partitioned by key, priced per request or provisioned capacity, with Streams for change data capture and global tables for multi-region replication. Choose relational for rich queries and transactions (Lumen's orders), DynamoDB for known access patterns at very high scale (session state, idempotency keys, rate-limit counters).

3.7 The VPC

A Virtual Private Cloud is a logically isolated network in one Region with a primary IPv4 CIDR (from /16 to /28; secondary CIDRs can be added) and optionally IPv6. A subnet lives in exactly one AZ and has a CIDR carved from the VPC's. Subnets are not "public" or "private" by any flag — the difference is entirely their route table: a public subnet's route table sends 0.0.0.0/0 to an Internet Gateway (IGW); a private subnet's sends it to a NAT gateway (or nowhere). Every route table also has an implicit local route for the VPC CIDR, so all subnets in a VPC can reach each other unless security groups or NACLs block it.

3.8 Internet Gateway and NAT gateway

The IGW performs 1:1 translation between an instance's private IP and its public or Elastic IP, enabling both inbound and outbound internet traffic for resources that have public IPs. A NAT gateway sits in a public subnet with an Elastic IP and lets resources in private subnets initiate outbound connections (to pull images, call LLM APIs, reach SaaS) while remaining unreachable from the internet — SNAT, exactly as in Chapter 1 §3.16. NAT gateways are zonal: deploy one per AZ and route each private subnet to its own AZ's NAT, or an AZ failure takes down egress everywhere. NAT options evolve, so check the current VPC documentation for newer deployment modes Version-sensitive · checked Nov 2026. NAT gateways charge per hour and per GB processed — often a surprise cost.

3.10 VPC endpoints and PrivateLink

Without endpoints, a pod in a private subnet reaches S3 or ECR through the NAT gateway — paying NAT processing for every byte and depending on internet egress. Gateway endpoints (S3 and DynamoDB only, free) add routes in your route tables to the service's prefix list. Interface endpoints (AWS PrivateLink) place an ENI with a private IP in your subnets for a service (ECR API and DKR, STS, Secrets Manager, SQS, CloudWatch Logs, Bedrock Runtime, and thousands of partner/SaaS services), with private DNS so the normal hostname resolves to the private IP. They cost per hour per AZ plus per GB, but remove NAT dependency and let you restrict access with endpoint policies and aws:SourceVpce conditions. PrivateLink also lets you expose your own service (behind an NLB) to other VPCs and accounts without peering.

3.11 Connecting VPCs: peering, Transit Gateway and VPC Lattice

VPC peering is a non-transitive one-to-one link (no overlapping CIDRs); fine for a few VPCs, unmanageable at dozens. Transit Gateway is a regional hub router: VPCs, VPNs and Direct Connect attach to it, with route tables controlling who reaches whom, inter-region peering, and per-attachment and per-GB charges. VPC Lattice is an application-layer service network: you register services (EKS, ECS, EC2, Lambda) and Lattice handles service discovery, L7 routing, authentication with IAM policies and cross-VPC/cross-account connectivity, even with overlapping CIDRs — a managed alternative to parts of a service mesh.

3.12 Route 53

Route 53 is AWS's DNS service: public and private hosted zones (private zones resolve only inside associated VPCs), the ALIAS record that points apex domains at AWS resources (ALB, CloudFront, S3 website) without a CNAME, routing policies (simple, weighted for canaries, latency-based, geolocation, failover with health checks, multivalue), and Route 53 Resolver for hybrid DNS (inbound/outbound endpoints, forwarding rules) and DNS Firewall. The VPC's built-in resolver lives at the VPC CIDR base + 2.

3.14 CloudFront

CloudFront is AWS's CDN: hundreds of edge locations terminate TLS (and HTTP/3) close to users, cache static and cacheable dynamic content, and forward misses to origins (S3 with Origin Access Control, ALBs, custom origins) over AWS's backbone. It integrates with AWS WAF and Shield for DDoS protection, and CloudFront Functions/Lambda@Edge run small pieces of code at the edge (header rewrites, auth checks). For Lumen, CloudFront serves the web app from S3 and fronts the API ALB for TLS and DDoS protection.

3.15 Serverless and the Lambda execution model

A Lambda function is code plus configuration (runtime, memory 128 MB–10,240 MB, timeout up to 900 s, ephemeral /tmp up to 10 GB, environment variables, VPC attachment, execution role) Version-sensitive · checked Nov 2026. CPU is allocated proportionally to memory (about one vCPU at 1,769 MB, up to six vCPUs at the maximum). Lambda runs each function instance in a Firecracker microVM execution environment. Each environment processes one invocation at a time; concurrency is achieved by running many environments in parallel. The lifecycle has three phases:

  1. Init — download code, start the runtime, run static initialisers and the handler class constructor (for Java: JVM start, class loading, Spring context if you use one). This is the cold start.
  2. Invoke — run the handler for one event. The environment is then frozen and kept warm for reuse; subsequent invocations skip Init.
  3. Shutdown — environments are reclaimed after an idle period or for maintenance.

Invocation types: synchronous (API Gateway, function URLs, SDK RequestResponse; caller waits; payload up to 6 MB), asynchronous (S3, SNS, EventBridge; Lambda queues the event and retries twice by default, with destinations or DLQs for failures; payload up to 1 MB since late 2025), and event source mappings (Lambda polls SQS, Kinesis, DynamoDB Streams, Kafka and invokes with batches) Version-sensitive · checked Nov 2026. Concurrency is governed by an account-level regional limit and per-function reserved concurrency; provisioned concurrency keeps environments pre-initialised.

3.16 Cold starts, SnapStart and native images

A plain Java 21 function with a few SDK clients typically cold-starts in roughly 1–3 seconds, and a full Spring Boot application longer, while Go and Python functions usually start in tens to a few hundred milliseconds Illustrative. Remedies for Java:

  • SnapStart (Java 11+, also Python 3.12+ and .NET 8+): when you publish a version, Lambda runs Init once, takes a Firecracker snapshot of the initialised memory and disk, caches it, and resumes new environments from the snapshot. Cold starts drop dramatically. Caveats: code that assumes uniqueness after init (random seeds, generated IDs, cached credentials, open network connections) must re-initialise using CRaC runtime hooks (beforeCheckpoint/afterRestore); SnapStart applies to published versions/aliases, and does not combine with provisioned concurrency or EFS.
  • GraalVM native image (via Spring Boot AOT or Quarkus/Micronaut): compile ahead of time to a native executable on a custom runtime (provided.al2023); starts in tens of milliseconds with lower memory, at the cost of build complexity and reflection configuration.
  • Lean handlers: avoid a full Spring context; use the SDK's lightweight HTTP client (UrlConnectionHttpClient or AWS CRT), initialise clients once in static fields, and tune -XX:TieredStopAtLevel=1 (via JAVA_TOOL_OPTIONS) for short-lived work.
  • Provisioned concurrency: pay to keep N environments warm; predictable but costs money even when idle.

3.17 Step Functions and event-driven serverless design

Step Functions orchestrates workflows as state machines defined in Amazon States Language: tasks (Lambda, ECS, 200+ direct SDK integrations), choices, parallel and map states, retries with backoff, catch blocks, and wait states up to a year (Standard workflows, exactly-once, auditable history) or high-volume short workflows (Express, at-least-once). It is the serverless implementation of the saga pattern (Part 2). Event-driven serverless design composes small functions through queues and events: producers emit facts ("OrderPlaced") to EventBridge or SNS; consumers subscribe via SQS queues (which buffer, retry and dead-letter); functions are idempotent and stateless; state lives in DynamoDB/S3; orchestration that needs visibility uses Step Functions.

3.18 When not to use serverless

  • Steady, high-throughput traffic (e.g., hundreds of requests per second around the clock): containers on reserved/Spot capacity are usually cheaper.
  • Strict low-latency p99 requirements where any cold start is unacceptable and provisioned concurrency is not cost-effective.
  • Long-running work beyond 15 minutes, or large in-memory state, GPUs, or persistent connections (WebSocket servers, database connection-heavy workloads without RDS Proxy).
  • Heavy frameworks you cannot slim, or when portability requirements rule out provider-specific event models.

4. Internal Working

4.1 A request from a user to an orders Pod

  1. DNS. The client resolves api.lumen.example.com. Route 53 holds an ALIAS record pointing at the CloudFront distribution, which returns IPs of a nearby edge location.
  2. Edge. CloudFront terminates TLS (HTTP/3 or HTTP/2), applies AWS WAF rules, and forwards the request (not cacheable: POST) to its origin — the public ALB — over AWS's network, adding a secret header that the ALB checks so it cannot be bypassed.
  3. ALB. The ALB's nodes live in the public subnets of three AZs. It terminates TLS again (ACM certificate), evaluates listener rules (/api/* → target group edge-gateway), picks a healthy target with its algorithm (round robin or least outstanding requests) and opens or reuses a connection to the target's pod IP.
  4. VPC fabric. With the VPC CNI, pod IPs are secondary IPs (or prefixes) on node ENIs in private subnets, so the ALB's packet is routed by the VPC's local route straight to the node; the security group attached to the node (or to the pod, with security groups for pods) must allow the ALB's security group on the target port.
  5. In-cluster. The Go gateway authenticates, then calls orders through the Kubernetes Service (Chapter 2 §4.2).
  6. Database. orders-service connects to the RDS endpoint DNS name, which resolves (via the VPC resolver) to the primary instance's private IP in a data subnet; the RDS security group allows 5432 only from the EKS pod/node security group.

4.2 A request from a Pod to AWS APIs and the internet

When assist-service reads a document from S3, the SDK resolves s3.eu-west-1.amazonaws.com to public S3 IPs. The private subnet's route table contains a route for the S3 prefix list pointing at the gateway endpoint, which is more specific than 0.0.0.0/0, so the traffic goes to S3 privately without touching the NAT gateway. When it calls Secrets Manager or Bedrock Runtime, private DNS on the interface endpoint makes the regular hostname resolve to the endpoint ENI's private IP in the same AZ. When it calls an external LLM API, the packet matches 0.0.0.0/0 → nat-xxxx in its AZ; the NAT gateway rewrites the source to its Elastic IP and forwards through the IGW. Each of these paths has different cost, failure modes and security controls — the reason to know which one your traffic takes.

4.3 How credentials reach a Pod (EKS Pod Identity)

You create an association between a Kubernetes ServiceAccount (lumen/orders) and an IAM role. The EKS Pod Identity Agent runs as a DaemonSet on each node. When a Pod using that ServiceAccount starts, EKS injects environment variables (AWS_CONTAINER_CREDENTIALS_FULL_URI and an authorisation token file) into its containers. The SDK's container credentials provider calls the agent on a link-local address; the agent exchanges the Pod's projected service account token with the EKS Auth API for temporary role credentials, which the SDK caches and refreshes. No keys are stored anywhere, and the role's trust policy is managed by EKS rather than per-cluster OIDC providers (the older IRSA mechanism, still widely used, works similarly with a web identity token and an IAM OIDC provider per cluster).

4.4 Lambda invocation internals

For an SQS event source mapping, Lambda's pollers long-poll the queue, accumulate a batch (up to the batch size or batching window), and invoke the function synchronously. The Lambda frontend authorises the call and routes it to the placement service, which finds a warm execution environment for that function version or creates one on a worker host: a Firecracker microVM is started (or restored from a SnapStart snapshot), the runtime and code are loaded, Init runs, then Invoke. The runtime fetches events from the Runtime API (/runtime/invocation/next) and posts results. If the function returns partial batch failures (batchItemFailures), only those messages become visible again after the visibility timeout; on full failure the whole batch returns to the queue; after maxReceiveCount attempts SQS moves messages to the dead-letter queue. The poller scales concurrency up as the queue backs up, bounded by the function's maximum concurrency setting.

4.5 How an RDS Multi-AZ failover works

RDS keeps a synchronous standby in another AZ (or, in Multi-AZ DB clusters, two readable standbys). If the primary's host, storage or AZ fails — or during patching — RDS promotes the standby and updates the endpoint's DNS record to the new primary's IP. Clients see connection errors until they reconnect and re-resolve DNS. That is why the JVM's DNS cache TTL (Chapter 1 §3.11) and HikariCP's validation and max-lifetime settings matter, and why the AWS Advanced JDBC Wrapper (which tracks cluster topology for faster failover) or RDS Proxy (which holds client connections across failover) are worth considering.

5. Architecture Diagrams

5.1 Lumen VPC layout

Reading the diagram: public subnets hold only things that must face the internet — ALB nodes and NAT gateways — and are small (/24). Private subnets are large (/19, 8,187 usable addresses each) because the VPC CNI gives every pod a VPC IP. Data subnets have no route to the internet at all; RDS is reachable only from inside the VPC. Each private subnet's default route goes to the NAT gateway in its own AZ, so losing AZ a does not break egress in AZ b. Endpoint traffic to S3, ECR and other AWS APIs bypasses NAT entirely. This is the network that the Terraform module in Chapter 3 §7.7 creates.

5.2 Packet path through security controls

Reading the diagram: no rule mentions an IP address except the CloudFront managed prefix list on the ALB. The pods accept traffic only from the ALB's security group, and the database only from the pods' security group. Because security groups are stateful, responses need no rules. If any arrow fails, the symptom is a timeout (packets silently dropped), not a refusal — the clue that points at security groups rather than at the application.

5.3 Event-driven serverless flow

Reading the diagram: the orders service knows nothing about notifications, fraud review or embedding — it emits facts. EventBridge rules route by content; SQS queues buffer each consumer independently so a slow consumer does not affect others, and dead-letter queues capture poison messages. Short, spiky work (sending emails) is a natural Lambda; heavy GPU-backed embedding runs as KEDA-scaled pods; multi-step processes with waiting and human approval run in Step Functions. Choosing the compute per consumer is the essence of pragmatic serverless.

5.4 Lambda execution environment lifecycle

Reading the diagram: everything in Init is paid once per environment, so put expensive setup (SDK clients, connection pools sized to 1, configuration loading) there, not in the handler. With SnapStart, Init happens at publish time and new environments take the Restore path; any state that must be unique per environment (random seeds, network connections, credentials) must be refreshed in afterRestore. Because each environment handles one request at a time, concurrency equals the number of environments, and each environment with a database connection is one more connection on your database — hence RDS Proxy.

6. The Numbers: IP Planning, Availability and Cost

6.1 IP address planning for EKS

With the VPC CNI each pod consumes a VPC IP, and nodes pre-allocate warm IPs or /28 prefixes. If Lumen expects up to 60 nodes per AZ running ~40 pods each, it needs roughly \(60 \times 40 = 2{,}400\) pod IPs per AZ plus node IPs and warm pools — comfortably inside a /19 (8,187 usable) but not a /22 (1,019). Running out of subnet IPs shows up as pods stuck in ContainerCreating with CNI errors. Mitigations: larger subnets, secondary CIDRs (e.g., 100.64.0.0/16 for pods with custom networking), prefix delegation, or IPv6 clusters.

6.2 Availability arithmetic

Intuition: independent redundant components multiply their unavailability; components in series multiply their availability. If one AZ-local deployment of a service is available 99.5% of the time and AZ failures are independent, a three-AZ deployment that survives any single-AZ loss has unavailability roughly \(\binom{3}{2}(0.005)^2 \approx 7.5 \times 10^{-5}\) — about 99.99% — before accounting for correlated failures and regional dependencies (which dominate in reality). In series, a request path of CloudFront (99.99%) × ALB (99.99%) × app (99.95%) × RDS Multi-AZ (99.95%) yields about \(0.9999^2 \times 0.9995^2 \approx 99.88\%\) Illustrative. Your SLO cannot exceed the product of your hard dependencies (Chapter 6).

6.3 NAT and data transfer cost

Data transfer pricing is a first-order architecture input. As a rough guide to public list prices in large US/EU Regions: a NAT gateway charges about \$0.045 per hour plus about \$0.045 per GB processed; cross-AZ traffic costs about \$0.01 per GB in each direction; internet egress starts around \$0.09 per GB; gateway endpoints for S3/DynamoDB are free; interface endpoints cost about \$0.01 per hour per AZ plus \$0.01 per GB Version-sensitive · checked Nov 2026 — verify on the AWS pricing pages for your Region. Example: if Lumen's nodes pull 3 TB/month of images and model artifacts from ECR and S3 through NAT, NAT processing alone is \(3{,}000 \times 0.045 = \$135\) per month that endpoints eliminate (S3 gateway endpoint free; ECR interface endpoints cost far less at this volume). Chatty cross-AZ service calls at 50 TB/month cost \(50{,}000 \times 0.02 = \$1{,}000\) per month — the case for topology-aware routing.

Lambda charges per request and per GB-second of duration (billed per millisecond), with a lower price on ARM/Graviton. Using commonly published x86 list prices of about \$0.20 per million requests and \$0.0000166667 per GB-second Version-sensitive · checked Nov 2026:

\[ \text{monthly cost} \approx N \times \left( \frac{0.20}{10^6} + M_{\text{GB}} \times t_{\text{s}} \times 0.0000166667 \right) \]

For 10 million invocations of the notification function at 1 GB and 120 ms: \(10^7 \times (2 \times 10^{-7} + 1 \times 0.12 \times 1.667 \times 10^{-5}) = 2 + 20 = \$22\) per month. A steady 300 requests/second API at 512 MB and 80 ms is \(7.8 \times 10^8\) invocations/month: \(156 + 7.8 \times 10^8 \times 0.5 \times 0.08 \times 1.667 \times 10^{-5} \approx 156 + 520 = \$676\) per month, versus a few hundred dollars for two or three small always-on containers that could serve the same load — the break-even intuition behind "serverless for spiky, containers for steady" Illustrative.

6.5 Lambda concurrency

By Little's Law (Chapter 1 §6.5), required concurrency = arrival rate × duration. At 500 requests/s and 200 ms average duration, you need \(500 \times 0.2 = 100\) concurrent environments. If each opens a database connection, that is 100 connections; a 2,000 req/s burst with a 2 s cold-start-inflated duration briefly needs 4,000 — far beyond what PostgreSQL tolerates. Use RDS Proxy, reserved concurrency limits or a queue in front.

6.6 SQS visibility timeout

Set the visibility timeout to at least six times the function timeout when Lambda consumes SQS (AWS's documented guidance), so that a message being processed — including retries within a batch — does not reappear and get processed twice in parallel. With a 30 s function timeout: visibility timeout ≥ 180 s.

// Dependencies: aws-lambda-java-core, aws-lambda-java-events, software.amazon.awssdk:sesv2,
// software.amazon.awssdk:url-connection-client, org.crac:crac, jackson-databind.
public class OrderPlacedHandler implements RequestHandler<SQSEvent, SQSBatchResponse>, Resource {

    // Initialised once per execution environment (or once at snapshot time with SnapStart).
    private static final ObjectMapper JSON = new ObjectMapper();
    private SesV2Client ses = newClient();

    public OrderPlacedHandler() {
        Core.getGlobalContext().register(this);   // receive SnapStart (CRaC) lifecycle callbacks
    }

    private static SesV2Client newClient() {
        return SesV2Client.builder()
                .region(Region.of(System.getenv("AWS_REGION")))
                .httpClient(UrlConnectionHttpClient.create())  // lightweight, fast to initialise
                .build();
    }

    @Override
    public void beforeCheckpoint(org.crac.Context<? extends Resource> ctx) {
        // Warm up class loading and JSON paths so the snapshot contains initialised code.
        JSON.convertValue(new OrderPlaced("warmup", "warmup@example.com", 0), OrderPlaced.class);
    }

    @Override
    public void afterRestore(org.crac.Context<? extends Resource> ctx) {
        ses = newClient();   // never reuse connections/credentials captured in the snapshot
    }

    @Override
    public SQSBatchResponse handleRequest(SQSEvent event, Context context) {
        List<SQSBatchResponse.BatchItemFailure> failures = new ArrayList<>();
        for (SQSEvent.SQSMessage msg : event.getRecords()) {
            try {
                OrderPlaced order = JSON.readValue(msg.getBody(), OrderPlaced.class);
                sendConfirmation(order);   // must be idempotent: SQS is at-least-once
            } catch (Exception e) {
                context.getLogger().log("failed " + msg.getMessageId() + ": " + e);
                failures.add(new SQSBatchResponse.BatchItemFailure(msg.getMessageId()));
            }
        }
        return new SQSBatchResponse(failures);   // only failed messages are retried
    }

    private void sendConfirmation(OrderPlaced o) {
        ses.sendEmail(SendEmailRequest.builder()
                .fromEmailAddress("orders@lumen.example.com")
                .destination(Destination.builder().toAddresses(o.email()).build())
                .content(EmailContent.builder().simple(Message.builder()
                        .subject(Content.builder().data("Order " + o.orderId() + " confirmed").build())
                        .body(Body.builder().text(Content.builder()
                                .data("Thank you! Total: " + o.totalCents() / 100.0).build()).build())
                        .build()).build())
                .build());
    }

    public record OrderPlaced(String orderId, String email, long totalCents) {}
}

package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log/slog"

	"github.com/aws/aws-lambda-go/events"
	"github.com/aws/aws-lambda-go/lambda"
	"github.com/aws/aws-sdk-go-v2/aws"
	"github.com/aws/aws-sdk-go-v2/config"
	"github.com/aws/aws-sdk-go-v2/service/sesv2"
	"github.com/aws/aws-sdk-go-v2/service/sesv2/types"
)

type orderPlaced struct {
	OrderID    string `json:"orderId"`
	Email      string `json:"email"`
	TotalCents int64  `json:"totalCents"`
}

var client *sesv2.Client // initialised once per execution environment

func handle(ctx context.Context, ev events.SQSEvent) (events.SQSEventResponse, error) {
	var resp events.SQSEventResponse
	for _, m := range ev.Records {
		var o orderPlaced
		if err := json.Unmarshal([]byte(m.Body), &o); err != nil {
			resp.BatchItemFailures = append(resp.BatchItemFailures, events.SQSBatchItemFailure{ItemIdentifier: m.MessageId})
			continue
		}
		_, err := client.SendEmail(ctx, &sesv2.SendEmailInput{
			FromEmailAddress: aws.String("orders@lumen.example.com"),
			Destination:      &types.Destination{ToAddresses: []string{o.Email}},
			Content: &types.EmailContent{Simple: &types.Message{
				Subject: &types.Content{Data: aws.String("Order " + o.OrderID + " confirmed")},
				Body:    &types.Body{Text: &types.Content{Data: aws.String(fmt.Sprintf("Total: %.2f", float64(o.TotalCents)/100))}},
			}},
		})
		if err != nil {
			slog.Error("send failed", "messageId", m.MessageId, "err", err)
			resp.BatchItemFailures = append(resp.BatchItemFailures, events.SQSBatchItemFailure{ItemIdentifier: m.MessageId})
		}
	}
	return resp, nil
}

func main() {
	cfg, err := config.LoadDefaultConfig(context.Background())
	if err != nil {
		panic(err)
	}
	client = sesv2.NewFromConfig(cfg)
	lambda.Start(handle)
}

8. Applications: How Teams Use AWS

8.1 Multi-account landing zones

Organisations separate workloads into many AWS accounts (per environment, per team or per domain) under AWS Organizations, with Control Tower or custom tooling providing a landing zone: centralised logging (CloudTrail organisation trail to a log archive account), security tooling (GuardDuty, Security Hub, Config) in a security account, IAM Identity Center for human SSO, SCPs as guardrails (deny disabling CloudTrail, deny leaving approved Regions), and a networking account with Transit Gateway and shared VPCs. An account is the strongest isolation boundary AWS offers — blast radius for both security incidents and quota exhaustion.

8.2 Containers on EKS, glue on Lambda

The Lumen pattern is common: long-running, latency-sensitive services on EKS (or ECS), event-driven glue and spiky background work on Lambda, workflows on Step Functions, and managed data services. Platform teams publish Terraform modules and Helm charts for each pattern so application teams compose them rather than design networks.

8.3 AI workloads on AWS

AI services add specific needs: GPU instances (scheduled through Karpenter/Auto Mode NodePools), model artifacts in S3 pulled through gateway endpoints, managed model APIs (Amazon Bedrock) reached privately through interface endpoints with IAM-scoped access to specific models, vector storage (Aurora PostgreSQL with pgvector, OpenSearch, or S3 Vectors), and cost controls on token usage. Keeping model traffic off the public internet via PrivateLink is often a compliance requirement.

8.4 Cost management

Mature teams tag every resource (default tags in Terraform), review Cost Explorer by tag weekly, buy Savings Plans for the steady base, use Spot for stateless and batch capacity (Karpenter handles interruptions), add VPC endpoints to cut NAT processing, keep traffic in-AZ where possible, and set budgets with alerts. FinOps is an engineering practice, not an accounting one.

8.5 Resilience patterns

Multi-AZ by default (EKS nodes in three AZs, RDS Multi-AZ, NAT per AZ); static stability (pre-provisioned capacity so an AZ loss does not require launching new resources during the event); backups and point-in-time recovery tested regularly; and, where justified, warm-standby or active-active in a second Region with Route 53 failover or global data stores (DynamoDB global tables, Aurora Global Database).

9. Case Studies

9.1 AWS us-east-1, December 2021: congestion on the internal network

Verified On 7 December 2021, an automated activity to scale capacity of an AWS service hosted on AWS's internal network triggered unexpected behaviour from a large number of clients, causing a surge of connection activity that congested the devices between the internal network and the main AWS network. Customer-facing services that depended on internal-network services (including parts of the EC2 APIs, the monitoring used by AWS operators, and the Service Health Dashboard itself) were impaired for hours, while already-running workloads largely continued. Lessons for customers: running capacity is more resilient than control-plane operations during an event (static stability), and your incident detection must not depend on the provider's status page. Source: AWS, "Summary of the AWS Service Event in the Northern Virginia (US-EAST-1) Region".

9.2 AWS us-east-1, October 2025: a DNS race condition in DynamoDB automation

Verified AWS's post-event summary describes an event from 23:48 PDT on 19 October to 14:20 PDT on 20 October 2025. A latent race condition in DynamoDB's automated DNS management system left an empty DNS record for the regional endpoint dynamodb.us-east-1.amazonaws.com, so clients could not resolve it; dependent services, including EC2 instance launches (whose internal systems depend on DynamoDB) and Network Load Balancer health checking, were impaired in later phases, with long recovery tails as backlogs drained. Lessons: DNS is a single point of failure even inside a cloud provider; recovery of control planes can take far longer than the triggering fault; and workloads that needed to launch instances during the event were hit hardest — again an argument for static stability and for understanding your provider dependencies. Source: AWS, "Summary of the Amazon DynamoDB Service Disruption in the Northern Virginia (US-EAST-1) Region".

9.3 AWS S3, February 2017: a mistyped command

Verified On 28 February 2017, an engineer debugging the S3 billing system in us-east-1 ran an established playbook command with a mistyped input that removed a larger set of servers than intended, including subsystems S3 needed to serve requests. Restart of those subsystems took hours because they had not been fully restarted in years while the region had grown. AWS changed its tooling to remove capacity more slowly and to block removals below minimum capacity. Lessons: operational tooling needs guardrails; recovery paths of rarely restarted systems must be exercised. Source: AWS, "Summary of the Amazon S3 Service Disruption in the Northern Virginia (US-EAST-1) Region".

9.4 Amazon Builders' Library: static stability

Verified Amazon's Builders' Library article on static stability explains how AWS designs systems (for example, EC2's data plane and Availability Zone independence) so that they keep working when dependencies such as control planes are impaired, and recommends customers pre-provision capacity across AZs rather than relying on reacting during an event. 12. Common Mistakes and Production Failures

  1. Static access keys in code, environment variables or CI. Use roles everywhere.
  2. "Action": "*" policies "to make it work", never tightened.
  3. Small subnets for EKS (/24) leading to IP exhaustion as the cluster grows.
  4. One NAT gateway for all AZs — a single-AZ failure takes down egress for the whole VPC, and cross-AZ NAT traffic costs extra.
  5. No VPC endpoints: paying NAT processing for ECR pulls and S3 traffic.
  6. Opening security groups to CIDRs (or 0.0.0.0/0) instead of referencing security groups.
  7. Health checks pointed at liveness or a deep dependency check, causing the ALB to drain all targets during a database blip.
  8. Default ALB deregistration delay (300 s) slowing every deployment for stateless APIs.
  9. Lambda + RDS without a proxy: a traffic spike opens thousands of connections.
  10. Non-idempotent SQS consumers, and visibility timeouts shorter than processing time, causing duplicate side effects.
  11. Spring Boot fat JAR on Lambda without SnapStart, then blaming Lambda for multi-second latency.
  12. Assuming a Region is a single failure domain you can ignore — or, the opposite, building multi-region active-active before mastering multi-AZ.
  13. Ignoring quotas (Lambda concurrency, ENIs per instance, EIPs, API rate limits) until a launch day.

13. Production Concerns

13.1 Performance

Keep chatty services in the same AZ (topology-aware routing) and close to their databases; use Graviton for price-performance; size Lambda memory by measuring (more memory means more CPU and often lower cost per invocation); enable HTTP keep-alive in SDK clients; use RDS Proxy or the AWS JDBC wrapper for connection-heavy and failover-sensitive workloads.

13.2 Security

  • Least-privilege roles per workload; SCP guardrails; IAM Access Analyzer.
  • Private EKS API endpoint; private subnets for all compute; data subnets without internet routes.
  • Encryption at rest with KMS everywhere (EBS, RDS, S3, Secrets); TLS in transit (rds.force_ssl).
  • VPC endpoint policies and S3 bucket policies requiring aws:SourceVpce for sensitive buckets.
  • CloudTrail, VPC Flow Logs, GuardDuty enabled organisation-wide; WAF on public entry points.

13.3 Scalability

Know your quotas and request increases early (Service Quotas); design partition keys for DynamoDB; use SQS to absorb bursts; pre-warm or pre-provision capacity for known events; consider cell-based architecture (many independent copies of the stack, each serving a subset of customers) for very large systems.

13.4 Monitoring

CloudWatch metrics for managed services (ALB 5xx and target response time, RDS CPU/connections/replica lag, SQS ApproximateAgeOfOldestMessage, Lambda errors/throttles/duration/concurrency, NAT ErrorPortAllocation), exported to Prometheus/Grafana via CloudWatch exporters or the managed Amazon Managed Service for Prometheus and Grafana; X-Ray or OpenTelemetry for traces through Lambda and API Gateway (Chapter 5). Alert on symptoms first (error rate, latency, queue age), causes second.

13.5 Reliability and maintainability

Everything through Terraform; tagging standards; runbooks for AZ evacuation (zonal shift for ALB/NLB), RDS failover and Lambda throttling; game days that simulate AZ loss with AWS Fault Injection Service (Chapter 6); and regular review of AWS Health events for your accounts.

14. Exercises

Exercise 1 · Foundation

A subnet's route table has 10.40.0.0/16 → local and 0.0.0.0/0 → igw-123. Is it public or private? What else is required for an EC2 instance in it to be reachable from the internet?

Solution

Public: its default route points to an Internet Gateway. The instance also needs a public IPv4 or Elastic IP (the IGW maps it 1:1), a security group allowing the inbound port from the source, and NACLs allowing inbound and the return ephemeral ports.

Exercise 2 · Intermediate

Plan the CIDRs for a VPC hosting an EKS cluster expected to reach 3,000 pods per AZ across three AZs, plus ALBs and RDS. Justify subnet sizes.

Solution

VPC 10.40.0.0/16. Private subnets /19 per AZ (8,187 usable) to fit 3,000 pods plus nodes and warm IPs with ~2.5x headroom: 10.40.32.0/19, 10.40.64.0/19, 10.40.96.0/19. Public /24 per AZ for ALB nodes and NAT gateways. Data /24 per AZ for RDS and caches. Leave the remaining space (e.g., 10.40.128.0/17) unallocated for future tiers or another cluster. Avoid overlap with on-prem and other VPCs that may be connected via Transit Gateway. Alternative: secondary 100.64.0.0/16 for pods with custom networking, or IPv6.

Exercise 3 · Intermediate

Your Java Lambda (1 GB, SQS-triggered) has p99 latency of 4.2 s, mostly cold starts, and creates a Spring ApplicationContext in the handler constructor. Give a prioritised plan.

Solution

(1) Enable SnapStart on a published version/alias; add CRaC hooks to refresh connections and credentials after restore. (2) Remove or slim the Spring context (plain handler with static SDK clients; if Spring is needed, use Spring Cloud Function with AOT). (3) Use the lightweight URL connection or CRT HTTP client; avoid classpath scanning. (4) Tune TieredStopAtLevel=1. (5) Measure Init duration in CloudWatch REPORT lines and restore duration. (6) If still insufficient and the function is on a latency-critical path, consider provisioned concurrency or a GraalVM native image. For an SQS consumer, also ask whether cold-start latency matters at all.

Exercise 4 · Advanced

After a traffic spike, orders-service pods calling a third-party payment API through a single NAT gateway see intermittent connection failures, and CloudWatch shows ErrorPortAllocation on the NAT. Explain and fix.

Solution

A NAT gateway can support about 55,000 simultaneous connections to each unique destination (IP, port, protocol). Many pods opening new connections per request to the same payment endpoint exhausts source ports, compounded by TIME_WAIT (Chapter 1). Fixes: connection pooling and keep-alive in the HTTP client (primary); NAT gateway per AZ to spread load; additional secondary IPs on the NAT gateway (each adds port capacity); if the provider offers PrivateLink, use it to bypass NAT. Monitor ErrorPortAllocation and active connection counts.

Exercise 5 · Advanced

Write the IAM policy statement allowing assist-service to read only objects under docs/ in bucket lumen-knowledge, and only through the VPC endpoint vpce-0abc.

Solution
{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::lumen-knowledge/docs/*",
  "Condition": {"StringEquals": {"aws:SourceVpce": "vpce-0abc"}}
}

Attach it to the role associated with the lumen/assist ServiceAccount via Pod Identity. For defence in depth add a bucket policy that denies all access not coming through the endpoint (with exceptions for administrative roles), and enable S3 Block Public Access.

15. Interview Questions

Conceptual What makes a subnet public in AWS?

Only its route table: a default route to an Internet Gateway. Instances additionally need public IPs to be reachable. Private subnets route to a NAT gateway or nowhere.

Conceptual Security groups vs NACLs?

SGs are stateful, allow-only, attached to ENIs, can reference other SGs; NACLs are stateless, allow/deny, ordered rules, attached to subnets, CIDR-only. Use SGs for micro-segmentation and NACLs as coarse guardrails.

Conceptual Explain the Lambda execution model and cold starts.

Each execution environment (Firecracker microVM) handles one invocation at a time; concurrency is the number of environments. A cold start runs Init (runtime start, code load, static init). Environments are reused while warm. SnapStart snapshots post-Init state at publish time; provisioned concurrency keeps environments warm.

Architecture Design the network for an EKS-based platform with an RDS database and calls to an external LLM API.

Three-AZ VPC; public subnets for ALB/NLB and per-AZ NAT; large private subnets for nodes/pods; isolated data subnets for RDS Multi-AZ; gateway endpoints for S3/DynamoDB; interface endpoints for ECR, STS, Secrets Manager, logs and (if used) Bedrock; SG references ALB → pods → RDS; egress to the LLM API via NAT with keep-alive pooling (or PrivateLink if offered); private EKS API endpoint; Flow Logs and WAF.

Architecture When would you choose ECS over EKS?

Small number of services, AWS-only, team without Kubernetes expertise, desire for minimal operational overhead and deep native integration. EKS when you need the Kubernetes ecosystem (operators, GitOps tooling, KEDA, service mesh), portability, or a platform for many teams.

Scenario A pod gets AccessDenied calling S3 after you moved from IRSA to Pod Identity. Debug it.

Check the pod identity association (namespace and ServiceAccount names), the role's trust policy (principal pods.eks.amazonaws.com with sts:AssumeRole and sts:TagSession), that the Pod Identity Agent is running, that the SDK version supports the container credentials provider, leftover IRSA env vars taking precedence, the role's permissions, bucket policy and endpoint policy denies, and use CloudTrail to see which principal made the call and why it was denied.

Scenario An SQS-triggered Lambda processes some messages twice. Why, and how do you fix it?

At-least-once delivery; visibility timeout shorter than processing time (or batch retries); full-batch failure re-delivering successful messages; function timeouts. Fix: idempotency keys (e.g., DynamoDB conditional writes or Powertools idempotency), visibility timeout ≥ 6× function timeout, ReportBatchItemFailures, FIFO with deduplication if ordering and dedupe are needed.

Conceptual What is static stability?

Designing so a system keeps operating during an impairment without needing to make changes — e.g., provisioning enough capacity in each AZ to absorb the loss of another, so you do not depend on control-plane actions (launching instances) during the event.

Coding Compute the monthly Lambda cost for 50M invocations at 256 MB and 40 ms on arm64, given prices per GB-s and per request.

GB-s = 5×10⁷ × 0.25 × 0.04 = 500,000 GB-s; multiply by the arm64 GB-s price (roughly 20% below x86 at list) plus 50 × the per-million request price. Show the formula; look up current prices rather than memorising them.

Behavioral Tell me about a cloud cost problem you found and fixed.

A strong answer names the signal (Cost Explorer by tag, unexpected NAT/data transfer line), the root cause (e.g., images pulled through NAT, cross-AZ chatter), the fix (endpoints, topology-aware routing), the measured savings, and the guardrail added (budgets, dashboards, module defaults).

16. Knowledge Check

  • Design for AZ failure always: resources and NAT per AZ, Multi-AZ databases, static stability.
  • IAM roles with least privilege for every workload; no static keys; explicit deny wins.
  • Subnets are public or private only by their route tables; size EKS subnets for pod IPs.
  • Security groups are stateful and should reference each other; NACLs are stateless guardrails.
  • VPC endpoints remove NAT cost and internet dependency for AWS APIs.
  • ALB for L7 routing; NLB for L4, static IPs and PrivateLink; tune health checks, idle timeouts and deregistration delay.
  • Lambda: one request per environment, cold starts in Init; SnapStart or native images for Java; idempotent SQS consumers.
  • Serverless wins for spiky, event-driven work; containers win for steady high load.
