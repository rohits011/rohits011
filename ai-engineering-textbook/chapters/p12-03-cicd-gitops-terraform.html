Part 12 · Chapter 3

CI/CD, GitOps, Infrastructure as Code & Terraform

A container image and a Helm chart are only useful if a trustworthy, automated path takes a commit to production — and if the cloud resources underneath are just as reproducible as the code. This chapter builds that path for the Lumen platform: GitHub Actions pipelines that test, build, sign and publish; Argo CD reconciling clusters from Git; Argo Rollouts and feature flags limiting blast radius; and Terraform (or OpenTofu) describing the VPCs, clusters and databases themselves.

  • Prerequisites: Chapter 12.2 (images, Kubernetes manifests, Helm/Kustomize); Git branching and pull requests; experience with a Jenkins or similar pipeline.
  • You will be able to: design a pipeline with the right tests at the right stage; publish immutable, signed artifacts; explain push vs pull deployment and GitOps principles; promote releases across environments; run canary and blue-green rollouts with automated analysis; and write, structure, test and safely operate Terraform with remote state and locking.

1. Introduction: Making Change Safe, Fast and Repeatable

Every production incident has a trigger, and the most common trigger is change: a deploy, a configuration update, an infrastructure modification. Yet organisations that deploy more often tend to have fewer and shorter incidents, because each change is small, tested automatically, observable and easy to reverse. That is the core insight behind continuous delivery, documented in the DORA research programme and the book Accelerate (2018): deployment frequency, lead time for changes, change failure rate and time to restore service move together in high-performing teams.

This chapter covers three disciplines that together make change safe:

  • CI/CD — every commit is built and tested automatically; every artifact that passes is a release candidate; delivery to environments is automated, gradual and reversible.
  • GitOps — the desired state of each environment lives in Git; agents in the clusters pull and reconcile it; Git history is the audit log and git revert is the rollback.
  • Infrastructure as Code — VPCs, clusters, databases, IAM and DNS are declared in version-controlled code (Terraform/OpenTofu), reviewed like application code, and applied by automation.

Bridging from Java & Spring Boot

What you already know
Maven/Gradle lifecycles (test, verify, deploy); a Jenkinsfile with stages for build, unit tests, SonarQube, and a manual "deploy to prod" job that runs a script against servers; artifacts in Nexus or Artifactory; perhaps Flyway or Liquibase migrations run at application startup; infrastructure created through the AWS console or tickets to an ops team.
Why that is not enough
Push-based Jenkins jobs hold production credentials, have no notion of drift (someone edits a server and the pipeline never notices), and make rollbacks bespoke scripts. Rebuilding an artifact per environment means what you tested is not what you shipped. Console-created infrastructure cannot be reviewed, reproduced or recovered.
The modern approach
Build once, produce an immutable, signed image referenced by digest; promote that digest through environments by changing Git; let Argo CD/Flux reconcile clusters; use Argo Rollouts to shift traffic gradually with automated metric analysis; declare infrastructure in Terraform with remote state, locking, plans reviewed in pull requests and policy checks.
Where Python and Go fit
Pipelines are polyglot: the same workflow template runs mvn verify, pytest and go test -race. Go dominates the tooling layer (Terraform, Argo CD, Flux, Helm, kubectl are all Go), and Terratest writes infrastructure tests in Go. Python is common for pipeline glue and for evaluating AI models as a pipeline gate.
In production
Most outages trace back to a change. The controls in this chapter — small batches, automated tests, progressive delivery, fast rollback, reviewed infrastructure plans, drift detection — are how teams keep change failure rate low without slowing down.
Use it when / avoid it when
Adopt all of it for any service with real users. Scale down rather than skip: a two-person team can use one workflow file, one Argo CD instance and a small Terraform repo. Avoid building bespoke deployment platforms when the off-the-shelf combination works.

1.1 Lumen's delivery path in one paragraph

A developer opens a pull request against orders-service. GitHub Actions runs unit tests, Testcontainers-based integration tests, static analysis and a container build. On merge to main the workflow builds a multi-architecture image once, scans it, generates an SBOM, signs it with Sigstore cosign using GitHub's OIDC identity, pushes it to Amazon ECR, and opens a pull request in the lumen-gitops repository updating the image digest for the dev environment. Argo CD in the dev cluster syncs. Promotion to staging and production is another reviewed digest change in Git. In production, Argo Rollouts shifts 10%, 25%, 50% then 100% of traffic to the new version while querying Prometheus; if the error rate or latency degrades, it aborts and returns all traffic to the old version automatically. The EKS cluster, VPC, RDS database and IAM roles all come from Terraform modules applied by a separate pipeline after a plan is reviewed.

2. History

Continuous integration was named by Grady Booch (1991) and made a core practice by Extreme Programming in the late 1990s; Martin Fowler's 2000 article (revised 2006) popularised it. CruiseControl (2001) was an early CI server; Hudson (2005, Kohsuke Kawaguchi at Sun) was forked as Jenkins in 2011 after Oracle's acquisition of Sun, and Jenkins Pipeline (Jenkinsfile, 2016) brought pipeline-as-code. Hosted CI followed: Travis CI (2011), CircleCI (2011), GitLab CI (2012–2015), and GitHub Actions (announced 2018, generally available with CI/CD in November 2019).

Continuous delivery was codified by Jez Humble and David Farley's book Continuous Delivery (2010), which introduced the deployment pipeline as a sequence of increasingly expensive quality gates and the rule "build your binaries only once". Accelerate (Forsgren, Humble, Kim, 2018) summarised the DORA research linking delivery practices to organisational performance.

Infrastructure as code grew from configuration management — CFEngine (1993), Puppet (2005), Chef (2009), Ansible (2012) — which configured existing servers. Cloud APIs enabled provisioning as code: AWS CloudFormation (2011) and HashiCorp Terraform (v0.1 in July 2014), whose provider model made one tool work across clouds and SaaS. Terraform 1.0 shipped in June 2021 with compatibility promises. In August 2023 HashiCorp relicensed Terraform from the MPL 2.0 to the Business Source License 1.1 (effective from 1.6), restricting competitive commercial use. The community responded with the OpenTF manifesto and a fork that the Linux Foundation adopted as OpenTofu in September 2023; OpenTofu 1.6.0 reached GA in January 2024 and the project joined the CNCF as a Sandbox project in April 2025. IBM completed its acquisition of HashiCorp in February 2025. Both tools continue to evolve: Terraform's 1.x line (1.16 per release trackers as of late 2026) and OpenTofu's 1.13 line, with features diverging (e.g., OpenTofu's client-side state encryption since 1.7) Version-sensitive · checked Nov 2026.

GitOps was coined by Alexis Richardson of Weaveworks in 2017, building on Kubernetes' declarative model. Weaveworks created Flux; Intuit created Argo CD (open-sourced 2018). Both became CNCF Graduated projects in late 2022. The OpenGitOps project (CNCF) published the four GitOps principles in 2021. Weaveworks itself shut down in February 2024, but Flux continued under the CNCF. Argo CD 3.0 shipped in 2025. Progressive delivery — canaries, blue-green, feature flags — has roots in practices at Google, Facebook and Netflix (Netflix and Google open-sourced the Spinnaker CD platform and its Kayenta canary analysis in 2015 and 2018); Argo Rollouts and Flagger brought it to Kubernetes.

3. Fundamentals

3.1 Continuous integration, delivery and deployment

  • Continuous integration: everyone merges small changes to the mainline frequently (at least daily), and every merge is built and tested automatically. A broken mainline is fixed immediately.
  • Continuous delivery: every change that passes the pipeline is releasable; deploying to production is a business decision executed by a button or a merge.
  • Continuous deployment: every change that passes the pipeline goes to production automatically, usually with progressive delivery and automated rollback as the safety net.

Trunk-based development — short-lived branches merged to main within a day or two, with incomplete features hidden behind flags — is the branching model that makes CI real. Long-lived feature branches and GitFlow's release branches delay integration and create merge risk.

3.3 The testing pyramid in CI

The pyramid says: many fast unit tests, fewer integration tests, very few end-to-end tests — because cost and flakiness grow toward the top. In Spring Boot terms: plain JUnit tests of domain logic at the base; slice tests (@WebMvcTest, @DataJpaTest) and @SpringBootTest with Testcontainers in the middle; contract tests (Spring Cloud Contract or Pact) between edge-gateway and orders-service to catch API breakage without spinning up both; and a thin layer of end-to-end smoke tests against a deployed environment. For AI services, add an evaluation stage: run a fixed evaluation set through assist-service and fail the pipeline if answer quality, groundedness or latency regress beyond a threshold (Part 8).

Flaky tests are pipeline bugs

A test that fails 2% of the time fails one in fifty builds and trains engineers to click "re-run". Quarantine flaky tests automatically (tag and exclude from the gating stage), track them, and fix them as you would a production bug.

3.4 Artifact management and immutability

"Build once, deploy many": the artifact tested in staging must be byte-for-byte the one deployed to production. For containers, that means referencing images by digest (sha256:…), not tag, and never rebuilding per environment. Environment differences come from configuration (ConfigMaps, Helm values). Registries (ECR, GHCR, Artifactory, Harbor) should have tag immutability enabled, lifecycle policies to expire untagged images, and replication to the regions you deploy to. Helm charts and even Terraform modules are also distributed as versioned artifacts (OCI registries can host all three).

3.5 Supply-chain security

The pipeline itself is an attack surface: a compromised action, dependency or build runner can inject code into artifacts that every environment trusts. Controls: pin third-party actions by commit SHA; least-privilege GITHUB_TOKEN permissions; short-lived cloud credentials via OIDC federation instead of stored keys; dependency pinning and review (lockfiles, Renovate); SBOMs (SPDX/CycloneDX) for every image; signing with Sigstore cosign (keyless signing binds the signature to the workflow's OIDC identity and records it in a transparency log); provenance attestations describing how the artifact was built (SLSA framework); and admission policies in the cluster that only accept images signed by your pipeline. Part 11 covers these in depth.

3.7 Progressive delivery with Argo Rollouts

Argo Rollouts provides a Rollout CRD that replaces a Deployment and adds canary and blue-green strategies with steps (setWeight, pause, analysis), traffic management through a mesh, an ingress controller or Gateway API (via plugin), and AnalysisTemplates that query Prometheus, Datadog, CloudWatch or a web hook and decide success or failure. On failure the Rollout aborts and shifts traffic back to the stable ReplicaSet without human intervention. Flagger (Flux ecosystem) offers similar functionality.

3.8 Feature flags

A feature flag is a runtime decision point: if (flags.isEnabled("new-pricing", user)) …. Flags enable trunk-based development (merge incomplete work disabled), targeted releases (internal users, then 1% of customers, then everyone), experiments (A/B tests) and kill switches (turn off an expensive LLM-powered feature under load). OpenFeature (a CNCF project) standardises the SDK API across languages and vendors (LaunchDarkly, Unleash, flagd, AWS AppConfig). Flags have a lifecycle: create, roll out, clean up. Stale flags are technical debt and a source of incidents — the Knight Capital case in §9 involved a repurposed flag.

3.9 GitOps principles

The OpenGitOps project defines four principles:

  1. Declarative — the system's desired state is expressed declaratively.
  2. Versioned and immutable — desired state is stored in a way that enforces immutability and versioning and retains a complete history (Git).
  3. Pulled automatically — software agents automatically pull the desired state from the source.
  4. Continuously reconciled — agents continuously observe actual state and attempt to apply the desired state.

Notice that principle 4 is the Kubernetes controller pattern (Chapter 2 §3.7) applied one level up: Argo CD is a controller whose desired state is a Git repository.

3.10 Push vs pull deployment

In push deployment, the CI system holds cluster credentials and runs kubectl apply or helm upgrade. It is simple, but the CI system becomes a high-value target with production access, and nothing notices if someone changes the cluster afterward. In pull (GitOps) deployment, an agent inside the cluster has the credentials; CI only writes to Git. The cluster's state is continuously compared with Git, so manual changes are detected (and optionally reverted — self-heal). The trade-off: an extra repository and an extra hop of latency, and the need to wire feedback (sync status) back to developers.

3.11 Argo CD and Flux

Argo CD models deployments as Application resources (source: repo, path, revision, Helm/Kustomize options; destination: cluster and namespace; sync policy), offers a rich UI with resource trees and diffs, SSO and RBAC, multi-cluster management from one instance, sync waves and hooks for ordering, and ApplicationSet to generate Applications from templates (per cluster, per directory, per pull request). Flux is a set of composable controllers (GitRepository/OCIRepository sources, Kustomization and HelmRelease appliers, image automation that writes new tags back to Git) designed to run in each cluster, with no UI by default. Both are mature CNCF Graduated projects; Argo CD tends to win when teams want a central UI and multi-cluster view, Flux when they want lightweight, per-cluster, CRD-only automation Opinion.

3.12 Environment promotion

Common repository layouts: directory per environment (envs/dev, envs/staging, envs/prod, each a Kustomize overlay or a values file) on a single branch — recommended — versus branch per environment, which causes painful merges and drift between branches. Promotion is a pull request that copies the digest (and any config changes) from one environment directory to the next, approved by the appropriate owners. Tools such as Kargo automate promotion pipelines on top of Argo CD; Argo CD Image Updater and Flux image automation can bump dev automatically.

3.13 Infrastructure as code: declarative vs imperative

Imperative IaC (shell scripts with the AWS CLI, Ansible playbooks for provisioning) describes steps: "create a VPC, then create subnets". Running it twice may create two VPCs. Declarative IaC (Terraform, CloudFormation, Pulumi's model, Crossplane) describes the end state: "there exists a VPC with these subnets"; the tool computes the steps by comparing the desired state with the current state. Declarative tools are idempotent and can show a plan before acting. Pulumi and the AWS CDK let you write the declaration in general-purpose languages (Java, Python, Go, TypeScript), which is attractive to application engineers but makes it easier to write non-deterministic code; Crossplane manages cloud resources as Kubernetes CRDs reconciled continuously.

3.14 Drift and immutable infrastructure

Drift is the difference between the declared state and reality, caused by console edits, scripts, other tools, or cloud-side changes. Terraform detects drift at plan time (it refreshes the real state); scheduled "drift detection" plans in CI catch it between changes. Immutable infrastructure means you never modify running servers in place: you build a new image (AMI, container) and replace instances. Combined with IaC, it eliminates snowflake servers and makes rollback a matter of pointing back to the previous image.

3.15 Terraform concepts

  • Providers — plugins that translate resources to API calls (hashicorp/aws, hashicorp/kubernetes, hashicorp/helm, Datadog, GitHub, Cloudflare…). Versions are pinned in required_providers and locked in .terraform.lock.hcl.
  • Resources (things Terraform manages), data sources (things Terraform reads), variables, outputs, locals.
  • State — a JSON document mapping each resource address (module.vpc.aws_subnet.private["eu-west-1a"]) to the real object ID and its last known attributes. Terraform needs it to know what it manages. State often contains secrets (database passwords, keys) and must be stored remotely, encrypted and access-controlled.
  • Backends and locking — remote state in S3 (with native S3 lockfiles via use_lockfile since 1.10; DynamoDB locking is deprecated since 1.11), HCP Terraform, GCS, Azure Blob, or a Kubernetes Secret. Locking prevents two concurrent applies from corrupting state.
  • Plan and apply — plan refreshes state, builds a dependency graph, and computes create/update/replace/destroy actions; apply executes a saved plan. Reviewing plans in pull requests is the single most important Terraform safety practice.
  • Modules — reusable directories of configuration with inputs and outputs (like a Java library with a public API). Use registry modules (terraform-aws-modules/vpc/aws) or internal ones, versioned by Git tag or registry version.
  • Workspaces — multiple state files for one configuration. Convenient for ephemeral copies, but separate root modules (or directories) per environment are clearer for long-lived environments with different shapes.
  • Lifecycle and refactoring — prevent_destroy, create_before_destroy, ignore_changes; moved blocks to rename resources without destroying them; import blocks (1.5+) to adopt existing resources; removed blocks (1.7+) to stop managing without destroying.
  • Testing — terraform validate, fmt, TFLint, policy checks (Checkov, tfsec/Trivy, OPA/Conftest on the plan JSON), the native terraform test framework (1.6+) with .tftest.hcl files and mocked providers, and Terratest for full integration tests that create and destroy real infrastructure.

4. Internal Working

4.1 How a GitHub Actions run executes

A push or pull request emits an event; GitHub evaluates every workflow file in .github/workflows/ whose on: filter matches (branches, paths). Each workflow has jobs, which run in parallel unless linked by needs; each job runs on a fresh runner (a GitHub-hosted VM, a larger runner, or a self-hosted runner such as Actions Runner Controller pods on Kubernetes) and executes steps sequentially. Steps either run shell commands or invoke actions (reusable units from repositories, pinned by tag or SHA). Jobs share data through artifacts and caches; secrets are injected as masked environment variables. When a job declares permissions: id-token: write, the runner can request a short-lived OIDC token from GitHub, signed by GitHub and containing claims such as repo, ref, environment and workflow. AWS STS validates that token against an IAM OIDC identity provider and a role trust policy that restricts which repository and branch may assume the role, and returns temporary credentials — no long-lived AWS keys exist anywhere. Environments add protection rules (required reviewers, wait timers, branch restrictions) and environment-scoped secrets. Reusable workflows (workflow_call) let a platform team publish one pipeline used by all services, like a Maven parent POM.

4.2 How Argo CD reconciles

  1. The repo-server clones (and caches) the Git repository at the target revision and renders manifests — plain YAML, Kustomize build, Helm template with the given values, or a config management plugin. Rendering is deterministic for a given commit.
  2. The application controller watches live resources in the destination cluster (via informers, like any controller) and compares the rendered desired state to live state, normalising fields that the cluster mutates (defaults, status). The result is a sync status (Synced/OutOfSync) and a health status computed by resource-specific health checks (a Deployment is Healthy when its rollout is complete; a Rollout when it is not paused/degraded).
  3. If auto-sync is enabled (or a user clicks Sync), the controller applies the difference in sync waves (ordered by the argocd.argoproj.io/sync-wave annotation) with optional PreSync/PostSync hook Jobs (e.g., a Flyway migration Job before the Deployment). With prune, resources removed from Git are deleted; with selfHeal, live changes that diverge from Git are reverted.
  4. Polling (default every 3 minutes) or a Git webhook triggers refresh; the controller also re-checks periodically, so drift is detected even without commits.

4.3 How an Argo Rollouts canary progresses

When the Rollout's pod template changes, the controller creates a canary ReplicaSet and executes the steps. For setWeight: 10 with a traffic router, it scales the canary to an appropriate size and updates the router (e.g., HTTPRoute backend weights, or an ALB's weighted target groups) so 10% of requests reach it. An analysis step creates an AnalysisRun from the template, which periodically executes the metric query and compares results against successCondition/failureCondition; exceeding failureLimit marks the run failed. A failed analysis aborts the Rollout: weight returns to 0, the canary scales down, and the Rollout is Degraded until a new revision is pushed (or the old one is re-applied — in GitOps, by reverting the commit). On success after the final step, the canary becomes the new stable ReplicaSet.

4.4 How Terraform plans and applies

  1. init — downloads providers matching version constraints (verifying checksums against the lock file), downloads modules, configures the backend.
  2. Lock — acquires the state lock (an S3 lock object or DynamoDB item); a second concurrent run fails fast.
  3. Refresh — for each resource in state, calls the provider's read operation to get current real attributes. This is where drift becomes visible.
  4. Graph — builds a directed acyclic graph of resources from references (aws_subnet.private.id referenced by an EKS node group creates an edge).
  5. Diff — for each resource, the provider compares configuration with state and decides: no-op, update in place, or replace (destroy and create) if a "ForceNew" attribute changed — for example changing an RDS instance's identifier or a subnet's CIDR. Replacement of stateful resources is the most dangerous line in any plan.
  6. Apply — walks the graph, executing independent operations in parallel (default parallelism 10), writing state after each resource, and releasing the lock at the end. A failure midway leaves state reflecting what was actually done; re-running continues from there.

5. Architecture Diagrams

5.1 The Lumen CI/CD and GitOps flow

Reading the diagram: the arrows out of CI go only to the registry and to Git — CI holds no cluster credentials. Each environment is reconciled by an Argo CD instance (or one central instance managing several clusters) that pulls from the gitops repository. Promotion to production is a reviewed pull request, giving an audit trail and a one-commit rollback. The production rollout is gated by metrics: Argo Rollouts decides whether to continue based on Prometheus, closing the loop between delivery and observability (Chapter 5).

5.2 Canary rollout timeline

Reading the diagram: users exposed to the faulty version were at most 50% of traffic for a few minutes — and in a well-tuned setup, the first analysis at 10% would catch most regressions. The key design choice is that rollback is automatic and does not depend on a human noticing a dashboard. In GitOps, Git still says "new version", so the final step is a revert commit; Argo CD then reports Synced and Healthy again.

5.3 Terraform repository and state layout

Reading the diagram: splitting state by environment and layer limits the blast radius of any one apply (a mistake in the eks root cannot touch the network), shortens plan times, and lets different teams own different layers. Dependencies between layers flow through outputs read with terraform_remote_state or, better, via data sources/SSM parameters, so layers are loosely coupled. Modules are versioned like libraries so that staging can test vpc v3.2.0 before production adopts it.

5.4 Pipeline as a state machine

Reading the diagram: each state is a stronger claim about the artifact ("it compiles", "it is published and signed", "it has run in staging"). Because the artifact is immutable, a promotion never repeats earlier work — it just records that the same digest has satisfied one more gate.

6. Metrics and Numbers

6.1 DORA metrics

The four key metrics are deployment frequency, lead time for changes (commit to production), change failure rate (fraction of deployments causing a failure in production), and time to restore service. A fifth, reliability, was added later. Compute change failure rate as

\[ \text{CFR} = \frac{\text{deployments causing incidents or rollbacks}}{\text{total deployments}} \]

Track them from your pipeline and incident data rather than surveys once you can. Use them for team learning, never as individual targets (Goodhart's law).

6.2 Batch size and risk

Intuition: if each change has an independent probability \(p\) of being faulty, a deploy that bundles \(n\) changes fails with probability \(1 - (1-p)^n\), and diagnosing which change failed takes longer as \(n\) grows. With \(p = 0.02\): a 1-change deploy fails 2% of the time; a 30-change monthly release fails \(1 - 0.98^{30} \approx 45\%\) of the time, and bisecting it is painful Illustrative. Small, frequent deploys reduce both probability per deploy and time to restore.

6.3 Canary detection power

To detect that a canary's error rate \(e_c\) is worse than baseline \(e_b\), you need enough requests. A rough rule from the normal approximation: the standard error of an observed error rate is \(\sqrt{e(1-e)/N}\). With baseline \(e_b = 0.5\%\) and the canary receiving \(N = 6{,}000\) requests (10% of 1,000 rps for 1 minute), the standard error is \(\sqrt{0.005 \times 0.995 / 6000} \approx 0.09\%\). A jump to 1% (five standard errors) is detectable in a minute; a jump to 0.6% is not. Low-traffic services need longer analysis windows or larger canary weights — or synthetic traffic.

6.4 Pipeline speed and parallelism

Pipeline duration is the critical path through the job graph, not the sum of jobs. If unit tests (6 min), static analysis (5 min) and image build (4 min) run in parallel before integration tests (8 min) and signing (1 min), duration is \(\max(6,5,4) + 8 + 1 = 15\) minutes. Caching (Maven repository, BuildKit layers, Go build cache) often halves stage times; test sharding divides the slowest stage by the shard count at the cost of runner minutes.

6.5 Terraform blast radius

The expected cost of a bad apply scales with the number of resources in the state file. Splitting a 2,000-resource monolith into ten 200-resource roots reduces both plan time (refresh is roughly linear in resources, bounded by API rate limits) and the worst-case damage of a single mistaken change by an order of magnitude.
