Part 9 · Chapter 4

Data Quality, Governance, Feature Stores, Airflow, dbt & Analytics Engineering

Moving data is the easy half. The hard half is knowing that it is right, knowing where it came from and who may see it, running thousands of interdependent jobs on time, and serving features to models without leaking the future. This chapter covers the control plane of a data platform: quality and contracts, governance and lineage, feature stores, orchestration with Airflow, transformation with dbt, and the human system of data engineers, analytics engineers, data scientists and ML engineers that all of it serves.

  • Prerequisites: Chapters 9.1–9.3 (lifecycle and roles, analytical storage and modelling, pipelines and idempotency).
  • You will be able to: define and test data quality across six dimensions; write a data contract; implement checks with Great Expectations, Soda and dbt; emit lineage with OpenLineage; design PII classification, masking and retention; build a Feast feature repository with point-in-time-correct training data; explain Airflow 3's architecture and write idiomatic, idempotent DAGs with assets and deferrable sensors; build dbt staging, incremental and snapshot models with contracts and unit tests; compare Airflow, Dagster and Prefect; and describe precisely how DE, AE, DS and MLE hand work to each other.

1. Introduction: The Control Plane of Data

Chapter 9.3 built pipelines that move and transform data correctly under retries. That is necessary but not sufficient. A pipeline can be perfectly idempotent and still publish garbage because an upstream team changed amount from dollars to cents. A dashboard can be correct and still violate GDPR because it exposes email addresses to a contractor. A model can score brilliantly offline and fail in production because its training features were computed with data from after the prediction time. And two hundred pipelines with implicit dependencies run by cron will, sooner or later, run in the wrong order.

This chapter is about the control plane: the systems and practices that make data trustworthy, governed, reproducible and scheduled. It is the part of data engineering most similar to what you already do as a backend engineer (contracts, validation, access control, migrations, CI/CD, observability), which is exactly why backend engineers are often the ones who make it work.

Bridging from Java & Spring Boot

What you already know
Bean Validation (@NotNull, @Positive) on request DTOs; OpenAPI and consumer-driven contract tests (Spring Cloud Contract, Pact) between services; Flyway migrations versioned in Git and applied in order by CI; Spring Security roles and method-level authorization; Quartz or @Scheduled jobs and Spring Batch's JobRepository for restartability; Micrometer metrics and alerts for SLOs.
Why that is not enough
Validation at the API boundary checks one request; data quality is about distributions, freshness, completeness and relationships across billions of rows from many producers you do not control. @Scheduled knows nothing about dependencies between jobs owned by different teams, backfills or data-aware triggering. Flyway evolves a schema you own; dbt evolves hundreds of derived models whose correctness depends on upstream data.
The modern approach
Data contracts at producer boundaries, automated tests at every layer (Great Expectations, Soda, dbt tests), observability for freshness/volume/schema/distribution anomalies, a catalog with column-level lineage (OpenLineage), policy-based access control with masking, a feature store for ML features, a workflow orchestrator (Airflow, Dagster, Prefect) for scheduling with explicit dependencies, and dbt for version-controlled, tested SQL transformations.
Where Python and Go fit
Airflow, Dagster, Prefect, Great Expectations, Soda, Feast and the OpenLineage client are Python-first. dbt is SQL plus Jinja (dbt Core is Python; the newer Fusion engine is Rust). Go appears in catalog and lineage backends and in Kubernetes operators that run tasks. Java appears in the Spark/Flink jobs that are orchestrated, and in OpenLineage's Spark and Flink integrations.
In production
Contracts are checked in CI on the producer's repository; quality checks gate publication (write-audit-publish); lineage drives impact analysis before changes; access policies are code; Airflow runs on Kubernetes with remote logging, a managed metadata database and alerting; dbt runs in CI on every pull request against sampled data.
Use it when / avoid it when
Adopt the full control plane once more than one team produces or consumes shared data. For a single analyst and three tables, a scheduled script with a few assertions is enough; introducing Airflow, a catalog and a feature store too early creates more operational surface than value.

Data as a product

The unifying idea of this chapter: treat each important dataset as a product with an owner, a documented interface (schema, semantics, freshness SLA), tests, versioning and consumers you notify before breaking changes, exactly as you treat a public API.

2. History

2.1 From cron to workflow engines (2000s–2015)

Early pipelines were cron entries and shell scripts, with dependencies expressed as "job B starts at 3 a.m. because job A usually finishes by 2:30". Hadoop brought Apache Oozie (XML-defined workflows), and LinkedIn built Azkaban. Spotify open-sourced Luigi in 2012, defining tasks and dependencies in Python. Maxime Beauchemin started Airflow at Airbnb in 2014; it was open-sourced in 2015, entered the Apache incubator in 2016 and became a top-level project in 2019. Airflow 2.0 (December 2020) brought a highly available scheduler, the TaskFlow API and a stable REST API. Airflow 3.0 (April 2025) was the largest change since: a Task SDK that separates task code from the core (workers talk to an API server rather than the metadata database), DAG versioning, assets (the renamed datasets) for data-aware scheduling, event-driven scheduling, a new React UI, and reworked backfills Version-sensitive · checked Nov 2026.

Dagster (Elementl, now Dagster Labs, first released 2019) reframed orchestration around software-defined assets. Prefect (2018) emphasized Pythonic, dynamic flows with a hybrid execution model. Netflix open-sourced its Maestro orchestrator in 2024 and Lyft open-sourced Flyte in 2020, both from very large internal deployments.

2.2 dbt and analytics engineering (2016–2026)

Fishtown Analytics (now dbt Labs) released dbt in 2016: SQL SELECT statements as models, Jinja templating, ref() for dependencies, tests and documentation, all in Git. The role of analytics engineer, popularized by the dbt community around 2018–2019, emerged to describe people applying software engineering practices (version control, testing, CI, modularity) to analytical SQL. dbt added snapshots, incremental models, model contracts and versions (1.5, 2023), and unit tests (1.8, 2024). In May 2025 dbt Labs announced the dbt Fusion engine, a Rust rewrite with SQL comprehension, distributed under the ELv2 licence, while committing to maintain Apache-licensed dbt Core Version-sensitive · checked Nov 2026.

2.3 Data quality and observability (2017–2026)

Great Expectations appeared in 2017–2018, introducing declarative "expectations" about data; it reached GX Core 1.0 in August 2024 with a simplified API. Amazon's Deequ (2018) brought unit tests for data on Spark. Soda introduced a YAML check language (SodaCL). Around 2019–2020 "data observability" vendors (Monte Carlo, Bigeye and others) applied monitoring and anomaly detection across warehouses. The term data contract gained wide currency around 2021–2022 as practitioners argued that quality problems must be fixed at the producer boundary rather than detected downstream.

2.4 Governance, lineage and regulation

The EU General Data Protection Regulation took effect on 25 May 2018, making data mapping, purpose limitation, retention and the right to erasure engineering requirements; California's CCPA followed in 2020. Open-source catalogs such as LinkedIn's DataHub (2020) and Lyft's Amundsen (2019), and later OpenMetadata, Unity Catalog (open-sourced 2024) and Apache Polaris, provided searchable metadata. OpenLineage (launched 2020, now an LF AI & Data project) standardized lineage events emitted by Spark, Airflow, dbt, Flink and others.

2.5 Feature stores (2017–2026)

Uber's 2017 description of Michelangelo included a shared feature store with offline and online components, popularizing the pattern. Feast was released in 2019 by Gojek with Google Cloud and is now the most widely used open-source feature store. LinkedIn open-sourced Feathr (2022) and Airbnb open-sourced Chronon (2024). Managed offerings exist on every major ML platform.

3. Fundamentals

3.1 Data quality dimensions

"The data is bad" is not actionable. Name the dimension:

DimensionQuestionExample check (TLC trips)
CompletenessIs everything that should be there present?No null pickup_ts; all 24 hours present for each day; row count within expected range
ValidityDo values conform to type, format, range and domain?payment_type in {0..6}; fare_amount ≥ 0; zone ids exist in the lookup
UniquenessAre entities represented once?trip_id unique; one current row per merchant in SCD2
ConsistencyDo related values agree, within and across datasets?total_amount ≈ fare + tip + tolls + surcharges; dashboard revenue equals finance ledger
Timeliness (freshness)Is the data recent enough for its use?Latest partition loaded by 06:00; max pickup_ts within 2 hours of now for streaming tables
AccuracyDoes data reflect reality?Sampled trips reconciled with meter records; hardest to automate, usually via reconciliation

Add distributional checks (null rate, mean, quantiles, category frequencies compared with recent history) because many failures produce valid-looking but wrong data: every value in range, but the share of card payments halved overnight.

3.2 Kinds of data tests

  • Schema tests: columns, types, nullability; usually enforced by table formats, contracts or registry compatibility.
  • Constraint tests: uniqueness, not-null, accepted values, ranges, referential integrity (relationships).
  • Business-rule tests: cross-column logic and reconciliations (total equals sum of parts; refunds never exceed original charge).
  • Volume and freshness tests: row counts, partition presence, max timestamp lag.
  • Distribution / anomaly tests: statistical comparisons with history; most observability tools automate these.
  • Unit tests for transformation logic: fixed inputs, expected outputs, run in CI without production data (dbt unit tests, pytest on PySpark functions).

Severity matters: some tests should block publication (write-audit-publish), others should warn. A test suite where everything blocks becomes a suite where everything gets disabled.

3.3 Data contracts

A data contract is an agreement between a data producer and its consumers, owned by the producer, that specifies: the schema (fields, types, nullability), semantics (what each field means, units, enumerations), quality guarantees (uniqueness, ranges), service levels (freshness, availability), ownership and support channel, versioning policy and deprecation process, and sometimes classification of sensitive fields. Crucially, it is enforced at the producer: in the producing service's CI (does this change break the contract?) and at runtime (schema registry compatibility, validation before publish). It shifts responsibility left, the same way consumer-driven contract tests shift API compatibility checks into the provider's build. Formats include JSON Schema/Avro/Protobuf with metadata, dbt model contracts for warehouse tables, and specification efforts such as the Open Data Contract Standard (ODCS) under the Linux Foundation's Bitol project.

3.4 Tools: Great Expectations, Soda, dbt tests

Great Expectations (GX Core) is a Python framework: you define expectations (ExpectColumnValuesToBeBetween, ExpectColumnValuesToBeUnique, and many more) grouped in suites, bind them to batches of data from pandas, Spark or SQL sources, and run validations that produce detailed results and HTML "Data Docs". Strong for programmable, Python-centric pipelines. Soda uses SodaCL, a YAML language of checks (row_count > 0, missing_count(col) = 0, freshness(ts) < 2h, anomaly detection) executed by Soda Core against warehouses and Spark. Strong for readable checks maintained by analysts. dbt tests are SQL queries that return failing rows: generic tests (unique, not_null, accepted_values, relationships, plus packages like dbt-utils and dbt-expectations), singular tests (custom SQL files), source freshness checks, and unit tests on model logic. Strong because tests live next to the models they protect and run in the same DAG.

3.5 Data observability

Observability for data mirrors service observability. The commonly cited pillars are freshness, volume, schema changes, distribution, and lineage (to find root cause upstream and impact downstream). Tools learn baselines from metadata and query history and alert on anomalies without hand-written tests for every table. Treat them like APM: they catch unknown unknowns; explicit tests catch known invariants. Both are needed.

3.6 Data catalogs

A catalog makes data discoverable and understandable: searchable inventory of tables, dashboards, pipelines and ML models; schemas; descriptions; owners; tags (domain, tier, PII classes); usage statistics; quality status; and lineage. Note two meanings of "catalog": the technical catalog that engines use to resolve table names and commit metadata (Hive Metastore, Glue, Iceberg REST, Unity, Polaris, from Chapter 9.2), and the business/metadata catalog for humans (DataHub, OpenMetadata, Atlan, Collibra, Unity Catalog's discovery features). Some products do both.

3.7 Lineage and OpenLineage

Lineage records which datasets and jobs produced which datasets, ideally down to columns. Uses: impact analysis (what breaks if I drop this column?), root-cause analysis (why is this dashboard wrong?), compliance (where does this PII flow?), and cost attribution. Lineage can be derived by parsing SQL, by reading query logs, or by instrumenting execution. OpenLineage is an open specification for runtime lineage: integrations in Airflow, Spark, dbt, Flink and others emit RunEvents (START, RUNNING, COMPLETE, FAIL, ABORT) describing a job, a run, and input and output datasets, with extensible facets (schema, column lineage, data quality metrics, SQL, source code location). Events go to a backend such as Marquez (the reference implementation), DataHub or a commercial catalog.

3.8 PII classification

You cannot protect what you have not labelled. Classify columns by sensitivity: direct identifiers (name, email, phone, government id), quasi-identifiers (zip code, birth date, precise location: combinations re-identify people), sensitive categories (health, biometrics, ethnicity, financial account numbers), and non-personal data. Classification combines declaration (producers tag fields in contracts), automated scanning (pattern and ML-based detectors over samples), and review. Tags propagate through lineage: a column derived from email inherits the PII tag. Location data deserves special care: precise coordinates combined with timestamps are highly re-identifying, because few people share the same home-to-work trip pattern. Recent TLC trip records contain taxi-zone ids rather than coordinates, which is a much safer granularity for a public dataset.

3.9 Access control

  • RBAC: grant privileges on catalogs, schemas, tables to roles (analyst, finance, data-eng). Simple, but explodes in large organizations.
  • ABAC / tag-based policies: policies keyed on tags ("columns tagged pii:email are masked unless the user has attribute pii_access=true and purpose support"). Scales because new tables inherit protection by tagging.
  • Column masking: dynamic masking functions return redacted, hashed or partial values based on the caller.
  • Row-level security: filters applied per user (a regional manager sees only their region's rows). Postgres RLS, Snowflake row access policies, BigQuery row-level security, Unity Catalog row filters.
  • Pseudonymization and tokenization: replace identifiers with stable tokens so joins still work; the mapping lives in a separately secured vault.
  • Purpose and audit: log every access to sensitive data; review grants periodically.

3.10 GDPR, retention and deletion

Key engineering implications (this is not legal advice): data minimization (collect and keep only what a purpose needs), purpose limitation, storage limitation (retention periods per dataset, enforced automatically), right of access (find all data about a subject), and right to erasure (delete it, including in derived datasets, backups within a reasonable time, and lakehouse snapshots). Erasure in a lakehouse means a row-level delete and snapshot expiry and file compaction so the bytes are physically gone. Designs that help: keep personal data in few, well-known tables keyed by subject id; reference subjects by pseudonymous ids elsewhere; or use crypto-shredding (encrypt each subject's data with a per-subject key and delete the key).

3.11 Feature stores

A feature is an input signal to a model ("zone's trip count in the last hour", "rider's average tip ratio over 30 days"). A feature store manages feature definitions and their data across the ML lifecycle:

  • Offline store: full history of feature values with timestamps, in the lakehouse or warehouse, used to build training datasets and batch scoring.
  • Online store: latest feature values per entity in a low-latency key-value store (Redis, DynamoDB, Cassandra, Bigtable), read by serving systems at prediction time in milliseconds.
  • Registry: definitions (entities, sources, transformations, TTLs, owners), versioned in Git.
  • Materialization: jobs that compute or copy feature values from offline sources into the online store (batch), or stream processors that write fresh values continuously.
  • Serving APIs: point-in-time historical retrieval for training; online lookup for inference.

The two problems it exists to solve are training-serving skew (the same feature computed differently in the training notebook and the production service) and point-in-time correctness.

3.12 Point-in-time correctness

To train a model that predicts at time t, each training example must use feature values as they were known at t. Joining labels to the latest feature values leaks future information: a churn model trained with "support tickets in last 30 days" computed today, for customers labelled 6 months ago, includes tickets filed after the prediction point, often the very tickets caused by the churn. Offline metrics look superb; production performance collapses. The correct operation is an as-of join (point-in-time join): for each (entity, timestamp) in the label table, take the most recent feature row with feature_ts <= label_ts (and within a TTL so stale values are treated as missing). Feature stores implement this for you; you can also write it with ASOF JOIN in DuckDB, window functions, or pandas merge_asof.

3.13 Orchestration concepts

An orchestrator schedules and coordinates units of work with dependencies. Core concepts: DAG (tasks plus dependency edges, no cycles); schedule (time-based, data-aware, or event-driven); logical date / data interval (the period of data a run is responsible for, distinct from wall-clock start time); retries with backoff; timeouts and SLAs; backfill (run past intervals); catchup (whether missed intervals run automatically); idempotency (every task safe to rerun for its interval); concurrency limits (pools, max active runs); sensors (wait for an external condition); and observability (run history, logs, alerts). An orchestrator should coordinate work, not do heavy work itself: tasks should call Spark, dbt, a warehouse or a Kubernetes pod.

3.14 Airflow concepts

  • DAG: a Python file defining tasks and dependencies; parsed repeatedly by the DAG processor.
  • Operators (templates for tasks: BashOperator, KubernetesPodOperator, provider operators for Spark, Snowflake, BigQuery, dbt), TaskFlow functions decorated with @task, and sensors (tasks that wait for a condition).
  • DAG run and task instance: one execution of a DAG for a logical date, and one execution of a task within it, with states (scheduled, queued, running, success, failed, up_for_retry, skipped, deferred...).
  • XCom: small metadata passed between tasks (ids, paths), not datasets.
  • Assets (Airflow 3; "datasets" in 2.x): logical data objects that tasks declare as outlets; DAGs can be scheduled when assets are updated, giving data-aware scheduling across teams.
  • Deferrable operators and the triggerer: a waiting task releases its worker slot and hands an async trigger to the triggerer process, resuming when the condition fires; essential for sensors at scale.
  • Pools and priority weights: limit concurrent use of shared resources (a warehouse, an API).
  • Connections and variables: externalized configuration, ideally backed by a secrets manager.
  • Dynamic task mapping: create N task instances at runtime from a list (one per partition or file).

3.15 dbt concepts

  • Model: a .sql file containing a SELECT; dbt wraps it in DDL according to its materialization.
  • ref() and source(): reference other models and declared raw tables; dbt builds the dependency DAG from these calls and resolves environment-specific names (dev schema vs prod).
  • Materializations: view, table, incremental (insert or merge only new/changed rows), ephemeral (inlined as a CTE), materialized_view, plus snapshots.
  • Tests: generic and singular data tests; unit tests on logic; source freshness.
  • Snapshots: SCD Type 2 tables built by comparing source rows over time (timestamp or check strategy).
  • Seeds: small CSVs versioned in the repo (mapping tables).
  • Macros and packages: reusable Jinja/SQL.
  • Contracts, versions and access: enforce a model's column names and types at build time; publish versioned models; mark models public/protected/private for cross-project use.
  • Exposures and semantic layer: declare downstream dashboards; define metrics once (MetricFlow) for consistent consumption.
  • Selectors and state: dbt build --select state:modified+ builds only changed models and their descendants in CI ("slim CI").

3.16 Analytics engineering

Analytics engineering is the practice of building and maintaining the transformed, tested, documented analytical data layer, usually in SQL with dbt, sitting between data engineering (raw data platform and pipelines) and analysis (data scientists and analysts). A typical layering: staging models (one per source table: rename, cast, light cleanup, no joins), intermediate models (reusable joins and business logic), and marts (facts and dimensions for a business domain, plus metric definitions). The analytics engineer owns the meaning of business entities and metrics, their tests, and their documentation.

3.17 Dagster and Prefect

Dagster is asset-centric: you declare software-defined assets (a table, a model, a file) as Python functions with their upstream assets, and Dagster derives the graph, tracks materializations, partitions, freshness policies and lineage, and integrates deeply with dbt (each dbt model becomes an asset). It suits teams who think in terms of datasets rather than tasks. Prefect is flow-centric and Pythonic: decorate functions as @flow and @task, run them anywhere, with dynamic control flow, retries, caching, and a server or cloud API that coordinates work pools and workers. It suits dynamic, code-heavy workflows and teams that want minimal framework. Airflow remains the most widely deployed, with the largest provider ecosystem and managed offerings (Amazon MWAA, Google Cloud Composer, Astronomer).

4. Internal Working

4.1 Airflow 3's components

  • Metadata database (Postgres or MySQL): DAG runs, task instances, serialized DAGs and their versions, assets and asset events, connections, variables. It is the system of record; size and back it up like any production database.
  • DAG processor: a separate process (mandatory and standalone in Airflow 3) that parses DAG files from DAG bundles (a local folder or a Git repository), executes their top-level Python, serializes each DAG to JSON and stores it, with a version, in the metadata database. Parsing runs in a loop; slow top-level code slows every DAG.
  • Scheduler: reads serialized DAGs, creates DAG runs when schedules or asset events demand, evaluates dependencies and trigger rules, and sends ready task instances to the executor, respecting pools, concurrency and priority. Multiple schedulers can run for high availability, coordinating through row-level locks (SELECT ... FOR UPDATE SKIP LOCKED) in the database.
  • Executor: a pluggable component inside the scheduler that decides how tasks run: LocalExecutor (subprocesses), CeleryExecutor (a queue and a fleet of workers), KubernetesExecutor (one pod per task), and the Edge executor for remote sites; multiple executors can be configured at once.
  • Workers: run task code through the Task SDK. In Airflow 3, workers no longer connect to the metadata database; they call the API server's Task Execution API to fetch connections, variables and XComs and to report state. That isolates user code from the database (security and scalability) and enables tasks in other languages and remote environments.
  • API server: serves the UI, the public REST API and the Task Execution API.
  • Triggerer: an asyncio event loop running triggers for deferred tasks (thousands per process), waking tasks when conditions fire.

4.2 The life of a task instance

  1. The DAG processor parses trips_daily.py, serializes the DAG, and stores version N.
  2. At the end of the data interval (say 2024-01-15 00:00 to 2024-01-16 00:00), the scheduler creates a DAG run with that logical date and its tasks as scheduled once dependencies allow.
  3. The scheduler checks pool slots and concurrency, marks the task queued and hands it to the executor.
  4. The executor starts it (a Celery message, a Kubernetes pod). The worker's Task SDK supervisor starts the task process, which requests its context from the API server, renders templates ({{ ds }}, {{ data_interval_start }}) and runs execute().
  5. If the task is a deferrable sensor, it raises a deferral: state becomes deferred, the worker slot is freed, the trigger is registered and run by the triggerer, and on firing the task is rescheduled to resume.
  6. On success the state becomes success, outlet asset events are recorded, and downstream tasks (and asset-scheduled DAGs) become eligible. On failure it becomes up_for_retry until retries are exhausted, then failed, firing callbacks and alerts.

Because DAG runs are versioned in Airflow 3, a rerun or backfill can use the DAG version the run was created with, avoiding the 2.x surprise of an old run being re-executed with today's code.

4.3 Why DAG files must be cheap to parse

The DAG processor imports each file repeatedly (by default every few minutes per file, and on change). Top-level code that queries a database, calls an API or reads a large file runs on every parse, slowing scheduling and hammering the dependency. Keep top-level code to DAG construction; put work inside tasks; use Jinja templates or runtime context for values; and use dynamic task mapping instead of generating tasks from a database query at parse time.

4.4 How dbt executes a project

  1. Parse: read dbt_project.yml, all models, YAML properties, macros and packages; render enough Jinja to discover ref()/source() calls and configs; build the manifest (a JSON graph of every node) and a DAG. Partial parsing reuses unchanged results. The Fusion engine additionally compiles and type-checks SQL itself, catching errors before hitting the warehouse.
  2. Select: apply selectors (--select fct_trips+, state:modified+, tags) to choose nodes.
  3. Compile: render each model's Jinja into pure SQL with resolved relation names for the target environment.
  4. Execute: walk the DAG in topological order with N threads; for each node, run the materialization macro: e.g. for table, create a temporary relation and atomically swap; for incremental, on the first run build the full table, later build only new rows into a temp relation and MERGE/INSERT/DELETE+INSERT according to the strategy; for tests, run the test query and count failing rows. dbt build interleaves models and their tests so that a failing test skips downstream models.
  5. Artifacts: write manifest.json, run_results.json and catalog.json, consumed by docs, CI state comparison, orchestrators and lineage tools.

4.5 Incremental models in detail

Inside an incremental model, is_incremental() is true when the target table exists, is not being fully refreshed, and the model is configured incremental. You use it to filter source rows to those newer than the target's high-water mark. The strategy determines how new rows land: append (no dedup), merge on unique_key (upsert), delete+insert (delete target rows matching keys, insert new), insert_overwrite (replace whole partitions, BigQuery/Spark), and microbatch (dbt 1.9+: process data in time batches by an event_time column, each batch independently retryable and backfillable). Late-arriving data needs a lookback window (reprocess the last N days), not a strict > max(ts) filter.

4.6 How Feast builds point-in-time training data

Given an entity dataframe of (entity keys, event timestamp, label) and a list of feature references, Feast's offline store generates a query per feature view that: selects feature rows whose timestamp is ≤ the entity row's timestamp and ≥ timestamp − TTL; ranks them by feature timestamp (and created timestamp as tiebreaker for corrections) descending per entity row; and keeps rank 1. The results are left-joined back so that entity rows with no valid feature value get nulls. Materialization runs the same logic for "now" and writes the latest values per entity into the online store, keyed by a serialized entity key, so that online lookups return exactly what offline retrieval would have produced for the current time.

4.7 An OpenLineage event

When an instrumented Spark job reading bronze.trips and writing silver.trips completes, the OpenLineage Spark listener sends a JSON RunEvent with eventType: COMPLETE, a run.runId (UUID, also linked to the parent Airflow task run via a parent-run facet), a job (namespace and name), inputs and outputs (dataset namespace such as s3://lake and name), and facets: the output schema, a columnLineage facet mapping each output column to the input columns it was derived from, output statistics (row count, bytes), and the SQL or logical plan. The backend stitches events from Airflow, Spark and dbt into one graph because they share dataset naming conventions.

5. Architecture

5.1 Airflow 3 architecture

Reading the diagram: only the DAG processor executes your DAG file's top-level code; only the scheduler decides what runs; only the API server touches the database on behalf of task code. That separation is the main architectural change in Airflow 3 and is why task code can no longer import ORM models and query the metadata DB directly (a common 2.x anti-pattern). Heavy work leaves Airflow entirely: tasks submit Spark jobs, dbt runs or warehouse queries and wait for them, preferably via deferrable operators so waiting costs no worker slot.

Note on the edges

Undirected edges to the metadata database denote read/write access by core components; task processes never appear on those edges because the API server is their single gateway.

5.2 Layered dbt project and its tests

Reading the diagram: every arrow comes from a ref() or source() call, so dbt knows the order without any hand-written dependencies. Staging models are thin views, one per source. The snapshot turns the zone lookup into an SCD2 history, from which the contract-enforced dim_zone is built. Exposures declare who consumes the marts (a dashboard and an ML training set), so impact analysis reaches beyond the warehouse. Tests are attached where they catch problems earliest: freshness at the source, logic in unit tests, integrity on the fact.

5.3 Feature store data flow

Reading the diagram: one set of definitions drives both paths, which is what prevents training-serving skew. Batch features are computed in the lakehouse and materialized to the online store; streaming features are pushed directly and also logged offline so training can see the same values serving saw. Logging the features actually used at prediction time back to Kafka closes the loop: it is the most reliable source for future training data and for skew monitoring (Chapter 10.2).

6. Mathematical Foundations

6.1 Freshness and quality SLOs

Treat datasets like services. Define an SLI such as "fraction of days the fct_trips partition for D−1 is published and passes blocking tests by 06:00". With a 99% SLO over a quarter (~90 days), the error budget is 0.9 days: one late day per quarter. End-to-end freshness of a chain of dependent pipelines is bounded by the sum of their latencies plus scheduling gaps:

\[ F_{\text{end}} \le \sum_{i=1}^{k} \left( L_i + G_i \right) \]

where \( L_i \) is stage runtime and \( G_i \) the wait between an upstream finishing and the downstream starting. Time-based schedules make \( G_i \) up to a full period; data-aware (asset) scheduling drives it to near zero.

6.2 Availability of chained pipelines

If a mart depends on \( k \) independent upstream pipelines each succeeding on time with probability \( p \), the mart is on time with probability \( p^k \). Illustrative With \( p = 0.99 \) and \( k = 20 \): \( 0.99^{20} \approx 0.82 \), so the mart is late about one day in five. This is why long dependency chains need retries, slack, and SLAs on the critical path, the same reasoning as availability of synchronous microservice call chains.

6.3 Anomaly thresholds for volume checks

A simple, robust volume check compares today's row count \( x \) with the last \( n \) same-weekday counts using the median \( \tilde{m} \) and median absolute deviation (MAD):

\[ z_{\text{robust}} = \frac{x - \tilde{m}}{1.4826 \cdot \mathrm{MAD}} \]

The factor 1.4826 makes MAD a consistent estimator of the standard deviation for normal data. Alerting at \( |z_{\text{robust}}| > 4 \) is resistant to past outliers (a holiday) contaminating the baseline, unlike a mean and standard deviation. Every threshold trades false alarms against missed incidents; tune per table tier.

6.4 Point-in-time join cost

A naive point-in-time join of \( n \) label rows against \( m \) feature rows per entity is \( O(n \cdot m) \). Sorting both by (entity, timestamp) and merging gives \( O((n + m)\log(n+m)) \), which is what merge_asof, ASOF JOIN and feature store engines do. A TTL bounds the lookback and therefore how much feature history must be scanned per label.

6.5 Orchestrator throughput

Scheduler capacity is roughly the number of task-state transitions per second the metadata database sustains. For \( D \) DAGs averaging \( t \) tasks per run and \( r \) runs per day, with about 5 state transitions per task, the load is \( 5 D t r / 86{,}400 \) transitions/s. Illustrative 2,000 DAGs × 30 tasks × 24 runs/day ≈ 83 transitions/s on average, with peaks at the top of each hour many times higher. That is why hourly DAGs cluster load at :00 and why spreading schedules (and keeping DAG parsing cheap) matters.

@dag(
    dag_id="tlc_daily",
    schedule="0 5 * * *",                          # after the data interval closes
    start_date=pendulum.datetime(2024, 1, 1, tz="UTC"),

    max_active_runs=3,
    default_args=default_args,
    tags=["tlc", "tier-1"],

    # Deferrable: waiting costs no worker slot; the triggerer polls S3 asynchronously.
    wait_for_raw = S3KeySensor(
        task_id="wait_for_raw",
        bucket_name="raw-landing",
        bucket_key="tlc/yellow/dt={{ ds }}/_SUCCESS",
        deferrable=True,
        timeout=6 * 3600,
        poke_interval=300,
    )

    @task
    def list_partitions(ds: str | None = None) -> list[str]:
        # Small metadata only (paths), never datasets, in XCom.
        return [f"s3://raw-landing/tlc/yellow/dt={ds}/part-{i:02d}.parquet" for i in range(4)]

    @task(pool="raw_validation", max_active_tis_per_dag=4)
    def validate_file(path: str) -> dict:
        import pyarrow.parquet as pq
        md = pq.ParquetFile(path).metadata                # footer only: cheap
        if md.num_rows == 0:
            raise ValueError(f"{path} is empty")
        return {"path": path, "rows": md.num_rows}

    load_bronze = KubernetesPodOperator(
        task_id="load_bronze",
        name="tlc-load-bronze",
        namespace="data-jobs",
        image="registry.example.com/data/spark-jobs:2026.11.3",   # pinned, immutable tag
        cmds=["spark-submit"],
        arguments=["--master", "k8s://https://kubernetes.default.svc",
                   "/opt/jobs/load_bronze.py", "--run-date", "{{ ds }}"],   # logical date
        outlets=[BRONZE_TRIPS],
        get_logs=True,
        on_finish_action="delete_succeeded_pod",
    )

    dbt_build = KubernetesPodOperator(
        task_id="dbt_build",
        name="tlc-dbt-build",
        namespace="data-jobs",
        image="registry.example.com/data/dbt-project:2026.11.3",
        cmds=["dbt"],
        arguments=["build", "--select", "+fct_trips+", "--target", "prod",
                   "--vars", '{"run_date": "{{ ds }}"}'],
        outlets=[FCT_TRIPS],
    )

    files = list_partitions()
    checked = validate_file.expand(path=files)        # dynamic task mapping: one per file
    wait_for_raw >> files
    checked >> load_bronze >> dbt_build
