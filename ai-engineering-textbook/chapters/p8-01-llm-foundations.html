LLM Foundations: Training, Tokenization, Context & Sampling

A large language model is, mechanically, a function that maps a sequence of tokens to a probability distribution over the next token, called in a loop. Everything you will fight with in production — cost, latency, nondeterminism, context limits, truncated JSON, weird behaviour on non-English input — falls out of that one sentence. This chapter builds the mental model an engineer needs to reason about those behaviours from first principles instead of from folklore.

  • Prerequisites: Comfort with probability basics and vectors; Part 7 Chapter 3 (attention & transformers) is helpful but not required — this chapter recaps what an engineer needs and links there for the full derivation.
  • You will be able to: explain how a model is pretrained and post-trained; predict token counts and cost for a workload; size a KV cache; reason about why long contexts are slow and lossy; choose decoding settings deliberately; and explain why two identical requests can return different answers.

1. Introduction: The Most Expensive Function Call in Your Stack

For most of your career, a remote dependency has been something with a contract: a REST endpoint with an OpenAPI schema, a JDBC driver returning typed rows, a Kafka topic with an Avro schema. You know what you send and you know, to a high degree of certainty, what comes back. A large language model (LLM) breaks almost every one of those assumptions. Its input is free text (or images, audio, documents) chopped into tokens; its output is generated one token at a time by sampling from a probability distribution; the same input can produce different outputs; the response can take anywhere from a few hundred milliseconds to several minutes; and you pay per token, in both directions.

Yet LLMs solve a class of problem that no amount of clever Spring code could solve before: turning unstructured language into structured decisions. Classifying a support ticket by intent, extracting fields from a contract PDF, summarising a 40-page incident report, translating a business question into SQL, deciding which internal API to call next — these were previously either impossible or required a dedicated ML team with labelled data and months of work. Now they are a prompt and an HTTPS call away. That shift is why "AI engineering" exists as a discipline: the model is a commodity component, and the engineering work is everything around it.

This chapter is the foundation for the rest of Part 8. We will not train a frontier model — you never will, and neither will your employer — but you need to understand how they are trained, because training explains behaviour. A model that was rewarded for sounding helpful will confidently produce plausible-looking nonsense when it does not know the answer. A model whose tokenizer was built mostly on English text will cost you more, and perform worse, on Hindi or Japanese. A model that attends to all previous tokens on every step will slow down and get more expensive as the conversation grows. These are not bugs in a particular vendor's product; they are properties of the architecture.

Bridging from Java & Spring Boot

What you already know
You have integrated slow, flaky, metered third-party APIs: payment gateways, address validation, SMS providers. You wrapped them in a RestClient or WebClient, added Resilience4j timeouts, retries and circuit breakers, cached aggressively, and tracked cost per call. You have also used Elasticsearch, where text is analysed into tokens and scored — conceptually close to how an LLM sees text.
Why that is not enough
An LLM call is a remote dependency whose output is probabilistic. Retrying the same request can yield a different answer; "success" (HTTP 200) does not mean the answer is correct; latency scales with how much the model writes; and cost scales with how much text you send. The contract is a natural-language instruction, not a schema, so you cannot unit-test it the way you test a @Service. You also cannot reason about failure modes like hallucination, truncation at the context limit, or token-count blow-ups without knowing how the model works inside.
The modern approach
Treat the model as a stochastic, expensive function with known mechanics: estimate tokens before you call, budget context deliberately, choose decoding behaviour on purpose, stream output to hide latency, constrain outputs with schemas, and evaluate quality statistically rather than with assertions. Know which levers you control (prompt, context, decoding, model choice) and which you do not (weights, tokenizer, training data).
Where Python and Go fit
Python is where the model ecosystem lives: tokenizers, Hugging Face transformers, evaluation tooling and every research paper's reference code. You will prototype and analyse in Python. Go is a strong fit for the infrastructure around models — LLM gateways, token-counting proxies, rate limiters — because it handles many concurrent long-lived streaming connections cheaply. Java/Spring remains the natural home for business integration (Spring AI, LangChain4j, the official Anthropic Java SDK).
In production
You will monitor input/output tokens per request, time-to-first-token (TTFT) and time-per-output-token (TPOT), cost per feature, cache hit rates, context-length distributions and truncation (max_tokens) stop reasons — the LLM equivalents of p99 latency and error rate.
Use it when / avoid it when
Use an LLM when the input is unstructured language and an approximate, reviewable answer creates value. Avoid it when a deterministic rule, a SQL query, a regex or a small classifier would do the job — those are cheaper, faster, testable and explainable. "Could a junior engineer write an if statement for this?" is a good first filter.

The rest of the chapter follows the life of a model: how it is built (pretraining and post-training), how it reads (tokenization and embeddings), how it thinks (the transformer, attention, the KV cache), how much it can hold (context windows), and how it speaks (decoding and sampling). Each piece ends with the production consequence, because that is what you will be paged for.

3. Fundamentals: Every Concept You Need Before Going Deeper

3.1 Next-token prediction

Strip away the chat interface and an LLM does exactly one thing: given a sequence of tokens \( x_1, \dots, x_t \), it outputs a probability distribution \( P(x_{t+1} \mid x_1, \dots, x_t) \) over its entire vocabulary — typically 32,000 to a few hundred thousand entries. It does not output "an answer"; it outputs a score for every possible next token. Everything else — conversations, tool calls, JSON — is built by choosing one token from that distribution, appending it, and asking again.

Why should predicting the next token produce something that looks like understanding? Because to predict text well across trillions of tokens of code, textbooks, forums, legal filings and fiction, the cheapest internal strategy is to model the processes that generated the text: grammar, facts, arithmetic patterns, the conventions of a stack trace, the logic of a proof. The model is never told to learn these; they are side-effects of minimising prediction error. That also explains the failure modes: the model learned what plausible text looks like, and plausibility is not truth.

3.2 Autoregressive decoding

Autoregressive means each output becomes part of the next input. Generation is a loop:

  1. Tokenize the prompt into IDs.
  2. Run the model over all prompt tokens to get the distribution for the next position (this first pass is called prefill).
  3. Pick a token from that distribution (the decoding strategy: greedy, sampling, etc.).
  4. Append it, run the model for just that one new position (a decode step), and repeat.
  5. Stop on an end-of-sequence token, a stop sequence, or the max_tokens limit.

Three production consequences follow directly. Output latency is linear in output length: a 2,000-token answer takes roughly 20 times longer to generate than a 100-token answer, so asking for concise output is a performance optimisation. Streaming is natural: tokens exist one at a time, so you can forward them to the user as they are produced, which is why every LLM API supports server-sent events. Errors compound: an early wrong token (a wrong function name, a hallucinated fact) becomes context for everything after it, and the model will usually rationalise rather than retract it.

3.3 Pretraining: data and objective

Pretraining is where nearly all of the compute — and the model's knowledge — goes. The recipe:

  • Data. Trillions of tokens drawn from filtered web crawls (Common Crawl derivatives), books, academic papers, code repositories, and increasingly synthetic data generated by earlier models. Labs invest heavily in deduplication, quality filtering (classifiers that score "educational value" or similarity to reference text), toxicity and PII filtering, and data mixing (what fraction is code vs. maths vs. multilingual text). Data composition is the most closely guarded part of most frontier recipes.
  • Objective. Causal language modelling: for every position in every training sequence, maximise the log-probability the model assigns to the actual next token. Equivalently, minimise cross-entropy loss. No labels are needed — the text is its own supervision, which is why it scales to the whole internet.
  • Result. A base model: an excellent document completer that will happily continue your prompt as if it were a web page. Ask a base model "What is the capital of France?" and it may respond with three more quiz questions, because that is what follows such a line on the web.

Two engineering facts come from pretraining. The model has a knowledge cutoff — it knows nothing after its training data was collected, and it does not reliably know where its cutoff is. And its knowledge is lossy and frequency-weighted: facts seen thousands of times (the syntax of @Transactional) are robust; facts seen once (your company's internal API) are absent or confabulated. That is the core argument for retrieval-augmented generation (Chapter 4).

3.4 Scaling laws

Scaling laws are empirical regularities: as you increase parameters N, training tokens D and compute C, the pretraining loss decreases as a smooth power law. Kaplan et al. (2020) first measured this for transformers; Hoffmann et al. (2022, "Chinchilla") showed that, for a fixed compute budget, many earlier models were too large and undertrained, and that parameters and tokens should grow roughly in proportion — on the order of twenty training tokens per parameter for compute-optimal training. In practice, modern labs deliberately "over-train" smaller models far beyond that ratio, because a smaller model that is cheaper to serve is worth extra one-off training compute when it will answer billions of requests. This is why small open models of a few billion parameters became surprisingly capable.

Why should you, an application engineer, care? Because scaling laws explain the product line-up every provider offers: a large, slow, expensive model; a mid-size workhorse; and a small, fast, cheap one. They share training recipes and differ mainly in scale, so capability differences are smooth, and routing easy requests to the small model (Chapter 5) is a predictable cost lever.

3.5 Post-training: supervised fine-tuning (instruction tuning)

Post-training turns the document completer into an assistant. The first step is supervised fine-tuning (SFT), also called instruction tuning: continue training on tens of thousands to millions of curated examples of the form (instruction, ideal response), formatted with a chat template — special tokens that mark system, user and assistant turns. After SFT, the model has learned the "shape" of being an assistant: answer the question, follow formatting instructions, stop when done.

The chat template matters operationally. When you call a messages API, the provider serialises your system, user and assistant messages into one token sequence using its template. When you self-host an open model, you are responsible for applying the right template — use the wrong one and quality silently degrades. Tool calls and structured outputs are also learned during post-training: the model sees examples of emitting a tool-call block in a specific format, which is why tool-use reliability varies so much between models.

3.6 Preference tuning: RLHF

SFT teaches imitation, but writing ideal answers is expensive and humans are better at comparing answers than writing them. Reinforcement learning from human feedback (RLHF), as described in OpenAI's InstructGPT paper (Ouyang et al., 2022), adds two stages:

  1. Reward model. Sample several responses to each prompt, have human labellers rank them, and train a model to predict a scalar "how much would a human prefer this?" score.
  2. Policy optimisation. Use reinforcement learning (classically PPO) to update the LLM to produce responses the reward model scores highly, with a KL-divergence penalty that keeps it close to the SFT model so it does not drift into gibberish that happens to fool the reward model.

RLHF is why chat models are polite, structured and eager to help. It is also a source of failure modes: sycophancy (agreeing with the user because labellers preferred agreeable answers), verbosity (longer answers were often rated higher), and confident tone regardless of certainty. When your application needs a model to say "I don't know," you are pushing against this training pressure, which is why grounding instructions and evaluation matter so much.

3.7 RLAIF and constitutional approaches

Human preference labels are slow and expensive. Reinforcement learning from AI feedback (RLAIF) replaces some or all human comparisons with judgements from a model following a written set of principles. Anthropic's Constitutional AI paper (Bai et al., 2022) is the best-known example: the model critiques and revises its own outputs against a "constitution," and those AI-generated preferences train the reward signal for harmlessness. For you, the takeaway is practical: the same technique — an LLM judging outputs against a rubric — is what you will use to evaluate your own application (Chapter 5), with the same strengths (scale) and weaknesses (bias toward the judge's own style).

3.8 Direct preference optimisation (DPO)

DPO (Rafailov et al., 2023) showed that the RLHF objective can be optimised directly on preference pairs (prompt, chosen, rejected) with a simple classification-style loss, without training a separate reward model or running an RL loop. It is more stable and far cheaper, which made preference tuning accessible to anyone who can fine-tune a model — including you, with the Hugging Face TRL library (Chapter 3 of this Part). Many open models now use DPO or one of its many variants as part of post-training.

3.9 Reasoning models and test-time compute

Classic chat models answer immediately: the first output token is already part of the answer. Reasoning models are trained to first produce a long internal chain of thought — exploring, checking, backtracking — and only then write the answer. They are typically trained with reinforcement learning on tasks with verifiable rewards (maths problems with known answers, code with unit tests), which rewards whatever reasoning process reaches correct answers. DeepSeek-R1's technical report (2025) documented this openly for an open-weight model.

The economic idea is test-time compute: instead of a bigger model, spend more tokens per request. Accuracy on hard problems rises with the thinking budget, but so do latency and cost — thinking tokens are billed as output tokens. Providers expose this as a knob: Anthropic's current API uses adaptive thinking with an effort level (low through max) rather than a fixed token budget, and returns either a summary of the reasoning or nothing at all rather than the raw chain of thought. 3.10 Tokenization

Models do not see characters or words; they see integer token IDs from a fixed vocabulary. A tokenizer is a deterministic, reversible mapping between text and IDs, trained once before pretraining and frozen forever after. Four families matter:

  • Byte-pair encoding (BPE). Start with individual characters; repeatedly find the most frequent adjacent pair in the training corpus and merge it into a new symbol; stop at the target vocabulary size. Common words become single tokens; rare words split into frequent fragments. You will implement this in §7.
  • Byte-level BPE. Run BPE over UTF-8 bytes instead of Unicode characters (popularised by GPT-2). The base vocabulary is just 256 byte values, so any string — emoji, Devanagari, binary garbage — is encodable with no "unknown" token. OpenAI's tiktoken encodings and most modern LLM tokenizers are byte-level BPE variants.
  • SentencePiece. A library (Kudo & Richardson, 2018) that treats input as a raw stream including spaces (encoded as a visible marker, ▁), so it works for languages without whitespace word boundaries. It supports both BPE and the Unigram algorithm, which starts with a large vocabulary and prunes tokens that least reduce corpus likelihood. Llama 1 and 2, T5 and many multilingual models use SentencePiece.
  • WordPiece. BERT's variant, similar to BPE but choosing merges by likelihood gain. You meet it mostly in older encoder-based embedding and reranking models.

A rule of thumb for English prose with modern tokenizers is roughly four characters, or three-quarters of a word, per token — but treat this as a planning estimate only. Code, JSON, numbers, URLs, UUIDs and non-Latin scripts tokenize very differently, and every provider's tokenizer is different (Anthropic, for instance, does not publish its tokenizer and offers a token-counting API instead; its documentation also notes that tokenizers can change between model generations).

Token counting and cost

Every commercial API bills per token, usually with different prices for input, output, cached input and cache writes, and output tokens cost several times more than input tokens. Token counts therefore drive three things you care about: cost (tokens × price), latency (output tokens dominate generation time; input tokens dominate time-to-first-token for long prompts), and feasibility (whether the request fits in the context window). Practical consequences:

  • Pretty-printed JSON with indentation can cost noticeably more than minified JSON, and verbose key names are paid on every request. Measure with your provider's counter before optimising.
  • Numbers are often split into multi-digit chunks inconsistently, which is one reason models are weak at exact arithmetic — delegate maths to a tool.
  • Long identifiers (UUIDs, hashes, base64 blobs) are token-expensive and carry no semantic value for the model. Strip or shorten them before sending.
  • Switching models can change your token counts for identical text, so re-baseline costs when you migrate.

Multilingual effects

Tokenizers trained on English-heavy corpora fragment other scripts into many more tokens per word. Petrov et al. (2023) measured that the same content can require several times more tokens in some languages than in English across popular tokenizers — and in extreme cases more than ten times. The consequences compound: users of those languages pay more per request, hit context limits sooner, wait longer, and often get lower quality, because the model saw less data in their language and has to reason over longer, less meaningful fragments. If you serve a multilingual user base (for example, Indian languages alongside English), measure token ratios per language early; it can change your cost model and your choice of model.

3.11 Embeddings: token vs. sentence embeddings

Inside the model, the first operation is a lookup: each token ID indexes a row in an embedding matrix, producing a dense vector (a few thousand dimensions in large models). These token embeddings are learned during training; similar tokens end up nearby. As the vectors flow through the transformer layers they become contextual: the vector for "bank" in "river bank" diverges from "bank" in "bank account".

A sentence (or text) embedding is different: a single fixed-size vector representing a whole passage, produced by a model trained specifically so that semantically similar passages map to nearby vectors (typically with contrastive learning on pairs of related texts, as in Sentence-BERT). You get one by calling an embedding model — a separate, much cheaper model than the chat LLM — and you store those vectors in a vector database for semantic search. Do not confuse the two: you cannot meaningfully average a chat model's token vectors and expect good retrieval. Chapter 4 covers choosing and operating embedding models.

3.12 The transformer, recapped for engineers

Part 7 Chapter 3 derives the transformer in full; here is the operational summary. Modern LLMs are decoder-only transformers: a stack of identical blocks (dozens to over a hundred), each containing two sub-layers with residual connections and normalisation:

  • Causal self-attention: every position computes a weighted mixture of information from all earlier positions (never later — that would be cheating at next-token prediction). This is how "it" gets linked to the noun it refers to, or a closing bracket to its opening one.
  • Feed-forward network (MLP): a per-position transformation where much of the model's factual "storage" is thought to live. In mixture-of-experts (MoE) models, this sub-layer is replaced by many expert MLPs and a router that sends each token to only a few of them, so a model can have a very large total parameter count while activating only a fraction per token.

Positional information is injected with schemes such as rotary position embeddings (RoPE), which also determine how well a model extrapolates to sequences longer than it was trained on. Attention variants such as multi-query and grouped-query attention (GQA) share key/value projections across heads to shrink the KV cache — a serving optimisation you will see in model cards.

3.13 Self-attention and the KV cache

In self-attention, each position produces three vectors: a query ("what am I looking for?"), a key ("what do I contain?") and a value ("what will I contribute if selected?"). A position's output is the softmax-weighted average of all earlier values, weighted by how well its query matches each key. The Java analogy is a fuzzy Map lookup: instead of an exact get(key) returning one value, you get a weighted blend of every value whose key resembles your query.

During generation, the keys and values for earlier positions never change — position 5's key is the same whether you are generating token 6 or token 600. So inference engines cache them: the KV cache. Each decode step computes Q, K, V only for the new token, appends K and V to the cache, and attends over the cache. Without it, generating n tokens would redo all prior work every step. With it, generation is fast, but memory grows linearly with sequence length and batch size — and GPU memory for the KV cache, not compute, is often what limits how many concurrent requests a server can handle. §6 shows how to size it; Chapter 3 covers how vLLM's PagedAttention manages it like virtual memory pages.

3.14 Context windows

The context window is the maximum number of tokens (input plus output) a model can process in one request. It is bounded by the positions the model was trained on and by the memory and compute cost of attention. In late 2026 the largest frontier windows are around one million tokens, with output caps far lower (Anthropic's current models, for example, list 1M-token context and up to 128K output tokens). Three facts temper the marketing number:

  • Lost in the middle. Liu et al. (2023) showed that models use information at the beginning and end of a long context more reliably than information buried in the middle. Newer models have improved substantially, but "fits in the window" still does not mean "will be used correctly." Put the most important instructions and evidence near the start or end, and evaluate on realistic long inputs.
  • Effective vs. advertised length. Simple "needle in a haystack" retrieval tests are easy; benchmarks such as RULER (Hsieh et al., 2024) that require multi-hop reasoning over long inputs show performance degrading well before the advertised limit for many models.
  • Long contexts are expensive. You pay for every input token on every request, and prefill time grows with prompt length (attention cost grows faster than linearly in principle). A chatbot that resends a 200K-token history on every turn is burning money; prompt caching (Chapter 2) and retrieval (Chapter 4) exist largely to avoid this.

3.15 Temperature and sampling

The model outputs logits — unnormalised scores — for every vocabulary entry. A decoding strategy turns them into a chosen token:

  • Greedy: always pick the highest-probability token. Deterministic in theory, prone to repetitive loops in long generations, and often not the best overall sequence.
  • Temperature \(T\): divide logits by \(T\) before the softmax. \(T < 1\) sharpens the distribution (more conservative), \(T > 1\) flattens it (more diverse, more errors), \(T \to 0\) approaches greedy.
  • Top-k: keep only the k most likely tokens, renormalise, sample. A fixed k is too permissive when the model is confident and too restrictive when it is not.
  • Top-p (nucleus): keep the smallest set of tokens whose cumulative probability reaches p (Holtzman et al., 2019). Adapts to the shape of the distribution.
  • Min-p: keep tokens whose probability is at least a fraction of the top token's probability (e.g. 0.05 × pmax). A newer, popular choice in open-model runtimes because it scales the cut-off with the model's confidence.
  • Beam search: keep the b best partial sequences and expand each, choosing by total sequence probability. Standard in translation and speech; rarely used for open-ended chat because it produces bland, repetitive text and multiplies compute.
  • Penalties: frequency/presence/repetition penalties down-weight tokens already generated. Useful against loops in small open models.

Two important caveats for production. First, temperature 0 is not a determinism guarantee: floating-point non-associativity, batching with other users' requests, different GPU kernels and MoE routing can all change logits slightly between calls, and a tiny change can flip an argmax. Second, providers increasingly control sampling for you: reasoning models often fix sampling parameters, and Anthropic's API version 2026-10-21 rejects temperature, top_p and top_k on Messages requests entirely (Claude 4.7 and later models already accepted only the defaults). 4. Internal Working: The Life of One Request

Let us follow a single request — "Summarise this incident report" with a 6,000-token report attached — from your RestClient to the GPU and back. Knowing these stages lets you attribute latency correctly and explains the metrics providers expose.

4.1 Serialisation and tokenization

The provider's API gateway authenticates you, applies rate limits, and renders your structured request (system prompt, tool definitions, message list, images) into a single token sequence using the model's chat template. Tool schemas are converted into text the model was trained to read, which is why defining twenty tools costs input tokens on every request even when none is used. The text is tokenized; images are converted into patches and then into embedding vectors that occupy context positions just like tokens.

4.2 Scheduling and continuous batching

Your request joins a queue on an inference server. Modern servers use continuous (in-flight) batching: rather than waiting for a whole batch to finish, the scheduler adds new requests and evicts finished ones at every decode step, so the GPU is always working on as many sequences as memory allows. This is why your latency depends on other customers' traffic, and why providers sell priority tiers and enforce rate limits in tokens per minute rather than requests per second.

4.3 Prefill: compute-bound

The server runs the full model over all 6,000 input tokens in parallel, producing logits for the first output position and populating the KV cache for every layer. Prefill is compute-bound: lots of matrix multiplications that GPUs do efficiently. Its duration dominates time to first token (TTFT), and it scales with prompt length. Prompt caching helps precisely here: if the first 5,000 tokens match a cached prefix, the server loads their KV entries instead of recomputing them, cutting TTFT and cost.

4.4 Decode: memory-bandwidth-bound

Each subsequent step processes a single new token per sequence. The arithmetic is small, but the server must stream every model weight and the sequence's entire KV cache from GPU memory for every step. Decode is therefore memory-bandwidth-bound, and its speed is measured as time per output token (TPOT) or its inverse, output tokens per second. Batching many sequences together amortises the weight reads, which is why throughput-oriented servers batch aggressively and why a lightly loaded self-hosted server can feel faster per user than a busy one.

4.5 Sampling, constraints and stopping

For each step, the logits pass through a processing pipeline: temperature scaling, top-k/top-p/min-p truncation, repetition penalties, and — if you requested a JSON schema or a strict tool call — a grammar mask that sets the logits of tokens that would violate the schema to negative infinity (constrained decoding, Chapter 2). A token is selected, checked against stop conditions (end-of-turn token, stop sequences, max_tokens), detokenized into bytes, and — if you are streaming — flushed to you as a server-sent event. Note that a single token may be an incomplete UTF-8 character; streaming clients must buffer bytes until a character is complete, which the official SDKs do for you.

4.6 Response and accounting

When generation stops, the API returns the content blocks and a stop_reason (end of turn, max tokens, a stop sequence, a tool call, or a refusal) plus a usage object with input, output, cache-read and cache-write token counts. Those two fields are the most important observability data you will ever log for an LLM call: stop_reason = max_tokens means the answer was truncated (and any JSON is probably broken); the usage numbers are your bill.

5. Architecture: Diagrams and Interactive Explorations

5.1 From raw text to deployed assistant

Reading the diagram: the left half (data, tokenizer, pretraining) produces raw capability and knowledge and consumes the vast majority of compute; the middle (SFT, preference tuning, reasoning RL) shapes behaviour — instruction following, tone, tool use, refusal style, reasoning habits; the right half is engineering for deployment. Note that the tokenizer is fixed before pretraining: it cannot be changed later without retraining, which is why tokenizer inefficiencies for certain languages persist through a model's lifetime. When a provider ships a "new version" of a model, changes can occur at any stage, so treat every model upgrade as a behavioural change requiring re-evaluation.

5.2 Inference request sequence

Reading the diagram: your service sees a single HTTP response, but it is really a long-lived stream whose first event arrives after prefill and whose subsequent events arrive at the decode rate. The final event carries the stop reason and token usage, so a client that aborts the stream early loses that accounting data — log what you have when you cancel. Because the stream can stay open for minutes, your HTTP client's read timeout must be much longer than for a normal REST call, or configured as an idle timeout between events.

5.3 A decoder block

Reading the diagram: each block adds ("residual") the output of attention and then of the MLP back onto its input, so information flows along a "residual stream" that every layer reads and writes. Only the attention sub-layer mixes information between positions, and only it needs the KV cache. After the last block, a final projection (the LM head) maps each position's vector to one logit per vocabulary entry. Full derivations — scaling by \(\sqrt{d_k}\), multi-head projections, positional encodings — are in Part 7 Chapter 3.

5.4 Interactive: byte-pair encoding

What to try: start with a short English sentence and step through the merges: frequent pairs such as "t"+"h" and then "th"+"e" merge first, so common words collapse into a single token. Now paste repeated technical vocabulary ("transaction transactional transactions") and see how a shared stem becomes one token with suffixes left over. Finally, type text in a script that is absent from the training text and observe it staying fragmented — that is the multilingual cost penalty from §3.10, in miniature.

5.5 Interactive: self-attention

What to try: pick a sentence with a pronoun ("The service crashed because it ran out of memory") and inspect the row for "it": the attention weights show how strongly that position draws from each earlier word. Rows sum to 1 because they are softmax outputs. In a causal LLM, the upper triangle (attention to future tokens) would be masked to zero; every row you inspect is a weighted lookup into the KV cache described in §3.13.

5.6 Interactive: temperature, top-k and top-p

What to try: set temperature to 0.2 and watch nearly all probability mass collapse onto the top token — effectively greedy. Raise it to 1.5 and see long-tail tokens become plausible picks. Then apply top-p 0.9 at high temperature: the tail is cut off, giving diversity without nonsense. Compare with top-k 3 on a flat distribution (where the model is unsure) versus a peaked one (where it is confident) to see why top-p adapts better than a fixed k.

6. The Math: Probabilities, Loss, Scaling and Memory

6.1 Softmax with temperature

Intuition: the model produces a raw score per token; softmax turns scores into probabilities that sum to 1, exaggerating differences exponentially; temperature controls how much exaggeration. For logits \(z_i\) and temperature \(T > 0\):

\[ p_i = \frac{\exp(z_i / T)}{\sum_{j=1}^{|V|} \exp(z_j / T)} \]

Worked example: logits \([2.0, 1.0, 0.1]\). At \(T=1\): \(e^{2}=7.39, e^{1}=2.72, e^{0.1}=1.11\), sum 11.22, so \(p \approx [0.66, 0.24, 0.10]\). At \(T=0.5\) the logits become \([4, 2, 0.2]\): \(54.6, 7.39, 1.22\), so \(p \approx [0.87, 0.12, 0.02]\). At \(T=2\): \([1, 0.5, 0.05]\) gives \(p \approx [0.50, 0.30, 0.19]\). Halving the temperature made the top token much more dominant; doubling it nearly equalised the options.

6.2 Top-p and min-p, formally

Sort probabilities in descending order \(p_{(1)} \ge p_{(2)} \ge \dots\). Top-p keeps the smallest prefix set \(S\) such that \(\sum_{i \in S} p_{(i)} \ge p\), then renormalises. Min-p keeps \(\{ i : p_i \ge \alpha \cdot p_{(1)} \}\). With \(p = [0.66, 0.24, 0.10]\): top-p 0.9 keeps the first two tokens (0.66 + 0.24 = 0.90), renormalised to \([0.73, 0.27]\); min-p with \(\alpha = 0.2\) keeps tokens with probability at least 0.132 — again the first two.

6.3 Training loss and perplexity

Pretraining minimises the average negative log-likelihood of the true next token — cross-entropy:

\[ \mathcal{L}(\theta) = -\frac{1}{N}\sum_{t=1}^{N} \log p_\theta(x_t \mid x_{<t}) \]

Perplexity is \(\exp(\mathcal{L})\): the effective number of equally likely choices the model is "torn between" at each step. A perplexity of 8 means the model is, on average, as uncertain as if choosing uniformly among 8 tokens. Perplexity is comparable only between models with the same tokenizer, since a different vocabulary changes what "one step" means — a subtle trap when reading model comparisons.

6.4 Scaling laws and training compute

A widely used approximation for training compute of a dense transformer is \(C \approx 6ND\) floating-point operations (forward and backward passes over \(D\) tokens with \(N\) parameters). Chinchilla fitted loss as

\[ L(N, D) = E + \frac{A}{N^{\alpha}} + \frac{B}{D^{\beta}} \]

where \(E\) is irreducible loss (the entropy of natural text) and the two other terms are penalties for too few parameters and too few tokens; the fitted exponents were both roughly 0.3. Minimising \(L\) under fixed \(C\) yields \(N\) and \(D\) growing in roughly equal proportion — the "about 20 tokens per parameter" heuristic. Back-of-envelope Illustrative: a 7-billion-parameter model trained compute-optimally would see about 140 billion tokens, costing \(6 \times 7\times10^{9} \times 1.4\times10^{11} \approx 5.9\times10^{21}\) FLOPs. Modern small open models are trained on trillions of tokens — tens of times past this point — because inference cost, not training cost, dominates their lifetime economics.

6.5 Attention cost

For a sequence of length \(n\) and head dimension \(d_k\), attention computes

\[ \text{Attention}(Q,K,V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}} + M\right)V \]

where \(M\) is the causal mask (\(-\infty\) above the diagonal). The \(QK^\top\) matrix has \(n^2\) entries, so naive prefill attention costs \(O(n^2 d)\) time; kernels like FlashAttention avoid materialising the full matrix in slow memory, making memory use roughly linear, but the arithmetic remains quadratic. During decode with a KV cache, each new token costs \(O(n d)\) for attention, so generating \(m\) tokens after an \(n\)-token prompt costs roughly \(O(m \cdot n \cdot d)\) for attention plus \(O(m \cdot N)\) for the rest of the model.

6.6 Sizing the KV cache

The KV cache stores one key and one value vector per layer, per KV head, per token:

\[ \text{bytes per token} = 2 \times L \times n_{kv} \times d_{head} \times b \]

with \(L\) layers, \(n_{kv}\) key/value heads, head dimension \(d_{head}\), and \(b\) bytes per element. Worked example Illustrative for a model shaped like many ~8B open models (32 layers, 8 KV heads via GQA, head dimension 128, FP16 so \(b = 2\)): \(2 \times 32 \times 8 \times 128 \times 2 = 131{,}072\) bytes = 128 KiB per token. A single 32K-token conversation needs 4 GiB of KV cache; 32 such concurrent conversations need 128 GiB — more than one 80 GB GPU, before counting the ~16 GB of weights. Without GQA (32 KV heads instead of 8) it would be four times worse. This arithmetic is why long-context self-hosting is expensive, why KV-cache quantization (FP8) exists, and why providers charge more for long prompts.

6.7 Cost arithmetic for an API workload

For a feature with \(R\) requests per day, average input \(I\) tokens, cache-read fraction \(h\), output \(O\) tokens, and prices \(p_{in}, p_{cache}, p_{out}\) per million tokens:

\[ \text{daily cost} = \frac{R}{10^6}\Big( I\,(1-h)\,p_{in} + I\,h\,p_{cache} + O\,p_{out} \Big) \]

Worked example Illustrative: 200,000 requests/day, 3,000 input tokens of which 2,500 are a cacheable system prompt and tool definitions (\(h \approx 0.83\)), 300 output tokens, with hypothetical prices \(p_{in}=\$2\), \(p_{cache}=\$0.20\), \(p_{out}=\$10\) per million. Uncached input: \(0.2 \times 500 \times 2 = \$200\); cached input: \(0.2 \times 2{,}500 \times 0.2 = \$100\); output: \(0.2 \times 300 \times 10 = \$600\). Total about \$900/day. Without caching the input term would be \$1,200, giving \$1,800/day. Note that output dominates even though it is a tenth of the tokens: shorter answers are usually the biggest cost lever. (Real prices vary by model and change often; always pull them from the provider's pricing page.) Cache writes typically cost a premium over normal input, so include that term when the cache churns.

6.8 Back-of-envelope latency

If a model streams at around 50–100 output tokens per second for a single request (a common order of magnitude for hosted mid-size models; measure your own) then a 1,000-token answer takes 10–20 seconds to finish. TTFT for a short prompt is often well under a second, but can grow to many seconds for very long prompts or when reasoning tokens are generated before the visible answer. Illustrative These numbers make the case for streaming in any user-facing feature, and for asynchronous job patterns (queue + callback) for anything that may exceed an HTTP gateway's timeout.

7.1 Byte-pair encoding from scratch (Python)

Implementing BPE once removes all mystery from "tokens." This trainer works on UTF-8 bytes (byte-level BPE), learns merges, and encodes/decodes text losslessly.

"""Minimal byte-level BPE trainer/encoder. Educational, not optimised."""
from collections import Counter


def get_pair_counts(ids: list[int]) -> Counter:
    return Counter(zip(ids, ids[1:]))


def merge(ids: list[int], pair: tuple[int, int], new_id: int) -> list[int]:
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and (ids[i], ids[i + 1]) == pair:
            out.append(new_id)
            i += 2
        else:
            out.append(ids[i])
            i += 1
    return out


class ByteBPE:
    def __init__(self) -> None:
        self.merges: dict[tuple[int, int], int] = {}
        self.vocab: dict[int, bytes] = {i: bytes([i]) for i in range(256)}

    def train(self, text: str, vocab_size: int, verbose: bool = False) -> None:
        assert vocab_size >= 256
        ids = list(text.encode("utf-8"))
        for new_id in range(256, vocab_size):
            counts = get_pair_counts(ids)
            if not counts:
                break
            pair, freq = counts.most_common(1)[0]
            if freq < 2:
                break  # nothing worth merging
            ids = merge(ids, pair, new_id)
            self.merges[pair] = new_id
            self.vocab[new_id] = self.vocab[pair[0]] + self.vocab[pair[1]]
            if verbose:
                print(f"merge {new_id}: {self.vocab[new_id]!r} (seen {freq}x)")

    def encode(self, text: str) -> list[int]:
        ids = list(text.encode("utf-8"))
        while len(ids) >= 2:
            counts = get_pair_counts(ids)
            # apply the earliest-learned merge first, exactly as in training
            pair = min(counts, key=lambda p: self.merges.get(p, float("inf")))
            if pair not in self.merges:
                break
            ids = merge(ids, pair, self.merges[pair])
        return ids

    def decode(self, ids: list[int]) -> str:
        return b"".join(self.vocab[i] for i in ids).decode("utf-8", errors="replace")


if __name__ == "__main__":
    corpus = (
        "the transaction manager commits the transaction. "
        "transactional outbox patterns keep transactions consistent. "
    ) * 50
    bpe = ByteBPE()
    bpe.train(corpus, vocab_size=300, verbose=True)
    for sample in ["the transactional outbox", "नमस्ते दुनिया", "transaction-id 9f3c2a"]:
        ids = bpe.encode(sample)
        assert bpe.decode(ids) == sample
        print(f"{sample!r}: {len(sample)} chars -> {len(ids)} tokens")

Run it and you will see English words from the corpus compress to one or two tokens, while the Hindi greeting (never seen in training) stays at one token per UTF-8 byte — three bytes per Devanagari character. That is exactly the multilingual penalty in production tokenizers, just exaggerated by a tiny corpus.

7.3 Implementing the decoding strategies (Python)

"""Greedy, temperature, top-k, top-p and min-p over a logits vector."""
import numpy as np

rng = np.random.default_rng(42)


def softmax(z: np.ndarray, temperature: float = 1.0) -> np.ndarray:
    if temperature <= 0:
        raise ValueError("use greedy() for temperature 0")
    z = z / temperature
    z = z - z.max()  # numerical stability: exp of large numbers overflows
    e = np.exp(z)
    return e / e.sum()


def greedy(logits: np.ndarray) -> int:
    return int(np.argmax(logits))


def top_k_filter(p: np.ndarray, k: int) -> np.ndarray:
    keep = np.argsort(p)[-k:]
    out = np.zeros_like(p)
    out[keep] = p[keep]
    return out / out.sum()


def top_p_filter(p: np.ndarray, top_p: float) -> np.ndarray:
    order = np.argsort(p)[::-1]
    cumulative = np.cumsum(p[order])
    cutoff = int(np.searchsorted(cumulative, top_p)) + 1  # smallest prefix reaching top_p
    out = np.zeros_like(p)
    out[order[:cutoff]] = p[order[:cutoff]]
    return out / out.sum()


def min_p_filter(p: np.ndarray, min_p: float) -> np.ndarray:
    out = np.where(p >= min_p * p.max(), p, 0.0)
    return out / out.sum()


def sample(logits, temperature=1.0, top_k=None, top_p=None, min_p=None) -> int:
    if temperature == 0:
        return greedy(logits)
    p = softmax(np.asarray(logits, dtype=np.float64), temperature)
    if top_k is not None:
        p = top_k_filter(p, top_k)
    if top_p is not None:
        p = top_p_filter(p, top_p)
    if min_p is not None:
        p = min_p_filter(p, min_p)
    return int(rng.choice(len(p), p=p))


if __name__ == "__main__":
    vocab = ["Paris", "paris", "Lyon", "France", "the", "banana"]
    logits = np.array([6.0, 3.5, 2.0, 1.5, 0.5, -2.0])
    for t in (0.3, 1.0, 1.8):
        print(f"T={t}:", dict(zip(vocab, np.round(softmax(logits, t), 3))))
    for settings in ({"temperature": 0}, {"temperature": 1.5},
                     {"temperature": 1.5, "top_p": 0.9}, {"temperature": 1.5, "min_p": 0.1}):
        picks = [vocab[sample(logits, **settings)] for _ in range(1000)]
        counts = {w: picks.count(w) for w in vocab if picks.count(w)}
        print(settings, counts)

7.5 A token-budget guard in Spring Boot (Java)

In production, check that a request fits your budget before sending it: oversized prompts fail with a 400 after you have already paid latency, or silently blow your cost model. This service uses the official Anthropic Java SDK's token-counting endpoint and rejects or trims requests that exceed a per-route budget.

package com.example.llm;

import com.anthropic.client.AnthropicClient;
import com.anthropic.client.okhttp.AnthropicOkHttpClient;
import com.anthropic.models.messages.MessageCountTokensParams;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.stereotype.Service;

import java.util.List;

// Maven: com.anthropic:anthropic-java (3.x, Version-sensitive · checked Nov 2026)
@Configuration
class AnthropicConfig {
    @Bean
    AnthropicClient anthropicClient() {
        return AnthropicOkHttpClient.fromEnv(); // reads ANTHROPIC_API_KEY
    }
}

class TokenBudgetExceededException extends RuntimeException {
    TokenBudgetExceededException(long actual, long budget) {
        super("Prompt needs " + actual + " input tokens; budget is " + budget);
    }
}

@Service
public class TokenBudgetGuard {
    private final AnthropicClient client;
    private final String model;
    private final long maxInputTokens;

    public TokenBudgetGuard(AnthropicClient client,
                            @Value("${llm.model:claude-sonnet-5-5}") String model,
                            @Value("${llm.max-input-tokens:50000}") long maxInputTokens) {
        this.client = client;
        this.model = model;
        this.maxInputTokens = maxInputTokens;
    }

    public long count(String system, String userText) {
        return client.messages().countTokens(
                MessageCountTokensParams.builder()
                        .model(model)
                        .system(system)
                        .addUserMessage(userText)
                        .build())
                .inputTokens();
    }

    /** Throws if the prompt exceeds budget; callers map this to HTTP 413 or trim and retry. */
    public long enforce(String system, String userText) {
        long tokens = count(system, userText);
        if (tokens > maxInputTokens) {
            throw new TokenBudgetExceededException(tokens, maxInputTokens);
        }
        return tokens;
    }

    /** Keeps the most recent documents that fit; older context is dropped first. */
    public List<String> fitNewestFirst(String system, String question, List<String> docsNewestFirst) {
        var kept = new java.util.ArrayList<String>();
        for (String doc : docsNewestFirst) {
            kept.add(doc);
            String candidate = String.join("\n\n", kept) + "\n\nQuestion: " + question;
            if (count(system, candidate) > maxInputTokens) {
                kept.remove(kept.size() - 1);
                break;
            }
        }
        return kept;
    }
}

Calling the counter once per document is simple but chatty; in a hot path, cache counts per document hash, or estimate locally with a conservative characters-per-token ratio and call the counter only near the boundary. Map TokenBudgetExceededException to an HTTP 413 in a @RestControllerAdvice so clients get a clear error instead of an opaque upstream 400.

7.6 A fast, conservative estimator for a gateway (Go)

An LLM gateway often needs to reject obviously oversized requests in microseconds, without a network call. A deliberately pessimistic heuristic is good enough as a first gate; the exact count is the provider's.

package main

import (
	"fmt"
	"unicode"
	"unicode/utf8"
)

// EstimateTokens returns a pessimistic token estimate: ASCII text at ~3 chars/token,
// digits and punctuation counted heavily, and non-ASCII runes at ~1 token each.
// Calibrate the constants against your provider's counter on real traffic.
func EstimateTokens(s string) int {
	var ascii, digitsPunct, nonASCII int
	for _, r := range s {
		switch {
		case r >= utf8.RuneSelf:
			nonASCII++
		case unicode.IsDigit(r) || unicode.IsPunct(r):
			digitsPunct++
		default:
			ascii++
		}
	}
	return ascii/3 + digitsPunct/2 + nonASCII + 4 // +4 for message framing
}

func main() {
	for _, s := range []string{
		"The payment service timed out while calling the fraud check API.",
		"भुगतान सेवा का समय समाप्त हो गया",
		`{"orderId":"9f3c2a7e-1b44-4c1e-9a0b-6d2f8e3c1a77","qty":2}`,
	} {
		fmt.Printf("%4d est. tokens  %q\n", EstimateTokens(s), s)
	}
}

Use the estimate to fail fast and to choose a route (for example, send very long inputs to a model with a larger window or to a summarise-first pipeline), and record both estimated and actual usage so you can recalibrate the constants.

8. Applications: How Teams Use These Foundations Day to Day

Foundational knowledge pays off in mundane engineering decisions far more often than in research. Patterns that show up repeatedly in production teams Opinion:

  • Capacity and cost planning. Before a feature launches, teams sample real inputs, count tokens with the target model's counter, estimate output length, and multiply by traffic — the formula in §6.7. This turns "will this be expensive?" into a spreadsheet the finance partner can read, and it frequently changes the design (cache the static prefix, summarise history, shorten answers).
  • Choosing reasoning effort per route. A support assistant might use low effort for intent classification, medium for drafting replies, and high effort for a nightly job that analyses escalations. The knowledge that thinking tokens are output tokens — the expensive kind — keeps this decision grounded.
  • Prompt layout for long contexts. Knowing about position effects ("lost in the middle"), teams place instructions at the start, the user's question at the end, and rank retrieved evidence so the most relevant chunks are not buried in the middle.
  • Streaming everywhere users wait. Because output time is linear in length, any interactive feature streams tokens over SSE or WebSocket, and server-to-server calls with long outputs move to asynchronous job patterns.
  • Multilingual budgeting. Products serving non-English markets measure tokens-per-character per language and sometimes select models with more efficient tokenizers for those languages, or translate-then-process when quality allows.
  • Self-hosting decisions. Teams considering open models size GPU memory with the KV-cache formula from §6.6 to decide how many concurrent long conversations a node can serve — the dominant cost driver for self-hosting.
  • Embeddings for search, not the chat model. Teams use cheap embedding models for semantic search, clustering and deduplication, reserving the chat LLM for generation — orders of magnitude cheaper per document.
  • Reproducibility engineering. Instead of relying on temperature 0, teams store the exact prompt, model ID, parameters and output for every call (for audit and debugging), cache results for identical inputs, and evaluate with multiple samples to measure variance.

9. Case Studies: What Published Work Shows

Each case below is drawn from a primary source you can read. Where a number is quoted, it is the authors' own claim.

9.1 Chinchilla: a smaller model trained on more data wins

Verified DeepMind's "Training Compute-Optimal Large Language Models" (Hoffmann et al., 2022) trained over 400 models to fit the relationship between parameters, tokens and loss. Their 70B-parameter Chinchilla, trained on about 1.4 trillion tokens with the same compute as their earlier 280B-parameter Gopher, outperformed Gopher across a large range of benchmarks. Lesson for engineers: parameter count is a poor proxy for capability; training data and recipe matter as much. When you compare models, compare measured performance on your task, not size. (arXiv:2203.15556)

9.2 Tokenizer unfairness across languages

Verified Petrov, La Malfa, Torr and Bibi (NeurIPS 2023), "Language Model Tokenizers Introduce Unfairness Between Languages," measured how many tokens popular tokenizers need for the same parallel text in different languages, finding large disparities — some languages needing many times more tokens than English for the same content, which translates directly into higher cost, higher latency and less usable context. Lesson: if you operate in India, Southeast Asia, or any non-English market, your per-request cost model must be per language. (arXiv:2305.15425)

9.3 Lost in the middle

Verified Liu et al. (2023, published in TACL 2024) tested multi-document question answering and key-value retrieval while moving the relevant information to different positions in a long input. Performance was highest when the relevant document was at the beginning or end of the context and dropped notably when it was in the middle — even for models marketed for long contexts. Lesson: long windows are not free retrieval; order your context and keep it lean. Later models have reduced the effect, so re-test on your model rather than assuming either way. (arXiv:2307.03172)

9.4 Character.AI: the KV cache is the bill

Verified In a June 2024 engineering post, "Optimizing AI Inference at Character.AI," the company described serving very long chat histories by attacking KV-cache size: multi-query attention in every layer, interleaving local (sliding-window) and global attention layers, and sharing KV caches across neighbouring layers — together reported to shrink the cache by more than 20x — plus keeping conversation KV caches in host memory between turns so most turns avoid recomputing the prefix (they reported a 95% cache rate). Lesson: the memory arithmetic in §6.6 is not academic; at chat scale it dominates serving cost, and prefix reuse across turns is the same idea as provider-side prompt caching. (Character.AI research blog)

9.5 Why temperature 0 is not deterministic

Verified In "Defeating Nondeterminism in LLM Inference" (Thinking Machines Lab, September 2025), Horace He and colleagues argue that the main user-visible cause of nondeterminism at temperature 0 is not GPU concurrency per se but inference kernels that are not batch-invariant: the numeric result for your request depends on how many other requests share the batch, which changes with server load. They released batch-invariant kernels that make inference reproducible at some throughput cost. Lesson: on a shared hosted API, you cannot control batch composition, so treat outputs as samples and design for variance. (Thinking Machines blog)

9.6 DeepSeek-R1: reasoning from reinforcement learning

Verified DeepSeek's January 2025 report described R1-Zero, trained with large-scale reinforcement learning directly on a base model using rule-based rewards (answer correctness and format), which developed long chains of reasoning, self-verification and reflection without supervised reasoning examples; the released R1 added a small amount of cold-start SFT data to improve readability. They also distilled R1's reasoning into smaller open models. Lesson: "reasoning" is a trained behaviour paid for at inference time in tokens; distillation can move some of it into cheaper models. (arXiv:2501.12948)

12. Common Mistakes, Misconceptions and Production Failures

  • "Temperature 0 makes it deterministic." It reduces variance but does not eliminate it on shared infrastructure (§9.5), and some current APIs reject the parameter outright. Tests that assert exact output strings will flake.
  • Estimating Claude or Gemini tokens with tiktoken. Different tokenizers, different counts. Use each provider's counter or the usage field from real responses.
  • Ignoring stop_reason. A response truncated at max_tokens looks like success (HTTP 200) but contains half an answer or invalid JSON. Always check it, alert on it, and size max_tokens generously for structured output.
  • Treating the context window as memory. Models are stateless between API calls; "memory" is whatever you resend. Resending ever-growing histories leads to cost explosions and eventually hard failures when the window is exceeded.
  • Assuming "fits in context" means "will be used." Burying the critical instruction in the middle of a 100K-token prompt is a reliability bug.
  • Forgetting the chat template when self-hosting. Feeding raw text to an instruction-tuned open model without its template yields degraded, rambling output that teams misdiagnose as "the model is bad."
  • Asking LLMs to do arithmetic, counting or character manipulation. Tokenization hides characters and splits numbers; use code or tools for these.
  • Assuming model upgrades are drop-in. A new version can change tokenization, verbosity, refusal behaviour and tool-call formatting. Pin model IDs, and promote new ones through your evaluation suite like any dependency upgrade.
  • Mixing up embedding models. Querying a vector index with vectors from a different embedding model (or version) than the one used to build it returns garbage silently.
  • Unbounded read timeouts or too-short ones. Default HTTP client timeouts (often 30–60 s) kill long generations; infinite timeouts tie up threads forever. Use streaming with idle timeouts and an overall deadline.
  • Believing the model knows today's date or its own version. Inject the current date and relevant facts into the prompt when they matter.

13. Production Engineering: Performance, Security, Reliability

13.1 Performance

  • Measure TTFT and TPOT separately. Record time to first streamed event and tokens per second after it, per model and route. A regression in TTFT points to longer prompts, cache misses or queueing; a regression in TPOT points to provider load or longer reasoning.
  • Cap output. Set max_tokens per route based on observed distributions (for example, p99 of successful outputs plus headroom), and instruct the model on length. Output length is the dominant latency and cost driver.
  • Stabilise prefixes. Keep system prompts and tool definitions byte-identical across requests (no timestamps or request IDs at the top) so prompt caching works; Chapter 2 shows the mechanics.

13.2 Cost governance

  • Log usage (input, output, cache read, cache write) with tenant, feature and model tags; aggregate into cost dashboards and alerts, exactly as you would for cloud spend.
  • Enforce per-tenant token budgets in a gateway (Go is well suited) to contain runaway loops and abusive clients — this is "unbounded consumption," one of the OWASP LLM Top 10 risks covered in Chapter 6.
  • Track tokens per language and per input type so you notice when a new customer segment changes your unit economics.

13.3 Reliability

  • Treat the model as an unreliable remote dependency: timeouts, bounded retries with jittered backoff on 429/5xx/overloaded errors, circuit breakers, and fallbacks to another model or a degraded non-LLM path (Chapter 2 implements this with Resilience4j).
  • Alert on abnormal stop reasons (max_tokens, refusals) as you would on 5xx rates.
  • Pin model versions; canary new ones behind a flag with an evaluation gate.

13.4 Security and privacy

  • Everything in the context window is visible to the model and can influence it — including retrieved documents and tool outputs, which may contain injected instructions. This is the root of prompt injection (Chapter 6 and Part 11 Chapter 5).
  • Tokens you send leave your trust boundary. Classify data, redact PII where possible, and check provider data-retention and regional-processing options before sending regulated data.
  • Model weights encode training data; do not assume a fine-tuned model cannot regurgitate sensitive examples it was trained on.

13.5 Maintainability

  • Externalise model IDs, effort levels and token limits into configuration (application.yml), not code, so swaps are reviewable and reversible.
  • Keep a small, versioned set of representative inputs for each feature; re-run it on every model or prompt change to detect drift. Chapter 5 turns this into a CI regression suite.

Exercise 1 · Foundational

Given logits \([3.0, 2.0, 0.0]\) compute the probabilities at temperatures 1.0 and 0.5. Then state which tokens survive top-p = 0.8 at temperature 1.0.

Solution

At \(T=1\): \(e^3=20.09, e^2=7.39, e^0=1\); sum 28.48 → \([0.705, 0.259, 0.035]\). At \(T=0.5\) logits become \([6, 4, 0]\): \(403.4, 54.6, 1\); sum 459.0 → \([0.879, 0.119, 0.002]\). Top-p 0.8 at \(T=1\): the first token alone gives 0.705 < 0.8, adding the second reaches 0.964 ≥ 0.8, so the first two survive, renormalised to \([0.731, 0.269]\).

Exercise 2 · Intermediate

Extend the ByteBPE class from §7.1 with a save()/load() pair that persists merges as JSON, and add a pre-tokenization step that splits text on whitespace and punctuation before applying BPE (so merges never cross word boundaries). Explain why production tokenizers pre-tokenize.

Solution
import json, re

PRETOKENIZE = re.compile(r"\s?\w+|\s?[^\w\s]+|\s+")

class PretokBPE(ByteBPE):
    def train(self, text, vocab_size, verbose=False):
        chunks = [list(m.encode("utf-8")) for m in PRETOKENIZE.findall(text)]
        for new_id in range(256, vocab_size):
            counts = Counter()
            for ids in chunks:
                counts.update(zip(ids, ids[1:]))
            if not counts:
                break
            pair, freq = counts.most_common(1)[0]
            if freq < 2:
                break
            chunks = [merge(ids, pair, new_id) for ids in chunks]
            self.merges[pair] = new_id
            self.vocab[new_id] = self.vocab[pair[0]] + self.vocab[pair[1]]

    def encode(self, text):
        out = []
        for piece in PRETOKENIZE.findall(text):
            out.extend(super().encode(piece))
        return out

    def save(self, path):
        with open(path, "w") as f:
            json.dump([[a, b, i] for (a, b), i in self.merges.items()], f)

    def load(self, path):
        with open(path) as f:
            for a, b, i in json.load(f):
                self.merges[(a, b)] = i
                self.vocab[i] = self.vocab[a] + self.vocab[b]  # merges are saved in creation order

Pre-tokenization stops merges like "dog." + "The" that span punctuation or words, which would waste vocabulary on accidental combinations and make tokenization of a word depend on its neighbours. GPT-2-style tokenizers use a regex for exactly this; leading spaces are kept attached to words, which is why " the" and "the" are usually different tokens.

Exercise 3 · Intermediate

A self-hosted model has 48 layers, 8 KV heads, head dimension 128, and stores the KV cache in FP8 (1 byte). Your GPU has 80 GB, of which the weights use 40 GB and runtime overhead uses 8 GB. How many concurrent 16K-token sequences can you hold? How does the answer change with FP16 KV cache?

Solution

Bytes per token = 2 × 48 × 8 × 128 × 1 = 98,304 B = 96 KiB. One 16,384-token sequence = 16,384 × 96 KiB = 1.5 GiB. Free memory ≈ 80 − 40 − 8 = 32 GB ≈ 29.8 GiB → about 19 concurrent full-length sequences. With FP16 the cache doubles to 3 GiB per sequence → about 9. In practice paged allocation (vLLM) lets you serve more sequences because most do not reach full length simultaneously, but this worst-case number is what you size for when users can all paste long documents.

Exercise 4 · Advanced

Write a Spring Boot @RestController endpoint POST /estimate that accepts { "texts": [...], "expectedOutputTokens": n, "requestsPerDay": r }, uses the TokenBudgetGuard from §7.5 to count input tokens per text, and returns the p50/p95 input tokens and a projected daily cost using prices loaded from configuration. Explain how you would keep the prices correct over time.

Solution
package com.example.llm;

import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.web.bind.annotation.*;
import java.util.List;

@ConfigurationProperties(prefix = "llm.pricing")
record Pricing(double inputPerMillion, double outputPerMillion) {}

record EstimateRequest(List<String> texts, long expectedOutputTokens, long requestsPerDay) {}
record EstimateResponse(long p50Input, long p95Input, double projectedDailyCost) {}

@RestController
class EstimateController {
    private final TokenBudgetGuard guard;
    private final Pricing pricing;

    EstimateController(TokenBudgetGuard guard, Pricing pricing) {
        this.guard = guard;
        this.pricing = pricing;
    }

    @PostMapping("/estimate")
    EstimateResponse estimate(@RequestBody EstimateRequest req) {
        List<Long> counts = req.texts().stream()
                .map(t -> guard.count("You are a helpful assistant.", t))
                .sorted().toList();
        long p50 = counts.get((int) Math.floor(0.50 * (counts.size() - 1)));
        long p95 = counts.get((int) Math.floor(0.95 * (counts.size() - 1)));
        double perRequest = p50 * pricing.inputPerMillion() / 1e6
                + req.expectedOutputTokens() * pricing.outputPerMillion() / 1e6;
        return new EstimateResponse(p50, p95, perRequest * req.requestsPerDay());
    }
}
// Register with @EnableConfigurationProperties(Pricing.class) on a @Configuration class.

Keep prices in configuration with the model ID and an "as of" date; review them when you change models and reconcile monthly against the provider's invoice or usage/cost reporting API. Using the median for cost is a simplification — for budgets, also compute the mean, since cost is linear in tokens and long-tail inputs matter.

Exercise 5 · Advanced

Design an experiment to measure output variance for a classification prompt on a hosted model whose API does not let you set temperature. What do you measure, how many samples, and how do you turn the result into a production decision?

Solution

Take a labelled set of, say, 200 representative inputs. Call the model k = 5 times per input (randomise order and time of day to vary batch conditions). Measure per-input agreement (fraction of runs matching the majority label), overall accuracy of the majority vote vs. single-run accuracy, and the set of inputs with disagreement. If single-run accuracy and agreement are high (for example, >98% agreement), ship a single call. If disagreement concentrates on ambiguous inputs, either clarify the label definitions in the prompt, constrain output with an enum schema, route low-agreement cases to a human, or use majority voting (self-consistency) for that route and accept the cost multiplier. Re-run the experiment on every model upgrade.

15. Interview Questions

Conceptual Explain how a chat model generates a response, from the moment the request arrives.

The request is rendered with the chat template and tokenized. The server runs prefill over all prompt tokens in parallel, computing logits for the next position and filling the KV cache. It then decodes autoregressively: sample one token from the (processed) distribution, append it, run a single-position forward pass that reuses the KV cache, repeat until an end-of-turn token, stop sequence or max_tokens. Tokens are detokenized and streamed. Prefill drives TTFT and is compute-bound; decode drives per-token latency and is memory-bandwidth-bound.

Conceptual What is the difference between pretraining, SFT, RLHF and DPO?

Pretraining learns language and knowledge by next-token prediction on huge unlabelled corpora, producing a base model. SFT fine-tunes on curated instruction–response pairs so the model behaves like an assistant. RLHF trains a reward model from human preference comparisons and optimises the policy against it with RL under a KL constraint. DPO optimises the same preference objective directly on chosen/rejected pairs with a classification-style loss, avoiding the reward model and RL loop. Reasoning models add RL on verifiable rewards.

Conceptual Why are LLMs bad at counting letters in a word or exact arithmetic?

They operate on subword tokens, not characters, so "strawberry" may be two or three opaque IDs; the model must have memorised spellings. Numbers are split into arbitrary multi-digit chunks, so digit-wise algorithms are not naturally represented. The fix is architectural: give the model a code-execution or calculator tool.

Architecture Your chat feature's cost doubled after customers started pasting long logs. What do you change?

Measure first: token distributions per request, cache hit rates, output lengths. Then: truncate or summarise logs before sending (keep error lines, stack traces, time window around the failure); move static instructions and tool definitions into a cacheable prefix; summarise older conversation turns instead of resending them; cap output with max_tokens and length instructions; route simple questions to a smaller model; enforce per-tenant token budgets at the gateway. Consider retrieval over logs instead of inlining them.

Architecture How would you size GPU memory for self-hosting an open 8B model serving 64 concurrent 8K-token conversations?

Weights: about 16 GB in BF16 (8B × 2 bytes), or roughly 5 GB at 4-bit. KV cache per token for a typical 8B GQA model (32 layers, 8 KV heads, head dim 128, FP16) is 128 KiB; 8K tokens is 1 GiB per conversation; 64 conversations is 64 GiB. Total ≈ 80 GB plus runtime overhead — so either one 80 GB GPU with an FP8 KV cache, or two GPUs. Paged attention lets you oversubscribe because most conversations are shorter than the maximum, but plan for the worst case or apply admission control.

Scenario A test asserting the exact LLM output passes locally and fails in CI intermittently. Why, and what do you do?

LLM outputs are samples; even at temperature 0, hosted inference is not batch-invariant and can vary, and some APIs no longer accept temperature at all. Replace exact-match assertions with property checks: schema validity, required fields, label in an allowed set, semantic checks via an evaluator, or tolerance-based metrics over a dataset. For unit tests of your own code, stub the model client with recorded responses.

Conceptual Explain top-p vs. top-k and when min-p helps.

Top-k keeps a fixed number of candidates regardless of confidence, so it includes junk when the model is sure and cuts good options when it is unsure. Top-p keeps the smallest set covering probability mass p, adapting to the distribution's shape. Min-p keeps tokens with at least a fraction of the top token's probability, which scales the cut-off with confidence and behaves well at higher temperatures; it is popular in open-model runtimes.

Coding Implement nucleus (top-p) filtering over a probability array.

Sort indices by probability descending; take the cumulative sum; find the first index where the cumulative sum reaches p; keep those indices; zero the rest; renormalise. See top_p_filter in §7.3. Edge cases: always keep at least one token; handle ties deterministically; operate in float64 to avoid cumulative sums slightly below 1.0.

Scenario Your product expands to Hindi and Tamil users; latency and cost per request jump. Explain and propose fixes.

English-centric tokenizers fragment Indic scripts into many more tokens per word, so inputs and outputs are longer in tokens, raising cost, TTFT and generation time, and consuming context faster. Measure tokens per character per language; evaluate models whose tokenizers handle these scripts efficiently; keep system prompts in English (cheaper) while instructing responses in the user's language; cap response length; and price per language if needed.

Conceptual Why do reasoning models cost more, and how do you control it?

They generate thinking tokens before the answer, billed as output tokens and adding latency. Control it with provider effort settings (for example, low/medium/high), choose effort per route, set output limits, and evaluate whether higher effort improves your metric enough to justify cost. Use non-reasoning or low-effort settings for simple tasks.

16. Knowledge Check

  • An LLM outputs a probability distribution over the next token; generation is a loop of sampling and appending.
  • Pretraining gives knowledge and capability; SFT and preference tuning (RLHF, RLAIF, DPO) shape behaviour; RL on verifiable rewards produces reasoning models that trade tokens for accuracy.
  • Tokens are the unit of cost, latency and context; tokenizers differ by provider and penalise some languages heavily.
  • Sentence embeddings come from dedicated embedding models and power semantic search; token embeddings are internal.
  • Prefill (compute-bound) sets TTFT; decode (memory-bound) sets per-token latency; output length dominates total latency and usually cost.
  • The KV cache makes decoding fast but its memory grows with sequence length and concurrency — the key self-hosting constraint.
  • Long context windows suffer position effects and cost; fitting is not the same as using.
  • Temperature 0 is not a determinism guarantee, and some APIs now remove sampling knobs; design for variance.

Which phase of inference primarily determines time-to-first-token for a long prompt?

  1. Decode, because it is memory-bandwidth-bound
  2. Detokenization of the output
  3. Prefill over all prompt tokens
  4. Sampling with top-p
Prefill processes the entire prompt before the first output token can be produced, and its cost grows with prompt length. Decode governs per-token latency after the first token; detokenization and sampling are negligible.

A model has 40 layers, 8 KV heads, head dimension 128 and an FP16 KV cache. Roughly how much KV memory does one 10,000-token sequence need?

  1. About 160 MB
  2. About 1.6 GB
  3. About 16 GB
  4. About 160 KB
2 × 40 × 8 × 128 × 2 bytes = 163,840 bytes per token; × 10,000 tokens ≈ 1.64 GB.

Why can the same text cost several times more tokens in Hindi than in English?

  1. Providers charge a surcharge for non-English languages
  2. Hindi text is always longer in characters
  3. The model translates to English internally first
  4. The tokenizer's vocabulary was learned mostly from English-heavy data, so other scripts split into more, smaller tokens
Subword vocabularies favour frequent strings in the tokenizer's training data. Scripts underrepresented there fragment into many tokens (down to raw bytes in byte-level BPE), increasing token counts, cost and latency.

What does DPO remove compared with classic RLHF?

  1. The separately trained reward model and the RL optimisation loop
  2. The need for preference data
  3. Supervised fine-tuning
  4. The reference model
DPO optimises the preference objective directly from chosen/rejected pairs with a closed-form loss. It still needs preference data and uses a reference policy in the loss; SFT usually precedes it.

You need consistent, machine-parseable classification labels from a hosted model whose API rejects the temperature parameter. What is the best primary approach?

  1. Retry until two consecutive outputs match
  2. Set top_k=1 instead
  3. Constrain output with a JSON schema enum, give clear label definitions, and validate
  4. Switch to beam search
Consistency should come from the output contract (schema/enum), clear instructions and validation, not from decoding knobs — which may be unavailable and do not guarantee determinism anyway. top_k is rejected along with temperature on such APIs, and hosted APIs do not offer beam search.

Which statement about the "lost in the middle" finding is most accurate?

  1. Models ignore everything after the first 4,000 tokens
  2. Models tended to use information at the start and end of long inputs more reliably than information in the middle
  3. It only affects models without positional encodings
  4. It means long-context models cannot be used for retrieval
Liu et al. found a U-shaped accuracy curve over the position of relevant information. Newer models improved, but the practical advice — put critical content at the edges and evaluate — still holds.
