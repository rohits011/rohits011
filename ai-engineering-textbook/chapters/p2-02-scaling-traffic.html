Scaling & Traffic: Load Balancers, Proxies, Gateways, Rate Limits

Chapter 1 gave you the numbers; this chapter gives you the machinery that lets a fleet of Spring Boot instances absorb them. We go from "add more pods" to the precise mechanics of how traffic is spread, protected and shaped: why statelessness is the prerequisite for everything, how L4 and L7 balancers really choose a backend, why power-of-two-choices beats round-robin on heterogeneous fleets, what belongs in a gateway and what does not, and how to build a rate limiter that is correct across fifty gateway nodes.

  • Prerequisites: Chapter 1 (Little's Law, percentiles, availability maths). Experience deploying Spring Boot behind a cloud load balancer or Kubernetes Service/Ingress.
  • You will be able to: choose between vertical and horizontal scaling with a cost argument; make services stateless and externalise sessions; select an L4 or L7 balancer and an algorithm for a given workload; configure health checks and graceful draining that drop zero requests on deploy; decide what belongs in an API gateway versus a BFF versus the service; and implement, compare and operate token bucket, leaky bucket, fixed window, sliding log and sliding window counter limiters, locally and on Redis.

1. Introduction: Getting Traffic to the Right Place, Safely

Every system that outgrows one machine faces the same three questions. Where does each request go? What happens to it on the way (authentication, routing, transformation, observation)? And how much of it do we accept before saying no? Load balancers answer the first, reverse proxies and API gateways the second, and rate limiters and load shedders the third. Together they form the traffic layer: the part of the architecture that sits between the internet and your Spring Boot code.

The traffic layer exists because horizontal scaling only works if requests can be spread across interchangeable instances, failing instances can be removed without users noticing, new versions can be rolled out without dropping connections, and abusive or excessive traffic can be stopped before it consumes the capacity that legitimate users need. Get any of these wrong and adding instances does not add capacity: sticky sessions pin load to a few hot instances, a naive algorithm sends requests to a server stuck in a GC pause, a deploy drops a few thousand in-flight requests, or a single misbehaving client consumes the database.

This chapter covers, in order: the scaling decision itself; statelessness and session externalisation; load balancing at layer 4 and layer 7 with every major algorithm and the health-checking and draining machinery around them; reverse proxies (NGINX, Envoy, HAProxy); API gateways (Spring Cloud Gateway, Kong, Envoy-based gateways, AWS API Gateway) and the Backend-for-Frontend pattern; and finally rate limiting in depth, from the five classic algorithms to distributed implementations with Redis and Lua, Bucket4j and Resilience4j in Spring, and golang.org/x/time/rate in Go.

Bridging from Java & Spring Boot

What you already know
You have deployed services behind an AWS ALB or a Kubernetes Ingress, maybe called other services through Spring Cloud LoadBalancer or a @LoadBalanced RestTemplate/WebClient, perhaps used spring-session-data-redis to share HTTP sessions, written a OncePerRequestFilter for auth, and configured a Resilience4j @RateLimiter on an outbound call.
Why that is not enough
Those are mostly defaults chosen by someone else. At scale you must reason about which layer balances (DNS, L4, L7, client-side), which algorithm suits a fleet with uneven instance sizes and long-tailed latencies, how health checks interact with deploys and autoscaling, why per-instance rate limiters are wrong by a factor of the instance count, and why a gateway full of business logic becomes a distributed monolith.
The modern approach
Stateless services with state in purpose-built stores; a cloud L4/L7 balancer or Envoy-family proxy at the edge; an API gateway for cross-cutting edge concerns only (TLS, authN, coarse authZ, routing, quotas, observability); latency-aware algorithms (least-request with power of two choices) for heterogeneous backends; active plus passive health checking; graceful shutdown coordinated with readiness; and rate limiting at multiple tiers with a token bucket at the core and a shared store for global limits.
Where Python and Go fit
Go dominates the proxy and gateway ecosystem's control planes and many data planes (Traefik, Caddy, much of the Kubernetes Gateway API tooling) and ships a high-quality token bucket in golang.org/x/time/rate. Python services sit behind the same proxies; Python is a convenient choice for limiter simulations and for small Redis-backed limiters in FastAPI middleware.
In production
Typical stack: DNS → CDN/WAF → cloud L4 or L7 balancer → API gateway (Spring Cloud Gateway, Kong, Envoy Gateway, or a managed gateway) → Kubernetes Service or service mesh → Spring Boot pods with graceful shutdown. Rate limits are enforced at the edge (per IP, per API key), at the gateway (per tenant/plan), and in services (per expensive operation, e.g. LLM calls).
Use it when / avoid it when
Use a gateway when you have many services or external API consumers needing consistent auth, quotas and routing. Avoid putting business logic, data aggregation for a single UI, or per-request database lookups in a shared gateway. Use distributed rate limiting when limits are contractual (API plans) or protect a shared scarce resource; prefer local limiters when approximate limits suffice, since they add no network hop.

2. History: From DNS Round-Robin to Programmable Proxies

2.1 DNS and hardware appliances (1990s–2000s)

The first web-scale load balancing was DNS round-robin: return several A records and let clients pick. It is crude (no health awareness, at the mercy of resolver caching) but still used today for coarse global distribution. In the late 1990s dedicated appliances from vendors such as F5 (BIG-IP) and Cisco took over, doing layer-4 balancing in specialised hardware and, increasingly, layer-7 features such as SSL termination and cookie persistence.

2.2 Software proxies (2000s)

HAProxy (Willy Tarreau, first released in 2001) and NGINX (Igor Sysoev, first public release 2004) showed that event-driven software on commodity servers could match appliances for most workloads. NGINX's asynchronous architecture was a direct response to the "C10K problem" (handling ten thousand concurrent connections), articulated by Dan Kegel around 1999. Both remain foundational.

2.3 Cloud load balancers and API gateways (2009–2016)

AWS launched Elastic Load Balancing in 2009, followed by the Application Load Balancer (L7) in 2016 and the Network Load Balancer (L4) in 2017. Netflix open-sourced Zuul, a JVM edge gateway, in 2013; many Spring engineers met gateways through Spring Cloud Netflix Zuul. Kong (2015) built a plugin-based gateway on NGINX/OpenResty, and AWS API Gateway launched in 2015. Google published Maglev (NSDI 2016), its software L4 balancer using consistent hashing across commodity machines.

2.4 Envoy, service mesh and Spring Cloud Gateway (2016–present)

Lyft open-sourced Envoy in September 2016: a C++ L4/L7 proxy designed around dynamic configuration APIs (xDS), rich observability, and advanced load balancing. Envoy became the data plane for Istio and many gateways (Envoy Gateway, Contour, Emissary, Gloo). Spring Cloud Gateway arrived in 2017–2018 as the reactive (Netty/WebFlux) successor to Zuul 1, and later gained a servlet-based "Server MVC" variant. The Kubernetes Gateway API reached v1.0 (GA for its core resources) in October 2023, standardising how gateways are configured across implementations.

2.5 Rate limiting algorithms

Token and leaky buckets come from network traffic shaping and policing in the 1980s–1990s (ATM networks standardised a leaky-bucket-equivalent, the Generic Cell Rate Algorithm). The web adopted them for API quotas. In 2017 Stripe and Cloudflare published widely read posts on production rate limiting, and in 2021 GitHub described moving its API limiter to sharded, replicated Redis with Lua scripts; §9 covers all three. Michael Mitzenmacher's 1996 thesis on the "power of two choices" provided the theory behind P2C balancing, now standard in Envoy, Finagle, gRPC and many others.

3. Fundamentals

3.1 Vertical versus horizontal scaling

Vertical scaling (scale up) means a bigger machine: more cores, more RAM, faster disks. It requires no code changes, keeps everything in one process and one memory space (no network hops, no distributed state), and is often the right first move. Its limits are hard ceilings (the largest instance type), super-linear cost at the top end, a single failure domain, and diminishing returns from contention: Amdahl's law (§6.1) says the serial fraction of work caps speed-up, and lock contention, memory bandwidth and GC can make a 96-core JVM slower per core than a 16-core one.

Horizontal scaling (scale out) means more machines behind a balancer. It gives near-linear capacity growth if instances are independent, allows incremental cost, provides redundancy, and enables rolling deploys. Its cost is distribution: state must live elsewhere, requests must be routed, and coordination (locks, consistency, distributed transactions) becomes expensive.

3.2 Stateless services and session externalisation

A service is stateless if any instance can handle any request, because nothing a request needs is stored only in a particular instance's memory or local disk. State still exists; it lives in a database, cache, object store, or the request itself (a token). Statelessness is what makes instances interchangeable, which in turn enables any balancing algorithm, autoscaling, rolling deploys and instant failover.

The classic violation is the HTTP session. A servlet container's in-memory HttpSession ties a user to one instance. The traditional fix, sticky sessions (session affinity via a cookie or source-IP hash at the balancer), keeps users on one instance but causes uneven load, loses sessions when an instance dies or is deployed, and fights autoscaling (new instances receive no existing users). Three better options:

  • Externalised sessions. Store session data in Redis (or a database) so any instance can load it. Spring Session replaces the container's HttpSession implementation transparently: spring-session-data-redis plus a couple of properties, and your existing session.getAttribute code works unchanged. Cost: one Redis round trip per request that touches the session (Spring Session saves lazily and only writes changed attributes by default).
  • Client-held state (tokens). Put identity and claims in a signed token (JWT or opaque token validated against an introspection endpoint/cache). The service validates and needs no server-side session at all. Cost: revocation is harder for self-contained JWTs (short expiry plus refresh tokens, or a revocation list), and tokens must stay small.
  • Move conversational state into the domain. Shopping carts, wizards and drafts become first-class persisted entities, not session attributes. This is usually the right choice for anything users would be upset to lose.

Other hidden state to hunt for when making a service stateless: local file uploads (use object storage), in-memory caches that must be consistent across instances (use a distributed cache or accept per-instance staleness), in-process scheduled jobs that must run once (use ShedLock or a dedicated scheduler), WebSocket connections (need a pub/sub fan-out layer so any instance can deliver to a user connected elsewhere), and in-memory rate-limit counters (§3.10).

3.3 Load balancing at layer 4 and layer 7

A layer-4 (transport) load balancer makes decisions per TCP connection (or UDP flow) using addresses and ports only. It does not parse HTTP. It either rewrites packet addresses (NAT), encapsulates packets to the backend, or uses direct server return (DSR) where responses bypass the balancer. L4 balancers are extremely fast (millions of packets per second per node), protocol-agnostic (work for databases, gRPC, MQTT, anything over TCP), and preserve end-to-end TLS if desired. Their limitation is granularity: all requests on a long-lived connection (an HTTP/2 or gRPC connection carrying thousands of requests) go to the same backend, which can badly unbalance load.

A layer-7 (application) load balancer terminates the client connection, parses the application protocol (HTTP/1.1, HTTP/2, HTTP/3, gRPC), and makes a decision per request. It can route by host, path, header or cookie; retry idempotent requests; terminate TLS; compress; add headers (X-Forwarded-For, trace context); and observe status codes and latency for health decisions. The cost is CPU (TLS and parsing), an extra hop with its own connection pools, and the need to hold certificates at the balancer.

Balancing can also happen in the client: the caller resolves a list of instances (from Kubernetes endpoints, Consul or Eureka) and picks one itself. Spring Cloud LoadBalancer, gRPC's built-in balancers and service-mesh sidecars all do this. Client-side balancing removes a hop and a central bottleneck but requires every client to implement the algorithm and health logic, which is why meshes move it into a sidecar.

3.4 Load-balancing algorithms

The algorithm decides which healthy backend receives the next connection or request. The right one depends on how uniform your backends and requests are.

  • Round-robin. Cycle through backends in order. Perfectly fair in request count, blind to request cost and backend speed. Good when backends are identical and requests are uniform and short.
  • Weighted round-robin. Backends receive traffic in proportion to static weights (e.g. an 8-core node weight 2, a 4-core node weight 1). Also used for canaries (weight 5% to the new version). Smooth weighted round-robin (as in NGINX) interleaves rather than sending bursts to the heavy node.
  • Random. Pick uniformly at random. Stateless and trivially distributed across many balancer nodes, but the maximum load on any backend is noticeably higher than the average due to variance.
  • Least connections / least outstanding requests. Send to the backend with the fewest active connections (L4) or in-flight requests (L7). Adapts automatically to slow backends (they accumulate in-flight requests and receive fewer new ones), which is what you want when request cost varies or a node is degraded. Requires the balancer to track counts; across many independent balancer nodes, each only knows its own counts.
  • Power of two choices (P2C). Pick two backends at random and send to the one with fewer outstanding requests (or lower latency-weighted load). Nearly as good as full least-connections, but O(1), robust to stale information, and it avoids the herding problem where many balancers simultaneously see the same "least loaded" backend and all pile onto it. Envoy's LEAST_REQUEST policy uses P2C by default when backends have equal weights.
  • Least response time / peak EWMA. Choose by an exponentially weighted moving average of observed latency multiplied by in-flight count (Finagle and Linkerd popularised peak-EWMA). Reacts quickly to backends that become slow.
  • Hashing (source IP, header, consistent hashing, ring hash, Maglev). Map a request attribute to a backend deterministically, so the same key always reaches the same backend. Used for cache locality (route all requests for tenant=42 to the instance with that tenant warm in its local cache) and for affinity. Consistent hashing (Chapter 3) ensures that adding or removing a backend remaps only about \(1/n\) of keys. Maglev hashing trades a little consistency for near-perfect balance and fast lookup tables.

3.5 Health checks: active, passive, and what "healthy" means

Active health checks probe each backend periodically (HTTP GET /actuator/health/readiness every few seconds) and remove it after N consecutive failures, re-adding it after M successes. Passive health checks (outlier detection) watch real traffic: if a backend returns five consecutive 5xx responses or its error rate exceeds the fleet's by a margin, eject it for a backoff period. Active checks catch dead instances before users hit them; passive checks catch instances that answer health probes but fail real requests. Use both.

The hard question is what the health endpoint should check. In Kubernetes and Spring Boot terms:

  • Liveness (/actuator/health/liveness): "is this process broken beyond repair?" If it fails, the container is restarted. It must not include dependencies: if the database is down and liveness fails, Kubernetes restarts every pod simultaneously, which fixes nothing and adds a cold-start storm.
  • Readiness (/actuator/health/readiness): "should this instance receive traffic right now?" Fails during startup (warm-up, cache loading), during shutdown (so the balancer stops routing), and optionally when a critical, instance-local resource is unavailable. Including a shared dependency (the database) in readiness is debatable: if it fails, all instances become unready and the balancer has nowhere to send traffic, turning a partial degradation into a full outage. Many teams exclude shared dependencies and handle their failure in code with fallbacks.
  • Startup probes protect slow-starting JVMs from being killed by liveness checks before they finish initialising.

Health checks have a fail-open subtlety: if all backends fail health checks, many balancers (Envoy's panic threshold, AWS ALB's behaviour when all targets are unhealthy) route to all of them anyway, on the theory that a broken health check is more likely than a fully dead fleet.

3.6 Connection draining and graceful shutdown

When an instance is removed (deploy, scale-in, node drain), requests already in flight must complete and no new requests must be routed to it. Connection draining (deregistration delay on AWS, drain timeouts in Envoy) is the balancer's half: stop sending new requests, wait up to a timeout for in-flight ones. The application's half is graceful shutdown: on SIGTERM, stop accepting new connections, finish in-flight requests, then exit.

In Kubernetes these two halves race. When a pod is deleted, the kubelet sends SIGTERM and, in parallel, the endpoint controller removes the pod from Service endpoints, which then propagates to kube-proxy, Ingress controllers and external balancers over the next few seconds. If the application stops accepting connections immediately on SIGTERM, requests routed during that propagation window fail. The standard fix is a preStop hook that sleeps a few seconds (long enough for endpoint removal to propagate) before SIGTERM reaches the JVM, combined with Spring Boot graceful shutdown (server.shutdown=graceful, which became the default in Spring Boot 3.4 Version-sensitive · checked Nov 2026) and a terminationGracePeriodSeconds longer than preStop plus the shutdown phase timeout. §4.3 walks through the timeline.

3.7 Reverse proxies

A forward proxy acts on behalf of clients (corporate egress proxies). A reverse proxy acts on behalf of servers: clients connect to it believing it is the origin, and it forwards to one or more backends. Load balancing is one reverse-proxy function among many: TLS termination, HTTP/2 and HTTP/3 to clients while speaking HTTP/1.1 to backends, connection pooling and keep-alive to backends (turning thousands of client connections into dozens of upstream ones), buffering slow clients so application threads are not held while a mobile phone trickles a response, compression, static file serving, caching, request size limits, header normalisation, and access logging.

  • NGINX: event-driven, very efficient, configured with a declarative file; dynamic reconfiguration requires reload (graceful) or the commercial edition/OpenResty Lua. Ubiquitous as an edge proxy and Kubernetes ingress controller (note that the community ingress-nginx controller project announced its retirement, with maintenance ending in March 2026 Version-sensitive · checked Nov 2026; new clusters typically adopt Gateway API implementations).
  • HAProxy: extremely mature L4/L7 balancer, excellent observability and algorithms, runtime API for dynamic changes.
  • Envoy: designed for dynamic environments; everything (listeners, routes, clusters, endpoints, secrets) can be updated at runtime via xDS APIs from a control plane; first-class HTTP/2, gRPC, retries, circuit breaking, outlier detection, rich stats and tracing. The data plane of Istio and many gateways.

3.8 API gateways

An API gateway is a reverse proxy specialised for APIs, sitting at the boundary between clients and a set of services. It centralises cross-cutting concerns that every service would otherwise reimplement:

  • Routing by path, host, header and version, including canary and blue/green weights.
  • Authentication (validate JWTs, API keys, mTLS client certificates) and coarse-grained authorisation (scopes, plans).
  • Rate limiting and quotas per API key, tenant, plan or route.
  • Request/response transformation (header injection, protocol translation such as REST to gRPC), CORS.
  • Observability: access logs, metrics per route and consumer, trace context propagation.
  • Resilience at the edge: timeouts, retries for idempotent routes, circuit breaking.
  • Developer-facing concerns for public APIs: API keys, usage plans, developer portals, monetisation.

Options a Spring engineer is likely to meet:

  • Spring Cloud Gateway: Java, configured with routes made of predicates and filters in YAML or Java DSL; the reactive variant runs on Netty/WebFlux, and a Server MVC variant runs on servlet stacks (well suited to virtual threads). Natural choice when the team is Java-centric and wants custom filters in Java. Current release train: Spring Cloud 2025.1 "Oakwood" with Gateway 5.0.x for Spring Boot 4 Version-sensitive · checked Nov 2026.
  • Kong: NGINX/OpenResty-based, extensible with plugins (Lua, Go, and others), with an open-source gateway and commercial offerings including a control plane and portal.
  • Envoy-based gateways: Envoy Gateway (the CNCF project implementing Kubernetes Gateway API on Envoy), Istio's ingress gateway, Contour, Emissary-ingress, Gloo. High performance, dynamic config, consistent with a mesh.
  • Managed cloud gateways: AWS API Gateway (REST and HTTP APIs, with usage plans and API keys, Lambda and HTTP integrations), Azure API Management, Google Cloud API Gateway/Apigee. Little to operate, per-request pricing, and service limits to check (e.g. AWS API Gateway's integration timeout and payload size limits).

The gateway is not your domain layer

A gateway that aggregates five services into a bespoke response for one screen, applies business validation, or queries a database per request becomes a shared bottleneck owned by no team, deployed on everyone's critical path. Keep shared gateways thin and generic; put client-specific aggregation in a BFF and business rules in services.

3.9 Backend for Frontend (BFF)

The BFF pattern gives each client experience (web, iOS/Android, partner API, perhaps an AI agent interface) its own thin backend owned by the team that owns that client. The BFF aggregates calls to downstream services, shapes payloads for that client (mobile wants fewer, smaller responses; web wants richer ones), handles client-specific auth flows (a web BFF can keep tokens server-side and give the browser only an HTTP-only session cookie, a pattern now recommended for browser-based OAuth apps), and evolves at the client's pace. It sits behind the shared gateway, which still handles edge concerns. GraphQL servers are often used as BFFs, letting clients choose fields. The risk is duplication across BFFs; shared logic belongs in downstream services, not copy-pasted between BFFs.

3.10 Rate limiting: purpose and algorithms

Rate limiting bounds how many requests a client (identified by IP, API key, user, tenant) may make in a time period. Its purposes are distinct and lead to different designs: protection (prevent any client from overloading the system or a scarce dependency), fairness (one tenant cannot starve others), commercial quotas (plan tiers, billing), abuse prevention (credential stuffing, scraping), and cost control (LLM token spend). Related but different: load shedding rejects work based on the server's own state (CPU, queue depth, concurrency) regardless of who sent it; concurrency limiting bounds in-flight requests rather than rate; backpressure signals upstream to slow down.

The five classic algorithms:

  • Token bucket. A bucket holds up to \(b\) tokens and refills at rate \(r\) tokens per second. Each request takes one token (or a cost-weighted number); with no tokens, it is rejected (or waits). Allows bursts up to \(b\) after idle periods while enforcing a long-run average of \(r\). State per key: token count and last refill timestamp; refill is computed lazily on each request. The most widely used algorithm (AWS API Gateway throttling, Bucket4j, Go's x/time/rate, Stripe's request limiter, Spring Cloud Gateway's Redis limiter).
  • Leaky bucket. Requests enter a FIFO queue of capacity \(b\) that drains at constant rate \(r\); when full, new requests are dropped. Output is perfectly smooth, which suits shaping traffic toward a fragile downstream, at the cost of added queueing latency. A "leaky bucket as meter" variant (equivalent to GCRA) tracks a theoretical arrival time instead of a queue and behaves like a token bucket.
  • Fixed window counter. Count requests per key in aligned windows (e.g. per minute, keyed by floor(now/60)); reject above the limit. Tiny state, one atomic INCR in Redis. Flaw: boundary bursts. A client can send the full limit at 12:00:59 and again at 12:01:00, so up to \(2\times\) the limit in any two-second span.
  • Sliding window log. Store a timestamp per accepted request (e.g. a Redis sorted set); on each request, drop timestamps older than the window and count the rest. Exact, no boundary problem, but memory is proportional to the limit (a 10,000-per-hour limit stores up to 10,000 timestamps per key).
  • Sliding window counter. Keep counters for the current and previous fixed windows and estimate the sliding count as \(\text{prev} \times \frac{\text{window} - \text{elapsed}}{\text{window}} + \text{curr}\). Constant memory, smooths the boundary problem, and is accurate to within a small error when traffic within the previous window is roughly uniform. Cloudflare described using this approach (§9).

3.11 Distributed rate limiting

A limiter that runs in each of 20 gateway instances with a limit of 100 per second admits up to 2,000 per second for a client whose requests are spread evenly, and an unpredictable amount if load is uneven. There are three ways to get a global limit:

  • Centralised store. Keep limiter state in Redis (or Memcached, or a dedicated service such as Envoy's global rate limit service backed by Redis) and update it atomically per request. Accurate, but adds a network round trip (~0.3–1 ms in-zone) and makes the store a critical dependency: decide whether to fail open (allow traffic when Redis is unreachable, prioritising availability) or fail closed (reject, prioritising protection). Most user-facing APIs fail open with a local fallback limiter.
  • Local limits with division. Give each of \(n\) instances a limit of \(L/n\). No network hop, but inaccurate when load is uneven or \(n\) changes; acceptable for protective limits, not for contractual quotas.
  • Hybrid / batched. Each instance consumes from a local allowance and periodically syncs with the central store (reserving batches of tokens). Reduces store load at the cost of brief over-admission. Common at very high request rates.

Atomicity matters: a read-modify-write of a token count from two gateway instances concurrently will double-spend tokens. In Redis, run the whole algorithm in a Lua script (or Redis Function), which executes atomically on the server; §7 implements this. In Redis Cluster all keys touched by a script must hash to the same slot, which is natural when the key is the client identifier.

4. Internal Working

4.1 Inside an L4 balancer: NAT, DSR and consistent flow hashing

A software L4 balancer such as Maglev, Katran (Meta's XDP/eBPF balancer) or Linux IPVS processes packets, not requests. For each incoming packet it computes a hash of the 5-tuple (source IP, source port, destination IP, destination port, protocol) and looks the hash up in a table to choose a backend. Every packet of the same TCP connection has the same 5-tuple, so all of them reach the same backend without the balancer storing per-connection state (though most also keep a connection-tracking cache). The packet is then either:

  • NATed: the destination address is rewritten to the backend, and replies come back through the balancer, which rewrites the source. Simple, but the balancer carries traffic in both directions.
  • Encapsulated with direct server return: the packet is wrapped (IP-in-IP or GUE) and sent to the backend, which unwraps it and replies directly to the client using the virtual IP as source. Because responses are typically much larger than requests, DSR lets a small balancer tier front enormous egress.

Many balancer nodes share one virtual IP via ECMP (equal-cost multi-path) routing from upstream routers, so the L4 tier itself scales horizontally. The hard part is what happens when a balancer node or a backend is added or removed: ECMP may send a connection's packets to a different balancer node, which must pick the same backend. This is why these systems use consistent hashing variants (Maglev hashing) so that independent nodes compute identical, stable assignments.

4.2 Inside an L7 proxy: the life of a request in Envoy

  1. Listener accepts the TCP connection on a worker thread (Envoy runs one event loop per worker thread; a connection stays on its thread for its lifetime, so no locking on the hot path).
  2. Network filter chain: the TLS transport socket performs the handshake (selecting certificates via SNI); the HTTP connection manager network filter decodes HTTP/1.1, HTTP/2 or HTTP/3 into streams.
  3. HTTP filter chain per request: e.g. JWT authentication, external authorisation, local or global rate limit, CORS, fault injection, then the router filter.
  4. Route matching selects a cluster (a named group of upstream endpoints) by host, path, headers, and weights.
  5. Load balancer for that cluster picks a healthy host using the configured policy (round robin, least request with P2C, ring hash, Maglev, random), excluding hosts ejected by outlier detection.
  6. Connection pool per upstream host provides an existing connection (HTTP/1.1 pools many connections; HTTP/2 multiplexes streams over few). Circuit-breaker thresholds (max connections, max pending requests, max requests, max retries) bound the pool; exceeding them fails fast with a 503 rather than queueing.
  7. The request is forwarded with a per-route timeout; on eligible failures the router may retry on a different host, subject to a retry budget.
  8. The response streams back through the filters in reverse; stats (per-cluster latency histograms, response codes) and access logs are emitted.

Spring Cloud Gateway follows a similar shape on Netty: route predicates select a route, a chain of GatewayFilters and global filters runs (including RequestRateLimiter, CircuitBreaker, Retry), and the Netty HTTP client forwards using a pooled connection, with Spring Cloud LoadBalancer choosing the instance for lb://service-name URIs.

4.3 A zero-downtime pod termination, step by step

  1. A rollout deletes pod P. The API server marks it terminating.
  2. In parallel: (a) the endpoints/EndpointSlice controller removes P from Service endpoints; kube-proxy, ingress controllers and cloud balancer integrations learn of this over the next ~1–10 s; (b) the kubelet runs P's preStop hook.
  3. The preStop sleep (e.g. 10 s) keeps the JVM serving normally while the removal propagates. Requests that still arrive are served.
  4. After preStop, the kubelet sends SIGTERM. Spring Boot's graceful shutdown begins: the readiness state switches to REFUSING_TRAFFIC, the web server stops accepting new connections, and in-flight requests are given up to spring.lifecycle.timeout-per-shutdown-phase (default 30 s) to complete.
  5. Application context closes: Kafka consumers commit and leave the group, Hikari closes connections, executors drain.
  6. If anything is still running when terminationGracePeriodSeconds (default 30 s, counted from the start of preStop) expires, the kubelet sends SIGKILL. Hence: grace period > preStop sleep + shutdown timeout + margin.

Long-lived connections need extra care: HTTP/1.1 keep-alive connections are closed by the server after the in-flight response (Tomcat sends Connection: close); HTTP/2 connections receive a GOAWAY frame so clients open new streams elsewhere; WebSockets and gRPC streams must be closed by the application with a reconnect hint.

4.4 Token bucket internals: lazy refill

A token bucket never runs a timer per key. It stores two numbers, tokens and lastRefill. On each request at time now:

elapsed   = now - lastRefill
tokens    = min(capacity, tokens + elapsed * refillRate)
lastRefill = now
if tokens >= cost:  tokens -= cost; ALLOW (remaining = tokens)
else:               DENY  (retryAfter = (cost - tokens) / refillRate)

This makes it O(1) in time and memory per key, and it works across processes as long as the read-compute-write is atomic. The retryAfter value is exactly what you return in a Retry-After header. Keys for idle clients can be expired after \(\text{capacity}/\text{rate}\) seconds, since by then the bucket would be full anyway and a missing key is equivalent to a full bucket.

4.5 Why Redis Lua scripts are atomic

Redis executes commands on a single main thread (Chapter 3 explains the event loop). A Lua script submitted with EVAL/EVALSHA (or a Redis Function invoked with FCALL) runs to completion on that thread with no other command interleaved, so a read-modify-write inside a script is atomic without locks or WATCH. Two implications: scripts must be short (a slow script blocks every client of that Redis node), and in Redis Cluster all keys a script touches must be declared in KEYS and live in the same hash slot (use hash tags like rl:{client42}:tokens and rl:{client42}:ts).

Time is a subtle issue. If each gateway instance passes its own clock into the script, clock skew between instances makes the limiter inaccurate. Using the Redis server's clock (redis.call('TIME'), allowed in scripts since Redis 5 because scripts are replicated by effects) gives one clock for all callers of that key.

5. Architecture: The Traffic Layer

Reading the diagram: each tier rejects a different kind of excess as early and as cheaply as possible. The CDN/WAF drops volumetric abuse and applies per-IP limits before traffic reaches your network. The cloud balancer spreads connections across zones and terminates TLS. The gateway authenticates and enforces per-key and per-tenant quotas with shared state in Redis. BFFs shape responses per client. Inside the services, an LLM proxy enforces the strictest and most expensive limits (tokens per minute, concurrent generations). Rejecting early matters because work done before a rejection is wasted; a request rejected at the CDN costs nothing, while one rejected after three service hops has consumed threads, connections and CPU along the way.

What to try: start with identical servers and round-robin; distribution is even. Now make one server much slower (or give the servers different capacities). Round-robin and random keep sending it an equal share, so its queue and latency grow without bound while others idle. Switch to least-connections: the slow server accumulates in-flight requests and naturally receives fewer new ones. Then try P2C: it achieves almost the same balance while only sampling two servers per decision, which is why it scales to many independent balancer nodes without coordination. Weighted round-robin fixes static capacity differences but cannot react to a server that becomes slow dynamically (a GC pause, a noisy neighbour).

Reading the diagram: endpoint removal and SIGTERM are triggered concurrently, not sequentially. Without the preStop sleep, the pod would stop accepting connections while some balancers still route to it, producing connection-refused errors on every deploy (often noticed only as a small error spike that "always happens during deploys"). The preStop delay converts the race into an ordering: by the time SIGTERM arrives, traffic has stopped arriving, and graceful shutdown only has to finish what is already in flight.

Reading the diagram: filters are ordered so that cheap rejections happen first: unmatched routes, then authentication (signature verification is CPU-only), then rate limiting (one Redis round trip), and only then the expensive upstream call. Putting the rate limiter before authentication would let unauthenticated traffic consume the limiter's Redis capacity and make it impossible to key limits by authenticated identity; putting it after the upstream call would be pointless. The circuit breaker sits closest to the upstream so it observes real upstream failures.

What to try: send a burst right before and right after a fixed-window boundary and watch the fixed window admit up to twice the limit in a short span, while the sliding log rejects the excess. Then let the system idle and send a burst: the token bucket admits a burst up to its capacity and then settles at the refill rate. That burst allowance is a feature for user-facing APIs (a page load fires ten requests at once) and a liability when protecting a fragile downstream, where you want a smaller bucket or a leaky bucket's smooth output. Change the capacity and refill rate to see how they independently control burst size and sustained throughput.

Reading the diagram: the gateway is shared and generic; each BFF is owned by the team that owns its client and can change as fast as that client. A web BFF can hold OAuth tokens server-side and give the browser only an HTTP-only cookie; a mobile BFF can collapse five calls into one compact response to save radio time; a public or agent-facing API is versioned and metered conservatively because its consumers cannot be redeployed in lockstep. Domain services stay unaware of client shapes.

6. The Math

6.1 Why vertical scaling saturates: Amdahl and the Universal Scalability Law

Intuition: if part of the work cannot be parallelised (a global lock, a single-threaded component), adding cores only speeds up the rest. If cores must also coordinate (cache-line bouncing, lock handoffs), adding cores can make things slower.

Amdahl's law for serial fraction \(\sigma\) and \(N\) processors gives speed-up \(S(N) = \frac{N}{1 + \sigma (N-1)}\), bounded by \(1/\sigma\). With 5% serial work, no number of cores exceeds a 20x speed-up. Neil Gunther's Universal Scalability Law adds a coherency term \(\kappa\):

\[ C(N) = \frac{N}{1 + \sigma (N - 1) + \kappa N (N - 1)} \]

With \(\kappa > 0\), capacity peaks at \(N^* = \sqrt{(1-\sigma)/\kappa}\) and then declines. Fitting \(\sigma\) and \(\kappa\) to load-test results at a few instance sizes or replica counts tells you where scaling stops paying. The same law applies to horizontal scaling when instances share a contended resource (a database row, a global lock in Redis).

6.2 Balls into bins: why random is unbalanced and P2C is not

Assign \(n\) requests to \(n\) servers. With uniform random choice, the most loaded server receives about \(\frac{\ln n}{\ln \ln n}\) requests with high probability, compared with an average of 1. With power of two choices (pick two at random, choose the less loaded), the maximum drops to about \(\frac{\ln \ln n}{\ln 2} + O(1)\): an exponential improvement. For \(n = 1{,}000\), \(\ln n / \ln\ln n \approx 3.6\) versus \(\ln\ln n/\ln 2 \approx 2.8\) (plus a constant); the gap widens with \(n\), and in the continuous-load setting with long-running requests it is much more dramatic. Choosing among \(d > 2\) only improves the bound by a constant factor (\(\ln\ln n/\ln d\)), which is why two is the sweet spot.

6.3 Token bucket bounds

A token bucket with capacity \(b\) and rate \(r\) admits at most

\[ A(t) \le b + r\,t \]

requests in any interval of length \(t\). This is an arrival curve in network-calculus terms. For \(b = 20\), \(r = 10\)/s: at most 20 in an instant, 30 in one second, 610 in a minute. Contrast a fixed window of limit \(L\) per window \(T\): in the worst case it admits \(2L\) within any interval just over \(\epsilon\) straddling a boundary, so the burst bound is \(2L\), not \(L\).

Retry-After for a denied request of cost \(k\) with \(x\) tokens left: \(t_{wait} = (k - x)/r\).

6.4 Sliding window counter error

With previous-window count \(p\), current-window count \(c\), window length \(T\) and elapsed time \(e\) in the current window, the estimate is

\[ \hat{n} = p\cdot\frac{T - e}{T} + c \]

The estimate is exact if the previous window's requests were uniformly distributed in time. If they were all at the start of the previous window, the true count in the sliding window is lower than the estimate (the limiter is stricter than needed); if all at the end, higher (it under-counts and over-admits). The worst-case over-admission is bounded by \(p\) times the fraction of the window, and in practice (with many independent clients) the error is small.

6.5 Local limits in a fleet

Suppose a global limit \(L\) and \(n\) gateway instances each enforcing \(L/n\) locally, with a client's requests landing on instance \(i\) with probability \(q_i\). The client is throttled at instance \(i\) once its rate there exceeds \(L/n\), i.e. when total rate \(\lambda\) exceeds \(\frac{L}{n q_i}\). With perfectly even routing \(q_i = 1/n\) the effective limit is exactly \(L\). With hashing or sticky connections (e.g. one HTTP/2 connection pinned to one instance, \(q_i = 1\)), the effective limit collapses to \(L/n\): the client is throttled at a fraction of its entitlement. Conversely, if \(n\) grows via autoscaling but per-instance limits are not recomputed, the effective limit grows to \(nL/n_0\). This is the quantitative argument for a shared store when limits are contractual.

6.6 Sizing the gateway and the limiter store

Illustrative Peak 60,000 requests per second at the gateway. If one gateway instance (4 vCPU) sustains 6,000 RPS at 60% CPU with JWT validation and one Redis call per request, you need 10 instances at peak, 15 for N+1 across three zones (each zone must carry half the load if one zone is lost: \(60{,}000/2/6{,}000 = 5\) per zone). The limiter store sees 60,000 script executions per second; a short Lua script executes in a few microseconds, so a single Redis primary can handle this, but for headroom and isolation many teams shard limiter keys across several Redis primaries by client ID (as GitHub describes in §9). Little's Law on the gateway's Redis connections: \(60{,}000 \times 0.0005\ \text{s} = 30\) concurrent operations fleet-wide, so a small pool per instance (or a single multiplexed Lettuce connection) suffices.

-- ARGV[1] = refill rate (tokens per second), ARGV[2] = capacity, ARGV[3] = cost
local key      = KEYS[1]
local rate     = tonumber(ARGV[1])
local capacity = tonumber(ARGV[2])
local cost     = tonumber(ARGV[3])

local t   = redis.call('TIME')                       -- server clock: one clock for all callers
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local state  = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(state[1])
local ts     = tonumber(state[2])
if tokens == nil then
  tokens = capacity
  ts = now
end

local elapsed = math.max(0, now - ts)
tokens = math.min(capacity, tokens + (elapsed * rate / 1000))

local allowed  = 0
local retry_ms = 0
if tokens >= cost then
  tokens  = tokens - cost
  allowed = 1
else
  retry_ms = math.ceil((cost - tokens) * 1000 / rate)
end

redis.call('HSET', key, 'tokens', tostring(tokens), 'ts', now)
-- an idle bucket refills completely after capacity/rate seconds; expire it then
redis.call('PEXPIRE', key, math.ceil(capacity * 1000 / rate) + 1000)
return { allowed, math.floor(tokens), retry_ms }

import org.springframework.data.redis.core.script.DefaultRedisScript;
import org.springframework.data.redis.core.script.RedisScript;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;
import java.util.List;

@Component
public class TokenBucketFilter extends OncePerRequestFilter {

    private static final Logger log = LoggerFactory.getLogger(TokenBucketFilter.class);

    private final StringRedisTemplate redis;
    private final RedisScript<List> script;
    private final MeterRegistry meters;
    private final double ratePerSecond = 20;
    private final int capacity = 40;

    public TokenBucketFilter(StringRedisTemplate redis, MeterRegistry meters) {
        this.redis = redis;
        this.meters = meters;
        var s = new DefaultRedisScript<List>();
        s.setLocation(new ClassPathResource("scripts/token_bucket.lua"));
        s.setResultType(List.class);
        this.script = s;   // Spring Data Redis uses EVALSHA and falls back to EVAL
    }

    @Override
    protected boolean shouldNotFilter(HttpServletRequest request) {
        return request.getRequestURI().startsWith("/actuator");
    }

    @Override
    protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String key = "rl:{" + clientId(req) + "}";   // hash tag keeps Cluster slot stable
        try {
            @SuppressWarnings("unchecked")
            List<Long> r = redis.execute(script, List.of(key),
                    String.valueOf(ratePerSecond), String.valueOf(capacity), "1");
            boolean allowed = r.get(0) == 1L;
            res.setHeader("RateLimit-Limit", String.valueOf(capacity));
            res.setHeader("RateLimit-Remaining", String.valueOf(r.get(1)));
            if (!allowed) {
                long retrySeconds = Math.max(1, (r.get(2) + 999) / 1000);
                res.setHeader("Retry-After", String.valueOf(retrySeconds));
                res.setStatus(429);
                res.setContentType("application/problem+json");
                res.getWriter().write("{\"title\":\"Too Many Requests\",\"status\":429}");
                meters.counter("ratelimit.rejected", "tier", "api").increment();
                return;
            }
        } catch (DataAccessException e) {
            // Fail open: availability over protection. Pair with a coarse local limiter in production.
            meters.counter("ratelimit.store.errors").increment();
            log.warn("rate limiter store unavailable, allowing request: {}", e.getMessage());
        }
        chain.doFilter(req, res);
    }

    private String clientId(HttpServletRequest req) {
        String apiKey = req.getHeader("X-Api-Key");
        if (apiKey != null && !apiKey.isBlank()) return "key:" + apiKey;
        return "ip:" + req.getRemoteAddr(); // set server.forward-headers-strategy=native behind a proxy
    }
}

"""Sliding-window-counter limiter on Redis, usable from FastAPI/Flask middleware.

import time
import redis

SCRIPT = """
-- KEYS[1] = current window key, KEYS[2] = previous window key
-- ARGV[1] = limit, ARGV[2] = window ms, ARGV[3] = elapsed ms in current window
local curr = tonumber(redis.call('GET', KEYS[1]) or '0')
local prev = tonumber(redis.call('GET', KEYS[2]) or '0')
local limit = tonumber(ARGV[1])
local window = tonumber(ARGV[2])
local elapsed = tonumber(ARGV[3])
local estimate = prev * ((window - elapsed) / window) + curr
if estimate >= limit then
  return {0, math.floor(estimate)}
end
redis.call('INCR', KEYS[1])
redis.call('PEXPIRE', KEYS[1], window * 2)
return {1, math.floor(estimate) + 1}
"""


class SlidingWindowLimiter:
    def __init__(self, client: redis.Redis, limit: int, window_s: int):
        self.r = client
        self.limit = limit
        self.window_ms = window_s * 1000
        self.script = client.register_script(SCRIPT)

    def allow(self, client_id: str) -> tuple[bool, int]:
        now_ms = int(time.time() * 1000)  # app clock: windows are coarse, skew of ms is harmless
        window_idx = now_ms // self.window_ms
        elapsed = now_ms % self.window_ms
        curr = f"sw:{{{client_id}}}:{window_idx}"
        prev = f"sw:{{{client_id}}}:{window_idx - 1}"
        allowed, count = self.script(keys=[curr, prev],
                                     args=[self.limit, self.window_ms, elapsed])
        return bool(allowed), int(count)

package main

import (
	"net"
	"net/http"
	"strconv"
	"sync"
	"time"

	"golang.org/x/time/rate"
)

type entry struct {
	lim      *rate.Limiter
	lastSeen time.Time
}

type PerClient struct {
	mu      sync.Mutex
	clients map[string]*entry
	r       rate.Limit
	burst   int
}

func NewPerClient(perSecond float64, burst int) *PerClient {
	p := &PerClient{clients: map[string]*entry{}, r: rate.Limit(perSecond), burst: burst}
	go p.janitor()
	return p
}

func (p *PerClient) get(id string) *rate.Limiter {
	p.mu.Lock()
	defer p.mu.Unlock()
	e, ok := p.clients[id]
	if !ok {
		e = &entry{lim: rate.NewLimiter(p.r, p.burst)}
		p.clients[id] = e
	}
	e.lastSeen = time.Now()
	return e.lim
}

// janitor evicts idle clients so the map does not grow without bound.
func (p *PerClient) janitor() {
	for range time.Tick(time.Minute) {
		p.mu.Lock()
		for id, e := range p.clients {
			if time.Since(e.lastSeen) > 3*time.Minute {
				delete(p.clients, id)
			}
		}
		p.mu.Unlock()
	}
}

func (p *PerClient) Middleware(next http.Handler) http.Handler {
	return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		id := r.Header.Get("X-Api-Key")
		if id == "" {
			id, _, _ = net.SplitHostPort(r.RemoteAddr)
		}
		res := p.get(id).Reserve()
		if delay := res.Delay(); delay > 0 {
			res.Cancel() // give the token back; we are rejecting, not waiting
			w.Header().Set("Retry-After", strconv.Itoa(int(delay.Seconds())+1))
			http.Error(w, "too many requests", http.StatusTooManyRequests)
			return
		}
		next.ServeHTTP(w, r)
	})
}

func main() {
	lim := NewPerClient(10, 20)
	mux := http.NewServeMux()
	mux.HandleFunc("/hello", func(w http.ResponseWriter, _ *http.Request) { w.Write([]byte("ok\n")) })
	http.ListenAndServe(":8080", lim.Middleware(mux))
}

The Go limiter is local to one process; put it behind a shared store (as in §7.3) when limits must be global. 8. Real-World Applications

  • Public API platforms (payments, communications, developer tools) publish per-key rate limits and quotas, return 429 with Retry-After and rate-limit headers, and enforce limits in a gateway backed by a shared store. Concurrency limits often protect expensive endpoints separately from request-rate limits.
  • Multi-tenant SaaS uses per-tenant limits for fairness ("noisy neighbour" protection) and plan-based quotas, often with separate buckets for reads, writes and expensive operations such as exports or AI generation.
  • E-commerce flash sales and ticketing combine rate limits with virtual waiting rooms (admission control at the edge that lets users in at the rate the backend can sustain) so that a 50x spike becomes a queue rather than an outage.
  • Internal platforms deploy a service mesh (Envoy sidecars or ambient/node proxies) so that every service gets P2C balancing, outlier detection, retries with budgets, mTLS and uniform metrics without library changes, with a shared gateway at the edge.
  • AI features: an internal "LLM gateway" centralises provider credentials, enforces per-team token budgets (token buckets where cost = tokens, not requests), caps concurrency per model, routes between providers and models, and records usage for chargeback. The same algorithms as this chapter, with cost-weighted consumption.
  • Mobile backends use BFFs to collapse chatty calls and to version payloads per app release, since old app versions remain in the field for months.
  • Zero-downtime deploys: readiness gates, preStop delays, connection draining and weighted canary routing at the gateway are standard parts of a progressive-delivery pipeline (Argo Rollouts, Flagger, or cloud-native equivalents).

9. Case Studies

9.1 Stripe: four kinds of limiters

Verified Stripe's 2017 engineering post Scaling your API with rate limiters describes running several distinct limiters in production: a request rate limiter (per user, token-bucket based, with burst allowance), a concurrent requests limiter (caps in-flight requests, valuable for CPU-heavy endpoints), and two load shedders that reserve capacity for critical traffic (e.g. prioritising critical API methods over less important traffic when the fleet is under stress). The post recommends implementing limiters as middleware, returning clear errors (429 for client-attributable limits, 503 for shedding), building dark-launch and kill switches so a misconfigured limiter can be disabled quickly, and it includes example Redis-backed code. The key design lesson: rate limiting (who is sending too much) and load shedding (the system is overloaded regardless of who) are different controls and you need both.

9.2 GitHub: a sharded, replicated Redis limiter

Verified In How we scaled the GitHub API with a sharded, replicated rate limiter in Redis (2021), GitHub explains moving its API rate limiter off a Memcached instance shared with other caches onto dedicated Redis with client-side sharding and replicas, and running the limiter logic as a Lua script so that each request's counter update and TTL handling is atomic. The post discusses problems such as inconsistent reset times reported to clients and how server-side scripting fixed them. Lessons for your design: give the limiter its own store (so cache evictions do not reset limits), shard by client key, and do the whole decision server-side in one round trip.

9.3 Cloudflare: approximate sliding windows at the edge

Verified Cloudflare's 2017 post How we built rate limiting capable of scaling to millions of domains compares fixed windows, exact sliding logs (accurate but memory-heavy) and an approximate sliding window computed from the previous and current window counters, which is the sliding window counter in §3.10 and §6.4. It explains why the approximation was accurate enough in their traffic and how counters are shared across servers in a data centre. The lesson: at very large key cardinality, constant memory per key matters more than perfect accuracy.

9.4 Google Maglev: a software L4 balancer

Verified The NSDI 2016 paper Maglev: A Fast and Reliable Software Network Load Balancer describes Google's distributed L4 balancer running on commodity Linux servers, using ECMP to spread packets across Maglev machines, kernel-bypass packet processing, and a consistent hashing scheme ("Maglev hashing") designed for even load and minimal disruption when backends change, with connection tracking to keep existing flows stable. It is the reference design behind several cloud L4 balancers and influenced Envoy's Maglev load-balancing policy.

9.5 Dropbox: load-aware balancing in Bandaid

Verified Dropbox's post Enhancing Bandaid load balancing at Dropbox by leveraging real-time backend server load information describes moving its internal proxy (Bandaid) from random choice-of-N based on active request counts to using load information reported by backends, crediting ideas from Netflix's edge load-balancing work. It illustrates the progression in §3.4: round-robin → P2C on local counts → load-aware selection using backend feedback, each step fixing an imbalance visible at scale.

11.2 Where should this concern live?

Reading the diagram: the gateway is for concerns that apply uniformly and need no domain data; the BFF for client-specific composition; services for anything involving business rules; the mesh or a shared library for service-to-service plumbing. Fine-grained authorisation ("can this user edit this document?") needs domain data and therefore belongs in the service, even though coarse checks ("does this token have the documents:write scope?") can be done at the gateway.

11.3 Fail open or fail closed?

When the limiter's store is unavailable: fail open for user-facing APIs where limits are protective and an outage of the limiter should not become an outage of the product (pair with a coarse local limiter so you are not completely unprotected). Fail closed where limits guard money or safety (expensive LLM spend, SMS sending that costs per message and attracts fraud, login attempts). Make the choice explicit per limit and test it.

11.4 Sticky sessions versus externalised state

Sticky sessions are acceptable as a performance optimisation (cache locality) when losing affinity is harmless. They are a liability when correctness depends on them. If you find yourself needing stickiness for correctness, externalise the state; if you want it for locality, prefer consistent hashing on a meaningful key (tenant, document) over cookie affinity, because hashing redistributes predictably when the fleet changes.

12. Common Mistakes and Production Failures

  • Per-instance limits presented as global limits. A limit of 100/s per pod becomes 3,000/s after autoscaling to 30 pods (§6.5).
  • Trusting X-Forwarded-For blindly. Clients can send their own header; keying IP limits on the first value lets attackers rotate fake IPs. Only trust the hops you control (Spring's ForwardedHeaderFilter/server.forward-headers-strategy with trusted proxies configured; NGINX real_ip with set_real_ip_from).
  • Read-modify-write limiters without atomicity. GET then SET from two instances double-spends tokens. Use Lua, Redis Functions, or atomic INCR.
  • Retries at every layer. Client, gateway, BFF and service each retry three times: one user action becomes 81 backend calls during an incident. Retry at one layer, with budgets and jittered backoff, and only for idempotent operations.
  • Retrying non-idempotent requests at the proxy. proxy_next_upstream on a POST /payments can charge twice. Restrict proxy retries to safe methods or require idempotency keys.
  • Dependencies in liveness probes. Database blip → all pods fail liveness → mass restart → thundering herd on the database as every pod reconnects and warms up.
  • No preStop delay. A small burst of 502/503 on every deploy that everyone has learned to ignore.
  • L4 balancing of gRPC. Long-lived HTTP/2 connections pin to a few backends; new pods get no traffic after scale-out. Use L7 balancing, client-side balancing, or connection max-age so clients reconnect.
  • Gateway as dumping ground. Business logic and data access in a shared gateway; every team's change risks every team's traffic.
  • Unbounded per-key state. In-memory limiter maps keyed by IP with no eviction become memory leaks under scanning attacks (the Go example's janitor exists for this reason).
  • Missing Retry-After. Clients retry immediately and amplify load. Always tell them when to come back.

A real-world pattern: the retry storm

Illustrative A downstream slows; gateway timeouts fire; the gateway retries twice; the mobile app also retries twice on 5xx. Effective load on the struggling service rises up to ninefold precisely when it can least handle it. Recovery requires shedding load deliberately. Prevent it with a retry budget (e.g. retries may add at most 10–20% to request volume), circuit breakers, and server-side load shedding that returns fast 503s with Retry-After.

13. Production Engineering

13.1 Performance

  • Enable upstream keep-alive and HTTP/2 between proxies and services; TLS handshakes and TCP setup per request waste CPU and add latency.
  • Right-size proxy timeouts from latency budgets (connect timeouts of ~1 s or less in-region; request timeouts per route).
  • Measure the gateway's added latency explicitly (gateway total time minus upstream time) and set an SLO for it.

13.2 Security

  • Terminate TLS with modern configurations (TLS 1.2 minimum, 1.3 preferred) and automate certificate rotation.
  • Validate JWTs at the gateway (signature, iss, aud, exp), but propagate identity to services in a form they can verify again (forwarded token or a signed internal token); do not let services trust unauthenticated headers such as X-User-Id that any internal caller could set.
  • Rate-limit authentication endpoints aggressively (per account and per IP) and protect expensive endpoints with concurrency limits.
  • Set request size limits, header size limits and slow-client timeouts at the proxy to blunt slowloris-style attacks.

13.3 Scalability and reliability

  • Run gateways and balancers across at least three zones with N+1 capacity; they are on every request's critical path, so their SLO must exceed every service's.
  • Keep the gateway's own dependencies minimal: a shared Redis for rate limits (with fail-open), a JWKS cache for keys; avoid synchronous calls to identity providers per request.
  • Use outlier detection with a maximum ejection percentage so a fleet-wide problem does not eject every host.

13.4 Monitoring

  • Per route and per consumer: request rate, error rate, latency histogram, 429 rate. A sudden 429 spike for one consumer is usually a client bug; a broad spike is usually a limit set too low or a store failure.
  • Balancer: healthy host count per cluster, ejections, connection pool saturation (pending requests), retries and retry-budget overflow.
  • Limiter store: command latency, script execution time, memory, evictions (should be zero for a limiter store; use noeviction or a generous maxmemory).

13.5 Maintainability

  • Keep gateway routes and limits as code, reviewed and deployed through CI with automated config validation; a bad route can take down everything.
  • Version limits per plan in configuration rather than code, and expose them to customers via documentation and response headers (the IETF RateLimit header fields draft is a reasonable convention).

14. Exercises

Exercise 1 · Foundational

A token bucket has capacity 50 and refill rate 5 per second. It is full at t = 0. A client sends 80 requests instantly at t = 0, then 1 request every 100 ms. (a) How many of the initial 80 are admitted? (b) From t = 0 onward, what is the steady admission rate? (c) When does the first request after the burst succeed?

Solution

(a) 50 (the capacity); 30 are rejected. (b) 5 per second, the refill rate; the client sends 10 per second, so half are rejected in steady state. (c) After the burst the bucket is empty; one token accrues after 0.2 s, so the request at t = 0.2 s succeeds (the one at 0.1 s fails).

Exercise 2 · Intermediate

Your fixed-window limiter allows 600 requests per minute per key. Show the worst-case number of requests a client can get accepted within any 2-second interval, and redesign the limiter so that no 60-second sliding interval exceeds 600 while keeping O(1) memory.

Solution

Worst case: 600 at 12:00:59.x and 600 at 12:01:00.x: 1,200 within about one second. A sliding window counter (two counters) reduces this to approximately 600 but not exactly. A naive token bucket with capacity 600 and rate 10/s does not help either: it admits \(b + rt\) in time \(t\), so up to 1,200 in 60 seconds. To cap any 60-second interval at 600 you need \(b + 60r \le 600\), e.g. \(b = 60, r = 9\)/s (60 + 540 = 600). That sacrifices some sustained throughput for a guarantee; alternatively use GCRA (equivalent arithmetic) with the same parameters. If the requirement is only "about 600 per minute, no 2x bursts", the sliding window counter is the pragmatic choice.

Exercise 3 · Intermediate

Users report intermittent 502s during every deployment of a Spring Boot service on Kubernetes behind an NGINX-based ingress. Readiness and liveness probes are configured. Explain the most likely cause and the fix, including concrete values.

Solution

The termination race (§4.3): SIGTERM and endpoint removal happen concurrently; the ingress keeps routing to the pod for a few seconds after the JVM stops accepting connections. Fix: add preStop sleep of ~10 s (longer than observed endpoint propagation), keep server.shutdown=graceful with spring.lifecycle.timeout-per-shutdown-phase=30s, set terminationGracePeriodSeconds to ~60, use maxUnavailable: 0 in the rollout, and ensure the ingress uses upstream keep-alive with retry on connection errors only for idempotent methods. Verify by running a constant-rate load test during a rollout and checking for zero 5xx.

Exercise 4 · Advanced

Design per-tenant LLM usage limits for an internal AI gateway: each tenant has 200,000 tokens per minute and 20 concurrent generations; requests declare max_tokens but actual usage is only known after completion. Write the algorithm (pseudo-code is fine) and describe the Redis data model.

Solution

Two limiters per tenant. (1) Token bucket in tokens: capacity 200,000, rate 200,000/60 ≈ 3,333 tokens/s. (2) Concurrency semaphore: a counter (or sorted set of request IDs with expiry timestamps, to survive crashes) with limit 20.

Algorithm. On request: estimate cost = prompt tokens (count with a tokenizer) + max_tokens. Atomically (one Lua script): refill bucket, check tokens ≥ estimate and concurrency < 20; if both pass, deduct estimate and add the request ID to the concurrency set with an expiry of now + timeout; else return 429 with Retry-After computed from the bucket. On completion: a second script refunds estimate − actual tokens (capped at capacity) and removes the request ID. A periodic sweep removes expired IDs (crashed workers).

Keys: llm:{tenant}:bucket (hash: tokens, ts) and llm:{tenant}:inflight (sorted set: member = request ID, score = expiry). The shared hash tag keeps both in one Cluster slot for one script. Fail closed if Redis is unreachable (money is at stake), with a small local emergency allowance.

Exercise 5 · Advanced

A gRPC service runs 10 pods behind an AWS NLB. After scaling to 20 pods during a traffic spike, CPU on the new pods stays near zero while the original pods are saturated. Explain why and give three fixes with trade-offs.

Solution

gRPC uses long-lived HTTP/2 connections; an L4 balancer balances connections, and existing clients keep their connections to the original pods. New pods only receive new connections. Fixes: (1) L7 balancing (an Envoy/ALB-style proxy that balances per stream): best balance, extra hop and cost. (2) Client-side balancing (gRPC with DNS or xDS resolver and round_robin or least-request): no extra hop, but every client must be configured and needs endpoint discovery. (3) Server-side max_connection_age (gRPC servers can send GOAWAY after a connection age, e.g. 5 minutes with a grace period), forcing clients to reconnect and rebalance: simple, but rebalancing is gradual and causes periodic reconnection overhead.

15. Interview Questions and Answers

Conceptual What is the difference between L4 and L7 load balancing, and when would you choose each?

L4 balances connections using addresses and ports, without parsing the application protocol: very fast, protocol-agnostic, can preserve end-to-end TLS, but balances poorly when connections are long-lived and multiplexed. L7 terminates the connection, parses HTTP/gRPC and balances each request: routing by path/header, retries, TLS offload, observability, at the cost of CPU and an extra hop. Choose L4 for non-HTTP protocols, extreme throughput, or TLS pass-through; L7 for HTTP APIs, gRPC, canaries and anything needing request-level policy. Large systems often use both: L4 in front of a fleet of L7 proxies.

Conceptual Why does power of two choices work so well, and why not always pick the global least-loaded server?

Comparing two random choices removes most of the variance of random assignment: the maximum load drops from roughly \(\ln n/\ln\ln n\) to \(\ln\ln n/\ln 2\). Picking the global minimum requires up-to-date global state; with many independent balancers using slightly stale counts, they all pick the same "least loaded" server simultaneously and overload it (herding). Random sampling of two decorrelates choices while still steering away from busy servers, and costs O(1).

Coding Implement a token bucket rate limiter that is safe across multiple gateway instances.

Store per-key state (tokens, last refill timestamp) in Redis; execute refill-check-deduct atomically in a Lua script using the Redis server clock; expire idle keys after capacity/rate seconds; return allowed, remaining and retry-after. The script and Spring filter are in §7.3. Discuss: hash tags for Cluster, fail-open versus fail-closed, hashing API keys, and that the round trip adds ~0.5 ms.

Architecture What belongs in an API gateway, and what doesn't? How does a BFF differ?

Gateway: TLS, authentication, coarse authorisation (scopes), routing and versioning, quotas/rate limits, CORS, request size limits, observability, edge resilience. Not: business rules, domain data access, response aggregation for one client. A BFF is a client-specific backend owned by the client team that aggregates and shapes data for that experience; it sits behind the gateway. The gateway is shared and generic; BFFs are many and specific.

Architecture How would you make a legacy Spring MVC app that uses HttpSession heavily horizontally scalable without sticky sessions?

Introduce Spring Session with Redis: transparent replacement of HttpSession, so code is unchanged. Audit session contents (size, serialisability, class evolution), switch to JSON serialisation, and move durable business state (carts, drafts) into domain tables over time. Also externalise other local state: file uploads to object storage, scheduled jobs with ShedLock, local caches reviewed for consistency. Then remove affinity at the balancer and verify with a test that hops between instances.

Scenario One API customer complains they are being rate-limited at half their contracted rate. Others are fine. What do you check?

Check whether limits are enforced locally per gateway instance: if the customer uses few long-lived connections (HTTP/2, keep-alive from a single server), their traffic may land on a subset of instances, each enforcing \(L/n\). Check the limiter key (are several of their API keys mapped to one bucket, or is the key the IP of a shared NAT?). Check cost weighting (some endpoints cost more tokens). Check clock skew if the script uses client clocks. Check for retries on their side counting double. Fix with a shared store or correct key.

Scenario During a dependency outage your services survived, but recovery took 20 minutes after the dependency came back. Why might that be?

Likely a thundering herd and retry storm: queued and retried requests, clients with synchronized backoff, cold caches and connection pools all hit the recovered dependency at once and knock it over again. Circuit breakers in half-open state may all probe simultaneously. Mitigations: jittered exponential backoff, retry budgets, gradual ramp-up (slow-start in the balancer for recovered hosts, supported by Envoy and NGINX Plus), admission control/load shedding in the dependency, and warming caches before full traffic.

Conceptual Compare token bucket and leaky bucket.

Both enforce a long-run rate. A token bucket permits bursts up to its capacity after idle periods (admitted traffic can be bursty), and rejects (or delays) when empty. A leaky bucket as a queue emits at a constant rate, smoothing bursts into steady output at the cost of queueing delay, and drops when the queue is full. Use token buckets for API limits where clients legitimately burst; leaky buckets for shaping traffic into a downstream that cannot tolerate bursts. As meters (GCRA), they are mathematically equivalent.

Conceptual What is the difference between liveness and readiness, and why should liveness not check the database?

Liveness answers "should this container be restarted?"; readiness answers "should it receive traffic?". If liveness depends on the database, a database outage causes every pod to be restarted simultaneously, adding cold starts and reconnection storms while fixing nothing. Liveness should detect only process-local failures (deadlock, unrecoverable state). Readiness may reflect startup and shutdown, and instance-local dependencies.

16. Knowledge Check

  • Scale stateless tiers horizontally; scale stateful primaries vertically until partitioning is unavoidable. Amdahl and USL explain why vertical scaling saturates.
  • Statelessness (externalised sessions, tokens, domain-persisted state) is the prerequisite for balancing, autoscaling and zero-downtime deploys.
  • L4 balances connections; L7 balances requests. HTTP/2 and gRPC need L7 or client-side balancing.
  • Least-request with power of two choices adapts to heterogeneous, long-tailed backends without global state or herding.
  • Use active and passive health checks; keep dependencies out of liveness; coordinate preStop, graceful shutdown and grace periods for zero-drop deploys.
  • Keep the shared gateway thin; put client-specific aggregation in BFFs and business rules in services.
  • Token bucket is the default rate-limit algorithm; fixed windows double at boundaries; sliding logs are exact but memory-heavy; sliding window counters are a constant-memory approximation.
  • Global limits need shared, atomic state (Redis + Lua with the server clock) and an explicit fail-open or fail-closed policy.

20 gateway pods each enforce a local limit of 50 requests/s for a client. The client's requests are spread evenly. What is the effective limit?

  1. 50 requests/s
  2. 1,000 requests/s
  3. 2.5 requests/s
  4. Unbounded
Each pod admits 50/s independently; with even spreading the client gets 20 × 50 = 1,000/s. Local limits must be divided by the instance count, or use a shared store.

A token bucket has capacity 100 and rate 10/s. What is the maximum number of requests it can admit in any 10-second interval?

  1. 100
  2. 110
  3. 200
  4. 1,000
The arrival bound is b + r·t = 100 + 10 × 10 = 200: a full bucket's burst plus everything refilled during the interval.

Why does an L4 load balancer often leave newly added gRPC backends idle?

  1. gRPC multiplexes many requests over long-lived HTTP/2 connections, and L4 balances connections, not requests
  2. L4 balancers cannot route TCP traffic
  3. gRPC requires sticky sessions
  4. New backends fail health checks for the first hour
Existing connections stay on existing backends; only new connections reach new pods. L7 balancing, client-side balancing or connection max-age fix it.

Which Kubernetes/Spring configuration best prevents 502s during rolling deploys?

  1. A liveness probe that checks the database
  2. Setting terminationGracePeriodSeconds to 0 for faster rollouts
  3. Sticky sessions at the ingress
  4. A preStop sleep, graceful shutdown, and a grace period longer than both combined
The preStop delay lets endpoint removal propagate before SIGTERM; graceful shutdown completes in-flight requests; the grace period must cover both or SIGKILL cuts requests off.

Why is a Redis-backed limiter implemented as a Lua script rather than GET followed by SET from the application?

  1. Lua is faster than Java
  2. The script runs atomically on Redis's main thread, preventing concurrent instances from double-spending tokens
  3. GET and SET are not available in Redis Cluster
  4. Scripts persist state to disk while GET/SET do not
A read-modify-write from two clients can interleave; a script executes with no other command interleaved and needs only one round trip.

Which concern belongs in a BFF rather than the shared API gateway?

  1. TLS termination
  2. Per-API-key rate limiting
  3. Aggregating three service calls into one compact response for the mobile home screen
  4. JWT signature validation
Client-specific composition and payload shaping belong to that client's BFF; the gateway handles generic edge concerns shared by all consumers.
