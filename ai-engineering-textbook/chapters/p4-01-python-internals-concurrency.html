Python Internals, Memory, the GIL & Concurrency

You already know how the JVM turns bytecode into machine code, how G1 or ZGC reclaims memory, and how a Tomcat thread pool or a virtual-thread executor serves requests. This chapter builds the same mental model for CPython: what a PyObject really is, why reference counting and a cycle collector coexist, why the Global Interpreter Lock exists and what free-threaded Python changes, and how to choose between threads, processes and asyncio for real AI-serving and data workloads.

  • Prerequisites: Comfortable writing Python; solid JVM knowledge (bytecode, JIT, GC, Java Memory Model, ExecutorService, CompletableFuture, virtual threads); basic Go goroutines.
  • You will be able to: read CPython bytecode with dis; predict memory behaviour of long-running Python services; explain the GIL handoff precisely; pick threads vs processes vs asyncio vs free-threading for a given workload; write correct structured-concurrency code with TaskGroup, timeouts and cancellation; and avoid the blocking-call and fork-safety bugs that take Python services down in production.

1. Introduction: Why a Java Engineer Must Understand CPython's Engine Room

Most Java engineers meet Python through a script, a notebook or a small FastAPI service bolted onto a Spring Boot estate to wrap a model. It feels like "Java without the ceremony" until the first production incident: a model-serving endpoint that uses eight threads but saturates exactly one core; an async def handler that stalls the whole process because somebody called requests.get inside it; a Celery worker whose resident memory climbs steadily after every fork even though nothing is "leaking". None of these are explained by Python syntax. They are explained by the runtime: CPython's object model, its memory manager and its concurrency rules.

The runtime matters more in the AI era than it did a decade ago. Python is the control plane of almost every ML system: data pipelines, feature engineering, training orchestration, evaluation harnesses, LLM agents and retrieval services. The heavy numerical work runs in C, C++, CUDA or Rust underneath NumPy, PyTorch, Polars or tokenizers, but the orchestration, the HTTP layer and the glue run in the interpreter. An engineer who can reason about where the interpreter is the bottleneck and where native code has already released the GIL is the one who can make a Python AI service cheap and fast instead of rewriting it in Go out of frustration.

This chapter is deliberately runtime-first. We start with what CPython is (a bytecode interpreter written in C, with no tracing JIT for most of its history), walk through the object model and memory management, then dissect the Global Interpreter Lock, and only then compare the three concurrency models that Python offers: OS threads, processes, and the asyncio event loop. Throughout we compare with the JVM and Go, because the contrasts are where the intuition comes from.

Bridging from Java & Spring Boot

What you already know
The JVM loads .class bytecode, interprets it, and HotSpot's C1/C2 JIT compiles hot methods to native code. Objects live on a managed heap reclaimed by a tracing, generational GC (G1, ZGC, Shenandoah). Java threads are OS threads (platform threads) or, since Java 21, virtual threads mounted on carrier threads. The Java Memory Model defines happens-before; synchronized, volatile and java.util.concurrent give you real parallel execution on every core. Spring MVC hands each request to a Tomcat worker thread; WebFlux uses an event loop (Netty).
Why that is not enough
CPython differs on nearly every axis. It is (by default) an interpreter without a production JIT; memory is reclaimed primarily by reference counting, with a tracing collector only for cycles; and in the default build a single Global Interpreter Lock lets only one thread execute Python bytecode at a time. Intuitions such as "add threads to use more cores" or "GC pauses are the main memory risk" are wrong or incomplete in Python.
The modern approach
Use asyncio (with structured concurrency via TaskGroup and asyncio.timeout) for high-concurrency I/O, processes (or native extensions that release the GIL) for CPU-bound work, and threads for blocking I/O libraries and for offloading from the event loop. Watch the free-threaded build (PEP 703, officially supported since 3.14) as the long-term path to true multi-core threading.
Where Python and Go fit
Python's asyncio is closest to Netty/WebFlux or Kotlin coroutines: cooperative, single-threaded, explicit await points. Go's goroutines are closest to Java virtual threads: preemptively scheduled by the runtime across all cores with blocking-style code. Java virtual threads and Go goroutines give you parallelism for free; Python asyncio gives you concurrency, not parallelism.
In production
Python web services usually run as several processes (Gunicorn/Uvicorn workers), each with its own interpreter and GIL, each running an event loop or a thread pool. Scaling is "more processes per pod, more pods" rather than "bigger thread pool".
Use it when / avoid it when
Use Python where the ecosystem (ML, data, LLM tooling) dominates the value and the interpreter is mostly orchestrating native code or waiting on I/O. Avoid CPU-heavy pure-Python hot loops on the request path, and be wary of Python for ultra-low-latency, high-fan-in gateways where Go or Java will be cheaper per request.

2. History: From a Hobby Interpreter to the Control Plane of AI

Guido van Rossum began Python over the Christmas holidays of 1989 and published version 0.9.0 in February 1991. Its design priorities were readability and easy extension in C. That second priority shaped the runtime more than anything else: the C API exposes the object layout and reference-counting macros directly to extension authors, which is why the runtime has been so hard to change.

Compare this with the JVM, which had a JIT (HotSpot, 1999) and parallel GC early, and whose native interface (JNI) was always awkward enough that the ecosystem stayed in pure Java. Insight

The GIL is not an accident of laziness; it is the price of a C API that lets any extension touch refcounts without locks. Every serious attempt to remove it (Greg Stein's 1999 patch, Larry Hastings' "Gilectomy" around 2016, and finally Sam Gross's nogil work that became PEP 703) had to solve the same problem: make refcounting thread-safe without making single-threaded code much slower.

3. Fundamentals: The Concepts Under Everything

3.1 Source, bytecode and the code object

CPython compiles each module to a tree of code objects. A code object (type code) is roughly the equivalent of a compiled Java method plus its constant pool entry: it holds the bytecode (co_code), constants (co_consts), local variable names (co_varnames), free/cell variable names for closures, the exception table (3.11+) and line tables. Compiled modules are cached as .pyc files in __pycache__, keyed by interpreter version: the analogue of .class files, except they are an implementation detail and can change format between minor versions.

Unlike the JVM, there is no verifier, no class loading/linking phase with constraints, and no ahead-of-time type information. Every operation (a + b) is resolved dynamically at runtime by looking at the types of the operands. That dynamic dispatch is the core cost the interpreter pays and the thing the 3.11+ "specialising adaptive interpreter" attacks.

3.2 Everything is an object (and every object is a PyObject)

In Java, int is a primitive stored inline in a register or an array slot and Integer is a boxed object. Python has no primitives: 42, True, None, a function, a class, a module and a code object are all heap-allocated objects with a common header. In C, every object begins with:

PyObject (default, GIL build, 64-bit)          PyVarObject (lists, tuples, ints...)
+-------------------------+                    +-------------------------+
| ob_refcnt  (8 bytes)    |                    | ob_refcnt  (8 bytes)    |
| ob_type -> PyTypeObject |                    | ob_type    (8 bytes)    |
+-------------------------+                    | ob_size    (8 bytes)    |
| ...type-specific fields |                    +-------------------------+
                                               | ...items / digits       |

Compare with a HotSpot object header: a mark word (hash, lock state, GC age) plus a compressed class pointer, 12–16 bytes. CPython's header is 16 bytes for fixed-size objects and 24 for variable-size ones, and objects that participate in cycle collection carry an extra GC header in front (two words in older versions, pointer-tagged in newer ones). A Python int holding 1 is 28 bytes; a Java int is 4. This is why a Python list of a million floats costs roughly 8 MB of pointers plus 24 MB of float objects, while a NumPy array costs 8 MB flat. The "everything is an object" model is the single biggest reason numerical Python must live in native arrays.

The ob_type pointer leads to a PyTypeObject, which is a vtable of C function pointers (tp_hash, tp_call, tp_getattro, tp_as_number->nb_add...). When the interpreter executes a + b, it ultimately calls Py_TYPE(a)->tp_as_number->nb_add(a, b), falling back to the reflected method on b. Classes you define in Python are also PyTypeObjects whose slots point to generic wrappers that look up __add__ in the class dictionary.

3.3 Names, not variables

A Python variable is a name bound to an object reference, stored in a dict (module globals), a fast-locals array (function locals), or a cell (closures). Assignment never copies an object; it increments a reference count and rebinds a name. This is the same as Java reference semantics for objects, but it applies to numbers too, so x = 1000; y = x makes both names point at one int object. Because ints are immutable, the difference is only visible through is and id().

3.4 Small-integer cache, interning and immortal objects

To avoid allocating an object for every loop counter, CPython pre-allocates the integers from -5 to 256 at startup; int creation in that range returns the shared singleton. Java's Integer.valueOf cache (-128 to 127) is exactly the same trick, and causes exactly the same bug class: comparing with is (Python) or == on boxed Integer (Java) "works" for small values and fails for large ones.

String interning stores one canonical copy of certain strings in an interned dictionary. Identifiers, attribute names and short identifier-like literals are interned automatically by the compiler, so attribute lookups can compare pointers before comparing characters. You can force it with sys.intern(), which is occasionally useful when you hold millions of repeated short keys (e.g. feature names in a parsed dataset) in memory; Java's String.intern() and G1's string deduplication solve the same problem.

Since 3.12 (PEP 683), objects like None, True, small ints and interned strings can be immortal: their reference count is set to a special value and increments/decrements leave it alone. This avoids writes to shared objects, which matters for two things: copy-on-write after fork (touching a refcount dirties a memory page) and free-threading (contended atomic writes to the refcount of None would be a disaster). Meta's engineering blog describes how immortalisation was motivated by Instagram's pre-fork server model.

3.5 Reference counting

Every time a reference is created (a name binding, a list slot, an argument passed on the stack), Py_INCREF increments ob_refcnt; when it is dropped, Py_DECREF decrements it, and if it reaches zero the type's tp_dealloc runs immediately, which may cascade to the objects it references. Consequences:

  • Deterministic destruction. A file object that goes out of scope is closed immediately in CPython. Do not rely on it (PyPy and free-threaded builds may delay it), but it explains why sloppy Python often "works" where equivalent Java would leak file handles until finalisation.
  • No stop-the-world pauses for acyclic garbage. The cost is spread across every assignment instead of concentrated in GC pauses.
  • Constant write traffic. Even reading an object (passing it to a function) writes to its header. That destroys copy-on-write sharing after fork and makes thread-safe refcounting expensive.
  • Cycles never reach zero. Hence the second collector.

3.6 The cyclic garbage collector

Container objects (lists, dicts, class instances, closures) are tracked by a generational cycle collector. It does not trace from roots like the JVM; instead it finds groups of objects whose reference counts are fully explained by references from inside the group. Those groups are unreachable from outside and can be freed. Collection is triggered by allocation counts: when allocations minus deallocations of tracked objects exceed a threshold (700 by default for the young generation historically; tunable with gc.set_threshold), a young collection runs; survivors are promoted. The details changed across versions, and 3.14 briefly shipped an incremental collector that was reverted in 3.14.5 because some applications saw memory growth Version-sensitive · checked Nov 2026. We go step-by-step through the algorithm in §4.

3.7 pymalloc: arenas, pools and blocks

Allocating every 28-byte int with malloc would be slow and fragment badly, so CPython has its own small-object allocator for requests of 512 bytes or less. It is a three-level hierarchy:

Arena (1 MiB on 64-bit since 3.10; mmap'd)
 +-- Pool (16 KiB since 3.10; one size class per pool)
 |    +-- block 32 B | block 32 B | block 32 B | ... (free list threaded through blocks)
 +-- Pool (size class 48 B)
 |    +-- block 48 B | block 48 B | ...
 +-- ...
Size classes are multiples of 16 bytes: 16, 32, 48, ... 512
Requests > 512 bytes go straight to the system malloc (or mimalloc in free-threaded builds)

An arena is returned to the OS only when every pool in it is empty. A long-running service that allocates a burst of objects, frees most of them, and keeps a few survivors scattered across many arenas will show high RSS that never comes down. That is not a leak in the Java sense; it is fragmentation, and it is the Python equivalent of a JVM heap that has grown to -Xmx and never shrinks. Mitigations: recycle worker processes (Gunicorn --max-requests, Celery worker_max_tasks_per_child), avoid creating huge numbers of tiny long-lived objects (use arrays, __slots__, NumPy), and measure with tracemalloc. Free-threaded builds use mimalloc instead of pymalloc because pymalloc's pools are protected by the GIL.

3.8 The GIL in one paragraph

The Global Interpreter Lock is a mutex (plus a condition variable and some flags) inside the interpreter state. A thread must hold it to execute bytecode or touch Python objects. A thread drops it when it performs blocking I/O, calls time.sleep, or when a C extension explicitly releases it (Py_BEGIN_ALLOW_THREADS), and it is asked to drop it when another thread has been waiting longer than the switch interval (5 ms by default, sys.getswitchinterval()). So two threads doing pure-Python arithmetic interleave on one core; two threads each waiting on a socket or each running a NumPy matrix multiply genuinely overlap.

3.10 Coroutines, tasks and futures

A coroutine is the object returned by calling an async def function; nothing runs until it is awaited or wrapped in a task. A Task is a coroutine scheduled on the event loop: the loop repeatedly calls its send() method, and each time the coroutine hits an await on something not yet ready it suspends, yielding a Future back to the loop. A Future is a placeholder for a result with callbacks, the direct analogue of CompletableFuture, except that it is not thread-safe and belongs to one loop. concurrent.futures.Future is a different, thread-safe class used by executors; asyncio.wrap_future bridges them.

3.11 The event loop

An event loop is a single-threaded scheduler: a ready queue of callbacks, a heap of timers, and a selector (epoll/kqueue/IOCP) for I/O readiness. Each iteration runs all ready callbacks, computes the timeout until the next timer, blocks in epoll_wait for at most that long, and then queues callbacks for sockets that became ready. Netty's NioEventLoop is the same design. The consequence you must internalise: any callback that runs for 100 ms blocks every other connection in that process for 100 ms.

3.12 Structured concurrency

Structured concurrency means that concurrent tasks have a lexical scope: they start inside a block and are guaranteed finished (completed, failed or cancelled) when the block exits. Python's asyncio.TaskGroup (3.11), Trio's nurseries, Java's StructuredTaskScope (preview since JDK 21) and Go's errgroup all express this. It solves the "orphaned background task" bug class: a task that keeps running after the request that spawned it has failed.

4. Internal Working: From def to Machine, Step by Step

4.1 Compilation pipeline

When you import a module, CPython checks for a valid .pyc; if absent or stale, it runs: tokenizer → PEG parser (since 3.9, PEP 617) → AST → symbol table (decides which names are local, global, free or cell) → compiler emitting a control-flow graph → peephole/flow-graph optimiser → assembler producing the code object. Then the module's top-level code object is executed, which defines functions (creating function objects that wrap nested code objects) and classes.

Let us read real bytecode. The exact opcodes vary by version; this is what 3.13 produces (run it yourself, the shape is what matters):

    s = 0
    for it in items:
        s += it.price * it.qty
    return s * (1 + tax)

The crucial difference: imul knows its operands are ints; BINARY_OP 5 does not, so the generic version has to check types and dispatch through nb_multiply every time.

4.2 The evaluation loop and the specialising adaptive interpreter

The heart of CPython is _PyEval_EvalFrameDefault in Python/ceval.c (since 3.12 largely generated from a DSL in Python/bytecodes.c). Conceptually it is a giant switch (or computed-goto table, or in 3.14+ optionally a tail-calling interpreter on supported compilers) over opcodes:

for (;;) {
    opcode = next_instr->op.code;   // fetch
    switch (opcode) {               // dispatch (computed goto in practice)
    case LOAD_FAST:  PUSH(frame->localsplus[oparg]); Py_INCREF(top); break;
    case BINARY_OP:  right = POP(); left = TOP();
                     res = binary_ops[oparg](left, right);   // generic dispatch
                     Py_DECREF(left); Py_DECREF(right); SET_TOP(res); break;
    ...
    }
    if (eval_breaker_is_set) handle_pending();   // GIL drop request, signals, async exc
}

Since 3.11 (PEP 659) the interpreter is adaptive. Each instruction that benefits from type information has inline cache entries. After an instruction executes a few times (a warm-up counter), it is quickened into a specialised variant based on observed types: BINARY_OP on two ints becomes BINARY_OP_MULTIPLY_INT; LOAD_ATTR on instances of one class becomes LOAD_ATTR_INSTANCE_VALUE that checks a type version tag and reads the attribute at a cached offset. If the guard fails too often, it de-specialises. Run dis.dis(total_price, adaptive=True) after calling the function a few hundred times and you will see the specialised opcodes.

This is the same idea as HotSpot's inline caches and type profiling in the interpreter tier, minus the compiler tier. It is why 3.11 was roughly 25% faster than 3.10 on the pyperformance suite (the figure the release notes quote), and why the experimental JIT (3.13+, "copy-and-patch") is built on top of these specialised "micro-ops": it stitches pre-compiled machine-code templates for each micro-op into a trace. As of 3.15 the JIT remains experimental and off by default in most builds Version-sensitive · checked Nov 2026.

4.3 Frames

Each call creates a frame holding the code object, the instruction pointer, the locals array and the value stack. Since 3.11 frames are allocated in a contiguous per-thread "data stack" and only materialised as full PyFrameObjects when something (a traceback, a debugger, sys._getframe) needs them. Function calls between Python functions no longer recurse on the C stack (3.11 "inlined" Python-to-Python calls), which made calls cheaper and deep recursion safer. Coroutine and generator frames are stored inside the generator object itself, which is why a suspended coroutine costs only a few hundred bytes to a couple of KB: far less than a thread stack, comparable to a goroutine's 2 KB initial stack or a virtual thread's heap-allocated stack chunk.

4.4 Reference-counting in action

import sys

class Node:
    def __init__(self, name):
        self.name = name
        self.peer = None
    def __del__(self):
        print(f"freed {self.name}")

a = Node("a")
print(sys.getrefcount(a))   # 2: the name 'a' + the temporary argument reference
b = a
print(sys.getrefcount(a))   # 3
del b
del a                       # refcount hits 0 -> "freed a" printed immediately

x, y = Node("x"), Node("y")
x.peer, y.peer = y, x       # a cycle
del x, y                    # nothing printed: each still referenced by the other
import gc
print("collected", gc.collect())   # "freed x", "freed y", then collected 2 (or more)

In 3.14+ some reference-count operations on local variables are elided by the compiler ("borrowed" references on the stack), so sys.getrefcount can report smaller numbers than older versions. Never write logic that depends on the exact count.

4.5 How the cycle collector finds garbage

The algorithm, for one generation being collected:

  1. Copy refcounts. For every tracked container in the generation, copy ob_refcnt into a scratch field gc_refs.
  2. Subtract internal references. For each container, call its tp_traverse, which visits every object it references; for each referenced object in the same generation, decrement its gc_refs. Now gc_refs counts only references from outside the generation (from older generations, from C stack variables, from the interpreter).
  3. Seed reachable set. Any object with gc_refs > 0 is definitely reachable from outside. Move everything else to a tentatively-unreachable list.
  4. Propagate. Traverse from each reachable object; anything it references that was tentatively unreachable is moved back to reachable.
  5. Finalise and free. What remains is unreachable cyclic garbage. Call finalisers (__del__, PEP 442 made this safe for cycles in 3.4), handle weakref callbacks, resurrected objects are re-checked, then tp_clear breaks the cycles and refcounting frees everything.
  6. Promote survivors to the next generation.

Notice the difference from a JVM tracing GC: CPython never needs to know the roots. The "roots" are implicit in the refcounts that are not explained by internal edges. The trade-off is that a full collection has to touch every tracked container in the process, which on a heap of tens of millions of dicts can take hundreds of milliseconds and, under the GIL, blocks every thread. That is the Python analogue of a long G1 mixed collection, and the reason large services tune gc.set_threshold or call gc.freeze() after start-up.

Java angle

gc.freeze() (3.7+) moves every currently tracked object into a permanent generation that the collector ignores. Calling it in a pre-fork server after loading the application and before forking workers is the Python version of class data sharing plus "don't scan the old gen": workers stop dirtying shared pages during collections. Instagram's 2017 post on copy-on-write friendly GC describes exactly this motivation.

4.6 The GIL handoff in detail

The "new GIL" (3.2+) works like this. The lock has a locked flag, a mutex, a condition variable, a switch_number counter and a drop_gil_request flag that is part of the eval breaker.

  1. Thread T1 holds the GIL and runs bytecode.
  2. Thread T2 wants it. It waits on the condition variable with a timeout equal to the switch interval (5 ms).
  3. If the wait times out and the switch_number has not changed (T1 has held the GIL the whole time), T2 sets drop_gil_request, which sets the eval breaker.
  4. T1, at its next eval-breaker check (on backward jumps and function entries, roughly every few instructions), sees the request, releases the GIL, signals the condition variable, and (with FORCE_SWITCHING) waits until another thread has actually taken it, so it cannot immediately re-grab it.
  5. T2 acquires the GIL and runs. switch_number increments.

If T1 instead performs a blocking system call (socket read, file read, time.sleep, lock.acquire), the C code wraps it in Py_BEGIN_ALLOW_THREADS/Py_END_ALLOW_THREADS and releases the GIL voluntarily. That is why I/O-bound threading works well in Python: while one thread waits for PostgreSQL, others run.

The convoy effect remains: an I/O thread that needs the GIL for just a microsecond after each recv may wait up to 5 ms behind a CPU-bound thread. Mixing a CPU-heavy thread with latency-sensitive I/O threads in one process therefore inflates tail latency in steps of the switch interval. Do not mix them; move CPU work to processes.

4.7 Free-threaded CPython: what actually changed

PEP 703 removes the GIL in a separate build (python3.13t/python3.14t; check with sys._is_gil_enabled()). Making that safe required:

  • Biased reference counting. Each object has a thread-local refcount field owned by the creating thread (non-atomic increments, cheap) and a shared field for other threads (atomic). Most objects are only touched by their owner, so most refcount operations stay cheap.
  • Immortalisation and deferred refcounting for objects like functions, code objects and module-level globals that are touched by every thread.
  • mimalloc replacing pymalloc, giving thread-safe allocation and the ability to scan heap pages for GC (the GC becomes stop-the-world across threads, closer to a classic tracing collector).
  • Per-object locks ("critical sections") inside builtin containers, so list.append from two threads stays safe, plus optimistic lock-free reads for dict and list item access.

The cost: single-threaded code was around 40% slower in 3.13's free-threaded build and the gap narrowed substantially in 3.14 (the PEP 779 acceptance criteria targeted at most about 10–15% overhead) Version-sensitive · checked Nov 2026. The bigger practical issue is extensions: a C extension that has not declared itself free-threading-safe causes the interpreter to re-enable the GIL at import time (with a warning) unless you force PYTHON_GIL=0. In 2026 the scientific stack (NumPy, and many others) ships free-threaded wheels, and 3.15's abi3t stable ABI lowers the maintenance burden, but you must verify every native dependency before relying on it.

4.8 How asyncio runs a coroutine

Under the hood, await is yield from on an awaitable's __await__ iterator. Walk through await reader.read(100) on a socket with no data:

  1. The Task's __step method calls coro.send(None).
  2. Execution reaches StreamReader.read, which finds its buffer empty and awaits a fresh Future (self._waiter).
  3. Future.__await__ yields itself up through every await in the chain to the Task.
  4. The Task sees a Future, registers self.__wakeup as its done-callback, and returns to the loop. The coroutine frame is suspended in memory.
  5. The loop's selector reports the socket readable; the transport's _read_ready callback reads bytes, feeds them to the protocol, which feeds the StreamReader, which calls self._waiter.set_result(None).
  6. Setting the result schedules the Future's callbacks with loop.call_soon; next iteration, Task.__wakeup runs, calls __step, which calls coro.send(None) again, and the coroutine resumes after the await.

Cancellation is the same machinery in reverse: task.cancel() arranges for __step to call coro.throw(CancelledError()) at the suspension point. The coroutine can catch it to clean up (it must re-raise it, or call uncancel() deliberately), which is how asyncio.timeout and TaskGroup implement deadlines and sibling cancellation.

The C-accelerated _asyncio module implements Task and Future in C since 3.6; uvloop goes further and replaces the loop and transports with Cython code over libuv, typically giving meaningfully higher throughput for socket-heavy workloads (the project's own benchmarks claim 2–4x versus the default loop; treat as vendor benchmark and measure your own).

4.9 multiprocessing start methods

  • fork: fork() the parent; the child gets a copy-on-write image of everything, including locks held by other threads (which will never be released in the child, a classic deadlock), open sockets and the state of any thread pools (threads are not copied, only the calling thread exists in the child). Fast start, dangerous with threads.
  • spawn: start a fresh interpreter and import the main module, then unpickle the target function and arguments. Safe, slow (hundreds of ms to seconds when importing PyTorch), and requires the if __name__ == "__main__": guard. Default on Windows and macOS (since 3.8).
  • forkserver: a clean single-threaded server process is started early; children are forked from it. A compromise: faster than spawn, safer than fork. Default on Linux since 3.14 Version-sensitive · checked Nov 2026; code that silently relied on fork inheriting globals breaks when upgrading.

Arguments and results cross process boundaries by pickling over pipes. For large arrays use multiprocessing.shared_memory.SharedMemory (3.8+) and wrap the buffer with NumPy, so only a name crosses the pipe.

6. The Math: Amdahl, the GIL, Little's Law and Memory Arithmetic

6.1 Amdahl's law with a GIL

Intuition: if a fraction of each request must run while holding a global lock, that fraction is serialised no matter how many threads you add. Amdahl's law gives the ceiling. Let \( p \) be the fraction of work that can proceed without the GIL (I/O waits, native code that releases it) and \( N \) the number of threads:

\[ S(N) = \frac{1}{(1-p) + \frac{p}{N}} \qquad \lim_{N \to \infty} S(N) = \frac{1}{1-p} \]

A request that spends 90% of its wall time waiting on PostgreSQL and an LLM API and 10% executing Python (\( p = 0.9 \)) can get at most a 10x speed-up from threads within one process: one core's worth of Python execution is the cap. If the request is 50% Python serialisation and validation, the ceiling is 2x. That is why Python services scale with processes: each process has its own GIL, so with \( W \) workers the serial fraction is divided across \( W \) independent locks.

6.2 Little's Law for sizing workers and concurrency

Little's Law relates average concurrency \( L \), throughput \( \lambda \) and latency \( W \): \( L = \lambda W \). For an async service handling 2,000 requests per second where each request awaits an upstream for 150 ms, you need \( L = 2000 \times 0.15 = 300 \) in-flight requests. With asyncio, 300 suspended coroutines are trivial (a few hundred KB). With a thread-per-request model you need 300 threads; feasible in Python, but each has an 8 MB virtual stack reservation and contends for the GIL on every wakeup.

The CPU side is different: if each request needs 2 ms of Python CPU, one process can sustain at most \( 1 / 0.002 = 500 \) requests/s regardless of concurrency model. 2,000 req/s therefore needs at least 4 worker processes, and with a safe target utilisation of about 60–70%, six. This two-sided calculation (concurrency from Little's Law, process count from CPU per request) is the core of Python capacity planning.

6.4 Cost model of the interpreter

A useful rule of thumb Opinion: a simple bytecode instruction costs on the order of 5–30 ns in CPython 3.12+, so a pure-Python loop body of 10 instructions runs at roughly 5–20 million iterations per second per core. HotSpot's C2-compiled loop doing the same arithmetic runs 50–100x faster. A Go loop is in the same range as Java. If your hot path executes more than a few million Python-level operations per request, you will be CPU-bound, and no concurrency model will rescue you; vectorise or move it native.

6.5 GC trigger arithmetic

The young collection triggers when \( \text{allocations} - \text{deallocations} > \text{threshold}_0 \). With the classic default of 700, a request that creates 70,000 container objects and keeps them until the end of the request triggers about 100 young collections, each traversing the young generation. Raising threshold0 to 50,000 (as some large services do) cuts collections by 70x at the cost of larger young generations. Survivors promote; older generations collect when their counters exceed their thresholds, and the full collection is additionally rate-limited by the ratio of pending to long-lived objects (the 25% rule, which avoids quadratic behaviour when building big data structures).

7.1 Proving the GIL: CPU-bound work with threads vs processes

7.2 I/O-bound fan-out: CompletableFuture vs asyncio TaskGroup vs errgroup

A realistic AI-backend task: given a user query, call an embedding service, a feature store and a policy service concurrently, with an overall deadline, failing fast if any call fails.

// Java 21+, virtual threads + HttpClient
import java.net.URI;
import java.net.http.*;
import java.time.Duration;
import java.util.concurrent.*;

public class FanOut {
    static final HttpClient http = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(1)).build();

    static String get(String url) throws Exception {
        var req = HttpRequest.newBuilder(URI.create(url)).timeout(Duration.ofSeconds(2)).build();
        return http.send(req, HttpResponse.BodyHandlers.ofString()).body();  // blocking is fine on a virtual thread
    }

    public static void main(String[] args) throws Exception {
        try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
            var emb = CompletableFuture.supplyAsync(() -> call("http://localhost:8081/embed"), exec);
            var feat = CompletableFuture.supplyAsync(() -> call("http://localhost:8082/features"), exec);
            var pol = CompletableFuture.supplyAsync(() -> call("http://localhost:8083/policy"), exec);
            CompletableFuture.allOf(emb, feat, pol).orTimeout(3, TimeUnit.SECONDS).join();
            System.out.println(emb.join() + feat.join() + pol.join());
        }
        // Note: allOf does NOT cancel siblings on failure; StructuredTaskScope (preview) does.
    }
    static String call(String u) { try { return get(u); } catch (Exception e) { throw new CompletionException(e); } }
}

7.3 Calling blocking code from asyncio correctly

import asyncio
import hashlib
import time
from concurrent.futures import ProcessPoolExecutor

def legacy_blocking_lookup(key: str) -> str:
    time.sleep(0.2)                      # e.g. a sync SDK with no async variant
    return key.upper()

def cpu_heavy_fingerprint(data: bytes) -> str:
    h = data
    for _ in range(200_000):             # pure-Python CPU work holding the GIL
        h = hashlib.sha256(h).digest()
    return h.hex()

async def handler(key: str, payload: bytes, pool: ProcessPoolExecutor) -> tuple[str, str]:
    loop = asyncio.get_running_loop()
    # I/O-ish blocking call: default thread pool is fine (GIL released during sleep/socket wait)
    looked_up = await asyncio.to_thread(legacy_blocking_lookup, key)
    # CPU-bound: a thread would still hold the GIL most of the time -> use a process pool
    fp = await loop.run_in_executor(pool, cpu_heavy_fingerprint, payload)
    return looked_up, fp

async def main():
    with ProcessPoolExecutor(max_workers=4) as pool:
        results = await asyncio.gather(*(handler(f"k{i}", b"x" * 64, pool) for i in range(8)))
        print(results[:2])

if __name__ == "__main__":
    asyncio.run(main())

Note that SHA-256 itself is implemented in C and releases the GIL for large inputs, but this loop hashes 32 bytes 200,000 times, so interpreter overhead dominates: a good example of why "it calls C code" is not the same as "it releases the GIL". Profile first.

7.4 Cancellation and timeouts done right

import asyncio
import contextlib

class Conn:
    async def close(self): await asyncio.sleep(0.01); print("conn closed")

async def stream_tokens(conn: Conn):
    try:
        for i in range(100):
            await asyncio.sleep(0.05)     # e.g. reading tokens from an LLM stream

        print("cancelled: flushing partial state")

        await asyncio.shield(conn.close())

            await stream_tokens(conn)
    print("deadline handled; event loop still healthy")

7.7 Thread-safety still matters with the GIL

import threading

counter = 0
def work():
    global counter
    for _ in range(1_000_000):
        counter += 1        # LOAD_GLOBAL, BINARY_OP, STORE_GLOBAL: a switch can occur between them

threads = [threading.Thread(target=work) for _ in range(4)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)   # may be < 4,000,000 on any build; very likely on free-threaded builds

# Fix: protect the read-modify-write
lock = threading.Lock()
def safe_work():
    global counter
    for _ in range(1_000_000):
        with lock:
            counter += 1

The GIL makes individual bytecodes atomic, not your read-modify-write sequences. It is like a JVM where every bytecode is synchronized but your methods are not. Whether the race is observable in a given run depends on version and timing (3.10+ only checks the eval breaker at certain instructions, so the race is rarer than it used to be), which makes such bugs nastier, not safer. Free-threading makes it routine.

8. Applications: How Engineering Teams Use These Models

8.1 LLM gateways and RAG services: asyncio all the way down

A retrieval-augmented generation endpoint spends almost all of its wall time waiting: on a vector database, on a reranker, on an LLM provider that streams tokens for several seconds. Teams build these on FastAPI or Starlette with async clients (httpx, the async variants of provider SDKs, asyncpg/psycopg 3) so that one process can hold hundreds or thousands of concurrent streams. The CPU-heavy parts (tokenisation via Rust-based tokenizers, JSON parsing with orjson, embedding math in NumPy) are native and short. This is the sweet spot for Python concurrency.

8.2 Model inference servers: threads around native kernels

PyTorch, ONNX Runtime and TensorFlow release the GIL inside their kernels and run their own intra-op thread pools. Inference servers therefore typically use a small number of threads or a dedicated executor for model(batch), and an asyncio front end that batches requests (dynamic batching) before handing them over. Tools like NVIDIA Triton, Ray Serve and vLLM separate the Python orchestration from C++/CUDA execution engines for the same reason.

8.3 Data pipelines: processes and vectorisation

ETL and feature-engineering jobs use processes (multiprocessing, Dask, Ray, Spark's Python workers) or move to columnar engines (Polars, DuckDB, Arrow) whose Rust/C++ cores are multi-threaded internally. Pure-Python row-by-row loops are the first thing a performance review eliminates.

8.4 Background workers: prefork pools

Celery's default prefork pool is a multiprocessing pool: N child processes, each executing one task at a time. That gives CPU parallelism and isolation (a segfaulting C extension kills one child, not the worker). For I/O-heavy tasks, teams switch to gevent/eventlet pools or to async-native queues such as arq; Chapter 4.3 covers this in depth.

8.5 Pre-fork web servers

Gunicorn loads the application in a master process and forks workers. With preload_app = True the imported code and data are shared copy-on-write, saving memory, until refcount writes and GC traversal dirty the pages. This is exactly the context of Instagram's GC work described next.

9. Case Studies

9.1 Instagram: disabling, then taming, the cycle collector

Verified Instagram's engineering team reported in 2017 that its Django web tier, which ran as uWSGI pre-forked workers, lost shared memory as soon as workers started handling requests. The cause was that refcount updates and GC traversals wrote to object headers in shared pages, triggering copy-on-write. Disabling the cycle collector reduced memory and let them run with about 10% more efficiency. A follow-up post described a more principled solution, contributed upstream as gc.freeze() in Python 3.7, letting them re-enable GC while keeping startup objects out of collection. Later, Meta's work on immortal objects (PEP 683, Python 3.12) went further by preventing refcount writes to shared objects entirely.

Lesson for Java engineers: in the JVM, sharing memory between processes is rare (CDS archives aside). In Python, pre-fork sharing is a mainstream memory optimisation, and the runtime's write-heavy memory management fights it.

9.2 Meta's Cinder and the Faster CPython effort

Verified Meta open-sourced Cinder, its performance-oriented CPython fork used for Instagram, which included a method-at-a-time JIT, "Static Python" that uses type annotations for faster code, and eager evaluation of coroutines. Several ideas flowed upstream: eager task factories in asyncio (asyncio.eager_task_factory, 3.12) and immortal objects. In parallel, the Faster CPython project (initially funded by Microsoft, 2021) delivered the specialising adaptive interpreter in 3.11.

9.3 Dropbox: type checking at scale (and why it matters for concurrency)

Verified Dropbox's 2019 post describes type checking 4 million lines of Python with mypy. Large async codebases especially benefit: forgetting an await produces a coroutine object instead of a value, a bug that type checkers catch immediately (pyright and mypy flag unused coroutines). Chapter 4.2 explores typing in depth.

9.4 Netflix: Python where it is strong

Verified Netflix's 2019 "Python at Netflix" post on its technology blog describes Python across security automation, operations tooling, ML and notebooks, alongside a predominantly JVM service tier. 12. Common Mistakes and Production Failures

  1. Blocking calls in async def. requests, time.sleep, sync DB drivers, open().read() of large files, CPU-heavy JSON parsing of a 50 MB payload. Symptom: p99 latency equal to the slowest request in the process, loop-lag spikes. Fix: async libraries, asyncio.to_thread, process pool.
  2. Fire-and-forget tasks that get garbage-collected. The loop keeps only weak references to tasks. asyncio.create_task(send_audit_event()) without storing the task can be collected mid-execution. Keep a strong reference set (and discard in a done-callback) or use a TaskGroup.
  3. Swallowing CancelledError. except Exception does not catch it (it inherits from BaseException since 3.8), but except BaseException or a bare except: does. Result: timeouts that never fire and shutdowns that hang.
  4. Assuming the GIL makes code thread-safe. See §7.7. Check-then-act on dicts, lazy singletons and counters all race.
  5. Fork after threads. Forking a process that has running threads (a logging handler thread, a gRPC channel, an OpenTelemetry exporter) can deadlock the child on a lock that was held at fork time. 3.12+ emits a DeprecationWarning; 3.14 moved the default to forkserver. Create clients after fork (Gunicorn post_fork, Celery worker_process_init).
  6. Unbounded gather. await asyncio.gather(*[fetch(u) for u in ten_thousand_urls]) opens 10,000 sockets at once and is the async equivalent of an unbounded thread pool. Bound with an asyncio.Semaphore or a worker-queue pattern.
  7. Reading RSS as a leak. pymalloc fragmentation and arenas that cannot be released look like leaks. Use tracemalloc snapshots to compare live allocations before concluding.
  8. Calling asyncio.run inside a running loop (e.g. inside a FastAPI handler or a Jupyter cell). It raises RuntimeError; restructure so the loop is created once at the top.
  9. Huge thread pools for CPU work. A 64-thread pool for pure-Python work only adds GIL contention and context switching.
  10. Relying on __del__ for resource cleanup. Order is not guaranteed for cycles, and free-threaded/PyPy builds delay it. Use context managers, exactly as you would use try-with-resources instead of finalize().

13. Production: Performance, Reliability and Observability

13.1 Process topology

Run one worker process per core you intend to use (fewer if native libraries use their own thread pools), with asyncio inside each for I/O concurrency. In Kubernetes, prefer several smaller pods (e.g. 2 CPUs, 2–4 workers) over one huge pod: it bounds blast radius and simplifies autoscaling. Set CPU limits carefully; CPython does not read cgroup quotas to size anything automatically, so os.cpu_count() returns the node's cores. Use os.process_cpu_count() (3.13+, respects affinity) or configure worker counts explicitly.

13.2 Memory hygiene

  • Recycle workers periodically (--max-requests with jitter) to cap fragmentation.
  • For pre-fork servers, load the app in the master, call gc.freeze() before forking, and disable or tune GC thresholds after measuring.
  • Use __slots__ or dataclasses with slots=True for millions of small objects; NumPy/Arrow for numeric data.
  • Monitor RSS, Python heap (tracemalloc in canaries) and GC pause time (gc.callbacks to time collections).

13.3 Observability of concurrency

  • Event-loop lag as a histogram metric (code in §7.6). Alert on p99 above tens of ms.
  • Sampling profiler: py-spy top --pid and py-spy dump (all threads' stacks without stopping the process) are the jstack/async-profiler of Python. py-spy record --gil shows only samples where the GIL is held, which identifies GIL hogs. 3.15 also ships a sampling profiler in the stdlib (profiling.sampling, "Tachyon") Version-sensitive · checked Nov 2026.
  • asyncio introspection: asyncio.all_tasks() plus task names; 3.14 added python -m asyncio ps PID and pstree to inspect running tasks of a live process.
  • Tracing: OpenTelemetry's context propagation uses contextvars, which automatically flow into tasks created with create_task (each task copies the current context), the analogue of MDC propagation that Java needs special executors for.

13.4 Reliability patterns

  • Every outbound call has a timeout; every request handler runs under an overall asyncio.timeout.
  • Bound concurrency with semaphores per downstream (bulkheads).
  • Graceful shutdown: on SIGTERM stop accepting, cancel the TaskGroup or wait with a deadline, flush telemetry, close pools.
  • Keep CPU-heavy work out of the web tier: queue it (Celery/arq) or use a dedicated process pool sized separately.

13.5 Security notes

Never unpickle data from untrusted sources: pickle (used by multiprocessing and many task queues) executes arbitrary code during deserialisation, just like Java native serialisation gadgets. Use JSON/msgpack/protobuf for anything crossing a trust boundary. Also be aware that thread-local or contextvars state that holds tenant IDs must be reset per request; leaking it across tasks is a data-isolation bug.

14. Exercises

Exercise 1 · Foundation

Predict, then verify with dis, why x = x + 1 on a global is not atomic but lst.append(1) on a shared list is atomic in the GIL build. What changes in the free-threaded build?

Solution

x = x + 1 compiles to LOAD_GLOBAL x, LOAD_CONST 1, BINARY_OP +, STORE_GLOBAL x: four instructions; a GIL switch between load and store loses an update. lst.append(1) is a single call into C (list_append) that does not release the GIL, so it executes atomically. In the free-threaded build the list's internal per-object lock (critical section) keeps append safe, while the global read-modify-write still races, now far more often because threads truly run in parallel. In both builds use a threading.Lock or restructure to thread-confined state plus a queue.

Exercise 2 · Intermediate

Write a bounded-concurrency async crawler: fetch 1,000 URLs with at most 50 in flight, an overall 30-second deadline, per-request 5-second timeouts, and collect failures without cancelling siblings.

Solution
import asyncio, httpx

async def crawl(urls: list[str], limit: int = 50) -> tuple[dict[str, int], dict[str, str]]:
    sem = asyncio.Semaphore(limit)
    ok: dict[str, int] = {}
    failed: dict[str, str] = {}

    async def one(client: httpx.AsyncClient, url: str) -> None:
        async with sem:
            try:
                r = await client.get(url, timeout=5.0)
                ok[url] = r.status_code
            except httpx.HTTPError as e:          # record, do not raise: siblings keep going
                failed[url] = type(e).__name__

    async with httpx.AsyncClient(limits=httpx.Limits(max_connections=limit)) as client:
        try:
            async with asyncio.timeout(30):
                async with asyncio.TaskGroup() as tg:
                    for u in urls:
                        tg.create_task(one(client, u))
        except TimeoutError:
            pass                                   # whatever finished is in ok/failed
    return ok, failed

Catching errors inside one is the deliberate choice to not fail fast; the TaskGroup then only cancels on the deadline. For 1,000 tasks, creating them all up front is fine; for 10 million, use a fixed set of worker tasks pulling from an asyncio.Queue to bound memory.

Exercise 3 · Advanced

A FastAPI service's p99 latency jumped from 40 ms to 900 ms after a release that added "PII redaction" using a regex over each response body. CPU is 35% per pod. Explain the mechanism and propose two fixes with trade-offs.

Solution

The redaction runs synchronously in an async def handler, on the event loop. A large body takes hundreds of ms of regex work holding the loop (and the GIL), so every other request in that worker waits: latency becomes the sum of co-scheduled redactions. Average CPU looks moderate because work is serialised per process. Fixes: (1) offload with run_in_executor to a process pool sized to spare cores: isolates CPU, costs pickling of the body and memory per process; (2) optimise the work (compile regexes once, use a linear-time engine such as the re2 bindings, stream redaction in chunks with await asyncio.sleep(0) between chunks to yield): cheapest, but still consumes the worker's single core. Long-term: move redaction to a dedicated service or queue, and add loop-lag alerts so the next regression is caught in canary.

Exercise 4 · Advanced

Your Celery workers (prefork, 8 children, fork start method) show RSS growing from 300 MB to 1.2 GB per child over a day, but tracemalloc shows stable live allocations. Diagnose and remediate.

Solution

Two non-leak effects combine. Copy-on-write erosion: children start sharing the parent's pages, but refcount writes and GC traversals dirty them, so each child's private (USS) memory grows toward a full copy; RSS double-counts shared pages anyway, so measure PSS/USS (smem, /proc/PID/smaps_rollup). Fragmentation: pymalloc arenas partially occupied by long-lived objects cannot be returned. Remediation: gc.freeze() in the parent before forking; worker_max_tasks_per_child and/or worker_max_memory_per_child to recycle; avoid caching large per-task objects at module level; consider jemalloc/mimalloc via LD_PRELOAD for large allocations, after measuring.

Exercise 5 · Expert

Design an experiment to decide whether to adopt the free-threaded build for an in-process feature-computation service currently running 8 processes per pod. What would you measure and what are the go/no-go criteria?

Solution

Inventory native deps and check free-threading support (import with -X gil=0 off, watch for the "GIL re-enabled" warning; check sys._is_gil_enabled()). Build a 3.14t/3.15t image. Benchmarks: (a) single-thread latency per request vs GIL build (expect some regression); (b) throughput of one process with 8 threads vs 8 processes; (c) memory per pod (expect a large win since shared caches are not duplicated); (d) race-detection: run the test suite under stress with thread sanitizer builds if available, and review module-level mutable state. Go criteria: equal or better throughput per pod, memory reduction worth the risk, p99 within SLO, all deps officially supported, and a rollback plan (two images). No-go if any critical dep re-enables the GIL or p99 regresses.

15. Interview Questions

Conceptual Why does CPython have a GIL, and why is removing it hard?

Reference counts are modified on almost every operation; making them atomic everywhere slows single-threaded code, and fine-grained locks on every object are worse. A single lock made the interpreter and every C extension thread-safe for free. Removal is hard because the C API exposes refcount macros and assumes the GIL protects global state; PEP 703 needed biased refcounting, immortalisation, deferred refcounting, a new allocator and per-object locks, plus ecosystem-wide extension changes.

Conceptual Compare CPython memory management with the JVM's.

CPython: reference counting frees most objects immediately; a generational cycle collector (based on subtracting internal references, not root tracing) handles cycles; pymalloc pools small objects; memory is rarely returned to the OS. JVM: no refcounts; tracing generational/regional collectors from roots with compaction (G1, ZGC), which defeats fragmentation but needs barriers and pauses or concurrent phases. CPython has predictable destruction and no compaction; JVM has higher throughput allocation (bump pointer) and compaction.

Conceptual What exactly happens when you call an async def function?

Nothing runs; it returns a coroutine object holding a suspended frame. Awaiting it runs it inline in the current task until it awaits an unresolved future; wrapping it in create_task schedules it independently on the loop. The task drives it via send() and resumes it when the awaited future completes.

Architecture You must serve an LLM-backed chat API with 10k concurrent streaming connections in Python. Design the process and concurrency model.

Async framework (FastAPI/Starlette) on Uvicorn with uvloop; workers = cores per pod; each worker holds thousands of streams as coroutines; async HTTP client with connection pooling to the LLM provider and per-provider semaphores; overall timeouts per stream; backpressure via bounded queues; CPU-bound pre/post-processing offloaded or native; horizontal scale by pods behind a load balancer with sticky-free design; observability: loop lag, in-flight streams, token throughput, provider latency. Gracefully drain streams on deploy.

Architecture When would you choose processes over the free-threaded build in 2026?

When any critical native dependency is not free-threading-safe, when isolation (crash containment, memory cap per worker) matters, when single-thread latency must not regress, or when the code base has unaudited shared mutable state. Choose free-threading when shared in-memory state is large (memory duplication across processes is expensive) and dependencies are certified.

Coding Implement a function that runs coroutines with at most N concurrently and returns results in input order.
import asyncio
from typing import Awaitable, Iterable, TypeVar
T = TypeVar("T")

async def bounded_gather(coros: Iterable[Awaitable[T]], n: int) -> list[T]:
    sem = asyncio.Semaphore(n)
    async def run(c: Awaitable[T]) -> T:
        async with sem:
            return await c
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(run(c)) for c in coros]
    return [t.result() for t in tasks]

Note: coroutine objects are created eagerly by the caller but do not run until awaited inside the semaphore. For huge inputs use a worker-queue to avoid creating all tasks.

Scenario A service's threads show 100% of one core and 0% on others, with 16 threads busy. What is happening?

Classic GIL saturation: the threads are executing Python bytecode, so only one runs at a time. Confirm with py-spy top --gil. Fix by moving the CPU work to processes, vectorising, or native code that releases the GIL.

Scenario After upgrading to Python 3.14, a batch job that used multiprocessing fails with errors about unpicklable objects or missing globals. Why?

The default start method on Linux changed from fork to forkserver. Children no longer inherit the parent's memory, so module-level state set at runtime is missing and targets/arguments must be picklable (no lambdas, local functions or open connections). Fix by making task functions top-level and passing state explicitly, or opt in to multiprocessing.get_context("fork") knowingly, accepting the thread-safety risks.

Conceptual How do Java virtual threads, Go goroutines and asyncio tasks differ?

Virtual threads and goroutines are runtime-scheduled, run blocking-style code, and are multiplexed across all cores (M:N); the runtime parks them on blocking I/O. Goroutines are also preempted asynchronously (signals since Go 1.14). asyncio tasks are cooperative on a single OS thread, switch only at await, need async-specific libraries, and give no parallelism. The upside of asyncio is that between awaits your code cannot be interleaved, which simplifies shared-state reasoning.

Behavioral Tell me about a time you diagnosed a performance problem in a runtime you did not know well.

Good answers show a method: establish a baseline, form hypotheses from the runtime's model (e.g. GIL, event loop), pick the right profiler (py-spy vs async-profiler), confirm with an experiment, fix, and add a guardrail metric. Mention collaborating with the team that owns the service and documenting the learning.

16. Knowledge Check

  • CPython is a stack-based bytecode interpreter with a specialising adaptive layer (3.11+) and an experimental JIT; it is far slower than HotSpot on pure-Python loops.
  • Every value is a heap PyObject with a refcount and type pointer; numeric data belongs in native buffers.
  • Refcounting frees most memory immediately; a generational cycle collector frees cycles; pymalloc fragmentation explains "leaks" that are not leaks.
  • The GIL serialises bytecode execution, is released for blocking I/O and by native code, and is handed off every 5 ms on request.
  • Free-threaded CPython is officially supported since 3.14 but is a separate build with ecosystem caveats.
  • asyncio provides cooperative single-threaded concurrency; never block the loop; use TaskGroup and asyncio.timeout for structured concurrency.
  • Use processes for CPU-bound Python; mind start methods (forkserver default on Linux since 3.14) and pickling.

  2. Objects in reference cycles
  3. Objects created in C extensions
  4. Small integers

  3. asyncio preempts the handler after 5 ms
  4. All of them stall for one second
The event loop is single-threaded and cooperative; a blocking call prevents the loop from running any other callback.

  4. Exceptions are logged and suppressed
