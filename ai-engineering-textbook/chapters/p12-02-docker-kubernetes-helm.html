Docker, Kubernetes & Helm

A container image replaces your fat JAR as the unit of delivery; Kubernetes replaces your hand-run servers with a control loop that continuously drives the cluster toward the state you declare; Helm and Kustomize package that declaration for many environments. This chapter explains all three from the inside, with production-grade artifacts for the Lumen platform's Spring Boot, Python and Go services.

  • Prerequisites: Chapter 12.1 (processes, cgroups, namespaces, TCP, DNS, load balancing); basic Docker CLI use.
  • You will be able to: build small, cache-efficient, secure images for JVM, Go and Python services; explain what every Kubernetes control-plane component does when you run kubectl apply; write Deployments with correct probes, resources, autoscaling and disruption budgets; route traffic with Services and Gateway API; and package it all as a Helm chart.

1. Introduction: From Fat JARs to Declarative Clusters

Spring Boot solved one deployment problem brilliantly: java -jar app.jar runs anywhere a JVM exists. But "anywhere a JVM exists" turned out to be the hard part. Which JDK version? Which OS packages for fonts or native libraries? Which CA certificates? Which system user, which ports, which memory settings? And once you have twenty services in three languages, how do you restart a crashed process, replace an unhealthy host, roll out version 2 without downtime, or scale to traffic?

Containers answer the first set of questions by shipping the whole userland — JRE, libraries, certificates, your app — as an immutable, content-addressed image that runs identically on a laptop and in production. Kubernetes answers the second set by letting you declare the desired state ("three replicas of orders-service v1.8.2, each with 1 CPU and 1.5 GiB, reachable as orders, never fewer than two available") and running controllers that continuously reconcile reality toward that declaration. Helm and Kustomize answer the third: how to express that declaration once and vary it per environment.

In Chapter 1 the Lumen platform ran on VMs under systemd. In this chapter we containerise orders-service (Spring Boot), assist-service (FastAPI) and edge-gateway (Go), and deploy them to Kubernetes with probes, resource budgets, autoscaling, disruption budgets and Gateway API routing. Chapter 3 will build these artifacts in CI and deploy them with Argo CD; Chapter 4 provides the EKS cluster.

Bridging from Java & Spring Boot

What you already know
Fat JARs built by spring-boot-maven-plugin; application-{profile}.yaml with spring.profiles.active; /actuator/health for load-balancer checks; external config through environment variables and @ConfigurationProperties; perhaps a Jenkins job that scps a JAR and restarts a systemd unit.
Why that is not enough
A fat JAR still depends on the host's JRE and OS; it does not restart itself, scale itself, or roll back. Spring profiles bake environment knowledge into the artifact. A single health endpoint conflates "restart me" with "do not send me traffic", which in Kubernetes causes cascading restarts.
The modern approach
The container image is the artifact (fat JAR → layered image). Configuration is injected at deploy time from ConfigMaps and Secrets (profiles → environment-specific values outside the image). Health becomes three probes — startup, liveness, readiness — mapped to Spring Boot's /actuator/health/liveness and /readiness groups. Deployment becomes a declarative manifest reconciled by controllers.
Where Python and Go fit
Go compiles to a static binary that fits in a 2–10 MB distroless image and starts in milliseconds — ideal for gateways and operators (Kubernetes itself is written in Go, and controllers are usually written with controller-runtime). Python images are dominated by dependency size (PyTorch wheels can exceed a gigabyte); careful layering and slim bases matter most there.
In production
Most incidents on Kubernetes are not Kubernetes bugs: they are probes that restart healthy-but-slow JVMs, memory limits below JVM footprint, missing PodDisruptionBudgets during node upgrades, and rollouts without readiness gating. Every one is covered here.
Use it when / avoid it when
Use Kubernetes when you run many services, need self-healing and standardised operations, or need portability across clouds. Avoid it for a handful of services a small team could run on a managed PaaS (App Runner, Cloud Run, ECS Fargate, Heroku-style platforms) — Kubernetes' operational cost is real.

2. History: From chroot to Gateway API

Process isolation is older than most engineers: chroot appeared in Unix V7 in 1979; FreeBSD jails in 2000; Solaris Zones in 2004; Linux namespaces and cgroups from 2002–2008 (Chapter 1). Docker, released by dotCloud in March 2013, did not invent isolation; it invented the developer experience — the Dockerfile, layered images, a registry protocol, and docker run. In June 2015 Docker and others founded the Open Container Initiative (OCI), which standardised the image format, the runtime specification (runc is the reference implementation) and later the distribution (registry) API. BuildKit, a new build engine, became Docker's default builder in Docker Engine 23.0 (2023).

Inside Google, Borg had run nearly all workloads on shared clusters since the mid-2000s; the 2015 EuroSys paper "Large-scale cluster management at Google with Borg" described it publicly. Google engineers (Joe Beda, Brendan Burns, Craig McLuckie and others) announced Kubernetes in June 2014 as an open-source system inspired by Borg and its successor Omega; version 1.0 shipped in July 2015 together with the formation of the Cloud Native Computing Foundation (CNCF), to which Google donated it. Key milestones since: CRDs (2017) and the operator pattern; the Container Runtime Interface (CRI) and the removal of the built-in Docker shim in v1.24 (May 2022), after which nodes run containerd or CRI-O directly; Gateway API v1.0 (October 2023) as the successor to Ingress; native sidecar containers GA in v1.33 (April 2025); Dynamic Resource Allocation (DRA, for GPUs and other devices) GA in v1.34 (August 2025); in-place Pod resize GA in v1.35 (December 2025); and v1.37 "Garhwal" in August 2026, with HPA scale-to-zero moving to beta Version-sensitive · checked Nov 2026.

In November 2025 Kubernetes SIG Network and the Security Response Committee announced the retirement of the community ingress-nginx controller — for years the de facto default Ingress implementation — with best-effort maintenance ending in March 2026 and a recommendation to migrate to Gateway API or another controller Verified. That event made Gateway API the default choice for new clusters.

Helm began at Deis in 2015 and joined the CNCF; Helm 3 (November 2019) removed the cluster-side Tiller component that had been a security liability; Helm 4 was released on 12 November 2025, Helm's tenth anniversary, with a redesigned plugin system (including WebAssembly plugins), server-side apply support and a restructured SDK Version-sensitive · checked Nov 2026. Kustomize was built into kubectl (kubectl apply -k) in v1.14 (2019).

3. Fundamentals

3.1 Images, layers and the OCI format

An OCI image is three kinds of content-addressed blobs: layers (tarballs of filesystem changes), a config (JSON with environment, entrypoint, user, working directory, and the ordered list of layer digests), and a manifest that points to the config and layers by SHA-256 digest. A multi-architecture image adds an index that points to one manifest per platform (linux/amd64, linux/arm64). Because everything is addressed by hash, two images that share a base layer store and transfer it once, and an image reference by digest (orders@sha256:3f1…) is immutable, while a tag (orders:1.8.2, or worse, :latest) is a mutable pointer.

At runtime, the container runtime stacks the read-only layers with an overlay filesystem (overlayfs) and adds a thin writable layer on top. Writes copy the file up into that layer (copy-on-write); deletions create "whiteout" entries. That is why deleting a file in a later Dockerfile step never reduces image size — the bytes remain in the earlier layer.

3.2 Dockerfile instructions and layer caching

Each RUN, COPY and ADD creates a layer; the builder reuses a cached layer if the instruction and its inputs (for COPY, the checksums of copied files) are unchanged and every previous layer was a cache hit. Order instructions from least to most frequently changing: base image, OS packages, dependency manifests (pom.xml, go.mod, pyproject.toml/uv.lock), dependency download, then source code. Copying the whole source tree before resolving dependencies invalidates the dependency layer on every commit and turns a 20-second build into a 5-minute one.

ENTRYPOINT and CMD have a shell form (CMD java -jar app.jar, run via /bin/sh -c) and an exec form (CMD ["java","-jar","app.jar"], run directly as PID 1). Use exec form so signals reach your process (Chapter 1, §3.2).

3.3 BuildKit and multi-stage builds

BuildKit builds a dependency graph of stages and executes independent stages in parallel, skips stages not needed for the target, and supports features the legacy builder never had: cache mounts (RUN --mount=type=cache,target=/root/.m2 persists the Maven repository across builds without putting it in a layer), secret mounts (--mount=type=secret,id=npmrc exposes a credential to one step without leaking it into image history), SSH forwarding, external cache export/import (--cache-to/--cache-from to a registry or GitHub Actions cache), multi-platform builds via docker buildx, and SBOM and provenance attestations.

A multi-stage Dockerfile uses a full SDK image (JDK + Maven, Go toolchain, Python build tools) in a build stage and copies only the output into a minimal runtime stage. For Java that means a JRE instead of a JDK; for Go, a static binary on a distroless or scratch base; for Python, a pre-built virtual environment on a slim base. Smaller runtime images pull faster (faster scale-out), have fewer CVEs, and give attackers fewer tools.

3.4 Layered Spring Boot jars, Buildpacks and Jib

A fat JAR is one 80 MB file; change one class and the whole 80 MB layer changes. Spring Boot's layered jar support (since 2.3) writes a layers.idx into the JAR that groups content into dependencies, spring-boot-loader, snapshot-dependencies and application. The tools jar mode (Spring Boot 3.3+, replacing the older layertools mode) extracts those groups into directories that you copy as separate image layers, so a typical code change ships only the few-hundred-KB application layer.

Two alternatives avoid writing a Dockerfile at all. Cloud Native Buildpacks (Paketo for Java) are what ./mvnw spring-boot:build-image uses: they detect a Java app, pick a JRE, apply memory calculator logic, layer the app, and produce a reproducible OCI image. Jib (Google) is a Maven/Gradle plugin that builds layered images directly from the build's class output — no Docker daemon required — and pushes them to a registry. Both trade flexibility for consistency; platform teams like them because every service gets the same base image and patching policy.

3.5 JVM container awareness and startup

Since JDK 10 (and 8u191) the JVM reads cgroup limits (-XX:+UseContainerSupport, on by default), so MaxRAMPercentage (default 25%!) applies to the container limit rather than host RAM, and availableProcessors() reflects the CPU limit. Two consequences: the default heap is often too small (25% of a 2 GiB limit is 512 MiB), so set -XX:MaxRAMPercentage=70 to 75; and in a container with fewer than 2 CPUs and less than 1792 MB, the JVM ergonomically selects SerialGC — usually fine for small services but surprising if you expected G1.

Startup time matters more on Kubernetes because it gates rollouts and autoscaling. Options, in increasing effort: Class Data Sharing archives (Spring Boot 3.3+ can produce a CDS-friendly layout; JDK 24's AOT cache, JEP 483, extends this), Spring AOT processing, CRaC checkpoint/restore (Spring Framework 6.1+ support), and GraalVM native images (milliseconds to start, lower memory, but longer builds and reflection constraints) Version-sensitive · checked Nov 2026.

3.6 Kubernetes architecture

A cluster has a control plane and worker nodes.

  • kube-apiserver — the only component that talks to etcd. A RESTful, versioned API for all objects; performs authentication, authorisation (RBAC), admission (mutating and validating webhooks, ValidatingAdmissionPolicy with CEL), schema validation, and serves watches — long-lived streams of change events that every other component consumes.
  • etcd — a strongly consistent key-value store using Raft consensus; holds all cluster state. Typically 3 or 5 members; losing quorum makes the API read-only or unavailable (running workloads keep running).
  • kube-scheduler — watches for Pods with no nodeName, filters nodes that cannot fit the Pod (resources, taints, affinity, topology spread), scores the rest, and binds the Pod to the best node by writing to the API.
  • kube-controller-manager — runs dozens of controllers (Deployment, ReplicaSet, StatefulSet, Job, Node, EndpointSlice, ServiceAccount, garbage collector…), each a reconciliation loop.
  • cloud-controller-manager — cloud-specific controllers (on EKS: node lifecycle; load balancers are usually handled by the AWS Load Balancer Controller add-on).
  • kubelet (every node) — watches Pods bound to its node, asks the container runtime (containerd via CRI) to create them, mounts volumes, runs probes, reports status, and enforces resource limits via cgroups.
  • kube-proxy (every node, optional with eBPF CNIs) — programs iptables, IPVS or nftables rules so Service virtual IPs reach backend Pods.
  • CNI plugin — gives each Pod an IP and connectivity (AWS VPC CNI, Cilium, Calico).
  • CoreDNS — cluster DNS: orders.lumen.svc.cluster.local → Service IP.

3.7 The reconciliation loop

Every Kubernetes controller follows one pattern: observe the desired state (spec) and the actual state (status, child objects), diff them, act to reduce the difference, and repeat. Controllers are level-triggered, not edge-triggered: they do not react to "a pod was deleted" as an event to be processed once; they react to "the current number of pods is 2 and the desired number is 3", which is robust to missed events, restarts and concurrent changes. Informers maintain a local cache fed by watches; work queues de-duplicate and rate-limit reconcile requests. Spring developers can think of it as a @Scheduled job that is also woken by change notifications, is idempotent, and never assumes what happened before.

3.8 Pods

A Pod is the unit of scheduling: one or more containers that share a network namespace (one IP, shared localhost), can share volumes, and are scheduled together on one node. Init containers run to completion, in order, before app containers start. Sidecar containers (GA in v1.33) are init containers with restartPolicy: Always: they start before the main containers, keep running alongside them, and are terminated after them — fixing long-standing problems with log shippers and service-mesh proxies in Jobs and during shutdown. Pods are cattle: they are never "moved"; a replacement Pod with a new name and IP is created.

3.10 Services and service discovery

Pod IPs change; a Service gives a stable virtual IP (ClusterIP) and DNS name to a set of Pods selected by labels. The EndpointSlice controller keeps the list of ready Pod IPs behind each Service. Types: ClusterIP (internal only), NodePort (a port on every node), LoadBalancer (provisions a cloud load balancer — on EKS an NLB via the AWS Load Balancer Controller), ExternalName (a DNS CNAME), and headless (clusterIP: None: DNS returns Pod IPs directly, used by StatefulSets and client-side balancing for gRPC).

3.11 kube-proxy: iptables, IPVS, nftables and eBPF

A ClusterIP exists on no interface; it is implemented by rules on every node. In iptables mode, kube-proxy writes a chain per Service that DNATs the destination to a randomly chosen endpoint (with probability rules); rule evaluation is linear, so clusters with tens of thousands of Services pay in update latency and CPU. IPVS mode uses the kernel's L4 load balancer with hash tables and real algorithms (round-robin, least-connection). nftables mode, GA in v1.33, uses the modern netfilter API with maps and is the forward path for kube-proxy Version-sensitive · checked Nov 2026. eBPF data planes such as Cilium replace kube-proxy entirely, resolving Service IPs at the socket level (connect() is rewritten to the backend address) or at the TC/XDP hooks, avoiding conntrack and DNAT for much of the traffic.

3.12 Ingress vs Gateway API

Ingress (stable since v1.19) is a single resource that maps hosts and paths to Services, with everything else — TLS options, timeouts, rewrites, canary weights — pushed into controller-specific annotations. That made Ingress manifests non-portable and mixed infrastructure and application concerns in one object. Gateway API splits roles: a GatewayClass (installed by the infrastructure provider, e.g., AWS Load Balancer Controller, Envoy Gateway, Cilium, Istio), a Gateway (owned by the platform team: listeners, ports, TLS certificates, which namespaces may attach), and HTTPRoute/GRPCRoute/TLSRoute objects (owned by application teams: matches, filters, weighted backends, timeouts). Header matching, traffic splitting and cross-namespace delegation are part of the spec, not annotations.

3.13 ConfigMaps and Secrets

A ConfigMap holds non-sensitive configuration; a Secret holds sensitive values, base64-encoded (not encrypted!) in the API, optionally encrypted at rest in etcd with a KMS provider, and access-controlled via RBAC. Both can be exposed as environment variables (read once at container start) or mounted as files (updated in place by the kubelet after a delay, except with subPath). Spring Boot consumes them naturally: environment variables map via relaxed binding (SPRING_DATASOURCE_URL), and mounted directories can be imported with spring.config.import=optional:configtree:/etc/config/. In production, secrets usually originate in a secret manager (AWS Secrets Manager, Vault) and are synced by External Secrets Operator or mounted by the Secrets Store CSI driver.

Profiles vs ConfigMaps

Keep Spring profiles for behavioural variation that the code knows about (e.g., a kubernetes profile enabling probe groups). Put environment values — URLs, pool sizes, feature toggles — in ConfigMaps per environment. One image, promoted unchanged from dev to prod, with environment supplied from outside: the third factor of the Twelve-Factor App.

3.15 Resources, requests, limits and QoS

Requests are what the scheduler reserves on a node and what cpu.weight is derived from; limits are the cgroup ceilings (cpu.max, memory.max). From them Kubernetes derives a QoS class: Guaranteed (every container has requests = limits for CPU and memory), Burstable (some requests set), and BestEffort (nothing set). Under node memory pressure the kubelet evicts BestEffort first, then Burstable Pods exceeding their requests; Guaranteed Pods are last. A common, defensible policy: memory request = limit (memory is not compressible; overcommit causes OOM kills), CPU request set from measured usage, CPU limit either absent or generous (Chapter 1 §6.4). LimitRange sets namespace defaults and ResourceQuota caps namespace totals.

3.16 Autoscaling: HPA, VPA, KEDA and node autoscaling

  • HorizontalPodAutoscaler (autoscaling/v2) changes replica count based on resource metrics (CPU/memory utilisation relative to requests), custom metrics (via a metrics adapter, e.g., requests per second from Prometheus) or external metrics, with configurable scale-up/scale-down behaviour and stabilisation windows.
  • VerticalPodAutoscaler recommends or applies requests/limits based on observed usage; with in-place resize (GA in v1.35) it can increasingly adjust resources without recreating Pods. Do not let VPA and HPA act on the same metric (CPU) for the same workload.
  • KEDA (CNCF) scales on event sources — SQS queue depth, Kafka lag, Prometheus queries, cron — and can scale Deployments to and from zero; it creates and drives an HPA under the hood.
  • Node autoscaling: Cluster Autoscaler adds nodes to node groups when Pods are unschedulable; Karpenter provisions right-sized instances directly and consolidates underused nodes (it underpins EKS Auto Mode — Chapter 4).

3.17 Rolling updates and PodDisruptionBudgets

A Deployment's default strategy, RollingUpdate, creates a new ReplicaSet and shifts Pods over, bounded by maxSurge (extra Pods allowed above desired) and maxUnavailable (Pods allowed below desired). A new Pod counts as available only after it is ready for minReadySeconds; a rollout that does not progress within progressDeadlineSeconds is marked failed (it is not automatically rolled back — that is the job of your CD tooling or Argo Rollouts, Chapter 3).

A PodDisruptionBudget limits voluntary disruptions — node drains during upgrades, Karpenter consolidation, cluster autoscaler scale-down — via the Eviction API: "at least 2 orders-service Pods must remain available" or "at most 1 may be unavailable". It does not protect against involuntary disruptions (node crash, OOM kill). Without PDBs, a routine node-group upgrade can evict all replicas of a service at once.

3.18 Custom resources and operators

A CustomResourceDefinition extends the API with your own types (kind: VectorIndex); an operator is a controller that reconciles those types, encoding operational knowledge as code. Examples you will use: cert-manager (Certificate), External Secrets (ExternalSecret), Argo CD (Application), Karpenter (NodePool), CloudNativePG (Cluster), Prometheus Operator (ServiceMonitor, PrometheusRule). Operators are usually written in Go with Kubebuilder/controller-runtime; Java teams can use the Java Operator SDK or Fabric8 client.

3.19 Helm and Kustomize

Helm is a package manager: a chart is a directory of Go-templated manifests plus values.yaml defaults and Chart.yaml metadata; helm install/upgrade renders templates with merged values and applies them as a release whose history Helm stores (as Secrets in the release namespace), enabling helm rollback. Charts can depend on other charts, be versioned and published to OCI registries, and run hooks (pre-install, pre-upgrade, post-upgrade, test) for migrations or checks. Kustomize takes the opposite approach: no templates; plain YAML bases plus overlays that patch them (strategic merge or JSON patch), set images, add labels and generate ConfigMaps with content hashes. Helm suits distributing reusable software with many options; Kustomize suits your own services where you want readable, valid YAML at every step. Many teams combine them (Kustomize post-processing a Helm chart) or let Argo CD render either.

4. Internal Working: What Happens After kubectl apply

4.1 From manifest to running container

  1. Client side. kubectl apply -f deployment.yaml reads your kubeconfig, authenticates (on EKS via an exec plugin that obtains a token from AWS IAM), and sends a request to the API server. With server-side apply (--server-side, also used by Helm 4 and Argo CD), the server computes the merge and records field ownership per manager, which prevents tools from silently overwriting each other's fields.
  2. API server pipeline. Authentication → authorisation (RBAC: can this identity patch deployments in namespace lumen?) → mutating admission (defaults, injected sidecars, image digest pinning by policy engines) → schema validation → validating admission (Kyverno/Gatekeeper policies, ValidatingAdmissionPolicy: "images must come from our ECR", "no privileged containers") → persistence to etcd with a new resourceVersion → watch events fan out.
  3. Deployment controller sees the Deployment's new pod template hash, creates (or scales) a ReplicaSet for it, and scales the old one down according to the rolling-update parameters.
  4. ReplicaSet controller sees desired replicas 3, actual 0, and creates three Pod objects with no nodeName.
  5. Scheduler watches unscheduled Pods. For each, it filters (enough allocatable CPU/memory for the requests? taints tolerated? node affinity? topology spread satisfiable? volumes attachable in that zone?) and scores (spreading, image locality, balanced utilisation), then writes a Binding.
  6. kubelet on the chosen node sees a Pod bound to it. It creates the Pod sandbox via CRI (containerd starts a "pause" container that holds the network namespace), calls the CNI plugin to attach an interface and IP, pulls images (respecting imagePullPolicy), mounts volumes, ConfigMaps and Secrets, runs init containers in order, starts sidecars and then app containers via runc (namespaces, cgroups, seccomp, capabilities — Chapter 1 §7.10, automated).
  7. Probes. The kubelet runs the startup probe until success, then liveness and readiness probes periodically. On readiness success, it updates the Pod's Ready condition.
  8. EndpointSlice controller adds the ready Pod's IP to the Service's EndpointSlice; kube-proxy (or Cilium) on every node updates its rules; the AWS Load Balancer Controller registers the Pod IP in the target group (with IP target mode). Only now does traffic arrive.

4.2 The packet path to a Pod

A request from edge-gateway to http://orders.lumen.svc.cluster.local:80: the gateway's resolver asks CoreDNS (the nameserver in its resolv.conf) and gets the ClusterIP, say 172.20.14.7. The gateway calls connect() to 172.20.14.7:80. In iptables mode the packet leaves the gateway Pod's network namespace through its veth pair, hits the node's PREROUTING/OUTPUT chains, matches KUBE-SERVICES → KUBE-SVC-… → randomly one KUBE-SEP-… chain, and is DNATed to a Pod IP and target port, e.g., 10.0.37.21:8080; conntrack records the translation. If the target Pod is on another node, the node routes the packet: with AWS VPC CNI, Pod IPs are real VPC addresses, so the packet travels on the VPC fabric with no overlay; with overlay CNIs it is encapsulated (VXLAN/Geneve). On the destination node it is delivered through the target Pod's veth to its network namespace and Tomcat's listening socket. The reply is reverse-NATed via conntrack so the gateway sees a response from the ClusterIP.

4.3 A rolling update, step by step

With replicas: 4, maxSurge: 1, maxUnavailable: 0: the controller creates one new Pod (5 total). When it becomes ready and stays ready for minReadySeconds, the controller scales the old ReplicaSet to 3 — which deletes one old Pod. Deletion sets a deletionTimestamp; the EndpointSlice controller removes the Pod from endpoints and, concurrently, the kubelet runs the preStop hook and sends SIGTERM. Because endpoint removal propagates asynchronously to every node's kube-proxy and to external load balancers, the Pod may receive new connections for a short time after SIGTERM — the reason for a preStop sleep (Chapter 1 §4.6). After terminationGracePeriodSeconds the kubelet sends SIGKILL. The cycle repeats until all four Pods run the new version.

4.4 How HPA decides

Every 15 seconds (the default sync period) the HPA controller fetches metrics (from metrics-server for CPU/memory, or the custom/external metrics APIs), computes a desired replica count per metric, takes the maximum, applies the behavior policies (e.g., scale up by at most 100% or 4 Pods per 60 s; scale down by at most 10% per minute after a 300 s stabilisation window), clamps to [minReplicas, maxReplicas], and updates the Deployment's scale subresource. Pods that are not yet ready or are missing metrics are treated conservatively to avoid thrashing during startup — another reason JVM startup time matters.

4.5 How Helm performs an upgrade

helm upgrade --install orders ./orders -f values-prod.yaml: Helm loads the chart and its dependencies, merges values (chart defaults ← parent chart ← -f files in order ← --set), renders templates with the Go template engine and Sprig functions, validates against the cluster API (optionally a JSON schema in values.schema.json), runs pre-upgrade hooks and waits for them, then computes a three-way merge between the previous release's manifest, the live objects and the new manifest (or uses server-side apply in Helm 4), applies changes, optionally waits for resources to become ready (--wait; Helm 4 uses kstatus-based readiness checking), runs post-upgrade hooks, and stores the new release revision. helm rollback orders 41 re-applies revision 41's stored manifest.

5. Architecture Diagrams

5.1 Control plane and nodes

Reading the diagram: there are no direct calls between the scheduler, controllers and kubelets — all coordination happens through objects in the API server, which each component watches. This hub-and-spoke design is why Kubernetes is extensible (your operator is just another watcher) and why API server and etcd health are critical: if the API is down, running Pods keep running, but nothing can be scheduled, scaled or healed. On EKS the control plane is managed by AWS across three Availability Zones; you operate the nodes (or delegate them with Auto Mode/Fargate).

5.2 Pod creation sequence

Reading the diagram: read the solid arrows as writes to the API and the dashed arrows as watch notifications. No component orders another to act; each reacts to state. That is why the same flow handles a node failure: the node controller marks the node's Pods for deletion, the ReplicaSet controller sees too few Pods and creates replacements, and the scheduler places them elsewhere — no special "failover" code exists.

5.3 Packet path through a Service and Gateway

Reading the diagram: the NLB sends traffic straight to gateway Pod IPs (IP target mode) rather than to NodePorts, avoiding an extra hop and preserving client IPs. The gateway resolves the orders Service name to a ClusterIP; that address is translated on the gateway's own node to a concrete Pod IP, possibly on another node. Because each new TCP connection is balanced independently, the gateway's keep-alive pool to orders should hold enough connections to spread load across replicas — or the gateway should resolve a headless Service and balance per request itself.

5.4 Gateway API role model

Reading the diagram: the platform team owns the Gateway (ports, TLS certificates, which namespaces may attach routes), and application teams own their HTTPRoutes in their own namespaces. Features that required controller-specific annotations on Ingress — timeouts, weighted canaries, header matching — are typed fields. The same HTTPRoute works on any conformant implementation, so migrating from one controller to another (as ingress-nginx users had to in 2026) does not require rewriting application routing.

5.5 Reconciliation as a state machine

Reading the diagram: note that there is no "event handled" terminal state. A controller always returns to Observe, so missed events, crashes and conflicting writers are tolerated: the next pass sees current reality. Conflicts (another writer updated the object first, detected by resourceVersion) lead to back-off and retry rather than corruption — optimistic concurrency, exactly like JPA's @Version.

6. The Math of Scheduling, Scaling and Rollouts

6.1 HPA replica calculation

Intuition: if Pods run at twice the target utilisation, you need twice as many. Formally, for each metric:

\[ \text{desired} = \left\lceil \text{current} \times \frac{\text{currentMetricValue}}{\text{targetMetricValue}} \right\rceil \]

with a default tolerance of 10% (no change if the ratio is within 0.9–1.1). Example: 4 replicas at average 85% CPU (of requests) with a 60% target → \(\lceil 4 \times 85/60 \rceil = \lceil 5.67 \rceil = 6\). Note the denominator is the request: if you set a CPU request of 100m on a service that needs 500m, utilisation reads 500% and HPA scales to the maximum. Requests must be realistic for HPA to work.

6.2 Bin-packing and allocatable capacity

A node's allocatable = capacity − kube-reserved − system-reserved − eviction threshold. An m7i.xlarge (4 vCPU, 16 GiB) on EKS might offer roughly 3.9 vCPU and ~14.5 GiB allocatable, and the VPC CNI also caps Pods per node by ENI/IP limits Illustrative. If orders-service requests 500m/1.5Gi, memory binds first: \(\lfloor 14.5 / 1.5 \rfloor = 9\) Pods, using \(9 \times 0.5 = 4.5\) vCPU — more than allocatable, so CPU binds at 7 Pods. Mixing memory-heavy (assist-service with an embedding model) and CPU-heavy (gateway) workloads improves packing.

6.3 Rolling update capacity

During a rollout with \(N\) desired replicas, available capacity is at least \(N - \text{maxUnavailable}\) and total Pods at most \(N + \text{maxSurge}\). Percentages round: maxSurge rounds up, maxUnavailable rounds down. With \(N = 10\), maxSurge: 25% → 3, maxUnavailable: 25% → 2: between 8 and 13 Pods, each "wave" replacing up to 5. Rollout duration is roughly

\[ T \approx \left\lceil \frac{N}{\text{maxSurge} + \text{maxUnavailable}} \right\rceil \times (t_{\text{start}} + t_{\text{ready}} + \text{minReadySeconds}) \]

For a Spring Boot service with 25 s to readiness, 10 s minReadySeconds and 2 Pods per wave across 20 replicas: \(10 \times 35 = 350\) s. Cutting JVM startup to 5 s with CDS/AOT reduces this to 150 s — faster deploys and faster rollbacks.

6.4 PodDisruptionBudget arithmetic

With \(N\) healthy replicas and minAvailable: m, the Eviction API allows \(N - m\) concurrent voluntary evictions. If \(N = m\) (e.g., 2 replicas, minAvailable: 2), zero evictions are allowed and node drains hang forever — a classic upgrade blocker. Prefer maxUnavailable: 1, which stays valid as replicas scale.

6.5 Image size and scale-out time

Pull time ≈ compressed size / effective throughput + decompression. A 450 MB JDK-based image at an effective 100 MB/s takes ~5 s to pull before the JVM even starts; a 180 MB JRE layered image takes ~2 s, and only changed layers are pulled on updates (often under 1 MB). For an autoscaling event that adds 20 Pods on 5 fresh nodes, image size directly adds to time-to-capacity Illustrative.

7.9 A minimal operator reconcile loop in Go

// Partial example (controller-runtime v0.19+): reconcile a VectorIndex custom resource
// into a Job that (re)builds the index. Scaffolding generated by Kubebuilder is omitted.
package controller

import (
	"context"
	"fmt"

	batchv1 "k8s.io/api/batch/v1"
	corev1 "k8s.io/api/core/v1"
	apierrors "k8s.io/apimachinery/pkg/api/errors"
	metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
	ctrl "sigs.k8s.io/controller-runtime"
	"sigs.k8s.io/controller-runtime/pkg/client"

	lumenv1 "example.com/lumen/api/v1"
)

type VectorIndexReconciler struct {
	client.Client
}

func (r *VectorIndexReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
	var idx lumenv1.VectorIndex
	if err := r.Get(ctx, req.NamespacedName, &idx); err != nil {
		return ctrl.Result{}, client.IgnoreNotFound(err) // deleted: owned Jobs are garbage-collected
	}

	// Desired state: one build Job per spec generation.
	jobName := fmt.Sprintf("%s-build-%d", idx.Name, idx.Generation)
	var job batchv1.Job
	err := r.Get(ctx, client.ObjectKey{Namespace: idx.Namespace, Name: jobName}, &job)
	if apierrors.IsNotFound(err) {
		job = batchv1.Job{
			ObjectMeta: metav1.ObjectMeta{Name: jobName, Namespace: idx.Namespace},
			Spec: batchv1.JobSpec{
				Template: corev1.PodTemplateSpec{Spec: corev1.PodSpec{
					RestartPolicy: corev1.RestartPolicyOnFailure,
					Containers: []corev1.Container{{
						Name:  "build",
						Image: idx.Spec.BuilderImage,
						Args:  []string{"--source", idx.Spec.SourceURI, "--model", idx.Spec.EmbeddingModel},
					}},
				}},
			},
		}
		if err := ctrl.SetControllerReference(&idx, &job, r.Scheme()); err != nil {
			return ctrl.Result{}, err
		}
		return ctrl.Result{}, r.Create(ctx, &job) // the Job's own watch event will requeue us
	} else if err != nil {
		return ctrl.Result{}, err
	}

	// Observed state -> status (level-triggered: computed from current reality every time).
	idx.Status.Ready = job.Status.Succeeded > 0
	idx.Status.ObservedGeneration = idx.Generation
	return ctrl.Result{}, r.Status().Update(ctx, &idx)
}

func (r *VectorIndexReconciler) SetupWithManager(mgr ctrl.Manager) error {
	return ctrl.NewControllerManagedBy(mgr).
		For(&lumenv1.VectorIndex{}).
		Owns(&batchv1.Job{}). // reconcile the parent when an owned Job changes
		Complete(r)
}

The function never asks "what changed?"; it computes the desired child from the spec, compares with what exists, and writes status from observed reality. Owner references give cascading deletion for free.

8. Applications: How Teams Run Kubernetes

8.1 Golden paths and internal charts

Platform teams rarely let every service write raw manifests. They publish a golden path: a base image per language, a shared Helm chart (like lumen-service) or a higher-level abstraction (a CRD such as kind: Microservice, or a Backstage software template) that bakes in probes, security contexts, PDBs, topology spread and observability annotations. Service teams set a dozen values instead of 200 lines of YAML; platform teams can roll out a security fix to every service by bumping the chart.

8.2 Multi-tenancy by namespace

Teams are separated by namespaces with RBAC, ResourceQuotas, LimitRanges, NetworkPolicies (default-deny plus explicit allows) and Pod Security Admission at the restricted level. Cluster-wide concerns — ingress/gateway, cert-manager, external-secrets, monitoring, Karpenter — live in platform namespaces managed by the platform team.

8.3 Policy as code

Admission policies (Kyverno, OPA Gatekeeper, or built-in ValidatingAdmissionPolicy with CEL) enforce organisational rules at the API: images only from approved registries and pinned by digest, non-root, resource requests present, no hostPath, required labels for cost allocation. Shift-left versions of the same policies run in CI (kyverno apply, conftest) so engineers see violations before merge.

8.4 AI and GPU workloads

Inference services like assist-service are increasingly scheduled onto GPU nodes. DRA (GA in v1.34) lets Pods request devices with structured parameters rather than opaque extended resources like nvidia.com/gpu: 1; Karpenter provisions GPU instances on demand; KEDA scales on queue depth or token throughput; and model weights are cached on node-local storage or pre-pulled images to cut cold-start times. Batch embedding jobs use Jobs with indexed completions.

8.5 Local development

Developers run kind, k3d or Docker Desktop's Kubernetes locally, with Tilt or Skaffold rebuilding images and syncing files on change, and Testcontainers for integration tests (Spring Boot's @ServiceConnection wires containers into the application context). The same Helm chart or Kustomize base is used locally as in production to catch configuration drift early.

9. Case Studies

9.1 Google Borg: the ancestor

Verified The Borg paper (Verma et al., EuroSys 2015) describes a cluster manager running hundreds of thousands of jobs across many clusters, with declarative job specifications, a central replicated store, a scheduler with feasibility checking and scoring, and priority/quota mechanisms. Kubernetes' Pods, labels, Services and the separation of scheduler from state store are directly informed by Borg's lessons, which the paper lists explicitly (for example, that "jobs" as the only grouping mechanism was too restrictive, which led to labels). Source: Large-scale cluster management at Google with Borg.

9.2 OpenAI: scaling Kubernetes to 7,500 nodes

Verified In January 2021 OpenAI described running Kubernetes clusters of up to 7,500 nodes for large ML training workloads. They reported issues and solutions around networking throughput (moving away from an overlay network), splitting Kubernetes events into a separate etcd cluster, API server memory, and monitoring at scale, and noted that many of their workloads use an entire node per Pod. The lesson for ordinary teams: the control plane (API server, etcd, watches) is the scaling bottleneck long before workers are. Source: OpenAI, "Scaling Kubernetes to 7,500 nodes".

9.3 The ingress-nginx retirement

Verified In November 2025 Kubernetes SIG Network and the Security Response Committee announced that the community ingress-nginx controller would be retired, with best-effort maintenance ending in March 2026 and no further releases or security fixes afterward; they cited a lack of maintainers and recommended migrating to Gateway API or another controller. A January 2026 statement from the Steering and Security Response Committees reiterated the risk of running it after retirement. The lesson: a "default" open-source component can be the least-funded piece of your stack — track the health of critical dependencies, and prefer standard APIs (Gateway API) that let you swap implementations. Sources: Kubernetes blog, "Ingress NGINX Retirement: What You Need to Know"; Kubernetes blog, Steering and SRC statement (2026).

9.4 Kubernetes failure stories

Verified The community-curated "Kubernetes Failure Stories" list collects public postmortems from many organisations — DNS failures, OOM kills, CPU throttling, etcd and API server overload, admission webhook outages. Reading a handful is the fastest way to learn which defaults bite in practice. Source: k8s.af — Kubernetes Failure Stories.

12. Common Mistakes and Production Failures

  1. Liveness probe checks the database. The DB has a blip; every replica of every service fails liveness and restarts; the restart storm (JVM warm-up, connection storms) prolongs the outage.
  2. No startup probe for slow JVMs. A liveness probe with a short initialDelaySeconds kills the JVM before it finishes starting, producing CrashLoopBackOff only under CPU-constrained conditions (e.g., during node scale-up).
  3. Memory limit below JVM footprint or -Xmx hard-coded to the limit → OOMKilled.
  4. No PDB, or a PDB that allows zero disruptions. The first causes outages during node upgrades; the second blocks upgrades indefinitely.
  5. Using :latest tags with imagePullPolicy: IfNotPresent — different nodes run different code. Pin digests.
  6. Deployment replicas set in Git while an HPA manages it. Every sync resets replicas to the Git value, fighting the autoscaler. Omit replicas when an HPA owns it.
  7. Secrets in ConfigMaps or baked into images, or assuming base64 is encryption.
  8. CPU requests far below real usage, making nodes overcommitted and HPA percentages meaningless.
  9. Ignoring the termination race: no preStop delay and app keep-alive shorter than the LB idle timeout → 502s on every deploy.
  10. Copying the whole repo before dependency resolution in Dockerfiles, destroying cache efficiency; or building as root and running as root.
  11. Helm values sprawl: every manifest field exposed as a value, until the chart is a worse version of raw YAML. Expose what varies; hard-code standards.
  12. Treating the cluster as a pet: manual kubectl edit in production. The next GitOps sync silently reverts it, or worse, it is never captured and lost on cluster rebuild.

13. Production Concerns

13.1 Performance

Measure startup (time to ready), steady-state CPU per request, memory working set and throttling for each service, and set requests from the 90th–95th percentile of usage. Keep images small and layered; pre-pull large images (AI models) with DaemonSets or bake them into node AMIs. Spread replicas across zones but be aware of cross-AZ data transfer cost (Chapter 4); topology-aware routing can keep Service traffic in-zone.

13.2 Security

  • Pod Security Admission restricted: non-root, no privilege escalation, dropped capabilities, seccomp RuntimeDefault, read-only root filesystem.
  • Default-deny NetworkPolicies; allow only required flows (gateway → orders, orders → RDS).
  • Workload identity (EKS Pod Identity or IRSA) instead of node IAM roles or static keys.
  • Image scanning (Trivy, Grype, ECR scanning), signed images (Sigstore cosign) and admission verification; SBOMs from BuildKit.
  • RBAC least privilege; no cluster-admin for CI; audit logs enabled; etcd encryption with KMS.

13.3 Scalability

Control-plane load scales with objects and watchers: large numbers of ConfigMaps, Secrets and CRDs, chatty controllers and kubectl get --watch loops from tools all cost API server memory. Use label selectors and field selectors, set revisionHistoryLimit, clean up completed Jobs (ttlSecondsAfterFinished), and prefer fewer, larger clusters per environment with namespaces over hundreds of tiny clusters — unless isolation requirements dictate otherwise.

13.4 Monitoring

kube-state-metrics (object state: desired vs available replicas, restarts, OOMKilled reasons), cAdvisor via the kubelet (container CPU, memory, throttling), node-exporter (node resources), control-plane metrics (API latency, etcd), and events exported to your log store. Alert on: Deployment unavailable replicas, CrashLoopBackOff, OOMKilled, Pods pending longer than N minutes, HPA at max replicas, PDB with zero allowed disruptions for a long time, certificate expiry. Chapter 5 builds these dashboards.

13.5 Reliability and maintainability

Upgrade the cluster at least every few minor versions (EKS standard support covers each minor for about 14 months, extended support for a further 12 at extra cost) Version-sensitive · checked Nov 2026; test upgrades in staging with the same add-ons; run kubectl deprecations-style checks (Pluto, kubent) in CI to catch removed APIs. Keep everything in Git and apply through GitOps so the cluster can be rebuilt from scratch — the ultimate disaster-recovery test.

14. Exercises

Exercise 1 · Foundation

A colleague's Dockerfile for a Spring Boot service is FROM eclipse-temurin:21-jdk, COPY . ., RUN ./mvnw package, CMD java -jar target/app.jar. List four problems and rewrite the key lines.

Solution

(1) Full JDK and Maven repository in the runtime image — large, more CVEs; use multi-stage with a JRE runtime. (2) COPY . . before dependency resolution destroys caching; copy pom.xml first and use a cache mount for ~/.m2. (3) Fat JAR as one layer; use -Djarmode=tools extract --layers and copy each layer. (4) Shell-form CMD means /bin/sh is PID 1 and SIGTERM may not reach the JVM; use exec form. Also: runs as root (add a user), no memory settings (MaxRAMPercentage), tests skipped/unskipped deliberately. See §7.1 for the rewritten file.

Exercise 2 · Intermediate

Write probe configuration for a Spring Boot service that takes between 20 and 70 seconds to start depending on node load, must be restarted if it deadlocks, and should stop receiving traffic if its PostgreSQL connection pool is exhausted — but must not be restarted for that reason.

Solution
startupProbe:
  httpGet: {path: /actuator/health/liveness, port: management}
  periodSeconds: 5
  failureThreshold: 20        # 100 s budget, covers 70 s worst case
livenessProbe:
  httpGet: {path: /actuator/health/liveness, port: management}
  periodSeconds: 10
  failureThreshold: 3
readinessProbe:
  httpGet: {path: /actuator/health/readiness, port: management}
  periodSeconds: 5
  failureThreshold: 2
# application.yaml: management.endpoint.health.group.readiness.include=readinessState,db

Liveness contains only livenessState (a deadlocked Tomcat will fail to answer and be restarted). Readiness includes db, so pool exhaustion removes the Pod from endpoints without restarting it. Consider whether all replicas could go unready simultaneously; if so, prefer a custom indicator with hysteresis.

Exercise 3 · Intermediate

An HPA targets 70% CPU. The Deployment has 5 replicas, each requesting 250m, and Pods are actually using 600m each. What does the HPA do, and what is wrong?

Solution

Utilisation = 600/250 = 240%. Desired = ceil(5 × 240/70) = ceil(17.1) = 18 replicas (clamped to maxReplicas). The request is unrealistic: the service needs ~600m per Pod at this load, so requests should be raised to ~600–700m. Then utilisation reads ~90%, and HPA computes ceil(5 × 90/70) = 7 — a proportionate response. Unrealistic requests also overcommit nodes and cause CPU contention.

Exercise 4 · Advanced

During an EKS managed node group upgrade, orders-service (3 replicas, all on one node due to no spread constraints, no PDB) had a 90-second outage. Explain the mechanism and design the fix with manifests.

Solution

The upgrade drains nodes via the Eviction API. Without a PDB, all three Pods on the drained node were evicted at once; replacements had to be scheduled, pull the image and pass startup/readiness (~60–90 s for a JVM). Fix: (1) topologySpreadConstraints on zone and hostname so replicas land on different nodes; (2) a PDB with maxUnavailable: 1 so drains evict one at a time and wait for replacements to be ready; (3) minReadySeconds and fast startup; (4) maxUnavailable: 0 in the rolling update strategy; (5) optionally a higher minimum replica count. See §7.4 for the manifests.

Exercise 5 · Advanced

Design a Helm chart change so that any change to a mounted ConfigMap rolls the Deployment, and explain why Kubernetes does not do this on its own. Then give the Kustomize equivalent.

Solution

The Pod template does not change when a referenced ConfigMap's data changes, so the Deployment controller sees no new template hash and does nothing (mounted files eventually update in place, but env vars never do, and many apps read config only at startup). Helm: add checksum/config: {{ include (print $.Template.BasePath "/configmap.yaml") . | sha256sum }} to spec.template.metadata.annotations. Kustomize: generate the ConfigMap with configMapGenerator, which suffixes a content hash to its name and updates references, changing the Pod template.

15. Interview Questions

Conceptual Walk me through what happens when you run kubectl apply on a Deployment.

Authentication, RBAC authorisation, mutating admission, validation, validating admission, write to etcd. The Deployment controller creates/updates a ReplicaSet; the ReplicaSet controller creates Pods; the scheduler filters and scores nodes and binds Pods; the kubelet creates the sandbox via CRI, sets up networking via CNI, pulls images, starts containers and runs probes; when ready, the EndpointSlice controller adds the Pod IP and kube-proxy/the CNI updates rules. Each step is a controller reacting to watched state.

Conceptual What is the difference between liveness and readiness, and why should liveness not check dependencies?

Liveness failure restarts the container; readiness failure removes it from Service endpoints. Dependencies failing is not fixed by restarting your process; including them in liveness turns a dependency blip into a fleet-wide restart storm.

Conceptual Explain QoS classes and how they affect eviction and OOM.

Guaranteed (requests = limits for CPU and memory on all containers), Burstable (some requests), BestEffort (none). Under node memory pressure, the kubelet evicts BestEffort first, then Burstable exceeding requests. The kubelet also sets oom_score_adj so the kernel OOM killer prefers BestEffort and spares Guaranteed.

Architecture Why did Kubernetes introduce Gateway API when Ingress already existed?

Ingress was too limited and relied on non-portable annotations; it mixed infrastructure and application concerns in one object. Gateway API offers role-oriented resources (GatewayClass, Gateway, Routes), typed features (header matching, weights, timeouts), multiple protocols and cross-namespace attachment rules, and conformance tests across implementations.

Architecture How would you make a JVM service scale fast enough for spiky traffic on Kubernetes?

Reduce time-to-ready (CDS/AOT cache, lazy init, smaller images, layer caching), keep headroom with a lower HPA target, scale on a leading metric (RPS or queue depth via KEDA) rather than CPU, aggressive scale-up behaviour, pre-provisioned node capacity (Karpenter with over-provisioning placeholders), and consider native images for extreme cases.

Coding Write a kubectl command to list Pods that were OOMKilled in the last restart across all namespaces.
kubectl get pods -A -o json | jq -r '.items[] | select(any(.status.containerStatuses[]?; .lastState.terminated.reason == "OOMKilled")) | "\(.metadata.namespace)/\(.metadata.name)"'
Scenario After a deploy, 1% of requests return 502 for about 20 seconds. What do you check?

Termination sequence: is there a preStop delay so endpoints/LB deregistration propagate before shutdown? Is server.shutdown=graceful on, and is the grace period long enough? Is the app's keep-alive timeout longer than the LB's idle timeout? Is maxUnavailable 0 and readiness correct so new Pods receive traffic only when ready? Check LB target health timelines against Pod events.

Scenario A node drain hangs forever during a cluster upgrade. Why might that be?

A PDB allows zero disruptions (e.g., minAvailable equals replicas, or replicas are unhealthy so the budget is already consumed), or a Pod has no controller and drain refuses to delete it, or local storage blocks eviction. Check kubectl get pdb -A for ALLOWED DISRUPTIONS 0.

Conceptual Helm vs Kustomize — when would you use each?

Helm for distributable packages with options, dependencies, versioned releases and rollback (third-party software, internal shared charts). Kustomize for patching plain YAML per environment with minimal abstraction. They compose: render Helm, then patch with Kustomize, often via Argo CD.

Behavioral Describe how you would migrate a team from VM deployments to Kubernetes.

Start with one low-risk service; containerise with a standard Dockerfile; define probes, resources and PDB from measured VM data; run in parallel behind a weighted DNS or LB split; build dashboards and runbooks; train the team; then migrate the rest via a golden-path chart. Communicate the operational responsibilities that change (no SSH, immutable deploys, GitOps).
