Application code is only one layer of your attack surface. The rest is the platform underneath it: where secrets live, how data is encrypted, how services prove who they are, what your cloud roles can do, what is inside your container image, how the cluster is configured, and whether the artifact you deploy is really the one you built. 1. Introduction: The Platform Is Part of Your Application

In a cloud-native estate, the question "is the order service secure?" includes: Is its database password in Git? Is customer data encrypted at rest with keys we control and can rotate? Do clients verify the server certificate, and does the server verify clients? Can its pod's cloud role delete every bucket? Does its image ship a shell, a package manager and 300 unused libraries with known CVEs? Can a compromised pod in another namespace reach it? Was the JAR built from the reviewed commit, or from something a compromised CI runner injected?

These questions span teams, which is precisely why they fall through gaps. This chapter equips you to own your service's answers.

Bridging from Java & Spring Boot

What you already know
You have encrypted a property with Jasypt (ENC(...)) or pulled one from Vault with Spring Cloud Vault; configured server.ssl.* or SSL bundles; used the JCA (Cipher, MessageDigest, KeyStore); built images with Jib or Buildpacks; written Helm values for a Deployment; added an IAM policy so your service could read from S3.
Why that is not enough
Jasypt with a master password in an environment variable moves the secret rather than managing it — no rotation, no audit, no revocation. The JCA lets you pick AES/ECB/PKCS5Padding without complaint. Buildpack images run as non-root, but a hand-written Dockerfile may not. A Helm chart without a securityContext runs privileged-ish defaults. An IAM policy with "Resource": "*" works on the first try — that is the problem.
The modern approach
Secrets in a manager (Vault, AWS Secrets Manager, GCP Secret Manager, Azure Key Vault) fetched at runtime with workload identity, rotated automatically, detected if leaked; AEAD encryption via high-level libraries (Tink) and KMS envelope encryption; TLS 1.3 everywhere with automated certificate management and mTLS between services; least-privilege IAM per workload; distroless/non-root images scanned and signed; Kubernetes with Pod Security Standards "restricted", default-deny NetworkPolicies and admission policies; SBOMs, SLSA provenance and signature verification at deploy time; and crypto agility to prepare for post-quantum migration.
Where Python and Go fit
Python's cryptography package and Go's standard crypto/* packages offer AEADs and TLS with good defaults (Go's TLS stack in particular is excellent, and Go supports hybrid post-quantum key exchange by default in recent versions). Go's static binaries make distroless or scratch images natural; Python images are larger and need more care. Supply-chain tooling (Syft, Grype, cosign) is itself written in Go.
In production
Platform teams provide the paved road: secret-store CSI driver or External Secrets Operator, cert-manager, a service mesh or SPIFFE for mTLS, IRSA/Pod Identity, admission policies (Kyverno/Gatekeeper), image signing in CI and verification at admission, CSPM for cloud posture, and centralised audit logs (CloudTrail, Kubernetes audit) feeding a SIEM.
Use it when / avoid it when
All of this applies to anything handling production data. Avoid inventing cryptography, building your own secret store, or adopting every tool at once — sequence the work by risk (secrets and IAM first, supply chain verification next, runtime security after).

2. History

2.1 Cryptography

DES was standardised in 1977; its 56-bit key was publicly brute-forced by the EFF's "Deep Crack" machine in 1998. Diffie and Hellman published public-key key exchange in 1976; RSA followed in 1977. AES (Rijndael) was selected by NIST in 2001. GCM mode was standardised in NIST SP 800-38D (2007); ChaCha20-Poly1305 was specified for IETF protocols in RFC 7539 (2015, updated by RFC 8439). SHA-1 collisions became practical with the SHAttered attack (Google and CWI, 2017). In August 2024 NIST published the first post-quantum standards: FIPS 203 (ML-KEM, from Kyber), FIPS 204 (ML-DSA, from Dilithium) and FIPS 205 (SLH-DSA, from SPHINCS+).

2.2 TLS and PKI

Netscape created SSL in the mid-1990s; TLS 1.0 (RFC 2246) followed in 1999, TLS 1.2 (RFC 5246) in 2008 and TLS 1.3 (RFC 8446) in August 2018, which removed static RSA key exchange, CBC-mode cipher suites and renegotiation, and cut the handshake to one round trip. TLS 1.0 and 1.1 were formally deprecated by RFC 8996 (2021). Heartbleed (2014) in OpenSSL leaked server memory, including private keys. Let's Encrypt began issuing free certificates in 2015 with the ACME protocol (RFC 8555, 2019), making automated certificate management normal. Certificate Transparency (RFC 6962, 2013) made mis-issuance publicly detectable. Version-sensitive · checked Nov 2026 In 2025 the CA/Browser Forum approved a schedule to shrink maximum public TLS certificate validity in steps, reaching 47 days by 2029 — making automation mandatory.

2.3 Secrets and identity in the cloud

HashiCorp Vault was released in 2015, introducing dynamic secrets (credentials generated on demand with leases). AWS Secrets Manager launched in 2018. AWS IAM Roles for Service Accounts (IRSA) arrived for EKS in 2019, followed by EKS Pod Identity in 2023; GCP and Azure offer workload identity equivalents. SPIFFE/SPIRE (CNCF) standardised workload identities for service-to-service mTLS. Kubernetes Secrets have existed since 1.0 (2015), stored base64-encoded (not encrypted) in etcd unless encryption at rest is configured.

2.4 Containers and Kubernetes

Docker (2013) made containers mainstream; Kubernetes 1.0 shipped in 2015. PodSecurityPolicy was deprecated in 1.21 and removed in 1.25 (2022), replaced by Pod Security Admission enforcing the Pod Security Standards (privileged, baseline, restricted). Google's distroless images (2017) popularised minimal runtime images. Runtime security tools such as Falco (CNCF, graduated 2024) detect suspicious behaviour via syscalls/eBPF.

2.5 Supply chain

The SolarWinds Orion compromise (disclosed December 2020) inserted a backdoor through the vendor's build system. In February 2021 Alex Birsan demonstrated "dependency confusion" against major companies' internal package names. US Executive Order 14028 (May 2021) pushed SBOMs into procurement. Log4Shell (CVE-2021-44228, December 2021) showed the cost of not knowing what is inside your software. Sigstore (2021, Linux Foundation/OpenSSF) made keyless signing practical; SLSA (Supply-chain Levels for Software Artifacts) reached v1.0 in April 2023 and Version-sensitive · checked Nov 2026 v1.2 in November 2025, which added a Source track. In March 2024 Andres Freund discovered the xz-utils backdoor (CVE-2024-3094) while investigating SSH latency — the product of a multi-year social-engineering campaign against a maintainer.

3. Fundamentals

3.1 Secrets management

A secret is any value that grants access: database passwords, API keys, OAuth client secrets, signing keys, TLS private keys, webhook HMAC keys, cloud access keys. The lifecycle has five stages, and most teams handle only the first:

  1. Storage — in a dedicated secret manager with encryption, access policy and audit: HashiCorp Vault / OpenBao, AWS Secrets Manager or SSM Parameter Store (SecureString), GCP Secret Manager, Azure Key Vault. Not in Git, not in container images, not in Helm values files, not in CI variables that every job can read.
  2. Delivery — the workload authenticates with its platform identity (Kubernetes service account → IRSA/Pod Identity/Workload Identity, or Vault's Kubernetes auth) and fetches only its own secrets. Delivery mechanisms: application SDK at startup (Spring Cloud Vault, Spring Cloud AWS), a sidecar/agent writing files (Vault Agent), the Secrets Store CSI Driver mounting files, or the External Secrets Operator syncing into Kubernetes Secrets.
  3. Rotation — scheduled and on-demand (after an incident or staff departure). Rotation must be designed: dual credentials (two active DB users, swap), or dynamic secrets that expire on their own.
  4. Revocation — ability to kill a credential immediately, and to know who used it.
  5. Detection — pre-commit hooks and CI scanning (gitleaks, TruffleHog, GitHub secret scanning with push protection), plus monitoring for leaked credentials in public places. A leaked secret must be rotated, not just deleted from Git history — assume it was copied the moment it was pushed.

Dynamic secrets (Vault's database secrets engine, AWS IAM temporary credentials, Cloud SQL IAM authentication) generate a unique credential per workload instance with a short lease. A leaked dynamic credential expires by itself, and audit logs attribute every query to a specific instance. They are the gold standard where supported.

Kubernetes Secrets are base64-encoded objects in etcd. They are only as safe as (a) etcd encryption at rest (EncryptionConfiguration, ideally with a KMS v2 provider), (b) RBAC on get/list/watch secrets — note that anyone who can create a pod in a namespace can mount any secret in it — and (c) node security. External Secrets Operator keeps the source of truth in a cloud secret manager and syncs; the Secrets Store CSI Driver can avoid creating Kubernetes Secret objects altogether.

About Jasypt: encrypting properties with a master password is better than plaintext in Git, but the master password becomes the secret you must manage, rotation means re-encrypting and redeploying, and there is no per-access audit. Treat it as a stepping stone to a secret manager.

3.3 Symmetric AEAD in practice

An AEAD takes a key, a nonce (number used once), plaintext and optional associated data (authenticated but not encrypted — e.g. a record ID or tenant ID so ciphertext cannot be swapped between records), and produces ciphertext plus a tag. Decryption verifies the tag and fails on any modification. The critical rule for AES-GCM: never reuse a nonce with the same key. Reuse reveals the XOR of plaintexts and lets an attacker forge tags. With 96-bit random nonces, NIST guidance limits a single key to about 232 encryptions to keep collision probability negligible (see §6). Envelope encryption with per-object data keys keeps you far below that limit. ChaCha20-Poly1305 is fast in software without AES hardware instructions; XChaCha20's 192-bit nonce makes random nonces safe at any realistic volume.

3.4 Asymmetric cryptography

Public-key cryptography solves key distribution: anyone can verify a signature or encrypt to a public key; only the private-key holder can sign or decrypt. It is slow and size-limited, so real systems use it to agree on or wrap symmetric keys (hybrid encryption, TLS key exchange) and to sign hashes. Choose elliptic-curve algorithms (X25519/Ed25519, P-256) for new designs; RSA remains ubiquitous in PKI and JWT.

3.5 Key management, KMS and envelope encryption

A KMS (AWS KMS, Google Cloud KMS, Azure Key Vault, or an HSM) holds key-encryption keys (KEKs) that never leave it in plaintext. Envelope encryption: for each object (or batch), ask the KMS to generate a data-encryption key (DEK); it returns the DEK in plaintext and encrypted under the KEK. Encrypt data locally with the DEK (AES-GCM), discard the plaintext DEK, and store the encrypted DEK next to the ciphertext. To decrypt, send the encrypted DEK to KMS (which checks IAM policy and logs the call), get the plaintext DEK back, decrypt locally. Benefits: bulk data never travels to the KMS; every decryption is authorised and audited; rotating the KEK does not require re-encrypting data (KMS keeps old key versions to unwrap old DEKs); crypto-shredding (destroy a KEK to make all data under it unrecoverable) supports deletion requirements.

Encryption context (AWS) / associated data binds the DEK to metadata such as tenant ID; decrypt fails if the context differs, and the context appears in CloudTrail — useful for audits and for preventing confused-deputy reuse of encrypted blobs across tenants.

3.6 Key rotation and crypto agility

Rotation limits the data exposed by one key compromise and the amount of data encrypted under one key. Design rotation in from day one: store a key ID/version with every ciphertext (Tink does this automatically with its keyset prefix), support decrypting with old versions while encrypting with the current one, and re-encrypt lazily or in background jobs when you must retire old keys. Crypto agility is the broader property of being able to change algorithms — not just keys — without redesign: algorithm identifiers in formats, abstraction layers (Tink primitives, JCA providers), inventories of where each algorithm is used. It is the prerequisite for post-quantum migration.

3.7 Post-quantum readiness

A sufficiently large quantum computer running Shor's algorithm would break RSA and elliptic-curve cryptography (key exchange and signatures). Symmetric crypto and hashes are only weakened modestly by Grover's algorithm (AES-256 remains comfortable). The urgent threat today is harvest now, decrypt later: traffic recorded today could be decrypted in future, so long-lived confidential data in transit needs quantum-resistant key exchange now. The industry response is hybrid key exchange combining a classical algorithm with ML-KEM, so security holds if either is unbroken. Version-sensitive · checked Nov 2026 Verified Chrome has negotiated X25519MLKEM768 by default since late 2024 (Chrome 131), and Cloudflare reports that a majority of human-initiated HTTPS traffic to its network is now post-quantum protected. Go's crypto/tls enables X25519MLKEM768 by default from Go 1.24; OpenSSL 3.5 (April 2025) added ML-KEM, ML-DSA and SLH-DSA. JDK support is arriving via JEPs (ML-KEM and ML-DSA APIs landed in JDK 24); hybrid TLS in the JDK's own TLS stack lags behind — terminating TLS at a PQ-capable proxy or mesh is the pragmatic route for Java services. Post-quantum signatures in the Web PKI are further away. Actions now: inventory cryptography, prefer hybrid key exchange at edges you control, and build agility.

3.8 TLS 1.3 essentials

TLS provides server authentication (via certificates), confidentiality and integrity for a connection. TLS 1.3 mandates forward secrecy (ephemeral (EC)DHE or KEM key exchange — a later theft of the server's private key does not decrypt recorded sessions), allows only AEAD cipher suites (TLS_AES_128_GCM_SHA256, TLS_AES_256_GCM_SHA384, TLS_CHACHA20_POLY1305_SHA256), encrypts most of the handshake including the certificate, and completes in one round trip (1-RTT), with optional 0-RTT resumption whose early data can be replayed — only use 0-RTT for idempotent requests. TLS 1.2 remains acceptable with ECDHE + AEAD suites; disable TLS 1.0/1.1.

3.9 Certificates and PKI

An X.509 certificate binds a public key to names (Subject Alternative Names — DNS names, IPs, URIs such as SPIFFE IDs) and is signed by a certificate authority. Verification builds a chain: leaf → intermediate(s) → a root in the client's trust store, checking each signature, validity dates, key usage/extended key usage, name constraints, and the hostname against SANs. Revocation (CRLs, OCSP) is unreliable in practice — browsers rely on short lifetimes and their own mechanisms; Let's Encrypt has ended OCSP in favour of CRLs and shorter-lived certificates. Internal services use a private CA (Vault PKI, AWS Private CA, cert-manager with a CA issuer, SPIRE, or the mesh's built-in CA) with lifetimes of hours to days.

3.10 Mutual TLS

In mTLS the server also requests and verifies a client certificate, so both ends are authenticated at the transport layer. It is the standard for service-to-service authentication in zero-trust networks (service meshes such as Istio and Linkerd do it transparently; SPIFFE IDs like spiffe://prod.example.com/ns/orders/sa/orders-api become the principal). mTLS authenticates the workload; it does not replace user-level authorization or per-request tokens. RFC 8705 also uses mTLS to bind OAuth tokens to client certificates.

3.11 IAM fundamentals

Cloud IAM answers "may principal P perform action A on resource R under conditions C?". Principals: human users (ideally federated via SSO, not IAM users with long-lived keys), roles assumed by workloads, service accounts. Policies: JSON documents of statements with Effect (Allow/Deny), Action, Resource and Condition. Policy types in AWS: identity-based (attached to roles/users), resource-based (bucket policies, KMS key policies), permission boundaries (cap on what identity policies can grant), Organizations SCPs and RCPs (account/organisation-wide guardrails), and session policies.

AWS policy evaluation, simplified: start with implicit deny; any applicable explicit Deny anywhere wins; then the request must be allowed by every applicable guardrail (SCPs, RCPs, permission boundary, session policy); and it must be allowed by an identity-based or resource-based policy (for same-account access, either suffices in most cases; cross-account access needs both sides). This is why "I added an Allow and it still fails" usually means an SCP, a boundary or a KMS key policy is missing an allow.

Least privilege in IAM: specific actions (not s3:*), specific resource ARNs (not *), conditions (source VPC, encryption context, tags, aws:PrincipalOrgID), separate roles per workload, no long-lived access keys, IAM Access Analyzer to generate policies from observed usage and to find external access.

3.12 Workload identity

Instead of distributing static cloud credentials, the platform issues a signed identity token to the workload (the Kubernetes service account token projected into the pod, or a CI provider's OIDC token), and the cloud exchanges it for short-lived credentials for a specific role. AWS: IRSA (OIDC federation, annotate the service account with a role ARN) or EKS Pod Identity (agent-based association); GCP: Workload Identity Federation for GKE; Azure: Microsoft Entra Workload ID. CI: GitHub Actions OIDC → AWS AssumeRoleWithWebIdentity, with trust policy conditions on repository and branch (token.actions.githubusercontent.com:sub). The result: no secrets to leak, credentials that expire in about an hour, and audit trails naming the workload.

3.13 Shared responsibility, misconfiguration and CSPM

Cloud providers secure the infrastructure (physical, hypervisor, managed-service internals); customers secure what they configure: identities, network exposure, data protection settings, and their workloads. The more managed the service, the more the provider handles — but configuration is always yours. Industry reports have long found that most cloud security failures stem from customer misconfiguration: public buckets, overly permissive security groups (0.0.0.0/0 on SSH or databases), unencrypted snapshots shared publicly, disabled logging, wildcard IAM. CSPM (cloud security posture management — AWS Security Hub, Microsoft Defender for Cloud, Google Security Command Center, or open-source Prowler/ScoutSuite) continuously evaluates configurations against benchmarks such as the CIS Foundations Benchmarks. Preventive guardrails (SCPs denying public bucket ACLs, policy-as-code checks on Terraform with Checkov/tfsec/OPA Conftest) beat detective ones.

3.14 Container image security

  • Minimal base images: distroless (no shell, no package manager), Chainguard/Wolfi images, or scratch for static Go binaries. Fewer packages, fewer CVEs, fewer tools for an attacker.
  • Non-root: USER 65532 (or any non-zero UID); never require root at runtime.
  • Multi-stage builds: build tools stay in the builder stage.
  • Pin by digest: FROM image@sha256:... so builds are reproducible and cannot silently change.
  • No secrets in layers: use BuildKit secret mounts; anything written in a layer is in the image forever even if deleted later.
  • Scan: Trivy, Grype, Docker Scout, cloud registry scanning — in CI and continuously in the registry (new CVEs appear for old images).
  • Sign and attest: cosign signatures and SBOM/provenance attestations (§3.17–3.18).

3.15 Kubernetes security

  • API access and RBAC: authenticate humans via OIDC; grant namespace-scoped Roles rather than ClusterRoles; avoid wildcards; watch for dangerous verbs (create pods, get secrets, escalate, bind, impersonate, nodes/proxy). Disable automounting of service-account tokens for pods that do not call the API.
  • Pod Security Standards: three levels — privileged (unrestricted), baseline (prevents known privilege escalations: no privileged containers, host namespaces, hostPath, added dangerous capabilities), restricted (hardened: must run as non-root, drop ALL capabilities, no privilege escalation, seccomp RuntimeDefault, restricted volume types). Enforced per namespace by the built-in Pod Security Admission controller via labels.
  • NetworkPolicies: by default all pods can talk to all pods. Apply default-deny ingress and egress per namespace, then allow specific flows (including DNS). Requires a CNI that enforces them (Calico, Cilium, cloud CNIs with policy support).
  • Admission control: validating/mutating policies with Kyverno, OPA Gatekeeper, or the built-in ValidatingAdmissionPolicy (CEL, GA in 1.30): require signed images from approved registries, resource limits, labels, no latest tags.
  • Secrets: encryption at rest with KMS; external secret stores; tight RBAC.
  • Runtime security: detect anomalous behaviour (shell spawned in a container, unexpected outbound connections, writes to sensitive paths) with Falco, Tetragon or commercial agents; read-only root filesystems make tampering visible.
  • Node and control plane: managed control planes, patched node images, restricted node IAM roles, IMDS hop limit, CIS Kubernetes Benchmark checks (kube-bench).
  • Audit logging: Kubernetes API audit logs to the SIEM.

3.16 Software supply-chain threats

Threats exist at every step from source to running workload: compromised developer accounts and source repositories; malicious or compromised dependencies (typosquatting, account takeover of maintainers, protestware, the xz-style long con); dependency confusion (a public package with the same name as your internal one and a higher version gets resolved by a misconfigured package manager); compromised build systems (SolarWinds); tampered artifacts in transit or in registries; and deployment of unverified artifacts. Defences map onto these steps: branch protection and signed commits; dependency pinning, lockfiles, private registries with scoped namespaces (and claiming your internal names publicly), and review of new dependencies; isolated, ephemeral, hermetic builds with provenance; signing; and verification at admission.

3.17 SBOMs

A Software Bill of Materials lists the components (with versions, package URLs, hashes, licences) in an artifact. Two main formats: CycloneDX (OWASP; also covers services, ML models, and VEX — vulnerability exploitability exchange statements saying "not affected because…") and SPDX (Linux Foundation, ISO/IEC 5962:2021; version 3.0 released 2024). Generate them at build time from the build tool's resolved graph (CycloneDX Maven/Gradle plugins) or from images (Syft), store them with the artifact (as attestations), and query them when the next Log4Shell lands.

3.18 SLSA and Sigstore

SLSA is a framework of incrementally adoptable levels describing how trustworthy an artifact's production was. The Build track levels: L1 — provenance exists (a document stating how the artifact was built: builder, source, parameters); L2 — provenance is generated and signed by a hosted build platform; L3 — the build platform is hardened so that builds are isolated from each other and signing material is inaccessible to user-defined build steps, making provenance unforgeable by tenants. v1.2 adds a Source track about the integrity of source history. Provenance uses the in-toto attestation format.

Sigstore provides free signing infrastructure: cosign signs and verifies container images and other artifacts; Fulcio is a CA that issues short-lived certificates binding a signing key to an OIDC identity (e.g. "this GitHub Actions workflow in this repository"); Rekor is a transparency log recording signatures so they can be audited. "Keyless" signing means no long-lived private key to protect: the CI job's OIDC identity is the signer. Verification checks the signature, the certificate identity and issuer, and the Rekor inclusion proof.

3.19 Security logging, audit and SIEM at the platform level

Collect: cloud control-plane audit logs (AWS CloudTrail including data events for sensitive buckets, GCP Cloud Audit Logs, Azure Activity Logs), KMS and secret-manager access logs, Kubernetes audit logs, VPC flow logs or equivalent, identity provider logs, CI/CD logs, and application security events (Chapter 11.1). Centralise in a SIEM, protect log integrity (separate account, object lock), correlate on identities, and write detections for high-signal events: root account use, IAM policy changes, disabling of logging, new access keys, secret reads by unexpected principals, KMS key deletion scheduled, privileged pods created, exec into production pods.

4. Internal Working

4.1 The TLS 1.3 handshake, message by message

  1. ClientHello: supported versions, cipher suites, supported groups (e.g. X25519MLKEM768, X25519, P-256), signature algorithms, a key share for the client's preferred group(s), a random value, SNI (server name), and ALPN (e.g. h2).
  2. ServerHello: chosen suite and group plus the server's key share. Both sides now compute the shared secret and, via HKDF, derive handshake traffic keys. If the client guessed the wrong group, the server sends a HelloRetryRequest (costing one extra round trip).
  3. Everything after ServerHello is encrypted: EncryptedExtensions, optional CertificateRequest (for mTLS), Certificate (the chain), CertificateVerify (a signature over the handshake transcript with the certificate's private key — proving possession), and Finished (a MAC over the transcript).
  4. The client validates the chain and hostname, verifies CertificateVerify and Finished, sends its own Certificate/CertificateVerify if requested, then Finished. Application data flows under traffic keys derived from the key schedule.
  5. The server may send NewSessionTicket messages enabling resumption (PSK), optionally with 0-RTT early data next time.

Because the key exchange is ephemeral and the certificate key is used only to sign the transcript, compromise of the certificate key later does not expose past sessions (forward secrecy). With a hybrid group such as X25519MLKEM768, the shared secret combines an X25519 secret and an ML-KEM-768 secret; an attacker must break both.

4.2 Certificate chain validation

The client (e.g. Java's PKIXValidator via the default X509TrustManager) builds a path from the leaf to a trust anchor using issuer/subject names and key identifiers, possibly fetching missing intermediates (Java does not fetch AIA by default — servers must send the full chain). For each certificate it checks the signature with the issuer's public key, validity period, basic constraints (only CAs may sign), key usage, extended key usage (serverAuth/clientAuth), name constraints, and policy. Then the endpoint identification algorithm checks that the requested hostname matches a SAN entry (Java's HttpsURLConnection/HttpClient do this; raw SSLSocket does not unless you set SSLParameters.setEndpointIdentificationAlgorithm("HTTPS")). Disabling any of these "for testing" is how production ends up trusting anyone.

4.3 Envelope encryption with AWS KMS, step by step

  1. Service calls GenerateDataKey with the KEK ID, key spec AES_256 and an encryption context (e.g. {"tenant":"t-42","purpose":"invoice"}). KMS checks the caller's IAM permissions and the key policy, then returns Plaintext (32 bytes) and CiphertextBlob (the DEK encrypted under the KEK, including a key version reference). CloudTrail records the call with the context.
  2. Service generates a 96-bit random nonce and encrypts the data with AES-256-GCM, using the context (or record ID) as associated data.
  3. Service stores {version, encryptedDek, nonce, ciphertext+tag}, and zeroes/drops the plaintext DEK.
  4. To read: call Decrypt with the encrypted DEK and the same context. KMS authorises, logs, unwraps with the right key version, returns the DEK. Decrypt locally; the GCM tag check fails if anything was altered.
  5. Caching DEKs for a short time (AWS Encryption SDK supports a caching cryptographic materials manager) reduces KMS calls and cost, trading some audit granularity.

4.4 How IRSA turns a service account into AWS credentials

  1. The EKS cluster has an OIDC issuer; an IAM OIDC identity provider for that issuer is registered in the account.
  2. The pod's service account is annotated with a role ARN. The EKS pod identity webhook mutates the pod to project a service-account token with audience sts.amazonaws.com into a file and sets AWS_ROLE_ARN and AWS_WEB_IDENTITY_TOKEN_FILE.
  3. The AWS SDK's default credential chain finds these and calls sts:AssumeRoleWithWebIdentity with the token.
  4. STS validates the token's signature against the cluster's OIDC discovery keys and evaluates the role's trust policy, which should restrict sub to system:serviceaccount:<namespace>:<name> and aud to sts.amazonaws.com.
  5. STS returns temporary credentials (typically valid for an hour); the SDK refreshes them automatically.

A trust policy that omits the sub condition lets any service account in the cluster assume the role — a common and serious misconfiguration. EKS Pod Identity simplifies this with an association API and an on-node agent, avoiding per-cluster OIDC providers.

4.5 The Kubernetes request path and admission

Every API request passes: authentication (client certs, OIDC tokens, service-account tokens) → authorization (RBAC, plus Node authorizer and webhooks) → mutating admission (defaults, sidecar injection, Kyverno mutate rules) → object schema validation → validating admission (Pod Security Admission, ValidatingAdmissionPolicy, Kyverno/Gatekeeper validate rules, image-signature verification webhooks) → persistence in etcd. Policies that must not be bypassed belong in validating admission, which sees the final object after all mutations. Note that admission only applies to API writes; it does not re-check running pods when policies change (use audit/background scans for that).

4.6 Producing and verifying provenance in CI

  1. The CI job (e.g. GitHub Actions on a hosted runner) builds the artifact from a specific commit.
  2. The job requests an OIDC token from the CI provider, whose claims identify the repository, workflow file, ref and commit.
  3. cosign (or actions/attest-build-provenance) generates an ephemeral key pair, obtains a short-lived certificate from Fulcio binding the public key to the OIDC identity, signs the artifact digest and an in-toto provenance statement, and records the signature in Rekor.
  4. The signature and attestations are stored in the registry next to the image (as OCI referrers).
  5. At deploy time, an admission controller (Kyverno verifyImages, Sigstore policy-controller) verifies: the signature is valid; the certificate identity matches an expected workflow (e.g. https://github.com/acme/orders/.github/workflows/release.yml@refs/heads/main); the issuer is the expected OIDC issuer; the Rekor entry exists; and optionally that provenance claims (source repo, builder) match policy.

4.7 How Log4Shell worked (defender's view)

Log4j 2 supported "lookups" — ${...} expressions expanded inside log messages — including a JNDI lookup. When an application logged an attacker-controlled string (a header, a username), Log4j expanded the lookup, made a JNDI request (e.g. LDAP) to an attacker-controlled server, and could load and execute a remote Java class (on older JDKs or via deserialization gadgets on newer ones). The root causes: an interpreter (lookup expansion) hidden inside a logging call — an injection sink nobody considered a sink — plus unrestricted outbound network access from servers. Effective mitigations, in order: upgrade (2.17.1+ for the 2.x line, now later versions), remove the JndiLookup class as a stopgap, restrict egress so servers cannot reach arbitrary LDAP/HTTP endpoints, and WAF rules as temporary virtual patching. Early mitigations such as the formatMsgNoLookups flag turned out to be incomplete (CVE-2021-45046), which is why "upgrade and verify" beats configuration workarounds.

4.8 How the xz backdoor worked (defender's view)

Over roughly two years, a contributor using the name "Jia Tan" built trust in the xz-utils project, aided by sock-puppet accounts pressuring the overworked maintainer to add a co-maintainer. Having gained release rights, they shipped release tarballs for versions 5.6.0 and 5.6.1 (February–March 2024) containing build-script modifications not present in the Git repository, which extracted a malicious object from binary "test files" during the build. On certain Linux distributions where OpenSSH's sshd is linked against libsystemd, which in turn loads liblzma, the payload hooked RSA key verification in sshd to allow an attacker holding a specific key to execute commands. It was caught before reaching most stable distributions because Andres Freund noticed sshd logins using unusually high CPU and Valgrind errors, and investigated. Lessons: release artifacts that differ from the source repository are a risk (reproducible builds and building from source tags address this); test fixtures and build scripts deserve review; maintainer burnout is a security issue; and transitive dependency chains (sshd → libsystemd → liblzma) are often invisible.

5. Architecture: Handshakes, Chains, Envelopes, Policies and Pipelines

5.1 TLS 1.3 with mutual authentication

Reading the diagram: the key exchange completes in the first flight (ClientHello/ServerHello), so the certificates travel encrypted — an observer cannot see which service identities are talking. CertificateVerify is a signature over the whole transcript, which both authenticates the server and prevents downgrade tampering. In mTLS the server's CertificateRequest triggers the client's own certificate; the server then maps the SPIFFE URI in the client certificate's SAN to an authorization principal. In a mesh, sidecars perform this on behalf of both applications.

5.2 A certificate chain

Reading the diagram: the root key is kept offline because compromising it compromises everything below; day-to-day issuance uses an intermediate that can be revoked and replaced. The server must send the leaf and intermediate; the client already has the root. Each check on the right is a place where custom "trust all" code silently disables security.

5.3 Envelope encryption

Reading the diagram: the KMS only ever handles 32-byte keys, so bulk data never leaves your service, while every decryption still requires a KMS call that IAM can deny and CloudTrail records. The encryption context must match on decrypt; a blob copied from tenant t-42 into tenant t-7's records fails to decrypt under t-7's context.

5.4 AWS IAM policy evaluation (simplified)

Reading the diagram: the default is deny; an explicit Deny anywhere is final; guardrails (SCPs/RCPs, boundaries, session policies) can only restrict, never grant; and a grant must come from an identity- or resource-based policy. The real algorithm has more nuance (e.g. how resource-based policies interact with boundaries for role sessions); consult the AWS documentation's evaluation flowchart when debugging. For KMS keys, the key policy is required to allow access — identity policies alone are not enough unless the key policy delegates to IAM.

5.5 Kubernetes defence layers

Reading the diagram: build-time controls reduce what can go wrong; admission controls ensure only compliant workloads start; runtime controls limit and detect what a compromised workload can do. Each layer catches failures of the previous one: an unsigned image is rejected at admission; a signed-but-vulnerable image is constrained by NetworkPolicy and a read-only filesystem; an exploit that spawns a shell is detected at runtime (and fails outright on distroless, which has no shell).

5.6 Supply chain from source to cluster

Reading the diagram: each arrow is a trust transfer that an attacker could intercept. The controls ensure that what runs in production can be traced to reviewed source built by a trusted builder from known dependencies — and that this is checked by machine at deploy time rather than assumed. Continuous scanning closes the loop: an image that was clean when built becomes vulnerable when a new CVE is published, and the SBOM makes that query instant.

6. The Math: Nonces, Key Sizes, Security Levels and Rotation

6.1 Random nonce collisions in AES-GCM

Intuition: if you pick nonces at random from a space of size \( N \), collisions become likely after about \( \sqrt{N} \) picks (the birthday bound). The probability of at least one collision among \( q \) random \( b \)-bit nonces is approximately

\[ P_{\text{coll}} \approx \frac{q^2}{2^{b+1}} \]

For GCM's 96-bit nonces and a target \( P \le 2^{-32} \): \( q^2 \le 2^{65} \Rightarrow q \le 2^{32.5} \). That is why NIST SP 800-38D limits random-nonce GCM to \( 2^{32} \) invocations per key. Illustrative A service encrypting 10,000 records per second would hit \( 2^{32} \approx 4.3\times10^9 \) in about 5 days with a single key — but with envelope encryption, each object has its own DEK and the bound is irrelevant. XChaCha20's 192-bit nonce pushes the bound to \( 2^{80} \).

6.2 Security levels

"Bits of security" means the attacker needs about \( 2^{n} \) operations. Approximate equivalences (NIST SP 800-57): AES-128 ≈ 128 bits; RSA-3072 ≈ 128 bits; ECC P-256 / X25519 ≈ 128 bits; RSA-2048 ≈ 112 bits; SHA-256 collision resistance ≈ 128 bits. Against quantum attackers, Grover roughly halves symmetric security (AES-256 → ~128), while Shor breaks RSA/ECC entirely regardless of size — hence ML-KEM. ML-KEM-768 targets roughly AES-192-equivalent security (NIST category 3).

6.3 Key rotation exposure

If a key is compromised at a uniformly random time and remains in use until the next rotation every \( T \), the expected data exposed under that key (for constant write rate \( w \)) is \( w\,T \) for past data (if no forward secrecy at rest) and the exposure window for future data averages \( T/2 \). Rotation does not help past data already encrypted under a stolen KEK unless you re-encrypt; it bounds future exposure.

6.4 Credential lifetime

Static access keys have unbounded lifetime until someone rotates them; workload-identity credentials typically last about an hour. If a credential leaks at a random point in its life, the expected remaining validity for 1-hour credentials is 30 minutes; for a key rotated yearly, about six months. This back-of-envelope comparison is the strongest argument for workload identity.

6.5 TLS overhead

A full TLS 1.3 handshake costs one round trip plus a signature and a key exchange; on modern servers ECDHE + ECDSA/RSA verification takes well under a millisecond of CPU. Hybrid ML-KEM adds roughly a kilobyte to the ClientHello and ServerHello — which can push ClientHello over a single packet and break buggy middleboxes, the main practical deployment issue Chrome and Cloudflare reported. Connection reuse (HTTP/2, keep-alive pools) amortises handshakes; for mTLS-heavy meshes, CPU cost is dominated by data encryption (AES-GCM with AES-NI runs at gigabytes per second per core).

7.2 Envelope encryption in Java with AWS KMS

package com.example.crypto;

import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;
import java.security.SecureRandom;
import java.util.Arrays;
import java.util.Map;
import javax.crypto.Cipher;
import javax.crypto.spec.GCMParameterSpec;
import javax.crypto.spec.SecretKeySpec;
import software.amazon.awssdk.core.SdkBytes;
import software.amazon.awssdk.services.kms.KmsClient;
import software.amazon.awssdk.services.kms.model.DataKeySpec;
import software.amazon.awssdk.services.kms.model.DecryptRequest;
import software.amazon.awssdk.services.kms.model.GenerateDataKeyRequest;
import software.amazon.awssdk.services.kms.model.GenerateDataKeyResponse;

/** Format: [1 byte version][2 bytes encDEK length][encDEK][12 bytes nonce][ciphertext||tag] */
public final class EnvelopeCrypto {
    private static final byte VERSION = 1;
    private static final SecureRandom RNG = new SecureRandom();
    private final KmsClient kms;          // credentials from IRSA / Pod Identity via the default chain
    private final String kekId;           // e.g. alias/orders-data

    public EnvelopeCrypto(KmsClient kms, String kekId) { this.kms = kms; this.kekId = kekId; }

    public byte[] encrypt(byte[] plaintext, String tenantId) throws Exception {
        Map<String, String> ctx = Map.of("tenant", tenantId);
        GenerateDataKeyResponse dk = kms.generateDataKey(GenerateDataKeyRequest.builder()
                .keyId(kekId).keySpec(DataKeySpec.AES_256).encryptionContext(ctx).build());
        byte[] dek = dk.plaintext().asByteArray();
        byte[] encDek = dk.ciphertextBlob().asByteArray();
        try {
            byte[] nonce = new byte[12];
            RNG.nextBytes(nonce);
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(Cipher.ENCRYPT_MODE, new SecretKeySpec(dek, "AES"), new GCMParameterSpec(128, nonce));
            c.updateAAD(aad(tenantId));
            byte[] ct = c.doFinal(plaintext);
            return ByteBuffer.allocate(1 + 2 + encDek.length + nonce.length + ct.length)
                    .put(VERSION).putShort((short) encDek.length).put(encDek).put(nonce).put(ct).array();
        } finally {
            Arrays.fill(dek, (byte) 0);
        }
    }

    public byte[] decrypt(byte[] blob, String tenantId) throws Exception {
        ByteBuffer b = ByteBuffer.wrap(blob);
        if (b.get() != VERSION) throw new IllegalArgumentException("unknown format version");
        byte[] encDek = new byte[b.getShort()];
        b.get(encDek);
        byte[] nonce = new byte[12];
        b.get(nonce);
        byte[] ct = new byte[b.remaining()];
        b.get(ct);
        byte[] dek = kms.decrypt(DecryptRequest.builder()
                .ciphertextBlob(SdkBytes.fromByteArray(encDek))
                .encryptionContext(Map.of("tenant", tenantId))      // must match, or KMS refuses
                .keyId(kekId).build()).plaintext().asByteArray();
        try {
            Cipher c = Cipher.getInstance("AES/GCM/NoPadding");
            c.init(Cipher.DECRYPT_MODE, new SecretKeySpec(dek, "AES"), new GCMParameterSpec(128, nonce));
            c.updateAAD(aad(tenantId));
            return c.doFinal(ct);                                     // AEADBadTagException if tampered
        } finally {
            Arrays.fill(dek, (byte) 0);
        }
    }

    private static byte[] aad(String tenantId) { return ("tenant:" + tenantId).getBytes(StandardCharsets.UTF_8); }
}

For new code, consider Google Tink (com.google.crypto.tink) or the AWS Encryption SDK, which implement this format, key-ID prefixes and rotation for you; the hand-rolled version above is shown so the mechanism is visible.

func seal(key, plaintext, aad []byte) ([]byte, error) {
	block, err := aes.NewCipher(key) // 32-byte key = AES-256
	if err != nil {
		return nil, err
	}
	gcm, err := cipher.NewGCM(block)
	if err != nil {
		return nil, err
	}
	nonce := make([]byte, gcm.NonceSize())
	if _, err := rand.Read(nonce); err != nil {
		return nil, err
	}
	return gcm.Seal(nonce, nonce, plaintext, aad), nil // nonce prepended
}

8. Applications: A Realistic Adoption Sequence

Opinion Teams rarely adopt everything at once. A sequence that front-loads risk reduction:

  1. Secrets out of Git and images; secret scanning with push protection; rotate anything that ever leaked.
  2. Workload identity replaces static cloud keys in pods and CI (GitHub OIDC → cloud roles).
  3. Least-privilege IAM per workload, generated from Access Analyzer data; SCP guardrails (no public buckets, no disabling CloudTrail, region restrictions).
  4. TLS everywhere with cert-manager/ACME; mTLS via mesh for service-to-service.
  5. Image hardening: distroless/non-root base images from the platform team, Renovate keeping digests fresh, registry scanning.
  6. Kubernetes baseline: PSS restricted on application namespaces, default-deny NetworkPolicies, RBAC review, audit logs to SIEM.
  7. Supply chain: SBOM per build, keyless signing, provenance; verify at admission first in audit mode, then enforce.
  8. Encryption: KMS-backed encryption at rest everywhere (usually a checkbox), plus application-level envelope encryption for the most sensitive fields.
  9. Runtime detection and PQ-readiness inventory.

Platform teams expose these as defaults ("golden path" templates) so application teams inherit them rather than rebuilding them per service.

9. Case Studies

9.1 Log4Shell (2021) Verified

CVE-2021-44228 (CVSS 10.0) in Log4j 2 was disclosed on 9–10 December 2021 and exploited at scale almost immediately; follow-up CVEs showed early mitigations were incomplete. CISA called it one of the most serious vulnerabilities it had seen and added it to KEV. Organisations with SBOMs and dependency inventories could answer "where are we exposed?" in hours. Egress restrictions blocked the remote class-loading step even on unpatched hosts. Sources: NVD CVE-2021-44228; CISA Apache Log4j vulnerability guidance.

9.2 The xz-utils backdoor (2024) Verified

CVE-2024-3094: malicious code in xz-utils 5.6.0 and 5.6.1 release tarballs targeted OpenSSH on some Linux distributions. Andres Freund's report to the oss-security list on 29 March 2024 described the build-time injection and the sshd impact; distributions rolled back within hours, and most stable releases were never affected. Source: Andres Freund's oss-security disclosure; NVD CVE-2024-3094.

9.3 Dependency confusion (2021) Verified

Security researcher Alex Birsan published packages to public registries with names matching internal package names he found referenced by large companies; build systems configured to consult both public and private registries fetched his higher-versioned public packages, executing his (benign, reporting-only) code inside many organisations, under their bug bounty programmes. Fixes: scoped/namespaced packages, a single proxied registry with explicit precedence, and claiming internal names publicly. Source: Alex Birsan, "Dependency Confusion".

9.4 Capital One (2019) — IAM as the blast-radius control Verified

Covered in Chapter 11.3: the SSRF gave access to instance-role credentials, and the role's broad S3 read permissions turned a bug into a large breach. It is the canonical case for least-privilege IAM and IMDSv2. Source: Capital One incident facts.

9.5 Chrome and Cloudflare deploy hybrid post-quantum key exchange Verified

Chrome enabled hybrid Kyber/ML-KEM key agreement by default in 2024 and Cloudflare reports the share of PQ-protected traffic on its network on Cloudflare Radar; both documented middlebox breakage from larger ClientHellos as the main deployment issue. Source: Cloudflare Radar: post-quantum encryption adoption; Cloudflare, "The state of the post-quantum Internet" (2024).

11. Engineering Trade-offs

11.1 Where should encryption happen?

LayerProtects againstDoes not protect againstChoose when
Disk/volume encryption (provider-managed)Stolen disks, decommissioned hardwareAnyone with database accessAlways (baseline, nearly free)
Database TDE / storage service encryption with customer-managed KMS keyAbove + lets you revoke the provider's ability to read via key policyApplication or DBA accessRegulated data; tenant-level crypto-shredding
Application-level field encryption (envelope)DB admins, backups, SQL injection reading the columnCompromise of the application itselfPII/PCI fields, secrets, per-tenant keys
Client-side / end-to-endThe service operatorEndpoint compromise; enables few server featuresMessaging, zero-knowledge products

Field encryption costs searchability (equality search needs deterministic encryption or blind indexes, each leaking some information) and complicates analytics. Encrypt only the fields that warrant it.

11.2 Mesh mTLS vs application TLS

A mesh gives uniform mTLS and identity with no code changes, but adds an infrastructure layer and makes the application trust the local sidecar. Application-level TLS (SSL bundles, Go tls.Config) keeps control in the service but multiplies configuration. Opinion Above a dozen services, a mesh (or ambient/eBPF-based mTLS) usually wins; keep per-request user tokens regardless.

11.3 Verification enforcement

Enforcing signature verification at admission risks blocking deploys when the verifier or Rekor is unavailable. Mitigate with highly available admission controllers, caching, and a documented break-glass path that is itself audited — rather than running in audit-only mode forever.

12. Common Mistakes

  • Deleting a leaked secret from Git history without rotating it.
  • Trust-all TrustManagers / InsecureSkipVerify: true / verify=False left over from testing.
  • AES-GCM with a fixed or counter-reset nonce, or AES/ECB because it was the JCA default for "AES".
  • Using SHA-256 for passwords or plain SHA-256(key || message) as a MAC.
  • Hard-coded keys in source or config, including "test" keys that end up in production.
  • IRSA trust policies without a sub condition.
  • "Action": "*" / "Resource": "*" policies that were meant to be temporary.
  • Images tagged latest, built from unpinned base images, running as root.
  • Secrets passed as build args (visible in image history).
  • No NetworkPolicies — every compromised pod can reach every database.
  • Granting create pods broadly, unaware it implies reading every secret in the namespace.
  • CI workflows triggered by pull_request_target that check out untrusted code with secrets available, and third-party actions pinned to mutable tags.
  • Generating SBOMs nobody queries and signatures nobody verifies.
  • Assuming "encrypted at rest" means protected from your own application's compromise.

13. Production Concerns

13.1 Certificate and key operations

Automate issuance and renewal (cert-manager, ACME, mesh CAs); alert on certificates expiring within 14 days and on renewal failures; test reload without restarts (Spring Boot SSL bundle reloading, Go GetCertificate callbacks). Expired certificates remain a leading cause of self-inflicted outages.

13.2 KMS and secret-manager limits

KMS APIs have per-account request quotas; envelope encryption with DEK caching keeps you within them. Secret managers charge per secret and per call — fetch at startup and on rotation events, not per request.

13.3 Monitoring and detection

Alert on: CloudTrail StopLogging/DeleteTrail, root logins, new IAM access keys, ScheduleKeyDeletion on KMS keys, GetSecretValue by unexpected principals, instance credentials used outside the account's network, Kubernetes exec into production pods, privileged pod creation attempts denied by admission, Falco shell-in-container events, and admission rejections for unsigned images.

13.4 Reliability

Every security dependency on the request path (KMS, Vault, admission webhooks, policy engines) needs an availability design: caching, retries with backoff, regional replicas, and explicit fail-open/fail-closed decisions per path. Vault needs auto-unseal (KMS-backed) to recover from restarts without humans.

13.5 Compliance mapping

These controls map onto common frameworks: SOC 2 (logical access, change management), PCI DSS v4 (encryption of cardholder data, key management, TLS), ISO 27001 Annex A, NIST SSDF (SP 800-218) for secure development and supply chain, and the EU Cyber Resilience Act's requirements for vulnerability handling and SBOMs for products with digital elements. 14. Exercises

Exercise 1 · Foundation

Pick the primitive: (a) verify a partner's webhook; (b) store a user's national ID number so support can display it; (c) prove a container image came from your CI; (d) store passwords; (e) fingerprint uploaded files for deduplication.

Solution

(a) HMAC-SHA-256 with a shared secret (or the partner's signature with their public key). (b) AEAD field encryption with an envelope DEK under a KMS KEK, AAD = record ID. (c) Digital signature (cosign keyless, identity = CI workflow). (d) Argon2id/bcrypt. (e) SHA-256 (or BLAKE3); note that hashing low-entropy data does not hide it.

Exercise 2 · Intermediate

Review this IAM policy for an image-thumbnail service and rewrite it: {"Effect":"Allow","Action":"s3:*","Resource":"*"}. The service reads originals from acme-uploads/originals/ and writes to acme-uploads/thumbs/.

Solution
{
  "Version": "2012-10-17",
  "Statement": [
    { "Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::acme-uploads/originals/*" },
    { "Effect": "Allow", "Action": "s3:PutObject", "Resource": "arn:aws:s3:::acme-uploads/thumbs/*",
      "Condition": { "StringEquals": { "s3:x-amz-server-side-encryption": "aws:kms" } } }
  ]
}

No delete, no list, no other buckets, no bucket-policy changes. Attach to a dedicated role via workload identity with a trust policy scoped to the thumbnail service account. If the bucket uses a customer-managed KMS key, add kms:Decrypt/kms:GenerateDataKey on that key only.

Exercise 3 · Intermediate

Apply the PSS "restricted" profile to an existing namespace running a Helm chart that sets no securityContext. Predict what fails and fix it.

Solution

Use kubectl label --dry-run=server --overwrite ns X pod-security.kubernetes.io/enforce=restricted to see warnings first. Failures: missing runAsNonRoot, allowPrivilegeEscalation not false, capabilities not dropped, no seccomp profile. Fix by adding pod/container securityContext as in §7.7; if the image needs root (e.g. binds port 80 or writes to /var), change the port to ≥1024, mount emptyDir for writable paths, and rebuild on a non-root base.

Exercise 4 · Advanced

A new critical CVE affects a library used somewhere in your 80 microservices. Using SBOMs stored as cosign attestations, describe the commands/queries to find affected running workloads within an hour, and how VEX helps.

Solution

List running image digests from the clusters (kubectl get pods -A -o jsonpath over status.containerStatuses[*].imageID); for each digest, fetch the SBOM attestation (cosign verify-attestation --type cyclonedx ... then extract the predicate) or query your SBOM store (Dependency-Track ingests CycloneDX and does this continuously); search for the package URL and vulnerable version range; scan with Grype against the SBOM. Teams that determined the vulnerable code is unreachable publish a VEX statement ("not_affected", justification "vulnerable_code_not_in_execute_path"), which scanners then use to suppress noise — reviewed, not assumed.

Exercise 5 · Advanced (local lab)

In a local kind or minikube cluster you own, install Kyverno, write a policy requiring cosign signatures from your own key pair (cosign generate-key-pair), push a signed and an unsigned image to a local registry, and show that only the signed one is admitted.

Solution

Use a verifyImages rule with attestors.entries.keys.publicKeys set to your cosign.pub (keyless needs internet access to Fulcio/Rekor; key-based works offline with rekor.ignoreTlog: true for the lab only). Deploy both images; the unsigned one is rejected with a Kyverno policy violation message. Then sign the second image and redeploy to confirm admission.

15. Interview Questions

Conceptual Explain envelope encryption and why it is used with a KMS.

Data is encrypted locally with a per-object DEK; the DEK is encrypted by a KEK held in the KMS and stored with the data. Bulk data never goes to the KMS, every decrypt is authorised and audited, KEK rotation does not require re-encrypting data, and destroying a KEK crypto-shreds all data under it.

Conceptual What does TLS 1.3 change compared with TLS 1.2?

Mandatory forward secrecy (no static RSA key exchange), AEAD-only cipher suites, encrypted certificates and most of the handshake, 1-RTT handshake with optional 0-RTT resumption (replayable), removal of renegotiation and many legacy options, simplified HKDF key schedule.

Conceptual What is "harvest now, decrypt later" and what should a backend team do about it today?

Adversaries record encrypted traffic to decrypt once quantum computers can break ECDH/RSA. Use hybrid PQ key exchange (X25519MLKEM768) where you control TLS endpoints (proxies, Go services, CDNs), inventory crypto usage, and build crypto agility. Symmetric encryption at rest with AES-256 is not the urgent concern.

Architecture How would you get secrets into a Spring Boot pod on EKS with no static credentials?

IRSA or EKS Pod Identity gives the pod a role; Spring Cloud AWS (or External Secrets Operator / Secrets Store CSI) fetches from Secrets Manager using that role; rotation via Secrets Manager rotation Lambdas or dynamic DB credentials from Vault (Kubernetes auth). Nothing secret in the image, Helm values or Git.

Coding What is wrong with Cipher.getInstance("AES")?

On most JCA providers it defaults to AES/ECB/PKCS5Padding: deterministic, no IV, no integrity — identical blocks produce identical ciphertext. Use AES/GCM/NoPadding with a unique 12-byte nonce, or Tink.

Conceptual What do the Pod Security Standards levels mean?

Privileged: no restrictions. Baseline: blocks known privilege escalations (privileged containers, host namespaces, hostPath, dangerous capabilities). Restricted: additionally requires non-root, dropping all capabilities, no privilege escalation, seccomp RuntimeDefault, limited volume types. Enforced per namespace via labels by Pod Security Admission.

Architecture How do SBOM, SLSA provenance and Sigstore signatures differ?

An SBOM says what is in the artifact; provenance says how and from what source it was built and by which builder; a signature says who vouches for the artifact digest. Admission policies verify the signature identity and can check provenance claims; SBOMs feed vulnerability and licence analysis.

Scenario An AWS access key was committed to a public repo 10 minutes ago. What do you do?

Deactivate/delete the key immediately (do not wait for history rewrite); check CloudTrail for its use since creation, especially from unfamiliar IPs; look for persistence (new users, keys, roles, Lambda functions, instances); rotate anything it could read; then replace the use case with workload identity, enable push protection, and run a blameless review. GitHub and AWS may already have flagged it via secret scanning partnerships.

Scenario What lessons does the xz backdoor teach for a Java shop that never used xz directly?

Transitive and system-level dependencies matter (base images include such libraries); build from source repositories rather than opaque release artifacts where possible; prefer minimal base images; monitor anomalies; support and vet critical upstream maintainers; maintain SBOMs including OS packages so you can answer "do we ship it?" immediately.

Conceptual Why is IRSA's trust policy sub condition critical?

Without it, any service account token from the cluster's OIDC issuer can assume the role, so compromising any pod grants this role's permissions. The condition pins the role to one namespace/service account.

16. Knowledge Check

  • Secrets live in a manager, are delivered via workload identity, rotated, revocable and scanned for; a leaked secret is rotated, not just deleted.
  • Use AEAD (AES-GCM, ChaCha20-Poly1305) with unique nonces, HMAC for integrity, slow hashes for passwords, and envelope encryption with a KMS.
  • Build crypto agility now; deploy hybrid ML-KEM key exchange where you terminate TLS.
  • TLS 1.3 gives forward secrecy and encrypted handshakes; validate full chains and hostnames; automate short-lived certificates; use mTLS between services.
  • IAM: explicit deny wins; guardrails only restrict; grant specific actions on specific resources to per-workload roles.
  • Kubernetes: PSS restricted, default-deny NetworkPolicies, minimal RBAC, admission policies, runtime detection.
  • Supply chain: lockfiles and private proxies, SBOMs, SLSA provenance, Sigstore signatures verified at admission.

What is the most serious consequence of reusing an AES-GCM nonce with the same key?

  1. Slightly slower decryption
  2. Loss of confidentiality (XOR of plaintexts) and the ability to forge authentication tags
  3. Ciphertext becomes larger
  4. Nothing, GCM is nonce-misuse resistant
GCM is catastrophically broken by nonce reuse; AES-GCM-SIV is the misuse-resistant variant.

  4. Depends on the bucket region

Which property of TLS 1.3 ensures that stealing a server's certificate private key next year does not decrypt traffic recorded today?

  1. Forward secrecy from ephemeral key exchange
  2. Certificate Transparency
  3. OCSP stapling
  4. 0-RTT resumption
Session keys come from ephemeral (EC)DHE/KEM shares; the certificate key only signs the transcript.
