1. Introduction: The Most Consequential Decision You Will Make Twice

Almost every performance and correctness problem in a backend eventually reaches the database. Requests are slow because a query scans instead of seeks; the system is wrong because two transactions interleaved in a way the developer did not imagine; the bill is high because an index nobody uses is maintained on every write; the migration is painful because the data model chosen in year one fits year three's access patterns badly. Unlike stateless services, which you can rewrite and redeploy in a day, data has gravity: moving it is slow, risky and expensive. Teams usually choose a database twice: once quickly at the start, and once, painfully, when the first choice stops fitting.

This chapter aims to make the first choice better and the second one rarer. It covers four layers that build on each other:

  • Selection: a framework that starts from access patterns and non-functional requirements rather than fashion, and an honest comparison of relational and NoSQL families, including the vector stores that AI features now require.
  • Transactions: what ACID promises, the precise anomalies each isolation level allows, and how PostgreSQL and MySQL actually implement them with MVCC and locking.
  • Storage engines and indexes: the two dominant on-disk structures (B+trees and LSM-trees), their amplification trade-offs, and every index type you are likely to use.
  • Query execution: the planner, statistics, join algorithms, EXPLAIN ANALYZE, and the application-side problems (N+1, pool sizing, pagination) that dominate Spring applications.

Bridging from Java & Spring Boot

What you already know
Entities, repositories, @Transactional(isolation = ...), @Version optimistic locking, @Query with JPQL, Flyway migrations adding indexes, HikariCP defaults, Pageable with Page<T>, and the moment you discovered spring.jpa.show-sql printing 101 queries for one endpoint.
Why that is not enough
JPA abstracts the database so well that it hides the costs: lazy loading turns object navigation into network round trips; Page<T> issues an OFFSET query plus a COUNT(*), both of which degrade linearly; @Transactional's default isolation is whatever the database default is, which differs between PostgreSQL (Read Committed) and MySQL (Repeatable Read) and allows different anomalies; and an index declared in a migration may never be used because the query does not match its column order.
The modern approach
Choose stores per access pattern (a relational database as the default system of record, specialised stores where a pattern demands them); know the isolation guarantees you rely on and test for anomalies; design indexes from queries, verify with EXPLAIN (ANALYZE, BUFFERS), and remove unused ones; fetch exactly the data needed (DTO projections, fetch joins, batch fetching); size pools from Little's Law; paginate with keysets.
Where Python and Go fit
Python (psycopg 3, SQLAlchemy 2) and Go (pgx v5, database/sql, sqlc) are common for data services and tooling; they make SQL more explicit than JPA does, which removes N+1 surprises but not planner or isolation surprises. §7 shows equivalent patterns.
In production
Managed PostgreSQL or MySQL (RDS/Aurora, Cloud SQL/AlloyDB, Azure) as the system of record; pg_stat_statements or Performance Schema to find expensive queries; read replicas; Redis for caching; OpenSearch/Elasticsearch for search; a columnar warehouse for analytics; pgvector or a dedicated vector database for embeddings.
Use it when / avoid it when
Use a relational database by default whenever data is related, needs transactions or ad-hoc querying, and fits within a large single primary (or a sharded deployment, Chapter 5). Reach for a NoSQL family only when a specific access pattern, scale profile or data shape clearly favours it, and you accept its consistency and query limitations.

2. History: From Codd to Vectors

2.1 The relational model (1970–1990s)

Edgar F. Codd's 1970 paper A Relational Model of Data for Large Shared Data Banks separated logical data from physical storage. IBM's System R (mid-1970s) produced SQL and the first cost-based optimizer (Selinger et al., 1979), whose dynamic-programming join ordering remains the template for planners today. Oracle shipped commercially in 1979. Rudolf Bayer and Edward McCreight published the B-tree in 1970–1972; its B+tree variant became the universal on-disk index. Jim Gray's work on transactions and the ACID acronym (named by Härder and Reuter in 1983), and the ARIES recovery algorithm (Mohan et al., 1992) defined how databases survive crashes using write-ahead logging.

2.2 Open-source relational databases (1990s–2000s)

Michael Stonebraker's POSTGRES project at Berkeley (from 1986) became PostgreSQL in 1996; MySQL appeared in 1995 and gained the transactional InnoDB engine (made the default in MySQL 5.5, 2010). Multi-version concurrency control, described academically in the late 1970s and early 1980s, became the dominant concurrency approach in both.

2.3 The NoSQL wave (2006–2015)

Google's Bigtable paper (2006) and Amazon's Dynamo paper (2007) showed how to build massively scalable stores by relaxing relational features. Their descendants include HBase, Cassandra (open-sourced by Facebook in 2008) and DynamoDB (2012). MongoDB (2009) popularised the document model; Redis (2009) the data-structure server; Neo4j the graph model. The log-structured merge-tree (O'Neil et al., 1996) became the storage engine of choice for write-heavy stores via LevelDB (2011) and RocksDB (Facebook, 2012). The "NoSQL" label itself spread in 2009.

2.4 NewSQL and the relational comeback (2012–present)

Google Spanner (2012) demonstrated globally distributed, externally consistent SQL transactions; CockroachDB, YugabyteDB and TiDB followed. Meanwhile PostgreSQL absorbed many NoSQL use cases: jsonb with GIN indexes (9.4, 2014), declarative partitioning (10, 2017), logical replication, and an extension ecosystem (PostGIS, TimescaleDB, Citus, pgvector). PostgreSQL 18 (September 2025) added an asynchronous I/O subsystem, B-tree skip scan for multicolumn indexes, and a built-in uuidv7() function; PostgreSQL 19 was released in November 2026 Version-sensitive · checked Nov 2026.

2.5 Vector search (2017–present)

Approximate nearest-neighbour (ANN) indexes such as HNSW (Malkov and Yashunin, first published 2016) and libraries such as Faiss (Meta, 2017) made similarity search over embeddings practical. With retrieval-augmented generation, vector search became a mainstream database feature: dedicated systems (Milvus, Qdrant, Weaviate, Pinecone) and extensions/features in general-purpose stores (pgvector for PostgreSQL, OpenSearch/Elasticsearch k-NN, Redis 8 vector sets, MongoDB Atlas Vector Search).

3. Fundamentals

3.1 A database selection framework

Choose a database by answering these questions in order, writing the answers down. The first questions are about the data and its use; vendor and fashion come last.

  1. What are the access patterns? List the top queries by frequency and importance: lookups by key, range scans by time, multi-attribute filters, joins across entities, full-text search, similarity search, graph traversals, aggregations over large ranges. The dominant patterns decide the data model.
  2. What consistency and transactional guarantees are required? Do multi-entity invariants need atomic enforcement (money, inventory, bookings)? Is read-your-writes enough? Can some reads be stale?
  3. What is the scale profile? Data volume and growth, read and write QPS, peak factor, value sizes, hot-spot risk (Chapter 1 estimation). Does it fit on one large primary for the planning horizon?
  4. What are latency and availability targets? Single-digit millisecond p99? Multi-region writes? RPO/RTO?
  5. How will the schema evolve? Stable and relational, or heterogeneous and fast-changing? (Note that "schemaless" stores still have a schema; it lives in application code.)
  6. What are the operational realities? Team expertise, managed-service availability, backup/restore and point-in-time recovery, observability, licensing, cost at projected scale, ecosystem (drivers, Spring Data support, migration tooling).

For most new systems of record, the answer is a relational database (PostgreSQL is the default choice of many teams), possibly accompanied by purpose-built stores: Redis for caching, a search engine for full-text, a warehouse for analytics, and a vector index for embeddings. This is polyglot persistence; its cost is keeping derived stores in sync (usually via CDC and Kafka, Chapter 7) and operating several systems.

3.2 The relational model and ACID

The relational model stores data as relations (tables) of tuples (rows) with typed attributes, related by keys, queried declaratively. Its enduring strengths: normalisation eliminates update anomalies by storing each fact once; joins recombine facts flexibly for queries nobody anticipated; constraints (primary keys, foreign keys, unique, check, exclusion) enforce invariants in the database regardless of which application writes; and transactions group operations atomically.

ACID is the set of transaction guarantees:

  • Atomicity: all of a transaction's writes take effect or none do. Implemented with a write-ahead log (WAL in PostgreSQL, redo log plus undo log in InnoDB); on abort or crash, partial work is rolled back.
  • Consistency: transactions move the database from one valid state to another with respect to declared constraints. This is partly the application's responsibility; the database enforces only the constraints you declare.
  • Isolation: concurrent transactions do not interfere beyond what the chosen isolation level permits. The ideal is serializability (the outcome equals some serial order); weaker levels trade anomalies for concurrency.
  • Durability: once committed, data survives crashes. The WAL is flushed (fsync) at commit (synchronous_commit in PostgreSQL, innodb_flush_log_at_trx_commit=1 in MySQL); replication extends durability beyond one machine.

3.3 Isolation levels and anomalies

Anomalies are the observable effects of interleaving that would not happen serially:

  • Dirty write: overwriting another transaction's uncommitted write. Prevented by every practical level.
  • Dirty read: seeing another transaction's uncommitted write.
  • Non-repeatable read (read skew): reading the same row twice and seeing different committed values, or reading two related rows at different points in time (e.g. seeing account A before a transfer and account B after it, so money appears to vanish).
  • Phantom read: re-running a query with a predicate and seeing a different set of rows because another transaction inserted or deleted matching rows.
  • Lost update: two transactions read a value, both compute a new value from it, both write; one update is lost (classic read-modify-write on a counter or JSON document).
  • Write skew: two transactions read an overlapping set of rows, each makes a decision based on what it read, and each writes to different rows, together violating an invariant neither violated alone. Example: an on-call rule "at least one doctor on call"; two doctors simultaneously check that two are on call and each removes themselves.

3.4 MVCC

Multi-version concurrency control keeps multiple versions of each row so that readers see a consistent snapshot without blocking writers, and writers do not block readers. Each transaction (or statement) reads the versions visible to its snapshot; writes create new versions. Conflicts only arise between writers of the same row. MVCC is why a long analytical SELECT in PostgreSQL or InnoDB does not block your OLTP updates. The two engines implement it very differently (§4.1, §4.2): PostgreSQL stores old and new versions side by side in the table (and cleans up later with VACUUM), while InnoDB updates rows in place in the clustered index and keeps old versions in undo logs. The difference explains PostgreSQL's bloat and vacuum tuning, InnoDB's purge lag and "history list length", and much of the debate in the Uber case study (§9.1).

3.5 NoSQL families and when to use each

"NoSQL" groups very different systems. What they share is relaxing some relational property (joins, multi-row transactions, fixed schema, or strong consistency) in exchange for a scaling or modelling advantage for particular access patterns.

  • Key-value stores (Redis/Valkey, DynamoDB in its simplest use, etcd, FoundationDB's base layer, RocksDB embedded). Operations: get/put/delete by key, sometimes ranges. Use for sessions, caches, feature flags, idempotency keys, user preferences, anything accessed only by primary key at very high rates. Avoid when you need queries by attributes other than the key.
  • Document stores (MongoDB, Couchbase, Firestore; also PostgreSQL jsonb). Store self-contained, nested documents (JSON/BSON), with secondary indexes on fields. Use when entities are naturally hierarchical and read/written as a whole (a product with variants, a CMS page, a user profile with nested settings), with heterogeneous attributes. Avoid when data is highly interconnected (many-to-many relationships require application-side joins or duplication).
  • Wide-column stores (Apache Cassandra, ScyllaDB, HBase, Google Bigtable). Data is partitioned by a partition key and sorted within a partition by clustering columns; each partition is a sorted map that can be very large. Queries must specify the partition key; you design tables per query ("query-first modelling"), duplicating data across tables. Use for very high write throughput, time-ordered data per entity (messages per channel, events per device), multi-datacenter replication with tunable consistency. Avoid for ad-hoc queries, joins, or strong multi-row transactions.
  • Graph databases (Neo4j, Amazon Neptune, JanusGraph; also recursive SQL CTEs or Apache AGE in PostgreSQL). Nodes and edges with properties; queries traverse relationships (Cypher, Gremlin, and the ISO GQL standard published in 2024). Use for deep or variable-length relationship queries: fraud rings, recommendations ("friends of friends who bought"), access-control graphs, knowledge graphs for GraphRAG. Avoid for simple one-hop relationships a relational join handles fine.
  • Time-series databases (TimescaleDB on PostgreSQL, InfluxDB, Prometheus, QuestDB, ClickHouse for many TS workloads). Optimised for append-heavy timestamped data, time-range queries, downsampling, retention policies and compression. Use for metrics, IoT telemetry, financial ticks. Avoid for frequently updated entities.
  • Search engines (Elasticsearch, OpenSearch, Apache Solr; Lucene underneath). Inverted indexes for full-text relevance ranking (BM25), faceting, fuzzy matching, aggregations. Usually a derived, eventually consistent copy of a system of record. Use for product search, log search, autocomplete. Avoid as the primary store of record.
  • Vector databases and indexes (pgvector, Milvus, Qdrant, Weaviate, Pinecone, OpenSearch k-NN, Redis 8 vector sets). Store embeddings and answer approximate nearest-neighbour queries with indexes such as HNSW (graph-based) or IVF (cluster-based), often combined with metadata filters and keyword search (hybrid retrieval). Use for semantic search, RAG retrieval, recommendations and deduplication. Key trade-offs: recall versus latency versus memory, filter handling, and update cost. For up to millions of vectors with relational metadata, pgvector inside your existing PostgreSQL is often simplest; at hundreds of millions to billions, or with demanding latency, dedicated systems earn their operational cost. Part 8 covers retrieval in depth.

3.7 Storage engines: B+trees and LSM-trees

Under any data model, a storage engine organises bytes on disk. Two designs dominate.

B+tree (update-in-place). Data lives in fixed-size pages (8 KB in PostgreSQL, 16 KB default in InnoDB) organised as a balanced tree. Internal pages hold keys and child pointers; leaf pages hold keys and either the row data (InnoDB clustered index) or pointers to it (PostgreSQL heap TIDs), and leaves are linked for range scans. Lookups descend from root to leaf in \(O(\log_F N)\) page reads, where fanout \(F\) is in the hundreds, so even billions of rows need only 3–5 levels, of which the upper levels are almost always cached. Writes modify pages in place (after logging to the WAL); a full page splits. Reads are fast and predictable; writes cost random I/O and write amplification (a 100-byte change rewrites an 8 KB page, plus WAL, plus full-page images after checkpoints in PostgreSQL). Used by PostgreSQL, InnoDB, SQL Server, Oracle, SQLite.

LSM-tree (log-structured merge). Writes go to an in-memory sorted structure (the memtable) and a sequential WAL for durability. When the memtable fills, it is flushed to disk as an immutable sorted file (an SSTable). Over time many SSTables accumulate; background compaction merges them, discarding overwritten and deleted (tombstoned) entries. Reads check the memtable, then SSTables from newest to oldest; Bloom filters per SSTable skip files that definitely do not contain the key, and sparse indexes/fence pointers locate the block within a file. Writes are sequential and fast; reads may touch several files; compaction consumes I/O and CPU in the background. Used by RocksDB (and through it MyRocks, CockroachDB's earlier storage, TiKV, Kafka Streams state stores), Cassandra, ScyllaDB, HBase, LevelDB, and Pebble (CockroachDB).

The comparison is usually framed through three amplification factors: write amplification (bytes written to storage per byte written by the application), read amplification (I/Os or bytes read per query), and space amplification (bytes on disk per byte of live data). No structure minimises all three (the "RUM conjecture"); compaction strategy chooses the point on the trade-off:

  • Size-tiered compaction (Cassandra STCS default for many years): merge SSTables of similar size into bigger ones. Low write amplification, higher space amplification (temporarily up to 2x during large merges) and read amplification.
  • Leveled compaction (RocksDB default, Cassandra LCS): levels L0, L1, …, each about 10x larger than the previous, each level (except L0) a set of non-overlapping SSTables. Lower read and space amplification (~1.1x), higher write amplification (each byte is rewritten roughly once per level times the fanout factor).
  • Time-window compaction (Cassandra TWCS): group SSTables by time window, never compact across windows; ideal for TTL'd time-series where whole files expire.
  • Unified / hybrid strategies (Cassandra 5.0's Unified Compaction Strategy, RocksDB universal compaction) let you tune between tiered and leveled behaviour.

3.8 Index types

An index is a redundant data structure that trades write cost and space for faster reads on specific predicates. Each index type serves different operators.

  • B-tree (default in PostgreSQL and MySQL): equality and range (=, <, >, BETWEEN, IN), prefix LIKE 'abc%' (with appropriate collation/operator class), ORDER BY without a sort, IS NULL. The workhorse.
  • Hash: equality only. In PostgreSQL, WAL-logged and crash-safe since 10; occasionally smaller and faster than B-tree for long keys with equality lookups, but no ordering or range support. InnoDB has no user-defined hash indexes (it has an internal adaptive hash index).
  • Composite (multicolumn): a B-tree on (a, b, c) is sorted by a, then b within a, then c. It efficiently serves predicates on a leftmost prefix: a; a, b; a, b, c; and a = ? AND b > ? (equality columns first, then one range column). It cannot efficiently serve b = ? alone, because b values are scattered across the whole index, except via a full index scan, or via the skip scan optimisation (MySQL 8.0.13+; PostgreSQL 18+) when the leading column has few distinct values. Column order rule of thumb: equality-filtered columns first (most selective among them first is a minor concern), then the range or sort column.
  • Covering index / index-only scan: if the index contains every column the query needs, the engine can answer from the index alone. PostgreSQL supports non-key payload columns with INCLUDE (11+), and index-only scans still check the visibility map (requires a well-vacuumed table). In InnoDB every secondary index implicitly includes the primary key, so a secondary index on (email) covers SELECT id FROM users WHERE email = ?.
  • Partial (filtered) index (PostgreSQL): indexes only rows matching a predicate, e.g. WHERE status = 'PENDING'. Tiny, cheap to maintain, perfect for queue-like tables where queries target a small subset. Also used for conditional uniqueness (UNIQUE (email) WHERE deleted_at IS NULL).
  • Expression (functional) index: index the result of an expression, e.g. lower(email) or (payload ->> 'customerId'). The query must use the identical expression. MySQL 8 supports functional key parts.
  • GIN (Generalized Inverted Index, PostgreSQL): maps each element (array element, jsonb key/value, full-text lexeme, trigram) to the rows containing it. Serves containment and membership: @>, ?, &&, full-text @@, and LIKE '%abc%' via pg_trgm. Fast reads, slower writes (mitigated by the pending list / fastupdate).
  • GiST (Generalized Search Tree): a balanced tree framework for data with overlap or distance semantics: geometric and geographic types (PostGIS), ranges (tstzrange overlap &&), nearest-neighbour ordering (ORDER BY location <-> point), and exclusion constraints (e.g. no two bookings for the same room with overlapping time ranges). SP-GiST covers space-partitioned structures (quadtrees, radix trees).
  • BRIN (Block Range Index): stores min/max (or other summaries) per range of table blocks (default 128 pages). Minuscule (kilobytes for terabyte tables) and effective only when the column's values correlate with physical row order, such as an append-only created_at. Ideal for huge time-series or log tables queried by time range.
  • Vector indexes (pgvector HNSW and IVFFlat): approximate nearest-neighbour over embeddings with distance operators (<-> L2, <=> cosine, <#> negative inner product).
  • Unique indexes enforce constraints; clustered organisation (InnoDB primary key, SQL Server clustered index) stores rows in index order, which makes primary-key range scans fast and makes the choice of primary key a physical-layout decision (random UUIDv4 keys cause page splits and poor locality; time-ordered UUIDv7 or sequences do not).

3.9 Query optimization basics

SQL is declarative: the planner/optimizer chooses how to execute. It enumerates candidate plans (access paths per table: sequential scan, index scan, bitmap scan, index-only scan; join orders; join algorithms), estimates each plan's cost using statistics about the data (row counts, distinct values, most common values, histograms, correlation), and picks the cheapest. Most bad plans are caused by bad estimates (stale statistics, correlated columns treated as independent, parameters whose selectivity varies wildly), not by the cost model itself. EXPLAIN shows the chosen plan with estimates; EXPLAIN ANALYZE executes it and shows actual rows and timings, so you can spot where estimate and reality diverge.

Join algorithms:

  • Nested loop: for each outer row, look up matching inner rows (ideally via an index). Best when the outer side is small and the inner side has an index on the join key. Cost roughly \(N_{outer} \times \text{cost(inner lookup)}\). Disastrous when the planner underestimates the outer side (estimated 10 rows, actually 1 million).
  • Hash join: build a hash table on the smaller input's join key, then probe it with each row of the larger input. Best for large, unsorted inputs with equality joins. Needs memory (work_mem); spills to disk in batches if the hash table does not fit.
  • Merge join: sort both inputs on the join key (or read them from indexes already sorted) and merge. Best when both inputs are large and already sorted, or for range-style join conditions in some engines.

3.10 Connection pooling

Opening a database connection is expensive (TCP, TLS, authentication, and in PostgreSQL a new backend process with its own memory). A connection pool (HikariCP is Spring Boot's default) keeps connections open and lends them to threads. Pool size is the most commonly misconfigured setting in Spring applications, and bigger is usually worse: the database can only execute as many queries concurrently as it has cores (plus some overlap for I/O waits), and extra concurrent queries add context switching, lock contention and memory pressure. HikariCP's documentation suggests starting from connections = (core_count × 2) + effective_spindle_count for the database server, shared across all application instances, and validating with load tests. Little's Law (Chapter 1) gives the application-side view: connections needed ≈ queries per second × average connection hold time. Where many instances must share a small number of database connections, add a server-side pooler (PgBouncer in transaction mode, RDS Proxy, or built-in poolers in some managed services).

3.11 Pagination: offset versus keyset

Offset pagination (ORDER BY created_at DESC LIMIT 20 OFFSET 10000) makes the database produce and discard 10,000 rows to return 20, so cost grows linearly with page depth; and concurrent inserts shift rows between pages, causing duplicates or skipped items. Spring Data's Page<T> adds a COUNT(*) query on every page, which on large tables can cost more than the page itself. Keyset (seek, cursor) pagination remembers the last row's sort key and asks for rows after it: WHERE (created_at, id) < (:lastCreatedAt, :lastId) ORDER BY created_at DESC, id DESC LIMIT 20. With an index on (created_at DESC, id DESC), every page is an index seek plus 20 rows, regardless of depth, and results are stable under inserts. The trade-off: no "jump to page 537", which users rarely need; infinite scroll and API cursors fit keyset naturally. Spring Data 3.1+ supports keyset scrolling with Window<T> and ScrollPosition.

4. Internal Working

4.1 PostgreSQL MVCC: tuples, visibility and vacuum

Every row version (tuple) in a PostgreSQL heap page carries a header with xmin (the ID of the transaction that created it) and xmax (the ID of the transaction that deleted or superseded it, or zero). An UPDATE never modifies a tuple in place: it marks the old tuple's xmax and inserts a new tuple (with a pointer from old to new, t_ctid). A DELETE just sets xmax. A transaction's snapshot records which transaction IDs were committed when it was taken; a tuple is visible if its xmin committed before the snapshot and its xmax is unset, aborted, or not yet committed as of the snapshot. Commit status is looked up in the commit log (pg_xact) and cached in tuple hint bits.

Consequences:

  • Dead tuples accumulate. Old versions remain until no snapshot can see them. VACUUM (usually autovacuum) removes them, making space reusable, and updates the visibility map (which enables index-only scans) and free space map. A long-running transaction (or an idle-in-transaction session, or a stale replication slot) holds back the cleanup horizon for the whole database, causing bloat in busy tables.
  • Every index points at a tuple location. A new tuple version normally requires new entries in every index on the table, even if indexed columns did not change. The HOT (heap-only tuple) optimisation avoids this when no indexed column changes and the new version fits on the same page; leaving free space in pages (fillfactor < 100) increases HOT updates for update-heavy tables.
  • Transaction ID wraparound. XIDs are 32-bit; vacuum must "freeze" old tuples before IDs wrap around (about 2 billion transactions). Neglected vacuum on huge, busy databases can force emergency anti-wraparound vacuums, which is why vacuum monitoring is a production essential.

4.2 InnoDB: clustered index, undo logs and next-key locks

InnoDB stores each table as a B+tree clustered on the primary key: leaf pages contain the full rows in primary-key order. Secondary indexes store the indexed columns plus the primary key value, not a physical pointer; a lookup by secondary index finds the primary key and then descends the clustered index (a "bookmark lookup"). Consequences: a long primary key bloats every secondary index; random primary keys (UUIDv4) scatter inserts across the clustered tree, causing page splits and poor cache locality; and updating a row does not change secondary indexes unless their columns change, because they reference the stable primary key.

Updates are made in place in the clustered index; the previous version is written to the undo log, and each row carries a hidden transaction ID and a roll pointer to its undo record. A consistent read reconstructs the version visible to its read view by following undo records. The purge thread removes undo records no longer needed; a long-running transaction stops purge, and the history list length grows (InnoDB's analogue of PostgreSQL bloat). The redo log (WAL) provides durability; the doublewrite buffer protects against torn page writes.

For locking reads under Repeatable Read, InnoDB takes next-key locks: a lock on an index record plus the gap before it, which prevents other transactions from inserting into the scanned range (preventing phantoms for locking reads). Range scans without a suitable index lock large parts of the table, which is a common cause of unexpected blocking and deadlocks in MySQL applications; insert intention locks and gap locks are what SHOW ENGINE INNODB STATUS deadlock reports are full of.

4.3 The write-ahead log and checkpoints

Both engines follow the WAL rule: a change is durable once its log record is flushed, and data pages can be written lazily later. At commit, the log is flushed (one sequential fsync, often batched across concurrent commits: group commit). Periodic checkpoints write dirty pages to data files so recovery need only replay the log since the last checkpoint. In PostgreSQL, the first modification of a page after a checkpoint writes a full-page image into the WAL (to survive torn pages), so very frequent checkpoints inflate WAL volume; max_wal_size and checkpoint_timeout balance recovery time against WAL volume. The WAL is also the replication stream (Chapter 5) and the source for CDC.

4.4 The LSM write and read paths

  1. Write: append the record to the WAL (sequential), insert into the memtable (a skiplist in RocksDB), acknowledge. Deletes write a tombstone.
  2. Flush: when the memtable reaches its size limit, it becomes immutable, a new memtable takes writes, and the immutable one is written as an L0 SSTable (sorted key-value blocks, an index block, a Bloom filter block, and metadata).
  3. Compaction: background threads merge SSTables per the compaction strategy, keeping the newest version of each key and dropping tombstones once no older data could be shadowed by them. If compaction falls behind the write rate, L0 files pile up and the engine stalls writes to protect read performance: the classic LSM failure mode under sustained heavy writes.
  4. Point read: memtable → immutable memtables → L0 files (which may overlap, so each is checked) → one file per deeper level. For each candidate file, consult the Bloom filter (in memory); if it says "maybe", use the block index to read one block (often from block cache).
  5. Range scan: merge iterators over the memtable and all levels; Bloom filters do not help (prefix Bloom filters can, for prefix-bounded scans).

Tombstones have a cost of their own: a range of deleted data still has to be read past until compaction removes it. Cassandra users meet this as "tombstone overwhelming" errors when queue-like access patterns delete heavily and then scan.

4.5 From SQL text to rows: the PostgreSQL query pipeline

  1. Parse the SQL into a parse tree; analyse it (resolve names, types, functions).
  2. Rewrite using rules (views are expanded here).
  3. Plan: generate access paths for each relation; for joins, explore join orders by dynamic programming (or, beyond geqo_threshold tables, a genetic algorithm); estimate costs from statistics and cost parameters (seq_page_cost, random_page_cost, cpu_tuple_cost, effective_cache_size…); choose the cheapest plan.
  4. Execute the plan tree using the Volcano/iterator model: each node pulls rows from its children.

Statistics are gathered by ANALYZE (run by autovacuum) from a random sample: per column, the fraction of nulls, number of distinct values, most common values with frequencies, a histogram of the rest, and the physical-order correlation. Since columns are assumed independent, correlated predicates (city = 'Paris' AND country = 'FR') are underestimated; CREATE STATISTICS (extended statistics: dependencies, n-distinct, MCV lists over column groups) fixes this. Prepared statements (which JDBC drivers use) may switch from custom plans to a cached generic plan after five executions if the generic plan's estimated cost is not much worse; with highly skewed parameters this can produce a plan that is terrible for some values (plan_cache_mode controls it).

4.6 How Hibernate produces N+1

Loading 50 Order entities with findAll() issues one query. Each Order has a lazy @ManyToOne Customer represented by a proxy and a lazy @OneToMany collection of OrderLines represented by a PersistentBag. When serialisation or a loop touches order.getCustomer().getName() and order.getLines(), each uninitialised proxy and collection triggers its own SELECT: 1 + 50 + 50 = 101 queries, each a network round trip (~0.5 ms or more), so an endpoint that should take 5 ms takes 60+ ms and holds a connection for all of it. (Eager @ManyToOne, the JPA default for to-one associations, does not fix this for queries: JPQL ignores the mapping's fetch type and loads the association with separate selects after the main query.) The fixes (§7.3) all make the number of queries independent of the number of rows: fetch joins, entity graphs, batch fetching (IN lists), or DTO projections.

Reading the diagram: the first question is about transactional and query needs, because that is where relational databases are uniquely strong and the hardest to retrofit. Scale is the second gate, and the answer is usually yes for longer than teams expect. Only when transactions and ad-hoc querying are not central does the dominant access pattern pick a NoSQL family. Many real systems traverse this chart several times, one per domain, ending with a relational system of record plus derived specialised stores.

Reading the diagram: both engines log first for durability; they differ in what happens next. The B+tree mutates pages in place, so each logical write eventually costs a random page write (amortised by checkpoints), and reads go straight to one leaf. The LSM engine never mutates files; writes are cheap and sequential, and the cost moves to background compaction and to reads, which may consult several structures. Bloom filters are what make LSM point reads competitive. The right engine depends on whether your workload is read-dominated with updates (B+tree) or write-dominated, append-heavy, and possibly larger than memory (LSM).

What to try: insert sequential keys (1, 2, 3, …) with a small order and watch splits always happen at the rightmost leaf, which leaves earlier leaves half full; this mirrors what happens with sequence or UUIDv7 primary keys (PostgreSQL and InnoDB both optimise the rightmost-split case to fill pages more fully). Then insert random keys: splits happen everywhere, mirroring UUIDv4 keys and their poorer page fill and cache locality. Increase the order and observe how few levels are needed for many keys; real database pages have orders in the hundreds, which is why a billion-row index is only about four levels deep.

Reading the diagram: each transaction reads a consistent snapshot and updates a different row, so snapshot isolation sees no write-write conflict and both commit, violating the invariant. Under Serializable, PostgreSQL's SSI notices that each transaction read data the other wrote (a rw-antidependency cycle) and aborts one with a serialization failure. The application must retry, which is why using Serializable requires a retry loop around the transaction (§7.4). Alternatives: lock the rows that represent the invariant with SELECT ... FOR UPDATE, or materialise the invariant into a row both transactions must update.

Reading the diagram: statistics feed the planner's row-count estimates, which feed costs, which choose access paths and join strategies. If the estimate for status='PENDING' is wrong by 1,000x (stale statistics after a bulk update, or skew the histogram misses), every downstream choice can be wrong: a nested loop where a hash join was needed, a sequential scan where an index was ideal. 6. The Math

6.1 B+tree height and lookup cost

With page size \(P\), key-plus-pointer size \(s\), fanout \(F \approx P/s\) and \(N\) keys, height is about \(\lceil \log_F N \rceil\). For 8 KB pages and 16-byte entries (8-byte key + overhead), \(F \approx 500\) (in practice less after headers and fill factor, say 300). Then \(300^3 = 2.7\times10^7\) and \(300^4 = 8.1\times10^9\): four levels index eight billion keys. The root and second level (1 + 300 pages ≈ 2.4 MB) are always cached; the third level (90,000 pages ≈ 700 MB) usually is; so a point lookup costs about one or two physical reads in the worst case.

6.2 Amplification in LSM compaction

Leveled with size ratio \(T\) (typically 10) and \(L\) levels: each byte is rewritten about \(T\) times per level as it is merged down, so write amplification \(\approx T \cdot L\) in the worst case (often half that in practice); space amplification \(\approx 1 + 1/T\) (about 1.1); point-read amplification about one file per level, mostly eliminated by Bloom filters. Tiered with \(T\) runs per tier: write amplification \(\approx L\) (each byte rewritten once per tier); space amplification up to \(T\) in the worst case for overwrite-heavy data; more runs to check per read. Example: 1 TB of data, \(T = 10\), memtable/L1 base of 256 MB gives \(L \approx \log_{10}(10^{12}/2.56\times10^8) \approx 3.6\), so 4 levels: leveled write amplification up to ~40x versus tiered ~4x. This is why tiered/universal compaction is chosen for write-dominated workloads and leveled for read- and space-sensitive ones.

6.3 Bloom filters

A Bloom filter of \(m\) bits with \(k\) hash functions holding \(n\) keys has false-positive probability

\[ p \approx \left(1 - e^{-kn/m}\right)^k \]

minimised at \(k = \frac{m}{n}\ln 2\), giving \(p \approx 0.6185^{m/n}\). Bits per key for a target \(p\): \(\frac{m}{n} = -\frac{\ln p}{(\ln 2)^2} \approx 1.44\log_2(1/p)\). For 1% false positives: about 9.6 bits per key and 7 hash functions; for 0.1%: about 14.4 bits per key. One billion keys at 1% costs about 1.2 GB of filter memory, which is why RocksDB lets you tune bits per key and skip filters on the last level.

6.4 Selectivity and when an index is worth it

An index scan reads \(\sigma N\) rows via random access (cost per row roughly random_page_cost if not cached), while a sequential scan reads all \(N/r\) pages sequentially (\(r\) rows per page). With PostgreSQL's default random_page_cost = 4 and seq_page_cost = 1, an index scan fetching one page per row beats a sequential scan only if \(4\sigma N < N/r\), i.e. \(\sigma < \frac{1}{4r}\). With 100 rows per page that is \(\sigma < 0.25\%\). Bitmap heap scans (which sort row locations by page) widen this range, and on SSDs many teams lower random_page_cost to about 1.1–2. The intuition holds: indexes win for selective predicates; for predicates matching a large fraction of the table, a sequential scan is correct, not a planner bug.

6.5 Join costs

With outer size \(N\), inner size \(M\): nested loop with index on inner: \(O(N \log M)\); nested loop without index: \(O(NM)\); hash join: \(O(N + M)\) time with \(O(\min(N,M))\) memory; merge join: \(O(N \log N + M \log M)\) if sorting is needed, \(O(N + M)\) if inputs are pre-sorted. A planner mis-estimate that predicts \(N = 10\) but gets \(N = 10^6\) turns a nested loop from 10 index lookups into a million.

6.6 Offset versus keyset pagination

Offset page \(p\) of size \(s\) costs \(O(\log N + (p+1)s)\) rows processed; keyset costs \(O(\log N + s)\) for every page. Fetching all pages of \(N\) rows by offset costs \(\sum_{p=0}^{N/s} (p+1)s \approx \frac{N^2}{2s}\): quadratic. For \(N = 10^6\) and \(s = 100\), that is \(5\times10^9\) rows processed versus \(10^6\) with keyset, a 5,000x difference, which is why offset-based exports and sync jobs time out on large tables.

6.7 Pool sizing

Application side (Little's Law): \(c = \lambda \times t_{hold}\). Database side: useful concurrency is bounded by the server's cores and I/O parallelism. HikariCP's guidance \((\text{cores} \times 2) + \text{effective spindles}\) for a 16-core database server with SSD storage suggests on the order of 30–40 total active connections doing work concurrently. With 20 application instances, that is about 2 per instance actively executing at once, which is why pools of 10 per instance with short transactions perform better than pools of 100. If \(\lambda t_{hold}\) exceeds what the database can execute concurrently, the fix is shorter hold times (faster queries, no remote calls inside transactions), caching, or read replicas, not a bigger pool.

CREATE TABLE customers (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    email       text NOT NULL,
    tier        text NOT NULL DEFAULT 'STANDARD',
    deleted_at  timestamptz
);

CREATE TABLE orders (
    id           uuid PRIMARY KEY DEFAULT uuidv7(),   -- PostgreSQL 18+: time-ordered UUIDs

    status       text   NOT NULL,
    total_cents  bigint NOT NULL,
    created_at   timestamptz NOT NULL DEFAULT now(),
    attrs        jsonb  NOT NULL DEFAULT '{}'
);

-- Case-insensitive unique email among non-deleted customers: expression + partial
CREATE UNIQUE INDEX customers_email_live_uq
    ON customers (lower(email)) WHERE deleted_at IS NULL;

-- INCLUDE makes the list query index-only (no heap fetch for these columns).
CREATE INDEX orders_customer_created_idx
    ON orders (customer_id, created_at DESC, id DESC) INCLUDE (status, total_cents);

-- Work queue: only a tiny fraction of rows are PENDING; index just those
CREATE INDEX orders_pending_idx ON orders (created_at) WHERE status = 'PENDING';

-- jsonb containment queries: attrs @> '{"channel":"mobile"}'
CREATE INDEX orders_attrs_gin ON orders USING gin (attrs jsonb_path_ops);

-- Huge append-only audit table queried by time range: BRIN is kilobytes, not gigabytes
CREATE TABLE order_events (
    order_id   uuid NOT NULL,
    occurred_at timestamptz NOT NULL,
    payload    jsonb NOT NULL
);
CREATE INDEX order_events_time_brin ON order_events USING brin (occurred_at);

-- No double-booking: exclusion constraint on overlapping ranges (GiST)
CREATE EXTENSION IF NOT EXISTS btree_gist;
CREATE TABLE room_bookings (
    room_id  bigint NOT NULL,
    during   tstzrange NOT NULL,
    EXCLUDE USING gist (room_id WITH =, during WITH &&)
);

7.4 Serializable transactions with retry

Using Serializable (or Repeatable Read in PostgreSQL) means some transactions will fail with SQLSTATE 40001 and must be retried from the beginning. The retry must wrap the transaction boundary, not run inside it.

package com.example.oncall;

import org.springframework.dao.ConcurrencyFailureException;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.TransactionDefinition;
import org.springframework.transaction.support.TransactionTemplate;

import java.util.concurrent.ThreadLocalRandom;

@Service
public class OnCallService {

    private final JdbcTemplate jdbc;
    private final TransactionTemplate serializable;

    public OnCallService(JdbcTemplate jdbc, TransactionTemplate template) {
        this.jdbc = jdbc;
        this.serializable = new TransactionTemplate(template.getTransactionManager());
        this.serializable.setIsolationLevel(TransactionDefinition.ISOLATION_SERIALIZABLE);
    }

    public void goOffCall(long doctorId, long shiftId) throws InterruptedException {
        for (int attempt = 1; ; attempt++) {
            try {
                serializable.executeWithoutResult(status -> {
                    Integer onCall = jdbc.queryForObject(
                            "select count(*) from doctors where shift_id = ? and on_call", Integer.class, shiftId);
                    if (onCall == null || onCall < 2) throw new IllegalStateException("last doctor on call");
                    jdbc.update("update doctors set on_call = false where id = ?", doctorId);
                });
                return;
            } catch (ConcurrencyFailureException e) {   // Spring translates SQLSTATE 40001/40P01 here
                if (attempt >= 5) throw e;
                Thread.sleep(ThreadLocalRandom.current().nextLong(5, 20L * attempt)); // jittered backoff
            }
        }
    }
}

PAGE_SQL = """
SELECT id, status, total_cents, created_at
FROM orders
WHERE customer_id = %(cid)s
  AND (%(after_ts)s::timestamptz IS NULL OR (created_at, id) < (%(after_ts)s, %(after_id)s))

8. Real-World Applications

  • Systems of record (orders, payments, accounts, entitlements) on PostgreSQL or MySQL with strict constraints, optimistic locking and carefully chosen isolation; financial invariants enforced by atomic SQL updates or Serializable transactions with retries.
  • Polyglot read models: the relational store feeds, via CDC and Kafka, a search index (OpenSearch), a cache (Redis), a warehouse (BigQuery, Snowflake, ClickHouse) and a vector index for RAG. Each derived store is optimised for one access pattern and can be rebuilt from the log.
  • Messaging and activity data on wide-column stores partitioned by conversation or entity and clustered by time (Discord, §9.2).
  • Queue-like tables in PostgreSQL using partial indexes and SELECT ... FOR UPDATE SKIP LOCKED to let many workers claim jobs without blocking each other; a pragmatic alternative to a broker at moderate volume.
  • Time-series and logs in partitioned tables with BRIN indexes or TimescaleDB hypertables, with partitions dropped for retention instead of mass DELETE.
  • Multi-tenant SaaS with a tenant_id leading every composite index and row-level security policies enforcing isolation in the database.
  • AI retrieval: pgvector HNSW indexes on embedding columns next to relational metadata, enabling filtered similarity search in one SQL query; or a dedicated vector store when scale demands it.
  • Performance engineering: teams run weekly reviews of pg_stat_statements top queries by total time, track index usage (pg_stat_user_indexes.idx_scan) to drop unused indexes, and gate migrations with EXPLAIN checks in CI against production-like statistics.

9. Case Studies

9.1 Uber: storage-engine internals decide a migration

Verified Uber's 2016 post Why Uber Engineering Switched from Postgres to MySQL attributes the move to properties of PostgreSQL's on-disk design as of the 9.2 series: because every index points directly at physical tuple locations and updates create new tuple versions, an update to a heavily indexed table rewrites entries in all indexes (write amplification); the physical WAL carried those amplified changes to replicas (replication bandwidth); replica MVCC interactions caused query cancellations; and major-version upgrades were difficult. It contrasts InnoDB's clustered primary key with secondary indexes referencing the primary key. The post itself notes it reflects an older PostgreSQL version, and many of the issues have since been mitigated (HOT updates existed already and are tunable with fillfactor; logical replication arrived in PostgreSQL 10; upgrade tooling improved). The durable lesson is the one this chapter's §4 teaches: the storage engine's representation of rows and indexes determines write amplification and replication cost, and those must be matched to the workload's update pattern.

9.2 Discord: matching the store to the access pattern

Verified Discord has published two posts on message storage. The 2017 post How Discord Stores Billions of Messages explains moving messages from MongoDB to Cassandra, modelling messages as partitions keyed by channel and a time bucket, clustered by a Snowflake-style message ID so that reading the latest messages in a channel is a single-partition, sorted read. The 2023 post How Discord Stores Trillions of Messages describes problems at larger scale (hot partitions from very busy channels, unpredictable latency, and costly maintenance such as compaction and garbage-collection pauses on a cluster of well over a hundred Cassandra nodes) and the migration to ScyllaDB fronted by Rust "data services" that coalesce concurrent requests for the same data, with a substantially smaller cluster and improved tail latency. Lessons: wide-column stores excel when the partition key matches the dominant read; partition sizing must anticipate skew; and the operational characteristics of the engine (GC, compaction) matter as much as its data model.

9.3 Meta: LSM-trees for space efficiency (MyRocks)

Verified The PVLDB 2020 paper MyRocks: LSM-Tree Database Storage Engine Serving Facebook's Social Graph (Matsunobu, Dong and Lee) describes replacing InnoDB with a RocksDB-based storage engine for MySQL in Facebook's user database tier, motivated primarily by space and write efficiency on flash storage: LSM compression and the absence of B+tree page fragmentation substantially reduced the storage footprint, and lower write amplification extended flash endurance, while keeping MySQL's SQL layer and replication. It is the clearest published example of the amplification trade-offs in §3.7 and §6.2 driving a production engine choice at large scale.

11. Engineering Trade-offs

11.1 B+tree or LSM?

WorkloadPreferWhy
Read-heavy OLTP with point and range reads, moderate writesB+treePredictable one-path reads; mature tooling
Write-heavy, append-mostly (events, telemetry, messages)LSMSequential writes, low write amplification with tiering
Storage cost dominates (huge datasets on flash)LSM (leveled + compression)Low space amplification, compression
Strict, low tail read latencyB+tree (or LSM with careful tuning)Compaction can cause latency variance

11.2 Isolation level choice

Default to Read Committed (PostgreSQL) or Repeatable Read (MySQL) and protect specific invariants explicitly: optimistic locking for entity updates, atomic SQL for counters, unique and exclusion constraints for uniqueness and non-overlap, SELECT ... FOR UPDATE for small critical sections. Use Serializable for complex invariants that span rows and are hard to reason about, accepting retries and some throughput loss. Opinion Serializable is under-used: correctness bugs from write skew are rare but expensive, and a retry loop is cheap.

11.3 Normalise or denormalise?

Normalise the system of record so each fact has one home; denormalise in derived read models (caches, search documents, materialised views, columns maintained by triggers or events) where a hot query needs it. Denormalising in the system of record trades read cost for update anomalies and must be justified by measured read pressure.

11.4 When to add an index

Add an index when a frequent or latency-critical query needs it and EXPLAIN confirms it will be used. Prefer extending an existing composite index (or adding INCLUDE columns) over adding a new one. On write-heavy tables, every index costs on every insert and update; measure write latency after adding. Remove indexes with zero scans over a representative period (taking care of indexes that back constraints or rare but critical queries).

12. Common Mistakes and Production Failures

  • Composite index in the wrong order. (created_at, customer_id) for WHERE customer_id = ? ORDER BY created_at forces scanning by time across all customers. Equality first, then range/sort.
  • Functions on indexed columns. WHERE lower(email) = ? or WHERE date(created_at) = ? cannot use a plain index on the column; use an expression index or rewrite as a range.
  • Implicit casts. Comparing a varchar column with a numeric parameter (common in MySQL) or mismatched types from JPA parameter binding prevents index use.
  • Leading wildcards. LIKE '%term%' cannot use a B-tree; use trigram GIN or a search engine.
  • N+1 and open-in-view. Lazy loading during JSON serialisation issues hundreds of queries per request and holds connections for the whole request.
  • Fetch-joining collections with pagination. Hibernate warns "firstResult/maxResults specified with collection fetch; applying in memory" and loads everything.
  • Huge pools. 100 connections × 40 pods = 4,000 PostgreSQL backends; memory exhaustion and contention. Small pools plus a server-side pooler.
  • Remote calls inside transactions. Calling an HTTP service or LLM while holding a transaction holds locks and a connection for seconds; move remote calls outside, or use the outbox pattern (Chapter 6).
  • Long-running transactions (including idle-in-transaction sessions from leaked connections) block vacuum/purge, causing bloat and degraded performance across the database.
  • Assuming MySQL Repeatable Read equals PostgreSQL Repeatable Read. Locking reads in InnoDB see the latest data, not the snapshot; logic that mixes plain and locking reads can behave unexpectedly.
  • Random UUIDv4 primary keys in InnoDB causing page splits, fragmented clustered indexes and poor buffer-pool hit ratios; prefer UUIDv7 or sequences.
  • Mass deletes for retention. DELETE FROM events WHERE created_at < … on billions of rows generates huge WAL, bloat and replication lag; partition by time and drop partitions.
  • Adding indexes or columns with blocking DDL on hot tables; use CONCURRENTLY, online DDL, or tools like gh-ost/pt-online-schema-change for MySQL.
  • Choosing NoSQL to avoid schema design, then discovering a need for ad-hoc queries and multi-entity invariants.

13. Production Engineering

13.1 Performance and monitoring

  • Enable pg_stat_statements (or MySQL Performance Schema/sys schema) and review top queries by total time, mean time and calls; set auto_explain with a threshold for slow queries in production.
  • Monitor: transactions per second, active versus idle connections, lock waits and deadlocks, replication lag, cache hit ratio of the buffer pool, checkpoint frequency, WAL generation rate, autovacuum activity, dead tuples and table bloat, oldest transaction age, and XID age (wraparound risk).
  • Application side: Hikari pending threads and acquisition time, query latency histograms per repository method (Micrometer observations for Spring Data), and query counts per request.

13.2 Reliability

  • Point-in-time recovery from continuous WAL archiving plus base backups; test restores regularly and measure RTO.
  • Statement and lock timeouts (statement_timeout, lock_timeout, idle_in_transaction_session_timeout) as guardrails; migrations set a short lock_timeout and retry so they never queue behind a long transaction while blocking everything behind them.
  • Capacity: track storage growth and IOPS headroom; plan vertical scaling or partitioning (Chapter 5) well before limits.

13.3 Security

  • Parameterised queries everywhere (JPA, JdbcTemplate, psycopg, pgx all parameterise by default; beware string concatenation in native queries and dynamic ORDER BY columns, which must be allow-listed).
  • Least-privilege roles: the application role cannot alter schema; migrations run with a separate role; read-only roles for replicas and analytics.
  • TLS to the database, encryption at rest, secrets from a vault with rotation; row-level security for multi-tenant isolation where appropriate; audit logging for sensitive tables.

13.4 Maintainability

  • Version all schema changes (Flyway/Liquibase), use expand-and-contract migrations for zero-downtime changes (add nullable column → backfill → switch reads → enforce constraint → drop old), and review migrations for locking behaviour.
  • Document access patterns next to each index so future engineers know why it exists.

14. Exercises

Exercise 1 · Foundational

Given an index on (tenant_id, status, created_at), which of these queries can use it efficiently as a range scan? (a) WHERE tenant_id = 7; (b) WHERE status = 'OPEN'; (c) WHERE tenant_id = 7 AND created_at > now() - interval '1 day'; (d) WHERE tenant_id = 7 AND status = 'OPEN' ORDER BY created_at DESC LIMIT 50.

Solution

(a) Yes, leftmost prefix. (b) Not efficiently (not a leftmost prefix; possibly a full index scan or, with few tenants, a skip scan in PostgreSQL 18+/MySQL 8). (c) Partially: the index narrows to tenant 7, but created_at follows status, so all statuses for the tenant are scanned and filtered by time (or skip-scanned over the few status values). An index on (tenant_id, created_at) would be better. (d) Yes, ideal: equality on the first two columns, then the index already provides created_at order, so the database reads 50 entries and stops.

Exercise 2 · Intermediate

A Spring service decrements inventory with: load entity, check qty > 0, set qty = qty - 1, save. Under load, inventory goes negative on PostgreSQL with default settings. Explain why and give three fixes with trade-offs.

Solution

Read Committed allows lost updates and check-then-act races: two transactions read qty = 1, both pass the check, both write 0 (lost update) or, with relative updates computed in Java, the check is stale. Fixes: (1) atomic SQL UPDATE inventory SET qty = qty - 1 WHERE sku = ? AND qty > 0 and check the affected row count: fastest, no retries, logic in SQL. (2) @Version optimistic locking with retry on OptimisticLockException: keeps logic in Java, retries under contention (bad for very hot SKUs). (3) SELECT ... FOR UPDATE (@Lock(PESSIMISTIC_WRITE)): serialises access per row, simple, but holds locks for the transaction's duration and can deadlock if rows are locked in different orders. Add a CHECK (qty >= 0) constraint as a backstop in all cases.

Exercise 3 · Intermediate

An admin endpoint lists orders with Pageable and is fast on page 1 but takes 9 seconds on page 4,000 (page size 50). EXPLAIN ANALYZE shows an index scan returning 200,050 rows into a Limit node. Explain and fix, including the count query.

Solution

Offset pagination: page 4,000 requires reading and discarding 199,950 rows. Spring Data's Page also runs COUNT(*) over the filtered set each time. Fix: switch to keyset scrolling (Window + ScrollPosition.keyset()) with a unique sort key (created_at, id) and a matching composite index; return Slice/Window (has-next) instead of Page to avoid the count, or show an approximate count from statistics (pg_class.reltuples) or a cached count. If deep random access is truly required, cap the maximum offset and offer filters instead.

Exercise 4 · Advanced

A query joining orders (50M rows) to customers (2M) filtered by orders.status = 'DISPUTED' AND orders.region = 'EU' uses a nested loop and takes 40 s. EXPLAIN ANALYZE shows the outer node estimated at 120 rows but actually returning 380,000. Diagnose and propose fixes.

Solution

Cardinality misestimate: the planner multiplies the selectivities of status and region as if independent, but disputes are concentrated in the EU (correlated), or statistics are stale after a bulk status change. Underestimating the outer side makes a nested loop with 380,000 inner index probes look cheap. Fixes: run ANALYZE orders (and check autovacuum/analyze thresholds for this table); add extended statistics CREATE STATISTICS ... (dependencies, mcv) ON status, region FROM orders; raise the per-column statistics target for skewed columns; consider a partial or composite index on (status, region). With correct estimates the planner should choose a hash join. Avoid planner hints/disabling nested loops globally; fix the estimate.

Exercise 5 · Advanced (design)

Choose storage for a support platform with: tickets and their state machine (strong consistency), comments (append-heavy, 2B rows/year), full-text search across tickets and comments, AI "similar tickets" suggestions, and SLA analytics dashboards. Justify each choice and how data flows between stores.

Solution

Tickets: PostgreSQL system of record, constraints for state transitions, optimistic locking. Comments: PostgreSQL table partitioned by month (2B rows/year is about 63 inserts/s average, fine for PostgreSQL), indexed on (ticket_id, created_at); old partitions detached to cheaper storage. A wide-column store is only justified if write rates are orders of magnitude higher. Search: OpenSearch index fed by CDC (Debezium → Kafka → indexer), eventually consistent within seconds. Similar tickets: embeddings generated asynchronously from the same CDC stream and stored with pgvector (HNSW) alongside ticket metadata, enabling filtered similarity in SQL; move to a dedicated vector store only if scale demands. Analytics: CDC into a columnar warehouse; dashboards never query the OLTP primary. All derived stores can be rebuilt from the primary plus the log.

15. Interview Questions and Answers

Conceptual Explain write skew and how PostgreSQL's Serializable level prevents it.

Write skew: two transactions read overlapping data, make decisions based on it, and write disjoint rows, jointly violating an invariant (two doctors both going off call). Snapshot isolation does not detect it because there is no write-write conflict. PostgreSQL's SSI tracks read-write dependencies via predicate (SIRead) locks; when it detects a pattern of two consecutive rw-antidependencies that could form a cycle, it aborts one transaction with SQLSTATE 40001. Applications must retry.

Conceptual Compare B+tree and LSM-tree storage engines.

B+trees update pages in place: fast, predictable reads (a few page reads), random writes and page-level write amplification. LSM-trees buffer writes in memory and flush immutable sorted files, merging them by compaction: fast sequential writes, reads may consult several files (mitigated by Bloom filters), background compaction costs I/O. Compaction strategy trades write versus read versus space amplification (leveled: low read/space, high write; tiered: the opposite). Choose B+tree for read-heavy OLTP, LSM for write-heavy or storage-sensitive workloads.

Conceptual What is the leftmost-prefix rule, and how do you order columns in a composite index?

A B-tree on (a, b, c) is sorted lexicographically, so it efficiently supports predicates constraining a leading prefix of the columns. Put equality-filtered columns first, then the column used for a range or ORDER BY; include extra selected columns (INCLUDE or trailing) for index-only scans. A range on an early column stops later columns from narrowing the scan. Skip scan can help when a leading column has few distinct values.

Coding Fix this N+1: an endpoint returns 100 orders with customer names and line counts.

Write a DTO projection query that joins and aggregates in one statement: select new OrderRow(o.id, c.name, count(l)) from Order o join o.customer c left join o.lines l where ... group by o.id, c.name order by ..., with keyset pagination. Alternatively a fetch join for the to-one customer plus @BatchSize/default_batch_fetch_size for lines, giving 1 + ceil(100/50) queries. Disable open-in-view and add a test asserting the statement count.

Architecture When would you choose Cassandra over PostgreSQL?

When the workload is dominated by very high write throughput on data naturally partitioned by a key and read along that key (messages per channel, events per device), needs multi-datacenter active-active replication with tunable consistency, and does not need joins, ad-hoc queries or multi-partition transactions; and when the team can model tables per query and operate compaction and repairs. Otherwise PostgreSQL (possibly partitioned or sharded) is simpler and more flexible.

Scenario PostgreSQL disk usage keeps growing although row count is flat, and queries slow down. What do you look for?

Bloat from dead tuples: check pg_stat_user_tables (n_dead_tup, last autovacuum), the oldest running transaction (pg_stat_activity, especially idle in transaction), stale replication slots holding back the xmin horizon, and long-running queries on replicas with hot_standby_feedback. Fix the blocker, tune autovacuum per table (lower scale factors for big hot tables), and reclaim space with pg_repack or partition rewrites if needed (plain VACUUM does not return space to the OS except at the end of a table; VACUUM FULL locks the table).

Scenario After a deploy, a query that took 5 ms now takes 2 s for some customers only. Nothing in the SQL changed. What could it be?

A generic-plan switch for prepared statements: after several executions, a cached generic plan chosen for average selectivity is used for all parameters, and it is terrible for large customers (skew). Or statistics changed after an analyze. Check EXPLAIN (ANALYZE) with the specific parameter, pg_stat_statements for the query, and plan_cache_mode; fixes include plan_cache_mode = force_custom_plan for that query/role, extended statistics, or restructuring the query.

Conceptual How do you size a HikariCP pool?

From both sides: the database can usefully run about cores × 2 (+ I/O parallelism) queries at once in total, which bounds the sum of all pools; Little's Law gives per-instance needs (query rate × hold time). Use fixed-size small pools (often 5–20), short connection timeouts, statement timeouts, keep transactions short and free of remote calls, and add PgBouncer/RDS Proxy when many instances share a database. Validate with load tests watching pending threads.

Architecture How would you add semantic search to an existing PostgreSQL-backed product?

Add an embedding column (pgvector) to a table or side table, populate it asynchronously from CDC or an outbox event (embedding calls are slow and fallible), create an HNSW index with the distance operator matching the embedding model, and query with metadata filters plus ORDER BY embedding <=> :q LIMIT k, ideally combined with full-text search (hybrid retrieval). Track embedding model version per row for re-embedding. Move to a dedicated vector store if scale, latency or filtering needs exceed what pgvector delivers.

16. Knowledge Check

  • Select databases from access patterns, transactional needs and scale, with a relational system of record as the default and derived specialised stores fed by CDC.
  • Isolation levels differ by engine: PostgreSQL defaults to Read Committed (Repeatable Read is snapshot isolation; Serializable is SSI); MySQL defaults to Repeatable Read with next-key locking. Lost updates and write skew need explicit handling.
  • PostgreSQL MVCC keeps versions in the heap and needs vacuum; InnoDB updates in place with undo logs and a clustered primary key.
  • B+trees favour reads; LSM-trees favour writes; compaction strategy trades write, read and space amplification; Bloom filters make LSM point reads cheap.
  • Index by query: equality columns first, then range/sort; use partial, expression, covering, GIN, GiST and BRIN indexes where they fit; verify with EXPLAIN (ANALYZE, BUFFERS).
  • Most slow plans are misestimates; fix statistics before forcing plans.
  • Eliminate N+1 with fetch joins, entity graphs, batch fetching or DTO projections; keep pools small; paginate with keysets.

Which anomaly is still possible under PostgreSQL Repeatable Read?

  1. Dirty read
  2. Non-repeatable read of a single row
  3. Write skew
  4. Lost update on the same row (both commit)
Repeatable Read in PostgreSQL is snapshot isolation: it prevents dirty and non-repeatable reads and aborts concurrent updates to the same row (40001), but write skew across different rows requires Serializable.

An index exists on (customer_id, created_at). Which query benefits most?

  1. WHERE created_at > now() - interval '1 hour'
  2. WHERE customer_id = 42 ORDER BY created_at DESC LIMIT 20
  3. WHERE lower(customer_name) = 'ada'
  4. WHERE created_at::date = current_date
Equality on the leading column plus ordering by the second column is served directly by the index order, stopping after 20 entries.

Approximately how many bits per key does a Bloom filter need for a 1% false-positive rate?

  1. About 10
  2. About 1
  3. About 64
  4. It depends on the key size
m/n = −ln p / (ln 2)² ≈ 9.6 bits per key, with k ≈ 7 hash functions, independent of key size.

Which index type suits a 5 TB append-only events table queried by time range?

  1. Hash
  2. GIN
  3. GiST
  4. BRIN
BRIN stores min/max per block range; when values correlate with physical order (append-only timestamps), it prunes most blocks with a tiny index.

EXPLAIN ANALYZE shows a nested loop whose outer node is estimated at 50 rows but returns 500,000. What is the most likely root cause?

  1. The nested loop algorithm is broken
  2. A cardinality misestimate from stale or insufficient statistics (e.g. correlated predicates)
  3. The connection pool is too small
  4. The query lacks a LIMIT
The planner chose nested loop because it believed the outer side was tiny. Refresh statistics, add extended statistics, or raise the statistics target so it can choose a hash join.

Why does keyset pagination outperform OFFSET for deep pages?

  1. It caches previous pages in the database
  2. It avoids sorting entirely
  3. It seeks directly to the last-seen key in an index instead of producing and discarding all earlier rows
  4. It uses a hash index
Each keyset page costs an index seek plus the page size; OFFSET costs grow linearly with page depth.
